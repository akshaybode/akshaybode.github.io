AWS CloudFormation

CloudFormation lets you define and provision AWS infrastructure as code (IaC). A template describes the desired state; CloudFormation creates, updates and deletes the resources as a single unit called a stack. For a data engineer this is how you reproducibly stand up the S3 landing zone, Glue catalog objects and crawlers that every lab in this course assumes.

Templates and template sections

A CloudFormation template is a YAML or JSON text file describing the desired state. Only Resources is mandatory; the other sections make templates reusable and flexible.

MappingsStatic lookup tables keyed by a parameterRegion → S3 endpoint, or env → retention days

ResourcesAWS resources to create — the only required sectionAWS::S3::Bucket, AWS::Glue::Database, AWS::Glue::Crawler
OutputsValues exported after stack creationBucket ARN, crawler name — consumed by other stacks or CI/CD

Stacks, change sets and drift

  • Change sets preview what an update will do before you apply it — essential before touching a production crawler or bucket policy.
  • Drift detection compares the stack's template to the actual resource configuration. If someone changed a bucket policy in the console, drift detection flags it.
  • Nested stacks let a parent template call child templates — useful when your data platform has separate modules for networking, storage and compute.
  • StackSets deploy the same stack across multiple accounts and regions from a management account — common in enterprise landing zones.
  • Rollback behaviour: by default a failed CREATE rolls back (deletes partial resources). A failed UPDATE rolls back to the previous known-good state. You can disable rollback for debugging, but you then inherit a broken partial stack.
CloudFormation vs other IaC on the exam. CloudFormation is native, free (you pay for the resources), and integrates with StackSets and drift detection. CDK synthesises CloudFormation. Terraform is third-party state. When the question says "AWS-native IaC with rollback and drift detection", the answer is CloudFormation.

Amazon CloudWatch

CloudWatch is AWS's proprietary monitoring service for applications and resources in real time. Metrics appear on dashboards; logs consolidate in log groups; alarms trigger actions when thresholds breach. Every data pipeline you build in this course should emit something CloudWatch can see.

Metrics: namespaces, dimensions and resolution

  • Standard resolution: one data point per minute — default for AWS service metrics and free-tier custom metrics.
  • High resolution: one data point per second — costs more, needed for sub-minute alerting on custom metrics.
  • Statistics: Average, Sum, Minimum, Maximum, SampleCount — aggregated over the chosen period.
aws cloudwatch put-metric-data \
  --namespace "DEA/DataPipeline" \
  --metric-data '[{
    "MetricName": "RowsProcessed",
    "Dimensions": [{"Name": "JobName", "Value": "customers-etl"}],
    "Timestamp": "2026-08-03T12:00:00Z",
    "Value": 10482,
    "Unit": "Count",
    "StorageResolution": 60
  }]'

EventBridge vs CloudWatch Alarms for pipeline failures. CloudWatch Alarms watch metrics — numeric time series. EventBridge reacts to events — structured state changes such as "Glue job X failed" or "Step Functions execution timed out". Glue job failure notification is an EventBridge pattern, not a native CloudWatch metric alarm, because Glue publishes job state as events. Use alarms for continuous numeric thresholds (iterator age, error rate, disk usage); use EventBridge for discrete lifecycle events.

CloudWatch Logs

Logs Insights query syntax

Logs Insights is an interactive query language over log groups. Queries run server-side — you pay per GB scanned, not per log group size.

fields @timestamp, @message
| filter @message like /ERROR/
| parse @message /\[*\] *(?<errorMsg>.*)/
| filter @logStream like /customers-etl/
| stats count() as errorCount by errorMsg
| sort errorCount desc
| limit 20

Common Insights commands: fields selects columns; filter keeps matching rows; parse extracts structured fields with regex; stats aggregates; sort and limit shape the result. Run this from CloudWatch → Logs → Logs Insights, selecting /aws-glue/jobs/output and /aws-glue/jobs/error.

Cross-account log delivery

  1. Create a Kinesis Data Stream in the destination account.
  2. Create an IAM role in the destination account with a trust policy allowing logs.<region>.amazonaws.com from the source account, plus a policy granting kinesis:PutRecord.
  3. In the source account, create a subscription filter on the log group pointing to the destination stream ARN and the cross-account role ARN.
  4. Optionally attach a resource policy on the Kinesis stream granting the source account write access.

AWS CloudTrail

CloudTrail is the audit and governance service that records API activity in your AWS account. Every console click and SDK call that changes state leaves a CloudTrail event. It is enabled by default for management events in the 90-day Event history, but long-term retention and data-level auditing require a trail.

Event types

Data events are off by default — and they are what data engineers need. Management events tell you someone created an S3 bucket; data events tell you someone read or wrote a specific object in that bucket. S3 object-level auditing, Lambda Invoke, and DynamoDB item-level reads all require enabling data events on a trail. They cost extra per event — the exam still expects you to know when they are required.
{
  "ReadWriteType": "All",
  "IncludeManagementEvents": true,
  "DataResources": [{
    "Type": "AWS::S3::Object",
    "Values": [
      "arn:aws:s3:::dea-lab-ab-4821/raw/*",
      "arn:aws:s3:::dea-lab-ab-4821/curated/*"
    ]
  }]
}

Trails

  • S3 delivery: trail log files land in an S3 bucket you designate — typically with lifecycle rules to Glacier for cost.
  • Log file validation: SHA-256 digest files prove logs were not tampered with after delivery.
  • KMS encryption: encrypt trail log files at rest with a CMK you control.
  • CloudWatch Logs integration: ship trail events to a log group for metric filters and near-real-time alerting on API calls (e.g. alert on DeleteBucket).

AWS Config

AWS Config assesses, audits and evaluates the configuration of your AWS resources — not API calls (CloudTrail) and not runtime metrics (CloudWatch). It is disabled by default. When enabled, it records configuration items and evaluates them against rules to produce compliance results.

Core concepts

Config rules

import json

def evaluate_compliance(configuration_item):
    resource_type = configuration_item["resourceType"]
    if resource_type != "AWS::S3::Bucket":
        return "NOT_APPLICABLE"
    encryption = configuration_item.get("configuration", {}).get(
        "serverSideEncryptionConfiguration", {}
    )
    if encryption:
        return "COMPLIANT"
    return "NON_COMPLIANT"

def lambda_handler(event, context):
    invoking_event = json.loads(event["invokingEvent"])
    ci = invoking_event["configurationItem"]
    compliance = evaluate_compliance(ci)
    return {
        "compliance_type": compliance,
        "Annotation": f"Bucket encryption check: {compliance}"
    }

AWS Trusted Advisor

AWS Trusted Advisor inspects your account against AWS best practices and surfaces recommendations in five categories: cost optimisation, performance, security, fault tolerance, and service limits. It is a governance and planning lens, not an audit log — it tells you what to improve, not who changed what.

Support plan access: all accounts get a subset of Trusted Advisor checks for free (core security and service-limit checks). The full catalogue of checks — including most cost optimisation, performance, and fault tolerance recommendations — requires a Business, Enterprise On-Ramp, or Enterprise support plan. Developer and Basic support see fewer checks; exact check counts vary and are listed in the Trusted Advisor console for your plan tier.

The service limits category is especially useful for data platforms: it flags Kinesis shard counts, Lambda concurrency headroom, VPC limits, and other quotas approaching maximum before a pipeline hits a hard wall. Pair those findings with capacity planning and Service Quotas increase requests where limits are soft.

ServiceWhat it doesContrast with Trusted Advisor
Trusted AdvisorBest-practice recommendations (idle resources, open security groups, limit headroom)Point-in-time guidance; no historical configuration timeline
AWS ConfigRecords configuration state over time; evaluates rules for COMPLIANT / NON_COMPLIANTDetective compliance and drift — "is encryption on?" not "you are paying for idle IPs"
Compute OptimizerRightsizing from CloudWatch utilisation metrics (EC2, Lambda, EBS, ECS)Data-driven instance size recommendations — not general best-practice checklists

For a data engineer, Trusted Advisor complements Config conformance packs and Cost Explorer: use Config to enforce encryption and public-access rules, Trusted Advisor to catch under-used Redshift clusters or over-provisioned Kinesis shards, and Compute Optimizer when EMR core nodes or Lambda functions show sustained low CPU.

The confused deputy problem

The confused deputy problem is a cross-service trust attack. You attach a resource-based policy to an IAM role that allows an AWS service principal — for example s3.amazonaws.com or cloudtrail.amazonaws.com — to call sts:AssumeRole. Without extra conditions, any resource in any account that uses that service can trick the service into assuming your role and acting on your resources. A third party creates a CloudTrail trail in their account that points at your role ARN; CloudTrail assumes your role on their behalf and could write to buckets you intended only for your own trails.

The same pattern applies to Glue and Lambda service roles: a bucket policy that trusts glue.amazonaws.com or lambda.amazonaws.com without scoping the calling resource lets a foreign account's job or function invoke your role. See Section 4 — Glue job roles and Section 5 — Lambda execution roles for how those roles are created; the defence lives in the role trust policy and any resource policy that grants cross-account access.

Defence: require aws:SourceArn and aws:SourceAccount in the role trust policy or resource policy so only the specific trail, bucket, job, or function you expect can trigger assumption:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "cloudtrail.amazonaws.com" },
    "Action": "sts:AssumeRole",
    "Condition": {
      "StringEquals": {
        "aws:SourceAccount": "123456789012"
      },
      "ArnLike": {
        "aws:SourceArn": "arn:aws:cloudtrail:us-east-1:123456789012:trail/audit-trail"
      }
    }
  }]
}

Policy evaluation logic

When a request arrives, AWS evaluates every applicable policy type. The rules are deterministic:

  1. Explicit deny in any policy always wins — one Deny overrides any number of Allow statements.
  2. If no explicit deny, there must be an explicit allow from at least one policy or the request is denied by default.
  3. For same-type policies (multiple identity-based policies), the union of allows applies unless a deny exists.
  4. Permission boundaries cap the maximum permissions an identity can receive — common for delegated admin scenarios.
  5. SCPs (Service Control Policies) in AWS Organizations set guardrails at the account or OU level — they filter what identity policies can grant but never grant permissions themselves.
  6. Session policies further restrict temporary credentials when assuming a role — the intersection of role policy and session policy applies.

SCPs never grant — they only filter. An SCP with Effect: Deny on s3:DeleteBucket prevents every identity in the account from deleting buckets, even admins — unless the SCP itself has an exception. An SCP cannot grant S3 access that the identity policy lacks. Exam distractors often show an SCP with Allow and expect you to know it does not work that way.

Permissions boundaries

A permissions boundary is a managed policy attached to an IAM user or role that sets the maximum permissions that identity can ever receive. It grants nothing on its own — there must still be an identity policy (or group policy) that allows the action. Effective permissions are the intersection of the identity policies and the boundary: if the identity policy allows iam:* but the boundary allows only iam:CreateRole and iam:AttachRolePolicy, the identity can create roles but cannot grant itself AdministratorAccess.

Permissions boundaries sit in the evaluation chain after SCPs and before identity policies — see the diagram above. They apply per identity in one account. Contrast with:

  • Service Control Policy (SCP) — organisation-wide guardrail on an OU or account; filters what any identity in that account can be granted, including the root user; never grants permissions.
  • Session policy — passed at AssumeRole time; further restricts the temporary session; intersection of role permissions and session policy applies for that session only.

The standard use case is safe permission delegation: a team lead receives iam:CreateRole, iam:PassRole, and iam:AttachRolePolicy plus a permissions boundary that caps which actions any role they create may perform. They can stand up Glue job roles for their squad without becoming a path to org-wide admin.

Developers must create roles but must not grant more than X. When a scenario says team members need to create IAM roles for Glue or Lambda but cannot escalate beyond a fixed permission set, the answer is a permissions boundary on the delegating identity (or on each created role), not an SCP alone. SCPs limit the whole account; boundaries limit what a specific power-user can delegate.

IAM Access Analyzer

IAM Access Analyzer continuously analyses resource policies (S3 buckets, IAM roles, KMS keys, Lambda functions, SQS queues) and flags resources that are accessible from outside your account or organisation. It uses zone of trust analysis — if a bucket policy grants Principal: "*" or a foreign account access you did not intend, Access Analyzer generates a finding. Use it after deploying a new pipeline to catch overly permissive bucket policies before data leaks.

AWS Organizations and SCPs

AWS Organizations groups multiple accounts under a management account. Service Control Policies attach to the organisation root, an OU, or an individual account. They are the guardrails that prevent junior admins from disabling CloudTrail, creating public S3 buckets, or launching expensive instance types — even if their IAM user has AdministratorAccess. Combine SCPs (what the account can never do) with least-privilege IAM (what each identity should do) for defence in depth.

Traps that catch people

  • CloudFormation import immutability — Resources imported into a stack cannot be updated the same way as created resources. Plan import for migration, not day-two changes.
  • Deleting stack without DeletionPolicy: Retain — Production S3 buckets and DynamoDB tables delete with the stack unless Retain is set on the resource.
  • Drift ignored — Console edits to bucket policies leave CloudFormation blind until drift detection runs — redeploy may overwrite manual fixes.
  • INSUFFICIENT_DATA alarms — New metrics or sparse pipelines keep alarms silent. Set missing-data treatment explicitly.
  • Composite alarm without child alarms — Composite logic references metric alarms that must exist and be in ALARM state.
  • Logs Insights for real-time alerting — Insights is query-on-demand per GB scanned. Use metric filters + alarms for continuous ERROR detection.
  • CloudTrail management-only trail — "Who read object X?" requires S3 data events — management events only show bucket-level API calls.
  • Lambda data events volume — Enabling Invoke data events on high-traffic functions adds cost quickly — scope to specific functions.
  • Missing iam:PassRole — Admin can create Glue jobs but fails without PassRole on the execution role ARN — the permission teams forget.
  • SCP Allow distractor — SCPs never grant access; they only filter what identity policies may allow.
  • Role chaining beyond one hour — Chained AssumeRole sessions cap at one hour even if the target role allows 12 hours.
  • Config rule without recorder — Rules show INSUFFICIENT_DATA if the configuration recorder is off or lacks permission to describe resources.

Production patterns

Data platforms deploy via CloudFormation nested stacks: networking, data stores, and Glue jobs as modules with exported bucket names and role ARNs. CloudWatch dashboards combine Glue job duration, SQS age, and custom RowsProcessed metrics; composite alarms reduce pager noise. Organisation CloudTrail with S3 data events on sensitive prefixes feeds CloudTrail Lake or Athena for audit SQL. Config conformance packs enforce encryption and public-access blocks with optional auto-remediation.

Observability stack

  • Embedded metric format from Lambda/Glue for batch custom metrics.
  • Metric filters on ERROR patterns → alarm → SNS.
  • Logs IA class for verbose job logs after 30 days.

Governance stack

  • Org CloudTrail + Config aggregator across accounts.
  • IAM Access Analyzer on new bucket policies.
  • SCP deny on cloudtrail:StopLogging, public S3 ACLs.

Anti-pattern: enabling every CloudWatch log group at INFO with indefinite retention on high-volume Kinesis consumers — ingestion and storage dominate the bill. Set retention (14–30 days for debug, 90 for audit) and use metric filters for signals, not full-text search on every request.

Where this fits with the rest of the exam

Section 16 underpins every other section: pipelines need IAM roles, CloudWatch alarms, CloudTrail audit, and often CloudFormation deployment. Exam scenarios rarely ask "what is CloudWatch" — they ask which tool detects drift, audits object reads, or denies access.

  • Section 4 — Glue: Glue job roles need PassRole, trust policy for glue.amazonaws.com, and CloudWatch log groups for job output.
  • Section 13 — Lake Formation: LF grants layer on IAM; CloudTrail logs GetDataAccess for audit.
  • Section 15 — Step Functions: Execution failures appear in CloudWatch; state machine role needs least privilege.
  • Section 7 — S3: Bucket policies use aws:SourceArn and aws:PrincipalOrgID for cross-service confused-deputy protection.
  • Section 20 — Security: KMS encryption complements CloudTrail and Config for defence in depth.
  • Section 19 — VPC: VPC Flow Logs to CloudWatch; interface endpoints reduce NAT costs logged separately.
How the exam frames management services. "Detect manual changes to deployed infrastructure" → CloudFormation drift detection. "Who downloaded file X from S3?" → CloudTrail data events. "Alert when ERROR lines spike in Glue logs" → metric filter + alarm, not Logs Insights on a schedule. "Enforce encryption across accounts" → Config conformance pack. "Explicit deny wins" → IAM evaluation — one Deny beats any Allow. Do not pick CloudWatch for audit trails — that is CloudTrail.

Interview questions

Answer each one out loud before opening it.

What is the difference between a CloudWatch metric filter and a subscription filter?Comparison

A metric filter pattern-matches log events and publishes a numeric value to a CloudWatch custom metric. You then alarm on that metric — useful for counting ERROR lines or tracking specific log signatures.

A subscription filter forwards matching (or all) log events to a downstream destination: Kinesis Data Streams, Kinesis Data Firehose, or Lambda. Use it when you need the raw log payload elsewhere — OpenSearch dashboards, S3 archival, or real-time processing — not when you just need a number to alarm on.

CloudTrail management events are enabled by default, but your security team wants S3 object-level auditing. What do you configure?Security

Create or update a CloudTrail trail with a data event selector for AWS::S3::Object, scoped to the bucket ARNs or prefixes you care about. Management events alone never record GetObject, PutObject, or DeleteObject. Data events incur per-event charges but are the only native way to audit object access.

Deliver the trail to an S3 bucket with log file validation enabled, optionally forward to CloudWatch Logs for real-time alerting, and consider CloudTrail Lake if you need SQL queries over months of history.

When would you use EventBridge instead of a CloudWatch Alarm to detect a failed Glue job?Design

Glue publishes job state changes as events (SUCCEEDED, FAILED, TIMEOUT), not as a simple numeric metric you can threshold. EventBridge matches the event pattern {"source":["aws.glue"],"detail-type":["Glue Job State Change"],"detail":{"state":["FAILED"]}} and routes to SNS, Lambda, or Step Functions for remediation.

CloudWatch Alarms are for continuous numeric metrics — iterator age, error counts, disk usage. Use alarms when the signal is a number over time; use EventBridge when the signal is a discrete state transition.

Explain the difference between a Glue service role and a role a data engineer assumes.Fundamentals

A Glue service role is assumed by the Glue service itself (Principal: glue.amazonaws.com). Glue calls sts:AssumeRole on your behalf when a crawler or job runs. Its trust policy names the service; its permission policy grants S3, catalog, and JDBC access the job needs.

A human-assumed role is assumed by a person via the console or CLI (Principal: your IAM user or federated identity). The engineer gets temporary credentials scoped to e.g. Athena query access without admin rights. Mixing these up — putting a human principal in a service role trust policy — is a common deployment error.

What happens during CloudFormation stack rollback on a failed update?Troubleshooting

CloudFormation re-applies the last known-good template state. Resources it created during the failed update are deleted; resources it modified are reverted to their previous configuration. The stack ends in UPDATE_ROLLBACK_COMPLETE — operational again but unchanged from before the update.

If rollback itself fails, the stack enters UPDATE_ROLLBACK_FAILED, which requires manual intervention — often skipping the broken resource or continuing rollback from the console. This is why change sets exist: preview the blast radius before applying.

How does AWS Config differ from CloudTrail?Comparison

CloudTrail records who did what API call when — an audit log of actions. Config records what the resource configuration looks like at each point in time and evaluates it against compliance rules.

Example: CloudTrail shows that alice@company.com called PutBucketPolicy at 14:03. Config shows whether the bucket currently has encryption enabled, public access blocked, and versioning on — and marks it NON_COMPLIANT if a rule is violated.

What does an explicit deny in an IAM policy do to the evaluation result?Exam

An explicit Deny always wins, regardless of how many Allow statements exist across identity policies, resource policies, permission boundaries, or session policies. The only thing that can restrict an SCP deny is an exception within the SCP itself — not an identity policy Allow.

Default is implicit deny: if no statement allows the action, the request fails even without an explicit Deny. This is why least privilege starts from zero permissions and adds only what is needed.

A Kinesis consumer is falling behind and data is going stale. Which CloudWatch metric do you alarm on?Troubleshooting

GetRecords.IteratorAgeMilliseconds in the AWS/Kinesis namespace. It measures how far behind the consumer's iterator is from the tip of the stream — effectively the age of the oldest unprocessed record. Alarm when it exceeds your latency SLA (e.g. greater than 60,000 ms for one minute).

Also watch IncomingRecords (producer rate) and WriteProvisionedThroughputExceeded (shard hot-spotting). If the consumer is Lambda, check concurrent execution limits and batch size as well.

What is the purpose of a CloudFormation change set?Fundamentals

A change set previews the actions CloudFormation will take before you commit an update — resources to add, modify, or delete, and whether each change requires replacement (which can mean downtime or data loss for stateful resources). It is the IaC equivalent of a dry run.

For a data pipeline stack containing an S3 bucket, Glue database and crawler, a change set might reveal that modifying the bucket name requires replacement — which would destroy data — prompting you to adjust the template before applying.

How do you deliver CloudWatch Logs from Account A to a Kinesis stream in Account B?Architecture

Four steps: (1) create the Kinesis Data Stream in Account B; (2) create an IAM role in Account B with a trust policy allowing Account A's CloudWatch Logs service to assume it, plus kinesis:PutRecord permission; (3) in Account A, create a subscription filter on the log group targeting the cross-account stream ARN and role ARN; (4) optionally add a resource policy on the stream granting Account A write access.

This pattern centralises log analytics in a security or platform account without copying credentials across accounts.

What is an AWS Organizations SCP, and can it grant permissions?Security

An SCP (Service Control Policy) is a policy attached to an organisation root, OU, or account that sets maximum permissions for all identities in that scope. It filters what identity-based and resource-based policies are allowed to grant.

SCPs cannot grant permissions — they only deny or pass through. Even if an IAM user has AdministratorAccess, an SCP denying cloudtrail:StopLogging prevents stopping CloudTrail. Use SCPs for organisation-wide guardrails; use IAM for fine-grained per-identity access.

Name the six Well-Architected pillars and give one data-pipeline example for Security.Exam

Operational Excellence, Security, Reliability, Performance Efficiency, Cost Optimization, and Sustainability.

Security example: encrypt all S3 buckets with SSE-KMS, enforce least-privilege IAM roles for Glue and Redshift, enable CloudTrail data events on sensitive prefixes, use Lake Formation column-level permissions instead of broad bucket policies, and rotate access keys or eliminate them in favour of role assumption.

Hands-on practice

Free tier where possible. Delete everything at the end of each task.

  1. Create a CloudWatch metric alarm on the AWS/Lambda Errors metric for a test function. Set threshold ≥ 1 in one 5-minute period and send an SNS email notification.

    CloudWatch → Alarms → Create alarm → Select metric → Lambda → By Function Name

    Alarm state changes to ALARM after you invoke the function with bad input that causes an error; you receive an SNS email.

    Show stepsConsole
    1. Create a simple Lambda that throws on event — or use an existing lab function.
    2. SNS → Topics → Create topic → Standard → subscribe your email → confirm.
    3. CloudWatch → Alarms → Create alarm → AWS/Lambda → Errors → select your function → period 5 min → threshold ≥ 1 → action: SNS topic.
    4. Invoke the function with input that triggers an error. Wait one period. Confirm ALARM state and email.
    aws lambda invoke --function-name my-test-fn \
  --payload '{"forceError": true}' /dev/null

aws cloudwatch describe-alarms --alarm-names "lambda-errors-my-test-fn"

    Cleanup: delete the alarm, SNS topic/subscription, and test Lambda.

  2. Run a CloudWatch Logs Insights query against /aws/lambda/<your-function> to find the top 10 error messages in the last hour.

    CloudWatch → Logs → Logs Insights → Select log group → Run query

    Query returns a table of parsed error messages sorted by count.

    Show stepsConsole 
    fields @timestamp, @message
| filter @message like /ERROR|Error|Exception/
| parse @message /.*(?<errorMsg>Error.*)/
| stats count() as hits by errorMsg
| sort hits desc
| limit 10

    Select the Lambda log group, set time range to Last 1 hour, run query. First 1 GB scanned per month is free. Adjust the filter pattern for Glue use /aws-glue/jobs/error instead.

  3. Write and attach a least-privilege customer-managed IAM policy that lets a Glue job role read only s3://dea-lab-<initials>-<random>/raw/* and write only to staging/*.

Recap

  • CloudFormation: template sections (Parameters, Mappings, Conditions, Resources, Outputs), stacks, change sets, drift detection, nested stacks, StackSets, rollback on failure.
  • CloudWatch metrics: namespaces, dimensions, standard (1 min) vs high-resolution (1 sec), custom metrics via PutMetricData, metric streams to Firehose.
  • Alarms: OK / ALARM / INSUFFICIENT_DATA; composite alarms; missing-data treatment; actions to SNS, Lambda, Auto Scaling.
  • Logs: log groups → streams → events; retention; Logs Insights queries; metric filters (→ metrics) vs subscription filters (→ Kinesis/Firehose/Lambda).
  • Cross-account logs: Kinesis stream + IAM role + trust policy in destination; subscription filter in source.
  • CloudTrail: management events (default, 90-day history) vs data events (off by default, needed for S3 object audit); trails to S3; CloudTrail Lake for SQL queries.
  • Config: configuration items, recorder, rules (managed vs custom Lambda/Guard), proactive vs detective, conformance packs, multi-account aggregation.
  • Well-Architected: six pillars; Tool workloads, lenses, milestones, HRIs/MRIs.
  • IAM: explicit deny wins; SCPs filter but never grant; service roles (glue.amazonaws.com) vs human-assumed roles; trust policy + permission policy.
  • Pipeline alerting: CloudWatch Alarms for numeric metrics; EventBridge for Glue job state changes and other discrete events.
