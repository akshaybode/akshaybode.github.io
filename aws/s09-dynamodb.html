Overview and NoSQL vs relational

Amazon DynamoDB is a fully managed, serverless NoSQL database. NoSQL means "Not Only SQL" — it supports key-value and document models without fixed schemas, horizontal scale-out, and single-digit millisecond latency at any table size.

Relational vs NoSQL

AspectRelational (RDS, Aurora, Redshift)NoSQL (DynamoDB)
Data shapeStructured tables, rows and columnsStructured, semi-structured, unstructured documents
SchemaPredefined schema enforced at writeSchemaless per item — each item can have different attributes
ScaleVertical (bigger instance) or read replicasHorizontal — partitions added automatically
Query languageSQL — joins, aggregations, complex filtersKey-based API — Query on partition key; no joins
Optimised forComplex ad-hoc queries, reporting, ACID transactions across rowsPredictable key access, high throughput, low latency at scale
Example use caseMonthly revenue report, dimensional modellingReal-time clickstream, session cache, IoT device state

DynamoDB characteristics

  • Key-value and document — items are JSON-like documents identified by a primary key.
  • Fully managed — no servers, patches or filesystem tuning.
  • High availability — synchronous replication across AZs in a Region.
  • Millisecond latency — single-digit ms at the 99th percentile for key-based reads and writes.

Global tables and multi-Region active-active

DynamoDB global tables (not on the deck) replicate tables across Regions with active-active writes. Applications write to the local Region; DynamoDB propagates changes typically within a second. Use global tables for disaster recovery, geo-proximity, and multi-Region active-active workloads. Conflict resolution is last writer wins based on timestamp — design keys so the same item is not written concurrently in two Regions unless you accept that semantics.

How partition keys map to storage

Query always targets one partition key (optionally filtering on sort key). You cannot efficiently look up by a non-key attribute without a secondary index or a Scan.

Attribute data types

Single-table design and overloaded keys

Production DynamoDB applications often use single-table design: one table holds multiple entity types, distinguished by composite keys and generic attribute names. The overloaded key pattern stores entity type in the sort key prefix — for example PK=USER#123, SK=PROFILE alongside PK=USER#123, SK=ORDER#456. GSIs invert the pattern for alternate access paths. This is beyond the deck but frequently tested at associate level when the scenario describes "one table for users and their orders".

GSI and LSI projection types

  • KEYS_ONLY — index keys from the base table only.
  • INCLUDE — keys plus up to 20 non-key attributes you specify.
  • ALL — full item copy — highest storage cost, lowest read latency.

DynamoDB Streams

DynamoDB Streams captures a time-ordered sequence of item-level changes (insert, update, delete) in a table. Each change becomes a stream record. Streams enable event-driven pipelines — CDC from DynamoDB into Lambda, Kinesis, or S3 without polling.

Classic CRUD APIs

Query vs Scan — the most common DynamoDB exam question. Query requires a partition key (and optional sort key condition). It reads only one partition (or index partition) and consumes capacity proportional to data read. Scan reads every item in the table or index — cost grows with table size regardless of how many items match. Never Scan a large table in production when a GSI + Query would work. FilterExpression on a Query filters after the key condition — it still reads every item in the partition that matches the key condition, and you pay for those reads.

Transactions

ConditionExpression for idempotency

Use ConditionExpression on PutItem to make writes idempotent — for example, "put this order only if the primary key does not exist yet". Combined with a natural business key as the partition key, retries from Lambda or Kinesis do not create duplicates.

import boto3

ddb = boto3.resource("dynamodb", region_name="us-east-1")
table = ddb.Table("Orders")

table.put_item(
    Item={
        "CustomerId": "C100",
        "OrderId": "O501",
        "Status": "PENDING",
        "OrderTotal": 750,
    },
    ConditionExpression="attribute_not_exists(OrderId)",
)

Capacity and cost

On-demand vs provisioned

WCU and RCU maths

OperationCapacity formulaExample
Writeceil(itemSize KB) × writes/sec × (2 if transactional)3 KB item at 10 writes/sec → 3 × 10 = 30 WCUs
Strongly consistent readceil(itemSize / 4 KB) × reads/sec × (2 if transactional)8 KB item at 1 read/sec → ceil(8/4) = 2 RCUs
Eventually consistent readStrong RCU ÷ 2 (round up)10 items × 3 KB, 10 reads/sec eventual → 10 units ÷ 2 = 5 RCUs

Worked WCU example

Suppose you ingest IoT telemetry: 500 writes per second, each item is 2.3 KB.

  • Round 2.3 KB up to 3 KB → 3 WCUs per write.
  • 500 writes/sec × 3 WCUs = 1,500 WCUs provisioned on the table.
  • If each write also updates a GSI projecting all attributes, the GSI needs its own 1,500 WCUs.
  • Transactional writes would double both to 3,000 WCUs each.

GSI capacity is separate

When you write an item, DynamoDB updates every GSI that projects attributes from that item. A write consumes WCUs on the base table and on each affected GSI. Size the GSI capacity (or use on-demand) alongside the table — throttling on a GSI write propagates back and throttles the base table write too.

Hot partitions and throttling

Write-sharding suffix: if many writes target the same logical entity, append a random suffix #0…#9 to the partition key on write and fan-out Query across shards on read. Example: DEVICE#123#shard4 instead of DEVICE#123.

Burst capacity and adaptive capacity

Backup, export and zero-ETL

  • Point-in-time recovery (PITR) — continuous backups for 35 days; restore to any second within that window. Enable on production tables — exam scenarios asking for "recover from accidental deletion an hour ago" point here, not on-demand backup alone.
  • On-demand backup — full table snapshot retained until you delete it; no second-level restore granularity. Good before schema changes.
  • Export to S3 — full or incremental export to S3 in DynamoDB JSON or Ion format for Athena/Glue analysis; does not consume read capacity on the table. Preferred over Scan for analytics snapshots.
  • Import from S3 — bulk load from S3 without consuming write capacity on the live table during import; creates a new table or overwrites with a import job.
  • Zero-ETL to Redshift — managed integration replicates DynamoDB changes into Redshift for analytics without Lambda/Kinesis glue. Competes with Streams → Lambda → S3 → COPY for "least operational overhead" questions — zero-ETL wins when the requirement is analytics-only replication.
  • Zero-ETL to OpenSearch — near-real-time search indexing from DynamoDB. Replaces the older Streams → Lambda → OpenSearch pattern from slide 223.
Kinesis Data Streams for DynamoDB. When you need stream data retained longer than 24 hours, fan-out to multiple consumers, or replay history, enable Kinesis streaming instead of (or in addition to) DynamoDB Streams. Kinesis Data Firehose can then land changes in S3 for the lake.

DynamoDB Accelerator (DAX)

DAX is a managed, in-memory cache for DynamoDB. It uses a write-through model: writes go to DynamoDB first, then update the cache. Reads can hit microsecond latency — roughly 10× faster than DynamoDB alone for hot keys.

DAX vs ElastiCache

AspectDAXElastiCache (Redis/Memcached)
PurposeDynamoDB-specific API cacheGeneral-purpose in-memory store
IntegrationDrop-in SDK endpoint changeApplication manages cache keys and invalidation
ConsistencyWrite-through; no strongly consistent DAX readsYou implement consistency logic
When DAX does not helpStrongly consistent reads, write-heavy workloads where cache churn is highN/A — different layer
DAX is not a write accelerator. Every write still hits DynamoDB and consumes WCUs. DAX helps read-heavy, eventually consistent access patterns — leaderboards, product catalogs, session lookups — not bulk ingestion.

Time to Live (TTL)

  • Designate one Number attribute (epoch seconds) as the TTL attribute.
  • Expired items appear in Streams as REMOVE events with user identity type Service.
  • Pair TTL with Streams + Lambda to archive expiring session or telemetry data to S3 before deletion.
  • TTL works in on-demand and provisioned modes and on global tables.

Biggest money leak. On-demand mode on tables with predictable 24/7 traffic — you pay per-request premium indefinitely. A provisioned table with auto scaling and reserved capacity for the baseline saves 50–70% at steady utilisation.
Surprise bill. A Scan on a terabyte table in on-demand mode charges for every item read, even if FilterExpression returns ten rows. A misconfigured Glue job or debug script running Scan in a loop can cost hundreds of dollars in hours.

Traps that catch people

  • 400 KB wall — Teams store PDFs or images in DynamoDB attributes. Writes above 400 KB fail. Store the object in S3 and keep a pointer attribute (s3://bucket/key) plus metadata in the item.
  • GSI throttles base table — Under-provisioned GSI write capacity causes ProvisionedThroughputExceededException on the base table PutItem even when the table itself has headroom. Size every GSI independently.
  • GSI reads are eventually consistent only — You cannot request strongly consistent reads on a GSI. Patterns needing read-your-writes across alternate keys must Query the base table or accept staleness.
  • FilterExpression does not save RCUs — A Query with a filter still reads every item matching the key condition and bills for those reads. Design the sort key or GSI so the key condition narrows data, not the filter alone.
  • Hot partition vs table capacity — Adaptive capacity helps uneven load across partitions but one partition key receiving more than 3,000 RCU or 1,000 WCU still throttles. Auto scaling adds table-wide units, not per-key units.
  • LSI creation window — LSIs exist only at table creation. Attempting to add one later requires a new table and migration — a common exam "what went wrong" scenario.
  • TTL is not instant — Items past expiry can appear in reads and Streams for up to 48 hours. Do not use TTL as a real-time access-control mechanism.
  • Transactional cost doubling — TransactWriteItems consumes 2× WCUs per item. Budget capacity for transactional paths separately from standard writes.
  • DAX and strong consistency — DAX serves eventually consistent reads from cache. GetItem with ConsistentRead=true bypasses DAX and hits DynamoDB directly — plan RCU for those paths.
  • Scan vs Query in analytics — Export to S3 or Streams → S3 avoids RCU entirely for bulk extracts. Scanning a production table for nightly reports is the wrong tool.

Production patterns

Operational store + lake export

Hot path: single-table design with composite keys and two GSIs for alternate lookups. Streams with NEW_AND_OLD_IMAGES feed Lambda that lands changes in S3 as Parquet. Nightly Glue job or zero-ETL to Redshift for analytics — never Scan the table for reports.

Large attribute offload

Keep items under 100 KB for predictable RCU. Store documents in S3; item holds docS3Key, contentType, sizeBytes. Lambda pre-signed URL for client download. Anti-pattern: storing base64 images in DynamoDB — hits 400 KB limit and doubles storage cost in GSIs projecting ALL.

Where this fits with the rest of the exam

DynamoDB is the default when a scenario needs single-digit millisecond key-value access at scale with no server management. It pairs with streaming ingestion in Section 6 (Streams → Lambda → Kinesis), operational-to-analytical replication in Section 10 (zero-ETL or Streams → S3 → COPY), and event-driven compute in Section 5 (Stream triggers, conditional writes). Object storage for large payloads lives in Section 7.

  • Kinesis Data Streams — when you need retention beyond 24 hours or multiple independent consumers of DynamoDB changes.
  • Redshift zero-ETL — managed CDC from DynamoDB to the warehouse without building Lambda glue.
  • Purpose-built database selection — DynamoDB vs DocumentDB vs Aurora when the scenario mentions documents or SQL.
  • Section 8 (ElastiCache) — general-purpose cache vs DAX when the data lives only in DynamoDB.
How the exam frames the choice. "Partition key access at any scale, millisecond latency" → DynamoDB. "Ad-hoc SQL across columns" → Redshift or Aurora, not DynamoDB. "MongoDB API" → DocumentDB. "Least operational overhead for DynamoDB → analytics" → zero-ETL or export to S3, not Scan. Do not pick DynamoDB when the access pattern requires joins, aggregations across entities, or full-table search without a designed GSI.

Interview questions

Answer each one out loud before opening it.

Explain Query versus Scan and when each is appropriate.Exam

Query requires a partition key equality condition (and optional sort key conditions). It reads only items in that partition — cost scales with items returned or filtered in that partition, not the whole table. Use Query (or GetItem for a full primary key) for every production access path.

Scan reads every item in a table or index. Cost is proportional to table size. Acceptable only for small tables, one-off admin tasks, or when backed by a parallel Scan on a GSI designed for export. Exam scenarios describing "find all users older than 30" without a key hint are steering you toward a GSI, not a Scan.

When would you add a GSI instead of an LSI?Design

Add a GSI when you need a different partition key, when the table already exists (LSIs cannot be added later), or when you need more than five alternate sort-key patterns. GSIs scale independently and support sparse indexes — only items with the projected attributes appear.

Choose an LSI only at table creation when you need an alternate sort key on the same partition key and strongly consistent reads on that pattern. LSIs share table capacity and have a 10 GB per-partition-key limit across base + LSIs.

How many RCUs do you need to strongly read fifty 6 KB items per second?Cost

Each 6 KB item rounds up to 2 × 4 KB units = 2 RCUs per strongly consistent read. Fifty items per second → 50 × 2 = 100 RCUs.

If eventually consistent reads were acceptable, the same workload would need 50 RCUs (half the strongly consistent cost).

What is a hot partition and how do you fix one?Troubleshooting

A hot partition is one physical partition receiving more read/write traffic than its share of table capacity — usually because the partition key has low cardinality (everyone writes to STATUS=ACTIVE) or a monotonic key concentrates new writes.

Fixes: redesign the partition key for high cardinality (use user ID, not status), add a random write-sharding suffix, split hot entities across composite sort keys, or use write buffering through SQS/Kinesis before DynamoDB. Adaptive capacity helps temporarily but is not a design strategy.

Describe the DynamoDB Streams → Lambda CDC pattern for keeping Redshift in sync.Architecture

Enable a stream with NEW_AND_OLD_IMAGES on the operational table. Attach a Lambda event source mapping. The handler transforms each INSERT/MODIFY/REMOVE into a staging record and writes to S3 or directly invokes Redshift COPY / the zero-ETL integration.

For analytics without custom code, DynamoDB zero-ETL to Redshift replicates changes automatically. Streams + Lambda still wins when you need custom transformation or multi-target fan-out.

On-demand versus provisioned capacity — how do you decide?Cost

On-demand when traffic is unknown, spikey, or the table is new — you pay per request, never throttle under service quotas, and accept a premium per million requests.

Provisioned + auto scaling when traffic is predictable and sustained — you pay for reserved RCU/WCU at lower unit rates, optionally with reserved capacity for a 1–3 year commit. Switch modes with UpdateTable once per 24 hours.

What does DAX not accelerate?Gotcha

DAX does not support strongly consistent reads — those always go to DynamoDB. It does not reduce write latency meaningfully because writes are write-through to the table. Scan-heavy analytics, write-heavy ingestion, and workloads needing item sizes near 400 KB see little benefit.

DAX is also DynamoDB-specific — ElastiCache is the answer when you cache computed aggregates or non-DynamoDB objects.

How do you implement idempotent order creation with DynamoDB?Design

Use the business order ID as the partition key (or sort key in a composite design). On PutItem, set ConditionExpression='attribute_not_exists(OrderId)'. A retry from API Gateway or Lambda that resubmits the same order gets ConditionalCheckFailedException instead of a duplicate row.

For updates, use condition expressions on a version attribute or status transition rules — for example, only allow PENDING → SHIPPED.

Why export DynamoDB to S3 instead of scanning the table for Athena?Performance

Export to S3 runs as a server-side job that does not consume table RCUs and produces a consistent snapshot in S3 format compatible with Athena and Glue. A Scan of a large table is slow, expensive in RCUs, and impacts production traffic.

Schedule exports for periodic analytics; use Streams for incremental CDC between exports.

  • DynamoDB = serverless NoSQL, key-value/document, schemaless items, 400 KB max item size.
  • Partition key alone must be unique; composite key allows duplicate partition values with different sort keys.
  • LSI: same PK, different SK, at creation only, max 5, strongly consistent. GSI: any keys, max 20, own capacity.
  • Query on partition key — efficient. Scan — reads entire table; avoid at scale.
  • 1 WCU = 1 KB write/sec. 1 RCU = 4 KB strongly consistent read/sec (2× eventual). Transactions cost double.
  • On-demand = pay per request, no throttling. Provisioned + auto scaling = cheaper at steady load.
  • Streams: 24h retention, view types KEYS_ONLY/NEW/OLD/BOTH, Lambda or Kinesis consumers.
  • DAX = write-through read cache, microsecond reads, no strongly consistent reads.
  • TTL deletes in background, no WCU, not immediate — pair with Streams to archive to S3.
  • Hot partitions → high-cardinality keys or write-sharding suffix. Export to S3 for Athena without RCU cost.
  • ConditionExpression on PutItem enables idempotent writes for at-least-once delivery sources.
