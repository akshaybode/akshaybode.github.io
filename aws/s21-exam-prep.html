Exam tactics

Scenario exams reward process, not memorised fact lists. The routine below matches the 130-minute / 65-question clock and the wording patterns AWS uses in DEA-C01.

Time budgeting

  • Two minutes per question on average — 130 ÷ 65. Bank time on short questions; spend three to four minutes on long scenarios.
  • Flag and move on. Unanswered and wrong score the same; return to flags in the last 20 minutes.
  • Do not leave any blank — there is no penalty for guessing.

Reading strategy

  • Read the last sentence first. The qualifier (least operational overhead, most cost-effective, real time) eliminates distractors before you compare services.
  • Underline constraints: latency, data volume, existing software, compliance, VPC-only.
  • Ignore services that solve a problem the question never asked about — a perfect security answer in an ingestion question is a distractor.

Eliminating distractors

  • Self-managed on EC2 (Kafka, Spark, Airflow, databases) loses to managed equivalents unless the question explicitly requires custom OS packages.
  • Wrong domain: GuardDuty in a data-format question; QuickSight in an ingestion question; Route 53 in a lake governance question.
  • Over-engineering: Step Functions for a single S3→Lambda step; Redshift cluster for twice-daily Athena-scale queries.

Multiple-response questions

Select TWO (or three) questions require all correct choices — partial credit does not exist. Evaluate each option independently: if one of five is wrong, do not select it even if the other looks right. Prefer two strong matches over guessing a third.

When two answers both work

Pick the one that matches the stated constraint, not your real-world preference. If both Glue and EMR can run Spark but the question says least operational overhead, Glue wins. If both Athena and Redshift can query the data but the question says ad-hoc queries a few times per day, Athena wins.

Longer answers

When stuck between two plausible options, the longer answer that names the correct integration path (e.g. "Firehose with Lambda transform and Glue Data Catalog conversion") is often correct — AWS wants you to recognise the full pattern. Shorter generic answers ("use S3") are usually incomplete.

The five most common traps:
  1. Firehose for replay — Firehose delivers forward; replay needs Data Streams, MSK or S3 reprocessing.
  2. Athena vs Redshift cost — infrequent ad-hoc on S3 is Athena; concurrent BI on loaded TB is Redshift.
  3. Forgetting KMS permissions — encrypted S3/Glue/Redshift failures need both S3 and kms:Decrypt on the role.
  4. SQS for streaming — queues are not durable logs with retention-based replay.
  5. EC2 "because flexible" — flexibility loses to managed when the question includes operational overhead or minimal management.

Domain 1 — Data Ingestion and Transformation (~34%)

Q1. A company ingests 20,000 clickstream events per second and needs consumers to reprocess the last 48 hours after a bug fix. Which solution meets the requirement with the LEAST operational overhead?Domain 1
  1. Amazon Kinesis Data Firehose to Amazon S3
  2. Amazon Kinesis Data Streams with a 48-hour retention period
  3. Apache Kafka on Amazon EC2
  4. Amazon SQS standard queue

Answer: B. Kinesis Data Streams retains records for up to 365 days and lets multiple consumers read from the same shard iterator or checkpoint, so replay within 48 hours is native. On-demand mode removes shard tuning.

Why not the others: A — Firehose is forward-only with no replay buffer. C — self-managed Kafka works but adds broker patching and monitoring the question excludes. D — SQS deletes messages after consumption and cannot replay a 48-hour window.

Traps that catch people

  • Same service, wrong capability — Firehose for replay; Athena for high-concurrency BI; SQS for streaming retention; Macie for threat detection; GuardDuty for PII classification; DMS for NFS files.
  • Qualifier swap — Identical stem, but least operational overhead → managed/serverless; most cost-effective → pay-per-use or Spot; lowest latency → provisioned capacity or Enhanced Fan-Out; fastest time to implement → console-native integration (Glue, Firehose, AppFlow).
  • Keyword → service map — "Sub-second" / "real time" → Kinesis Streams or Flink; "near real time" → Firehose; "exactly-once FIFO" → SQS FIFO; "SQL over S3" → Athena; "no code" profiling → DataBrew; "managed Kafka" → MSK; "minimal downtime database" → DMS full load + CDC; "existing SFTP" → Transfer Family.
  • Technically possible but not AWS-native — Kafka on EC2, Spark on self-managed EMR forever, cron on EC2 instead of EventBridge, JDBC in Lambda for heavy ETL — all work in reality but lose when the question rewards managed services.
  • KMS permission half-fix — Adding s3:GetObject without kms:Decrypt on SSE-KMS buckets — most common Domain 4 trick.
  • Glue without S3 route — VPC connection alone fails; subnet needs gateway endpoint or NAT — appears in Domain 1 and 4 questions.
  • Athena vs Redshift false dichotomy — Both query S3 via Spectrum technically, but exam intent separates ad-hoc scan billing from warehouse concurrency.
  • Over-orchestration — Step Functions for one Lambda step; MWAA for three Glue jobs — match orchestrator complexity to step count.
  • Ignoring minimum bills — Athena 10 MB floor; Glue 10-minute crawler minimum; Fargate 1-minute minimum — small frequent jobs accumulate.

Interview questions

Answer each one out loud before opening it. These are strategy and design questions — not duplicates of the practice exam above.

How do you decide between Athena and Redshift for a new analytics workload?Comparison

Start with query pattern and concurrency. Athena is serverless over S3: you pay per TB scanned, there is no cluster to size, and it suits ad-hoc or intermittent SQL. Redshift suits many concurrent users, complex joins on data that lives in the warehouse, and predictable performance from columnar storage and result caching.

Then check data location. If data must stay in the lake, Athena or Redshift Spectrum avoids COPY. If the team already loads curated Parquet nightly and runs dashboards all day, Redshift (often Serverless for spiky use) wins. Cost crossover is usually query volume: a handful of daily analysts on partitioned Parquet → Athena; a department hitting the same models hourly → Redshift.

Walk me through designing an event-driven pipeline from S3 raw landing to curated Parquet and an SNS alert on failure.Architecture

Ingest: producers write to s3://bucket/raw/ with Hive-style prefixes. Enable EventBridge notifications on the bucket (or S3 → EventBridge).

Orchestrate: EventBridge rule matches Object Created under raw/ and starts a Step Functions Standard workflow (or Glue Workflow for Glue-only shops). States: start Glue job (JSON → partitioned Parquet in staging/), on failure → SNS to ops topic, on success → optional second job for aggregation into curated/.

Catalog: Glue crawler on curated/ registers tables. Athena workgroup with scan limits for validation queries. Idempotency: job writes overwrite partition paths deterministically.

How would you cut this pipeline's cost in half without changing the business outcome?Cost

Audit the three cost levers: storage class, compute idle time, and bytes scanned. Move raw data older than 90 days to S3 Intelligent-Tiering or Glacier Instant Retrieval; keep curated Parquet in Standard. Terminate EMR/Redshift provisioned resources when jobs finish; switch intermittent workloads to Athena, Glue pay-per-run, or Redshift Serverless.

On the lake side, convert JSON to Snappy Parquet, partition by date, and enforce workgroup bytes-scanned limits in Athena. Enable query result reuse where queries repeat. For streaming, right-size Kinesis shards or use on-demand mode; use Firehose instead of custom consumers when replay is not required.

When do you put Kinesis Data Streams in front of Firehose instead of Firehose alone?Design

Add Data Streams when you need more than one consumer at different speeds (Flink for real-time + Firehose for archive), replay within retention after code fixes, or sub-minute latency for a custom consumer. Firehose alone is enough when the only destination is S3/Redshift/OpenSearch and near-real-time (buffered) delivery satisfies the SLA.

Cost trade-off: paying for stream shards plus Firehose is justified when replay or multi-consumer fan-out is a stated requirement; otherwise Firehose direct from producers (or via API) is cheaper and simpler.

Explain how you would implement fine-grained access on a shared data lake for multiple teams.Security

Register S3 locations in Lake Formation, revoke overly broad IAM catalog permissions, and grant per-team LF-tags or named permissions on databases, tables and columns. Analyst roles assume IAM roles that Lake Formation vends temporary credentials for.

Combine with SSE-KMS CMKs whose key policies trust only approved roles, S3 Block Public Access account-wide, and CloudTrail data events on sensitive prefixes. For Redshift consumers, sync LF grants to Spectrum external tables or use Redshift datashares with RLS for row filters.

A Glue job suddenly went from 20 minutes to 3 hours. What is your troubleshooting order?Troubleshooting

Check input volume (more files or larger partitions?), then Spark UI / job metrics for skew, spill to disk, and shuffle-heavy stages. Verify DPU allocation — under-provisioned jobs crawl. Look for small files problem after upstream changes; compact partitions if needed.

Confirm no downstream lock (Iceberg commit contention, Redshift lock). Compare CloudWatch glue.driver.ExecutorAllocationManager.executors.numberMaxNeeded and error logs. Roll back recent code or schema changes if correlated.

What is your approach to making a Lambda + S3 pipeline idempotent?Design

Assume at-least-once delivery. Use deterministic output keys (curated/year=…/id=…) so retries overwrite. Track processed object keys or ETags in DynamoDB with conditional writes. For aggregations, design merge logic (delete partition + insert, Iceberg MERGE, or Redshift staging table swap).

Enable partial batch failure reporting on SQS/Lambda if batching. Dead-letter queues capture poison objects after N tries without blocking the whole queue.

Compare DMS, DataSync and Snowball for migration — how do you choose?Comparison

DMS: homogeneous or heterogeneous database migration and ongoing CDC with minimal downtime. DataSync: scheduled file replication NAS → S3/EFS over the network. Snowball/Snowmobile: offline bulk when bandwidth or time constraints make network transfer impractical at terabyte/petabyte scale.

Many replatforming projects use two: Snowball for initial bulk, DMS for incremental DB sync, DataSync for file shares — pick per data shape, not one service for everything.

How do VPC endpoints change the security posture of a data pipeline?Security

Interface and gateway endpoints keep traffic between your VPC and AWS services on the AWS private network, avoiding the public internet and often NAT Gateway data processing charges. A Glue job or Lambda in private subnets reaches S3 via the S3 gateway endpoint; reaches KMS, Secrets Manager, or STS via interface endpoints.

Security groups and endpoint policies add another layer: you can restrict which buckets or actions are reachable even after network path exists. Exam phrase cannot leave the VPC points here.

Describe how Redshift distribution and sort keys interact with query performance.Performance

Distribution (DISTKEY) controls which compute node holds which rows. KEY on a high-cardinality join column co-locates joins and reduces shuffle. ALL replicates small dimension tables. EVEN spreads when no clear join key. Skew on a low-cardinality KEY melts one node.

Sort keys physically order data on disk for range filters — compound sort for multi-column predicates, interleaved for equal-weight columns (maintenance-heavy). After loads, run VACUUM and ANALYZE; use SVV_TABLE_INFO to inspect skew and unsorted regions.

Book only when practice scores are consistently above 850 equivalent (56+ on this set). A fixed date converts passive watching into revision.

Where to book

  • Create or sign in to your AWS Certification Account at aws.training (Certification → Go to your account). This is separate from the console login.
  • Exam delivery is through Pearson VUE or PSI — you choose the provider when scheduling. Both offer test-centre and online proctored options in most countries.
