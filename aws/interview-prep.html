How to structure an answer

Interviewers score reasoning under constraints, not whether you memorised every AWS quota. A strong answer follows the same skeleton every time — it sounds conversational but is deliberate.

  1. Clarify the requirement. Restate the business need in one sentence. "Dashboards in five minutes" is different from "sub-second fraud decline." Ask one clarifying question if the prompt is ambiguous — interviewers reward it.
  2. State the constraint you are optimising for. Latency, cost, operational overhead, compliance, replayability, team skill — pick the one the scenario emphasises and say it aloud.
  3. Name the option you would pick and why. Tie each service to the constraint. "Firehose because near-real-time is acceptable and we want least ops" beats "Firehose, Kinesis, Lambda, S3" with no glue between them.
  4. Name the option you rejected and why. One sentence: "Not EMR because the job is 20 minutes nightly and a cluster left idle dominates cost."
  5. Say how you would measure success. A metric (IteratorAgeMilliseconds, Athena TB scanned per day, row-count reconciliation tolerance), an alarm, or a data-quality check.
  6. Say what would make you change your mind. "If QPS exceeds 5,000 sustained, I'd revisit on-demand Kinesis vs provisioned shard maths."

Worked example — weak versus strong

Prompt: "A Glue job that used to take 20 minutes now takes three hours. What do you do?"

Weak answer

"I would check Glue logs and add more DPUs. Maybe run VACUUM. Could also check if S3 is slow."

Lists actions with no diagnosis order, no metrics, no prevention — interviewer learns you guess.

Strong answer (abbreviated)

"I'd confirm input volume first — compare Records read and S3 prefix listing for today's partition against last week. If volume is flat, I'd open Spark stages for skew or a stage doing a full shuffle because a pushdown predicate was removed. CloudWatch glue.ALL.s3.filesystem.read_bytes tells me if we're reading ten times more data. Fix: restore partition filter, compact small files, or salt a hot join key — only then add DPUs if CPU-saturated. Prevent with a duration p95 alarm and CI check that job parameters still include the predicate."

Exam overlap. The same structure wins DEA-C01 scenario questions — the qualifier (most cost-effective, least operational overhead) is step 2 in the skeleton above. See Section 21 decision tables after you finish the course sections.

A Glue ETL job that used to finish in 20 minutes now takes three hours. Walk me through your investigation.Troubleshooting

I would start by confirming the symptom is real and isolated: compare the last ten successful runs in the Glue console (Job runs → Duration, DPU hours, Records read) against today's run. Check whether input volume actually grew — a crawler may have registered new partitions, or upstream dropped ten times more files into the same prefix. CloudWatch metrics Glue.driver.ExecutorRunTime, glue.ALL.s3.filesystem.read_bytes, and Spark UI stages (enable the job's Spark UI or check continuous logging to S3) tell you whether time went into reading, shuffling, or writing.

The usual culprits for a sudden 9× slowdown without a code deploy: partition explosion (someone removed a pushdown predicate and the job now lists every file under the table root), small-file problem (millions of tiny JSON files instead of consolidated Parquet), data skew (one key dominates a join so one executor runs long while others idle), or concurrency contention (another job on the same account hit the Glue DPU quota and yours queued in Flex mode). I would query the Data Catalog for partition count, run aws s3 ls s3://bucket/prefix/ --recursive --summarize on a sample day, and open the slowest Spark stage.

Fix depends on diagnosis: re-enable pushdown predicates and partition filters; compact small files with a one-off job writing coalesce(1) or repartition by date to Parquet; salt skewed join keys; increase worker DPUs only after confirming the job is CPU-bound, not I/O-bound. Prevent with a daily CloudWatch alarm on job duration p95, a crawler schedule that does not re-list stale partitions, and a file-size guardrail (Firehose/Glue writes target 128–256 MB objects). See Section 4 for Glue-specific tuning.

Ongoing monitoring: watch Duration, error rate, and data-volume reconciliation alarms in CloudWatch (Section 16). Document findings in the pipeline runbook so the next on-call engineer starts from evidence, not guesswork.

A Glue Spark job fails with executor OutOfMemoryError. How do you diagnose and fix it?Troubleshooting

Confirm in CloudWatch Logs under /aws-glue/jobs/error or the Spark driver log: is it driver OOM (collecting too much to the driver) or executor OOM (shuffle, wide transformations, or caching)? The stack trace usually names the stage. Enable Spark UI or set --enable-continuous-cloudwatch-log and --enable-metrics so you can correlate the failure with the stage that spiked memory.

Executor OOM fixes: increase --executor-memory and worker count; avoid .collect() and huge broadcasts; drop unnecessary .cache(); repartition before a wide join so each task gets a manageable slice; use Glue's resolveChoice and column pruning early to shrink rows. Driver OOM often comes from groupBy on high-cardinality keys sent to the driver — push aggregation to executors or write intermediate results to S3 instead of collecting.

Prevent by sizing DPUs from a benchmark on a representative partition, setting job bookmarking so re-runs do not re-read history, and adding a CloudWatch alarm on glue.driver.aggregate.numFailedTasks. For recurring wide joins, document the expected shuffle size and cap input with pushdown predicates. Cross-reference Section 4 DPU pricing before permanently doubling workers.

A Kinesis consumer's IteratorAgeMilliseconds keeps climbing. What is happening and what do you do?Troubleshooting

Rising iterator age means the consumer is falling behind the head of the stream — records are arriving faster than they are processed, or processing is stalled. Confirm in CloudWatch on the stream: GetRecords.IteratorAgeMilliseconds (per consumer), IncomingRecords, and ReadProvisionedThroughputExceeded. Check the consumer: Lambda Duration and Errors, or KCL checkpoint lag in DynamoDB (LeaseTable timestamps).

Common causes: insufficient Lambda concurrency or batch size too small; a downstream call (RDS, API) timing out inside the handler; a hot shard because partition keys are skewed; too many consumers sharing standard-mode 2 MB/s read per shard; or a poison record causing repeated retries. Fix: scale Lambda reserved concurrency, increase batch window cautiously, add shards or switch to on-demand mode, enable enhanced fan-out for multiple heavy consumers, fix or route poison records to a DLQ, and optimise handler code to avoid synchronous blocking I/O.

Prevent with an alarm on iterator age (e.g. > 60 seconds for near-real-time SLAs), load tests before launch, and idempotent handlers so safe retries do not corrupt state. Architecture note: if replay matters, keep Data Streams as the buffer and treat Firehose as a delivery path only — see Section 6.

Producers are getting ProvisionedThroughputExceededException on Kinesis. Walk me through the fix.Troubleshooting

Check CloudWatch WriteProvisionedThroughputExceeded per shard. If one shard spikes while others are idle, the partition key is hot — all traffic hashes to one shard and hits the 1 MB/s or 1,000 records/s per-shard write limit. If all shards throttle evenly, aggregate write rate exceeds total shard capacity.

Fix hot keys by increasing cardinality: use deviceId or userId instead of country, or append a random suffix (userId#n) and deduplicate in the consumer with a window on event time. Fix capacity limits by adding shards (UpdateShardCount), switching to on-demand mode, or using KPL aggregation to pack more records per PutRecords call. Implement exponential backoff with jitter on retries — tight loops amplify throttling.

Prevent with producer-side monitoring on throttled records, shard metrics dashboards, and load tests that simulate peak traffic including Black Friday multiples. Document partition-key design in the runbook so a new service does not reuse a low-cardinality key.

An Athena query that scanned 200 GB yesterday suddenly scans 2 TB today with the same SQL. Why?Troubleshooting

First verify in Athena query history: DataScannedInBytes and the exact SQL — did someone remove a WHERE on partition columns, change a join, or point at a different table/database? Run SHOW PARTITIONS table or check the Glue catalog: new partitions may have landed outside the filter range, or a crawler registered partitions that do not match the path layout so partition pruning failed.

Other causes: table switched from Parquet to raw JSON (no column pruning benefit); SELECT * replaced a column list; a view was recreated without predicates; MSCK REPAIR added thousands of empty or duplicate partitions; or someone dropped and recreated the table without partition_projection so Athena now scans all prefixes under the root.

Fix: restore partition filters and column projection; convert to Parquet with Snappy; use partition projection for high-cardinality date partitions; run ANALYZE or Glue crawler for stats. Prevent with AWS Lake Formation or IAM policies that block full-table scans for analysts, Cost Explorer alerts on Athena spend, and query audit via CloudTrail data events on S3. Details in Section 3.

New files landed in S3 but Athena returns zero rows. How do you debug?Troubleshooting

Work through the stack: (1) Are the files under the prefix the table expects? Compare S3 path to LOCATION in SHOW CREATE TABLE. (2) Does the Glue catalog know about new partitions? Run MSCK REPAIR TABLE or trigger the crawler; check SHOW PARTITIONS. (3) File format mismatch — CSV headers, wrong delimiter, or Parquet schema drift. (4) SerDe and column names: partition keys in the path must match catalog keys exactly (year=2026/month=08/).

Confirm with a direct S3 read: aws s3 ls s3://bucket/prefix/ and a small SELECT * FROM table$partitions. Check Lake Formation permissions if the table is governed — zero rows can mean access denied on new prefixes. Athena engine version differences occasionally affect timestamp parsing.

Fix: repair partitions, align path template, fix crawler schedule, or add partition projection so new dates appear without repair. Prevent with an EventBridge rule on S3 ObjectCreated triggering a Lambda that calls batch_create_partition, plus a data-quality check comparing S3 object count to catalog partition count nightly.

A Redshift query has been queued in WLM for 40 minutes. What do you check?Troubleshooting

Open Query Monitoring Rules and STL_WLM_QUERY / SVL_QUERY_STATE to see which queue holds the query and whether concurrency slots are exhausted. Check STV_WLM_SERVICE_CLASS_STATE for running vs queued count. Often a long-running ETL job or a rogue scan occupies all slots in the same queue as the analyst query.

Also check for locks: STL_TR_CONFLICT and SVV_TRANSACTIONS — a COPY or VACUUM may block DDL. Review query priority: short-query acceleration (WLM queue config) may need a dedicated queue for dashboards. On RA3, confirm compute scaling is not starved.

Fix: kill or reschedule the blocking query (CANCEL / PG_TERMINATE_BACKEND), move ETL to a separate queue with fewer concurrent slots but higher memory, enable concurrency scaling for burst (watch cost), or rewrite the queued query (distribution key mismatch causes massive redistribution). Prevent with WLM auto rules, query timeouts, and separating BI from batch workloads — see Section 10.

Redshift cluster disk usage is at 95%. What is your plan before it hits 100%?Troubleshooting

Check SVV_DISKUSAGE and STV_PARTITIONS to see which tables consume space. On RA3, local SSD is primarily for cache — high usage may mean unsorted rows needing vacuum or too many temp tables from large sorts. Run SELECT "table", size, tbl_rows FROM SVV_TABLE_INFO ORDER BY size DESC LIMIT 20.

Immediate actions: run VACUUM DELETE ONLY on tables with heavy deletes; VACUUM FULL during a maintenance window for deep reclaim; drop staging tables left from failed loads; archive cold data to S3 and use Spectrum for historical queries (Section 10 Spectrum); enable automatic table optimization or consider resizing to a node type with more local storage on DC2 (legacy).

Prevent with lifecycle policies moving data older than N months to S3 Parquet, monitoring PercentageDiskSpaceUsed in CloudWatch, and enforcing sort keys that match delete patterns. RA3 clusters offload to S3 — still monitor because large unsorted tables hurt performance before they hurt disk.

Fix the 12 bad rows at source or quarantine them: run COPY with MAXERROR 100 and ACCEPTINVCHARS / TRUNCATECOLUMNS if appropriate, or use a staging table with VARCHAR columns, load all rows, insert clean rows to prod with casts and filters, route bad rows to an error table for partner notification. For Parquet, schema evolution mismatches show as column count errors — align Glue catalog schema.

DynamoDB is throttling writes on one partition key only. Explain and fix.Troubleshooting

DynamoDB partitions have a per-partition throughput ceiling (~3,000 RCU / 1,000 WCU per second per partition, with burst). CloudWatch ThrottledRequests split by operation, plus ConsumedWriteCapacityUnits with dimension TableName, shows throttling. If one hot key dominates (e.g. all counters updating global#counter), only that partition throttles while table-level metrics look healthy.

Fix: redesign the access pattern — shard the hot key (counter#0 … counter#9 and sum on read), use write sharding for high-frequency status updates, or switch to on-demand if traffic is spiky and unpredictable. For transient spikes, enable auto scaling on provisioned mode with target tracking at 70% utilization.

Prevent with partition key design reviews, item collection size monitoring (ItemCollectionMetrics for LSI hot spots), and load tests. See Section 9 for WCU maths and GSI write amplification.

A Lambda triggered by S3 events processes some files twice. How do you find out why and stop duplicates?Troubleshooting

S3 event notifications deliver at least once — retries after Lambda failures, duplicate events on versioning overwrites, or overlapping prefix filters can invoke twice for the same object. Check CloudWatch Logs for duplicate requestId values with the same object key and timestamp; S3 server access logs show multiple POST notifications.

Confirm whether the handler is idempotent: does it INSERT blindly or UPSERT on a natural key? Check SQS DLQ if using async invocation. Lambda's account-level concurrency retries can re-drive the same batch.

Fix: make processing idempotent — write to deterministic paths (curated/date=…/file.parquet overwrite), use DynamoDB conditional writes on a file-ETag primary key, or maintain a processed-files table. Optionally insert SQS between S3 and Lambda for single-consumer ordering per prefix. Prevent with idempotency keys in the design doc and integration tests that invoke the handler twice. Covered in Section 5.

A Lambda function keeps hitting its 15-minute timeout. What are your options?Troubleshooting

Inspect CloudWatch Logs for where time goes — X-Ray segments show downstream calls. If the function processes large S3 objects synchronously, downloads, or runs heavy pandas work, 15 minutes is a hard Lambda limit and cannot be raised.

Options in order: (1) Split the work — S3 trigger sends a message to SQS with key ranges; Step Functions Map state processes prefixes in parallel Lambdas. (2) Move compute to Glue or EMR for batch transformation. (3) Stream processing with partial progress in DynamoDB. (4) Increase memory (which proportionally increases CPU) if the bottleneck is single-threaded compute within one invocation.

Prevent by sizing workloads to the right service upfront — Lambda for seconds of work, Glue for Spark minutes-to-hours. Set CloudWatch alarm on Duration p99 approaching 900 seconds and use reserved concurrency to avoid retry storms.

A nightly pipeline silently produced half the expected row count. How do you investigate?Troubleshooting

Compare row counts at each layer: source system export count, S3 object metrics (NumberOfObjects custom metric or S3 Inventory), Glue job RecordsWritten in the run metrics, and target table COUNT(*) for the load date partition. Identify the first layer where count drops — that is where the bug lives.

Check Glue job bookmarks: did a partial run commit bookmark state and skip files? Check for filters (pushdown predicate too aggressive), inner joins that drop unmatched rows, and late-arriving data excluded by a watermark. Review Step Functions execution history for a skipped branch. Query orchestrator logs for SUCCESS despite partial writes.

Fix the transform and backfill the missing partition after resetting bookmark for that day only. Prevent with data quality gates: assert row count within ±5% of trailing average, fail the Step Function if check fails, SNS to on-call. Store expected counts in a manifest file alongside each drop.

On EMR, one Spark task takes 90% of total job runtime — classic data skew. What do you do?Troubleshooting

Open the Spark UI → Stages → sort by duration → skew column shows max task vs median. The stage is usually a shuffle join or groupBy where one key (null, empty string, or a mega-customer) owns most rows.

Fixes: filter null keys early; salting — add random suffix to hot keys on both sides of join, join, then aggregate away salt; use broadcast join if one side is small enough; repartition by a higher-cardinality column; use Adaptive Query Execution (Spark 3.x) with skew join hints. On EMR, increase executor count only helps if tasks are balanced.

Prevent with data profiling before production joins, AQE enabled in cluster config, and CloudWatch alarm on job duration p95. For recurring skew, pre-aggregate hot keys in a separate pipeline stage. See Section 13 EMR.

A Step Functions execution is stuck in Running for hours. How do you debug?Troubleshooting

Open the execution graph in the Step Functions console — the currently active state is highlighted. Common stuck states: Wait with a far-future timestamp, Task waiting on a sync job (Glue StartJobRun.sync, EMR create cluster) that failed without heartbeat, or Callback waiting for SendTaskSuccess that never arrives.

An Amazon OpenSearch Service domain is in yellow cluster health. What does that mean and what do you do?Troubleshooting

Yellow means all primary shards are assigned but at least one replica shard is unassigned — you can still query and index, but you have no redundancy. Check cluster health API: GET _cluster/health and GET _cat/shards?v for UNASSIGNED shards. Common on single-AZ domains with replica count = 1 when a node is down, or when disk watermark triggered relocation.

Also check JVM memory pressure (JVMMemoryPressure > 85% causes throttling), UltraWarm/Cold tier issues, and blue/green deployment in progress. CloudWatch logs for slow indexing and bulk rejections.

Fix: add a node or AZ for replica placement, free disk (delete old indices, curator ILM), reduce shard count on new indices, or temporarily set number_of_replicas to 0 on dev clusters (not prod). Prevent with three-AZ deployment for production, automated snapshots to S3, and alarms on storage and JVM pressure.

Design ingestion and serving for 1 TB/day of clickstream data with dashboards refreshed every five minutes.Design

Ingest: Kinesis Data Streams (or on-demand mode) with high-cardinality partition keys (sessionId) for even shard load. Producers use KPL aggregation. Two consumer paths: (1) Managed Flink or Lambda for five-minute tumbling-window aggregates written to DynamoDB or ElastiCache for sub-second dashboard reads; (2) Firehose to S3 Parquet partitioned by event_date/hour for historical Athena/Redshift analysis.

Serving: QuickSight SPICE refreshed every five minutes from the aggregate table, or direct query to Redshift materialized views refreshed on schedule. Trade-off accepted: five-minute latency is not true real time — we avoided per-event dashboard queries against the lake, which would destroy Athena economics.

Why not Firehose-only: five-minute aggregates need stateful processing Firehose cannot do. Why not EMR batch: cannot meet refresh SLA. Cost levers: on-demand Kinesis for spike handling, Parquet compaction nightly via Glue, SPICE vs direct query based on concurrent user count.

Validate the design with a back-of-envelope cost estimate using named billing units before the interview ends — interviewers notice when you close the loop on cost.

Design a batch pipeline for 200 nightly CSV drops from partners, each with a different schema.Design

Star schema versus snowflake — when does denormalisation win?SQL

Star: dimensions denormalised (one wide dim_customer with city, state, region columns). Snowflake: dimensions normalised to 3NF (customer → city → region tables). Denormalisation wins in Redshift/Athena when query patterns join fact to many dimension attributes frequently — fewer joins, better columnar compression on wide dimensions, simpler SQL for analysts.

Snowflake schema wins when dimensions are huge shared hierarchies (org chart, product catalog) updated centrally — normalise to avoid inconsistent duplicates. On columnar MPP, the join cost of snowflake is often worse than storing redundant dimension strings.

Exam/interview answer: default to star for analytics warehouses; snowflake only when update anomalies or storage dedup of slow-changing hierarchies justify the join cost.

How would you find and fix distribution skew in Redshift?SQL 
SELECT trim(name) AS table, slice, count(*) AS rows
FROM stv_slices s
JOIN stv_blocklist b ON s.slice = b.slice
JOIN stv_tbl_perm p ON b.tbl = p.id
JOIN pg_table_def d ON d.tablename = p.name
GROUP BY 1, 2
ORDER BY 1, rows DESC;

Query SVV_DISKUSAGE or stv_tbl_perm joined with slice counts — skew ratio = max slice rows / min slice rows. High skew on DISTKEY value (NULL or mega-key) causes one slice to own most data.

Rapid-fire technical

Short questions, short answers — use for warm-up the morning of the interview.

QuestionAnswer
Firehose vs Data Streams?Firehose: managed delivery to S3/Redshift/OpenSearch, buffered (~60s+), no replay, least ops. Data Streams: durable log, custom consumers, replay within retention, sub-second, you build consumers (Lambda/Flink/KCL).
When does Spectrum beat Athena?Spectrum: SQL inside Redshift joining local tables to S3 without egress/second engine. Athena: standalone SQL on S3, no cluster, pay per scan. Spectrum wins when data already in Redshift queries; Athena when no cluster or cross-account lake queries.
What does a Glue job bookmark do?Persists processed file/partition state between runs so incremental jobs skip already-seen data. Reset for full reload. State in Glue Data Catalog.
What does VACUUM do in Redshift?Reclaims space from deleted rows and re-sorts rows per sort key. VACUUM DELETE ONLY is lighter; FULL reclaims maximum space. Needed after large DELETEs or loads with suboptimal sort.
LSI vs GSI in DynamoDB?LSI: same partition key, alternate sort key, must define at creation, shares throughput, strong consistency available. GSI: different PK/SK, eventual consistency default, separate throughput, create anytime — use for alternate access patterns.
SQS visibility timeout?Time a consumed message is hidden from other consumers after receive. Must exceed Lambda max processing time; if too short, duplicate processing; too long, slow retry on failure.
Gateway vs interface VPC endpoint?Gateway (S3, DynamoDB): free, route table entry, no ENI. Interface (most AWS APIs): ENI in subnet, hourly + data charge, private IP DNS — needed for Glue, STS, etc.
SSE-KMS vs SSE-S3?SSE-S3: AWS-managed keys, free, audit via CloudTrail. SSE-KMS: CMK control, key policy/grants, rotation, per-request KMS charge, CloudTrail shows which key decrypted.
Standard vs Express Step Functions?Standard: exactly-once semantics, up to 1 year, async integrations, $25/1M transitions. Express: at-least-once, <5 min, high volume, $1/1M + duration — streaming/event rates.
Partition projection?Athena/Glue feature defining partition values in metadata instead of listing S3 — avoids MSCK/crawler for high-cardinality dates. Requires predictable path template.
Splittable file format?Format where readers split work across parallel tasks on byte boundaries — Parquet, ORC, line-delimited JSON/CSV. Whole-file gzip JSON is not splittable — one task reads entire file.
At-least-once vs exactly-once?At-least-once: duplicates possible on retry (SQS, Lambda, Kinesis). Exactly-once: end-to-end once semantics (hard; Kafka idempotent producer + transactional; Step Functions Standard state transitions). Design idempotent consumers.
What is a pushdown predicate in Glue?Filter passed to catalog so only matching S3 partitions are read — saves DPU and time.
Redshift concurrency scaling?Burst compute adds transient clusters billed per second when WLM queues — for unpredictable analyst spikes, not ETL default.
Glue Flex execution?Queued cheaper DPU pricing for non-urgent jobs — trade latency for cost.

Additional rapid-fire (expand for detail)

What is the difference between AWS Glue Data Catalog and Hive Metastore?Fundamentals

Glue Data Catalog is AWS's managed metastore — integrated with Athena, Redshift Spectrum, EMR, and Lake Formation. Hive Metastore is the open-source interface; on AWS you can run it on EMR or use the Glue Data Catalog as a drop-in replacement via the Hive metastore client. For new builds, default to Glue Catalog for IAM and LF integration.

When would you pick MSK over Kinesis Data Streams?Comparison

MSK when you need full Kafka protocol compatibility, existing Kafka clients/connectors, longer retention with Kafka semantics, or on-prem Kafka migration with minimal code change. Kinesis when you want native AWS integration, serverless/on-demand scaling, and least ops — exam default unless the question says "Kafka" explicitly.

What does Lake Formation govern that IAM alone cannot?Security

Column-level, row-level, and tag-based access on Glue catalog tables across principals — enforced at query engines (Athena, Redshift Spectrum) without duplicating S3 bucket policies per prefix. IAM controls API access; LF controls which rows/columns appear in SQL results. See Section 13.

Recap

  • Open with clarify requirement → constraint → chosen option → rejected option → measure success → what would change your mind.
  • Troubleshooting answers name a metric, a log or system table, then fix, then prevention.
  • Design answers draw ingest → store → transform → serve and state the trade-off you accepted.
  • Cost answers name the billing unit (TB scanned, DPU-hour, shard-hour, RPU-second) and the specific lever.
  • Cross-cutting failures are usually idempotency, partition design, or capacity — check those first.
  • At-least-once delivery is the AWS default; design MERGE, deterministic paths, and dedupe keys.
  • Prefer same-region compute and S3 gateway endpoints before blaming application code for slowness.
  • Lake Formation row filters and Redshift RLS beat trust-me WHERE clauses for multi-tenant isolation.
  • Replay requires immutable raw retention — Firehose alone is not a replay log.
  • Say "I would verify X in CloudWatch Y" even in design questions — interviewers reward operational thinking.
  • Weak answers list services; strong answers chain reasoning to constraints.
  • Answer behavioural questions with frameworks, not fabricated war stories.
