File formats and compression

The exam assumes you can pick a storage format from a scenario's access pattern, explain why columnar beats row for analytics, and calculate how much an Athena bill drops when you convert CSV to Snappy-compressed Parquet. The course mentions Parquet in passing; this section is the depth the exam expects.

Columnar stores values column-by-column with encodings (dictionary, RLE, bit-packing). A query that selects three of thirty columns reads roughly one-tenth of the bytes — that is the mechanism behind Athena cost savings, not magic compression alone.

Everyday analogy — Row formats are a packed moving truck: to get one box from the back, you unload everything. Columnar formats are a warehouse with aisles labelled by item type: you walk only the aisles you need.

Compression codecs

Compression applies at two levels: file-level (whole CSV.gz) and column-level inside Parquet/ORC (each column compressed independently). Exam questions often conflate them — columnar + column-level Snappy is the winning combination for Athena.

Why CSV → Snappy Parquet cuts Athena bills 80–95%. Athena charges per terabyte scanned from S3. Two independent levers apply: column pruning (read only referenced columns) and compression (fewer bytes per column). Both multiply.

Worked byte calculation

Suppose a fact table lands as uncompressed CSV totalling 1 TB with 20 columns. An analyst runs:

SELECT customer_id, order_date, SUM(amount)
FROM orders_csv
WHERE order_date BETWEEN DATE '2025-01-01' AND DATE '2025-01-31'
GROUP BY customer_id, order_date;

On CSV, Athena reads all 20 columns for every row in every file the partition filter includes → ~1 TB scanned (ignoring partition pruning for simplicity).

After CTAS to Snappy Parquet with the same data:

  • Column pruning: three columns referenced → ~3/20 of logical data → ~150 GB.
  • Snappy compression: typical 3× on numeric/date columns → ~50 GB.
  • Bill: at ~5 USD/TB, 1 TB scan ≈ 5 USD vs 50 GB ≈ 0.25 USD — a 95% reduction. Even a five-column query on the same Parquet table (~25 GB) lands near 88% savings.

Add Hive-style partitions on order_date and the scan drops to January's prefix only — another order-of-magnitude cut beyond format conversion.

The small-files problem

Thousands of files under 10 MB each destroy performance: S3 LIST operations multiply, Athena/Glue spend time opening files, and column statistics are weaker. Targets used in production and cited on the exam:

  • Target file size: 128 MB–1 GB per object after compaction.
  • Cause: streaming micro-batches (Firehose, Kinesis → Lambda), per-file uploads, or repartition(5000) without coalesce.
  • Fix: Glue job with coalesce or repartition to a sensible count, Iceberg/Delta compaction, or S3 Inventory + batch copy. See Section 4 partitioning and Section 3 performance.

WITH (
  format = 'PARQUET',
  parquet_compression = 'SNAPPY',
  external_location = 's3://dea-lab-ab-4821/staging/orders_parquet/',
  partitioned_by = ARRAY['order_year', 'order_month']
) AS
SELECT
  order_id,
  customer_id,
  order_date,
  amount,
  YEAR(order_date)  AS order_year,
  MONTH(order_date) AS order_month
FROM dea_lab.orders_csv;
GZIP CSV is a trap. Smaller on disk but not splittable — a 500 MB .csv.gz file is processed by one Athena task. Snappy Parquet splits across row groups in parallel. "Compress the CSV with GZIP to save money" is often the wrong answer when the question allows Parquet.

Schema evolution in practice

When upstream adds a column:

  • CSV — add column at end; old files lack it → Glue/Athena reads NULL for missing.
  • Parquet — new files carry new schema in footer; mixed schemas in one table work if column names are stable.
  • Avro — reader resolves writer schema to reader schema; best for Kafka where producers upgrade independently.
  • Iceberg — explicit ALTER TABLE ADD COLUMN; metadata tracks versions (open table formats).

The exam contrasts "fail the pipeline" with "evolve schema gracefully" — Glue crawlers with updateBehavior=LOG and table formats win over brittle fixed-schema CSV pipelines.

Compaction job pattern (Glue)

import sys
from awsglue.utils import getResolvedOptions
from pyspark.context import SparkContext
from awsglue.context import GlueContext

args = getResolvedOptions(sys.argv, ["TARGET_PATH", "PARTITION"])
sc = SparkContext()
glue = GlueContext(sc)
spark = glue.spark_session

path = f"{args['TARGET_PATH']}/{args['PARTITION']}"
df = spark.read.parquet(path)

target_files = max(1, int(df.count() * 200 / (128 * 1024 * 1024)))  # ~128 MB est.
df.repartition(target_files).write.mode("overwrite").parquet(path)

Data modelling for analytics

The exam asks you to recognise star and snowflake schemas, explain slowly changing dimensions, and map a logical model onto Redshift distribution and sort keys. The course shows Redshift tables but never walks through dimensional modelling from first principles.

Normalisation versus denormalisation

Normalisation (3NF) removes redundancy — customers live in one table, orders reference customer_id. It minimises storage and update anomalies; OLTP systems (RDS, DynamoDB) use it. Denormalisation duplicates data to speed reads — a wide fact table with customer attributes repeated on every row. Analytics workloads (OLAP) favour denormalisation because joins across billions of rows are expensive and scans are cheap.

Star and snowflake schemas

ElementRoleExample
Fact tableMeasures at a defined grain; foreign keys to dimensionsfact_sales(order_id, date_key, product_key, store_key, quantity, revenue)
Dimension tableDescriptive context; relatively small, widedim_product(product_key, sku, name, category)
GrainWhat one row represents"One row per order line" — never mix grains in one fact
Surrogate keyInteger warehouse key, not the source-system natural keyproduct_key instead of mutable SKU

A star schema has dimensions directly joined to the fact table. A snowflake schema normalises dimensions further (category → subcategory → product). Snowflake saves storage; star schema means fewer joins — Redshift and the exam usually prefer star for query simplicity.

Slowly changing dimensions (Types 0–4)

TypeBehaviourWhen to use
Type 0Never update — retain original valueImmutable attributes (date of birth)
Type 1Overwrite in placeCorrect errors; history does not matter
Type 2New row with effective dates; current flagTrack history — "what did we believe at close?"
Type 3Add limited prior-value columnOnly need previous value, not full history
Type 4Mini-dimension for volatile attributesHigh-cardinality changes (customer segment flapping daily)

Type 2 is the exam favourite. When a customer's address changes, close the old row and insert a new one:

-- Stage incoming change from Glue/Lambda
CREATE TEMP TABLE stg_customer AS
SELECT 1001 AS customer_nk, 'Jane Doe' AS name, '456 Oak St' AS address, 'CA' AS state;

-- Close existing current row
UPDATE dim_customer
SET effective_to = CURRENT_DATE - 1,
    is_current   = FALSE
WHERE customer_nk = 1001
  AND is_current  = TRUE;

-- Insert new version
INSERT INTO dim_customer (
  customer_key, customer_nk, name, address, state,
  effective_from, effective_to, is_current
)
SELECT
  (SELECT COALESCE(MAX(customer_key), 0) + 1 FROM dim_customer),
  customer_nk, name, address, state,
  CURRENT_DATE, DATE '9999-12-31', TRUE
FROM stg_customer;

Snowflake versus star on AWS

Snowflake normalises dimensions (e.g. dim_product → dim_category → dim_department). Fewer duplicated strings in dimensions but extra joins at query time. On Redshift, star schemas with DISTSTYLE ALL dimensions avoid repeated network shuffles — the exam answer for warehouse modelling is usually star + denormalised dimensions unless the question emphasises storage cost over query simplicity.

Open table formats

Plain Parquet files in S3 are immutable blobs — you cannot update one row or delete a GDPR record without rewriting whole files. Apache Iceberg, Hudi, and Delta Lake add a transactional metadata layer on top of Parquet so lakes behave more like warehouses.

Problems they solve

  • ACID transactions — concurrent writers do not corrupt each other.
  • Row-level UPDATE, DELETE, MERGE — GDPR erasure, CDC upserts.
  • Time travel — query snapshots before a bad deploy.
  • Schema evolution — add, rename, drop columns with metadata tracking.
  • Partition evolution — change partition layout without rewriting all history (Iceberg especially).

For DEA-C01, Iceberg + Athena is the combination most often correct when the question mentions time travel or MERGE on a lake without spinning up Redshift.

Iceberg DDL and MERGE

CREATE TABLE dea_lab.events_iceberg (
  event_id   bigint,
  user_id    bigint,
  event_type string,
  event_ts   timestamp,
  payload    string
)
PARTITIONED BY (day(event_ts))
LOCATION 's3://dea-lab-ab-4821/curated/events_iceberg/'
TBLPROPERTIES (
  'table_type' = 'ICEBERG',
  'format'     = 'parquet',
  'write_compression' = 'zstd'
);
MERGE INTO dea_lab.events_iceberg t
USING dea_lab.events_staging s
ON t.event_id = s.event_id
WHEN MATCHED THEN
  UPDATE SET event_type = s.event_type,
             event_ts   = s.event_ts,
             payload    = s.payload
WHEN NOT MATCHED THEN
  INSERT (event_id, user_id, event_type, event_ts, payload)
  VALUES (s.event_id, s.user_id, s.event_type, s.event_ts, s.payload);

When plain Parquet is enough

Parquet lake suffices

  • Append-only batch loads (nightly ETL)
  • Partition overwrite per day (INSERT OVERWRITE)
  • No row-level deletes required
  • Single writer per partition

Reach for a table format

  • GDPR/CCPA delete-my-data requests
  • CDC upserts from DMS or Debezium
  • Concurrent streaming + batch writers
  • Auditable time travel after bad deploys
Glue version matters. Iceberg/Hudi/Delta write support requires Glue 4.0 or 5.0 Spark jobs. A Glue 2.0 exam distractor cannot write Iceberg natively. See Section 4 job types and Section 13 EMR for Spark-heavy alternatives.

Data quality and observability

Glue Data Quality and DQDL

DQDL (Data Quality Definition Language) is a declarative ruleset attached to a Glue table or evaluated inline in an ETL script. Under the hood, AWS implements many rules with Deequ (Amazon's open-source Spark library for unit tests on data).

Rules:
  - IsComplete "ID"
  - IsComplete "Email"
  - IsUnique "ID"
  - ColumnValues "Age" between 0 and 120
  - ColumnLength "State" = 2
  - RowCount > 10
  - CustomSql "SELECT COUNT(*) FROM primary WHERE ID IN (SELECT ID FROM primary GROUP BY ID HAVING COUNT(*) > 1)" = 0

Results publish to:

  • Glue console — per-run quality score and rule breakdown.
  • CloudWatch metrics — Glue/DataQuality namespace for alarms.
  • EventBridge — glue.dataQualityRulesetEvaluationCompleted for routing failures to SNS, Lambda, or Step Functions.

EvaluateDataQuality in a Glue job

from awsglue.transforms import EvaluateDataQuality

rules = """
  IsComplete "ID"
  IsUnique "ID"
  ColumnValues "Age" between 0 and 120
"""

dq = EvaluateDataQuality.apply(
    frame=dyf,
    ruleset=rules,
    publishing_options={
        "CloudWatchMetricsEnabled": True,
        "ResultsS3Prefix": "s3://dea-lab-ab-4821/staging/dq-results/"
    }
)

# Split passing vs failing rows (conceptual — use DynamicFrame filters)
good = dq.filter(lambda x: x["DataQualityEvaluationResult"] == "Passed")
bad  = dyf.join(good, on=["ID"], how="left_anti")

bad.toDF().write.mode("append").json("s3://dea-lab-ab-4821/rejected/customers/")

DataBrew profile jobs

AWS Glue DataBrew profile jobs compute column-level statistics (null %, distinct count, histograms) without writing rules first — useful for discovery before you codify DQDL. Profiles do not block pipelines; rulesets do.

Quarantine, do not fail. Exam scenarios with "ensure bad records do not block the pipeline" → write failures to rejected/ or a dead-letter path, alert via EventBridge, continue processing valid rows. Failing the entire job on one malformed line is the distractor.

Observability beyond DQ scores

  • Pipeline SLAs — custom CloudWatch metric when curated partition lands; alarm if empty after deadline.
  • Row-count reconciliation — source COUNT vs target COUNT in Step Functions choice state.
  • Freshness — S3 LastModified on latest partition versus expected schedule.
  • Lineage — Glue Data Catalog lineage; exam expects awareness that impact analysis traces upstream tables.

Wire alarms to CloudWatch dashboards. Data quality without alerting is a report, not observability.

Amazon DataZone

Amazon DataZone is a data management service for cataloguing, discovering, sharing and governing data across AWS accounts and business teams. It sits above the technical metadata in the Glue Data Catalog and adds a business-facing portal, glossary, and request/approval workflow so domain owners can publish datasets without every consumer needing direct Lake Formation grants.

Relationship to Glue Data Catalog and Lake Formation

DataZone does not replace the Glue Data Catalog or Lake Formation. Publishers register assets that point at existing Glue databases and tables (or Redshift datashares). DataZone adds business metadata, ownership, and a governed subscription path. When a subscription is approved, DataZone orchestrates the underlying Lake Formation permission grant or cross-account share — consumers never bypass the approval queue with a raw IAM policy.

Lake Formation alone enforces who can run SQL against which columns; it has no business glossary, no self-service portal, and no cross-domain publishing workflow. DataZone fills that gap for organisations adopting a data mesh — decentralised domain ownership with central interoperability standards.

Data mesh and when the exam picks DataZone

In a data mesh, each business unit owns its datasets ("data products"), publishes them with documented SLAs, and consumers discover them through a federated catalogue rather than a central ETL team copying everything into one warehouse. DataZone is AWS's managed implementation of that federated catalogue plus governance workflow.

DataZone versus Lake Formation alone. "Analysts need a searchable business catalogue with approval before accessing Finance tables in another account" → Amazon DataZone. "Block SELECT on the SSN column for role AnalystRole" → Lake Formation column filter. "Register technical schema and run crawlers" → Glue Data Catalog. DataZone is the answer when the scenario emphasises discovery, glossary, subscription workflow, or cross-team data sharing — not when the question is purely SQL-level permission enforcement.

Pipeline patterns and programming concepts

Domain 1 lists programming concepts explicitly: idempotency, checkpointing, window functions, CTEs, joins, MERGE, and version control. The course demonstrates individual services; this section ties the semantics together.

Delivery semantics

GuaranteeMeaningAWS realityYour job
At-most-onceMay lose recordsRare — usually a bugNot acceptable for billing data
At-least-onceMay duplicateKinesis, SQS, Lambda retries, FirehoseDesign idempotent sinks
Exactly-onceNeither lose nor duplicateManaged Flink with checkpoints; Iceberg MERGEHard — simulate with idempotency keys

Idempotency means replaying the same input leaves the system in the same state: partition overwrite, MERGE on natural key, deterministic S3 keys (date=2026-08-03/run_id=abc/), DynamoDB conditional writes.

Streaming concepts

  • Checkpointing — Flink/KCL persist offsets + state so a restart continues without reprocessing from scratch (unless you reset).
  • Watermarks — event-time progress; allow late-arriving records within a lateness bound.
  • Late data — route to a side output or include in the next window via allowed lateness.

Streaming detail lives in Section 6; the exam tests vocabulary, not Flink API trivia.

Batch patterns

  • Backfill — reprocess historical partitions after a logic fix; use Step Functions to loop dates.
  • Partition overwrite — idempotent daily load: replace year=2026/month=08/day=03/ entirely.
  • Append — only when duplicates are impossible or deduplicated downstream.

CDC patterns

SourceMechanismTarget pattern
RDS / Oracle / SQL ServerAWS DMS CDC tasksIceberg MERGE or S3 Parquet + Glue bookmark
DynamoDBDynamoDB Streams → Lambda/FirehoseAggregate to S3; MERGE on partition key

Fan-in, fan-out, DLQs

Fan-out: one Kinesis stream → multiple consumers (enhanced fan-out in Section 6). Fan-in: many S3 prefixes → one Glue job with catalog partitions. Dead-letter queues (DLQ): SQS queue or S3 prefix for poison messages that exceed max retries. Poison pill: one bad record that crashes the parser — skip, quarantine, alert.

Retry: exponential backoff with jitter (sleep(base * 2^attempt + random) prevents thundering herd on recovery. SQS visibility timeout must exceed Lambda processing time.

Retry policy with jitter (Lambda pseudocode)

import random, time

def call_with_retry(fn, max_attempts=5):
    for attempt in range(max_attempts):
        try:
            return fn()
        except TransientError:
            if attempt == max_attempts - 1:
                raise
            base = 2 ** attempt
            time.sleep(base + random.uniform(0, 1))

Generative AI and vector stores

DEA-C01 now includes GenAI integration at the data-engineering layer: where embeddings live, how Knowledge Bases retrieve context, and what you build versus what Bedrock runs. You are not tested on transformer maths.

Amazon Bedrock

Bedrock is the managed API layer for foundation models. Data engineers care about the data plane around it — document ingestion, embedding endpoints, Knowledge Base sync, and logging invocations to CloudWatch — not fine-tuning math. Integration with SageMaker appears when custom models or batch transform are in scope; Bedrock is the shortcut when a pre-trained model suffices.

  • Foundation-model access — API calls to Claude, Titan, Llama, etc. without hosting weights.
  • Model choice — trade-off latency, cost, context window, and task (embeddings vs chat).
  • On-demand — pay per input/output token; spiky workloads.
  • Provisioned throughput — reserved model units for steady high QPS; cheaper at scale, commitment required.

The data engineer's job in RAG

  1. Chunking — split documents (512–1024 tokens) with overlap; preserve metadata (source, page).

AWS CodeDeploy

AWS CodeDeploy automates application deployments to EC2 instances, on-premises servers, Lambda functions, and ECS services. In a data-platform pipeline it sits alongside CodePipeline (orchestration stages) and CodeBuild (compile and test): CodeBuild produces an artifact (Glue script zip, Lambda bundle, CloudFormation template); CodePipeline invokes a deploy action that CodeDeploy executes with a chosen strategy. For Glue and EMR, deployment is usually CloudFormation or the Glue/EMR API promoting a script and job definition — CodeDeploy applies when the compute surface is Lambda, ECS/Fargate stream processors, or EC2-hosted custom runners.

Deployment strategies

Each strategy trades deployment speed, cost (duplicate infrastructure), and blast radius if the new version is bad.

StrategyHow it worksCostRisk
In-placeStop old version, install new version on the same instances — brief downtime or reduced capacity during the swapLowest — no duplicate fleetHighest — all traffic hits the new build immediately; bad deploy affects everyone
Blue/greenRun old (blue) and new (green) environments in parallel; shift traffic or DNS atomically after validationHighest — double compute until cutoverLow — instant rollback by routing back to blue
CanaryRoute a small percentage of traffic to the new version first; monitor metrics; gradually increase or roll backMedium — partial duplicate capacity during the rampLow — limited blast radius on the first slice
LinearIncrease traffic to the new version in fixed steps on a timer (e.g. 10% every minute) until 100%Medium — similar to canary with predictable step timingLow–medium — automated progression; bad metrics should trigger rollback mid-ramp

For Lambda, traffic shifting uses weighted aliases. CodeDeploy (or SAM/CDK deployment preferences) configure pre-set ramp shapes:

  • Canary10Percent5Minutes — 10% to the new version for five minutes, then the remainder if healthy.
  • Linear10PercentEvery1Minute — add 10% per minute until fully shifted.
  • AllAtOnce — equivalent to in-place for Lambda; fastest, no gradual validation.

Pair any ramp with a CloudWatch alarm on errors or latency; CodeDeploy can automatically roll back the alias weights when the alarm enters ALARM state — the exam expects you to know rollback is alarm-driven, not manual only.

Blue/green and canary for data pipelines

Request-driven services (API Gateway → Lambda) can shift traffic percentages directly. Batch and ETL pipelines have no live traffic to split — you adapt the same ideas:

  • Dual-write — run old and new Glue job versions writing to separate prefixes (curated_v1/ and curated_v2/) until reconciliation passes.
  • Dual-read / shadow — new job writes to a staging table; compare row counts, checksums, and sample diffs against production output before cutover.
  • Canary slice — process one partition or one tenant through the new logic while the rest stays on the old path; expand partition scope after metrics hold.
  • Cutover — swap the Athena view, Spectrum external table location, or Redshift view to point at the validated prefix; keep the old path for quick rollback.

Glue and EMR job versions are deployed by promoting an S3 script and updating the job definition (or CloudFormation stack parameter) — not by HTTP traffic shifting. A new Glue job version runs on the next scheduled trigger or manual start; blue/green for Glue means two job definitions or two stacks writing to parallel outputs until you reconcile and rename.

Deployment strategy choice. "Zero-downtime Lambda with gradual validation and automatic rollback on error rate" → canary or linear alias shifting with CloudWatch alarm rollback. "Fastest deploy to a dev EC2 agent, downtime acceptable" → in-place. "Validate a new ETL output against production before switching analysts to it" → blue/green table or prefix swap with reconciliation — not Lambda traffic weights.

Resilience, backup and disaster recovery

Data engineers own RPO/RTO targets for pipelines and stores. The exam contrasts backup-and-restore with pilot light and multi-Region active-active — mainly as cost vs recovery-time trade-offs.

RPO and RTO

  • RPO (Recovery Point Objective) — maximum acceptable data loss measured in time. Snapshot every hour → RPO ≤ 1 hour.
  • RTO (Recovery Time Objective) — maximum downtime before service restores. Cold backup RTO is days; active-active RTO is minutes.

Four DR strategies

StrategyRTOCostAWS pattern
Backup and restoreHours–daysLowestS3 cross-Region replication async; restore Redshift from snapshot
Pilot lightTens of minutesLowCore data replicated; compute scaled to zero until failover
Warm standbyMinutesMediumSmaller Redshift/ RDS replica running in DR Region
Multi-site active-activeNear zeroHighestDynamoDB global tables, Aurora Global Database, Route 53 routing

Cross-Region and service-native HA

  • S3 — CRR/SRR; 99.999999999% durability in-Region; versioning + MFA delete for accidental overwrite protection (Section 7).
  • Redshift — automated snapshots; snapshot copy to DR Region; RA3 with managed storage.
  • DynamoDB — global tables for multi-Region active-active; PITR for in-Region undo.
  • Aurora — Global Database < 1 second cross-Region replication lag for DR.

Interview questions

Answer each one out loud before opening it. These are drawn from the extras material — the gaps practice exams hit hardest.

Why does converting CSV to Snappy Parquet reduce Athena cost more than GZIP-compressing the CSV?Cost

GZIP on CSV reduces bytes on disk but Athena still reads every column in every row because CSV is row-oriented. Snappy Parquet adds column pruning — a query referencing three of thirty columns reads roughly ten percent of the logical data — plus compression inside column encodings.

GZIP CSV also loses splittability unless files are small, limiting parallelism. Parquet row groups split across workers. The exam's "most cost-effective" answer is almost always columnar + partition pruning, not compression alone.

Explain Type 2 slowly changing dimension and when you would use it instead of Type 1.SQL

Type 2 preserves history by closing the old dimension row (effective_to, is_current=false) and inserting a new row with a new surrogate key when an attribute changes. Type 1 overwrites in place.

Use Type 2 when reports must answer "what did we know at the time?" — regulatory reporting, historical revenue by store manager, any metric tied to dimension state at transaction time. Type 1 is for corrections where history does not matter.

When would you choose Apache Iceberg over plain Parquet on S3?Architecture

Choose Iceberg when you need row-level updates or deletes (GDPR), MERGE/upsert CDC, concurrent writers, time travel after bad deploys, or partition layout changes without rewriting terabytes of history.

Plain partitioned Parquet is fine for append-only daily batches with partition overwrite idempotency. Iceberg adds metadata overhead but unlocks warehouse semantics on the lake — Athena and Glue 4.0+ support it natively.

How does Glue Data Quality integrate with the rest of an observability stack?Design

DQDL rulesets evaluate inside crawlers or ETL jobs (Deequ engine). Results expose a quality score in Glue, publish metrics to CloudWatch for alarms, and emit EventBridge events on completion. Failed rules can trigger Lambda, SNS, or Step Functions to quarantine data without stopping the entire pipeline.

DataBrew profiles complement rulesets by discovering null rates and distributions before you codify thresholds.

What is idempotency and how do you achieve it on at-least-once AWS infrastructure?Design

Idempotency means running the same operation twice produces the same end state. Kinesis, SQS, and Lambda retries deliver at-least-once, so duplicates are expected.

Techniques: deterministic S3 output paths with overwrite, Iceberg/Redshift MERGE on natural keys, partition-level replace, DynamoDB conditional writes, deduplication on event ID in Flink. Design sinks first, not after the first duplicate incident.

Where do embeddings live in a Bedrock Knowledge Base architecture, and who keeps them fresh?Architecture

Bedrock Knowledge Bases typically store embeddings in OpenSearch Serverless (vector index) with source documents in S3. Alternatives: Aurora pgvector, Kendra, Neptune Analytics depending on hybrid search and transactional needs.

The data engineer owns ingestion: chunk documents, call Bedrock embedding models, bulk index, and re-sync on S3 changes via EventBridge/Lambda. Bedrock orchestrates retrieval at query time; it does not watch your buckets automatically without configured sync.

A CFO asks why Athena spend doubled after a new dashboard launched. What do you check first?Troubleshooting

Open Cost Explorer filtered to Athena, then inspect query metrics in CloudWatch or Athena recent queries. Look for full-table scans, missing partition filters, CSV/JSON formats, and dashboards that select *.

Fix order: add partition predicates, convert to Parquet with column pruning, enable workgroup bytes-scanned limits, consider result reuse for identical queries. One CTAS job often pays back in the first billing cycle.

Compare backup-and-restore vs pilot light DR for a Redshift-centric warehouse.Comparison

Backup and restore: automated snapshots plus cross-Region copy; lowest cost; RTO hours to days while you provision a cluster and restore. Good for regulatory backup requirements.

Pilot light: snapshots replicated continuously, minimal DR cluster or Serverless namespace ready to scale; RTO tens of minutes; moderate cost. Exam questions trade money vs downtime — active-active global Redshift is rare; DynamoDB/Aurora are the usual active-active examples.

What is the small-files problem and how does it hurt both performance and cost?Performance

Thousands of files under ~10 MB force engines to open many S3 objects, increasing LIST/plan time and reducing sequential read throughput. Athena may scan less data but still slow; Glue pays DPU-minutes for overhead.

Target 128 MB–1 GB per file via compaction jobs, sensible repartition, or Iceberg rewrite data files. Common cause: streaming micro-batches landing every minute.

How would you deploy a Glue ETL job change safely through dev, staging and prod?Design

Store scripts and CloudFormation/CDK in Git; CodePipeline runs CodeBuild pytest on transforms, deploys stacks per environment with parameterized bucket/database names. Integration test against fixture data in dev; promote artifact unchanged to staging; run DQ ruleset gate; blue/green or partition swap in prod.

Never edit the Glue console in prod directly — exam "least operational overhead" for ongoing changes still means automation, not manual clicks.

A Kinesis consumer receives duplicate records after a deployment. Is this a bug?Gotcha

Usually no — Kinesis delivery is at-least-once. After restarts or shard merges, consumers replay from the last checkpoint. The bug is a non-idempotent sink (blind INSERT without dedup).

Fix the sink: MERGE on event ID, dedup window in Flink, or idempotent DynamoDB write. Enhanced fan-out does not change semantics.

DynamoDB item is 450 KB. What pattern fixes it without leaving DynamoDB?Exam

400 KB is the hard item limit — you cannot store 450 KB in one item. Store the blob in S3, keep metadata and an S3 pointer in DynamoDB (< 400 KB). Alternatively split across items with a shared partition key and sort keys — but S3 offload is the exam's usual answer for large payloads.

Recap

  • Columnar Parquet + Snappy + partition pruning cuts Athena scans 80–95%; CSV GZIP alone does not enable column pruning.
  • Target file sizes 128 MB–1 GB; compact small files from streaming ingest.
  • Star schema: facts with measures at defined grain; dimensions with DISTSTYLE ALL on Redshift; facts DISTKEY + date SORTKEY.
  • SCD Type 2 closes old rows and inserts new versions — required when history affects metrics.
  • Iceberg/Hudi/Delta add ACID, MERGE, time travel; plain Parquet suffices for append-only overwrite pipelines.
  • Glue Data Quality + DQDL → CloudWatch + EventBridge; quarantine bad rows to rejected/ instead of failing the job.
  • At-least-once is the AWS default — design idempotent sinks (MERGE, partition overwrite, dedup keys).
  • Bedrock RAG: chunk → embed → vector index (OpenSearch/pgvector) → retrieve; engineer keeps index fresh.
  • Know billing units: TB scanned, DPU-hour, RPU-second, shard-hour, WCU/RCU, GB-month.
  • Deploy pipelines as code; test transforms with pytest; promote via parameterized stacks; use CodeDeploy canary/linear for Lambda, prefix reconciliation for Glue.
  • Amazon DataZone adds business catalogue and subscription workflow on top of Glue Catalog and Lake Formation — pick it for cross-team discovery, not column filters alone.
  • RPO/RTO drives DR strategy cost; S3 durability ≠ backup — versioning and CRR protect against logic errors.
  • Memorise hard limits: Athena 10 MB min scan, Kinesis 1 MB record, DynamoDB 400 KB item, Lambda 15 min, SQS 256 KB / 14-day retention.
