AWS Lake Formation

AWS Lake Formation is a governance layer on top of Amazon S3 and the AWS Glue Data Catalog. It does not replace S3 storage or Glue crawlers — it centralises who may read which tables, columns, and rows in a data lake, and enforces those permissions across Athena, Redshift Spectrum, EMR, and Glue jobs without duplicating IAM policies on every bucket prefix.

How it works — end to end

Lake Formation implements a governed data lake in five practical steps that mirror the deck workflow:

  1. Define data sources — register S3 buckets and paths (and optional JDBC connections) as Lake Formation data lake locations. LF becomes the data lake administrator for those prefixes.
  2. Data ingestion — copy or stream data into registered locations (Glue jobs, DMS, Firehose, or manual upload). Blueprints automate common ingestion patterns.
  3. Catalog and organise — Glue crawlers discover schema and partitions; Lake Formation creates or adopts databases and tables in the Glue Data Catalog.
  4. Clean and transform — Glue ETL, EMR, or Athena CTAS prepare curated datasets; LF permissions apply to outputs in registered locations.
  5. Set up security and analyse — grant SELECT, INSERT, ALTER, etc. at database, table, column, or row level; consumers query through Athena, Redshift Spectrum, or EMR with LF enforcing filters.

Relationship to the Glue Data Catalog and IAM

Lake Formation does not replace the Glue Data Catalog — it governs access to catalogue objects. Crawlers and Glue jobs still create databases, tables, and partitions in Glue; LF registers underlying S3 locations and issues grants on those catalogue entries. When Athena runs SELECT * FROM sales, the engine asks Lake Formation whether the caller's IAM role has SELECT on that table (and applies any column/row filter). If allowed, LF returns temporary data-access credentials scoped to the permitted S3 prefixes and columns.

IAM still matters: principals must be able to call Athena, Glue, and lakeformation:GetDataAccess. LF sits between IAM and the data — denying at the LF layer blocks access even when S3 bucket policy would allow s3:GetObject. For encrypted tables, KMS key policies must also permit the role. Think of IAM as "can this principal use the analytics service" and LF as "which tables/rows/columns may they see".

What Lake Formation adds over S3 bucket policies plus IAM

Plain S3 + IAM can restrict object prefixes, but analysts need table-level access in SQL engines. Without Lake Formation you must either expose whole prefixes or maintain duplicate ACL logic in every service. Lake Formation adds:

  • Central catalogue permissions — one grant model for Athena, Redshift Spectrum, EMR, and Glue against Glue Catalog tables, not per-bucket IAM policies.
  • Column-, row-, and cell-level security — data filters hide columns or rows at query time; IAM and bucket policies cannot express this.
  • LF-Tags (tag-based access control) — attach tags like Environment=Prod, Classification=PII; grant permissions by tag expression instead of naming every table.
  • Cross-account sharing via RAM — share databases/tables without copying data; recipient creates resource links for local querying.
  • Audit trail — Lake Formation logs permission changes; combined with CloudTrail for API calls.
The exam question. "Centralise fine-grained access to a shared S3 data lake queried by multiple teams through Athena" → Lake Formation on top of Glue Catalog + S3. Bucket policies alone are insufficient when the requirement mentions column-level, row-level, or cross-account table sharing.
Everyday analogy — S3 bucket policies are building keys (which floors you may enter). Lake Formation is the room-level access card system — same building, but marketing may enter the "campaigns" room while finance enters "ledger", even though both share one S3 warehouse.

Security — database, table, and column grants

Database-level grants apply to all current and future tables in the database. Table-level is the most common — SELECT for analysts, INSERT for ETL roles. Column-level lists permitted columns in a data filter. Row-level adds a filter expression (e.g. region = 'EU'). Cell-level combines both — only specific columns for rows matching the predicate.

Hybrid access mode means a principal needs both an IAM permission (e.g. s3:GetObject on the prefix) and a Lake Formation grant. IAM Allowed Principals (IAM-only passthrough) lets legacy IAM policies satisfy access without an LF grant — useful during migration but bypasses LF row/column filters for those principals. New data lake locations should use LF-first permissions.

Cross-account sharing

  • Share setup — producer shares databases or tables (or LF-Tag policies) through AWS Resource Access Manager (RAM).
  • Granular access — data filters on shared tables enforce row/column rules in the consumer account.
  • Resource links — consumer creates a resource link (alias) in their Glue Catalog; Athena and Spectrum query through the link without copying S3 data.
  • Troubleshooting — verify RAM invitation accepted, LF DESCRIBE on resource link, IAM role has lakeformation:GetDataAccess, and S3 bucket policy allows consumer account if using external locations.

Grant permissions — CLI examples

aws lakeformation grant-permissions \
  --principal DataLakePrincipalIdentifier=arn:aws:iam::123456789012:role/DataAnalystRole \
  --resource '{"Table": {"DatabaseName": "sales_db", "Name": "orders"}}' \
  --permissions SELECT

aws lakeformation grant-permissions \
  --principal DataLakePrincipalIdentifier=arn:aws:iam::123456789012:role/FinanceRole \
  --resource '{"LFTagPolicy": {"ResourceType": "TABLE", "Expression": [{"TagKey": "Team", "TagValues": ["Finance"]}]}}' \
  --permissions SELECT DESCRIBE

The second command is LF-TBAC: any table tagged Team=Finance becomes readable by the Finance role without naming each table.

Amazon EMR

Amazon EMR (Elastic MapReduce) runs open-source big-data frameworks — Apache Spark, Hive, HBase, Presto/Trino, and Flink — on managed Hadoop clusters. You pay for underlying EC2 (or EKS/Fargate for newer deployment models) plus an EMR hourly premium per instance. EMR wins when you need petabyte-scale custom Spark/Hive, existing Hadoop tooling, or frameworks Glue does not expose.

Security — IAM, VPC, and encryption

Every cluster uses IAM roles: a service role for EMR itself, an EC2 instance profile for nodes (S3 access via EMRFS, CloudWatch logs), and optional Auto Scaling role. Launch clusters in private subnets with security groups restricting SSH and internal Hadoop ports. Enable encryption at rest for EBS volumes and S3 (SSE-S3 or SSE-KMS) and in-transit TLS between nodes. Kerberos authentication is supported for multi-tenant Hadoop environments migrated from on-premises.

Frameworks and when to choose EMR

  • Apache Spark — default for ETL, ML feature prep, and large-scale SQL (spark-sql).
  • Apache Hive — HiveQL over catalogued data; metastore backed by Glue on modern clusters.
  • HBase — random read/write on billions of rows (time-series keys, wide-column NoSQL on HDFS).
  • Presto / Trino — interactive federated SQL across S3, Hive, JDBC sources.
  • Apache Flink — stateful stream processing on EMR (batch and streaming unified).

  • Primary (master) node — tracks cluster health, schedules jobs, hosts HDFS NameNode. Always On-Demand; never Spot-only.
  • Core nodes — run tasks and store HDFS blocks. Minimum count depends on HDFS replication; losing all core nodes loses data not on S3.
  • Task nodes — compute-only workers; no HDFS. Safe to run on Spot Instances for fault-tolerant, idempotent jobs.

Cluster types — transient versus long-running

Transient clusters launch, run one or more steps, then terminate — ideal for nightly batch and cost control. Long-running clusters stay up for streaming (Spark Structured Streaming), interactive notebooks, or always-on Hive/Presto. Long-running costs more but avoids cluster startup latency (minutes).

Apache Hive

Apache Hive is a distributed SQL layer over files in HDFS or S3. It stores table metadata in a Hive metastore (schema, location, partitions) while data stays in open formats (Parquet, ORC, text). On AWS, the metastore maps to the Glue Data Catalog, so Athena, EMR, and Redshift Spectrum share one catalogue.

Hive metastore and Glue Data Catalog

The metastore holds databases, table DDL, column types, SerDe info, and partition lists. When EMR is configured with hive.metastore.client.factory.class=com.amazonaws.glue.catalog.metastore.AWSGlueDataCatalogHiveClientFactory, DDL in Hive creates tables in Glue. Crawlers and Glue jobs see the same tables without export/import.

External versus managed tables

  • Managed tables — Hive owns data; DROP TABLE deletes S3/HDFS files. Rare in modern lakes (prefer explicit lifecycle on S3).
  • External tables — Hive stores metadata only; DROP TABLE removes catalogue entry but leaves data. Standard for data lakes where multiple engines read the same prefix.

Partitions

Partition columns (e.g. year, month, day) map to directory paths. Queries with partition predicates skip irrelevant paths — critical for cost and performance on S3.

CREATE EXTERNAL TABLE IF NOT EXISTS sales_db.orders (
  order_id    BIGINT,
  customer_id INT,
  amount      DECIMAL(10,2),
  order_ts    TIMESTAMP
)
PARTITIONED BY (region STRING, dt STRING)
STORED AS PARQUET
LOCATION 's3://dea-lab-ab-4821/curated/orders/';

ALTER TABLE sales_db.orders ADD IF NOT EXISTS
  PARTITION (region='us-east', dt='2026-08-01')
  LOCATION 's3://dea-lab-ab-4821/curated/orders/region=us-east/dt=2026-08-01/';

-- After bulk load of new date folders:
MSCK REPAIR TABLE sales_db.orders;

Where Hive still beats Spark SQL

  • Hive ACID transactions on ORC for row-level updates/deletes in batch pipelines (Spark has Delta/Iceberg alternatives).
  • Mature HiveQL UDF ecosystem and existing on-prem Hive scripts during migration.
  • Hive LLAP (Low Latency Analytical Processing) for interactive SQL on Hadoop without a separate Presto cluster.
  • Strict Hive compatibility when third-party tools expect Hive metastore Thrift API verbatim.

For greenfield ETL on AWS, Glue Spark or EMR Spark SQL usually replaces Hive — but exam scenarios mentioning "existing Hive warehouse" or "HiveQL" expect EMR + Glue Catalog integration.

HiveQL and execution engines

HiveQL resembles SQL with Hadoop extensions (CLUSTER BY, DISTRIBUTE BY, LATERAL VIEW EXPLODE). On EMR, the default execution engine is often Tez or Spark (Hive-on-Spark) rather than classic MapReduce — still invoked via hive -e or Beeline. Partition pruning is automatic when the WHERE clause filters on partition columns; missing partitions require MSCK REPAIR or manual ALTER ADD PARTITION after new S3 folders land.

Amazon Managed Grafana

Amazon Managed Grafana is a fully managed deployment of open-source Grafana for operational dashboards — metrics, logs, and traces. It targets DevOps and SRE monitoring, not business BI. Reach for Grafana when you need real-time infrastructure dashboards; reach for QuickSight when business analysts need governed BI over warehouses and SPICE.

Workspace and data sources

  • Workspace — logically isolated Grafana server (URL, plugins, users). One workspace per environment is common.
  • Data sources — CloudWatch, AMP, X-Ray, Timestream, OpenSearch, Prometheus, SQL databases via plugins.
  • Authentication — AWS IAM Identity Center (successor to SSO) or external SAML 2.0; map IdP groups to Grafana roles (Admin, Editor, Viewer).

Amazon OpenSearch Service

Amazon OpenSearch Service is a managed search and analytics engine for log analytics, full-text search, and real-time application monitoring. A domain is a cluster of nodes; OpenSearch Dashboards provides Kibana-compatible visualisation. Ingest via API, Kinesis Data Firehose, Lambda, or Logstash.

ISM policies automate transitions: e.g. day 7 hot → warm, day 30 snapshot to cold, day 365 delete. Moving back to hot for reindexing is supported but slower than hot-only indices. The deck also mentions archiving to Glacier for unused indices — in practice ISM snapshot-to-S3 and cold tier achieve the same cost goal within OpenSearch without exporting to a separate Glacier vault.

Performance — JVM memory pressure and circuit breakers

OpenSearch runs on the JVM. Each shard, segment, and field cache consumes heap. CloudWatch metric JVMMemoryPressure measures heap usage; sustained values above ~85% risk GC thrashing and rejected requests. OpenSearch uses circuit breakers (parent, fielddata, request) to fail queries before out-of-memory kills — a breaker trip means "reduce load or scale up", not "disable safety". Mitigations: fewer/larger shards on new indices, force-merge old segments, delete unused indices, move cold data to UltraWarm, upgrade to larger r6g data nodes, and avoid wildcard queries on high-cardinality text fields in production.

Shard sizing

Shard count is set at index creation and is hard to change without reindexing. Guidance:

  • Target 10–50 GB per primary shard for log analytics (balance parallelism vs overhead).
  • Each shard consumes JVM heap — over-sharding causes JVMMemoryPressure and circuit breaker trips.
  • Formula starting point: primary_shards = ceil(expected_index_size_GB / 30), then validate against query latency and heap.
  • Replicas multiply storage but improve read throughput and HA — number_of_replicas: 1 minimum for production.

Ingestion paths

  • Kinesis Data Firehose — near-real-time delivery from streams/logs to OpenSearch with optional Lambda transform; handles buffering and retries.
  • Lambda — custom parsing/enrichment on CloudWatch Logs subscriptions or S3 events before bulk index.
  • Logstash / OpenSearch Ingestion — managed ingestion pipelines (successor patterns to self-managed Logstash).

Snapshots and ISM

Register an S3 snapshot repository on the domain; take automated snapshots for restore and migration. Index State Management (ISM) policies move indices to UltraWarm after N days, snapshot to cold tier, then delete — controlling cost without manual curation.

Security — FGAC, IAM, and network isolation

Fine-grained access control (FGAC) enables an internal user database or IAM-based roles mapped to OpenSearch security roles. Index-level, document-level, and field-level permissions restrict which indices a user searches. External IdPs integrate via SAML 2.0 or OpenID Connect for SSO.

  • IAM principal access — attach IAM policies allowing es:ESHttp* on the domain ARN; FGAC maps the IAM role to OpenSearch permissions. Useful for Lambda/Firehose delivery roles.
  • Internal user database — master user defined at domain creation; additional users in Dashboards security UI when FGAC enabled.
  • VPC domain — endpoints only in your VPC; no public internet path. Access from Dashboards, Lambda, or Firehose requires VPC endpoints or same-VPC placement.
  • Public domain — domain endpoint on internet; combine resource-based access policies with FGAC and IP allow lists.
  • Encryption — require HTTPS (TLS 1.2+); enable encryption at rest with KMS on EBS; optional node-to-node encryption.
  • Audit logs — publish search, index, and error logs to CloudWatch or S3 for compliance forensics.

Reliability — dedicated masters, multi-AZ, and snapshots

Production domains should use three dedicated master nodes (small instance types suffice — masters coordinate, they do not hold all data) across three AZs to avoid split-brain. Data nodes run in multi-AZ with replica shards on different AZs. Register an S3 snapshot repository (repository-s3 plugin configured on domain) and schedule automated snapshots; restore to a new domain for DR tests. Cross-cluster replication copies indices to a follower domain in another Region for geo-redundancy.

OpenSearch Serverless

OpenSearch Serverless removes domain capacity planning. Collections (time series, search, vector) auto-scale in OpenSearch Compute Units (OCUs). Data and indexing OCUs bill separately; ideal for spiky log volumes without provisioning r6g data nodes. Integrates with Lambda, S3, and Kinesis for ingestion. Trade-off: less manual control over shard topology and version plugins versus managed domains.

Memory pressure. When JVMMemoryPressure stays high, scale up data nodes, reduce shard count on new indices, delete unused indices, or move old data to UltraWarm/Cold — not "add more replicas" (replicas increase memory use).

Amazon QuickSight

Amazon QuickSight is AWS's serverless business intelligence service. Authors build analyses and publish dashboards; readers consume them in-browser or embedded in apps. Data comes from SPICE (in-memory cache) or direct query to live sources.

SPICE capacity planning

Each Standard author includes 10 GB SPICE per user; Enterprise authors share pooled capacity purchased per GB ($0.38/GB/month beyond included allocation). Size imports by aggregating in Athena/Redshift before SPICE load when possible — importing a 500 GB fact table into SPICE fails or incurs heavy overage. Incremental refresh (Enterprise) updates changed partitions only. When data exceeds SPICE or must be live, switch the dataset to direct query and accept source latency/cost.

Authentication to data sources

QuickSight runs in the AWS service account and assumes an IAM role you configure (or auto-created) to read S3, Athena, Glue Catalog, Redshift, and RDS. For Athena, the role needs S3 read on query results and data paths plus Glue catalog permissions. For Redshift, use a Redshift data source with credentials stored in QuickSight or IAM-based federation. For RDS/Aurora in a private VPC, create a VPC connection (Enterprise) — QuickSight attaches ENIs in your subnets with security groups allowing inbound from QuickSight to the database port.

Embedded analytics

QuickSight Embedded (Enterprise) registers domains and generates signed URLs or uses the embedding SDK to place dashboards in SaaS apps. Row-level security rules still apply per embedded viewer identity.

Row-level and column-level security

Row-level security (RLS) applies dataset rules that filter rows based on the viewer's QuickSight username or group membership — e.g. {region} = <user's region attribute>. Rules attach to datasets before dashboards; the same dashboard shows different rows per viewer. Column-level security hides sensitive fields (salary, SSN) from specific groups while other columns remain visible — configured per dataset field.

Both features require Enterprise edition. Standard edition shows all rows/columns in a published dashboard to every reader with access.

Amazon Q in QuickSight

Amazon Q adds generative BI: users ask questions in natural language ("What were top products last quarter?") and Q generates visuals, narratives, or SQL-backed answers from SPICE or direct-query datasets. Requires Author Pro or Reader Pro licensing on top of Enterprise. Q respects RLS — users only see answers scoped to their permitted rows.

Cross-Region and cross-account access patterns

QuickSight runs in a chosen Region; datasets can reference cross-Region S3/Athena if IAM permits. For cross-account private databases: Enterprise VPC connections plus VPC peering, Transit Gateway, PrivateLink, or RAM-shared VPC (slides 491–493). Standard edition cannot deploy ENIs into your VPC — RDS/Redshift must allow inbound from the QuickSight service CIDR or use public endpoints (not recommended for production).

RLS and column-level security are Enterprise-only. Exam scenarios where "each sales rep sees only their region" → QuickSight Enterprise with row-level security dataset rules, not IAM alone.

Traps that catch people

  • LF replaces IAM — Teams grant LF SELECT but forget the analyst role still needs IAM S3 and lakeformation:GetDataAccess. Athena fails with opaque access errors. Fix both layers.
  • IAMAllowedPrincipals silently bypasses LF — The backwards-compatibility setting lets legacy IAM-only principals ignore LF table permissions. New LF grants appear ignored until you disable it account-wide.
  • Spot on master or sole core nodes — Spot interruption on the master kills the cluster; core nodes hold HDFS replicas. Use Spot on task nodes only for fault-tolerant compute.
  • Instance fleets with custom scaling policies — Custom CloudWatch scaling attaches to instance groups, not fleets. Fleets use managed scaling only — exam wording matters.
  • EMRFS consistent view — Pre-2020 exams required consistent view for S3 LIST consistency. S3 is strongly consistent now — enabling consistent view adds unnecessary overhead on new clusters.
  • HDFS as durable storage — Core node HDFS dies with the cluster. Treat HDFS as shuffle cache; land curated data on S3 via EMRFS.
  • Over-sharding OpenSearch — Too many small shards exhaust JVM heap on data nodes. Aim for 10–50 GB per shard on new indices; use _shrink or reindex to consolidate.
  • Skipping dedicated masters at scale — Data nodes doubling as masters under load cause cluster instability. Production domains use three dedicated master nodes.
  • QuickSight Standard for RLS — Row-level and column-level security require Enterprise. Buying Standard and trying dataset user filters fails compliance scenarios.
  • SPICE for huge raw tables — Importing hundreds of GB into SPICE triggers overage charges or import failure. Aggregate in Athena/Redshift first or use direct query.
  • Grafana vs QuickSight — Managed Grafana monitors infrastructure metrics; it is not governed BI with SPICE and RLS. Wrong tool for "sales dashboard per region".
  • Cross-account LF without resource link — Consumer accepts RAM share but analysts query empty catalog until a resource link is created and granted locally.

Production patterns

A governed lake pattern registers S3 locations in Lake Formation, applies LF-Tags by domain (Finance, PII), and shares read-only resource links to consumer accounts via RAM — Athena and Redshift Spectrum query through the same Glue Catalog without copying data. Row and column data filters enforce analyst scope; IAM execution roles for Glue and Athena still need least-privilege S3 and lakeformation:GetDataAccess. Disable IAMAllowedPrincipals only after every principal has LF grants.

Batch analytics compute

  • EMR Serverless or transient EMR for nightly Spark on S3.
  • Spot task nodes; core nodes On-Demand; Glue Data Catalog as Hive metastore.
  • Long-running custom libraries or sustained clusters → EMR on EC2 over Glue when DPU cost or Spark version control wins.

Search and BI layer

  • OpenSearch with ISM: hot → UltraWarm → cold snapshot; dedicated masters in prod.
  • QuickSight Enterprise with SPICE for shared KPIs; direct query for live ops.
  • Managed Grafana for pipeline/infra metrics — not analyst dashboards.

Anti-pattern: running EMR as a 24×7 cluster for one hourly job because "startup is slow". Transient clusters with bootstrap actions, EMR Serverless, or Glue for the same transform cost less and reduce patch burden. Another anti-pattern: OpenSearch as primary data lake — index derived metrics and logs, not canonical Parquet.

Interview questions

Answer each one out loud before opening it.

What does Lake Formation add that S3 bucket policies and IAM cannot do alone?Exam

LF adds centralised catalogue permissions on Glue tables with column-, row-, and cell-level data filters, LF-Tags for tag-based access, and cross-account sharing via RAM without copying data. IAM/S3 operate at the object prefix level and cannot enforce SQL-level column or row restrictions across Athena, Spectrum, and EMR consistently.

Explain LF-TBAC versus naming every table in a grant.Security

LF-Tags attach key-value labels to databases/tables/columns. Grants reference tag expressions (Team=Finance) so new tagged tables inherit access automatically. Named-resource grants list explicit database.table pairs — simpler for small lakes but operational overhead grows with table count.

When would you choose EMR over AWS Glue for an ETL job?Comparison

Choose EMR for petabyte-scale Spark/Hive, custom JARs, HBase/Presto/Flink, fine-grained cluster tuning, or migrating on-prem Hadoop. Choose Glue when the question emphasises least operational overhead, native Data Catalog/crawler integration, or standard scheduled PySpark ETL at GB–TB scale.

Why should Spot Instances be used on task nodes but not the sole master node?Cost

The master coordinates the cluster and runs critical services — losing it stops the cluster. Task nodes are stateless workers; Spot interruption with 2-minute notice is acceptable if YARN retries failed tasks. Core nodes hold HDFS data — Spot-only core fleets risk data loss if too many nodes disappear at once.

What is the difference between EMR core nodes and task nodes?Architecture

Core nodes run tasks and participate in HDFS — they store replicated blocks. Task nodes only run YARN containers; they do not store HDFS data. Scale task nodes for bursty compute; keep minimum core count for HDFS replication when not using S3-only (EMRFS) storage.

How does the Hive metastore relate to the Glue Data Catalog on EMR?Fundamentals

EMR can configure the Hive metastore client to use AWS Glue Data Catalog as its backing store. DDL executed in Hive creates/updates Glue tables — the same metadata Athena and Spectrum query. Migration path: point EMR at Glue instead of self-managed RDS/Derby metastore.

Managed Grafana or QuickSight for a CloudWatch ops dashboard?Design

Managed Grafana — built for metrics/logs/traces, native CloudWatch and Prometheus plugins, alerting on infra thresholds. QuickSight — business BI over warehouses with SPICE, RLS for analysts, not ideal for sub-minute infra alerting.

OpenSearch domain is hitting JVMMemoryPressure alerts — what do you check?Troubleshooting

Check shard count (too many small shards), force-merge or delete old indices, move aged data to UltraWarm/Cold, reduce field cardinality, scale up data node RAM, and verify queries are not returning huge result sets. Circuit breakers trip before OOM — fix root cause rather than disabling breakers.

How do you size primary shards for a new log index?Performance

Estimate total index size, divide by target 30 GB per shard (within the 10–50 GB guidance), round up for primaries. Set replicas separately for HA/read scaling. Shard count is fixed at creation — overshooting wastes heap; undershooting creates hot shards.

SPICE or direct query for a Redshift dashboard refreshed every minute?Design

Direct query — SPICE refresh minimum is daily (Standard) or hourly (Enterprise), not every minute. Direct query hits live Redshift for current data; accept higher source load or aggregate in Redshift materialised views first.

How does QuickSight reach an RDS instance in a private subnet?Security

Enterprise edition with a VPC connection: QuickSight creates ENIs in your subnets/security groups allowing traffic to RDS. Standard edition cannot — the database would need a public endpoint or unsupported workarounds. Cross-account uses VPC peering, PrivateLink, or shared VPC.

Cross-account Lake Formation share is accepted but Athena cannot query the table — what do you verify?Troubleshooting

Confirm RAM share status, consumer created a resource link, LF DESCRIBE/SELECT granted on the link to the analyst role, IAM role has lakeformation:GetDataAccess, Athena workgroup uses that role, and underlying S3 bucket policy permits consumer if required.

Recap

  • Lake Formation = governance on Glue Catalog + S3; column/row/cell filters and LF-Tags; cross-account via RAM + resource links.
  • Hybrid access mode requires both IAM and LF grants; IAM Allowed Principals bypass LF for migration only.
  • EMR: master (1) + core (HDFS + tasks) + task (compute-only, Spot OK); transient clusters use --auto-terminate.
  • EMRFS → S3 is strongly consistent — no EMRFS consistent-view needed on new workloads.
  • Instance fleets = mixed Spot/On-Demand; instance groups = custom auto scaling policies.
  • Glue = least ops ETL; EMR = petabyte/custom Hadoop/Spark/HBase/Presto.
  • Hive external tables + partitions; metastore → Glue Catalog on EMR.
  • Grafana = ops metrics/logs; QuickSight = business BI + SPICE + RLS (Enterprise).
  • OpenSearch: watch JVMMemoryPressure; 10–50 GB/shard; UltraWarm/Cold for cost; ISM for lifecycle.
  • QuickSight VPC data sources and RLS require Enterprise; Athena/Redshift via IAM role assumed by QuickSight.
