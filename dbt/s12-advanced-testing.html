Unit tests

A unit test runs a model against fake input rows you define in YAML — no warehouse data required. dbt substitutes your mocked given inputs for the real upstream relations, executes the model SQL, and compares the result to expect rows. If they differ, the test fails.

Generic and singular tests scan whatever is currently in the warehouse. That is fine for integrity checks on production-sized tables, but awkward for logic you want to verify in isolation: a join predicate, a CASE branch, an edge date. Unit tests let you pin down those cases with three rows of input and an expected output, run them in CI without seeding the warehouse, and fail fast when someone changes the SQL.

Why mart_fullmoon_reviews is a good first unit test

The mart joins fct_reviews to seed_full_moon_dates and labels each review as 'full moon' or 'not full moon' based on whether the review date equals the day after a full moon. The business rule is easy to get wrong by one day; a unit test with three review dates and one seed date proves the join and CASE logic without loading 273 lunar rows or millions of reviews.

The model SQL (from Section 9) ends with:

{{ config(
  materialized = 'incremental',
  incremental_strategy='microbatch',
  event_time='review_date',
  begin='2009-06-20',
  batch_size='year',
  full_refresh=false,
  tags = ['fact'],
  schema='mart'
) }}

WITH fct_reviews AS (
    SELECT * FROM {{ ref('fct_reviews') }}
),
full_moon_dates AS (
    SELECT * FROM {{ ref('seed_full_moon_dates') }}
)

SELECT
  r.*,
  CASE
    WHEN fm.full_moon_date IS NULL THEN 'not full moon'
    ELSE 'full moon'
  END AS is_full_moon
FROM
  fct_reviews r
  LEFT JOIN full_moon_dates fm
  ON (TO_DATE(r.review_date) = DATEADD(DAY, 1, fm.full_moon_date))

The unit test does not load the incremental config branches; it exercises the core SELECT. For incremental-specific branches, use overrides in the unit test YAML (see Deeper detail).

The join and label portion alone:

SELECT
  r.*,
  CASE
    WHEN fm.full_moon_date IS NULL THEN 'not full moon'
    ELSE 'full moon'
  END AS is_full_moon
FROM
  fct_reviews r
  LEFT JOIN full_moon_dates fm
  ON (TO_DATE(r.review_date) = DATEADD(DAY, 1, fm.full_moon_date))

unit_tests.yml syntax

Unit tests live in YAML files anywhere under model-paths. The course places them in models/mart/unit_tests.yml next to the mart they exercise. Each entry names the test, the target model, mocked inputs, and expected output.

  • airbnb/
    • models/
      • mart/
        • mart_fullmoon_reviews.sql
        • unit_tests.yml ← new in this section
unit_tests:
  - name: unittest_fullmoon_matcher
    model: mart_fullmoon_reviews
    given:
      - input: ref('fct_reviews')
        rows:
          - {review_date: '2025-01-13'}
          - {review_date: '2025-01-14'}
          - {review_date: '2025-01-15'}
      - input: ref('seed_full_moon_dates')
        rows:
          - {full_moon_date: '2025-01-14'}
    expect:
      rows:
        - {review_date: '2025-01-13', is_full_moon: "not full moon"}
        - {review_date: '2025-01-14', is_full_moon: "not full moon"}
        - {review_date: '2025-01-15', is_full_moon: "full moon"}

Reading the given and expect blocks

given is a list of mocked upstream relations. Each item has input: (a ref(), source(), or literal relation) and rows: (inline dicts). dbt replaces those relations with ephemeral tables built from your rows when it compiles and runs the unit test. You only mock what the model reads directly — here fct_reviews and seed_full_moon_dates, not staging models further upstream.

expect holds the rows the model should produce. Comparison is set-based: column values must match. Order may matter depending on adapter and dbt version; for deterministic tests, keep inputs small and sort keys explicit in the model if needed.

Walk through the expected labels:

  • 2025-01-13 — no seed row where full_moon_date + 1 day = 2025-01-13, so LEFT JOIN misses and the CASE yields 'not full moon'.
  • 2025-01-14 — seed has full moon on 2025-01-14, but the join compares review date to 2025-01-15 (14 + 1), so still no match.
  • 2025-01-15 — matches DATEADD(DAY, 1, '2025-01-14'), join hits, label is 'full moon'.
Unit tests are logic tests, not data-quality tests. Use them for transforms you own. Keep scanning live tables with generic tests from Section 11 for production volume checks.

Unit tests compile the model SQL against mocked CTEs. They do not require fct_reviews or the seed to exist in the warehouse, though in practice you usually run them after the project parses cleanly.

Inline rows versus SQL fixtures

The course uses inline dict rows because the inputs are tiny. For wider schemas, use format: sql with a multi-line SQL string that returns rows, or reference a fixture file. Inline dicts are the fastest to read in notes and diffs:

    given:
      - input: ref('fct_reviews')
        format: sql
        rows: |
          SELECT '2025-01-13'::DATE AS review_date
          UNION ALL
          SELECT '2025-01-14'::DATE
          UNION ALL
          SELECT '2025-01-15'::DATE

On BigQuery use DATE '2025-01-13' instead of Snowflake cast syntax. Unit tests compile with your active adapter, so fixture SQL must be warehouse-valid.

What unit tests do not cover

Unit tests validate the SQL logic dbt compiles for a model. They do not replace:

  • Performance testing on billion-row facts
  • Freshness checks on sources (Section 9)
  • Cross-model singular tests like consistent_created_at from the Section 11 exercise (reviews after listing creation)
  • Package-provided expectations from dbt_expectations (Section 16)

The course exercise after unit tests asks you to write a singular test in tests/consistent_created_at.sql joining dim_listings_cleansed to fct_reviews — that belongs in Section 11 as a warehouse scan, not a unit test, because it validates referential timing across two built models on real data.

SELECT * FROM {{ ref('dim_listings_cleansed') }} l
INNER JOIN {{ ref('fct_reviews') }} r
USING (listing_id)
WHERE l.created_at > r.review_date
Everyday analogy — unit tests are like checking a recipe with three measured ingredients in a test kitchen. Generic data tests are like tasting every dish that leaves the restaurant on a Friday night. You need the kitchen test to trust the recipe; you need the tasting to catch supplier problems.

Selecting and scoping test runs

The same --select syntax that limits models applies to tests. Scope runs to one model's test suite, or run only unit tests across the project.

All tests attached to one model

When you change mart_fullmoon_reviews, run every test that depends on it — generic column tests, singular tests, and unit tests — without executing the whole project:

dbt test --select mart_fullmoon_reviews

This is the everyday loop during development: edit SQL, run scoped tests, fix, repeat. It is cheaper than dbt test with no selector on a large project.

Only unit tests

The test_type:unit selector runs unit tests and skips generic and singular tests. Useful in CI when you split fast logic tests from heavy warehouse scans:

dbt test --select "test_type:unit"
CommandRunsSkips
dbt testAll testsNothing
dbt test --select mart_fullmoon_reviewsTests on that model (unit + data)Tests on other models
dbt test --select "test_type:unit"All unit testsGeneric and singular tests
dbt test --select dim_listings_minimum_nightsOne singular test by nameEverything else (Section 11)
Combine selectors when needed. dbt test --select mart_fullmoon_reviews,test_type:unit narrows further. Use dbt ls --select test_type:unit to preview which tests match before running them.

dbt build versus dbt test

dbt build runs models, tests, snapshots, and seeds in DAG order. When a test fails, downstream nodes skip. In development you often run dbt test --select model_name after a quick dbt run on the same model. In CI, dbt build --select state:modified+ keeps cost down while still running tests on what changed.

Model contracts

A model contract is a promise about the shape of the relation dbt will create: which columns exist and what type each one is. With enforced: true, dbt validates that promise at compile time against your model SQL and fails the build before the warehouse runs anything if the contract is broken.

Data tests from Section 11 run after the table exists and scan rows. Contracts run before or during the build and catch structural breaking changes: a renamed column, a dropped field, a type widening you did not document. Downstream tools, APIs, and BI layers that depend on a stable schema benefit most.

Enabling a contract on dim_hosts_cleansed

Add a config.contract block and declare data_type on every column in the model YAML:

  - name: dim_hosts_cleansed
    config:
      contract:
        enforced: true
    columns:
      - name: host_id
        data_type: integer
      - name: host_name
        data_type: string
      - name: is_superhost
        data_type: string
      - name: updated_at
        data_type: timestamp
      - name: created_at
        data_type: timestamp

What enforced: true actually checks

At parse/compile time dbt compares the contract to the model's inferred output schema:

  • Every contracted column must appear in the model SELECT.
  • Column types must match the declared data_type (with adapter-specific mapping).
  • Extra columns not listed in the contract may fail the build depending on adapter and contract settings.

If you rename host_name to host_display_name in SQL but forget the YAML, compilation fails with a contract violation instead of silently breaking every dashboard that selected host_name.

When to adopt contracts

Enable contracts on models that external systems consume: marts synced to CRM tools, tables exposed through a semantic layer, or datasets listed in an exposure (Section 15). Staging models change often during development; contracting every src_ model adds friction without benefit.

A practical rollout: start with one published mart or dimension, enforce the contract in CI via dbt build, and expand to other gold tables once the team keeps YAML in sync with SQL changes.

Warehouse differences

Contracts are supported on Snowflake, BigQuery, Databricks, Redshift, and Postgres with adapter-specific type names. On BigQuery, use types like int64 and string in YAML where the adapter expects them. When unsure, run dbt compile and read the error — it names the mismatch explicitly.

Warehouse constraints

Constraints go further than contracts: dbt emits actual DDL constraints on the created table — NOT NULL, primary keys, foreign keys, and check clauses — where the adapter supports them. Tests detect violations after the fact; constraints prevent some violations at insert time.

The course switches dim_hosts_cleansed from a view to a table before adding constraints. Views cannot carry warehouse constraints in most engines; tables can.

{{
  config(
    materialized = 'table'
  )
}}
WITH src_hosts AS (
    SELECT * FROM {{ ref('src_hosts') }}
)
SELECT
    host_id,
    NVL(host_name, 'Anonymous') AS host_name,
    is_superhost,
    created_at,
    updated_at
FROM src_hosts

Constraint YAML on dim_hosts_cleansed

Combine contract, constraints, and data tests in one model block. Constraints and tests overlap for not_null and unique — constraints enforce at the warehouse; tests still scan and report in dbt's test output:

  - name: dim_hosts_cleansed
    config:
      contract:
        enforced: true
    columns:
      - name: host_id
        data_type: integer
        constraints:
          - type: not_null
        data_tests:
          - unique

      - name: host_name
        data_type: string
        constraints:
          - type: not_null

      - name: is_superhost
        data_type: string
        data_tests:
          - accepted_values:
              arguments:
                values: ['t', 'f']

      - name: updated_at
        data_type: timestamp

      - name: created_at
        data_type: timestamp

Constraint types and warehouse support

Not every adapter enforces every constraint type as real DDL. dbt still documents the intent in the manifest; some adapters emit informational constraints only.

Constraint typeWhat it doesSnowflakeBigQueryPostgresDatabricks
not_nullColumn cannot be NULLEnforcedEnforced (NOT NULL)EnforcedEnforced
primary_keyUnique + not null on column setEnforcedNot as PK DDL; use testsEnforcedEnforced (Unity Catalog)
foreign_keyValues must exist in parent tableEnforced (limited)Not enforcedEnforcedEnforced (Unity Catalog)
checkBoolean SQL expression on rowEnforced (recent)LimitedEnforcedVaries
uniqueUnique valuesVia tests primarilyVia testsUNIQUE constraintVia tests / UC
Constraints are not a replacement for dbt tests on every warehouse. On BigQuery, many constraint types are metadata-only. Keep data_tests: for unique, relationships, and custom checks even when you declare constraints. The dbt docs matrix for your adapter is authoritative.
Foreign keys on full refreshes. Building a child table before its parent exists fails FK creation. dbt's DAG ordering usually prevents this, but manual runs with partial selectors can hit ordering issues. Use dbt build for constraint-heavy projects.

Constraints versus data tests

A not_null constraint stops bad inserts at the warehouse boundary. A not_null generic test scans the whole table on every test run and reports rows in dbt's failure output (and optional store_failures table from Section 11). Teams use both: constraints for hard guarantees on published marts, tests for observability and CI reporting.

primary_key and foreign_key examples

The course stops at not_null plus a unique data test on host_id. In production you might add explicit key constraints when the adapter enforces them:

      - name: host_id
        data_type: integer
        constraints:
          - type: not_null
          - type: primary_key

      - name: listing_id
        data_type: integer
        constraints:
          - type: not_null
          - type: primary_key

      - name: host_id
        data_type: integer
        constraints:
          - type: foreign_key
            expression: "dim_hosts_cleansed (host_id)"

Foreign key syntax and whether expression or to: is required depends on dbt version and adapter. Read the constraints page for your warehouse before enabling on large facts — enforced FKs on incremental loads can add insert latency.

check constraints

A check constraint embeds a boolean expression that each row must satisfy. Example: price > 0 on a listings mart. Postgres and Snowflake enforce checks in DDL; BigQuery often does not. Overlap with custom generics like positive_values is common — choose constraint for warehouse-native enforcement, generic test for portable CI reporting.

Three layers of protection on a published mart

Contract — compile-time column names and types (enforced: true)
Constraints — warehouse DDL where adapter supports it (not_null, keys, check)
data_tests — runtime scans and custom generics (Section 11 + this section)
Materialization note from the repo. The comment at the top of dim_hosts_cleansed.sql reminds you that the model started as a view and became a table specifically for constraints. Reverting to view removes DDL enforcement.

Custom generic tests

When built-in tests are not enough, write a reusable generic test as a Jinja macro in tests/generic/. The {% test name(...) %} block defines SQL that returns failing rows; zero rows means pass — same contract as singular tests, but parameterised and attachable from YAML.

Section 11 uses stock generics like unique and relationships. Here you author positive_values to assert a numeric column is strictly greater than zero, and reuse it on minimum_nights and price without duplicating SQL.

positive_values

Parameters model and column_name are injected by dbt when the test is attached to a column. Return any row where the column fails the rule:

{% test positive_values(model, column_name) %}
SELECT * FROM {{ model }} WHERE {{ column_name }} <= 0
{% endtest %}

Attach it in YAML like any built-in generic:

      - name: minimum_nights
        data_tests:
          - positive_values

How {% test %} differs from {% macro %}

Generic tests live under tests/generic/ and use the {% test %} … {% endtest %} block. dbt registers them as test macros with the test name. Reusable SQL fragments without the test wrapper belong in macros/ and are covered in Section 13.

Generic test naming and discovery

Files in tests/generic/ register macros named after the file (without extension). The test name in YAML is the macro name: positive_values, not positive_values.sql. List discovered tests with:

dbt ls --select dim_listings_cleansed --resource-type test

Package tests like dbt_utils.unique_combination_of_columns follow the same YAML attachment pattern but live in dbt_packages/ after dbt deps (Section 13).

Debugging a failing positive_values test

When the test fails, dbt reports a failure count. Query the failing rows directly with the same predicate, or enable store_failures from Section 11 to persist them:

SELECT listing_id, minimum_nights
FROM {{ ref('dim_listings_cleansed') }}
WHERE minimum_nights <= 0

In the course project, dim_listings_cleansed normalises minimum_nights from 0 to 1 in SQL, so the test often passes. If you remove that CASE from Section 7, the test fails until data or logic is fixed — demonstrating why custom generics encode team rules explicitly.

Multiple columns with one generic

Attach the same generic to many columns independently. Each attachment becomes its own test node with a generated name:

      - name: minimum_nights
        data_tests:
          - positive_values

      - name: price
        data_tests:
          - positive_values

Each test scans one column. For multi-column rules (e.g. end date after start date), use a singular test or a custom generic with extra parameters.

Test parameters

Generic test macros can accept extra arguments beyond model and column_name. Declare them in the {% test %} signature and pass values from YAML under arguments:.

dbt injects standard parameters automatically based on where you attach the test. Column-level tests always receive model (a relation) and column_name (a string). Table-level tests like minimum_row_count only receive model plus whatever you add to the signature.

minimum_row_count with min_row_count

This test warns when a table has fewer rows than a threshold. It is a table-level test (no column), so the macro takes model and min_row_count:

{% test minimum_row_count(model, min_row_count) %}
{{ config(severity = 'warn') }}

SELECT
    COUNT(*) as cnt
FROM
    {{ model }}
HAVING
    COUNT(*) < {{ min_row_count }}
{% endtest %}

Attach with the argument value in YAML (current dbt 1.11 syntax nests args under arguments:):

  - name: dim_listings_cleansed
    data_tests:
      - minimum_row_count:
          arguments:
            min_row_count: 1000
          config:
            severity: error

The macro sets severity = 'warn' as a default inside the test body. The YAML config.severity: error overrides that default for this specific attachment — the listings dimension is critical enough that an unexpectedly small table should fail the pipeline, not just warn.

Argument nesting changed in dbt 1.8+. Older projects passed min_row_count: 1000 at the top level next to the test name. Current form uses arguments:. The course repo uses the modern shape.

Validating parameter wiring

After adding a parameterized generic, confirm dbt parsed the argument by listing the test node. The compiled test SQL in target/compiled/airbnb/tests/generic/ should show the literal threshold value substituted into the HAVING clause.

dbt compile --select minimum_row_count_dim_listings_cleansed_
type target\compiled\airbnb\tests\generic\minimum_row_count.sql

On Mac or Linux use cat target/compiled/... instead of type. If min_row_count is missing, the YAML arguments: block is mis-indented or the macro signature does not declare the parameter name.

Every test resolves to a severity: error (fail the run) or warn (log a warning, continue). Set severity in the test macro, in YAML per test, or dynamically with warn_if and error_if.

errorNon-zero on failurePrimary keys, revenue facts, legal reporting columns
warnZero unless configured otherwiseNice-to-have checks, staging tables, experimental marts

Precedence: YAML config on a specific test beats the default inside the macro. Project-level data_tests: config in dbt_project.yml (Section 11) can set defaults for all tests of a type.

Setting severity in three places

  1. Inside the test macro — {{ config(severity = 'warn') }} in minimum_row_count.sql applies to every use unless overridden.
  2. On the YAML attachment — config: severity: error under minimum_row_count: for one model.
  3. In dbt_project.yml — global defaults, e.g. all dbt_utils.expression_is_true tests warn in dev.

warn_if and error_if

For tests that return a count of failures, dbt can escalate or de-escalate based on how many rows failed. warn_if and error_if accept a Jinja expression, often comparing failure count to a threshold:

      - name: host_id
        data_tests:
          - relationships:
              arguments:
                to: ref('dim_hosts_cleansed')
                field: host_id
              config:
                warn_if: ">0"
                error_if: ">=500"

warn_if: ">0" means any failure warns. error_if: ">=500" upgrades to error only at scale — a handful of orphan keys from a late-arriving dimension might warn in CI while a systemic join break fails hard. Expressions refer to the number of failing rows dbt counted.

Do not warn on everything. Teams that set every test to warn train CI to ignore yellow output. Reserve warnings for thresholds you actually triage; keep contract-breaking columns at error.

dbt test — warn severity

dbt test --select minimum_row_count_dim_listings_cleansed_
15:22:11  Running with dbt=1.11.12
15:22:14  1 of 1 WARN 1 minimum_row_count_dim_listings_cleansed_ ............... [WARN 1 in 0.31s]
15:22:14  Completed successfully

A WARN line still shows Completed successfully with exit code 0 unless your orchestrator treats warnings as failures. Configure that explicitly in production pipelines.

Project-level test defaults

Combine with the data_tests: block in dbt_project.yml from Section 11 to set severity or store_failures for all tests under a folder:

models:
  airbnb:
    mart:
      +data_tests:
        +severity: warn

Specific test YAML config.severity: error on minimum_row_count overrides the folder default for that one attachment. Precedence: test YAML > macro inline config > project/folder config.

warn_if / error_if in practice

Graduated severity suits slowly drifting data: a relationships test on host_id might warn on ten orphan listings after a partial host load but error on ten thousand. Document thresholds in the test description so on-call engineers know when to escalate.

Traps that catch people

  • Unit test mocks wrong columns — YAML rows omit columns the model SELECT expects. dbt may infer NULLs or fail compilation. Match column names to the model output, not the raw source.
  • Expecting unit tests to need seeds loaded — mocked ref('seed_full_moon_dates') replaces the seed; you do not run dbt seed first for that test.
  • Contract without data_type on every column — partial contracts fail compilation or give false confidence. List all output columns.
  • Constraints on views — dim_hosts_cleansed must be a table. Building as view silently skips or errors on constraint DDL depending on adapter.
  • Assuming FK enforcement on BigQuery — FK metadata may exist but inserts are not blocked. Keep relationships tests.
  • Custom test returns zero rows on error — inverted logic (SELECT passing rows) makes failures pass. Return failing rows only.
  • Forgetting {% endtest %} — generic test files with unclosed blocks fail parse. One block per file in the course pattern.
  • severity: error in macro overridden accidentally — project-level test config can surprise you. Check effective config with dbt ls --resource-type test and manifest.
  • warn_if never errors — setting only warn_if without error_if on catastrophic tests lets CI stay green during outages.
  • Unit test for incremental without overrides — incremental models may need unit_tests: overrides: for config; otherwise mocked runs hit incremental branches incorrectly.
  • Duplicate enforcement — not_null constraint plus not_null test doubles maintenance without doubling protection on metadata-only adapters.
  • Changing join logic without updating unit test — the full-moon date offset change passes compile but fails unit test; that is intended — update expect rows when business rules change.
  • SQL fixture dialect mismatch — unit test SQL using Snowflake ::DATE syntax fails on BigQuery CI. Write fixture SQL for your adapter or use inline dict rows.
  • Contract on incremental without fixed schema — dynamic columns from macro loops break contracts. Contract explicit columns only on stable marts.
  • Running test_type:unit in old dbt — selector not recognised on pins before unit test support; upgrade or use test name selector.

Production patterns

Mature teams split the test pyramid: unit tests on PR for every model with non-trivial logic; contract enforcement on all marts exposed to BI; full data tests nightly or on state:modified+ in slim CI. Custom generics live in a shared internal package once the project outgrows two copies of the same SQL.

Constraints go on published gold tables with stable schemas, not on ephemeral staging. Foreign keys from facts to dimensions are common on Postgres and Snowflake; on BigQuery teams rely on relationships tests exclusively.

Pattern: two-stage CI

Job 1: dbt test --select test_type:unit + dbt compile (contracts). Job 2: data tests on modified nodes only. Keeps PR feedback under two minutes.

Anti-pattern: unit test everything

Mocking ten upstream refs for a wide mart is brittle. Unit-test the logic-heavy intermediate; data-test the final mart.

unit_tests:
  - name: test_incremental_filter
    model: fct_reviews
    overrides:
      macros:
        is_incremental: false
    given:
      - input: ref('src_reviews')
        rows:
          - {review_date: '2024-01-01'}
    expect:
      rows:
        - {review_date: '2024-01-01'}

Testing strategy summary

A balanced Airbnb project test suite after Sections 11 and 12 might look like: generic tests on every primary key column; singular tests for cross-model business rules; unit tests on marts with non-obvious joins; contracts on dimensions exposed to BI; constraints where Snowflake or Postgres enforce them; custom generics for domain rules like positive prices and minimum row counts on critical tables.

Review cost monthly: if test runtime exceeds model runtime, tighten selectors in CI and demote nice-to-have checks to warn severity.

Interview questions

Answer each one out loud before opening it.

What is the difference between a unit test and a generic data test?Comparison

A unit test mocks upstream inputs in YAML, runs the model SQL against those rows, and compares output to expected rows. It validates transform logic without warehouse data.

A generic data test scans the materialised relation in the warehouse and checks a property — uniqueness, not-null, relationships. It validates live data quality at runtime.

Use unit tests for logic and edge cases; use data tests for production integrity. See Section 11 for generic and singular tests.

How do given and expect work in a unit test?Testing

given lists mocked upstream relations with inline rows. dbt substitutes them for real tables when executing the model under test.

expect defines the rows the model should output. Mismatch fails the test. You mock direct parents only — for mart_fullmoon_reviews, mock fct_reviews and seed_full_moon_dates, not src_reviews.

How do you run only unit tests in dbt?Fundamentals

dbt test --select "test_type:unit" runs all unit tests and skips generic and singular tests. Quote the selector in shells that treat colon specially.

To run unit tests for one model, combine selectors: dbt test --select mart_fullmoon_reviews,test_type:unit. Use dbt ls --select test_type:unit to list matches first.

What does enforced: true on a model contract do?Modelling

It requires every contracted column to be declared with data_type and validates at compile time that the model SQL output matches that schema. Breaking changes fail before warehouse DDL runs.

Contracts catch structural drift; they do not scan for NULLs or duplicates. Pair with data tests and constraints for full coverage.

Why did dim_hosts_cleansed change from a view to a table?Design

Warehouse constraints (not_null, primary keys, foreign keys) apply to tables, not views, on most adapters. The course switches materialization to table before adding constraints in YAML.

Views remain valid for models without constraints. Published marts with DDL guarantees are often materialized as tables or incremental tables.

What is the difference between a constraint and a not_null data test?Comparison

A not_null constraint is DDL on the table that rejects inserts violating the rule at the warehouse boundary where the adapter enforces it.

A not_null generic test queries existing rows and reports violations in dbt's test output, optionally storing failures. It runs on schedule in CI, not at insert time.

On BigQuery, constraints may be metadata-only; tests remain essential.

How do you write a custom generic test?Jinja

Create a file in tests/generic/ with a {% test test_name(model, column_name) %} block. Write SQL returning failing rows; zero rows means pass. Close with {% endtest %}.

Reference the test in YAML under data_tests:. Extra parameters go in the macro signature and are passed via arguments: in YAML, as with minimum_row_count.

When would you use warn severity instead of error on a test?Production

Use warn for checks you want visibility on without blocking deploys — staging tables, soft SLAs, or thresholds handled with warn_if. The default in minimum_row_count.sql is warn.

Use error for tests that must gate merges: primary keys, financial totals, contracted marts. Override macro defaults in YAML config.severity per attachment.

What are warn_if and error_if?Testing

Config options that set severity based on how many rows failed. warn_if: ">0" warns on any failure; error_if: ">=500" errors only at scale.

Useful for relationships tests where a few orphan keys are tolerable but hundreds indicate a broken join. Without error_if, warnings may never fail the job.

Your unit test passes but production data is wrong. Why?Troubleshooting

Unit tests only cover mocked scenarios you wrote. Missing edge cases, wrong mock data, or upstream quality issues not exercised by the unit test still break production.

Unit tests prove logic for given inputs; data tests scan live tables. You need both. Add a generic test or singular test for the production failure mode you discovered.

Which warehouses enforce foreign key constraints from dbt?Certification

Snowflake, Postgres, and Databricks (Unity Catalog) enforce foreign keys in varying degrees. BigQuery records FK metadata but does not enforce referential integrity on insert.

Always keep relationships data tests for portable integrity checks regardless of constraint DDL.

How do you pass min_row_count to a custom generic test?Modelling

Declare min_row_count in the {% test minimum_row_count(model, min_row_count) %} signature. In YAML:

minimum_row_count: with arguments: min_row_count: 1000 under the model's data_tests:. Override severity with config: severity: error at the same level as arguments.

When would you choose a unit test over a singular test for mart_fullmoon_reviews?Design

Use a unit test when you care about the join and CASE logic for known dates without depending on warehouse volume or seed load order. Three mocked rows prove the offset rule cheaply on every PR.

Use a singular test when the assertion spans models on live data — like the consistent_created_at exercise — or when the rule requires production scale (no reviews before listing exists across the full history).

Keep the unit test for regression on the full-moon label; add singular or generic tests for cross-table rules documented in Section 11.

What happens if you enable enforced contract but omit data_type on one column?Gotcha

dbt fails at parse or compile time. Every column in the model output must declare data_type when contract.enforced is true. Partial contracts are not allowed.

The error points at the model YAML file. Add the missing column block before any warehouse build runs. This is stricter than data tests, which only need column names in YAML for documentation.

Can you attach minimum_row_count to a column?Testing

No. minimum_row_count is a table-level test — its macro signature only takes model and min_row_count, not column_name. Attach it under the model's data_tests:, not under a column.

Column-level generics like positive_values receive column_name automatically from dbt based on where you attach them in YAML.

How do contracts interact with model versions?Modelling

When a model uses the versions: feature (see Section 19), each version can declare its own columns, constraints, and contracts. The course's dim_hosts_cleansed v2 adds a stricter host_name column block inside the version definition while sharing contract config at the model level.

Unit tests can target a specific version with the versions: key in unit test YAML when you need to test breaking changes between v1 and v2 before deprecation.

Recap

  • Unit tests mock upstream rows in given and assert output in expect — no warehouse data required.
  • models/mart/unit_tests.yml tests mart_fullmoon_reviews full-moon labelling with three review dates and one seed date.
  • dbt test --select mart_fullmoon_reviews runs all tests on that model; dbt test --select "test_type:unit" runs only unit tests.
  • Built-in generic and singular tests are covered in Section 11 — this section adds unit tests, contracts, constraints, and custom generics.
  • Model contracts with enforced: true validate column names and types at compile time; every column needs data_type.
  • Constraints emit warehouse DDL (not_null, primary_key, foreign_key, check); support varies by adapter — tables required, not views.
  • dim_hosts_cleansed becomes a table with contract, not_null constraints, and existing data tests together.
  • Custom generic tests live in tests/generic/ using {% test name(...) %} ... {% endtest %}; return failing rows.
  • positive_values fails rows where column <= 0; attach like any generic under data_tests:.
  • minimum_row_count takes min_row_count via arguments:; default severity warn in macro, override in YAML.
  • warn_if and error_if tune severity by failure count for graduated CI gates.
  • Contracts catch schema breaks early; data tests and unit tests catch bad rows and bad logic respectively.
  • Use dbt ls --resource-type test to audit which tests attach to a model before a large test run.
  • Folder-level +severity in dbt_project.yml sets defaults; per-test YAML overrides win.
