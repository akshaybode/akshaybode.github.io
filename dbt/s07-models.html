Model basics

A dbt model is a .sql file under models/ containing a single SELECT statement. dbt reads the file, resolves Jinja macros like {{ ref() }}, wraps the result in the appropriate CREATE statement for the materialization, and executes it against your warehouse. You never write CREATE TABLE or CREATE VIEW yourself.

That separation is the core contract. Your job is to express the transformation logic; dbt's job is to turn it into DDL, run it in dependency order, and record what happened. If a model fails, dbt stops the run and does not build downstream models that depend on it.

Where models live

Every model file maps to one node in the DAG. The file name (without .sql) becomes the model name. A file at models/dim/dim_listings_cleansed.sql builds a model called dim_listings_cleansed. Subfolders are organisation only — they do not appear in the model name unless you configure a custom alias.

Naming conventions in this project

The Airbnb project uses prefixes to signal layer and purpose:

  • src_ — staging models. One raw source table in, renamed columns out. No business rules yet beyond aliasing.
  • dim_ — dimension models. Cleansed, conformed entities (listings, hosts) that other models join to.
  • fct_ — fact models (added in later sections). Events and metrics at a grain.
  • mart_ — presentation-layer models for a specific use case.

Prefixes are convention, not dbt syntax. dbt does not enforce them. Teams adopt them so a file name tells you its role before you open it.

Folder defaults from dbt_project.yml

Materialization and other behaviour can be set per folder in dbt_project.yml. The Airbnb project configures three layers before you touch individual model files:

models:
  airbnb:
    +materialized: view
    dim:
      +materialized: table
    src:
      +materialized: ephemeral

Staging in src/ is ephemeral: dbt inlines it as a CTE inside downstream models instead of creating a warehouse object. Dimensions in dim/ persist as tables. Anything outside those folders defaults to views. Section 8 goes deep on what each materialization means; for now, know that src_ models compile away and dim_ models become queryable tables in your dev schema.

Anatomy of a model file

A minimal model has three parts: an optional {{ config() }} block at the top, one or more CTEs in a WITH clause, and a final SELECT. The instructor builds every model in this section with CTEs even when a single SELECT would suffice, because the pattern scales: add a second CTE for a join, a third for a filter, without restructuring the file.

Everyday analogy — a model file is a recipe card. The CTEs are prep steps (wash the vegetables, dice the onion). The final SELECT is the dish. dbt is the kitchen that reads every recipe, works out which dishes need which prep steps first, and cooks them in order.

Rules every model must follow

dbt enforces a few constraints that differ from writing ad hoc SQL in a worksheet:

  • One statement per file. The file must compile to a single SELECT (or a WITH … SELECT). Multiple semicolon-separated statements fail parsing.
  • No DDL in model files. Do not write CREATE, INSERT, DELETE, or MERGE. dbt generates DDL from the materialization config. Exceptions exist (hooks, incremental logic via config) but not inline in the model body.
  • Valid Jinja. Every {% if %} needs {% endif %}; every {{ ref() }} must reference a model that exists or will exist in the same project.
  • Unique model names. Two files cannot produce the same model name. Collisions between models/a/foo.sql and models/b/foo.sql fail at parse time.
Valid in a model fileNot valid in a model file
WITH cte AS (…) SELECT …CREATE TABLE … AS SELECT …
{{ ref('upstream') }}INSERT INTO other_table …
{{ config(materialized='table') }}GRANT SELECT ON … (use hooks or orchestration)
CASE, window functions, joinsMultiple SELECT statements separated by semicolons

Python models (.py files) follow a different contract — introduced in Section 17. This section covers SQL models only.

ref() and the DAG

{{ ref('model_name') }} is how one dbt model references another. It records a dependency, resolves to the correct schema-qualified relation for your current target, and feeds the lineage graph. Every ref() call is an edge in the directed acyclic graph (DAG) dbt uses to determine build order.

What ref() does at compile time

When dbt compiles dim_listings_cleansed, it finds {{ ref('src_listings') }} and substitutes whatever that parent actually is in the warehouse. What gets substituted depends on the parent's materialization. If the parent is a table or a view, ref() resolves to its fully qualified relation name for the active target, such as "AIRBNB"."DEV"."DIM_HOSTS_CLEANSED". If the parent is ephemeral, as every src_ model in this project is, there is no relation to point at, so dbt inlines the parent's compiled SQL as a CTE at the top of the child's query instead.

That distinction explains something readers hit immediately in this section: you can query DIM_LISTINGS_CLEANSED in Snowflake after a run, but there is no SRC_LISTINGS object to query, even though dbt run reported success for it. Nothing is broken — the staging model exists only as text that was pasted into its children.

Three things happen in one macro call:

  1. Dependency registration. dbt adds an edge src_listings → dim_listings_cleansed to the manifest. Build order follows these edges.
  2. Environment resolution. The same project code builds into DEV for you and PROD for production without editing SQL. ref() looks up where that model was (or will be) built for the active target.
  3. Lineage. dbt docs generate and dbt Cloud's lineage view read these edges to draw the graph.
WITH src_listings AS (
  SELECT
    *
  FROM
    {{ ref('src_listings') }}
)
SELECT
  listing_id,
  listing_name,
  room_type,
  CASE
    WHEN minimum_nights = 0 THEN 1
    ELSE minimum_nights
  END AS minimum_nights,
  host_id,
  REPLACE(
    price_str,
    '$'
  ) :: NUMBER(
    10,
    2
  ) AS price,
  created_at,
  updated_at
FROM
  src_listings
Never hard-code a dbt-built table name. Writing FROM AIRBNB.DEV.SRC_LISTINGS instead of {{ ref('src_listings') }} compiles and may even run — but dbt no longer knows about the dependency. Build order breaks, lineage disappears, and a dev run might read a stale or wrong schema. This is the most common beginner mistake in dbt interviews and in production incidents.

How dbt picks build order

dbt topologically sorts the DAG. Models with no dependencies (or only source dependencies) compile first. Models that depend on them come next. Independent branches run in parallel up to the threads limit in profiles.yml.

When you run dbt run --select dim_listings_cleansed, dbt still builds src_listings first even though you did not name it, because dim_listings_cleansed depends on it. That behaviour is called parent inclusion and is the default for selection syntax.

After any parse or run, target/manifest.json contains every node and edge. Useful commands before you have run anything:

The + prefix means "this model and all its parents". A trailing + (dim_listings_cleansed+) means "this model and all its children". Section 17 covers the full selection language.

BigQuery and Postgres note. On Snowflake, dbt creates objects in the schema from profiles.yml (DEV in the course). On BigQuery, the schema maps to a dataset; on Postgres, a schema inside a database. ref() resolves correctly on all adapters — the difference is only in how the warehouse names and bills for the resulting objects.

Reading dependencies from manifest.json

After dbt parse or any run, each model node in target/manifest.json includes depends_on.nodes — a list of upstream model and source IDs. Tools (dbt Cloud, Elementary, custom scripts) read this file rather than re-parsing SQL.

For dim_listings_cleansed, you would see a dependency on model.airbnb.src_listings. That edge is what powers:

  • Automatic parent builds when you select a child model
  • Impact analysis ("if I change src_listings, what breaks?")
  • State-aware CI in production (Section 19)

Show direct parents of a model

dbt ls --select 1+dim_listings_cleansed --output json
# lists src_listings (depth 1) and dim_listings_cleansed
dbt ls --select 2+dim_listings_cleansed
# would include grandparents if dim_listings_cleansed had a longer chain

Compiled SQL

dbt is a compiler first and a runner second. Every model passes through Jinja rendering to produce warehouse-native SQL, which lands in target/compiled/. When you actually execute, dbt wraps that SQL in DDL and writes the final script to target/run/. Reading these files is the fastest way to understand what dbt really sent to Snowflake.

target/compiled versus target/run

DirectoryContentsWhen it appearsUse it to

target/manifest.jsonParsed project graph: nodes, edges, configs, compiled pathsAny parse commandPower selectors, defer, state comparison, docs
logs/dbt.logFull debug log with timings and adapter messagesEvery invocationConnection issues, adapter errors, slow model diagnosis

Path pattern for a model file at models/dim/dim_listings_cleansed.sql:

  • target/compiled/airbnb/models/dim/dim_listings_cleansed.sql
  • target/run/airbnb/models/dim/dim_listings_cleansed.sql

What compiled SQL looks like for a dimension

After dbt compile --select dim_listings_cleansed, the compiled file expands ref('src_listings'). Because src_listings is ephemeral, dbt inlines its entire query as nested CTEs rather than referencing a table:

WITH raw_listings AS (
    SELECT * FROM AIRBNB.RAW.RAW_LISTINGS
),
src_listings AS (
    SELECT
        id AS listing_id,
        listing_url,
        name AS listing_name,
        room_type,
        minimum_nights,
        host_id,
        price AS price_str,
        created_at,
        updated_at
    FROM raw_listings
)
SELECT
  listing_id,
  listing_name,
  room_type,
  CASE WHEN minimum_nights = 0 THEN 1 ELSE minimum_nights END AS minimum_nights,
  host_id,
  REPLACE(price_str, '$')::NUMBER(10, 2) AS price,
  created_at,
  updated_at
FROM src_listings
Typo check. If your compiled SQL shows a wrong column name or a missing CTE, the bug is in your model file or an upstream ephemeral model — not in dbt's compiler. Fix the source .sql and recompile.

What run SQL adds

The run artifact wraps compiled logic in the materialization DDL. For a table materialization (the dim/ folder default), dbt generates something like:

create or replace transient table AIRBNB.DEV.dim_listings_cleansed
as (
  -- compiled SELECT from target/compiled/... goes here
);

Exact DDL varies by adapter and dbt version. Snowflake uses CREATE OR REPLACE TRANSIENT TABLE for tables in dev; views get CREATE OR REPLACE VIEW. The course's on-run-start hook and per-model post-hook in dbt_project.yml also appear in run SQL or execute separately — check logs/dbt.log if row counts in audit_log do not match expectations.

Certification: know the difference between compile and run. Compile renders Jinja and writes target/compiled/; run executes warehouse DDL/DML and writes target/run/. Tests compile and execute query SQL; they do not use the materialization wrapper.

Debugging workflow the instructor recommends

When a model fails or returns unexpected results, the course teaches this sequence rather than sprinkling {{ log() }} everywhere:

  1. Read the error message in the terminal — compilation errors cite the model file; database errors cite the warehouse.
  2. Run dbt compile --select failing_model if compilation succeeded but results look wrong.
  3. Open target/compiled/airbnb/models/…/failing_model.sql and copy the SQL into a Snowflake worksheet.
  4. Execute piecemeal: run each CTE separately to find which step drops rows or throws a cast error.
  5. Fix the models/ file; never edit target/ directly.

Section 16 adds structured logging and test debugging, but compiled SQL remains the first tool for model logic issues.

Staging src_ models

Staging models sit between raw warehouse tables and business logic. In this project they live in models/src/, use the src_ prefix, and default to ephemeral materialization. Their job is narrow: read one raw table, rename columns to stable names the rest of the project will use, and change nothing else.

src_listings — the first model

The instructor creates models/src/src_listings.sql and reads directly from the raw table. In the video the FROM clause is hard-coded; the finished repo uses source() once sources are defined.

-- import raw_listings
WITH raw_listings AS (
        SELECT * FROM {{ source('airbnb', 'listings') }}
)
SELECT 
   id AS listing_id,
   listing_url,
   name AS listing_name,
   room_type,
   minimum_nights,
   host_id,
   price AS price_str,
   created_at,
   updated_at
FROM raw_listings

Notice what staging deliberately does not do: no CASE on minimum_nights, no casting price_str to a number. Those are cleansing rules belonging in the dimension layer. Keeping staging dumb makes it obvious where renames stop and business rules begin.

Building src_listings step by step (lecture flow)

The instructor creates the file in this order during the recording:

  2. Create src_listings.sql with a raw_listings CTE reading from AIRBNB.RAW.RAW_LISTINGS.
  3. Add the final SELECT with column renames only — no filters, no casts.
  4. Run dbt run --select src_listings. Terminal shows ephemeral SUCCESS; nothing new appears in SHOW TABLES IN SCHEMA DEV.

src_reviews

Reviews staging follows the same pattern: one CTE on the raw table, column renames in the final SELECT.

WITH raw_reviews AS (
    SELECT
        *
    FROM

    DATE AS review_date,
    reviewer_name,

Snowflake uppercases unquoted identifiers, so DATE in the raw table becomes review_date in staging. On Postgres you would quote reserved words; on BigQuery, backtick if needed. The staging layer is where you normalise naming once so downstream models never think about raw column quirks.

Dimension dim_ models

Dimension models apply business cleansing and typing on top of staging. They live in models/dim/, reference staging through ref(), and persist as tables by default. This section builds two dimensions: listings (with type casting and a minimum-nights rule) and hosts (with a null-name default).

dim_listings_cleansed

The listings dimension reads from src_listings and implements three cleansing steps the staging layer deferred:

  • Minimum nights. Raw data sometimes has 0; the business rule treats that as 1.
  • Price. price_str holds values like $125.00; strip the dollar sign and cast to NUMBER(10,2).
  • Column selection. Drop listing_url from the dimension if not needed for analytics (the course keeps the core attributes).
{{
  config(
    materialized = 'view',
    event_time='created_at'
  )
}} 
WITH src_listings AS (
    SELECT * FROM {{ ref('src_listings') }}
)
SELECT 
  listing_id,
  listing_name,
  room_type,
  CASE
    WHEN minimum_nights = 0 THEN 1
    ELSE minimum_nights
  END AS minimum_nights,
  host_id,
  REPLACE(
    price_str,
    '$'
  ) :: NUMBER(
    10,
    2
  ) AS price,
  created_at,
  updated_at
FROM
  src_listings

In the lecture recording, the model has no config() block and inherits the folder default of table. The finished repo overrides to view and adds event_time='created_at' for microbatch features introduced later. When following the video, omit the config block; when cloning the repo, keep it as-is.

On BigQuery you would use SAFE_CAST(REPLACE(price_str, '$', '') AS NUMERIC) instead of Snowflake's :: NUMBER syntax. On Postgres, CAST(REPLACE(price_str, '$', '') AS NUMERIC(10,2)). The pattern is the same; only the cast function differs.

dim_hosts_cleansed — NVL cleansing pattern

Host names are nullable in the raw feed. Downstream joins and dashboards break on null labels, so the dimension replaces nulls with a readable default. Snowflake's NVL(a, b) returns b when a is null; other warehouses use COALESCE(a, b) or IFNULL(a, b) with identical semantics.

FunctionEngineEquivalent in dim_hosts_cleansed
NVL(host_name, 'Anonymous')Snowflake, OracleWhat the course uses
COALESCE(host_name, 'Anonymous')ANSI · Postgres · BigQueryPortable alternative
IFNULL(host_name, 'Anonymous')BigQuery · MySQLSame behaviour, different name

After building both dimensions, the dev schema holds two queryable objects (table or view depending on config). Staging remains invisible except through compiled SQL. That is the intended medallion-style separation at small scale.

Running and selecting models

dbt run executes every model in dependency order (or a subset you name). The terminal output tells you materialization type, success or failure, and timing. Learning to read that output saves hours when a pipeline fails in production.

Read the log line carefully:

build versus run at this stage

dbt build runs models and tests together in DAG order. In Section 7 you have no tests yet, so dbt build behaves like dbt run. Once tests exist in Section 11, prefer dbt build --select dim_hosts_cleansed to run the dimension and its tests in one command.

Traps that catch people

  • Hard-coded schema names — FROM AIRBNB.DEV.DIM_LISTINGS works in your laptop schema and breaks in CI or a colleague's schema. Always use ref() for dbt-built models and source() for raw tables once sources exist.
  • Expecting to query ephemeral models — SELECT * FROM src_listings fails because no object exists. Compile the downstream model or temporarily set materialization to view while debugging.
  • Wrong build order assumption — dbt builds parents before children automatically, but only when dependencies are declared via ref(). A hard-coded table name removes that guarantee.
  • Stale views after switching to ephemeral — if you previously materialized staging as views, old DEV.SRC_* views remain until dropped manually. Queries against them return stale data. See Section 8.
  • Case sensitivity on Snowflake — unquoted identifiers fold to uppercase. NAME AS host_name in src_hosts reads the raw column correctly because Snowflake stored it uppercase. On Postgres, quote mixed-case identifiers explicitly.
  • Cast failures on price — if price_str contains unexpected characters, :: NUMBER fails the whole model run. Staging keeps the string; dimension casting is where you discover dirty data. Add tests in Section 11.
  • Running from wrong directory — commands must run from the folder containing dbt_project.yml. Running from repo root finds no project.
  • Confusing compiled and run SQL — editing files in target/ has no effect. Changes must go in models/; target is regenerated every run.
  • Thread count of 1 in dev — the course uses one thread for clarity. Independent model branches could run in parallel with higher threads; leaving it at 1 makes every run feel slower than necessary.
  • Forgetting parent hooks — the project's post-hook inserts into audit_log on every table build. If that table is missing, the model fails even when SQL is correct. Run once after setup or check Section 6 hooks.

Production patterns

Real teams extend the src_ / dim_ / fct_ prefix convention with an int_ (intermediate) layer for reusable joins that are not yet marts. Staging stays one-to-one with sources; intermediate holds complex logic shared by multiple marts; dimensions and facts face consumers or other models. The course skips int_ until the power-user branch, but the principle starts here: each layer has one job.

Staging as ephemeral is the default in many Snowflake dbt projects; BigQuery teams sometimes prefer staging as views when query planners handle nested views well and analysts want to inspect staging in the console. Postgres teams often use views for staging because ephemeral chains can hit statement-length limits on deep projects. The course choice (ephemeral) is correct for Snowflake at this scale.

Convention: one source, one staging model

Each raw table gets exactly one src_ model. Joins happen in intermediate or mart layers, not in staging. Violating this makes lineage misleading and reuse harder.

Anti-pattern: god staging model

A single src_all that joins listings, hosts and reviews "for convenience" cannot be reused when only one source changes. Dependencies become opaque and incremental strategies impossible.

Interview questions

Answer each one out loud before opening it.

What is a dbt model, and how is it different from a table in your warehouse?Fundamentals

A dbt model is a .sql file under models/ containing a SELECT statement plus optional Jinja config. dbt compiles it, determines dependencies, and executes the appropriate DDL to create or replace a warehouse object (or inline it as a CTE if ephemeral).

A table in the warehouse is the persisted result. The model is the source code; the table is one possible output of running that code. You version-control models; tables are regenerated on each run.

Explain what {{ ref('model_name') }} does and why you should use it instead of a hard-coded table name.Fundamentals

ref() resolves to the correct relation for the active target environment, registers a dependency in the DAG so build order is correct, and enables lineage in documentation. Hard-coded names break all three: wrong schema in another environment, arbitrary build order, and missing lineage edges.

In production, hard-coded dev schema names are a common source of "works on my machine" incidents where CI reads empty tables or production data leaks into dev queries.

What is the dbt DAG, and what guarantees does dbt make about it?Design

The DAG (directed acyclic graph) is the dependency graph of all models, sources, seeds, snapshots and tests. Edges come from ref(), source() and test relationships. dbt guarantees acyclicity — it refuses circular dependencies — and topological sort for execution order.

Independent subgraphs can run in parallel up to the thread limit. Failed nodes block descendants from running in the same invocation.

What is the difference between target/compiled and target/run?Troubleshooting

target/compiled/ holds SQL after Jinja rendering — essentially your model's SELECT with macros expanded. It is written by dbt compile and dbt run without executing warehouse DDL for the compiled file alone.

target/run/ holds the full statement dbt executed, including CREATE TABLE/VIEW AS wrappers, hooks and adapter-specific syntax. Use compiled to debug logic; use run to reproduce exactly what the warehouse received.

Why does the course materialize src_ models as ephemeral?Modelling

Staging is an implementation detail, not an analytics product. Ephemeral materialization inlines staging SQL into downstream models as CTEs, avoiding clutter in the dev schema and guaranteeing staging is always fresh when a dimension rebuilds.

The trade-off is that you cannot query staging directly or easily run singular tests against it in isolation. Teams accept that for thin renames; heavy staging sometimes becomes views instead.

Walk me through what happens when you run dbt run --select dim_listings_cleansed.Fundamentals

dbt parses the project, computes the subgraph for the selection, includes parents by default, and sorts topologically. It compiles src_listings (ephemeral) and executes its logic as part of compiling dim_listings_cleansed. It then runs the DDL for dim_listings_cleansed (table or view depending on config) against the warehouse.

Terminal output shows two steps: ephemeral success for staging (no persisted object) and table/view success for the dimension. Compiled and run artifacts land in target/.

How do folder-level configs in dbt_project.yml interact with a config block inside a model file?Gotcha

Model-level {{ config() }} in the SQL file overrides folder-level settings in dbt_project.yml, which override project-level defaults. Most specific wins.

Example: dim/ defaults to table, but dim_listings_cleansed.sql sets materialized='view' — that model becomes a view. Interviewers use this to test whether you know config precedence without guessing.

Your dimension model succeeds but returns zero rows. How do you debug it?Troubleshooting

Work upstream. Count rows in the raw source table. Run dbt compile --select dim_model and read target/compiled/ to verify the FROM clause points at the expected source. Check for silent filters in staging or dimension SQL.

If raw has rows but compiled SQL points at an empty schema, you likely hard-coded a schema name or are on the wrong target. dbt debug confirms active schema.

When would you use a CTE in a dbt model versus creating a separate staging model?Design

Use a separate staging model when the transform is reused by multiple downstream models or represents a stable contract on a source (renamed columns). Use an inline CTE within one model for steps only that model needs (a one-off filter or intermediate aggregation).

Over-splitting creates DAG noise; under-splitting duplicates logic. The course uses one staging model per source because every dimension and fact will reuse those renames.

Compare ref() and source(). When do you use each?Comparison

source() references raw tables defined in YAML that dbt does not build — ingestion owns them. ref() references other dbt models in the project. Sources get freshness checks and appear as source nodes in lineage; refs form the model-to-model DAG.

Section 7 uses hard-coded raw names in the video; Section 9 moves to source(). Using ref() on a raw table or source() on a dbt model are both wrong and fail compilation or misrepresent lineage.

What happens if two models ref each other?Gotcha

dbt detects cyclic dependencies at parse time and refuses to compile. If model A references model B and model B references model A, you get a compilation error describing the cycle. The DAG must be acyclic.

Fix by introducing an intermediate model that breaks the cycle, or restructuring so one direction uses a source or snapshot instead of a ref. Cycles are a design smell in analytics modelling anyway — they usually mean two definitions claim to be the source of truth for the same entity.

Why might dim_listings_cleansed be a view in the repo but a table in the lecture?Comparison

The lecture follows folder defaults: dim/ means table unless overridden. The finished repo sets materialized='view' on dim_listings_cleansed and adds event_time for later microbatch lessons. Both are valid teaching paths.

Views cost no storage and always reflect current upstream logic; tables cost a rebuild but query faster for heavy BI. The exam tests whether you know config overrides folder defaults, not which choice the course repo made.

Recap

  • A dbt model is a .sql file under models/ with a single SELECT; dbt handles DDL and execution order.
  • File name (without extension) is the model name; subfolders organise but do not prefix the name.
  • src_ models in models/src/ default to ephemeral — inlined as CTEs, no warehouse object.
  • dim_ models in models/dim/ default to table — persisted, queryable dimensions.
  • {{ ref('model_name') }} declares dependencies, resolves environments, and powers lineage.
  • Never hard-code dbt-built table names; use ref() so the DAG and build order stay correct.
  • target/compiled/ = Jinja expanded; target/run/ = full DDL dbt executed.
  • Staging renames columns; dimensions apply business cleansing (CASE, casts, NVL).
  • dbt run --select model_name builds the model and its parents; full runs rebuild everything persisted.
  • Ephemeral models show SUCCESS 0 in run output; table/view models report row counts or adapter-specific metrics.
  • Lesson uses hard-coded AIRBNB.RAW.*; repo uses source() after Section 9.
  • Section 8 explains view, table, ephemeral and incremental in depth.
  • The DAG after this section has five models; only dim_listings_cleansed and dim_hosts_cleansed appear as objects in your dev schema.
