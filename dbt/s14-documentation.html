Descriptions in schema.yml

The fastest documentation win is a description field on every model and every column in models/schema.yml. dbt parses these strings at compile time, stores them on each node in manifest.json, and renders them in the docs site. No separate wiki, no Confluence page that drifts out of date.

In the Airbnb project, schema.yml already declares data_tests: from Sections 11–12. This section adds human-readable description keys at the same levels. Model descriptions explain grain and business purpose; column descriptions explain identifiers, foreign keys, and domain vocabulary.

Model-level description

A model entry can carry a top-level description sibling to columns: and data_tests:. It renders as the header text when you click the model in the docs UI. Keep it to one or two sentences: what one row represents and who consumes it.

models:
  - name: dim_listings_cleansed
    description: Cleansed table which contains Airbnb listings.
    data_tests:
      - minimum_row_count:
          arguments:
            min_row_count: 1000
          config:
            severity: error
    columns:
      - name: listing_id
        description: Primary key for the listing
        data_tests:
          - unique
          - not_null

The course adds similar descriptions to dim_hosts_cleansed and documents columns on fct_reviews. Descriptions are optional in dbt — parse succeeds without them — but empty docs sites are the norm on teams that skip this step until an audit forces a catch-up sprint.

Column-level description

Each entry under columns: can include description:. These appear in the column list on the model's docs page and in search results. Document primary keys, foreign keys, enum-like fields, and anything a new hire would ask in their first week.

      - name: host_id
        description: The host's id. References the host table.
        data_tests:
          - not_null
          - relationships:
              arguments:
                to: ref('dim_hosts_cleansed')
                field: host_id

      - name: room_type
        description: Type of the apartment / room
        data_tests:
          - accepted_values:
              arguments:
                values: ['Entire home/apt', 'Private room', 'Shared room', 'Hotel room']

Descriptions support Markdown

dbt renders description strings as Markdown in the docs site. That means **bold**, bullet lists, inline code, and links work in YAML descriptions without a separate docs block. For long prose or content reused across several columns, prefer a docs block and {{ doc('name') }} instead of pasting the same paragraph five times.

Write descriptions for the reader who does not have warehouse access. "Primary key" is minimal but better than nothing. "Surrogate hash of listing_id, review_date, reviewer_name, review_text; one row per guest review" tells an analyst what grain means without opening the SQL file.

Relationship to tests in the same file

Keeping description and data_tests: on the same column documents both the meaning and the guarantees. When a relationships test fails, the column description tells the reader which parent model the foreign key expects. When someone removes a test in a pull request, the description reminds them why the column mattered.

  - name: fct_reviews
    columns:
      - name: listing_id
        data_tests:
          - relationships:
              arguments:
                to: ref('dim_listings_cleansed')
                field: listing_id

      - name: reviewer_name
        data_tests:
          - not_null
      
      - name: review_sentiment
        data_tests:
          - accepted_values:
              arguments:
                values: ['positive', 'neutral', 'negative']

Production teams often split YAML by layer (models/dim/_dim__models.yml) but keep the same shape: model description, columns with descriptions, tests nested under columns or at model level. The course uses one schema.yml for teaching clarity.

Source descriptions (cross-reference)

Sources accept the same description keys in sources.yml (Section 9). Documenting airbnb.listings at the source layer explains raw ingestion semantics; documenting src_listings explains the staging rename layer. Both appear in lineage and search. A common pattern: short source description ("Fivetran-synced Airbnb listings export"), longer staging doc block referenced from the ephemeral model's YAML entry if you attach tests there.

Searching the docs site

After dbt docs serve, the search bar indexes model names, column names, and description text from manifest. Typing minimum_nights finds the column and the docs block content once doc() is resolved. Typing superhost finds accepted-values tests and any description mentioning the term. This is why consistent vocabulary between descriptions and test names matters — analysts search natural language, not macro names.

Docs blocks and doc()

When the same explanation appears in multiple places, or when Markdown is too long for a YAML string, define a docs block in a .md file and reference it with {{ doc('block_name') }}. dbt resolves the block at parse time and inlines the rendered Markdown wherever the reference appears.

Defining a docs block

Docs blocks live in any file under your configured model, seed, snapshot, or macro paths. The course uses models/docs.md. Syntax is a Jinja block tag pair wrapping Markdown content:

{% docs dim_listing_cleansed__minimum_nights %}
Minimum number of nights required to rent this property. 

Keep in mind that old listings might have `minimum_nights` set to 0 in the source tables. Our cleansing algorithm updates this to `1`.

{% enddocs %}

Block names are global within a project. Use a naming convention — model__column, model__overview, source__table__column — so collisions are obvious in code review. The double underscore is convention, not syntax.

Referencing with doc()

In YAML, wrap the Jinja call in quotes so the parser treats it as a string dbt will render:

      - name: minimum_nights
        description: '{{ doc("dim_listing_cleansed__minimum_nights") }}'
        data_tests:
          - positive_values

At parse time dbt replaces the doc() call with the Markdown body from the docs block. The docs site shows the formatted paragraph under the minimum_nights column, including the inline code around minimum_nights and 1 from the block content.

Docs blocks versus inline YAML

Use inline YAML strings for one-line definitions. Use docs blocks when:

  • The same text appears on multiple columns or models (DRY documentation).
  • You need multi-paragraph Markdown, lists, or code examples.
  • Non-engineers edit prose in .md files while engineers own YAML structure.

Docs blocks are not warehouse objects. They never appear in the lineage graph as nodes. They only enrich metadata on the nodes that reference them.

Naming convention for block names

The course uses dim_listing_cleansed__minimum_nights — note the singular listing in the block name while the model is dim_listings_cleansed. That mismatch is harmless if the reference matches exactly, but greenfield projects usually align names (dim_listings_cleansed__minimum_nights) to reduce grep confusion. Pick a team standard early and enforce it in code review.

Multiple docs blocks in one file

docs.md can hold many blocks back-to-back. dbt parses all of them at once. Splitting by domain (docs/listings.md, docs/reviews.md) keeps files reviewable when the project grows past a few dozen blocks.

{% docs dim_listings_cleansed__room_type %}
Allowed room types mirror Airbnb's source export. Hotel room
was added in a 2019 source schema change; historical rows may
be null before that date — handled in staging, not here.
{% enddocs %}

{% docs dim_listings_cleansed__price %}
Cleansed numeric price in USD, parsed from the source string
column that included a dollar sign prefix.
{% enddocs %}

Project overview and overview.md

Every dbt docs site has a homepage. The reserved docs block name __overview__ defines that page: pipeline context, onboarding links, architecture diagrams, and anything you want visible before a reader clicks into a model.

The __overview__ block

Create models/overview.md (or any path under your project paths) with a single block named __overview__. dbt renders it as the landing page when you open the docs site.

{% docs __overview__ %}
# Airbnb pipeline

Hey, welcome to our Airbnb pipeline documentation!

Here is the schema of our input data:
![input schema](assets/input_schema.png)

{% enddocs %}

The course repository stores the diagram at airbnb/assets/input_schema.png. The project's dbt_project.yml declares asset-paths: ["assets"], so dbt can resolve image paths relative to the project when generating docs. The instructor's script also shows a hosted copy at https://dbt-datasets.s3.us-east-2.amazonaws.com/input_schema.png — either works; local assets version with git, hosted URLs do not.

What input_schema.png shows

The PNG is an entity-relationship sketch of the three raw tables the course loads into Snowflake: raw_listings, raw_hosts, and raw_reviews. It depicts how raw_listings.host_id references raw_hosts.id and how raw_reviews.listing_id references raw_listings.id. That picture is the same join logic you built in Section 7; placing it on the overview orients new readers before they open the lineage graph.

Overview content is not a model. It does not get built in the warehouse, tested, or selected with dbt run. It is pure documentation metadata parsed like any other docs block. You can include Mermaid-style diagrams only if your docs deployment supports them; standard dbt docs renders CommonMark Markdown plus images.

Project-level Markdown elsewhere

Besides overview.md, teams add:

  • Layer README files — models/mart/README.md checked into git for developers; optionally mirrored in docs blocks.
  • CONTRIBUTING.md at repo root for git, not auto-published by dbt.
  • Exposure and metric descriptions — added in later sections (Section 15 exposures, semantic layer in advanced material).

Only content inside {% docs %}...{% enddocs %} in project paths is picked up by dbt's docs engine. A plain README.md in the repo root is for GitHub unless you wrap it or link from __overview__.

Linking from overview to models

Markdown links to models use the docs site's URL scheme after generation. During authoring, the reliable pattern is to name models in prose and let readers use search. In dbt Cloud, @-mention style linking exists; in Core's static site, relative links like [dim_listings_cleansed](#!/model/model.airbnb.dim_listings_cleansed) work once you know the node id from manifest.json.

dbt docs generate and dbt docs serve

Documentation is not live by default. You generate a static site plus JSON artifacts, then serve them locally or publish the target/ output to object storage or dbt Cloud.

dbt docs generate

This command parses the project (if needed), queries the warehouse information schema for every relation dbt manages, and writes artifacts under target/. It must succeed against a reachable warehouse for column types and row counts to appear.

Run it from the airbnb folder after models exist in the warehouse. If you never ran dbt run, generate still succeeds but catalog entries may be empty for relations that do not exist yet.

dbt docs serve

Starts a local web server (default port 8080) that serves the generated static site and opens the lineage graph in your browser. It is for local development and demos — not for production hosting.

Typical workflow: edit descriptions in YAML or docs blocks, run dbt parse or any command to refresh manifest.json, run dbt docs generate to refresh catalog metadata, run dbt docs serve, refresh the browser. In CI, teams run generate once per merge and upload target/index.html plus JSON to S3 or GCS.

manifest.json versus catalog.json

These two files answer different questions. Confusing them is a common interview trap.

ArtifactWritten byContainsRequires warehouse?
target/manifest.jsonAny parse command (dbt parse, dbt run, dbt build, dbt docs generate)Full project graph: models, tests, sources, macros, configs, compiled paths, YAML descriptions, depends_on edgesNo — parse is local
target/catalog.jsondbt docs generate onlyWarehouse metadata: column names, types, stats, table sizes for relations dbt knows aboutYes — queries information schema
target/run_results.jsonRun commands that execute nodesPass/fail, timing, rows affected for last invocationYes
target/index.htmldbt docs generateStatic docs SPA entry pointGenerate needs catalog step
Everyday analogy — manifest.json is the blueprint (what you intended to build and how pieces connect). catalog.json is the building inspector's report (what actually exists in the warehouse right now and how big it is).

What manifest stores for documentation

Each node in manifest.json includes a description field with the fully rendered text after doc() resolution. Search in the docs UI indexes this text. External tools — Elementary, Monte Carlo, custom lineage portals — read manifest rather than re-parsing SQL.

{
  "nodes": {
    "model.airbnb.dim_listings_cleansed": {
      "name": "dim_listings_cleansed",
      "resource_type": "model",
      "description": "Cleansed table which contains Airbnb listings.",
      "depends_on": {
        "nodes": ["model.airbnb.src_listings"]
      },
      "columns": {
        "minimum_nights": {
          "name": "minimum_nights",
          "description": "Minimum number of nights required to rent this property.\n\nKeep in mind..."
        }
      }
    }
  }
}

What catalog adds

Catalog merges warehouse reality into the docs UI: data types you did not declare in YAML, row counts, last modified times (adapter-dependent). That is why the column list in docs can show types even before you add data_type contract fields. On BigQuery and Snowflake the information schema queries differ; dbt abstracts them per adapter.

persist_docs (production extension)

The course does not enable it, but production teams often set +persist_docs: in dbt_project.yml so model and column descriptions push into warehouse COMMENT metadata. BI tools that read Snowflake or BigQuery comments then show dbt descriptions without opening the docs site.

models:
  airbnb:
    +persist_docs:
      relation: true
      columns: true

persist_docs runs COMMENT statements on each model build — extra DDL cost, negligible on Snowflake for most projects but worth knowing for thousands of columns. Relation-only persistence is a lighter first step.

dbt docs generate hits the warehouse. Every relation in the graph triggers information schema queries. On a large project, running generate in a tight dev loop adds up. Parse locally while editing prose; generate once before sharing the docs link.

Docs workflow in the course CI reference

The course GitHub repo includes a workflow step that runs dbt docs generate after builds — the pattern production teams copy. Artifacts are not committed to git; they are output for optional upload. Your local workflow mirrors it: build models in dev, generate, serve, share the localhost URL during pair review, then tear down the server.

Navigating the static docs UI

The generated site has four areas worth knowing:

  • Project overview — the __overview__ block; entry point for onboarding.
  • Models — searchable list grouped by folder; each page shows description, columns, tests, SQL source link, and lineage button.
  • Sources — declared sources from sources.yml with freshness config visible.
  • Macros — project and package macros; argument docs from YAML appear here when defined.

Clicking "Code" on a model shows the raw SQL file content syntax-highlighted. That is the same file in git — not compiled SQL. For compiled output, use target/compiled/ as in Section 7.

When manifest and catalog disagree

Manifest says a model exists in the project; catalog says whether the table or view is actually in the warehouse. Common mismatches: you renamed a model but the old relation still exists (orphan table); you added a column in SQL but have not run the model yet (catalog column list lags); contract enforcement failed mid-build. The docs UI may show YAML-declared columns from manifest while catalog lacks types until the build succeeds. Treat catalog as live truth for types and row counts, manifest as intended truth for graph and descriptions.

Reading the lineage graph

The lineage view is a directed acyclic graph (DAG) of every resource dbt knows about: sources, seeds, models, snapshots, tests, and (from Section 15 onward) exposures. Edges follow ref(), source(), and declared dependencies — not orchestration schedule order.

Opening the graph

After dbt docs serve, click the lineage icon or open a model and choose "View lineage". You can pan, zoom, filter by resource type, and click nodes to jump to documentation. Green nodes typically indicate selected resources; upstream parents appear to the left, downstream children to the right.

Using lineage for impact analysis

Before changing dim_listings_cleansed, select it in the graph and inspect downstream nodes. Every child model, exposure, and test that depends on it may need revalidation. In production, the same graph powers dbt ls --select dim_listings_cleansed+ and Slim CI's state:modified selectors from Section 19.

Seeds and snapshots appear with distinct node styling. Sources sit in the leftmost column when declared in sources.yml (Section 9). Tests attach to the columns or models they guard; clicking a test in the docs site shows compiled SQL from target/compiled/.

Graph versus execution order

The DAG shows dependency order, not timing. fct_reviews and dim_listings_w_hosts may build in parallel if neither references the other. Orchestrators (Section 18) schedule dbt invocations; the graph tells them what must finish before what, not when the cron fires.

Lineage graph UI controls

In the docs lineage view, learn these controls once — they save time in every later section:

  • Resource type filters — hide tests or macros clutter when presenting to stakeholders.
  • Export / screenshot — browser screenshot for architecture docs; some teams script manifest → diagram tools for auto-updates.
  • Node colour — selected node highlighted; upstream/downstream fade helps focus impact analysis.
  • Double-click model — opens the model docs page with column list and test summary.

Compare graph navigation with CLI: dbt ls --select +dim_listings_cleansed lists ancestors; dbt ls --select dim_listings_cleansed+ lists descendants. The graph is the visual version of those selectors documented in Section 17.

Certification: know that lineage comes from ref() and source() at parse time, that macros do not appear as separate nodes, and that dbt docs generate combines manifest (graph + descriptions) with catalog (warehouse columns).

Documenting tests and macros in test_docs.yml

Generic tests and project macros are code. models/test_docs.yml (or a file under macros/) documents their arguments the same way models get column descriptions — so the docs site explains what minimum_row_count expects before someone attaches it in YAML.

test_docs.yml structure

The course documents the custom generic test macro test_minimum_row_count from Section 12:

macros:
  - name: test_minimum_row_count
    description: "Test that a model has at least a minimum number of rows."
    arguments:
      - name: model
        description: "The model to test."
      - name: min_row_count
        description: "The minimum number of rows the model should have."

When you open the macro page in docs (under Macros), the argument list renders with these descriptions. That helps analysts who attach minimum_row_count in schema.yml without reading the SQL implementation.

Conventions for test documentation

  • Name matches the macro — for generic tests, the macro is typically test_<test_name>; document under that name.
  • One entry per custom generic — built-in tests (unique, not_null) already ship with dbt docs.
  • Package macros — dbt_utils and dbt_expectations document themselves in package repos; you only document project-specific wrappers.
  • Keep arguments in sync — if you add a where argument to the macro, update test_docs.yml in the same pull request.

Markdown support and images in docs

dbt docs renders CommonMark Markdown in descriptions, docs blocks, and the overview page. Images, headings, lists, and fenced code blocks work wherever Markdown is accepted.

Markdown in descriptions

Inline and block Markdown in YAML descriptions is rendered when the docs site loads. Useful patterns:

  • Bold for grain statements: This table is **one row per listing**.
  • Bullet lists for acceptable values when not using accepted_values test alone.
  • Links to Notion or Slack channels for stewards: [Data owner](https://...)
  • Fenced code for example values: `` `Entire home/apt` `` in backticks.

YAML multiline strings use | or > for paragraphs; docs blocks are easier for long Markdown because you avoid YAML escaping.

Embedding images

input_schema.png purpose in the course

The PNG is not decorative. It encodes the same foreign-key structure the staging models assume: listings belong to hosts; reviews belong to listings. When a relationships test fails on fct_reviews.listing_id, an analyst can open the overview, see the ERD, and trace which raw parent table is broken without reading SQL. YAML multiline descriptions without docs blocks

For medium-length Markdown still inline in YAML, use block scalars:

      - name: review_sentiment
        description: |
          Sentiment label assigned in **mart** processing.
          - `positive` — guest praise dominates
          - `neutral` — mixed or factual tone
          - `negative` — complaint or criticism

Once the list grows past a few lines, move to a docs block so diffs stay readable and translators can work in .md files only.

Traps that catch people

  • Expecting docs without generate — editing YAML and refreshing an old dbt docs serve tab shows stale text until you re-run generate or at least parse for manifest-only fields.
  • Missing doc() quotes in YAML — unquoted {{ doc(...) }} can be interpreted as YAML syntax errors or empty nodes. Wrap in single quotes.
  • Wrong docs block name — typos fail compilation, not at runtime. CI parse step catches them if you run dbt parse on pull requests.
  • Hard-coded tables break lineage — documentation and impact analysis are wrong together when ref() is bypassed; the graph is not a separate concern.
  • Catalog empty for new models — you documented a model that never ran; types show from YAML contract only if enforced, otherwise blank until first build.
  • Image path relative to wrong root — paths in overview are project-relative, not relative to the .md file. Use assets/... from project root.
  • Committing target/ to git — manifest in PR artifacts is intentional for Slim CI; committing full docs HTML bloats the repo. Publish artifacts to storage instead.
  • Duplicating test and docs prose — when a column has both accepted_values and a description listing values, they drift. Describe meaning in docs; let tests enforce values.
  • Macro docs file ignored — test_docs.yml must live under a configured path and use valid YAML schema or parse warns and skips entries.
  • Assuming BI reads dbt docs — Looker, Tableau, and Preset do not auto-sync unless you use persist_docs or a catalog integration.
  • Overview __overview__ typo — only the exact name __overview__ becomes the homepage; double underscores matter.
  • Ephemeral models in lineage confuse stakeholders — explain that ephemeral nodes are compile-time CTEs, not queryable tables, when walking non-technical readers through the graph.

Production patterns

Mature teams treat documentation as a CI artifact: every merge to main runs dbt build (or at least run + test) on prod, then dbt docs generate, then uploads target/manifest.json, catalog.json, and static HTML to a private S3 bucket fronted by CloudFront or serves via dbt Cloud's hosted docs. Pull requests run dbt parse to validate doc references and optionally publish preview docs from the dev schema for reviewer comment.

Documentation ownership follows code ownership: each model folder has a CODEOWNERS entry; empty descriptions fail a custom lint (dbt-checkpoint, sqlfluff-adjacent tools, or a simple script over manifest). Stewards fill meta: with Slack channel and PII classification for governance tools that ingest manifest.

Pattern: docs in the same PR as logic

Require description updates when column semantics change. Reviewers reject "fix later" on docs the same way they reject missing tests.

Anti-pattern: docs sprint once a year

A quarter-end scramble to document 200 models produces generic text nobody trusts. Incremental docs in each feature PR stays accurate.

Interview questions

Answer each one out loud before opening it.

How do you document a dbt model and its columns?Fundamentals

Add description at the model level and under each column in schema.yml (or split YAML files under models/). dbt parses these into manifest.json and renders them in the docs site as Markdown.

For long or reused text, define a {% docs %} block in a .md file and set description: '{{ doc("block_name") }}' in YAML. Run dbt docs generate to merge warehouse catalog metadata and dbt docs serve to preview locally.

What is the difference between manifest.json and catalog.json?Comparison

manifest.json is written on any parse: it holds the full project graph, configs, dependencies, compiled paths, and documentation strings from YAML and docs blocks. No warehouse connection is required.

catalog.json is written by dbt docs generate only. It queries the warehouse information schema for column types, relations, and statistics for objects dbt knows about. Docs UI merges both: manifest for structure and descriptions, catalog for live warehouse metadata.

Explain doc() and docs blocks.Jinja

A docs block is defined with {% docs block_name %}...{% enddocs %} in a Markdown file under project paths. The block body is Markdown stored in the project, not the warehouse.

{{ doc('block_name') }} is a Jinja function that inlines the rendered block wherever it appears — typically in a YAML description field. Block names are project-global. The special name __overview__ becomes the docs homepage.

What creates edges in the dbt lineage graph?Fundamentals

Edges come from parse-time dependency discovery: {{ ref('model') }} links models, {{ source('source', 'table') }} links sources to models, and declared exposure depends_on links models to downstream consumers. Tests attach to models or columns but are separate node types.

Hard-coded table names do not create edges. Macros expand inline and do not appear as nodes. The graph reflects logical dependencies, not orchestration schedule or runtime parallelism.

When would you use persist_docs?Production

When BI tools, SQL IDEs, or warehouse catalog products should show the same descriptions as dbt docs without users opening the docs site. +persist_docs: {relation: true, columns: true} in dbt_project.yml pushes COMMENT metadata on model build.

Trade-offs: extra DDL each run, adapter-specific comment limits, and descriptions must be kept in YAML/docs blocks as source of truth — warehouse comments are overwritten on build, not edited in the UI long term.

Your colleague added a doc() reference but the docs site shows the raw Jinja. Why?Troubleshooting

Most often the YAML description was not quoted, so the file stores literal curly braces as a plain string and dbt never treats it as a Jinja template to render at parse time. Fix: description: '{{ doc("block_name") }}'.

Less common: they edited YAML but never re-ran parse or generate, and the browser shows a cached older manifest. Run dbt parse, dbt docs generate, and hard-refresh.

How do you document a custom generic test?Testing

Add a macros: entry in YAML (the course uses models/test_docs.yml) with name matching the test macro (e.g. test_minimum_row_count), a description, and an arguments list naming each parameter with its own description.

The docs site macro page then documents how to attach the test in schema.yml under data_tests: with arguments: nested correctly for dbt 1.8+.

Does dbt docs generate require models to be built first?Gotcha

Parse and manifest generation do not require built models. Catalog generation queries the warehouse for relations that exist; if a model was never run, it may appear in lineage from manifest but lack column types and stats in catalog until the relation exists.

Best practice: run dbt build (or at least run models) on the target schema, then generate docs so the site shows complete metadata. CI prod jobs typically chain build then generate.

How would you host dbt docs for a production project?Design

Common pattern: CI on main runs dbt docs generate against prod (or a dedicated docs target), uploads target/index.html, static assets, manifest.json, and catalog.json to private object storage, and serves via HTTPS with SSO in front. dbt Cloud offers hosted docs on job completion.

Avoid leaving dbt docs serve running on a shared server — it is a dev command. Store artifacts, not live Python servers, in production.

Why document columns that already have not_null and unique tests?Design

Tests enforce constraints; descriptions convey meaning. A not_null test does not explain that host_id is a foreign key to dim_hosts_cleansed or what to do when it fails. Documentation reduces slack questions and speeds onboarding.

Together they form a contract: description for humans, tests for machines. Certification questions often pair "where do descriptions live" with "where do tests live" — same YAML file, different keys.

What is the __overview__ docs block?Fundamentals

A reserved docs block name whose Markdown body renders as the landing page of the dbt docs site. The course defines it in models/overview.md with a pipeline title, welcome text, and an ERD image (assets/input_schema.png).

It is the right place for architecture context, links to runbooks, and diagrams that do not belong on a single model page. It is not a model and is not built in the warehouse.

How does documentation relate to data governance and catalog tools?Production

dbt manifest is a machine-readable graph many catalogs ingest (Atlan, Alation, Monte Carlo, Snowflake Horizon). Descriptions and meta fields become tags and stewardship metadata. persist_docs bridges to warehouse-native comments.

dbt docs alone is not a full enterprise catalog — it covers dbt-managed resources, not every raw landing table or SaaS dataset — but it is the authoritative source for transformation logic definitions when the project is well documented.

Recap

  • Model and column description fields in schema.yml are the primary documentation surface.
  • Descriptions render as Markdown in the dbt docs site.
  • Reusable prose lives in {% docs block_name %}...{% enddocs %} blocks, typically in models/docs.md.
  • Reference a block with '{{ doc("block_name") }}' in quoted YAML descriptions.
  • __overview__ in models/overview.md defines the docs homepage; the course embeds assets/input_schema.png for the raw ERD.
  • dbt docs generate builds catalog metadata and static site assets; it queries the warehouse information schema.
  • dbt docs serve previews docs locally at http://localhost:8080 — not for production hosting.
  • manifest.json holds the graph, configs, and descriptions; catalog.json holds warehouse column metadata.
  • Lineage edges come from ref() and source(); macros do not appear as separate nodes.
  • test_docs.yml documents custom generic test macros under a macros: YAML key.
  • asset-paths in dbt_project.yml lets docs blocks reference project images.
  • Optional persist_docs pushes descriptions into warehouse COMMENT metadata on build.
