Why this page exists

The 22 numbered sections teach dbt on Snowflake with one well-scoped project. That is the right place to start, but it is not the full product surface area. The five topics below are not a deployment checklist — you do not need mesh on day one of your first dbt job. They are the vocabulary senior analytics engineers use when the monolith outgrows one team, when the CFO asks why two dashboards disagree, or when your company picks a second warehouse.

dbt Mesh and multi-project setups

dbt Mesh is the pattern for connecting multiple dbt projects so one team can depend on another team’s models without copying SQL or sharing one monolithic repository. Instead of a single giant DAG, you get bounded domains with explicit public interfaces.

Why large orgs split one giant project

A single project with five hundred models works until it does not. Merge conflicts multiply. CI runs rebuild unrelated subgraphs. Ownership blurs: finance models break when marketing changes a staging table nobody knew they depended on. Blast radius of a bad deploy grows with every new model in the same repo.

Splitting by domain — ingestion staging in one project, core dimensions in another, domain marts in a third — gives each team a repo they can deploy independently, review with domain experts, and scale CI against a smaller DAG. The cost is coordination: downstream projects must consume upstream outputs through a stable contract, not by reaching into private models.

Cross-project ref()

Within one project, {{ ref('dim_listings_cleansed') }} resolves to a relation in your target schema. Across projects, dbt resolves the same syntax against models declared in a dependency project. You install the upstream project as a package-like dependency (see dependencies.yml below), and dbt knows which relations are addressable from outside.

The mental model: ref() still means “the model I depend on,” but the compiler may fetch that model’s metadata from another repository’s manifest rather than from a file in your tree.

WITH listings AS (
  SELECT * FROM {{ ref('dim_listings_cleansed') }}
),
reviews AS (
  SELECT * FROM {{ ref('fct_reviews') }}
)
SELECT
  l.listing_id,
  r.review_date,
  r.review_sentiment
FROM listings l
INNER JOIN reviews r ON l.listing_id = r.listing_id

Project dependencies via dependencies.yml

dbt 1.6+ introduced first-class project dependencies. A downstream project lists upstream projects in dependencies.yml (alongside or instead of package-only workflows). Each entry names the project, where to find its artifacts (Git revision, registry, or local path for development), and which environment’s manifest to trust.

projects:
  - name: airbnb_core
    project: airbnb_core
    revision: 1.2.0
    repository: https://github.com/myorg/dbt-airbnb-core.git

After dbt deps, the downstream project can reference public models from airbnb_core as if they lived in the same graph, subject to access rules. Private models in the upstream project remain invisible.

Public models as the mesh boundary

Not every upstream model should be consumable. Mark the interface layer explicitly with access: public in schema YAML. Private models stay internal; protected models may be visible but not ref-able across projects depending on configuration. Public models are the published API of a domain.

models:
  - name: dim_listings_cleansed
    access: public
    description: Cleansed listings dimension — stable interface for downstream marts.
    config:
      contract:
        enforced: true
    columns:
      - name: listing_id
        data_type: integer
      - name: price
        data_type: number(10,2)

The course already enforces a contract on dim_hosts_cleansed in the real Airbnb models/schema.yml. In a mesh, that same pattern marks the model as something downstream teams can rely on without reading the SQL.

  - name: dim_hosts_cleansed
    config:
      contract:
        enforced: true
    columns:
      - name: host_id
        data_type: integer
        constraints:
          - type: not_null
      - name: host_name
        data_type: string
        constraints:
          - type: not_null

Contracts as the interface between meshes

Model contracts (covered in Section 12) become more important in a mesh than in a monolith. The upstream team commits to column names, types, and constraints; the downstream team codes against the contract, not against tribal knowledge. When the upstream team needs a breaking change, they version the model (Section 19) or publish a new public model and deprecate the old one.

Contracts fail the build on drift. If dim_listings_cleansed suddenly adds a non-null column without updating YAML, enforced contracts stop the run before downstream marts compile against a surprise shape. That is desirable pain in a mesh; it replaces silent breakage in twelve dependent dashboards.

Group-based access control

Large deployments pair mesh boundaries with groups in schema YAML. A group names a set of models owned by a team; access levels (private, protected, public) attach to models in that group. The course Airbnb project does not define groups — it is a single-team tutorial — but the YAML shape is the same as contracts:

groups:
  - name: finance
    owner:
      name: Finance Analytics
      email: finance-analytics@example.com

models:
  - name: fct_reviews
    group: finance
    access: protected

Groups feed documentation, ownership metadata, and (on dbt Cloud) governance features. On Core, they primarily structure who may mark models public and which models appear in cross-project dependency graphs.

End-to-end mesh workflow

A typical week for two teams: the core team merges a change to dim_listings_cleansed, runs prod CI, uploads manifest.json to an artifact store or registry. The marketing team bumps the pinned revision in dependencies.yml, runs dbt deps, and their CI compiles mart_fullmoon_reviews against the new upstream contract. If the core team added a breaking column without a version bump, the downstream compile or contract test fails before any warehouse write.

Mapping the Airbnb course project to mesh boundaries

If you were to mesh-ify the course DAG without changing business logic, a sensible cut is:

  • Project raw_and_staging — sources, ephemeral src_* models, snapshots on raw tables. Public output: cleansed staging views if downstream needs them, often none (core reads raw via contracts on snapshots).
  • Project core — dim_listings_cleansed, dim_hosts_cleansed, fct_reviews, dim_listings_w_hosts. All marked public with contracts mirroring the course schema.yml.
  • Project marts — mart_fullmoon_reviews, exposures in dashboards.yml, domain-specific analyses. Depends on core via dependencies.yml.

The course keeps all three layers in one repo for pedagogy. In production, the marts team should not need write access to snapshot definitions owned by the ingestion team.

The Semantic Layer and MetricFlow

The dbt Semantic Layer defines business metrics and dimensions once, in YAML, and exposes them to BI tools through a consistent query interface. MetricFlow is the engine that compiles metric requests into warehouse SQL. The goal is the same as centralising dim_listings_cleansed in the course project, but at the metric definition layer above facts and dimensions.

The different revenue number problem

Section 2 describes stage 3 failure mode: finance and product report different revenue on the same day because each dashboard encodes its own filters, grain, and fee logic. dbt models fix the table layer — everyone reads the same fct_reviews — but BI tools can still define “revenue” differently in their semantic models.

The Semantic Layer pushes the definition into dbt: one metric: total_booking_value with documented filters, grain, and aggregation. Tableau, Hex, Excel (via API), and custom apps query the same metric object; MetricFlow generates the SQL so the number matches everywhere.

Semantic models

A semantic model sits on top of one or more dbt models (often a fact and its dimensions). It declares entities (primary and foreign keys), dimensions (attributes you filter or group by), and measures (raw aggregatable columns before metrics wrap them).

semantic_models:
  - name: reviews
    model: ref('fct_reviews')
    description: Review fact table for sentiment and volume metrics.
    defaults:
      agg_time_dimension: review_date
    entities:
      - name: review
        type: primary
        expr: review_id
      - name: listing
        type: foreign
        expr: listing_id
    dimensions:
      - name: review_date
        type: time
        type_params:
          time_granularity: day
      - name: review_sentiment
        type: categorical
    measures:
      - name: review_count
        agg: count
        expr: review_id

Metrics defined once

Metrics reference semantic models and apply business logic: filters, derived calculations, cumulative windows, and conversion to consistent units. A ratio metric might divide booking value by night count; a derived metric might combine two measures with coalesce rules finance signed off on.

metrics:
  - name: total_reviews
    label: Total reviews
    type: simple
    type_params:
      measure: review_count
    filter: |
      {{ Dimension('review_sentiment__review_sentiment') }} is not null

How MetricFlow prevents inconsistent KPIs

When an analyst asks for “total reviews by sentiment last month,” the BI tool sends a metric request to MetricFlow, not a hand-written SELECT COUNT(*). MetricFlow resolves join paths between semantic models, applies the metric filter, respects the time spine, and emits warehouse-specific SQL. Two tools requesting the same metric with the same filters get identical queries modulo adapter dialect.

That does not remove the need for good dbt models. Garbage in fct_reviews still produces garbage metrics. The Semantic Layer governs the last mile where definitions used to diverge.

Cloud-only history, Core and Fusion today. The hosted Semantic Layer API launched on dbt Cloud first. dbt Core users historically had no supported SL path without Cloud. As of dbt 1.11+ and the Fusion line, MetricFlow-powered semantic projects can be developed and queried locally via the Semantic Layer CLI and Fusion tooling, but hosted multi-tenant SL (scheduling, caching, partner OAuth) remains a Cloud product. Check current docs before promising a Core-only SL deployment to stakeholders.
Certification: the Analytics Engineering exam focuses on models, tests, and deployment — not MetricFlow YAML. Expect conceptual “why centralise metrics” questions at the maturity level of Section 2, not syntax drills on semantic_models.

Querying metrics in practice

Once metrics exist, consumers request them through the Semantic Layer API (Cloud), JDBC/ODBC drivers, or partner integrations (Tableau, Hex, etc.). The request specifies metric names, dimensions to group by, and time range. MetricFlow compiles to SQL against the underlying dbt models — typically facts and dimensions you already test in CI.

mf query --metrics total_reviews \
  --group-by review_sentiment \
  --where "review_date >= '2024-01-01'"

For the Airbnb project, sensible first metrics might be total_reviews, avg_sentiment_score (if derived from a dimension), and listings_with_reviews at listing grain — all grounded in fct_reviews and dim_listings_cleansed you already built.

Relationship to exposures

The course defines a dashboard exposure in models/dashboards.yml pointing at mart_fullmoon_reviews. Exposures document lineage to BI assets; semantic metrics document lineage to KPI definitions. Mature teams link exposures to metrics so the docs site shows both the mart table and the official metric objects built on it.

Time spines and cumulative metrics

MetricFlow supports derived and cumulative metrics (running totals, conversion rates) when you define a time spine model — a dense date dimension dbt materialises once. The course seed seed_full_moon_dates.csv is a specialised calendar; a general time spine would be a generated date series joined in semantic YAML. Getting time spine grain wrong (day vs week) is a common source of metric mismatch between Finance (monthly) and Product (daily).

Start here

One semantic model on fct_reviews, two metrics (total_reviews, distinct_listings_reviewed), one BI tool connected.

Scale later

Join multiple semantic models on shared entities (listing, host), add saved queries, expose via API to reverse-ETL tools.

Adapters beyond Snowflake

dbt is warehouse-agnostic in architecture but not in behaviour. Every adapter translates the same Jinja model into dialect-specific DDL and DML. The course runs on Snowflake; the same Airbnb SQL compiles differently on BigQuery, Databricks, Redshift, Postgres, or DuckDB.

How models translate across warehouses

Core concepts — ref(), materializations, tests, snapshots — are shared. Adapter code paths differ for: identifier quoting, CREATE TABLE AS syntax, incremental strategies (merge versus delete+insert), Python model execution, clustering or partitioning clauses, and support for newer materializations like materialized_view or microbatch.

The Airbnb staging model src_listings reads a raw table; on Snowflake the instructor uses :: NUMBER(10,2) casts in dim_listings_cleansed. On BigQuery you would use CAST(... AS NUMERIC); on Postgres ::numeric(10,2). dbt does not auto-translate casts inside your SQL — only the wrapper DDL and incremental macros are adapter-aware.

The course repo databricks branch

The bootcamp Git repository includes a databricks branch with the same Airbnb project adapted for Databricks SQL / Unity Catalog: profile targets, catalog and schema naming, and incremental nuances that differ from Snowflake. If your job runs on Databricks, compare that branch against main side by side — the business logic in dim_listings_cleansed.sql and fct_reviews.sql stays the same; connection and materialization config change.

BigQuery specifics

Partitioning and clustering belong in model config (partition_by, cluster_by). Incremental models often use merge with partition filters to limit scan cost. Python models are not supported — the course’s disabled dim_review_sentiment.py would need a SQL port or a separate Spark job outside dbt.

Databricks specifics

Unity Catalog three-level names (catalog.schema.table) replace Snowflake database.schema. Delta Lake underpins merges and materialized views. The databricks branch shows profile and catalog settings; grants in dbt_project.yml map to UC privileges differently from Snowflake roles.

Redshift and Postgres

Redshift lacks microbatch and native materialized view support in dbt’s adapter at the same maturity as Snowflake. Merge performance depends on distribution keys and sort keys you must design. Postgres suits smaller datasets; incremental merge is emulated. Many teams use DuckDB locally with the DuckDB adapter for fast unit-test loops, then deploy to Snowflake or BigQuery in CI.

DuckDB as local adapter

DuckDB adapter lets you run a subset of the Airbnb DAG on a laptop with no cloud account. Limitations: no Python models, dialect differs from Snowflake, source definitions must point at loaded CSV or parquet instead of AIRBNB.RAW.RAW_LISTINGS. Useful for teaching, unit tests, and compile-time graph validation — not a prod target for this course project.

Porting dim_listings_cleansed: concrete diff

The course model casts price with Snowflake syntax. This is the line every adapter migration hits first:

  REPLACE(
    price_str,
    '$'
  ) :: NUMBER(
    10,
    2
  ) AS price,

BigQuery equivalent: CAST(REPLACE(price_str, '$') AS NUMERIC). Postgres: CAST(REPLACE(price_str, '$', '') AS numeric(10,2)). dbt will not rewrite this for you — adapter portability stops at the materialization wrapper.

Incremental and Python on alternate adapters

fct_reviews uses is_incremental() and dbt_utils.generate_surrogate_key — both work across adapters. Microbatch config on mart_fullmoon_reviews requires Snowflake, BigQuery, or Databricks. The disabled Python models dim_review_sentiment.py and dim_long_term_listings.py run on Snowflake Snowpark and Databricks; they fail compile on Postgres or Redshift until rewritten in SQL or moved to an external Spark job.

Materialized views

dbt’s materialized_view materialization creates warehouse-native materialized views instead of plain views or full tables. The warehouse maintains precomputed results and refreshes them according to its own rules; dbt owns the DDL lifecycle on each run.

materialized_view versus view and table

A view (the default for most Airbnb models in dbt_project.yml) stores only a query definition; every consumer pays the full compute. A table stores data and refreshes only when dbt rebuilds it. A materialized_view stores precomputed results and lets the warehouse refresh incrementally when supported — a middle ground for read-heavy, moderately fresh datasets.

{{
  config(
    materialized='materialized_view',
    on_configuration_change='apply'
  )
}}
SELECT
  l.listing_id,
  l.listing_name,
  l.price,
  h.host_name,
  h.is_superhost
FROM {{ ref('dim_listings_cleansed') }} l
LEFT JOIN {{ ref('dim_hosts_cleansed') }} h ON l.host_id = h.host_id

Warehouse-native refresh versus dbt run

When dbt runs a materialized view model, it issues CREATE MATERIALIZED VIEW or the adapter equivalent on first build, then compares config on subsequent runs. The warehouse may also auto-refresh when base tables change (Snowflake dynamic tables overlap this space; materialized views are the dbt-native path on supported adapters).

dbt does not poll refresh status. If upstream dim_listings_cleansed updates between dbt runs, the MV becomes stale until the warehouse refreshes it or dbt recreates it. Understand your platform’s refresh semantics before choosing MV over incremental table.

on_configuration_change behaviour

Model config can include on_configuration_change: apply (alter the MV when cluster keys, indexes, or refresh options change), continue (warn and keep existing), or fail (stop the run). This mirrors incremental on_schema_change but targets MV-specific settings.

SettingWhen config drift detectedRisk
applyAdapter attempts in-place alterMay trigger full refresh on some platforms
continueRun succeeds; MV keeps old configSilent mismatch between docs and reality
failRun stopsSafest for prod when someone edits warehouse UI manually

Adapter support summary

First-class materialized_view materialization targets Snowflake, BigQuery, and Databricks in current adapter releases. Redshift and Postgres either lack support or require falling back to table with scheduled refreshes. Always check the adapter changelog for your pinned version before planning MV-heavy architectures.

MV is not free freshness. Auto-refresh bills warehouse compute on every base-table change. A hot staging table feeding an MV can cost more than a nightly incremental table rebuild. Model the refresh frequency before swapping every view for an MV.

When the course models are MV candidates

dim_listings_w_hosts joins two cleansed dimensions — expensive if every dashboard repeats the join. A materialized view refreshed when dim_listings_cleansed or dim_hosts_cleansed updates could serve read-heavy workloads. fct_reviews is a poor MV candidate: append-heavy fact with incremental logic already optimised in the course.

Config reference

models:
  airbnb:
    dim:
      +materialized: table
    marts:
      +materialized: materialized_view
      +on_configuration_change: fail

Start with on_configuration_change: fail in production until you understand how your warehouse alters MVs. Relax to apply only after observability confirms alter behaviour is acceptable.

Snowflake dynamic tables versus dbt materialized_view

Snowflake also offers dynamic tables as a native refresh mechanism with a different operational model. dbt’s materialized_view materialization targets warehouse materialized view objects through adapter macros. Teams on Snowflake should read both docs before choosing: dynamic tables integrate tightly with Snowflake scheduling; dbt MVs integrate with your existing dbt run DAG and lineage. The course does not cover either; both appear in advanced production architectures after incrementals stop being enough for read latency.

Elementary and data observability

dbt tests (Sections 11–12, 16) assert rules you define: uniqueness, relationships, accepted values, expectations. Elementary adds observability on top: statistical anomaly detection, lineage-aware alerting, and report UI for trends dbt alone does not surface.

What Elementary adds beyond built-in tests

  • Anomaly detection — learns typical row counts, null rates, and column distributions; alerts when today’s run deviates without you writing a threshold for every metric.
  • Lineage-aware alerting — ties failures to upstream models and sources so on-call knows whether src_listings or fct_reviews triggered the blast radius.
  • Slack and email reports — scheduled data quality digests for stakeholders who never open the dbt Cloud UI.
  • Observability UI — HTML report from test and run metadata stored in your warehouse.

Installation steps in order

  1. Add Elementary to packages.yml next to the existing dbt_utils and dbt_expectations pins from the course repo.
  2. Run dbt deps — same workflow as Section 13.
  3. Enable Elementary models in dbt_project.yml under an elementary schema.
  4. Run dbt run --select elementary after your main DAG or include Elementary models in nightly prod job.
  5. Install the Elementary CLI (pip install elementary-data) in the same virtualenv or a dedicated observability venv.
  6. Configure Slack webhook or email in Elementary config for edr monitor alerts.
  7. Schedule edr monitor after prod dbt build from your orchestrator (Section 18).

Elementary does not replace dbt test in CI. Keep failing tests blocking merges; use Elementary for trend detection and executive-friendly reports that aggregate last night’s run metadata.

Package version pinning. Pin Elementary in packages.yml the same way the course pins metaplane/dbt_expectations at 0.10.10. Upgrading observability packages without CI validation can break metadata model schemas.
Elementary stores metadata in your warehouse. Budget storage and compute for its schema. Disable in dev sandboxes if you only need it in prod and staging.

Warehouse cost control

dbt is free; Snowflake, BigQuery, and Databricks are not. The course mentions cost in passing across materializations, tests, CI, and orchestration. This section consolidates those threads into one operational checklist.

Query result caching

Snowflake caches result sets for 24 hours when the underlying data is unchanged. Repeated dbt docs generate catalog queries and identical test SQL may hit cache. Do not rely on cache for cost planning — CI always runs fresh. BigQuery offers similar behaviour with shorter TTL and slot billing nuances. Design pipelines assuming every scheduled run pays full compute.

Resource monitors and budgets

On Snowflake, resource monitors cap warehouse credit burn and can suspend or notify. Pair a monitor with the course’s separate dev and prod warehouses from Section 19 profiles. Alerts before the invoice teaches more than post-hoc finance reviews.

Workload isolation with multiple warehouses

Route dev schemas to an X-Small warehouse that auto-suspends aggressively; prod and CI use larger warehouses with longer suspend timeouts. The course post-hook on every model writes to audit_log — small overhead per model, but hundreds of models on a Large warehouse add up. Tag-based selectors (Section 17) let nightly jobs run facts on one warehouse and lightweight tests on another.

Incremental over full-refresh

fct_reviews in the Airbnb project is incremental for a reason: appending new review dates scans only recent rows. A mistaken dbt run --full-refresh --select fct_reviews on production rescans history. Microbatch on mart_fullmoon_reviews (Section 19) limits batch windows. Default to incremental; treat full-refresh as a named backfill operation with approval.

Testing cost

Every unique test is a GROUP BY over the full column. dbt_expectations quantile tests scan entire tables. store_failures: true in the course dbt_project.yml writes failing rows to _test_failures — useful for debugging, extra storage and insert cost. Split fast tests into every CI run; run expensive expectations nightly (Section 18).

data_tests:
  +store_failures: true
  +schema: _test_failures

On a small Airbnb dev schema the cost is negligible. On a billion-row fact in prod, a failing unique test that stores ten million duplicate keys hurts. Use severity: warn or sampling for exploratory tests; keep error severity on business-critical constraints only.

Right-sizing dev versus prod

Developers should not use prod warehouses. Use dbt run --select my_model+, --empty, and --sample from Section 16 before touching full tables. Slim CI with defer (Section 19) prevents PR builds from replaying production-scale fact loads in dev schemas.

Audit post-hook overhead

The course dbt_project.yml runs an INSERT INTO audit_log post-hook on every model. On Snowflake that is one small DML per model per run. At hundreds of models, consider restricting the hook to prod-only via {% if target.name == 'prod' %} in a macro wrapper, or batching audit writes — a pattern beyond the course but relevant when estimating run time and cost at scale.

{% macro audit_log_insert() %}
  {% if target.name == 'prod' %}
    INSERT INTO {{ target.schema }}.audit_log
    VALUES ('{{ this }}', CURRENT_TIMESTAMP)
  {% endif %}
{% endmacro %}

Snowflake-specific levers (course warehouse)

Because the bootcamp targets Snowflake, these controls appear most often in real jobs aligned with the course:

  • Warehouse auto-suspend — set to 60 seconds on dev; prod CI may use 300 seconds to avoid cold-start thrash on chained jobs.
  • Query timeout — abort runaway tests at the session level before they scan a fact table for an hour.
  • Result cache — do not disable for cost savings; it helps repeated doc generation. Do not depend on it for budget math.
  • Zero-copy clone — useful for prod-like dev datasets without doubling storage; out of course scope but cheaper than full copy.
  • Credit visibility — map dbt model tags to warehouse query tags in a macro so Snowflake query history attributes spend to fct_reviews vs tests.

When mart_fullmoon_reviews uses microbatch with year-sized batches (Section 19), nightly cost is bounded by batches touched, not full history. Align orchestrator schedules with batch boundaries so you do not accidentally widen the event-time window in cron args.

Measure before optimising. Use Snowflake query history (or your warehouse’s equivalent) tagged by dbt model name for one week before changing materializations. Optimising a model that accounts for 1% of spend is procrastination; optimising fct_reviews full-refresh mistakes is survival.

Traps that catch people

  • Ref to private upstream model — cross-project ref() fails at parse time if the model is not public. Mark interface models access: public explicitly.
  • Contract enforced on wrong adapter — not all adapters validate constraints identically. Test contract failures in the target warehouse, not only on Snowflake.
  • Semantic model stale grain — MetricFlow joins break silently if fct_reviews grain changes but semantic YAML does not. Version metrics with model changes.
  • Assuming SL fixes bad models — metrics aggregate garbage the same way dashboards did; fix facts first.
  • MV on ephemeral upstream — cannot materialize through ephemeral; build on table or view models only.
  • on_configuration_change apply surprise — alters MV and triggers full refresh on some platforms during a minor config tweak.
  • Elementary without dbt run results — CLI has nothing to analyse if tests never ran or metadata models disabled.
  • dbt_expectations + Elementary duplicate alerts — tune severity so one row-count dip does not page three channels.
  • Databricks branch copied without UC grants — compile succeeds, run fails on permission. Mirror grants from Snowflake roles conceptually, not literally.
  • DuckDB prod syntax — casts and functions that work locally fail in Snowflake. CI must compile against prod adapter.
  • Mesh dependency pin drift — downstream pins revision: main and breaks weekly. Pin semver tags.
  • Groups without owners — documentation shows orphan domains. Fill owner email for on-call routing.
  • SL metric without tested upstream — MetricFlow query succeeds while fact table fails uniqueness tests. Keep model tests as gate before publishing metrics.
  • Cross-region artifact latency — mesh manifest fetch from distant registry slows CI. Mirror artifacts to same region as warehouse.
  • Materialized view on wide join — refresh cost exceeds incremental table maintenance for dim_listings_w_hosts-scale joins with volatile dimensions.

Production patterns

Teams adopting mesh start by extracting one stable domain — often core dimensions like dim_listings_cleansed and dim_hosts_cleansed — into a core project with public contracts. Domain marts stay downstream. Semantic models attach only to public facts and dimensions so MetricFlow never references staging SQL teams should not see.

Observability: run Elementary after prod dbt build, route anomalies to the same Slack channel as orchestrator failures from Section 18. Keep explicit expectations on sources; let Elementary watch row counts on fct_reviews and ingestion freshness on raw_listings.

Pattern: adapter matrix in CI

Job 1: Snowflake full build. Job 2: BigQuery dbt compile only on main. Catches dialect drift without doubling run cost.

Anti-pattern: mesh as copy-paste

Duplicating SQL into two repos without public models recreates monolith pain with extra git overhead. Publish contracts or stay monolith.

Mesh readiness checklist (conceptual)

  • Core dimensions have enforced contracts (course already does this for hosts).
  • Breaking changes use model versions or new public model names.
  • Upstream CI publishes manifest.json on every prod deploy.
  • Downstream pins semver revisions, not floating main.

Interview questions

Answer each one out loud before opening it.

When would you split a dbt monolith into a mesh instead of using folders inside one project?Design

Split when independent teams need separate deploy cadences, CI blast radius grows painful, or ownership boundaries are clearer than a shared repo. Separate repos with public models and contracts beat folders when merge conflicts and unrelated test failures block releases weekly.

Stay monolith when one team owns fewer than roughly a hundred models and coordination overhead exceeds merge pain. Mesh adds artifact sync, dependency pinning, and contract governance — worth it only when organisational boundaries match domain boundaries.

How do public models and contracts work together in dbt Mesh?Modelling

access: public marks which models downstream projects may reference via cross-project ref(). Contracts specify column names, types, and constraints those consumers can rely on. Enforced contracts fail the build if SQL drift breaks the published shape.

The course’s dim_hosts_cleansed contract is the same idea inside one repo; mesh exports it as the API between teams.

What problem does the Semantic Layer solve that well-tested dbt models alone do not?Comparison

Tested models guarantee table shape and row-level rules, not consistent metric definitions in BI tools. Finance and product can still define different aggregations on the same fct_reviews. The Semantic Layer centralises metrics and dimensions so MetricFlow generates identical SQL for every consumer.

Section 2’s “different revenue number” problem moves from duplicated dashboard SQL to duplicated metric YAML if you skip the SL layer.

How does MetricFlow differ from the legacy dbt_metrics package?Comparison

MetricFlow is the supported compiler for semantic_models and first-class metrics YAML. The old package used a parallel spec and macro layer that diverged from dbt Core releases. New work should use semantic models; the package is legacy.

MetricFlow also powers partner BI integrations and (depending on deployment) Cloud SL APIs, whereas the package only emitted SQL inside dbt runs.

You migrate the Airbnb project from Snowflake to BigQuery. What breaks first?Troubleshooting

Cast syntax in dim_listings_cleansed (:: NUMBER), Snowflake-specific functions in macros, profile and auth config, and incremental merge/partition settings. Python models like dim_review_sentiment.py are not portable to BigQuery within dbt.

Run dbt compile --target bigquery and diff compiled SQL before claiming parity. The databricks branch of the course repo shows which files change for another adapter.

When would you choose materialized_view over incremental table?Design

Choose MV when the warehouse supports efficient auto-refresh, read volume is high, staleness of minutes to hours is acceptable, and upstream change rate is moderate. Choose incremental table when you need explicit control over merge windows, microbatch slices, or adapter lacks MV support.

dim_listings_w_hosts is a read-heavy join candidate; fct_reviews with append-only dates fits incremental better than MV on volatile upstreams.

What does on_configuration_change control for materialized views?Fundamentals

It defines behaviour when MV-specific config (cluster keys, refresh options) drifts between dbt’s recorded state and the model config. apply attempts to alter the MV; continue warns and proceeds; fail stops the run. Similar philosophy to incremental on_schema_change but for MV metadata.

How does Elementary complement dbt_expectations rather than replace it?Testing

dbt_expectations encodes explicit rules: regex on price, quantile bounds, row-count parity. Elementary learns baselines and flags statistical anomalies you did not write tests for. Expectations catch known bad data; Elementary catches “something changed about volume or distribution.”

Run both: expectations in CI on critical columns; Elementary after prod builds for trend monitoring and Slack digests.

Your PR CI bill tripled after adding mesh projects. What do you investigate?Cost

Check whether each repo runs a full dbt build without defer, whether downstream rebuilds upstream facts locally, and whether artifact download fails silently forcing full graph runs. Verify selectors use state:modified+ and prod manifest freshness.

Also check test tiering: expectations on every push across three projects multiply scan cost.

Explain cross-project ref() to someone who only knows single-repo dbt.Fundamentals

Syntax is identical: {{ ref('dim_listings_cleansed') }}. The compiler resolves the model from an upstream project listed in dependencies.yml instead of from a local SQL file. Only public models are visible. Private staging models stay inside the upstream repo.

Developers still run dbt deps to fetch dependency metadata before compile, analogous to packages but for whole projects.

How would you decide between Elementary, dbt Cloud metadata, and custom Great Expectations for observability?Comparison

Elementary fits teams already running dbt Core with tests in CI who want anomaly detection and Slack reports without a second orchestration stack. It reuses dbt run results and installs as a package — minimal new infrastructure beyond the CLI and a schema.

dbt Cloud observability is integrated if you are on Cloud for scheduling and already pay for the platform; less relevant for pure Core shops. Standalone Great Expectations suits organisations with non-dbt pipelines that also need validation — heavier operational footprint than Elementary for a dbt-only shop like the Airbnb project.

For the course project specifically: start with built-in tests and dbt_expectations; add Elementary when row-count drift on fct_reviews becomes a production incident category.

Recap

  • dbt Mesh splits monoliths into domain projects linked by dependencies.yml and cross-project ref().
  • Public models with enforced contracts are the API between mesh projects.
  • Groups in schema YAML document ownership; the course repo does not use them yet.
  • The Semantic Layer + MetricFlow centralise metrics so BI tools agree on KPIs.
  • Legacy dbt_metrics is superseded by semantic models — check Cloud vs Core/Fusion availability before promising SL.
  • Adapters share concepts but differ on merge, microbatch, Python models, and materialized views.
  • The course Git repo has a databricks branch for adapter-specific Airbnb config.
  • materialized_view uses warehouse refresh; tune on_configuration_change carefully.
  • Elementary adds anomaly detection and reporting atop dbt tests; it complements dbt_expectations.
  • Warehouse cost control: incremental models, Slim CI with defer, test tiering, and right-sized warehouses.
