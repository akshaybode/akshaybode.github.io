Microbatching

Microbatch is an incremental strategy introduced in dbt 1.9 that processes time-bounded slices of a model instead of merging row-by-row or scanning the entire upstream table every run. dbt divides history along an event_time column, rebuilds each batch independently, and replaces only the affected partitions in the warehouse.

By the end of the course, mart_fullmoon_reviews — introduced as a plain table in Section 9 — becomes a microbatch incremental model in a custom mart schema. The join logic to the full-moon seed is unchanged; only materialization and batching config change. Read Section 9 for the seed join predicate and sanity checks; this section covers the incremental mechanics.

What microbatch replaces

Classic incremental models append or merge new rows using is_incremental() filters. That works when late-arriving data is rare and the merge key is stable. It struggles when:

  • Upstream facts can change inside historical windows (corrections, backfills).
  • A full recompute of a year is cheaper than row-level merge logic on Snowflake.
  • You want idempotent batch rebuilds aligned to calendar periods for audit.

Microbatch answers by treating each time window as a mini full-refresh. Run Monday's job and only 2024's slice reprocesses; prior years stay untouched unless you widen the event-time window.

Incremental strategyUnit of workBest when
delete+insert / mergeNew/changed rows since last runAppend-mostly facts, stable keys
appendInsert-only new rowsImmutable event streams
microbatchTime-bounded batches on event_timePeriodic recompute of historical slices, large facts

event_time on upstream facts

Microbatch requires every model in the chain to declare which column defines event time. The fact table must expose it first:

{{
  config(
    materialized = 'incremental',
    on_schema_change='fail',
    event_time='review_date'
    )
}}

WITH src_reviews AS (
  SELECT * FROM {{ ref('src_reviews') }}
)
SELECT 
  {{ dbt_utils.generate_surrogate_key(['listing_id', 'review_date', 'reviewer_name', 'review_text']) }} as review_id,
  *
FROM src_reviews
WHERE review_text is not null
{% if is_incremental() %}
  {% if var("start_date", False) and var("end_date", False) %}
    {{ log('Loading ' ~ this ~ ' incrementally (start_date: ' ~ var("start_date") ~ ', end_date: ' ~ var("end_date") ~ ')', info=True) }}
    AND review_date >= '{{ var("start_date") }}'
    AND review_date < '{{ var("end_date") }}'
  {% else %}
    AND review_date > (select max(review_date) from {{ this }})
    {{ log('Loading ' ~ this ~ ' incrementally (all missing dates)', info=True)}}
  {% endif %}
{% endif %}

The mart inherits the same event_time so batches align with review dates flowing from fct_reviews. Without event_time on upstream nodes, dbt cannot compute batch boundaries and compilation fails.

CLI event-time flags

Microbatch runs accept optional window overrides:

  • --event-time-start — inclusive lower bound for batches to process.
  • --event-time-end — exclusive upper bound.
  • --full-refresh — rebuild selected batches even if dbt considers them current.

Force a full refresh across a decade window:

dbt run -s mart_fullmoon_reviews --full-refresh --event-time-start "2020-01-01" --event-time-end "2030-01-01"

Use narrow windows when backfilling a single bad year after upstream corrections. Use wide windows cautiously on large facts — each year batch still scans upstream rows in that period.

The threads:4 requirement

Microbatch can hang without threads: 4. A dbt bug present since version 1.9 causes microbatch runs to stall when thread count is too low. Set threads: 4 (or higher) on every output in profiles.yml before running microbatch models. This is not documented as prominently as it should be; if your run appears frozen with no SQL activity, check threads first.

The production profile sets four threads on dev, staging, and prod:

    dev:
      type: snowflake
      ...
      threads: 4
      warehouse: COMPUTE_WH
    prod:
      type: snowflake
      ...
      threads: 4
      warehouse: COMPUTE_WH

On BigQuery and Databricks the same config key applies; adapter parallelism differs internally but the course recommendation stands until the upstream bug is fixed.

How dbt chooses batches on each run

On the first microbatch run, dbt walks forward from begin in steps of batch_size until it reaches the latest event_time present in upstream data. Each batch compiles the model SQL with an implicit filter on event_time so the warehouse only scans rows in that window. Subsequent runs compare batch metadata against the existing incremental table and skip batches dbt considers unchanged unless you pass --full-refresh or widen the CLI event-time window.

Setting full_refresh=false in config does not mean "never rebuild" — it means "respect batch staleness logic instead of dropping the whole table every run." When upstream facts backfill 2018 rows, the 2018 batch becomes eligible again even if 2019–2024 were already current.

batch_size valueTypical useTrade-off
hourNear-real-time pipelines, small daily volumeMany batches; higher orchestration overhead
dayDaily ELT with moderate historyBalance between parallelism and batch count
monthMonthly reporting martsFewer batches; larger per-batch scan
yearCourse demo on review history since 2009~15 batches total; each year scan is bounded

Upstream event_time on dim_listings_cleansed

The course also sets event_time='created_at' on dim_listings_cleansed (a view overriding the dim folder table default — see Section 8). Any model in a microbatch chain must expose a consistent event-time column. Facts use review_date; dimensions may use created_at when they participate in batch downstream paths.

Contrasting microbatch with timestamp incremental

fct_reviews still uses classic timestamp incremental with is_incremental() and max(review_date) when vars are absent. The mart layers microbatch on top of that fact output. The fact appends new review dates incrementally; the mart recomputes year batches of enriched rows (including the full-moon label) without scanning the entire fact history every time. Two strategies coexist in one DAG — strategy is per-model, not per-project.

Everyday analogy — timestamp incremental is a diary where you only append today's page. Microbatch is a photo album where you reprint one year's section when someone sends corrected pictures from that year, without reprinting the whole album.

Debugging microbatch runs

When batches behave unexpectedly, work through this sequence:

  1. Confirm threads: 4 in the active profile output.
  2. Query min/max event_time in the warehouse fact table — batch range cannot exceed data.
  3. Run dbt compile -s mart_fullmoon_reviews and inspect target/compiled/ for batch filters injected into SQL.
  4. Check logs/dbt.log for batch start/end log lines and skipped batch messages.
  5. Retry with an explicit narrow window: --event-time-start / --event-time-end.

On BigQuery, batch replacement may use partition decorators; on Databricks, delta replaceWhere patterns differ — the dbt adapter abstracts this, but warehouse query history still shows one statement per batch.

full_refresh=false versus CLI --full-refresh

These interact but are not the same knob. Model config full_refresh=false is the default steady-state: respect batch staleness, skip unchanged batches. Passing --full-refresh on the CLI overrides for that invocation and forces selected batches to rebuild even if dbt would skip them. Operators use CLI full refresh after logic bugs in the mart SQL; they use config full_refresh=false day-to-day to keep incremental behaviour.

Steady scheduled run

dbt run -s mart_fullmoon_reviews — processes new/stale year batches only.

Backfill one bad year

--full-refresh --event-time-start 2019-01-01 --event-time-end 2020-01-01

Initial historical load

Wide window or first run from begin through max review_date.

Model lifecycle: versioning, deprecation, disabling

Production teams ship breaking column changes without renaming every downstream ref(). dbt model versions let you keep one logical model name (dim_hosts_cleansed) while v1 and v2 SQL live in separate files. Deprecation dates warn consumers before removal; enabled: false removes nodes from the DAG entirely.

Creating version 2 SQL

Version 1 remains in dim_hosts_cleansed.sql (a view in earlier sections, promoted to table when contracts arrive). Version 2 lives in a separate file with stricter null handling on host_name:

{#
  You might have `view` as the materialization as we only 
  replace `materialized` with `table` when we implement constraints. 
#}
{{
  config(
    materialized = 'table' 
    )
}} 
WITH src_hosts AS (
    SELECT
        *
    FROM
        {{ ref('src_hosts') }}
)
SELECT
    host_id,
    NVL(
        host_name,
        'N/A'
    ) AS host_name,
    is_superhost,
    created_at,
    updated_at
FROM
    src_hosts

The behavioural change is subtle but real: v1 passes through null names; v2 guarantees a string. Downstream joins and not-null constraints depend on v2 semantics.

Declaring versions in schema.yml

YAML ties file names to version numbers and marks v1 deprecated:

  - name: dim_hosts_cleansed
    versions:
      - v: 1
        defined_in: dim_hosts_cleansed
        deprecation_date: 2030-01-01
      - v: 2
        columns:
          - include: '*'
            exclude: [host_name]
          - name: host_name
            description: The name of the host (N/A if not available)
            data_type: string
            constraints:
              - type: not_null
    latest_version: 2
    description: Cleansed table for the Airbnb hosts
    config:
      contract:
        enforced: true
YAML keyPurpose
defined_inSQL file for v1 (filename without .sql)
v: 2 without defined_indbt expects dim_hosts_cleansed_v2.sql by convention
latest_versionDefault when ref('dim_hosts_cleansed') has no version argument

Deprecating models

deprecation_date on a version (or model) tells dbt to emit warnings when the node is built or referenced. It does not auto-disable the model — consumers still compile until you remove the version or set a past date and delete the SQL. Pair deprecation warnings with comms and a sunset ticket.

For whole-model deprecation (not versioning), add deprecation_date at the model level in YAML. Docs and dbt ls --resource-type model show deprecated nodes; CI can fail on warnings with --warn-error.

Disabling models

When a model should not run at all — experimental Python transforms, demo-only dimensions — set enabled: false. Disabled nodes disappear from dbt run, dbt build, and lineage for execution (they still parse unless you remove the file).

The course disables two Python models added in Section 17:

def model(dbt, session):
    dbt.config(
        materialized = "table",
        packages = ["holidays"],
        enabled=False # We add this line in the Model Lifecycle / Disabling Models section
    )
def model(dbt, session):
    dbt.config(
        materialized = "table",
        enabled= False, # We are disabling this Model later in the Model Lifecycle section
        packages = ["textblob"]
    )

Override at runtime without editing files: temporarily flip enabled=True in the Python config to run a disabled model locally. For YAML models, equivalent is config(enabled=false) in the model file or folder-level YAML.

Versioning and enforced contracts together

Version 2 of dim_hosts_cleansed ships with contract.enforced: true at the model level (from Section 12). The v2 YAML block redefines host_name with a not_null constraint matching the NVL(..., 'N/A') logic in SQL. Versioning lets you change contract shape without renaming the model; consumers opt into v2 explicitly or inherit via latest_version.

Version before rename. Renaming dim_hosts_cleansed to dim_hosts_cleansed_v2 breaks every ref(), exposure, and dashboard. Versions keep the public name stable while SQL files diverge.

Migration playbook for breaking host changes

When shipping v2 in a real team, the sequence looks like this:

  1. Merge v2 SQL file and YAML versions block with latest_version: 2 but keep v1 defined_in active.
  2. Update critical downstream models to ref(..., v=2) one PR at a time.
  3. Run full prod build; verify v2 table matches contract tests.
  4. Set deprecation_date on v1 far enough out for downstream consumers to migrate.
  5. After sunset, remove v1 SQL and the v1 version stanza from YAML.

The course compresses this into one lesson; production spreads it across sprints. The exam tests the YAML mechanics, not the project-management timeline.

Relationships tests still reference logical model name

In schema.yml, the listings host foreign key test still points at the versioned model without a version suffix:

          - relationships:
              arguments:
                to: ref('dim_hosts_cleansed')
                field: host_id

That resolves to v2 once latest_version: 2. If v1 and v2 coexist during migration, ensure tests target the version your consumers actually use.

Switching targets on the CLI

Default is target: dev. Override per invocation:

Never point an experimental full-refresh at prod by habit. Muscle memory dbt run --full-refresh against --target prod rebuilds production facts. Use separate shell prompts, profile colours, or wrapper scripts that require typing the target name.

Working with targets in dbt Cloud versus Core

dbt Cloud maps environments to targets under the hood — a Development environment is your personal schema, Production is prod. In dbt Core, you replicate that with profile outputs and DBT_ENV_NAME. The course teaches Core explicitly so the profile YAML and env vars are visible; Cloud users should still understand what happens when they click "Run" in the IDE (it is dbt build --target dev with their user schema).

profiles-dir and project-dir together

CI always runs from cd airbnb with --profiles-dir _prod_profiles. The profile name airbnb: must match profile: in dbt_project.yml. A common mistake is copying profiles to the wrong directory or running dbt from the repo root instead of the project folder — symptoms include "profile not found" or wrong schema resolution.

Environment variables

env_var() in profiles.yml keeps secrets and personal identifiers out of git. dbt reads them from the process environment at parse time; missing vars fail fast with a clear error.

What the course externalises

  • SNOWFLAKE_ACCOUNT — account locator.
  • DBT_USER — Snowflake user for key-pair auth.
  • PRIVATE_KEY — PEM private key body (multiline in CI secrets).
  • PRIVATE_KEY_PASSPHRASE — key encryption passphrase if applicable.
  • DBT_ENV_NAME — short name embedded in dev schema (DBT_MYDEV, DBT_FEATURE_AUTH).

Setting variables on Windows (PowerShell)

Download helper scripts from https://dbtsetup.nordquant.com. Source the PowerShell script, then set the personal schema name:

. ..\set-env.ps1
$env:DBT_ENV_NAME="MYDEV"

Verify:

dbt debug --profiles-dir _prod_profiles

Setting variables on Mac / Linux

. ../set-env.sh
export DBT_ENV_NAME="MYDEV"

Secrets in CI

GitHub Actions inject secrets as environment variables. The course workflows map repository secrets to the same names profiles.yml expects:

    env:
      SNOWFLAKE_ACCOUNT:      "${{ secrets.SNOWFLAKE_ACCOUNT }}"
      DBT_USER:               "${{ secrets.DBT_USER }}"
      PRIVATE_KEY: |
        ${{ secrets.PRIVATE_KEY }}
      PRIVATE_KEY_PASSPHRASE: "${{ secrets.PRIVATE_KEY_PASSPHRASE }}"

PR CI derives DBT_ENV_NAME from the branch name (uppercase, slashes and hyphens become underscores) so each pull request builds into an isolated schema without manual setup.

Never commit secrets. profiles.yml in the course repo contains only env_var() placeholders. Real keys live in shell exports locally and GitHub Secrets in CI.

env_var() behaviour and defaults

env_var('DBT_ENV_NAME') with no second argument fails compilation if the variable is unset — intentional fail-fast. You can supply a default for local convenience: env_var('DBT_ENV_NAME', 'LOCAL'). The course omits defaults so missing setup is obvious.

Jinja filters on env vars are common in profiles: | upper | trim normalises schema names regardless of whether the developer typed mydev or MYDEV.

Multiline private keys in CI

Snowflake key-pair auth stores the PEM body in PRIVATE_KEY. In GitHub Actions, the pipe literal syntax preserves newlines:

PRIVATE_KEY: |
  ${{ secrets.PRIVATE_KEY }}

Locally, set-env.ps1 and set-env.sh load the same variables from files outside git. Never paste keys into Slack or commit them to a branch — rotate immediately if leaked.

Custom schemas

By default dbt builds every model into target.schema from the active profile. Production teams split marts, snapshots, and staging into named schemas. The schema config on a model sets the custom name; generate_schema_name macro controls how custom and target schemas combine.

schema config on the mart

mart_fullmoon_reviews sets schema='mart' alongside microbatch config. Resolution depends on target:

  • dev: DBT_MYDEV_MART — personal prefix plus custom suffix.
  • prod: MART — clean custom name only.

The generate_schema_name macro

Real project code:

{% macro generate_schema_name(custom_schema_name, node) -%}

  {% set custom_schema_name_cleansed = custom_schema_name | trim | upper %}
  {% set target_schema_cleansed = target.schema | trim | upper %}

  {%- if custom_schema_name is none -%}
    {# No custom schema: always use target schema as-is (uppercased above) #}
    {{ target_schema_cleansed }}
  {%- else -%}
    {%- if target.name == 'prod' -%}
        {# Prod: use clean custom schema name only #}
        {{ custom_schema_name_cleansed }}
    {%- else -%}
      {# Staging / Dev / feature branches: prefix with personal/branch schema. #}
      {{ target_schema_cleansed }}_{{ custom_schema_name_cleansed }}
    {%- endif -%}
  {%- endif -%}
{%- endmacro %}

The macro checks target.name == 'prod', not the schema string. Adding a staging target keeps the prefixed pattern so staging experiments do not write bare MART names that collide with production.

Certification: default dbt behaviour concatenates target.schema and custom schema with an underscore. Overriding generate_schema_name is the supported way to change that.

Default dbt behaviour without the macro

If you delete generate_schema_name.sql, dbt's built-in logic produces <target.schema>_<custom_schema> in all environments. That yields PROD_MART in production — often wrong when BI tools expect schema MART. The course macro is the standard pattern for "clean prod names, prefixed dev names."

Folder-level schema in dbt_project.yml still applies: a model inherits folder defaults unless overridden in its own config() block. mart_fullmoon_reviews sets schema inline because it is the teaching example for mart-layer separation.

Cleaning up dev schemas

Every PR CI run that sets DBT_ENV_NAME from the branch name creates schemas like DBT_FEATURE_LOGIN_MART. Without cleanup, Snowflake accumulates orphaned objects. The course ships a macro that drops all schemas matching the dev prefix.

drop_dev_schemas macro

{% macro drop_dev_schemas() %}

  {# Use the resolved target schema as the prefix (e.g. DBT_<env_name> on the dev target) #}
  {% set prefix = target.schema | upper %}

  {# Safety guard: only drop dev schemas (prefixed DBT_), never PROD/STAGING #}
  {% if not prefix.startswith('DBT_') %}
    {{ exceptions.raise_compiler_error("Refusing to drop schemas: target.schema (" ~ prefix ~ ") is not a dev schema (must start with DBT_)") }}
  {% endif %}

  {{ log(" * drop_dev_schemas: Looking for schemas with prefix:  " ~ prefix, info=True) }}

  {# Find all schemas matching the prefix #}
  {% set results = run_query(
    "SELECT schema_name
     FROM information_schema.schemata
     WHERE schema_name ILIKE '" ~ prefix ~ "%'"
  ) %}

  {# Drop each matching schema #}
  {% if execute %}
    {% set schemas = results.columns[0].values() %}

    {% if schemas | length == 0 %}
      {{ log(" * drop_dev_schemas: No schemas found matching prefix: " ~ prefix, info=True) }}
    {% else %}
      {{ log(" * drop_dev_schemas: Found " ~ schemas | length ~ " schema(s) to drop:", info=True) }}
      {% for schema in schemas %}
        {{ log(" * drop_dev_schemas: Dropping: " ~ schema, info=True) }}
        {% do run_query("DROP SCHEMA IF EXISTS " ~ schema ~ " CASCADE") %}
      {% endfor %}
    {% endif %}

  {% endif %}

{% endmacro %}

Execute with dbt run-operation:

dbt run-operation drop_dev_schemas --profiles-dir _prod_profiles

The macro runs a compiler error if you accidentally point it at prod or staging where target.schema does not start with DBT_. That guard is essential — without it, one wrong target flag becomes catastrophic.

What CASCADE drops

DROP SCHEMA ... CASCADE removes every table, view, and staged object inside the schema. For dev prefixes this includes both the base schema (DBT_MYDEV) and suffixed custom schemas (DBT_MYDEV_MART) because the macro matches ILIKE 'DBT_MYDEV%'. Seeds loaded into the dev schema, incremental tables, and test failure tables all disappear together — which is what you want when a PR merges or you reset local experiments.

When not to run drop_dev_schemas

  • Mid-PR when you still need the schema for debugging a failed Slim CI run.
  • When two developers share the same DBT_ENV_NAME — one person's cleanup drops another's work.
  • Against staging or prod targets — the macro refuses, but double-check --target dev before running.

CI runs cleanup only on merged PR close, not on every push. Local developers run it manually when switching features or reclaiming warehouse storage.

dbt retry

When dbt build fails partway through, fix the error and resume without re-running successful nodes:

dbt build --profiles-dir _prod_profiles
# fix dim_listings_cleansed.sql
dbt retry --profiles-dir _prod_profiles

dbt retry requires the prior command to have written run_results.json in the same target/ directory. It does not replace state comparison — it only continues a interrupted run.

What manifest.json stores for state diff

Each node entry includes a checksum of compiled content, config hashes, depends_on lists, and database identifiers from the last run. state:modified compares current parse output against those fields. Changing a comment in SQL modifies the body checksum; changing materialized='table' to view triggers config modified; adding a ref() triggers dependency modified.

Open target/manifest.json in a JSON viewer when debugging unexpected selector results — search for the model unique_id (e.g. model.airbnb.dim_listings_cleansed) and compare checksum values between dev and prod artifact directories.

Separate target-path for prod artifacts

Deferring state

--defer tells dbt to resolve ref() and source() for unselected upstream models against relations recorded in the comparison manifest's environment — typically production — instead of building them in your dev schema.

Defer in practice

dbt run-operation drop_dev_schemas --profiles-dir _prod_profiles
dbt run --profiles-dir _prod_profiles --target dev --state target-prod --select state:modified --defer

Without defer, a one-line change to mart_fullmoon_reviews still requires rebuilding fct_reviews, src_reviews, seeds, and every upstream dimension in your personal schema. With defer, dbt reads prod's fct_reviews while writing the mart into DBT_MYDEV_MART.

--favor-state

When both a local dev relation and a deferred prod relation exist for the same node, dbt normally prefers the local build. --favor-state reverses that: the deferred relation from the comparison manifest wins. Use it when dev schemas contain stale partial builds that would shadow prod data during CI validation.

dbt build --profiles-dir _prod_profiles --target dev \
  --select state:modified+ --defer --favor-state --state ./prod-target

Why defer saves warehouse cost

A pull request touching one mart should not recompute multi-terabyte facts. Slim CI downloads the last prod manifest.json (and relies on prod relations still existing at the database locations recorded in that manifest), selects state:modified+, and defers everything else. You pay for the changed subgraph plus tests, not the entire Airbnb DAG.

Defer assumes prod relations still exist. If prod dropped a table but the artifact still references it, deferred runs fail at query time. Refresh prod artifacts after every deploy and align retention policies with defer expectations.

Local defer workflow mirroring CI

To reproduce Slim CI on a laptop before opening a PR:

  1. Obtain the latest prod artifact — download from GitHub Actions or compile prod locally if you have prod read access.
  2. Place it in airbnb/prod-target/ or target-prod/.
  3. Set DBT_ENV_NAME to a personal value not shared with CI branch names.
  4. Run dbt ls --state ./prod-target --select state:modified+ and review the list.
  5. Run dbt build --state ./prod-target --select state:modified+ --defer.

This catches "modified+" blast radius surprises before CI spends warehouse credits.

Snapshots deserve special care: they are stateful history tables. Section 10 notes that deferring snapshot refs while running snapshots locally can desynchronise history. Many teams run snapshots only in prod and defer to prod snapshot outputs in PR CI.

Defer resolution order

  1. dbt parses the current project and applies --select.
  2. For each upstream node not in the selection, dbt checks the comparison manifest for database/schema/identifier.
  3. With --defer, compiled SQL references those prod locations instead of dev target schema names.
  4. Selected nodes still build into the active target (DBT_<branch> in PR CI).

PR Slim CI: pr-slim-ci.yml

On every pull request: set DBT_ENV_NAME from branch name, download prod artifact, run deferred modified build.

Key design decisions in this workflow:

  • uv sync installs locked dependencies from pyproject.toml — same pin as local dev.
  • Branch sanitisation prevents invalid Snowflake schema characters.
  • if_no_artifact_found: fail prevents silent full builds that mask missing prod state.
  • state:modified+ includes downstream tests on changed subgraph — catches broken marts when a dim changes.

The workflow uses dawidd6/action-download-artifact to pull the latest successful prod-build artifact from main — not the PR branch. That guarantees defer targets match what production actually deployed.

Traps that catch people

  • Microbatch without event_time upstream — compilation fails or batches misalign. Add event_time to every model in the microbatch chain, not just the mart.
  • threads: 1 hang — run appears stuck with no SQL. Set threads: 4 in every profile output before debugging SQL.
  • Defer without prod artifact — --state path missing manifest.json makes state:modified unreliable and defer resolution fails.
  • Local dev shadowing defer — partial local builds of upstream models make dbt prefer dev tables unless you pass --favor-state.
  • drop_dev_schemas on prod target — macro guard prevents this, but never remove the DBT_ prefix check when customizing.
  • Custom schema macro ignores target.name — dev writes bare MART and collides with production naming conventions.
  • ref() without version during migration — silently picks latest_version; explicit v=2 documents intent during breaking changes.
  • Missing DBT_ENV_NAME — profile compilation error or schema named DBT_ with empty suffix. Set env var before every dev run.
  • CI guard copied without secrets — bootcamp workflows skip on the official repo; your fork needs secrets and must remove or adjust the if: guard.
  • Assuming defer replaces prod data — defer reads prod; it does not write to prod. PR builds still land in DBT_<branch>.
  • full_refresh=false misunderstanding — microbatch still rebuilds batches deemed stale; it is not append-only.
  • Enabled false still in selectors — disabled models are excluded automatically, but docs and parse still see the file unless removed.
  • Prod-build artifact expiry — 90-day retention in course workflow; long-idle repos need manual prod rebuild before first PR after hiatus.
  • Branch name sanitisation — CI replaces / and - with _ in DBT_ENV_NAME; local env names should follow the same rules to match cleanup.
  • Staging target without macro branch — staging uses prefixed custom schemas like dev; only prod gets bare MART.

Cross-warehouse notes

Microbatch is supported on Snowflake, BigQuery, and Databricks adapters in dbt 1.9+. Postgres and Redshift do not offer microbatch — teams on those warehouses stay on merge or delete+insert incrementals. Defer and state selectors are adapter-agnostic; only artifact storage and CI runner OS differ. Key-pair auth in the course profile is Snowflake-specific; BigQuery uses service account JSON via env vars with the same env_var() pattern.

Production patterns

Mature teams treat the prod manifest as a first-class artifact with the same retention policy as migration scripts. Main-branch merges upload target/; PR jobs download it before any warehouse spend. Developers set DBT_ENV_NAME to their initials locally and never share prod credentials on laptops without read-only roles.

Schema macro conventions split cleanly: prod gets semantic names (MART, STAGING, CORE); non-prod prefixes with DBT_<identity> so cleanup macros stay safe. Microbatch models tag with fact for selective nightly batch reruns using event-time windows.

Pattern: artifact-driven Slim CI

Prod upload → PR download → dbt ls -s state:modified+ --state ... logged to job output → defer build. Reviewers see blast radius before approve.

Anti-pattern: shared dev schema

One DBT_DEV schema for all engineers causes overwrite races and makes defer pointless. Personal or branch schemas fix isolation.

Some teams borrow a blue/green deployment pattern for the warehouse itself: a full production build lands in a parallel schema (green) while the current schema (blue) keeps serving BI traffic; a single view-swap or a change to generate_schema_name's target promotes green to live once the build and its tests pass, and blue stays around as an instant rollback. This trades extra storage and a full rebuild for zero-downtime cutovers, which matters more for a microbatch model with strict freshness SLAs than for a nightly batch job that already runs before anyone reads the dashboard.

Interview questions

Answer each one out loud before opening it.

What is microbatch incremental and when would you choose it over merge?Production

Microbatch rebuilds time-bounded slices of a model on an event_time column instead of merging row-by-row. Each batch (hour, day, month, year) is processed as a mini full-refresh of that window.

Choose it when historical slices may need recompute, when batch idempotency matters for audit, or when warehouse engines handle partition replacement cheaper than merge logic. Stick with merge/append when data is append-only and late-arriving rows are the main concern.

Why does microbatch require threads: 4 in profiles.yml?Gotcha

A dbt bug since version 1.9 causes microbatch runs to hang when thread count is too low. The course sets threads: 4 on dev, staging, and prod outputs as a workaround.

If a microbatch run shows no progress and no warehouse queries, check threads before rewriting SQL. This is operational knowledge teams learn after a stuck CI job.

What does event_time do and where must it be configured?Fundamentals

event_time names the column dbt uses to partition microbatch windows. It must appear in the model config for every node in a microbatch chain — the fact (fct_reviews) and the downstream mart (mart_fullmoon_reviews).

CLI flags --event-time-start and --event-time-end optionally narrow which batches run in a given invocation.

How do dbt model versions work without renaming ref() everywhere?Design

YAML declares versions: with v: 1 pointing at defined_in: dim_hosts_cleansed and v2 living in dim_hosts_cleansed_v2.sql. latest_version: 2 makes bare ref('dim_hosts_cleansed') resolve to v2.

Downstream models pin explicitly with ref('dim_hosts_cleansed', v=2) during migration. v1 carries deprecation_date to warn consumers before removal.

What is the difference between deprecating and disabling a model?Comparison

Deprecation (deprecation_date) keeps the model in the DAG but emits warnings when it is built or referenced. Consumers still compile until the model is removed.

enabled: false removes the node from execution entirely — it will not run on dbt build. The course disables expensive Python models (dim_fullmoon, dim_review_sentiment) this way.

How do dev and prod targets differ in the course profiles.yml?Production

Both share credentials via env_var(). Dev uses schema: "DBT_{{ env_var('DBT_ENV_NAME') | upper | trim }}" for personal isolation. Prod uses schema: PROD plus the custom schema macro for semantic names like MART.

Switch targets with --target prod or --target dev. Default is target: dev in the profile.

Explain generate_schema_name and why prod checks target.name.Design

The macro overrides dbt's default schema concatenation. When a model sets schema='mart', prod returns MART only. Non-prod targets prefix with target.schema → DBT_MYDEV_MART.

Checking target.name == 'prod' keeps staging and dev on the prefixed pattern so experiments never write unprefixed production-like schema names.

What does --defer do and why does Slim CI use it?Cost

--defer resolves unselected upstream ref() and source() nodes against relations recorded in the comparison manifest — typically production — instead of building them in the dev schema.

Slim CI selects state:modified+ and defers everything else so a one-line mart change does not rebuild multi-gigabyte facts in a throwaway PR schema. That is the primary warehouse cost savings.

What is --favor-state and when do you need it?Troubleshooting

When both a local dev copy and a deferred prod relation exist, dbt normally prefers the local table. --favor-state forces the deferred relation from the comparison manifest to win.

Use it in CI when partial local runs left stale upstream tables that would shadow correct prod data during validation.

What is state:modified and what artifact does it require?Production

state:modified selects nodes whose SQL, config, or dependencies differ from a saved project state. Pass --state path/to/artifacts pointing at a directory containing manifest.json from a prior deploy.

state:modified+ adds downstream dependents. Prod CI uploads that manifest; PR CI downloads it before building.

How does drop_dev_schemas prevent catastrophic prod drops?Gotcha

The macro reads target.schema and raises a compiler error unless the prefix starts with DBT_. Prod and staging schemas fail the guard before any DROP SCHEMA runs.

It then queries information_schema.schemata for all schemas matching the prefix and drops them with CASCADE — including custom suffix schemas like DBT_MYDEV_MART.

Why are the GitHub Actions workflows guarded with if: github.repository != ...?Production

The bootcamp repo ships workflows as teaching references. The guard skips jobs on the official course repository where secrets are not configured, so student forks do not fail CI by default.

Production-ready copies live in zoltanctoth/dbt-reference-production-repo. Real deployments remove or adjust the guard and configure GitHub Secrets.

What does dbt retry do versus re-running dbt build?Fundamentals

dbt retry reads run_results.json from the immediately prior invocation and reruns only failed or skipped nodes. Successful models are not repeated.

Re-running dbt build executes the full selection again. Retry is for fixing a mid-pipeline syntax error without paying twice for completed models.

What does the --empty flag do on dbt build --target prod?Certification

--empty creates relations with zero rows while still validating compilation, contracts, and DDL against the warehouse. The course uses it to smoke-test custom schema resolution on prod without loading data.

It is cheaper than a full prod build and catches schema macro mistakes before a real deploy.

How does Slim CI derive DBT_ENV_NAME from a branch name?Production

The workflow reads github.head_ref, replaces / and - with underscores, uppercases the result, and writes it to GITHUB_ENV. Branch feature/login becomes DBT_FEATURE_LOGIN schema prefix.

The same sanitisation runs in pr-cleanup.yml so merged branch schemas are dropped with the matching prefix.

Recap

  • Microbatch uses incremental_strategy='microbatch', event_time, begin, and batch_size to rebuild time slices instead of row merges.
  • Set threads: 4 in profiles before microbatch runs — lower values can hang (dbt bug since 1.9).
  • mart_fullmoon_reviews ends as microbatch incremental in schema mart; join logic unchanged from Section 9.
  • Model versions keep one logical name; v2 lives in dim_hosts_cleansed_v2.sql; dim_listings_w_hosts uses ref('dim_hosts_cleansed', v=2).
  • deprecation_date warns consumers; enabled: false removes nodes from execution.
  • Dev target schema is DBT_{{ env_var('DBT_ENV_NAME') }}; prod uses PROD plus clean custom schemas via macro.
  • generate_schema_name prefixes custom schemas in non-prod; prod uses bare custom names when target.name == 'prod'.
  • drop_dev_schemas drops only schemas starting with DBT_; refuses prod/staging targets.
  • --state plus state:modified+ selects changed nodes; prod manifest uploaded by prod-build.yml.
  • --defer reads upstream from prod artifact; --favor-state prefers deferred refs over stale local tables.
  • Slim CI workflows are reference-only in the bootcamp repo; live pattern in zoltanctoth/dbt-reference-production-repo.
  • dbt retry resumes failed nodes from the prior run without repeating successes.
