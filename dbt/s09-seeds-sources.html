Seeds: CSV reference data in the warehouse

A seed is a CSV file dbt loads into a table. Use seeds for small, static or slowly changing reference datasets that belong in version control — country codes, holiday calendars, manual mappings — not for data your ELT pipeline already loads.

What dbt seed does

When you run dbt seed, dbt reads every CSV in the seeds/ folder (configured by seed-paths in dbt_project.yml), infers column types, and creates or replaces a table in your target schema. The table name is the filename without the extension: seed_full_moon_dates.csv becomes seed_full_moon_dates.

Downstream models reference seeds with {{ ref('seed_full_moon_dates') }} — the same function used for models. dbt treats seeds as first-class nodes in the DAG: they appear in lineage, respect build order, and run before models that depend on them when you use dbt build.

Seeds are forSeeds are not for
Reference lookups under a few hundred thousand rowsLarge fact tables your loader already owns
Data that changes only when you commit a PRHigh-frequency updates from an API
CSV files you want in git next to the models that use themPII-heavy extracts that should never be in version control
One-off mappings the business maintains in a spreadsheetAnything Fivetran or Airbyte already lands in raw
Rule of thumb: if the row count fits comfortably in Excel and updates when an analyst edits a file, it is probably a seed. If a loader job appends millions of rows nightly, it is a source.

Seeds land in your development schema (DEV in the course) by default. On Snowflake the fully qualified name is something like AIRBNB.DEV.SEED_FULL_MOON_DATES. BigQuery puts them in your dataset; Postgres in your search path schema.

You can configure seeds in dbt_project.yml or a seeds/schema.yml file — column types, quoting, schema overrides. The course keeps defaults; the important part is that the CSV exists and dbt seed has run at least once before any model calls ref('seed_full_moon_dates').

Seed configuration in dbt_project.yml

The course project declares where seeds live in dbt_project.yml:

seed-paths: ["seeds"]

You can also set project-wide seed defaults under a seeds: block — schema overrides, quoting, column types, tags. The course leaves seeds at defaults, but a typical production override looks like this:

seeds:
  airbnb:
    +schema: reference
    +quote_columns: false
    seed_full_moon_dates:
      +column_types:
        full_moon_date: date

+schema: reference would load seeds into a dedicated reference schema instead of your dev target schema. +quote_columns: false matters on Postgres where quoting changes case sensitivity. Explicit column_types prevents dbt from inferring full_moon_date as a string when you need a native DATE for joins.

Seeds in the DAG and CLI commands

Seeds are nodes in the same manifest as models. List them with dbt ls --resource-type seed or include them in selectors: dbt seed --select seed_full_moon_dates, dbt build --select +mart_fullmoon_reviews (the + prefix pulls upstream seeds and models).

CommandRuns seeds?Runs models?When to use
dbt seedYesNoCSV changed in git; first-time setup
dbt runNoYesModels only; assumes seeds already loaded
dbt buildYes (if selected)YesEnd-to-end: seed → model → test in DAG order
dbt source freshnessNoNoFreshness queries on declared sources only

On every dbt seed, dbt typically truncates and reloads the seed table (adapter-dependent; Snowflake uses a full replace). That is acceptable for 273 rows and unacceptable for a million-row CSV — another reason seeds stay small.

dbt ls — seeds in the project

dbt ls --resource-type seed
14:12:01  Running with dbt=1.11.12
airbnb.seeds.seed_full_moon_dates
Seeds are not incremental. There is no materialized='incremental' for seeds. Every seed run reloads the whole file. If your reference data changes daily at scale, it belongs in a source table loaded by Fivetran or a batch job, not in git as a CSV.

Explicit column types with seeds/schema.yml

When dbt infers types incorrectly — treating a ZIP code as a number, or a date as varchar — add a schema YAML next to your CSV. The course does not need this for seed_full_moon_dates because a single date column infers cleanly on Snowflake, but the pattern is worth knowing before your first production seed breaks a join:

seeds:
  - name: seed_full_moon_dates
    config:
      column_types:
        full_moon_date: date

Other useful seed config keys include quote_columns (whether to wrap column names in quotes — important on Postgres), delimiter for non-comma CSVs, and +schema to load into a dedicated reference schema instead of your dev target schema. All of these can also live under seeds: in dbt_project.yml at the project or seed-name level.

Declaring sources in sources.yml

Sources tell dbt about tables your project reads but does not build. They live in YAML — typically models/sources.yml — and give you a stable logical name, documentation hooks, freshness checks, and source-level tests without hard-coding database.schema.table strings in every model.

Why not hard-code raw table names?

Early in the course, staging models used fully qualified names like AIRBNB.RAW.RAW_LISTINGS. That works until you need a second environment, rename a table, or want freshness checks. Sources centralise the physical mapping in one file; models call {{ source('airbnb', 'listings') }} and dbt resolves the rest at compile time based on your target.

The course declares one source package named airbnb pointing at the raw schema with three tables:

sources:
  - name: airbnb
    schema: raw
    tables:
      - name: listings
        identifier: raw_listings

      - name: hosts
        identifier: raw_hosts

      - name: reviews
        identifier: raw_reviews
        config:
          loaded_at_field: date
          freshness:
            warn_after: {count: 1, period: hour}
            error_after: {count: 24, period: hour}

Breaking down the structure:

  • name: airbnb — the first argument to source(). A label for this group of raw tables, not necessarily the database name.
  • schema: raw — the warehouse schema (Snowflake) or dataset prefix where the physical tables live. Combined with your profile's database, this resolves to AIRBNB.RAW.
  • tables: — one entry per raw table this project reads. Each gets a logical name used in source('airbnb', 'listings').
  • identifier: — optional. When the physical table name differs from the logical name, identifier holds the real table name in the warehouse.

Later sections add column-level tests to this file — dbt_expectations checks on room_type and price appear in the finished repo. Those tests run against the source, not a model, which is why sources.yml is the right home for them. See Section 11 for the full testing story.

Where sources.yml lives

dbt discovers YAML anywhere under model-paths. The course uses models/sources.yml at the top level; some teams use models/staging/_sources.yml or split by domain (_sources__airbnb.yml). Filename does not matter to dbt — only that the file is under a configured path and parses as valid YAML.

Multiple YAML files merge. You can split sources across files — _sources__airbnb.yml, _sources__stripe.yml — and dbt merges them at parse time. Conflicting table names under the same source name are a parse error; duplicate source names with different schemas need careful naming.

source() versus ref()

ref() points at something dbt builds — a model, a seed, a snapshot. source() points at something dbt only documents and tests — a table your loader owns. Mixing them up breaks lineage semantics and freshness monitoring.

Everything downstream still uses ref(). dim_listings_cleansed calls ref('src_listings'); fct_reviews calls ref('src_reviews'). The rule is simple: source() appears at the boundary where dbt's responsibility ends and the loader's begins; ref() everywhere inside the project DAG.

Never ref() a raw table. If you write {{ ref('raw_listings') }} for a table dbt does not build, compilation fails. If you hard-code RAW.RAW_LISTINGS instead, it compiles — and silently removes the table from source freshness, source tests, and the sources layer of the lineage graph.

Compiled resolution

At compile time on the course Snowflake target, {{ source('airbnb', 'listings') }} becomes something like AIRBNB.RAW.RAW_LISTINGS. Open target/compiled/airbnb/models/src/src_listings.sql after dbt compile to verify. The exact database depends on your profile; the logical names stay stable across environments.

Everyday analogy — source() is the address book entry for a supplier warehouse you never own but receive shipments from. ref() is the internal recipe card for something your kitchen actually cooks. You do not list the supplier's shelf as one of your recipes.

The identifier escape hatch

Logical source table names should read well in models — short, domain-friendly, consistent. Physical raw tables often have ugly prefixes like raw_ from the loader. The identifier property bridges the gap without renaming tables in the warehouse.

When logical name equals physical name

If you omit identifier, dbt assumes the physical table name matches the logical name. For a table declared as name: orders in schema raw, dbt looks for raw.orders.

When they differ

The Airbnb loader created raw_listings, raw_hosts, and raw_reviews. In models you want to write source('airbnb', 'listings') — cleaner than repeating raw_listings in every file. The YAML maps them:

Logical name (in source())identifier (physical table)Full Snowflake path (course)
listingsraw_listingsAIRBNB.RAW.RAW_LISTINGS
hostsraw_hostsAIRBNB.RAW.RAW_HOSTS
reviewsraw_reviewsAIRBNB.RAW.RAW_REVIEWS

You can also override database and schema per table if a source spans databases — uncommon in the course project but typical when one dbt project reads from both a landing zone and a curated raw layer in enterprise setups.

Naming convention: keep logical names stable across renames of physical tables. When the platform team renames raw_listings to lz_airbnb_listings, you update one line in sources.yml, not forty models.

Identifier and snapshots

Snapshots in Section 10 reference sources directly: relation: source('airbnb', 'listings'). The identifier mapping applies there too — dbt resolves to the physical table before building the snapshot SQL.

Source freshness

Freshness checks answer one question: is the raw data recent enough to trust? dbt compares the maximum value of a timestamp column in the source table against the current time and raises a warning or error when data is stale.

Configuration on the reviews source

Only the reviews table carries freshness config in the course — it is the largest, append-only table with a clear event timestamp. The raw column is date (review submission date); dbt needs to know which column to inspect:

      - name: reviews
        identifier: raw_reviews
        config:
          loaded_at_field: date
          freshness:
            warn_after: {count: 1, period: hour}
            error_after: {count: 24, period: hour}
  • loaded_at_field — column holding when the row was loaded or when the event occurred. Here it is date from the raw reviews export. In production you often prefer a true load timestamp from your ELT tool (_fivetran_synced, _airbyte_extracted_at) if the event date can lag behind ingestion.
  • warn_after — emit a warning (exit code still 0 by default in older behaviour; check your dbt version) when the max loaded_at_field is older than one hour.
  • error_after — fail the freshness invocation when data is older than twenty-four hours. Pipelines wired to CI treat a non-zero exit code as a blocker.

The finished repo may have error_after commented out during local development so stale sample data does not block builds. Uncomment it before wiring freshness into production orchestration.

What dbt actually queries

For each configured source, dbt runs a query equivalent to:

SELECT MAX(date) AS max_loaded_at
FROM AIRBNB.RAW.RAW_REVIEWS

It then compares max_loaded_at to the warehouse's current timestamp. If the gap exceeds error_after, the source is error; if it exceeds only warn_after, it is warn; otherwise pass.

StatusMeaningTypical pipeline action
passMax timestamp within both thresholdsContinue to dbt build
warnOlder than warn_after but not error_afterAlert on-call; may still run transforms
errorOlder than error_afterStop downstream jobs; page the data platform team
runtime errorQuery failed (missing column, no permissions)Fix config or grants before trusting any freshness result
loaded_at_field must exist and be a timestamp-like type. Pointing freshness at a varchar date column usually works on Snowflake if values cast cleanly, but a typo in the column name produces a runtime error, not a stale warning. Verify with a direct SELECT MAX(date) in a worksheet first.

Freshness versus data quality tests

Freshness is operational metadata — is the pipe flowing? Column tests in sources.yml (added later in the course) are data quality — are the values plausible? Run freshness before expensive model builds; run source tests as part of dbt build or CI.

Later in the course you will run source tests with selectors like dbt test --select source:airbnb.listings (Section 11). That command scans the raw table for test failures; it does not check staleness. Freshness and tests complement each other but use different commands and answer different questions.

Check typeCommandQuestion answered
Freshnessdbt source freshnessWhen was the newest row loaded?
Source data testdbt test --select source:airbnb.listingsDo column values meet expectations?
Model testdbt test --select src_listingsDid our transform preserve quality?
Build (all of the above for selected nodes)dbt build --select +mart_fullmoon_reviewsSeed, run, and test in DAG order

Period units for warn_after and error_after

Both thresholds accept a count and a period. Valid periods are minute, hour, and day. The course uses one hour for warn and twenty-four hours for error on reviews — aggressive for a demo dataset, reasonable for a live feed that should update hourly. A nightly batch loader might instead use warn_after: {count: 26, period: hour} and error_after: {count: 48, period: hour} to tolerate a missed run without paging on-call every morning.

You can set freshness at the source level (applies to all tables that do not override) or per table under config:, as the course does for reviews only. Listings and hosts have no freshness block because the course treats them as slowly changing dimension sources where staleness is less critical than reviews volume.

Exit codes for orchestration

Orchestrators (Airflow, Dagster, cron, GitHub Actions) rely on exit codes to decide whether to continue. After running freshness, inspect the shell exit code:

ShellCommand to read last exit code
Mac / Linux (bash, zsh)echo $?
Windows Command Promptecho %ERRORLEVEL% (run a failing command first to see a non-zero example)

The course demonstrates exit codes with a deliberate failure:

dbt source freshness
echo $?
dbt source freshness

In PowerShell, $? tells you whether the last command succeeded as a boolean — it does not replace $LASTEXITCODE for numeric exit codes your orchestrator expects.

The course script demonstrates exit codes with a deliberately failing command first so you see a non-zero value. On Windows Command Prompt:

dir C:\nonexistent
echo %ERRORLEVEL%

After dbt source freshness returns ERROR for stale data, echo %ERRORLEVEL% in cmd or $LASTEXITCODE in PowerShell should be non-zero. Wire your CI step to fail when that happens:

dbt source freshness --select source:airbnb.reviews
if ($LASTEXITCODE -ne 0) {
  Write-Error "Source freshness failed — aborting build"
  exit $LASTEXITCODE
}

Freshness results artifact

dbt writes freshness results to target/sources.json (path may vary slightly by version). Orchestrators can parse the max loaded timestamp and status per source for dashboards. When debugging, open that file after a run to see the exact timestamp dbt compared against your thresholds without re-querying the warehouse.

Certification: know that dbt source freshness is separate from dbt test, that freshness requires loaded_at_field, and that warn_after / error_after accept a count and period (minute, hour, day).

mart_fullmoon_reviews: joining seed and facts

The mart combines the incremental fact table with the full-moon seed to label each review as occurring on the night after a full moon or not. It is the first model in the course that joins a seed to a fact — a pattern you will reuse whenever reference data enriches events.

The model as built in this section

At this point in the course, the mart is a full table rebuild:

{{ config(
  materialized = 'table',
) }}

WITH fct_reviews AS (
    SELECT * FROM {{ ref('fct_reviews') }}
),
full_moon_dates AS (
    SELECT * FROM {{ ref('seed_full_moon_dates') }}
)

SELECT
  r.*,
  CASE
    WHEN fm.full_moon_date IS NULL THEN 'not full moon'
    ELSE 'full moon'
  END AS is_full_moon
FROM
  fct_reviews
  r
  LEFT JOIN full_moon_dates
  fm
  ON (TO_DATE(r.review_date) = DATEADD(DAY, 1, fm.full_moon_date))

The join logic

The instructor's hypothesis: guests leave worse reviews the night after a full moon. The join matches a review to a seed row when the review date equals the day after the full moon:

  • fm.full_moon_date — the astronomical full moon (from the seed).
  • DATEADD(DAY, 1, fm.full_moon_date) — the calendar day after.
  • TO_DATE(r.review_date) — normalises the fact timestamp for comparison.

A LEFT JOIN keeps every review. When no seed row matches, fm.full_moon_date IS NULL and the CASE returns 'not full moon'.

Sanity-checking the mart

After the first successful build, run a grouped count to confirm both labels appear and the full-moon bucket is not empty:

SELECT
  is_full_moon,
  COUNT(*) AS review_count
FROM mart_fullmoon_reviews
GROUP BY 1
ORDER BY 1;

Spot-check a known full moon: pick a date from the seed, add one day, and confirm reviews on that calendar day show 'full moon':

SELECT *
FROM mart_fullmoon_reviews
WHERE TO_DATE(review_date) = '2009-06-08'
LIMIT 10;

The mart depends on both upstream nodes. If you run dbt run --select mart_fullmoon_reviews without seeding first, you get a relation-not-found error on the seed. If fct_reviews is empty, the mart builds successfully but returns zero rows — a reminder that dbt run does not load seeds automatically.

Production evolution (forward link)

By Section 19 (Production), this mart becomes a microbatch incremental model in a dedicated mart schema — matching the fact's event_time so each batch rebuilds only one year of reviews instead of the full history. The join logic stays identical; only the config() block changes:

{{ config(
  materialized = 'incremental',
  incremental_strategy='microbatch',
  event_time='review_date',
  begin='2009-06-20',
  batch_size='year',
  full_refresh=false,
  tags = ['fact'],
  schema='mart'
) }}

WITH fct_reviews AS (
    SELECT * FROM {{ ref('fct_reviews') }}
),
full_moon_dates AS (
    SELECT * FROM {{ ref('seed_full_moon_dates') }}
)

SELECT
  r.*,
  CASE
    WHEN fm.full_moon_date IS NULL THEN 'not full moon'
    ELSE 'full moon'
  END AS is_full_moon
FROM
  fct_reviews
  r
  LEFT JOIN full_moon_dates
  fm
  ON (TO_DATE(r.review_date) = DATEADD(DAY, 1, fm.full_moon_date))

Traps that catch people

  • Forgetting dbt seed before dbt run — models calling ref('seed_full_moon_dates') fail with a relation-not-found error. Add seed to CI before models, or use dbt build which runs seeds first.
  • Hard-coding raw tables after adding sources.yml — some models still use AIRBNB.RAW.RAW_LISTINGS while others use source(). Freshness and source tests skip the hard-coded paths entirely.
  • Wrong loaded_at_field — using the event date when loads batch weekly makes freshness look stale every weekend even though the pipe is healthy. Prefer a true ingestion timestamp when your loader provides one.
  • Identifier typo — identifier: raw_listing (missing s) compiles but queries an empty or wrong table. Compare compiled SQL in target/compiled to a direct worksheet query.
  • source() in marts — reading raw tables deep in the DAG bypasses staging cleansed logic and breaks the layering convention. Sources belong in src_ models only.
  • Seeds with secrets — putting API keys or employee lists in CSV seeds commits them to git forever. Seeds are plain text in version control.
  • Case sensitivity on identifier — on Snowflake, unquoted identifiers fold to uppercase. A mixed-case physical table name may need quoting in YAML or the warehouse.
  • Freshness on static sample data — course sample reviews never update; error_after: 1 hour always fails in prod unless you disable it locally. Comment out or lengthen thresholds for dev.
  • Confusing ref and source in snapshots — snapshots must reference source() for raw mutable tables, not ref('src_listings'), if you want to snapshot the raw feed before staging transforms.
  • Renaming a seed CSV without updating refs — changing seed_full_moon_dates.csv to full_moon_dates.csv changes the relation name to full_moon_dates. Every ref('seed_full_moon_dates') breaks until you update SQL or add a alias: in seed config.
  • Assuming freshness runs during dbt run — a successful model run does not imply raw data is fresh. Freshness is opt-in via dbt source freshness or explicit orchestration steps.

Production patterns

Teams treat sources.yml as the contract with upstream data producers. Each source documents owner, SLA, and freshness thresholds. Orchestration runs dbt source freshness as a gate before dbt build — if reviews are stale, downstream marts do not run and BI keeps serving yesterday's build rather than silently partial data.

Seeds stay small: currency codes, fiscal calendars, marketing campaign mappings maintained by analysts in git. Anything larger moves to a managed table with a loader job and becomes a source. Multi-environment setups override schema: or database: per target in YAML so dev reads a sandbox raw schema while prod reads the real landing zone.

Pattern: freshness gate in CI

Nightly job: freshness → build → test. Freshness failure exits non-zero; Airflow/Dagster skips transform tasks. Alerts include max loaded timestamp and threshold breached.

Anti-pattern: giant seeds

Checking a 10 GB CSV into git and running dbt seed daily. Repo bloat, slow clones, full-table reloads. Use the loader instead.

sources:
  - name: airbnb
    schema: "{% raw %}{{ target.name }}_raw{% endraw %}"
    tables:
      - name: reviews
        identifier: raw_reviews

Interview questions

Answer each one out loud before opening it.

When would you use a seed instead of a source?Comparison

Use a seed when the data is small, version-controlled CSV reference data that dbt should load directly — holiday calendars, country codes, manual mappings like seed_full_moon_dates. The team owns the file in git and reloads it with dbt seed.

Use a source when an external system or ELT tool already loads the table into the warehouse — Fivetran landing raw_reviews, an API batch job, a shared landing zone. dbt declares and tests it but never builds it.

If the dataset grows beyond a few hundred thousand rows or updates on a schedule independent of your dbt deploys, migrate from seed to source plus loader.

What is the difference between source() and ref()?Fundamentals

ref() resolves to relations dbt materialises — models, seeds, snapshots. It encodes build order: dbt runs the referenced node first. It resolves schema per target so dev and prod stay isolated.

source() resolves to tables declared in YAML that dbt does not build. It enables freshness checks, source tests, and a dedicated sources layer in lineage. Use it at the staging boundary only.

Hard-coding a physical table name avoids both functions and breaks environment isolation, freshness, and DAG completeness.

What does the identifier property do in sources.yml?Modelling

It maps the logical table name used in source('airbnb', 'listings') to a different physical table name in the warehouse — here raw_listings. Models stay readable; renames of physical tables require a one-line YAML change.

Without identifier, dbt assumes the physical name equals the logical name. Use identifier whenever loaders impose prefixes like raw_, lz_, or stg_ on actual table names.

How does source freshness work?Fundamentals

dbt runs SELECT MAX(loaded_at_field) on the source table and compares the result to the current warehouse time. If the age exceeds warn_after or error_after (each a count + period), the source gets status warn or error.

It is operational monitoring — is data arriving? — not a row-level quality test. Configure on tables that receive regular loads and have a reliable timestamp column.

Your freshness check always warns in development. Why?Troubleshooting

Sample datasets often have a fixed max date from when the dump was created. If warn_after: 1 hour and the newest review is months old, every freshness run warns or errors even though nothing is wrong with your code.

Fixes: lengthen thresholds for dev, comment out error_after locally (as the course repo does), use target-specific YAML overrides, or refresh sample data. Production pipelines against live feeds should keep strict thresholds.

Why declare sources in YAML instead of hard-coding table names?Design

Centralised declaration gives you one place to change database/schema/table mappings per environment, attach documentation, run source-level tests, and configure freshness. Models stay environment-agnostic.

Hard-coded DATABASE.SCHEMA.TABLE strings compile but bypass the sources layer in lineage, skip freshness, and break when you clone prod data to a dev schema with a different name.

Can you run dbt test on a source?Testing

Yes. Column tests under a source table in sources.yml run against the raw relation before staging transforms. The course adds dbt_expectations tests on room_type and price in a later section.

Source tests catch upstream problems at the boundary. Staging tests catch your transform logic. Both belong in a mature project; neither replaces freshness for staleness detection.

What happens if you forget to run dbt seed before building a model that refs a seed?Gotcha

The model fails at runtime with a relation-not-found error because the seed table does not exist in the target schema. dbt build avoids this by running seeds first in DAG order; plain dbt run does not load seeds automatically.

CI pipelines should either use dbt build or explicitly run dbt seed before dbt run when seeds changed in the commit.

How would you check whether dbt source freshness failed in a PowerShell CI script?Production

Run dbt source freshness, then inspect $LASTEXITCODE. Non-zero means failure or error-level staleness depending on configuration. Do not rely on $? alone for numeric exit codes.

On bash agents use echo $? or set -e so the script stops before downstream steps. Wire alerts to the freshness JSON artifact in target/ for max loaded timestamps.

Why does mart_fullmoon_reviews join on review_date = full_moon_date + 1 day?SQL

The business question is whether reviews submitted the night after a full moon differ in sentiment. The seed stores the astronomical full moon date; adding one day shifts to the calendar day guests would have experienced the aftermath.

A LEFT JOIN preserves all reviews; unmatched rows become 'not full moon'. Getting the offset wrong by one day would mislabel the analysis — always validate edge dates against a known full moon in the seed.

Does dbt run load seeds automatically?Fundamentals

No. dbt run executes models only. Seeds load with dbt seed or as part of dbt build when seeds are in the selected subgraph. If a model references ref('seed_full_moon_dates') and the seed table does not exist, the run fails at query time.

CI should either run dbt build end-to-end or run dbt seed as an explicit prerequisite step whenever seed CSVs change in the commit.

How do you select a single source table for freshness or tests?Certification

Use the source:source_name.table_name selector syntax. Examples from the course project: dbt source freshness --select source:airbnb.reviews, dbt test --select source:airbnb.listings, dbt source freshness --select source:airbnb for all tables under the source that have freshness config.

This is parallel to model selectors (dbt run --select fct_reviews) but targets declared sources instead of built models. The wildcard source:* selects every source node in the project.

Recap

  • Seeds are CSV files in seeds/ that dbt loads into tables via dbt seed. Reference them with ref('seed_name').
  • seed_full_moon_dates.csv holds lunar calendar dates used to enrich reviews in the full-moon mart.
  • Sources declare raw warehouse tables in models/sources.yml — dbt documents and tests them but does not build them.
  • source('airbnb', 'listings') is for raw tables; ref('src_listings') is for dbt-built models and seeds.
  • identifier maps a friendly logical name to the physical table name (listings → raw_listings).
  • Source freshness compares MAX(loaded_at_field) to warn_after and error_after thresholds.
  • dbt source freshness runs those checks; use $LASTEXITCODE in PowerShell or echo $? on Mac/Linux for exit codes.
  • Staging models (src_*) should be the only models calling source().
  • mart_fullmoon_reviews LEFT JOINs fct_reviews to the seed on review_date = full_moon_date + 1 day.
  • The mart starts as a table in this section; production refactors it to microbatch incremental in Section 19.
  • dbt build runs seeds before models; plain dbt run does not.
  • Do not put large or frequently updated datasets in seeds — use sources and a loader instead.
