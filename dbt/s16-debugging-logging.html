Debugging and Logging

When something breaks in a dbt project, you need a repeatable workflow: run one test or one model in isolation, read the compiled SQL instead of guessing, add structured logging where Jinja is opaque, and use --empty and --sample to iterate without scanning full tables. This section adds dbt_expectations tests to the Airbnb project and teaches the tooling that turns cryptic errors into fixable problems.

dbt_expectations package tests

dbt_expectations brings Great Expectations-style data quality checks into dbt as generic tests. Instead of writing custom SQL for regex matches, quantile bounds, or row-count comparisons against another table, you declare them in YAML and let the package macros generate the test queries.

The original Great Expectations project is a Python library for validating datasets in notebooks and pipelines. The dbt port wraps similar logic as Jinja macros so tests run inside your normal dbt test workflow, appear in lineage, and respect selectors.

Pin the metaplane fork at 0.10.10. The course and repo use metaplane/dbt_expectations, not the deprecated calogica/dbt_expectations package. Install details and dbt deps workflow are in Section 13. After deps, tests are namespaced in YAML as dbt_expectations.expect_*.
packages:
  - package: dbt-labs/dbt_utils
    version: 1.3.3
  - package: metaplane/dbt_expectations
    version: 0.10.10 # Check https://github.com/metaplane/dbt-expectations/releases for the latest release

Source-level expectations

The instructor adds expectations directly on raw source columns in models/sources.yml. Source tests run against the loaded relation in the raw schema — before any model SQL transforms the data. That catches upstream feed problems at the boundary.

sources:
  - name: airbnb
    schema: raw
    tables:
      - name: listings
        identifier: raw_listings
        columns:
          - name: room_type
            data_tests:
              - dbt_expectations.expect_column_distinct_count_to_equal:
                  arguments:
                    value: 4
          - name: price
            data_tests:
              - dbt_expectations.expect_column_values_to_match_regex:
                  arguments:
                    regex: "^\\\\$[0-9][0-9\\\\.]+$"
      - name: hosts
        identifier: raw_hosts

      - name: reviews
        identifier: raw_reviews
        config:
          loaded_at_field: date
          freshness:
            warn_after: {count: 1, period: hour}
            # error_after: {count: 24, period: hour}

expect_column_distinct_count_to_equal scans the column and counts distinct values — a quick sanity check that the categorical domain has not changed (for example, Airbnb adding a fifth room type). expect_column_values_to_match_regex returns failing rows where the pattern does not match; the regex uses doubled backslashes because YAML and Jinja both consume escape characters.

Model-level expectations

On cleansed and mart models, expectations validate transforms preserved business rules: row counts match upstream, types cast correctly, and distribution bounds hold.

  - name: dim_listings_w_hosts
    data_tests:
      - dbt_expectations.expect_table_row_count_to_equal_other_table:
          arguments:
            compare_model: source('airbnb', 'listings')
    columns:
      - name: price
        data_tests:
          - dbt_expectations.expect_column_values_to_be_of_type:
              arguments:
                column_type: number
          - dbt_expectations.expect_column_quantile_values_to_be_between:
              arguments:
                quantile: .99
                min_value: 50
                max_value: 500
          - dbt_expectations.expect_column_max_to_be_between:
              arguments:
                max_value: 5000
              config:
                severity: warn

Use selectors during development (dbt test --select dim_listings_w_hosts) rather than running the entire project after every YAML edit. On BigQuery and Databricks the SQL pattern is similar; adapter-specific type names in expect_column_values_to_be_of_type may differ — check the package macro for your warehouse.

Compiled expectations SQL (what to look for)

Package tests are macros like your custom generics from Section 12. After dbt test, the compiled file contains plain SQL your warehouse runs. A row-count parity test compiles roughly to two counts compared:

WITH a AS (
    SELECT COUNT(*) AS n FROM DEV.dim_listings_w_hosts
),
b AS (
    SELECT COUNT(*) AS n FROM AIRBNB.RAW.RAW_LISTINGS
)
SELECT *
FROM a
CROSS JOIN b
WHERE a.n != b.n

A regex test on raw price returns rows that fail the pattern — each row is one violation dbt counts in the FAIL N summary:

SELECT *
FROM AIRBNB.RAW.RAW_LISTINGS
WHERE NOT REGEXP_LIKE(price, '^\\$[0-9][0-9\\.]+$')

Testing a single model or source

A full-project dbt test on a mature DAG can take minutes and scan terabytes. During development you almost always want one model or one source table. The same --select syntax from dbt run applies to tests.

One model and its column tests

dbt test --select dim_listings_w_hosts

This selects every test node attached to dim_listings_w_hosts in schema.yml — built-in generics, custom generics from Section 12, and dbt_expectations tests added in this section. It does not automatically build the model; the relation must already exist from a prior dbt run or dbt build.

One source table

dbt test --select source:airbnb.listings

The source:name.table selector syntax runs freshness checks (if configured) and every column test declared under that source table in sources.yml. Use this when debugging raw feed quality before touching model SQL.

Listing what will run

Before executing, confirm selection with dbt ls:

dbt ls --resource-type test --select dim_listings_w_hosts

Each line is a test node name. If the list is empty, your selector typo'd or the model has no tests declared. If the list is unexpectedly long, you used a broad fragment match.

Worked example: isolate one failing expectations test

Suppose the quantile test fails after a price cast change:

  1. Note the full test name from the FAIL line: expect_column_quantile_values_to_be_between_dim_listings_w_hosts_price__...
  2. Re-run only that node: dbt test -s expect_column_quantile_values_to_be_between_dim_listings_w_hosts
  3. Open compiled SQL; confirm the 99th percentile calculation uses the NUMBER column, not the old VARCHAR
  4. Run SELECT APPROX_PERCENTILE(price, 0.99) FROM DEV.dim_listings_w_hosts in a worksheet to see the actual value
  5. Adjust min_value/max_value in YAML if the business bound was wrong, or fix the model cast if the data is wrong

The --debug flag

--debug is a global flag that raises dbt's internal log level to DEBUG for the entire invocation. It belongs before the subcommand: dbt --debug test, not dbt test --debug (though dbt often accepts the latter via argparse forwarding).

dbt --debug test --select dim_listings_w_hosts

Prefer target/compiled over --debug. The course instructor starts with --debug, then switches to opening compiled SQL files because they are stable, searchable, and safe to paste into a PR. --debug floods the terminal and may print credentials-adjacent metadata. Use it when you need adapter-level detail; use target/compiled/ for test logic.

Everything logged at DEBUG also lands in logs/dbt.log regardless of whether you passed --debug on the CLI. The flag mainly controls what prints to stdout during the run.

When --debug helps vs hurts

  • Helps — adapter connection failures, obscure macro recursion errors, verifying which exact SQL dbt sent when the warehouse error message truncates the query.
  • Hurts — reading test failure logic (use compiled files), sharing output in Slack (too verbose, may leak config), CI logs (noise hides the actual FAIL line).

For compilation errors specifically, dbt compile --select model_name without --debug is usually enough; the error message points at file and line number in your project.

Reading logs/dbt.log after --debug

Even without --debug, dbt writes to logs/dbt.log continuously. After a failed run, search the log for ERROR, the test node name, or the model name. The log file includes timestamps and full SQL at DEBUG level when the global log level allows it.

  • airbnb/
    • target/
      • compiled/ Jinja rendered — preferred for test SQL
      • run/ Full DDL/DML executed
    • logs/
      • dbt.log --debug increases verbosity here and on stdout

In shared environments, rotate or truncate dbt.log periodically — it grows across sessions and may contain connection metadata you do not want in long-lived files.

Logging with log() and macros

dbt exposes a Jinja log() function for printf-style debugging inside macros and models. Messages always write to logs/dbt.log; passing info=True also prints them to the console during the run.

The learn_logging macro

The course adds a teaching macro in macros/logging.sql that demonstrates three logging behaviours and the difference between SQL comments and Jinja comments:

{% macro learn_logging() %}
    {{ log("Call your mom!") }}
    {{ log("Call your dad!", info=True) }} --> Logs to the screen, too
--  {{ log("Call your dad!", info=True) }} --> This will be put to the screen
    {# log("Call your dad!", info=True) #} --> This won't be executed
{% endmacro %}

The two comment styles behave very differently, and the macro is written to make that visible. A SQL line comment (--) is just text as far as Jinja is concerned: Jinja renders the line first and only then does the warehouse ignore it, so a {{ log(...) }} hidden behind -- still executes and still prints. A Jinja comment ({# ... #}) is removed at parse time, so the call inside it never runs at all. That is why line 4 still logs when you call the macro while line 5 does not.

The trailing --> is a SQL comment, not an arrow. Because -- opens a line comment, everything after it on that line is ignored by the warehouse. The course author uses it as an inline annotation. It is harmless here, but do not copy the habit into a model where the same line also carries SQL you actually need.

Running the macro

Macros that do not belong to a model run via dbt run-operation:

dbt run-operation

dbt run-operation learn_logging
16:22:01  Running with dbt=1.11.12
16:22:02  Call your dad!
16:22:02  Completed successfully

Only the info=True line appears on screen. Call your mom! went to logs/dbt.log at DEBUG level only. Open that file and search for Call your mom to confirm.

log() is not for secrets. Values you pass to log() are written in plain text to disk. Never log passwords, tokens, or PII. Use static labels like log("incremental branch: date filter", info=True) instead of dumping row contents.

Logging in models (fct_reviews pattern)

Section 13 adds logging inside the incremental model to show which branch ran. That is the production use case for log(..., info=True) — not the teaching macro, but real pipeline observability:

{% if is_incremental() %}
    {{ log("fct_reviews: incremental run — filtering on review_date", info=True) }}
    WHERE review_date > (SELECT MAX(review_date) FROM {{ this }})
{% else %}
    {{ log("fct_reviews: full refresh — no date filter", info=True) }}
{% endif %}

During a failed nightly incremental run, search the orchestrator log for that string before opening compiled SQL. If you see "full refresh" when you expected incremental, the model was rebuilt from scratch — check for accidental --full-refresh or a config change.

Debugging YAML, SQL and model errors

dbt failures fall into three buckets: YAML or project config parse errors (before compilation), Jinja compilation errors (macro/syntax in your SQL files), and warehouse execution errors (compiled SQL is valid but the database rejects it). Each bucket has a different first file to open.

Reading a compilation error

Compilation errors include the project file path and often the Jinja line. Example when a macro name is misspelled:

Compilation error

dbt run --select dim_listings_cleansed
16:30:04  Compilation Error in model dim_listings_cleansed (models/dim/dim_listings_cleansed.sql)
  'unknown_macro' is undefined. This can happen when calling a macro that does not exist.
  > in macro some_wrapper (macros/broken.sql)
  > called by model dim_listings_cleansed (models/dim/dim_listings_cleansed.sql)

Read from the bottom up: the model file called a macro; the macro file has the undefined reference. Fix macros/broken.sql, not the model. When the stack is deep, reproduce with dbt compile --select dim_listings_cleansed for a fast loop.

Common YAML indentation mistakes

YAML errors surface at parse time with a line number in the YAML file. Typical mistakes when adding dbt_expectations tests:

  • arguments: at wrong indent — must nest under the test name, not at column level sibling to data_tests:.
  • Tabs instead of spaces — YAML forbids tabs; some editors insert them silently.
  • Missing colon after test name — - dbt_expectations.expect_column_max_to_be_between needs a trailing colon before arguments:.
  • Regex backslashes under-escaped — JSON-style regex in YAML often needs \\\\ for one literal backslash in the compiled pattern.
  • config: sibling to arguments: — severity and tags belong under the test item, not under columns: root.
columns:
  - name: price
    arguments:          # WRONG — not a valid schema.yml key here
      max_value: 5000
    data_tests:
      - dbt_expectations.expect_column_max_to_be_between
columns:
  - name: price
    data_tests:
      - dbt_expectations.expect_column_max_to_be_between:
          arguments:
            max_value: 5000
          config:
            severity: warn

Workflow from Section 11, applied here to expectations failures:

  1. Run the failing test with a narrow selector.
  2. Find the compiled file under target/compiled/airbnb/models/schema.yml/ (search for expect_column and the model name).
  3. Copy SQL into a worksheet; run it directly against the warehouse.
  4. Inspect failing rows; trace back to model or source logic.
  5. Fix, dbt run --select upstream_model+, re-test.

Model SQL errors vs test errors

When dbt run fails with a warehouse error, open target/run/airbnb/models/<path>/<model>.sql for the exact statement Snowflake executed. The error line number refers to compiled SQL, not your model file — map back manually or diff against target/compiled.

Do not edit files under target/. They are regenerated every run. Fix the source .sql or .yml in your project; dbt overwrites target/ on the next compile.

YAML mistake: tests key renamed

On dbt 1.8+ the key is data_tests:, not tests:. A file copied from an old tutorial may parse but dbt ignores the block or errors depending on version flags:

columns:
  - name: listing_id
    tests:           # outdated on dbt 1.11
      - unique
columns:
  - name: listing_id
    data_tests:
      - unique
      - not_null

Finding compiled test files quickly

Generic test filenames are auto-generated and long. Use ripgrep from the project root instead of clicking through folders:

Get-ChildItem -Recurse target/compiled -Filter "*expect_column_max*"
# or: rg -l "expect_column_max" target/compiled/

On Unix shells: rg -l "quantile" target/compiled/airbnb/models/schema.yml/. The search term should be a unique fragment of the test node name from the terminal FAIL line.

Debugging a Database Error in dim_listings_w_hosts

When the warehouse rejects model SQL (not a test), the stack trace points at the model file but the line numbers refer to compiled SQL. Example: join to a versioned ref typo:

Runtime error

dbt run --select dim_listings_w_hosts
16:45:02  Database Error in model dim_listings_w_hosts (models/dim/dim_listings_w_hosts.sql)

Parse error anatomy (YAML)

When indentation is wrong, dbt fails before any model compiles. The message names the file and often the line where the parser lost track of nesting:

dbt parse — YAML error

dbt parse
16:48:01  Parsing Error
  Invalid models.config.test entry in models/schema.yml:
  at path: ['columns', 0, 'data_tests', 0]:
  'arguments' is not a valid property
  Raw Error:
  while parsing a block mapping in "models/schema.yml", line 94, column 11

The at path: line is the fastest fix hint — it tells you which YAML key dbt did not expect at that depth. Compare the failing block character-for-character with a working test from the same file. Online YAML validators help for bracket matching, but dbt's own error path is usually enough.

Compilation error anatomy (Jinja in SQL)

When YAML parses but Jinja fails, the error cites the model file and the undefined symbol:

dbt compile — undefined ref

dbt compile --select dim_listings_w_hosts
16:49:12  Compilation Error in model dim_listings_w_hosts (models/dim/dim_listings_w_hosts.sql)
  Model 'dim_listings_w_hosts' depends on a node named 'dim_hosts_cleansed' which was not found

This usually means the upstream model was renamed, excluded by a selector, or lives in a disabled package path — not that the SQL syntax is wrong. Run dbt ls --select +dim_listings_w_hosts to see whether the parent node exists in the current graph. For package tests, a similar message appears when dbt deps was skipped and the macro namespace is missing entirely.

Fast compile loop. Keep a second terminal on dbt compile --select model_name while editing. Compilation is free on the warehouse and catches most Jinja and YAML reference errors before you pay for a full run.

--empty and --sample for fast iteration

Running the full DAG against production-sized tables on every save is slow and expensive. dbt 1.8+ adds flags to build models with zero rows or a time-bounded sample so you can validate SQL shape and compilation quickly in dev.

--empty

dbt run --empty executes models but replaces the body with a query that returns no rows while preserving the column schema. The warehouse still creates or replaces the relation — useful for checking DDL, grants, and hooks without scanning data.

dbt run --empty
# Verify in worksheet: SELECT COUNT(*) FROM AIRBNB.DEV.DIM_LISTINGS_W_HOSTS;

Expect COUNT(*) = 0 for every model built. Downstream tests that require row counts will fail — run without --empty before testing data quality.

--sample and event_time

--sample filters models that declare an event_time column in config. The course adds it to dim_listings_cleansed:

{{
  config(
    materialized = 'view',
    event_time='created_at'
  )
}} 
WITH src_listings AS (

--empty on a single model

You can combine --empty with selectors — you do not have to empty the entire project:

Global flags and behaviour changes

Beyond --debug, --empty, and --sample, dbt exposes global flags in dbt_project.yml under a top-level flags: key and via environment variables. They toggle behaviour changes between major versions without breaking existing projects immediately.

Reference docs:

  • Supported global configs
  • Managing behaviour changes with flags

When upgrading dbt Core (the course pins 1.11.x), read the behaviour-change flags for your version before a blanket upgrade. A flag might switch default test severity, YAML validation strictness, or how microbatch incremental models schedule batches — topics touched in Section 8 and Section 19.

flags in dbt_project.yml vs CLI. Project-level flags apply to every invocation in that directory. CLI flags like --empty are per-command overrides. Do not confuse them with model config() blocks — those are node-level.

Flags relevant to debugging

Debugging "it worked last month" often starts with a flag that changed default YAML validation or test severity.

dbt debug vs dbt --debug

Do not confuse dbt debug (connection and configuration sanity check) with dbt --debug <subcommand> (verbose logging for that run). Run dbt debug once when setting up a machine or after rotating credentials. Run dbt --debug test when a specific invocation fails and you need adapter-level detail. Section 6 covers dbt debug output in the setup context.

Traps that catch people

  • Testing before building — tests query the warehouse relation. Fresh dev schema + dbt test yields "relation does not exist". Run dbt build --select +model first.
  • Expectations on empty sample — --sample "3 days" with stale created_at builds zero-row tables; quantile tests may pass vacuously or fail oddly. Know your data timeline.
  • Wrong expectations fork — calogica/dbt_expectations from old tutorials breaks on dbt 1.11. Pin metaplane 0.10.10 per Section 13.
  • Regex escaping in YAML — under-escaped \\ causes tests that never match or match everything. Copy patterns from working project files.
  • --debug before subcommand — dbt test --debug often works but the documented form is dbt --debug test. In scripts, use the global form consistently.
  • Editing target/compiled — changes disappear on next run and never fix the source. Always edit project files.
  • log() with info=True in hot macros — a macro called per row or per column floods CI. Log once per model execution.
  • Assuming DEBUG logs appear on screen — only info=True prints by default. Read logs/dbt.log for debug-level messages.
  • source: selector typo — source:airbnb.listing (missing s) selects nothing silently with an empty success message from dbt ls.
  • event_time without sample support — models without event_time config ignore --sample and run full data — surprise bill.
  • WARN treated as green CI — expect_column_max_to_be_between with warn severity exits 0; monitor warnings explicitly in orchestration.
  • Compiled test file hunt — generic test filenames are extremely long. Grep target/compiled for the column name instead of browsing manually.

Production patterns

Mature teams treat debugging as artifact-first: every failed CI job attaches the compiled test SQL from target/compiled (or uses store_failures from Section 11) rather than re-running with --debug. Logging uses info=True sparingly at model boundaries — incremental watermark, batch ID, rows affected — and ships logs to the orchestrator's sink (Airflow/Dagster task logs in Section 18).

Expectations tests split into tiers: cheap built-ins on every PR, expensive distribution and parity tests nightly. Source regex tests run on ingestion completion; mart quantile tests run after full build.

Pattern: artifact-driven debug

CI uploads target/compiled and logs/dbt.log as job artifacts on failure. Engineers reproduce by copying one SELECT, not replaying the whole DAG with debug logging.

Anti-pattern: permanent --debug in CI

Log volume explodes, secrets risk increases, and the signal-to-noise ratio hides the one FAIL line that matters. Use structured log(..., info=True) at known points instead.

{% macro log_context(model_name) %}
  {% if execute %}
    {{ log("model=" ~ model_name ~ " target=" ~ target.schema, info=True) }}
  {% endif %}
{% endmacro %}

store_failures and expectations together

When an expectations test fails with FAIL 47, you only know the count from the terminal. Enable store_failures: true in project or test config (Section 11) to persist those rows to a side table in the warehouse. Query that table instead of re-running the quantile scan during investigation.

      - dbt_expectations.expect_column_values_to_match_regex:
          arguments:
            regex: "^\\\\$[0-9][0-9\\\\.]+$"
          config:
            store_failures: true

Failure tables land in a schema derived from your target — typically <target_schema>_dbt_test__audit on Snowflake. The table name encodes the test node. Drop failure tables after triage or they accumulate across runs.

Interview questions

Answer each one out loud before opening it.

How do you debug a failing dbt test without re-running the entire project?Troubleshooting

Run the test in isolation with dbt test --select model_name or a fragment of the test node name. Open the compiled SQL under target/compiled/<project>/models/schema.yml/, copy it into a warehouse worksheet, and execute it to see failing rows.

If the relation is missing, build upstream first with dbt build --select +model_name. Avoid --debug unless you need adapter connection detail — compiled SQL is faster to read for test logic.

What is the difference between target/compiled and target/run?Fundamentals

target/compiled holds SQL after Jinja rendering — the SELECT body for models and the full SELECT for tests. It is what you read to debug logic.

target/run holds the statement dbt actually executed, including CREATE VIEW/TABLE wrappers, merge logic for incremental models, and sample/empty modifiers. Use it when the warehouse error references DDL or when verifying what --sample injected.

What does dbt --debug add to a test run?Troubleshooting

It sets internal logging to DEBUG for the whole invocation. You see adapter connection details, macro expansion steps, and full SQL strings in the terminal and in logs/dbt.log.

It does not change test logic or warehouse cost materially. For test failures, compiled files are usually clearer than scrolling debug output. Use --debug for connection issues or when the warehouse truncates error messages.

How does log() behave with and without info=True?Jinja

log("message") writes at DEBUG level to logs/dbt.log only — nothing on stdout during a normal run.

log("message", info=True) also prints to the console at INFO level, which is why learn_logging shows "Call your dad!" but not "Call your mom!" when run via dbt run-operation.

Why pin metaplane/dbt_expectations instead of calogica?Gotcha

The original calogica package lagged behind dbt Core releases and is unmaintained. Metaplane maintains a fork compatible with modern dbt; the course pins version 0.10.10 in packages.yml.

Installing the wrong package name yields missing macros at parse time or tests that fail to compile. Always run dbt deps after changing packages.yml.

When would you use dbt run --empty versus --sample?Comparison

--empty builds relations with zero rows but correct schema — ideal for validating DDL, hooks, and grants without scanning data. Data tests that need rows will fail.

--sample "N days" requires event_time config and filters to a recent window — ideal for debugging transform logic cheaply when recent data exists. The course dataset may yield empty samples because dates are historical.

How do you test only the raw listings source?Testing

dbt test --select source:airbnb.listings runs freshness (if configured) and all column tests under that source table in sources.yml, including dbt_expectations regex and distinct-count tests.

Preview with dbt ls --resource-type test --select source:airbnb.listings. The selector uses logical source and table names from YAML, not warehouse identifiers like raw_listings.

What causes a dbt_expectations regex test to fail every row?Testing

Usually incorrect escaping in YAML — the pattern that reaches Snowflake is not the pattern you intended. The course uses "^\\\\$[0-9][0-9\\\\.]+$" for dollar-prefixed prices.

Debug by opening the compiled test SQL, inspecting the literal regex applied in the WHERE clause, and testing that regex against sample values in a worksheet. Also confirm you are testing the right column (price on raw listings is still a string).

Why might expect_table_row_count_to_equal_other_table fail after a model change?Modelling

The model query now filters, deduplicates, or joins in a way that changes row count versus the raw source — for example an INNER JOIN to hosts dropping listings without matching hosts, or a WHERE clause excluding inactive listings.

Compiled SQL for both sides shows the counting logic. Decide whether the mismatch is a bug (unintended drop) or the test is wrong (mart should not match raw 1:1). Update the test or fix the model accordingly.

How do you run a macro purely for logging demonstration?Jinja

dbt run-operation learn_logging executes the macro without building models. Macros in macros/logging.sql must be discovered via dbt parse and live under configured macro paths.

This is the same mechanism used for operational macros like grant runners and cleanup jobs — run-operation is the entry point for side-effect-only Jinja.

Your CI passes but local dbt test fails on the same commit — what do you check first?Troubleshooting

Compare targets: schema name, warehouse size, and whether CI ran --empty or slim selectors while you ran full tests locally. Different row counts between dev and CI schemas cause expectations parity tests to diverge.

Check dbt debug for connection differences, confirm both environments ran dbt run on parents before test, and diff compiled SQL from each target's target/compiled if schemas differ.

What does FAIL 0 versus ERROR mean on a test node?Testing

FAIL N means the test query ran and returned N violating rows. ERROR means the test query never completed — missing relation, syntax error, permission denied, or timeout.

For ERROR, open logs/dbt.log for the warehouse message and target/compiled for the SQL. For FAIL N, open compiled SQL and run it — the rows returned are your violations.

Recap

  • dbt_expectations (metaplane 0.10.10) adds Great Expectations-style generic tests — install via Section 13 packages.yml.
  • Source tests live in sources.yml; model tests in schema.yml — both use the dbt_expectations.expect_* namespace.
  • dbt test --select dim_listings_w_hosts runs only that model's tests; source:airbnb.listings runs source tests.
  • dbt --debug test floods DEBUG output — prefer target/compiled/ for reading test SQL.
  • log() writes to logs/dbt.log; info=True also prints to the console.
  • dbt run-operation learn_logging executes a macro without building models.
  • Compilation errors stack from model to macro — read bottom-up and fix the deepest file first.
  • YAML test arguments nest under the test name inside arguments:, not at column root.
  • target/compiled = Jinja-resolved SQL; target/run = full executed statement including DDL.
  • dbt run --empty builds zero-row relations for schema validation.
  • dbt run --sample "N days" needs event_time config — may return empty on historical course data.
  • Expensive expectations tests belong in nightly or slim CI, not every PR.
