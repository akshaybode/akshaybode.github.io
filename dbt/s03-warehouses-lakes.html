What a data warehouse is

A data warehouse is a central store optimised for analytical queries over integrated, historical data. It is not where your application writes orders in real time; it is where analysts and downstream pipelines read a consistent picture of the business after extract and load have finished.

Bill Inmon's definition still holds: a warehouse is subject-oriented (organised around business concepts like customers or listings rather than application screens), integrated (one agreed definition per entity, even when ten source systems disagree), time-variant (history is preserved or reconstructable), and non-volatile (data arrives on a schedule; you do not delete a row because someone cancelled an order in the app). Those four properties are what separate a warehouse from a copy of production tables dumped into a folder.

Inmon versus Kimball

Inmon advocates a normalized enterprise data warehouse first: third-normal-form entities shared across the company, with departmental data marts built on top. The benefit is a single source of truth at the entity level; the cost is a long upfront modelling effort and many joins at query time unless you add marts anyway.

Kimball starts from dimensional modelling: star schemas with conformed dimensions that different fact tables reuse. You ship business-facing marts faster because each mart is a wide, denormalized table tuned for a subject area. The course's Airbnb project is Kimball-flavoured — dim_listings_cleansed, dim_hosts_cleansed, fct_reviews — even though dbt does not force either methodology. Section 5 goes deep on the dimensional side.

Cloud warehouse: separating storage and compute

On-premise warehouses like early Oracle or Teradata bundles tied storage and compute to the same hardware purchase. Cloud warehouses — Snowflake, BigQuery, Redshift Serverless, Databricks SQL — decouple them. Your data sits in managed object storage (or a storage layer you never resize by hand); you spin up compute clusters only when something needs to run.

That separation changed cost economics entirely. You no longer leave a massive server running overnight because the storage is attached to it. You suspend compute when idle, scale warehouse size up for a heavy dbt run, and scale down for a dashboard that only scans a mart. dbt fits this model because every model run is a burst of compute against data that already lives in storage.

Warehouse versus database versus schema

Snowflake naming trips up beginners because everyday English uses “database” and “warehouse” loosely. In Snowflake specifically:

  • Virtual warehouse — compute cluster (COMPUTE_WH). No data stored here.
  • Database — top-level container for schemas (AIRBNB).
  • Schema — namespace for tables and views (RAW, DEV).
  • Table — persisted rows (raw_listings).

When dbt compiles {{ source('airbnb', 'raw_listings') }} it resolves to a three-part name like AIRBNB.RAW.RAW_LISTINGS. The warehouse is chosen separately in profiles.yml and can change without moving data.

ETL versus ELT preview

Classic ETL transformed data before loading into the warehouse, often on a separate server with limited scale. ELT loads raw data first, then transforms inside the warehouse using its columnar engine. dbt is the T in ELT: it assumes raw tables already exist and pushes all transformation SQL to Snowflake. That only makes economic sense because warehouses separated storage from compute and made large scans affordable. Section 4 names the load tools that feed the raw layer.

OLTP versus OLAP

OLTP (online transaction processing) systems record business events one row at a time with strict consistency. OLAP (online analytical processing) systems scan and aggregate large histories to answer questions nobody asked when the row was written. Running heavy OLAP on an OLTP database is one of the most expensive mistakes in data engineering.

Why a GROUP BY on production Postgres hurts the app

Imagine pointing Metabase at the same Postgres instance that powers an Airbnb booking flow. A analyst runs:

SELECT
  room_type,
  AVG(minimum_nights),
  COUNT(*)
FROM listings
GROUP BY room_type;

On a row store, Postgres must read every column of every row even though only room_type and minimum_nights matter. The query holds buffers and CPU while bookings wait. Replication to a read replica still copies WAL traffic; heavy analytics on the replica can lag it minutes behind production. Locks and vacuum activity compound the pain.

The fix is architectural: replicate or export into a columnar warehouse, then point dbt and BI at that copy. The course's raw_listings table is exactly such a copy — loaded once from CSV via COPY INTO, never updated by a booking app.

OLTP on Postgres

Rows stored together. Index seek on id is instant. Full-table aggregation reads every byte of every row and competes with checkout traffic.

OLAP on Snowflake

Columns stored separately. The same GROUP BY reads two columns across micro-partitions, uses parallel workers, and never touches the app database.

Read replicas are not a warehouse

Teams sometimes promote a Postgres read replica as “the analytics database.” It removes load from the primary but keeps row-oriented storage, OLTP indexing, and vacuum maintenance. Heavy scans still hurt; you still lack columnar compression and warehouse-scale parallelism. A replica is a stopgap; a warehouse is the destination.

Do not point dbt at production OLTP. Even read-only credentials do not protect you from scan cost and lock contention. Load into the warehouse first; transform there.

Columnar storage

Analytical warehouses are fast because they store columns separately, compress aggressively, and skip data that cannot match your filter. Every dbt model is a SELECT; how much data that SELECT touches is the main lever on runtime and bill.

Row layout versus column layout

In a row store, one listing record sits contiguously: id, name, room_type, price, .... Fetching one row by primary key is cheap. Aggregating price across ten million listings reads ten million full rows.

In a column store, all price values sit together, then all room_type values, and so on. A query that needs three of forty columns reads roughly three fortieths of the bytes, before compression.

Compression and encoding

Columns compress well because adjacent values tend to repeat. Run-length encoding stores “Entire home/apt repeated 40,000 times” instead of 40,000 identical strings. Dictionary encoding maps low-cardinality strings to integer codes — every sentiment value in raw_reviews might become a one-byte code.

Predicate pushdown means the engine applies your WHERE review_date > '2024-01-01' while reading compressed column chunks, skipping whole chunks that fail min/max metadata.

Concrete scan example

Suppose raw_listings has forty columns totalling 2 KB per row and one million rows (~2 GB logical). A narrow projection:

SELECT
  room_type,
  minimum_nights,
  host_id
FROM AIRBNB.RAW.raw_listings;

On Snowflake, the query profile will show bytes scanned closer to 150 MB than 2 GB. Add a selective filter on created_at and partition pruning drops further chunks entirely.

Snowflake micro-partitions and clustering

Snowflake splits each table into immutable micro-partitions of roughly 50–500 MB of compressed data. Each micro-partition stores min/max metadata per column. A filter on listing_id or date lets the optimizer skip partitions that cannot contain matching values.

Clustering (automatic or explicit on a key like review_date) co-locates related rows in the same micro-partitions so pruning works better over time. The course dataset is small enough that clustering barely matters; on fct_reviews at production scale, clustering on the incremental watermark column is standard practice.

Why SELECT * is expensive

Beginners write SELECT * in staging models because it is fast to type. In a columnar warehouse it is an anti-pattern: dbt still generates plain SQL, and the warehouse charges for every column you read. A staging model with SELECT * from raw_reviews pulls comments — large text — even when downstream models only need ids and dates.

The course's src_listings lists columns explicitly for a reason. When you add a column to a raw table, you add it once in staging; you do not silently widen every downstream scan.

Wide ephemeral chains multiply scans. An ephemeral model inlines into every child. If the inlined CTE uses SELECT *, each downstream model pays for the full width again. Explicit column lists in staging pay off immediately.

Partition pruning on raw_reviews

Even without explicit partitioning, Snowflake pruning helps on date once tables grow. This pattern mirrors what you will use on the incremental fact:

SELECT
  listing_id,

FROM AIRBNB.RAW.raw_reviews

GROUP BY 1, 2;

Data lakes and schema-on-read

A data lake stores files in cheap object storage (S3, ADLS, GCS) and applies structure when someone reads them. That flexibility lowered the bar to landing data but created “data swamps” when nobody enforced quality at write time.

Object storage and open file formats

Lakes put blobs in buckets with horizontal scale and pennies-per-gigabyte pricing. Common formats:

  • Parquet — columnar, splittable, the de facto analytics format.
  • ORC — similar columnar design, common in Hive-era Hadoop stacks.
  • Avro — row-oriented with embedded schema, popular for Kafka landing zones.
  • JSON / CSV — human-readable, schema-light, expensive to query at scale.

The Airbnb CSVs in the course (s3://dbt-datasets/listings.csv and siblings) are loaded into Snowflake tables, not left as lake files. In a lake-first architecture the same files would land as Parquet under a prefix like s3://airbnb/raw/listings/ and be registered in a catalog.

Why lakes were attractive

Teams could dump everything first and model later. Data scientists could read the same S3 objects with Spark. Storage cost stayed low because object storage undercuts proprietary warehouse storage on paper. The downside arrived six months later: duplicate files, unknown schemas, no ACID guarantees, and queries that scanned entire buckets because nobody maintained partition columns.

Everyday analogy — schema-on-write is a library with a card catalogue: nothing gets shelved unless it matches a slot. Schema-on-read is a warehouse of unlabelled boxes: you can store anything, but finding a book means opening boxes until you get lucky.

Data swamp symptoms

A lake becomes a swamp when:

  • Multiple teams write to the same prefix with incompatible folder conventions.
  • Nobody owns deduplication — the same export lands daily with overlapping files.
  • Schema drift is discovered in a notebook, not at ingest.
  • PII sits in plain CSV because access control is only at the bucket level.

The course avoids this by loading typed tables in RAW immediately. dbt tests in Section 11 then guard the transformed layer.

Medallion architecture on a lake

Bronze — raw files exactly as landed (s3://airbnb/bronze/reviews/).
Silver — cleaned, typed, deduplicated Parquet (what src_reviews would be if it wrote files).
Gold — business marts (mart_fullmoon_reviews).

On Snowflake the same idea maps to schemas: RAW is bronze, dbt staging is silver logic, dimensions and facts are gold. The labels differ; the progression does not.

The lakehouse and open table formats

A lakehouse adds warehouse-like guarantees — ACID transactions, metadata, time travel, schema evolution — on top of cheap object storage through an open table format. It is the industry's attempt to stop choosing between flexible lakes and trustworthy warehouses.

Delta Lake, Iceberg and Hudi

Three open table formats dominate:

  • Delta Lake (Databricks) — transaction log in _delta_log; tight Spark integration.
  • Apache Iceberg — vendor-neutral manifest files; Snowflake external and managed Iceberg tables; engine support across Spark, Trino, Flink.
  • Apache Hudi — strong incremental upsert and change-data-capture patterns.

All three store data as Parquet (or similar) files plus a metadata layer that tracks which files belong to which snapshot.

What a table format actually is

A table format is not a new file type. It is a manifest over Parquet files: a snapshot id, schema version, partition statistics, and the list of file paths that constitute the table at a point in time. Queries read the manifest first, prune files, then scan Parquet column chunks — same columnar benefits as a native warehouse table, with storage on S3.

ACID means concurrent writers do not corrupt each other; time travel means you can SELECT yesterday's snapshot; schema evolution means adding a column does not require rewriting every historical file immediately.

Databricks and Snowflake Iceberg support

Databricks built the lakehouse narrative around Delta Lake and Unity Catalog for governance. Snowflake added Iceberg tables (managed and external) so the same Snowflake SQL and role model can sit over S3-stored Iceberg while still using virtual warehouses for compute. BigQuery has BigLake; Redshift supports external tables over open formats.

dbt has adapters for Snowflake, Databricks, BigQuery and others — you point profiles.yml at the platform and keep writing models. Platform choice moves to setup; the project structure stays familiar. Section 6 walks through Snowflake specifically.

Iceberg does not change dbt's role. dbt still compiles SELECT statements and wraps them in DDL. Whether the underlying relation is a native Snowflake table or an Iceberg table changes adapter configuration and a few materialization details, not the modelling workflow.

Time travel and snapshots

Lakehouse formats expose snapshot ids or timestamps for historical reads. Snowflake native tables offer Time Travel for up to 90 days (edition-dependent). dbt snapshots are different: they build explicit Type 2 history tables you control in SQL. All three answer “what did we know then?” at different layers — storage engine versus transformation project.

Lakehouse metadata layer over Parquet files

Query engine — Snowflake, Spark, Trino reads manifest first.
Table format — Iceberg / Delta manifest: schema, snapshots, file list.

dbt adapters across platforms

dbt Labs maintains adapters for the major warehouse and lakehouse targets. The course pins dbt-snowflake~=1.11.0. Switching to Databricks means dbt-databricks and a Unity Catalog host in profiles.yml; the project layout, ref() graph, and test syntax stay the same. That portability is why analytics engineering standardised on dbt rather than warehouse-specific stored procedures.

Choosing between the three

Warehouse, lake and lakehouse are not moral choices; they are trade-offs on governance, cost model, and who needs to query the data. Most teams learning dbt should start with a cloud warehouse and only add lake or lakehouse patterns when a concrete requirement forces them.

Honest advice for this bootcamp: Snowflake (or BigQuery if that is your job) plus dbt covers analytics engineering end to end. Lakes shine when you must retain semi-structured telemetry indefinitely or feed ML feature stores. Lakehouses bridge that gap when SQL governance and open storage must coexist. Do not build a lake because a vendor slide said so; build it when unstructured volume or multi-engine access makes warehouse storage uneconomical.

Snowflake specifics for this course

Virtual warehouses versus databases

A virtual warehouse is compute only — CPU and memory workers that execute queries. A database is storage plus namespace: schemas, tables, views. They scale independently. COMPUTE_WH runs your queries; AIRBNB holds your data. Suspending COMPUTE_WH stops billing for compute; storage in AIRBNB still accrues at the storage rate.

AIRBNB.RAW and AIRBNB.DEV schemas

AIRBNB.RAW contains the three landing tables loaded from S3. dbt declares them in sources.yml and never writes to RAW in the default course flow. AIRBNB.DEV is created empty for transformed objects; when you run dbt with target dev, models land in a personal schema (often DEV or DBT_<username> depending on macro configuration).

Warehouse sizing, auto-suspend and credits

COMPUTE_WH defaults to X-Small in the manual script. Scale up when queries queue or spill to remote storage; scale down for cost. Auto-suspend (commonly 60–300 seconds) stops the warehouse after idle time. Each resumed run bills a one-minute minimum on Snowflake. Credits map to warehouse size and run time; storage and cloud services are separate line items on the invoice.

Traps that catch people

  • Treating warehouse and database as the same thing — suspending compute does not delete data, but beginners sometimes recreate databases thinking they cleared a bill. Know which object is storage versus compute.
  • Running analytics on OLTP — read replicas are not warehouses. They inherit row-oriented layout and OLTP indexing assumptions.
  • SELECT * in staging — widens every downstream scan. Explicit columns in src_* models are a performance and cost habit, not pedantry.
  • Ignoring bytes scanned — Snowflake and BigQuery both expose this in query history. A model change that doubles scanned bytes doubles cost even if runtime looks similar due to cache.
  • Lake without catalog — files multiply; nobody knows the canonical path. Always pair object storage with a metastore or table format manifest.
  • Assuming Iceberg is free storage — open files on S3 are cheap; rewriting snapshots, vacuuming, and cross-cloud egress are not.
  • One warehouse size for everything — BI dashboards and dbt full refreshes have different peak needs. Some teams use separate warehouses and resource monitors.
  • Confusing Time Travel with dbt snapshots — Snowflake Time Travel is storage-level history for native tables; dbt snapshots are explicit SCD2 tables you model. They solve overlapping but not identical problems.
  • Default role mismatch — the dbt user defaults to TRANSFORM; connecting as ACCOUNTADMIN in worksheets bypasses the least-privilege pattern the course teaches.

Production patterns

Teams typically run dbt against a dedicated warehouse (or warehouse size) with auto-suspend and a resource monitor cap. BI tools get a separate, smaller warehouse so a rogue dashboard cannot queue a nightly dbt job. Storage stays in production databases; developers clone or build into isolated schemas rather than sharing one DEV namespace.

Pattern: split warehouses

COMPUTE_DBT for scheduled builds, COMPUTE_BI for dashboards. Resource monitors cap each independently.

Anti-pattern: shared admin

Everyone connects as ACCOUNTADMIN on one always-on Large warehouse. Costs spike and grants become untraceable.

The anti-pattern worth naming at scale: giving every analyst direct write access to RAW “for convenience.” Raw layers should be append-only with pipeline-owned loads; dbt and analysts work downstream where tests apply.

Interview questions

Answer each one out loud before opening it.

What is a data warehouse, in one sentence and four properties?Fundamentals

A centralized analytical store integrated from many sources, optimized for read-heavy aggregations rather than transactional writes. Inmon's four properties: subject-oriented, integrated, time-variant, non-volatile.

Subject-oriented means organised by business entity (listings, hosts), not by source application screen. Integrated means one definition of host id across feeds. Time-variant means history matters. Non-volatile means loads are append-oriented; you do not mirror every OLTP delete unless you design for it.

Explain the difference between OLTP and OLAP with a concrete example.Comparison

OLTP handles many short read/write transactions on current state — booking a listing, updating a password. OLAP scans historical data to compute aggregates — average review sentiment by room type last quarter.

Running the OLAP query on the OLTP database contends for I/O and CPU with checkout traffic. The warehouse copy (raw_reviews in Snowflake) exists precisely to isolate that workload.

Why is columnar storage faster for analytics?Performance

Queries typically touch few columns across many rows. Column stores read only those columns, compress them better because values repeat, and skip micro-partitions using min/max metadata (predicate pushdown and partition pruning).

Row stores win on point lookups; column stores win on scans and aggregations — the shape of almost every dbt model and BI query.

What is schema-on-read versus schema-on-write?Fundamentals

Schema-on-write enforces structure when data lands (Snowflake COPY INTO with a typed table). Schema-on-read applies structure at query time (reading JSON from S3 with inferred types).

Write-time enforcement fails bad data early at the pipeline; read-time enforcement is flexible but pushes quality failures to consumers, which is how data swamps form.

What is a lakehouse and how does it differ from a data lake?Design

A data lake is files in object storage with loose governance. A lakehouse adds a table format layer (Delta, Iceberg, Hudi) with ACID transactions, snapshots, and schema evolution over those files.

You keep cheap storage and open formats while gaining warehouse-like reliability for SQL engines and catalogs.

When would you choose a warehouse over a lakehouse?Design

When the team primarily needs governed SQL analytics, BI, and dbt transformations on structured data without multi-engine Spark requirements. Cloud warehouses deliver that with less operational surface area.

Choose lakehouse when you must store massive semi-structured data, share files across Spark and SQL, or enforce open storage with catalog-level governance. Many orgs use both: lake for raw landing, warehouse or managed Iceberg for curated marts.

Why is SELECT * a bad habit in Snowflake and dbt staging models?Cost

Columnar billing and I/O scale with columns read. SELECT * pulls large text columns like comments even when downstream models never use them, and ephemeral models inline that width into every child.

Explicit projections in staging document the contract and keep scans narrow through the DAG.

What is the difference between a Snowflake virtual warehouse and a database?Fundamentals

A virtual warehouse is compute: workers that execute queries and bill credits while running. A database is a namespace for schemas and tables where data persists regardless of warehouse state.

Suspending COMPUTE_WH stops compute charges; tables in AIRBNB remain and continue to incur storage cost.

What does an open table format like Iceberg actually store?Architecture

Parquet (or similar) data files plus a metadata layer: manifest lists, snapshot ids, partition stats, schema versions. Queries consult metadata to prune files, then read column chunks from Parquet.

It is not a replacement for Parquet; it is governance and atomicity over Parquet files in a bucket.

Your Snowflake bill doubled but dbt run count is unchanged. Where do you look first?Troubleshooting

Query History sorted by total credits: look for bytes scanned spikes, new full-table scans, warehouses that stopped suspending, or BI tools hitting the same warehouse. Check warehouse size changes and whether result cache masked regression until data changed.

Compare Query Profile before and after for the top five expensive queries. dbt model changes that remove filters or widen joins are the usual culprit inside the transformation layer.

Recap

  • A data warehouse is a central, integrated, subject-oriented, time-variant, non-volatile store for analytics.
  • Inmon builds a normalized enterprise hub; Kimball builds conformed dimensional marts — the course follows Kimball-shaped models.
  • Cloud warehouses separate storage (database) from compute (virtual warehouse); that separation enables suspend/resume cost control.
  • OLTP is row-oriented transactional traffic; OLAP is scan-heavy aggregation. Never run OLAP on production OLTP.
  • Columnar storage, compression, predicate pushdown and partition pruning make analytical scans cheap.
  • SELECT * in dbt staging widens every downstream scan; list columns explicitly like src_listings does.
  • Data lakes store cheap files with schema-on-read flexibility; without governance they become swamps.
  • Lakehouses add ACID, time travel and catalogs over open files via Delta, Iceberg or Hudi.
  • For learning dbt, start with a cloud warehouse unless you have a concrete lake requirement.
  • This course uses Snowflake AIRBNB database, RAW landing schema, COMPUTE_WH, role TRANSFORM, user dbt.
  • Raw tables: raw_listings, raw_hosts, raw_reviews loaded from s3://dbt-datasets/.
  • dbt adapters exist for warehouse and lakehouse platforms; the modelling workflow stays the same.
