The exam in detail

The dbt Analytics Engineering Certification is an online, proctored, closed-book exam aligned to dbt Core 1.11. It tests whether you can build, test, document and deploy dbt models in a real warehouse — not whether you have memorised marketing copy.

Verify before you book. Question count, time limit, passing score, price and retake policy change. The figures below match the public study guide as of early 2026; confirm the current numbers on the dbt Labs certification page and download the latest Analytics Engineering Study Guide (v1.11) before paying for a voucher.

Developing and optimizing dbt models

The largest practical domain: writing models, choosing materializations, using sources and seeds, and selecting the right subgraph to build. Expect scenarios about ref(), incremental logic, folder defaults and Python models.

Key facts the exam tests

  • A dbt model is a SELECT only — dbt wraps it in DDL based on materialization.
  • ref('model_name') builds the DAG, resolves per target, and enables lineage. Hard-coded schema.table names break all three.
  • Default materialization is view when nothing else sets it.
  • Four materializations: view, table, incremental, ephemeral. Ephemeral creates no queryable relation; it inlines as a CTE.
  • is_incremental() returns false on first run and full refresh; returns true on subsequent incremental runs.
  • Config precedence (highest wins): model file {{ config() }} > model-specific YAML > folder YAML > project YAML > dbt default.
  • Selection grammar: +model (parents), model+ (children), @model (parents and children), tag:, path:, source:.
  • Python models run on Snowflake, BigQuery and Databricks — not Postgres or Redshift.
  • From dbt 1.12, named selectors use -s selector:name instead of --selector name.

Materialization comparison — exam rapid review

MaterializationWarehouse objectQueryableTestable directlyRebuild pattern
viewViewYesYesReplace view DDL each run
tableTableYesYesFull CREATE OR REPLACE / drop+create
incrementalTableYesYesAppend/merge new rows only
ephemeralNone (CTE)NoNoInlined into parents
 
{{
  config(
    materialized='incremental',
    on_schema_change='append_new_columns'
  )
}}
WITH src_reviews AS (
  SELECT * FROM {{ ref('src_reviews') }}
)
SELECT * FROM src_reviews
WHERE review_text IS NOT NULL

{% if is_incremental() %}
  AND review_date > (SELECT MAX(review_date) FROM {{ this }})
{% endif %}

On first run is_incremental() is false — the entire filter block is skipped and all rows load. On subsequent runs only rows newer than the watermark append. --full-refresh forces a full rebuild and also makes is_incremental() false.

Managing dbt models governance

Contracts, constraints, model versions, deprecation and access controls. The exam asks when to enforce a contract, how ref('model', v=2) resolves, and what happens when a deprecated model is still referenced.

Key facts the exam tests

  • contract: {enforced: true} fails the build if model output does not match declared column types and constraints.
  • Model versions live under versions: in YAML; latest_version: and deprecation_date: control which version ref() resolves to by default.
  • ref('dim_hosts_cleansed', v=2) pins a specific version; omitting v uses the latest non-deprecated version.
  • Access modifiers (access: private|protected|public) restrict which projects or groups can reference a model (dbt 1.5+).
  • Constraints in YAML (constraints:) document PK/FK/not-null at the model level; enforcement depends on warehouse and contract settings.
models:
  - name: dim_hosts_cleansed
    latest_version: 2
    versions:
      - v: 1
        defined_in: dim_hosts_cleansed
        deprecation_date: '2025-06-01'
      - v: 2
        defined_in: dim_hosts_cleansed_v2
        columns:
          - include: all
            exclude: [old_column]

Downstream models pin versions with {{ ref('dim_hosts_cleansed', v=2) }} as in dim_listings_w_hosts.sql. Omitting v resolves to the latest non-deprecated version.

Debugging data modeling errors

Compilation errors, wrong compiled SQL, zero-row models, and Jinja mistakes. Know which artifact to open and which command reproduces the failure without a full rebuild.

Key facts the exam tests

  • Parse phase builds manifest.json without executing warehouse SQL. Compilation errors surface here first.
  • target/compiled/ holds rendered SQL; target/run/ holds DDL sent to the warehouse.
  • dbt compile --select model_name renders SQL without running it.
  • {% if execute %} guards warehouse-touching Jinja during the parse pass.
  • Compilation Error with “unexpected end of template” usually means an unclosed Jinja block.
  • Model depends on node X not found — typo in ref() or file outside model-paths.
  • dbt --log-level debug increases verbosity in logs/dbt.log for stubborn failures.

Troubleshooting and optimizing dbt pipelines

Slow runs, failed CI, orchestration gaps, and production deployment issues. Scenarios often pair a symptom (tests skipped, wrong schema) with the command or config that fixes it.

Key facts the exam tests

  • dbt build runs seeds, snapshots, models and tests in DAG order; failed tests skip downstream nodes.
  • dbt run builds models only — tests never run.
  • dbt retry re-runs only failed nodes from the immediately previous invocation.
  • dbt has no built-in scheduler; Airflow, Dagster, cron or dbt Cloud invoke it.
  • Microbatch incremental models need adequate threads in profiles (course notes: 4+) or runs can hang.
  • Production uses separate targets/schemas; generate_schema_name macro customises dev vs prod naming.
  • dbt clean removes target/ and dbt_packages/; run dbt deps after cleaning packages.
Symptom in productionLikely fix
CI builds entire DAGAdd state:modified+ and publish prod manifest
CI fails on missing upstream tableAdd --defer with prod manifest
Dev schemas accumulatingdrop_dev_schemas macro pattern from Section 19
Nightly job six hoursIncremental models missing; full-refresh abuse
Tests pass in dev, fail in prodDifferent row volumes; check empty-table false passes

Implementing dbt tests

Generic, singular and unit tests; YAML structure; severity; store_failures. The exam loves the four built-in generics and the rule that any returned row means failure.

Key facts the exam tests

  • Four built-in generic tests: unique, not_null, accepted_values, relationships.
  • Tests compile to SELECT queries. Zero rows = PASS; any row = FAIL (or WARN if severity: warn).
  • YAML key is data_tests: (not legacy tests:). Generic arguments nest under arguments: from dbt 1.10.
  • Singular tests are one-off SQL files in tests/; generic tests are reusable macros declared in YAML.
  • Unit tests use unit_tests: in YAML with mock inputs — no warehouse data required.
  • Default test severity is error. WARN exits 0 but prints a warning.
  • You cannot test ephemeral models directly — no relation exists.
models:
  - name: dim_listings_cleansed
    columns:
      - name: room_type
        data_tests:
          - accepted_values:
              arguments:
                values: ['Entire home/apt', 'Private room', 'Shared room', 'Hotel room']
      - name: host_id
        data_tests:
          - relationships:
              arguments:
                to: ref('dim_hosts_cleansed')
                field: host_id

Creating and maintaining dbt documentation

Descriptions, docs blocks, the docs site, exposures and persist_docs. Expect questions about where descriptions live and what dbt docs generate produces.

Key facts the exam tests

  • Column and model descriptions live in schema.yml (or equivalent YAML).
  • {% docs %} blocks in .md files define reusable description snippets referenced with {{ doc('name') }}.
  • dbt docs generate writes catalog.json (warehouse metadata) and serves lineage from manifest.json.
  • Exposures document downstream consumers (dashboards, ML models) and appear in lineage.
  • meta: on models/columns holds arbitrary key-value metadata for tools.
  • persist_docs pushes descriptions to the warehouse catalog (adapter-dependent).
models:
  - name: dim_hosts_cleansed
    description: "{{ doc('dim_hosts_cleansed') }}"
    columns:
      - name: host_id
        description: Primary key of the host dimension.
      - name: is_superhost
        description: Whether Airbnb marks the host as a superhost.

The {{ doc('dim_hosts_cleansed') }} macro pulls reusable markdown from models/docs.md. Column descriptions can be inline strings or doc blocks. Exposures in dashboards.yml carry their own descriptions and link to dependent models for lineage.

Leveraging the dbt state

Manifest comparison, Slim CI, defer and state:modified. Know which artifact CI downloads from production and what --defer does when upstream relations are missing locally.

Key facts the exam tests

  • manifest.json in target/ captures the full compiled graph after each invocation.
  • state:modified selects nodes changed relative to a prior manifest (typically prod artifacts in CI).
  • state:modified+ adds downstream children of modified nodes.
  • --defer resolves ref() to production relations for unbuilt upstream models during CI.
  • Slim CI pattern: dbt build --select state:modified+ --defer --state path/to/prod/manifest.
  • Production manifest artifacts are published intentionally; local target/ stays in .gitignore.

Implementing and maintaining external dependencies

Sources, freshness, packages, seeds and exposures. Questions cover dbt source freshness, packages.yml, and the difference between a seed and a source.

Key facts the exam tests

  • Sources are declared in YAML with sources:; referenced in SQL with {{ source('name', 'table') }}.
  • Source freshness uses loaded_at_field and warn_after / error_after thresholds.
  • dbt source freshness runs freshness checks; it does not load data.
  • Packages install via dbt deps from packages.yml into dbt_packages/.
  • Seeds are CSV files loaded with dbt seed; for small static reference data only.
  • Exposures declare downstream dependencies on dbt models for lineage and impact analysis.
  • on-run-start and on-run-end hooks in dbt_project.yml run SQL at job boundaries.
sources:
  - name: airbnb
    tables:
      - name: raw_listings
        loaded_at_field: updated_at
        freshness:
          warn_after: {count: 12, period: hour}
          error_after: {count: 24, period: hour}

Run dbt source freshness --select source:airbnb.raw_listings to evaluate thresholds. Stale sources WARN or ERROR depending on config; they do not stop dbt run unless you wire freshness into orchestration.

Practice exam

25 scenario questions covering all eight topic areas. Answer each one before opening the explanation. Aim for 80%+ before booking the real exam.

Q1. A colleague runs dbt run on a fresh clone, then dbt test. A broken primary key in fct_reviews propagates into three downstream marts before any test fails. Which command would have prevented this?Fundamentals

Correct: dbt build

dbt build interleaves tests in DAG order. After fct_reviews builds, its tests run immediately; if a unique test fails, downstream models that depend on fct_reviews are skipped rather than built with bad data.

Why the others are wrong: dbt run never runs tests — that is exactly the failure mode described. dbt test alone does not build models, so on a fresh clone relations may not exist. dbt compile renders SQL without executing anything in the warehouse. dbt seed only loads CSV seeds.

Q2. dim_listings_cleansed lives in models/dim/ where dbt_project.yml sets +materialized: table, but the model file contains {{ config(materialized='view') }}. What materialization runs?Modelling

Correct: view

Config in the model SQL file wins over folder-level YAML. This is the exact pattern in the Airbnb project: dim/ defaults to table, but dim_listings_cleansed.sql overrides to view.

Why the others are wrong: table would apply only if the model file had no config block. incremental and ephemeral are not set anywhere for this model. dbt does not average or merge conflicting configs — most specific wins.

Q3. Which statement about ephemeral models is true?Modelling

Correct: Ephemeral models create no queryable relation in the warehouse; their SQL is inlined as a CTE in downstream models.

That is why switching src/ to ephemeral requires manually dropping old views once — dbt stops maintaining them but Snowflake keeps the objects until dropped.

Why the others are wrong: Ephemeral models cannot be queried directly with SELECT in a worksheet — there is no relation. You cannot run a data test against an ephemeral relation because nothing persists. Ephemeral does not write to a temp table; it inlines. Ephemeral is not the dbt default — view is.

Q4. An incremental model runs for the first time on an empty warehouse schema. What does is_incremental() return inside the model Jinja?Modelling

Correct: false

On first build the target relation does not exist yet, so dbt performs a full load. The {% if is_incremental() %} block is skipped and all historical rows are loaded.

Why the others are wrong: true applies only when the target relation already exists and you are not doing a full refresh. null and error are not return values of is_incremental(). The value does not depend on whether source data exists — only on target relation state.

Q5. You need to declare that review_id in fct_reviews must exist in dim_listings_cleansed.listing_id. Which built-in generic test fits?Testing

Correct: relationships

relationships validates foreign-key integrity by checking that values in the child column appear in the parent model column you specify via to: and field: arguments.

Why the others are wrong: unique checks no duplicates within one column on one model. not_null only checks for NULLs, not referential integrity. accepted_values checks an enum list, not a join to another table. A singular test could work but the question asks for the built-in generic.

Q6. In schema.yml under dbt 1.11, where do arguments for a generic unique test on column listing_id belong?Testing

Correct: Under data_tests:, nested in arguments: when parameters are required

From dbt 1.10+, generic test parameters belong under arguments:. The parent key is data_tests:, not legacy tests:.

Why the others are wrong: Top-level tests: is deprecated. Putting args directly on the test name without arguments: is the old syntax the exam marks wrong. Config blocks set test behaviour like severity, not column-level generic args. Macros are defined in .sql files, not schema.yml structure.

Q7. A singular test tests/consistent_created_at.sql returns 12 rows. What is the test result?Testing

Correct: FAIL (or WARN if severity is warn)

Every dbt test compiles to a SELECT. Any row returned means failure. Twelve rows means twelve violations.

Why the others are wrong: PASS requires zero rows. ERROR means the query could not execute — syntax error, missing relation, permission denied. SKIP applies to downstream nodes when an upstream model failed in dbt build, not to a completed test query. LIMIT in the test SQL does not cap failures — if any row matches, it fails.

Q8. What is the default severity for a data test if none is specified?Testing

Correct: error

Unset severity defaults to error, which fails the invocation (exit code non-zero) unless overridden at project level.

Why the others are wrong: warn must be explicit. info and critical are not standard dbt test severity values. skip is a run result status for unexecuted nodes, not a severity config.

Q9. CI downloads manifest.json from production and runs dbt build --select state:modified+ --defer --state ./prod_artifacts. What does --defer do?Production

Correct: Resolves ref() to production relations for upstream models not built in the CI schema

Slim CI builds only changed nodes and their children. Unmodified upstream models are not rebuilt in the ephemeral CI schema; --defer points refs at prod so the subgraph can still run.

Why the others are wrong: defer does not skip tests — tests on modified nodes still run. It does not defer job scheduling. It does not compare manifests — that is --state. It does not push artifacts back to production automatically.

Q10. Which file should you open first when a model compiles but returns zero rows unexpectedly?Troubleshooting

Correct: target/compiled/<path>/model_name.sql

Compiled SQL shows the fully rendered query including incremental filters. A watermark ahead of source data or an always-false WHERE is visible there.

Why the others are wrong: dbt_project.yml holds config, not rendered SQL. packages.yml lists package dependencies. profiles.yml holds connection settings. manifest.json is graph metadata — useful for lineage, not row-level logic debugging.

Q11. A snapshot YAML uses hard_deletes: invalidate. What happens when a source row is deleted?Modelling

Correct: The active snapshot row for that key is invalidated/end-dated per the snapshot strategy

hard_deletes: invalidate (replacing legacy invalidate_hard_deletes) tells the snapshot to treat deletes as SCD Type 2 closures rather than silently ignoring them.

Why the others are wrong: Snapshots do not automatically purge all history on delete. New snapshot tables are not created per delete event. dbt run does not execute snapshots — use dbt snapshot. Source freshness is unrelated to snapshot delete handling.

Q12. Which dbt command loads CSV files from the seeds/ directory into the warehouse?Fundamentals

Correct: dbt seed

Seeds are the only data dbt loads directly. dbt seed creates or replaces seed relations.

Why the others are wrong: dbt run builds models only. There is no dbt source command — freshness uses dbt source freshness. dbt deps installs packages. dbt snapshot runs snapshot definitions.

Q13. You added dbt_utils to packages.yml. Which command installs it into dbt_packages/?Fundamentals

Correct: dbt deps

dbt deps reads packages.yml and installs declared packages locally.

Why the others are wrong: dbt run executes models, not package install. pip install installs Python libraries, not dbt packages. dbt build assumes deps are already installed. dbt debug tests the connection.

Q14. From dbt 1.12 onward, how do you run a named selector called nightly_models?Production

Correct: dbt build -s selector:nightly_models

Selector invocation changed at 1.12 from --selector name to -s selector:name graph syntax.

Why the others are wrong: --selector nightly_models is pre-1.12 syntax — know both, but prefer the new form on 1.12+. --select nightly_models selects a node named nightly_models, not a selector definition. dbt selector run is not a command.

Q15. contract: {enforced: true} is set on dim_hosts_cleansed. The model SELECT returns STRING where YAML declares NUMBER. What happens?Testing

Correct: The build fails with a contract enforcement error

Enforced contracts compare actual model output types to declared YAML columns and fail the run on mismatch.

Why the others are wrong: dbt does not silently cast incompatible types under enforced contracts. WARN is for test severity, not contract enforcement. Documentation-only contracts without enforced: true do not fail builds. Success would contradict the enforced contract purpose.

Q16. Which ref() call pins dim_hosts_cleansed to version 2 when multiple versions exist?Production

Correct: {{ ref('dim_hosts_cleansed', v=2) }}

The v argument selects a specific published version from the versions: block in YAML.

Why the others are wrong: version=2 is not the Jinja kwarg syntax. ref('dim_hosts_cleansed_v2') only works if a separate model file exists with that name — versioning uses the v arg on the base name. ref(2) is invalid syntax.

Q17. A source includes loaded_at_field: updated_at and error_after: {count: 24, period: hour}. Which command checks staleness?Fundamentals

Correct: dbt source freshness

Freshness checks compare the maximum loaded_at_field to thresholds and WARN or ERROR accordingly.

Why the others are wrong: dbt test runs data tests, not source freshness blocks. dbt run builds models. dbt debug validates profile connection. dbt compile renders SQL without freshness queries.

Q18. What is the high-level execution order for dbt build on a project with seeds, snapshots, models and tests?Fundamentals

Correct: seeds, then snapshots, then models with tests interleaved per DAG

dbt build loads seeds first, runs snapshots second, then walks the model DAG executing each model followed by its tests before children build.

Why wrong orders fail: Models before seeds break refs to seeded tables. Running all tests only after all models describes dbt run then dbt test, not dbt build. Snapshots after dependent models can break first-run ordering when snapshots feed models.

Q19. Which graph operator selects a model and all its downstream children but not parents?Production

Correct: model+

The trailing + means downstream children. fct_reviews+ selects the fact and every model that depends on it.

Why the others are wrong: +model selects parents (upstream). @model selects parents and children. model alone includes parents by default in many contexts but not all children. tag:fact selects by tag, not graph direction.

Q20. exposures: in dashboards.yml document a Preset dashboard consuming dim_listings_w_hosts. What appears in dbt docs lineage?Fundamentals

Correct: A downstream exposure node linked to the referenced models

Exposures are first-class nodes in the DAG. They show as consumers in documentation lineage, connecting BI assets back to dbt models for impact analysis.

Why the others are wrong: Exposures do not create warehouse tables. They are not tests. They do not replace sources. They do not schedule dashboard refreshes — they document dependency only.

Q21. A macro calls run_query() to look up the max date from a table. When must it be wrapped in {% if execute %}?Jinja

Correct: Always — run_query touches the warehouse and execute is false during parsing

During parse, dbt builds the graph without guaranteed warehouse access. run_query() without an execute guard errors or returns nothing useful at parse time.

Why the others are wrong: compile-only is not a separate execute flag for this purpose. test runs still need the guard at parse. Production-only is wrong — the parse pass happens in every environment. Never wrapping works only for macros that never touch the warehouse.

Q22. on_schema_change: append_new_columns is set on an incremental model and a new column appears in the SELECT. What happens on the next run?Modelling

Correct: dbt adds the new column to the existing target table and continues incremental loads

append_new_columns is the permissive schema evolution strategy — new columns are appended without failing the run or full refreshing.

Why the others are wrong: fail is a different explicit strategy that errors on schema drift. Silent ignore is not the behaviour — dbt handles the DDL. Full refresh is not required unless you choose that strategy or run --full-refresh. The model does not auto-convert to table materialization.

Q23. After dbt docs generate, which two JSON files primarily power the documentation website?Fundamentals

Correct: manifest.json and catalog.json

manifest.json holds project metadata, descriptions and lineage edges from the last parse/build. catalog.json holds warehouse column types and stats queried during docs generate.

Why the others are wrong: run_results.json records execution outcomes, not docs content. packages.yml is source config, not generated output. profiles.yml is credentials. semantic_manifest.json relates to Semantic Layer, not core docs.

Q24. Which files belong in version control vs stay local-only in a standard dbt project?Production

Correct: models/, macros/, tests/, snapshots/, seeds/, dbt_project.yml, packages.yml in git; profiles.yml and target/ out of git

Project code and config live in the repo. Credentials in profiles.yml default to ~/.dbt/ precisely because they must not be committed. target/ is regenerated output; production manifest publishing is a deliberate CI exception, not normal dev workflow.

Why the others are wrong: Committing profiles exposes secrets. Ignoring models/ would lose the project. dbt_packages/ is often gitignored because dbt deps restores it — teams differ, but profiles never go in. logs/ stays local. Compiled SQL in target/ is never edited manually.

Q25. unit_tests: in YAML differ from data_tests: because unit tests —Testing

Correct: supply mock input rows and expected output without querying the warehouse

Unit tests validate transformation logic in isolation. given: blocks provide inputs; expect: blocks assert output rows. No source tables required.

Why the others are wrong: data_tests scan real warehouse tables and fail on returned rows. Unit tests are not faster singular tests — they use a different framework. Generic tests are reusable macros, not unit tests. Unit tests can run in CI without seeding production data volumes.

Timed drill: 25 questions in 45 minutes simulates exam pacing (~1.8 min/question). Repeat after revisiting weak topic sections.

Traps that catch people

  • Assuming equal topic weighting — there are none. A documentation question counts the same as an incremental strategy question. Do not skip Section 14 because it feels easy.
  • Studying only multiple choice — fill-in-the-blank asks for exact keys like materialized and data_tests. If you cannot type them, you will fail those items.
  • Using legacy tests: syntax — the exam bank for 1.11 expects data_tests: and arguments:. Old blog posts will steer you wrong.
  • Confusing dbt run with dbt build — scenario questions describe downstream poisoning that only build prevents. This appears in nearly every practice set.
  • Forgetting ephemeral has no relation — questions ask whether you can test or query ephemeral models directly. The answer is no.
  • Ignoring config precedence — a table folder default plus a view model config is a classic exam setup. File config wins.
  • Booking last-minute — slots require 48 hours lead time. Thursday-morning exams must be booked by Tuesday morning.
  • Second monitor left connected — proctors fail the environment check. Disconnect before the system test.
  • Thinking WARN tests protect production — WARN exits 0; CI may still deploy. Know severity semantics.
  • Skipping state:modified study — Slim CI questions appear under leveraging dbt state, not just production section titles.
  • Mixing up seed and source — seeds are loaded by dbt; sources are declared external tables already in the warehouse.
  • Assuming immediate retake — check current cooling-off period on the FAQ; policies change.

Why does the exam include fill-in-the-blank and build-list formats instead of only multiple choice?Certification

Analytics engineers write YAML and Jinja daily. Recognising a correct config in a list proves less than typing data_tests: or ordering CI steps correctly. dbt Labs designed the exam to separate people who have operated dbt from people who watched videos about it.

Build-list items also test whether you understand process order — parse before execute, seeds before models, tests gating children in dbt build.

Explain config precedence as if the interviewer will ask you to resolve a deliberate conflict.Modelling

Highest to lowest: model file {{ config() }}, model-specific entry in dbt_project.yml, folder-level YAML, project-wide YAML, dbt default. For materialization the default is view.

Example: dim/ folder sets table, but dim_listings_cleansed.sql sets view — effective result is view. Inspect with dbt compile --select model_name and read the log line (sql view model vs sql table model).

Compare generic, singular and unit tests — when would you use each on the Airbnb project?Testing

Generic tests in YAML cover column-level rules: unique on listing_id, accepted_values on room_type. Singular tests cover cross-model logic like consistent_created_at.sql where two timestamps must align. Unit tests mock inputs for a model transformation without warehouse data — the course uses them on mart_fullmoon_reviews.

All three use failing-row semantics except unit tests which compare expected output rows directly.

Describe Slim CI using state:modified+, defer and a production manifest.Production

CI downloads manifest.json from the last successful production run. state:modified+ selects models changed in the PR plus downstream children. --defer resolves unbuilt upstream refs to production relations so the subgraph can execute in an ephemeral schema without rebuilding the entire warehouse.

Typical command: dbt build --select state:modified+ --defer --state ./prod_artifacts. This saves warehouse cost and minutes per PR.

A certification scenario asks what happens when an enforced contract column type mismatches. Explain the full failure path.Testing

With contract: {enforced: true}, dbt compares the model query result schema to YAML-declared columns. Type mismatch fails the node during the contract check phase — the run reports error, downstream nodes skip if using dbt build.

Without enforcement, YAML documents intent but dbt does not fail the build — useful for gradual rollout. The exam tests the difference directly.

What is the difference between a seed and a source, and which command touches each?Fundamentals

Seeds are CSV files in seeds/ loaded by dbt via dbt seed — small static reference data like seed_full_moon_dates. Sources are existing warehouse tables declared in YAML and referenced with {{ source() }}; dbt never loads them. Freshness checks use dbt source freshness.

Confusing the two is a common exam trap — sources are external; seeds are project-owned files.

How would you prepare in the final week before the exam if you already completed the bootcamp?Certification

Days 1–2: timed practice exam on this page plus official sample questions. Days 3–4: revisit sections where you scored below 80%, focusing on YAML typing drills. Day 5: redraw project tree, config precedence, and build order from memory. Day 6: rest and system check. Exam day: no cramming — trust muscle memory.

Run at least three hands-on commands in the Airbnb repo: dbt build -s +fct_reviews+, dbt source freshness, dbt deps.

Explain DOMC question strategy to someone who has never seen the format.Certification

Discrete Option Multiple Choice presents several statements about a scenario. Each statement is scored independently — true or false — rather than picking one winner from a list. A statement that is mostly true but wrong in one word counts false.

Read each option in isolation. Do not assume exactly one statement must be true. The exam documentation links to Caveon's DOMC guide — skim it before booking.

What debugging artifacts do you inspect when a model compiles successfully but test count drops to zero?Troubleshooting

First dbt ls --resource-type test --select model_name+ to see whether tests exist in the graph. If they do, check whether you used dbt run instead of dbt build — run never executes tests. If selection is wrong, widen --select.

Inspect logs/dbt.log for skipped nodes. Confirm data_tests: YAML still parses — a YAML error can drop tests silently during parse in some setups.
