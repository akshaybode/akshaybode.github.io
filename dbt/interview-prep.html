How to use this page

These are scenario questions, not flashcards. An interviewer is listening for how you think: whether you ask clarifying questions, whether you separate symptoms from causes, and whether you can tie a warehouse problem back to a modelling decision.

Cover the summary, say your first step out loud, then open the answer and compare. If your version missed a step, close it and try again without reading. Pair with a colleague if you can — the follow-up questions (“what if the source changed?”, “what would you check in prod?”) are where interviews actually live. Cross-links point at the numbered course sections where the bootcamp goes deeper on a topic; this page assumes you have built the Airbnb project through fct_reviews, dim_listings_cleansed, the mart layer, and snapshots.

Structure every answer. A workable template: restate the problem, name what you would inspect first (logs, compiled SQL, row counts, lineage), form a hypothesis, validate it with one cheap query, then describe the fix and how you would prevent recurrence. Interviewers forgive not knowing every dbt flag; they do not forgive jumping to a solution before understanding the failure mode.

Follow-ups to prepare for

Interviewers rarely stop at the first answer. After you describe debugging a slow model, expect: “How would you know if it happens again?” After a modelling answer: “What would you do at ten times the data volume?” After a testing answer: “Who decides if we ship with a failing warn-level test?” Have a second beat ready — usually monitoring, documentation, or a phased rollout.

Debugging and incidents

Answer each one out loud before opening it. These are the questions that start with “something broke in production” — see also Section 16 for the course’s debugging toolkit.

Do not skip clarifying questions. “A model got slow” is ambiguous. Ask whether runtime jumped suddenly or crept over weeks, whether only prod is affected, and whether the model is incremental, a view, or a snapshot. Your first thirty seconds should sound like a calm incident commander, not a guess at the answer.

The scenarios below reference the course DAG. In a live interview you may not have Snowflake open — describe exactly which artifact you would open first and what you expect to see if your hypothesis is correct. That habit matters more than getting the root cause right on the first try.

A model went from two minutes to forty — walk me through how you’d find out why?Troubleshooting

First I would confirm scope: one model or the whole DAG, dev or prod, and whether anything changed in code, upstream data volume, or warehouse state (auto-suspend, warehouse size, query queue). I would pull the last successful run from orchestration logs and compare row counts, bytes scanned, and execution time in the warehouse query history.

For a model like fct_reviews, I would open target/compiled/airbnb/models/fct/fct_reviews.sql and check whether the incremental filter still applies — a missed is_incremental() branch or a --full-refresh turns a cheap merge into a full-table rebuild. I would also check whether an upstream source doubled in size or lost partition pruning because someone removed a date predicate.

If compiled SQL looks unchanged, the regression is almost always warehouse-side: a bigger warehouse was downsized, clustering keys stopped working, or a concurrent job is competing for the same resources. Document the root cause and add a runtime alert or a row-count test so the next regression pages someone before the CFO does.

In the interview, narrate the commands: dbt compile --select fct_reviews, then inspect Snowflake query history filtered by user and model name. Mention dbt run --select fct_reviews --sample "7 days" from Section 16 as a cheap way to reproduce transform logic on a subset when event_time is configured.

Close with prevention: store per-model runtime in observability (dbt Cloud run metadata, Elementary, custom logging macro), alert when duration exceeds a rolling baseline, and cap concurrent full-refresh jobs in orchestration so one mistaken flag does not scan the whole fact history.

A test passes but the numbers are visibly wrong — what does that tell you?Testing

Passing tests only prove what you asserted. A unique test on review_id says nothing about whether revenue is correct; a not_null test passes on empty tables in some configurations. Wrong numbers with green tests usually mean the tests guard the wrong thing, the grain is wrong, or the test scope excludes the bad rows.

I would reconcile at the grain the business cares about: compare COUNT(*) and key sums between the mart and a trusted source query, then bisect upstream models with dbt build --select +mart_fullmoon_reviews. If staging matches raw but the mart does not, the bug is in transform logic; if staging is already wrong, the bug is earlier or in the source.

This is a signal to add relationship tests, aggregate reconciliation tests, or a singular test that encodes the business rule that was violated. See Section 11 and Section 12 for generic versus singular tests and unit tests.

Concrete example: mart_fullmoon_reviews could pass uniqueness on review_id while double-counting listings because the join to dim_listings_w_hosts exploded rows after a host duplicated in source. A dbt_utils.unique_combination_of_columns test on the mart grain, or a singular test asserting review count equals fct_reviews, closes that gap.

The CFO’s dashboard disagrees with finance’s numbers — how do you resolve it?Troubleshooting

Stop debating totals until both sides agree on definitions: metric formula, grain, date timezone, inclusion rules (gross versus net, cancelled bookings, refunds), and as-of date. Write each definition down before running a single query — most “data bugs” are two correct queries answering different questions.

Then trace lineage from each number to the warehouse table. The CFO’s dashboard may read a cached extract or an exposure built on mart_fullmoon_reviews while finance exports from a spreadsheet tied to a snapshot taken yesterday. Compare row counts, date filters, and join keys at each layer.

When definitions should match, pick one query as ground truth, diff at daily grain, and find the first date or segment where totals diverge. Fix the model or document the intentional difference in the dbt docs description and the exposure metadata so the disagreement does not recur every month.

Walk the interviewer through a reconciliation query pattern: aggregate both sides by DATE_TRUNC('day', review_date), full outer join on date, filter where absolute difference exceeds a tolerance. The first diverging day tells you whether a deploy, a loader change, or a filter change caused the drift. Reference exposures in Section 15 as the place to document which dashboard owns which mart.

A dbt run succeeded but a table is empty — what happened?Gotcha

Success means dbt executed without error, not that rows were written. An incremental model with an over-restrictive WHERE clause, a filter that excludes all source data, or a dbt run --empty left in a CI job all produce zero-row relations with a green checkmark.

For fct_reviews, I would check the compiled incremental predicate: if max(review_date) on the target is ahead of the source because of bad seed data or a timezone cast, every new run matches nothing. I would also verify the upstream src_reviews still has rows and that a view was not swapped for a table pointing at an empty dev schema.

Add a minimum row-count test or a generic test like the course’s minimum_row_count on critical facts, and compare SELECT COUNT(*) before and after in the orchestration step so emptiness fails the pipeline even when dbt reports OK.

fct_reviews row counts dropped by half after an incremental run — where do you start?Troubleshooting

Half is too clean to ignore — suspect a join that became inner, a deduplication key change, or an incremental strategy that deleted rows. I would compare COUNT(*) on src_reviews versus fct_reviews for the same date range, then read the compiled merge SQL under target/run/ to see whether delete-plus-insert logic ran.

The surrogate key in fct_reviews is built from listing_id, review_date, reviewer_name, and review_text. If any of those columns changed upstream (trimming, encoding, null handling), keys no longer match and merges can drop or duplicate rows. Check whether on_schema_change='fail' should have stopped the run — if it did not fire, the schema did not change but the data did.

Run a full refresh in dev with a backup, diff old versus new keys, and add a singular test that compares daily review counts to the source until the merge logic is verified. See Section 8 on incremental strategies.

Mention on_schema_change='fail' on fct_reviews — it protects against column drift but not against logic changes inside the SELECT. Version control diff on the model file is part of the incident checklist.

A downstream mart looks fine but upstream staging has duplicate keys — how did that slip through?Testing

Downstream models can hide upstream duplicates: a GROUP BY in the mart, a DISTINCT, or a join that collapses rows makes the mart look healthy while staging is wrong. Without a unique test on the staging grain, duplicates propagate silently until someone drills into detail rows.

I would run dbt test --select src_listings and add a unique test on listing_id if the grain is one row per listing. Then inspect the raw source: reloads, CDC duplicates, and multiple snapshots loaded into the same table are common causes.

Fix at the lowest layer that should enforce grain — usually staging — and add relationship tests from facts to dimensions so bad keys surface when facts are built, not when a dashboard looks odd. The course project tests cleansed dimensions; a production project would test staging too.

Follow-up the interviewer might ask: “Would you dedupe in staging or in the fact?” Answer: dedupe in staging if the grain is defined there (one row per listing in src_listings); dedupe in the fact if duplicates represent legitimate multiple events. Never hide duplicates in a mart aggregate without documenting the grain change.

Compile succeeds but the warehouse returns “object does not exist” at runtime — what do you check?Troubleshooting

Compile resolves ref() and source() to relation names for your current target; runtime fails when that relation is missing in the warehouse. Common causes: upstream model not built in this schema, wrong target selected, or a source pointing at a table the loader has not created yet.

Run dbt ls --select +model_name --output name --output schema to see resolved locations, then dbt build --select +model_name to build ancestors. If only prod breaks, compare dev and prod grants and database names in profiles.yml.

For the Airbnb project, a failure on ref('src_reviews') often means staging was skipped in a selective run. In CI, ensure modified+ builds include new dependencies. Mention dbt debug for connection issues versus missing relations — different fixes.

Modelling judgment

These questions probe whether you can design models others will trust. The Airbnb project is the reference — see Section 5 and Section 7.

Modelling interviews are not about memorising Kimball terminology. The interviewer wants to hear you choose grain deliberately, place logic once, and explain trade-offs between normalisation and consumption speed. Reference real files: dim_listings_cleansed.sql, dim_listings_w_hosts.sql, mart_fullmoon_reviews.sql.

Medallion language. Even if the company does not use the word, map your answer: staging (src_*), conformed dimensions and facts (dim_*, fct_*), and marts (mart_*). Interviewers use different vocabulary; translating your DAG into their layer names shows experience.
When would you denormalize versus keep a snowflake schema?Modelling

Denormalize when query consumers are many, SQL skill varies, and join performance or simplicity matters more than storage deduplication. The course’s dim_listings_w_hosts joins listing and host attributes so analysts do not repeat the same join in every notebook.

SELECT
  listing_id,
  listing_name,
  room_type,
  CASE
    WHEN minimum_nights = 0 THEN 1
    ELSE minimum_nights
  END AS minimum_nights,
  host_id,
  REPLACE(price_str, '$') :: NUMBER(10, 2) AS price
FROM {{ ref('src_listings') }}

Keep a snowflake (normalized) shape when dimensions change independently, when the same dimension is reused across many facts with different grains, or when you need a single place to fix host attributes without rebuilding wide tables. Maintain normalized core models and expose denormalized marts as views or tables on top.

The wrong answer is always one or the other. A mature project has both: cleansed dimensions at canonical grain, plus purpose-built marts that trade redundancy for consumption speed.

In interviews, mention maintenance cost: when host phone numbers change, a wide table forces you to rebuild every dependent mart or accept stale host columns until the next run. Normalized dim_hosts_cleansed updates once; wide tables ref() it. That trade-off is the heart of the question.

How do you decide the grain of a new fact table?Design

Start from the business event, not the source file. Ask: “What is one row?” For reviews, one row per review (or per review per listing per day if the source duplicates) — the course builds fct_reviews at review grain with a surrogate key when natural keys are messy.

List the metrics the fact should support. If stakeholders need listing-day metrics and review-level metrics, you may need two facts at different grains rather than one fact that aggregates away detail. Document the grain in the model description and enforce it with a unique test on the primary key.

If you cannot state the grain in one sentence, the model is not ready to build. Resolve ambiguities with stakeholders before writing SQL, not after a dashboard shows double-counted revenue.

Cite fct_reviews explicitly: grain is one review event; the surrogate key handles composite natural keys that might not be unique if the source sends revisions. If the business later asks for “one row per listing per day summarised,” that is a different model (aggregate fact or mart), not a silent grain change on the existing fact.

A stakeholder wants a column added to five different marts — where does the logic go?Design

Once, as upstream as possible. Add the column to the shared dimension or staging model that owns the attribute, then expose it through ref() to each mart. If five marts need the same CASE expression copied five times, you have a missing intermediate model.

If the column is mart-specific (a segment flag only used in one campaign analysis), it belongs in that mart. If it describes a listing or host, it belongs in dim_listings_cleansed or dim_hosts_cleansed even if only some marts select it today.

For repeated logic that is not a column (complex date windows, currency conversion), extract a macro or an intermediate model. The interview signal is DRY without premature abstraction — three copies is a pattern, one copy is fine.

Example: adding “is_full_moon_night” to multiple marts belongs in the seed join logic once — the course centralises full-moon logic in mart_fullmoon_reviews via seed_full_moon_dates and dim_fullmoon. Other marts should ref() that pattern rather than rejoin the seed five times with slightly different date math.

Should host attributes live in dim_listings_w_hosts or a separate bridge table?Modelling

For a strict one-host-per-listing domain, a wide dimension like dim_listings_w_hosts is appropriate and matches how analysts think about the Airbnb dataset. You get simple joins and fast consumption at the cost of repeating host columns on every listing row.

A bridge table (listing-host pairs) is warranted when listings can have co-hosts, ownership changes, or many-to-many relationships over time. Then grain is listing-host-period, and facts join through the bridge with careful effective-date logic.

Ask whether host attributes are truly listing-scoped or host-scoped. Superhost status belongs on the host dimension; “minimum nights for this listing” belongs on the listing side. Mixing the two in one wide table without documenting ownership causes silent inconsistencies when host data updates.

Reference dim_listings_w_hosts.sql from the course: it joins cleansed listings to cleansed hosts on host_id. If the interviewer asks about SCD Type 2, explain that this model is typically current-state unless you add effective dates from snapshots.

When is a wide mart_fullmoon_reviews-style table the right choice versus normalized facts and dims?Design

A wide mart is right when one audience runs one predictable query pattern repeatedly — here, reviews enriched with listing, host, and calendar attributes for a specific analysis (full-moon nights). Building it once in dbt saves every analyst from chaining five joins.

Normalized facts and dims are right when many teams slice the same events differently, when dimensions are governed centrally, or when wide marts would multiply storage and refresh cost unsustainably. Facts stay narrow; dimensions version independently.

In practice, build normalized cores for reuse, then marts as consumer-specific projections. Document which marts are official products versus exploratory so the team knows which to trust for KPIs.

The course mart joins reviews to listing, host, and calendar attributes for a niche analysis. That is the right shape when the audience is fixed and the SQL would otherwise be copy-pasted across notebooks. It is the wrong shape when ten teams need different column subsets — then expose dimensions and facts and let BI tools join, or ship multiple thin marts.

How do you handle slowly changing dimensions when the source does not send history?Modelling

You cannot reconstruct history you never captured. Options: start snapshotting now with dbt snapshots (Section 10), backfill from whatever audit columns exist (updated_at on raw_listings), or accept type 1 overwrite and document that historical reporting is point-in-time only.

For the Airbnb project, raw_listings_snapshot and raw_hosts_snapshot capture changes going forward. Analysts asking “what was the price last quarter?” before the snapshot existed need a different source or an explicit “not available” answer.

When only current state exists, use type 1 in dimensions and avoid fake effective dates. When audit timestamps exist, you can sometimes rebuild partial history with window functions, but validate against known events before trusting it for finance.

Mention snapshot YAML config from the course (raw_listings_snapshot.yml): strategy, unique key, and updated_at column are choices you defend in an interview. Check strategy versus timestamp affects cost and correctness when rows can be hard-deleted.

When would you use an ephemeral model instead of a view in staging?Design

Ephemeral models inline as CTEs — no relation in the warehouse, no direct tests against the model itself. The course uses ephemeral-style staging in early layers to avoid cluttering the catalog with intermediate objects analysts should not query.

Choose ephemeral when the logic is purely preparatory, short-lived in the DAG, and never a consumer-facing boundary. Switch to a view or table when analysts need to query staging directly, when you need to test it independently, or when the same CTE would compile into multiple huge copies and hurt performance.

Interview trap: ephemeral errors surface at the downstream model line number, which complicates debugging — mention that trade-off. See Section 8 for materialisation comparison.

Testing and trust

Interviews test whether you can make data trustworthy without blocking the team. See Section 11 and Section 12.

A strong candidate distinguishes test types and assigns them to layers: source freshness on raw_listings, schema tests on staging keys, business-rule singular tests on cleansed dimensions, unit tests on incremental logic, and lightweight checks in CI versus heavy reconciliation nightly. Weak answers treat “add more tests” as uniformly good without mentioning cost or merge gates.

models:
  - name: dim_listings_cleansed
    columns:
      - name: listing_id
        data_tests:
          - unique
          - not_null
      - name: host_id
        data_tests:
          - relationships:
              arguments:
                to: ref('dim_hosts_cleansed')
                field: host_id
How do you decide what to test on a new model?Testing

Test grain first: unique and not_null on the primary key. Test relationships for every foreign key to a dimension. Then test business rules that would embarrass you if wrong — non-negative prices, minimum nights logic, row counts within expected bounds.

Prioritize by blast radius: a broken staging model poisons everything downstream; a broken ad-hoc analysis model does not. For dim_listings_cleansed, the course tests column values and row-count parity with raw; for a new mart, add tests that encode the mart’s specific filters.

Do not test everything on day one. Cover what would fail silently and add tests when bugs appear. Document untested assumptions in the model description so the next hire knows the gap.

Map tests to failure modes: uniqueness catches loader duplicates; relationships catch orphaned foreign keys after inner joins; accepted-values catches enum drift in room_type; singular tests catch business rules like the course’s dim_listings_minimum_nights test. Say which you would skip initially (expensive cross-warehouse comparisons) and why.

A critical test would take 20 minutes to run on every commit — what do you do?Cost

Never run a 20-minute test on every PR. Tier your tests: fast schema and uniqueness checks in CI on a slim dev target; heavy reconciliation tests on a nightly schedule or pre-production deploy. Use selectors (Section 17) to define tags like ci versus nightly.

Make the expensive test cheaper if possible: sample recent partitions, compare aggregates instead of row-by-row diffs, or test against a materialized subset. A test that compares daily totals for the last seven days catches most regressions at a fraction of the cost.

If the test must stay expensive, treat it as a monitoring job with alerting, not a merge gate. Communicate the trade-off to the team: what risk you accept in CI versus what you catch overnight.

selectors:
  - name: ci_tests
    definition:
      method: tag
      value: ci
  - name: nightly_heavy
    definition:
      method: tag
      value: nightly

Run dbt test --selector ci_tests on PR and dbt test --selector nightly_heavy on schedule. A unique test on a billion-row fact belongs in nightly unless the warehouse can prune partitions.

How do you communicate data quality issues to non-technical stakeholders?Behavioural

Lead with impact, not mechanism. “Revenue for March may be overstated by roughly 3% because cancelled listings were included” lands better than “the left join on dim_listings_cleansed failed a relationship test.” Give a time-bound estimate for fix and a workaround if one exists.

Separate what you know from what you are still verifying. Offer a daily check-in until resolved. After the fix, send a short post-mortem: what happened, what we changed, what we added so it is caught earlier next time.

Use the dbt docs site or exposure descriptions as the permanent record of definitions so “what does this number mean?” does not depend on one engineer’s memory.

Bad example: “The relationship test on host_id failed.” Good example: “About 200 listings temporarily show no host name because yesterday’s host load was incomplete; listing counts are correct, host attributes may be blank until tonight’s run.” Tie severity to decisions: can we still close the month?

Your unique test on review_id passes but you know duplicates exist — how?Gotcha

The test runs against the relation in the target schema you built, not against your mental model of the data. If you inspected raw raw_reviews but the test runs on fct_reviews after deduplication, both can be true. Alternatively, duplicates share the same surrogate key because the hash inputs collided or nulls were handled unexpectedly.

Nulls also break intuition: in SQL, two nulls are not equal, so a unique test on a nullable column may pass with duplicate-looking business rows. Open the compiled test SQL, run it manually, and run a GROUP BY on the columns humans consider the natural key.

Fix the key definition or add a singular test on the natural key columns. Consider dbt_utils.generate_surrogate_key with explicit null handling documented in the model.

The course builds review_id from four columns in fct_reviews.sql. Walk through what happens if review_text is null (filtered out) versus empty string (included) — small cleansing differences change the key and can hide duplicates from humans while satisfying the hash.

What tests would you add to dim_listings_cleansed that the course project skips?Testing

The course covers regex on raw price strings and minimum nights bounds; I would add accepted-values tests on room_type, a relationship test from host_id to dim_hosts_cleansed, and a singular test that no listing has minimum_nights greater than 365 unless the business allows it.

Cross-model tests matter: expect row count to be less than or equal to raw listings if inactive listings are filtered, with the exceptions documented. Add a recency test if listings should always have a recent updated_at from the loader.

For production, source freshness on raw_listings (Section 9) belongs in the same conversation — a perfect dimension built from stale raw data still fails the business.

Mention dbt_expectations from the course for distribution tests (price ranges, regex on raw strings before cleansing). Interviewers like hearing that tests belong on raw, staging, and mart layers — not only on the final presentation table.

How do you test an incremental model’s merge logic without a full refresh?Testing

Use unit tests (Section 12): mock inputs with fixed rows, run the model logic, assert expected outputs including updated and deleted rows. The course’s unit_tests.yml on the mart layer shows the pattern; apply the same to incremental facts.

In dev, run two incremental loads with controlled vars — fct_reviews supports start_date and end_date vars for windowed loads. Insert known rows into a dev source stub, run incremental twice, and assert idempotency: running the same window again should not change counts.

Compare target/run merge SQL against what the warehouse executed. For delete-plus-insert strategies, verify the delete predicate matches the insert key set. A full refresh in an isolated schema is the last resort, not the first test.

Cite the course vars on fct_reviews: start_date and end_date let you load a controlled window twice and assert row counts stay stable. That is cheaper than cloning prod and safer than testing merge logic only in production.

Source freshness failed but the pipeline kept running — was that wrong?Testing

Depends on policy. Freshness checks in sources.yml warn or error based on configuration and orchestration settings. If reviews are stale but marketing only needs listing attributes, continuing with a warning can be correct — if finance needs today’s reviews, it is wrong.

Define severity per source and exposure: freshness on raw_reviews should block fct_reviews and downstream marts when SLAs require current data. Document the behaviour in runbooks so on-call does not guess.

Interview answer: tie freshness to consumer impact, not generic “always fail.” Reference Section 9 for source configuration and Section 19 for job design.

How would you design CI for a dbt project with no tests today?Production

Week one: CI runs dbt parse and dbt compile on every PR to catch syntax and Jinja errors. Week two: add unique and not_null on primary keys for the ten most-used models. Week three: add source freshness and one aggregate reconciliation test on the main fact.

Use a dedicated CI target with read-only prod sources or masked dev data, dbt build --select state:modified+ if you have a previous artifact, or slim CI with --empty for schema validation when data is sensitive. Block merge on compile failure; warn on test failure until the backlog is triaged.

Publish artifacts (manifest.json) from prod runs so CI can do state-aware selection. Document the roadmap so stakeholders see testing as incremental hardening, not a month-long freeze.

First three models to test in the Airbnb project: dim_listings_cleansed (unique on listing_id), fct_reviews (unique on review_id, not_null on listing_id), src_reviews (relationship to raw or row-count bounds). That covers the spine of the DAG in under two minutes of CI time on a dev target.

Mention dbt build versus dbt run from Section 17: in mature CI, build runs tests in dependency order and stops early — preferable once you have any tests at all.

A production run failed at 3am — walk through your response?Production

Acknowledge the alert, check orchestration for the failing node and error class (compile, warehouse timeout, test failure). If downstream dashboards are broken, assess blast radius: can consumers use yesterday’s table or a fallback view?

For a model failure, read logs/dbt.log and the warehouse error. Re-run the single model with dbt run --select model_name after a fix; do not re-run the entire DAG unless dependencies require it. For a test failure, decide whether to fix data, fix logic, or pause consumers while investigating.

Communicate status to stakeholders if SLAs are at risk. After recovery, capture a short incident note: root cause, fix, and preventive test or monitor. See Section 16 for log locations and compile versus run artifacts.

Typical 3am triage sequence

dbt run --select fct_reviews --target prod
Database Error: Numeric value '$1,200' is not recognized
→ open dim_listings_cleansed compiled SQL — price cast broke on new format
dbt test --select dim_listings_cleansed --target prod
1 of 3 FAIL — dbt_expectations regex on raw still passes; cleansed cast fails at runtime

Narrate rollback: revert the merge, re-run last green artifact, notify consumers, fix forward with a regex test on cleansed output. Production interviews want calm sequencing, not heroics.

How do you roll out a breaking model change without breaking downstream consumers?Production

Use expand-contract: add new columns or a v2 model alongside the old one, migrate consumers, deprecate the old model with a sunset date. Renaming or removing a column in place breaks every BI query and notebook that selected it.

For grain changes ( splitting fct_reviews grain, for example), ship a new fact with a new name, mark the old fact deprecated in docs, and give consumers a mapping period where both exist. Versioned schemas or aliases can shield prod while dev validates.

In dbt, leverage exposures to list downstream dashboards and owners. Notify them before merge, run their queries against the candidate schema in staging, and gate deploy on signed-off reconciliation.

The course ships dim_hosts_cleansed_v2 alongside v1 as a teaching pattern — in production you would deprecate v1 in docs, set a removal date, and use dbt contracts (Section 19) if consumers depend on stable column types.

Your prod dbt job is green but the BI dashboard is stale — what do you check?Troubleshooting

dbt finished; something after dbt did not. Check whether the BI tool caches extracts on its own schedule, whether the dashboard points at a different schema or database than prod dbt writes to, and whether a view was refreshed but an extract was not.

Verify MAX(updated_at) or row counts on the table the dashboard queries versus what dbt just built. A common mistake is dev target credentials in the BI connection, or an exposure documenting mart_fullmoon_reviews while the dashboard still queries an old table name.

Align orchestration: trigger BI refresh from the dbt job success webhook, or document independent schedules so stakeholders know the dashboard lag is expected. Exposures in Section 15 help document the intended link.

Checklist item interviewers like: compare MAX(review_date) in the dashboard’s SQL to the same query on the prod mart. If prod is fresh and the dashboard is not, the bug is outside dbt — do not re-run the whole DAG.

How would you structure dev, staging, and prod schemas for the Airbnb project at scale?Production

Developers get personal schemas (or prefix) built from generate_schema_name macros — the course customizes this in macros/generate_schema_name.sql. CI writes to ephemeral CI schemas destroyed after the run. Staging mirrors prod structure with masked or sampled data for integration tests.

Prod is one canonical schema (or database) per layer: staging, dimensions, facts, marts. Raw stays loader-owned. No one queries prod tables directly for ad-hoc experiments; they branch in git and build to dev.

Document target names in profiles.yml, restrict prod credentials to the orchestrator, and use grants managed by dbt hooks or platform IAM so personal schemas cannot overwrite prod.

Reference the course macro drop_dev_schemas.sql for cleaning ephemeral dev objects — at scale, automate schema expiry so abandoned dev tables do not accumulate storage cost. Interview answer ties environment strategy to cost and security, not just naming conventions.

When do you fail the pipeline versus warn and continue?Production

Fail when downstream models would propagate wrong data: failed uniqueness on a primary key, broken relationship on a foreign key, freshness beyond SLA on a critical source, or a fact row-count drop beyond threshold. Continuing poisons trust and makes rollback harder.

Warn when the issue is isolated and well understood: a non-critical mart failed, a documentation-only change broke, a test flagged a known data quirk with a ticket open. Store warnings in observability tooling and review in standup.

Make the policy explicit in project docs so on-call does not debate at 3am. Severity tags on tests (error versus warn in dbt Cloud, or custom hooks) encode the contract.

Example: fail on fct_reviews uniqueness; warn on documentation-only test failures; fail on source freshness for raw listings if the daily executive dashboard depends on it. Connect policy to exposures in dashboards.yml so severity matches business impact.

How do you safely test a prod fix without writing to prod twice?Production

Clone prod data to a staging schema or use a clone database (Snowflake zero-copy clone, BigQuery snapshot) and run dbt build --target staging against the fixed branch. Compare row counts and key metrics to prod before merging.

For logic-only fixes, dbt compile plus manual execution of compiled SQL in a worksheet limited to a sample window validates the change without materialising the full DAG. Use --sample when event_time is set, as on fct_reviews.

Never test experimental fixes by running unreviewed SQL directly in prod. The interview signal is disciplined promotion: dev branch, staging build, compare, merge, prod deploy with monitoring.

Architecture and trade-offs

Senior interviews probe system design, not just SQL. Cross-link to Section 8, Section 10, and Extras for Mesh and cost topics.

Architecture answers should acknowledge constraints: dbt is batch-oriented, the warehouse bills per scan, and organisational boundaries matter as much as technology. When asked about real-time or Mesh, start with “what problem are we solving?” before naming products.

Everyday analogy — Choosing incremental versus snapshot is like choosing between a diary entry (events append) and a photo album of your house (how it looked over time). You would not take a daily full photo album of every review written; you might snapshot listing price because the source overwrites it.
When would you choose an incremental model over a snapshot?Comparison

Incremental models append or merge new events efficiently — fct_reviews is the right tool when you have a reliable timestamp and only need current-plus-new rows, not full history of every attribute change.

Snapshots capture slowly changing attributes on a mutable source: raw_listings_snapshot tracks how price and availability changed even when the loader overwrites rows. Use snapshots when history matters and the source does not provide it.

If you need both event stream and attribute history, you often need both patterns: incremental facts for reviews, snapshots for listing attributes. Choosing wrong means either runaway cost (snapshotting a billion-row fact) or lost history (incremental overwrite on a dimension).

Say explicitly: fct_reviews with event_time='review_date' is optimised for append-heavy event data; raw_listings_snapshot captures how listing attributes drift. An interviewer follow-up might ask about hard deletes — point to snapshot hard-delete handling in Section 10.

How would you evaluate whether to introduce dbt Mesh?Design

Mesh solves ownership boundaries between teams, not performance. Evaluate it when multiple groups maintain separate dbt projects, cross-team ref() breaks release cadence, and contracts are negotiated informally instead of enforced.

Prerequisites: stable public models, semantic agreement on grain, CI that can run cross-project, and organizational willingness to version interfaces. If one team owns the Airbnb pipeline end to end, Mesh adds overhead without benefit.

Pilot with one downstream consumer project referencing a published package or Mesh node, measure deploy friction before and after, and read the trade-offs in Extras. Do not adopt Mesh because it is fashionable.

Anti-pattern to name: splitting the Airbnb repo into three projects because three engineers work on it — if they deploy together and share one warehouse schema, a monorepo with folders and ownership tags is simpler. Mesh pays off when legal, cadence, or stack boundaries are real.

Your company wants real-time data — how does that change the dbt architecture?Design

dbt is batch-oriented. Real-time KPIs usually come from streaming into the warehouse (materialized views, streaming tables, or a separate serving layer) while dbt builds authoritative batch marts on a schedule for reconciliation and complex joins.

Draw a clear line: what must be sub-minute (operational alerts, fraud) versus what can be hourly or daily (finance, executive dashboards). Do not run dbt every minute on full models; incremental micro-batches with tight SLAs on small models are the compromise.

Document dual paths so analysts know which table is provisional versus certified. The Semantic Layer and MetricFlow (Extras) can unify definitions across batch and near-real-time sources if both expose the same grain.

For Airbnb-style analytics, reviews do not need second-level latency; listing price monitoring might. Put real-time on the narrow use case; keep mart_fullmoon_reviews on hourly or daily dbt with tests. Reconcile streaming counts to batch totals daily — drift between paths is a common production incident.

When would you use a Python model like dim_review_sentiment instead of SQL?Comparison

Python models fit ML inference, API calls, and transformations SQL expresses poorly (NLP, complex stats, library ecosystems). The course’s sentiment dimension is the pattern: call a model or UDF per batch, write results back as a table.

SQL remains default for joins, aggregations, and anything warehouse-native compute handles cheaply. Python adds operational complexity: cluster sizing, package management, longer compile times, and harder local debugging.

Interview answer: choose Python when the warehouse would ship data out to a notebook anyway; keep the boundary thin and persist results so downstream models stay SQL. See Section 20 for Python model mechanics.

Downstream marts should ref('dim_review_sentiment') like any SQL model — the interviewer is checking you will not embed ML training inside a mart or call APIs row-by-row in SQL UDFs without batching.

How do you decide between views and tables for mart layer models?Cost

Views are free at rest but charge on every query; tables cost storage and build time but amortize compute across consumers. A mart queried fifty times a day by a BI server should usually be a table; a mart used weekly for ad-hoc exploration can be a view.

On Snowflake, also consider dynamic tables and materialized views for middle ground. The course uses views for dimensions and incremental tables for large facts — a sensible default until query patterns prove otherwise.

Measure before optimizing: warehouse query history shows which models dominate spend. Promote hot views to tables or incremental models; demote cold tables to views if freshness allows.

Cite materialization defaults from Section 8: the course leaves dimensions as views and facts as incremental where size warrants it. In an interview, ask how many concurrent BI users hit the mart — that number drives the answer more than dogma.

The warehouse bill doubled after adding snapshots — is that expected?Cost

Often yes, especially timestamp-strategy snapshots that scan the full source each run. raw_listings_snapshot compares every row daily; as listings grow, snapshot cost grows linearly or worse if the warehouse cannot prune.

Mitigate: snapshot only columns and entities that need history, use check strategy when appropriate, reduce frequency, or move high-volume history capture to CDC. Compare snapshot cost to the cost of wrong historical reports — sometimes the bill is correct.

Track bytes scanned per snapshot in query history and alert on week-over-week growth. Snapshots are easy to add and expensive to forget.

Quantify when you can: if raw_listings has 50k rows and the snapshot runs daily with timestamp strategy, you scan 50k rows times 365 times per year — acceptable at course scale, unacceptable at billion-row scale. That is the cost conversation interviewers want.

Would you put raw tables in the dbt project as sources or as models?Fundamentals

Sources. Raw tables are loaded by EL tools; dbt reads them via source() in staging models like src_listings. Declaring them in sources.yml enables freshness, source tests, and lineage without implying dbt owns the load.

Do not turn raw into models unless your team also owns extraction — that blurs ownership and makes loader failures look like transform failures. Staging is the first dbt-owned layer.

Follow-up: document the contract with the loader team (expected columns, load frequency, primary keys). Analytics engineering sits at that boundary in many organisations.

Behavioural and soft skills

Analytics engineering is stakeholder work. These questions test communication and judgment under ambiguity — answer with specific stories where you can.

Use the STAR format (Situation, Task, Action, Result) but keep it under two minutes. If you are early in your career, say so and offer a hypothetical grounded in the Airbnb project: “I have not had this in production yet; here is how I would handle it on mart_fullmoon_reviews.” Honesty plus structure beats inventing a war story.

Questions to ask them. Good candidates ask: Who owns data quality when a source breaks? How is dbt deployed today? Is there a semantic layer? What does on-call look like for the data team? It signals you evaluate employers too.
Tell me about a time a stakeholder disagreed with your definition of a metric?Behavioural

Use STAR: situation (two teams reported different “active listings”), task (align definition without breaking existing dashboards), action (workshop to write SQL-backed definitions, implemented as a documented mart with tests), result (single source adopted, disagreement resolved by reference to docs).

Emphasize curiosity over defensiveness. You asked what decision the metric drives, discovered one side included inactive listings and the other did not, and proposed explicit status filters rather than arguing whose SQL was “right.”

If you lack a work example, walk through the Airbnb case: define “review volume” at review grain versus listing grain and show how each answer changes the number.

Interview tip: end with how you prevented recurrence — updated docs, added a semantic definition in the project overview, or created a certified metric in the semantic layer. Employers hire people who close loops, not people who win arguments.

How do you push back on a request for a report you believe is wrong?Behavioural

Validate the underlying decision, not the requester. “Help me understand what you will do if this number is X” often reveals a join that double-counts or a filter that excludes the segment they care about.

Offer an alternative: prototype the requested query, show the duplication or bias with a small example, and propose a corrected version with the same shape they expect. Document both in the ticket so the choice is explicit.

If they insist after understanding the flaw, deliver with clear caveats in writing and log the exposure description. Your job is informed consent, not veto power on every bad query.

Example: a request to “count listings with reviews” by joining dim_listings_cleansed to fct_reviews without deduplicating listings double-counts multi-review listings. Show the inflated total beside a correct COUNT(DISTINCT listing_id) and let them choose.

Describe how you would onboard a new analyst to a dbt project?Behavioural

Day one: clone repo, dbt debug, run dbt build --select +dim_listings_cleansed, open generated docs and walk the DAG from sources to marts. Day two: fix a trivial doc typo via PR to learn CI. Day three: pair on adding a column with tests.

Point them at project conventions: naming, schema layout, where macros live, how selectors work, and the team’s definition of done (tests, description, owner). Assign a small vertical slice (one source through one mart) rather than throwing them at legacy tech debt.

Reference Section 6 for environment setup and Section 21 for conventions. Good onboarding produces a merged PR in the first week, not just completed videos.

Include a guided tour of dbt docs generate && dbt docs serve — lineage clicks matter more than README prose for analysts. Assign ownership of one model in schema.yml descriptions so they learn documentation is part of shipping.

How do you prioritize when three teams want conflicting model changes?Behavioural

Make trade-offs visible: impact (revenue reporting versus internal ops), effort, risk, and deadline. Escalate to a product owner or data lead with a written option set, not a hallway negotiation.

Look for shared primitives: both teams may need the same host attribute added once upstream rather than two competing marts. Sequencing matters when changes collide on the same model file.

Protect stability: freeze breaking changes near month-end close, batch contract changes, and communicate the roadmap in a public channel so teams see where they queue.

Use concrete prioritisation frameworks: RICE, ICE, or “regulatory deadline first, then revenue-impacting KPIs, then internal convenience.” Analytics engineering interviews are not only SQL — show you can manage a backlog without letting the DAG become everyone’s scratch pad.

Tell me about a time you had to explain a data delay to leadership?Behavioural

Lead with facts and ETA: what is delayed, why (upstream loader missed SLA, warehouse outage, failed test blocking deploy), when you expect recovery, and what is available now (yesterday’s table, manual estimate).

Avoid blaming vendors without a mitigation plan. Describe what you changed so the delay is less likely next time: freshness alert, redundant schedule, or a staged rollback path.

Leadership cares about decisions blocked, not dbt logs. Frame impact in their terms: board deck numbers, campaign launch, or regulatory filing.

If you lack a personal story, describe a plausible Airbnb scenario: source freshness on raw_reviews failed because the loader stalled, you blocked fct_reviews and downstream marts, and the executive dashboard showed yesterday’s data with a banner until recovery.

How do you handle a situation where the business wants a number you cannot defend?Behavioural

Name the gap explicitly: missing source data, undefined grain, or a methodology that violates accounting rules. Provide a range or proxy with documented assumptions rather than a false precision point estimate.

Propose a path to a defensible number: new loader field, snapshot history, stakeholder sign-off on definition, time estimate. If they need something today, ship a labeled provisional metric separate from certified KPIs.

Protect your credibility long term. Analytics engineers who ship numbers they cannot explain become scapegoats when audits fail. Written assumptions in model descriptions and exposures are your defense.

Example: “Average nightly revenue for full-moon listings” when price in raw listings is a string and half the rows lack bookings — ship a provisional metric with documented exclusions, not a precise-looking false decimal in the CEO slide.

How do you explain what you do as an analytics engineer to a non-technical executive?Behavioural

Skip “dbt” in the first sentence. Say you make the numbers people see in dashboards trustworthy and consistent — you define what a listing, a review, and a revenue metric mean once, test them, and document them so teams do not argue about spreadsheets.

Use the Airbnb analogy: three messy raw feeds become clean dimensions, a fact table of reviews, and dashboards everyone can rely on. You are the engineer between the database and the business decision.

If they want one word: “I build and guard the company’s official definitions of its data.” That framing connects to CFO disagreements and metric ownership without jargon.

Certification overlap: Scenario interviews reuse the same distinctions as the dbt Analytics Engineering exam — materialisation choice, test types, incremental versus snapshot, and what dbt does not do. If a scenario stumps you here, revisit Section 22 for structured review.

Recap

Interview preparation is repetition with feedback. Work through one block per sitting; mark complete when you can answer without opening the details and when your follow-ups sound natural.

  • Structure answers: restate, inspect, hypothesize, validate, fix, prevent recurrence.
  • Slow models: compare compiled SQL, incremental predicates, upstream volume, and warehouse query history before changing code.
  • Green tests with wrong numbers mean wrong test coverage or wrong grain — reconcile at business grain, not just primary keys.
  • Metric disagreements are usually definition disagreements; write SQL-backed definitions before debating totals.
  • Put shared logic upstream of marts; wide tables are consumer products, not the only place transformations happen.
  • Tier tests: fast checks in CI, expensive reconciliation on a schedule; tag selectors accordingly.
  • Production changes use expand-contract; never rename or drop columns in place without a migration window.
  • Incremental for event streams; snapshots for mutable history — the Airbnb project uses both for a reason.
  • dbt is batch; real-time needs a deliberate dual-path architecture with certified versus provisional tables.
  • Behavioural answers need impact, actions, and outcomes — use the Airbnb project as a concrete example when you lack war stories.
  • Cross-link course sections for depth; this page trains interview reflexes, not replacement for hands-on practice.
  • Rehearse out loud with a peer; follow-up questions are where scenario interviews are won or lost.
  • Before onsite, run one full debugging narrative and one modelling trade-off narrative end-to-end with timings under five minutes each.
  • Bring the Airbnb DAG mental map: raw → staging → dimensions/facts → marts → exposures.
  • Ask your interviewer what their dbt CI looks like — shows seniority and turns the interview into a conversation.
  • Forty-two scenarios total: seven per theme including follow-up-style prompts on compile errors, ephemeral models, source freshness, and prod promotion.
  • Link debugging answers to Section 16, testing to 11/12, production to 19, snapshots to 10.

Return to the course contents when you want structured lectures; return here when you want to pressure-test judgment.

Suggested study loop: one theme per day (debugging Monday, modelling Tuesday, and so on), five questions per session spoken aloud, then mark complete when you can teach the recap checklist to someone else without notes.
