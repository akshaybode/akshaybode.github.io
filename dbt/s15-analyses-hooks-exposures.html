Analyses

An analysis is a .sql file under analyses/ that dbt parses, compiles with Jinja, and stores in the project graph — but never runs or materialises in the warehouse during dbt run. It is version-controlled ad-hoc SQL: the exploratory query you would paste into a worksheet, kept next to the models it references.

Models create relations. Analyses do not. That distinction matters for cost, scheduling, and CI: dbt run and dbt build skip analyses entirely. You execute the compiled SQL yourself in the warehouse UI, a notebook, or a BI tool after reviewing what dbt generated.

BigQuery and Postgres behave the same at the dbt layer. Analyses compile to SQL strings under target/compiled/ regardless of adapter. The course uses Snowflake; on BigQuery the compiled path is still target/compiled/airbnb/analyses/, and you paste the result into the BigQuery console.

full_moon_no_sleep.sql

The course hypothesis (stated tongue-in-cheek in the lecture title) is whether Airbnb guests leave worse reviews during a full moon. Rather than building a mart for a throwaway question, the instructor adds an analysis that aggregates mart_fullmoon_reviews by is_full_moon and review_sentiment.

WITH fullmoon_reviews AS (
    SELECT * FROM {{ ref('mart_fullmoon_reviews') }}
)
SELECT
    is_full_moon,
    review_sentiment,
    COUNT(*) as reviews
FROM
    fullmoon_reviews
GROUP BY
    is_full_moon,
    review_sentiment
ORDER BY
    is_full_moon,
    review_sentiment

Every construct here is standard dbt SQL: a CTE reading from {{ ref('mart_fullmoon_reviews') }}, then a grouped aggregation. Because mart_fullmoon_reviews already joins reviews to full-moon dates (see Section 9), the analysis stays thin — it asks a business question without adding another permanent table.

dbt compile and where compiled SQL lives

To see warehouse-ready SQL without executing it, run dbt compile. dbt resolves all Jinja, replaces ref() with fully-qualified relation names for your target, and writes one file per analysis under target/compiled/<project>/analyses/.

When to use an analysis versus a model. If the result should refresh on a schedule, be tested, and appear in the DAG as a queryable table, build a model (often a mart). If the SQL is exploratory, tied to a one-time investigation, or a scratchpad for an analyst, use an analysis. Promote to a model when stakeholders ask for it weekly.

Storing analysis results without a model

Teams sometimes paste compiled analysis SQL into a worksheet and save results as a CSV for a slide deck. That output is not tracked by dbt. If the investigation recurs, either keep re-running the analysis (cheap when the upstream mart is small) or promote to a model. Avoid creating "temporary" tables by hand in the warehouse without a dbt model to manage them — they become orphan relations nobody dares drop.

Analyses versus singular tests

Both live outside models/ and compile without materialising by default, but tests assert something (dbt test fails the run when rows return) while analyses produce a result set for human inspection. The course's tests/dim_listings_minimum_nights.sql from Section 11 is a singular test; full_moon_no_sleep.sql is read-only exploration with no pass/fail semantics.

Upstream context: mart_fullmoon_reviews

The analysis depends on a mart built in Section 9 that joins fact reviews to a seed of full-moon calendar dates. By Section 15 the mart may be configured as a microbatch incremental model in the custom mart schema, but the analysis file does not change — ref('mart_fullmoon_reviews') always resolves to whatever relation dbt currently builds.

WITH fct_reviews AS (
    SELECT * FROM {{ ref('fct_reviews') }}
),
full_moon_dates AS (
    SELECT * FROM {{ ref('seed_full_moon_dates') }}
)

SELECT
  r.*,
  CASE
    WHEN fm.full_moon_date IS NULL THEN 'not full moon'
    ELSE 'full moon'
  END AS is_full_moon
FROM
  fct_reviews r
  LEFT JOIN full_moon_dates fm
  ON (TO_DATE(r.review_date) = DATEADD(DAY, 1, fm.full_moon_date))

The join uses DATEADD(DAY, 1, fm.full_moon_date) because the seed stores the astronomical full-moon instant while reviews are dated on the calendar day guests checked out. The analysis does not need to know that detail — it reads the finished is_full_moon label. That separation is deliberate: business rules live in the mart; the analysis asks a question on top.

If you accidentally include analyses in a large dbt build selector union, dbt skips them without error. They still appear in manifest.json under nodes with keys like analysis.airbnb.full_moon_no_sleep, which external catalog tools can ingest for dependency tracking even when the SQL never ran.

Everyday analogy — a model is a recipe the kitchen cooks every night; an analysis is a recipe card in the binder for when the chef wants to experiment on a slow Tuesday. The ingredients (ref() targets) are the same; only the commitment to serving it nightly differs.

Hooks

Hooks are SQL (or macro calls) dbt executes at defined points in a run: before or after individual models, or once at the start or end of the entire invocation. The course uses them to create an audit log table and insert one row per model built — a pattern teams extend for grants, logging, and housekeeping.

HookScopeWhen it runsTypical use
pre-hookSingle modelBefore the model's main DDL/DMLTruncate staging, set session vars, acquire locks
post-hookSingle modelAfter the model succeedsAudit rows, secondary indexes, ANALYZE
on-run-startEntire invocationOnce before any modelCreate scratch tables, log run start
on-run-endEntire invocationOnce after all models (success or partial)Notify Slack, vacuum, aggregate run stats

on-run-start: create the audit table

The course adds a project-level on-run-start hook in dbt_project.yml that creates an audit_log table in the target schema if it does not exist. This runs once at the beginning of every dbt run, dbt build, or any command that executes models.

on-run-start:
  - "CREATE TABLE IF NOT EXISTS {{ target.schema }}.audit_log ( model_name STRING, run_timestamp TIMESTAMP )"

The hook is a list of strings, each treated as a SQL statement (or macro invocation). dbt sends them to the warehouse in order. Using IF NOT EXISTS makes the hook idempotent: the second run does not fail if the table is already there.

on-run-start runs even when you select one model. Any invocation that builds models triggers it. Keep start hooks lightweight — a heavy scan here adds latency to every partial run.

post-hook: log each model name

Under models.airbnb, the course sets a +post-hook that inserts into audit_log after every model in the project succeeds. The + prefix merges this config with folder-level and model-level settings.

on-run-start:
  - "CREATE TABLE IF NOT EXISTS {{ target.schema }}.audit_log ( model_name STRING, run_timestamp TIMESTAMP )"

models:
  airbnb:
    +grants:
      select: ["transform", "reporter"]
    +post-hook:
      - "INSERT INTO {{ target.schema }}.audit_log VALUES ('{{ this }}', CURRENT_TIMESTAMP)"
    +materialized: view
    dim:
      +materialized: table
    src:
      +materialized: ephemeral
    fct:
      +tags: ['fact']

{{ this }} inside a post-hook resolves to the relation identifier of the model that just finished — the same object you would reference when configuring incremental strategies. Each successful model append one audit row with its name and a timestamp.

dbt run (audit side effect)

dbt run --select dim_listings_cleansed

15:22:02  1 of 1 START sql table model DEV.dim_listings_cleansed .............. [RUN]
15:22:04  1 of 1 OK created sql table model DEV.dim_listings_cleansed .......... [SUCCESS 1 in 1.84s]

After this run, querying SELECT * FROM <your_schema>.audit_log ORDER BY run_timestamp DESC shows a row for dim_listings_cleansed. Failed models do not run post-hooks on the failed step — dbt stops the model's hook chain when the main statement errors.

Pre-hooks and on-run-end

The course focuses on on-run-start and post-hook, but the same mechanics apply to pre-hook (list under a model or folder config) and on-run-end (project-level list like on-run-start). Common production patterns:

  • pre-hook — DELETE FROM staging WHERE load_date = CURRENT_DATE before reloading a daily staging model.
  • post-hook — GRANT SELECT ON {{ this }} TO ROLE analyst when adapter-native grants are not used (prefer the grants config when supported).
  • on-run-start — create temp tables, set warehouse size via session parameter (adapter-specific).
  • on-run-end — insert a summary row into an operations table with run_started_at, model count, and status from run_results via a macro.

Hooks run in the same transaction context as the model on some adapters and separately on others. On Snowflake, a failed post-hook can leave the model built but the hook errored — read adapter docs before putting business-critical logic only in hooks. Prefer idempotent statements and test hooks in dev first.

Hooks as macro calls

Hook entries can invoke macros: - "{{ log_model_run() }}". That keeps complex logic in macros/ and leaves YAML readable. Section 16 expands logging macros; the audit pattern here is the lightweight precursor.

Config precedence for hooks

Hooks merge the same way as materialization config. A model file can override project defaults:

Multiple hooks in a list run sequentially. If both project and model define post-hook, dbt merges lists unless the model uses a config that replaces rather than extends — check the docs for your dbt version when mixing +post-hook (append) with inline config(post_hook=...) in SQL.

  post_hook=[]

on-run-end for run summaries

The course does not add on-run-end, but it is the natural place for a single INSERT summarising the whole run instead of one row per model. A macro can read results from the context dbt passes to on-run-end hooks and write aggregate status. That reduces warehouse chatter compared to fifty per-model INSERTs on large projects.

on-run-end:
  - "{{ log_run_summary() }}"

Grants

dbt can apply warehouse privileges when it creates or replaces a relation. The course grants SELECT on every model to the transform and reporter roles — aligning dbt-managed objects with the Snowflake roles set up in Section 6 for the transform pipeline and Preset read access.

models:
  airbnb:
    +grants:
      select: ["transform", "reporter"]

The +grants config sits beside +materialized under models.airbnb, so all models inherit it unless overridden. Supported keys depend on the adapter; on Snowflake, select maps to GRANT SELECT ON TABLE/VIEW ... TO ROLE .... The reporter role was created for the Preset service user in the Snowflake setup script:

CREATE ROLE REPORTER;

CREATE USER PRESET
  LOGIN_NAME='preset'
  TYPE=SERVICE
  RSA_PUBLIC_KEY="<<Add Your Public Key File's content here>>"
  DEFAULT_WAREHOUSE='COMPUTE_WH'
  DEFAULT_ROLE=REPORTER
  DEFAULT_NAMESPACE='AIRBNB.DEV';

GRANT ROLE REPORTER TO USER PRESET;
GRANT SELECT ON ALL TABLES IN SCHEMA AIRBNB.DEV to ROLE REPORTER;
GRANT SELECT ON FUTURE TABLES IN SCHEMA AIRBNB.DEV to ROLE REPORTER;

Without +grants, new models would inherit only default role ownership (typically the role in your profile). BI users would lack access until someone ran manual GRANTs. Applying grants on build keeps permissions in git next to the model definitions.

ApproachProsCons
+grants in dbt_project.ymlVersion controlled; applied every build; per-folder overridesAdapter-specific keys; re-grants on every full refresh
Snowflake FUTURE GRANTsOne-time admin setupNot in git; easy to drift from dbt project intent
post-hook GRANT SQLFull SQL flexibilityHarder to read; duplicates adapter logic
IAM / data catalog productCentral policyOutside dbt; may fight dbt grants if both apply
BigQuery uses dataset ACLs and IAM, not GRANT ROLE. dbt-bigquery supports a different grants shape (roles/bigquery.dataViewer etc.). The course pattern is Snowflake-native; translate role names to IAM bindings on BigQuery datasets.

Config precedence for grants

Like materialization, grants merge from project → folder → model file config(). A sensitive mart can narrow grants in its SQL file while the project default stays broad. If grants seem ignored, check whether the model uses a custom schema macro from Section 19 — grants apply to the built relation in that schema.

How dbt grants relate to Section 6 Snowflake setup

The bootcamp Snowflake script creates two roles relevant here. TRANSFORM is the dbt developer and CI role with broad DDL rights. REPORTER is read-only for BI. The dbt profile typically uses TRANSFORM (or a personal role with transform privileges) to build models. Preset connects as PRESET user with default role REPORTER.

When dbt builds a model with +grants: { select: ["transform", "reporter"] }, Snowflake receives GRANT statements after CREATE. That complements the script's GRANT SELECT ON FUTURE TABLES for REPORTER — dbt grants cover the specific relation immediately, while future grants cover objects created outside dbt. Teams standardise on one mechanism to avoid redundant GRANT churn in query history.

analysis-paths: ["analyses"]
test-paths: ["tests"]

macro-paths: ["macros"]

Verify grants after your first hooked run. In Snowflake, run SHOW GRANTS TO ROLE REPORTER or inspect the table's grants. If Preset later returns "insufficient privileges", the fix is almost always a missing SELECT grant or wrong schema in the connection, not the chart definition.

Building a dashboard in Preset

dbt builds the tables; a BI tool consumes them. The course connects Preset (hosted Apache Superset) to Snowflake using the same credentials as your local profile, then charts mart_fullmoon_reviews to explore full-moon review patterns visually — the same data the analysis aggregates in SQL.

Snowflake credentials for Preset

Preset needs a database connection: account identifier, user, role, warehouse, database, and schema. The instructor copies values from the local dbt profile rather than retyping from memory.

Read profiles.yml

cat ~/.dbt/profiles.yml
# Mac / Linux / Windows PowerShell

type %USERPROFILE%\.dbt\profiles.yml
# Windows CMD alternative

From profiles.yml, map fields into Preset's Snowflake connection form: account, user (often the PRESET service user rather than your personal login), role (REPORTER), warehouse, database (AIRBNB), schema (DEV or your target schema). The course uses key-pair auth for the service user; Preset accepts the public key registration matching the Snowflake user definition.

Preset workflow (course demonstration)

  1. Create a Preset workspace (or use the course trial instance) and add a Snowflake database connection with the reporter credentials.
  2. Test the connection — Preset runs a lightweight query; failures are usually wrong account URL, role not granted, or missing warehouse usage.
  3. Add a dataset pointing at AIRBNB.<schema>.MART_FULLMOON_REVIEWS (or browse schemas after connection).
  4. Create charts — for example a bar chart of review counts by is_full_moon, or sentiment breakdown filtered to full-moon nights.
  5. Assemble a dashboard combining listing metrics from dim_listings_w_hosts and full-moon review charts from the mart.
  6. Copy the dashboard URL for the exposure declaration in the next section.

Chart ideas for mart_fullmoon_reviews

The course builds at least one chart on the full-moon mart. Concrete starting points that match the analysis logic:

  • Grouped bar chart — X axis is_full_moon, series review_sentiment, metric COUNT(*). Mirrors full_moon_no_sleep.sql visually.
  • Big number — count of reviews where is_full_moon = 'full moon' and sentiment is negative; good for a headline KPI tile.
  • Time series — reviews per week coloured by full-moon flag; needs review_date from the mart's underlying fact columns.
  • Table — raw sample rows for executives who want to read individual reviews on full-moon nights.

Combine with dim_listings_w_hosts on a dashboard for listing- and host-level filters (room type, price band) while full-moon metrics update in a separate chart row. The exposure in the next section declares both models as dependencies because the executive dashboard uses both datasets.

Tableau, Looker, and Metabase follow the same pattern. dbt does not care which BI tool queries the mart. Preset is the course choice because it connects quickly to Snowflake with a service user; the architecture is always "dbt builds, BI reads".

Exposures

An exposure declares a downstream consumer of dbt models — a dashboard, application, or ML pipeline — in YAML. It does not run in the warehouse. It adds nodes and edges to the lineage graph so dbt docs and manifest consumers show what breaks when a model changes.

The course file is models/dashboards.yml (plural). It defines one exposure named executive_dashboard that links to the Preset URL and lists model dependencies.

Why exposures appear in the DAG

During parsing, dbt creates exposure nodes and edges from each entry in depends_on to the referenced models. In dbt docs serve, the lineage graph shows the exposure on the right with arrows from dim_listings_w_hosts and mart_fullmoon_reviews. Selecting a model and viewing downstream impact now includes the executive dashboard — something that would be invisible if the BI tool were only documented in a wiki.

Exposures do not participate in dbt run ordering — they are metadata. They do appear in dbt ls --resource-type exposure and in manifest JSON for tools like Metaplane, Monte Carlo, or internal impact scripts.

Certification: know that exposures are declared in YAML, use depends_on with ref(), appear in lineage as consumer nodes, and are not executed by dbt. Distinguish them from analyses (SQL files) and models (materialised relations).

depends_on and incomplete graphs

Only declared dependencies draw edges. If the Preset dashboard also queries fct_reviews directly but you omit it from depends_on, the docs graph under-reports blast radius. Teams audit BI query logs or use catalog integrations to reconcile. When in doubt, list every model the dashboard dataset references.

Exposures can depend on sources as well: - source('airbnb', 'raw_listings'). That is rare for dashboards fed only from marts but useful when documenting apps reading raw landing tables.

Exposure types and maturity

The type field categorises the consumer for docs filtering and for teams ingesting manifest JSON. Valid values include dashboard, notebook, analysis, ml, and application. The course uses dashboard for the Preset executive board.

maturity: low signals the dashboard is new or experimental — it renders as metadata in the docs UI and helps prioritise which consumers need notice before breaking schema changes. Raise to high when the dashboard is executive-critical and listed in change-management runbooks.

Owner metadata and governance

The owner block with name and email does not send mail automatically. It surfaces in the docs UI so an engineer doing impact analysis knows whom to notify before renaming mart_fullmoon_reviews columns. Some teams add meta: on exposures for Slack channels or PagerDuty services, ingested by catalog products the same way model meta is.

The biggest waste is a project-wide post-hook that writes one row per model on every CI slim run. Scope hooks with folder config: audit only production marts, not ephemeral staging rebuilt twenty times a day in pull request jobs.

Traps that catch people

  • Expecting analyses to run on dbt run — they never materialise; only compile unless you execute SQL manually. CI jobs that only run dbt build never touch analyses.
  • ref() typo in analysis — compile fails the same as in models; the error points at the analysis file, which some teams forget is in the graph.
  • post-hook runs on view replacement — each full refresh of a table fires the hook; incremental models fire after each successful merge, which can multiply audit rows.
  • audit_log string quoting — model names with quotes in hook SQL break INSERT statements; use macros to escape or log relation names from adapter.get_relation.
  • Grants to non-existent roles — run fails at GRANT time on Snowflake; create roles in infra before adding to YAML.
  • REPORTER role without future grants — tables built before FUTURE GRANT setup may lack access; dbt +grants fixes new builds but not old tables until rebuild.
  • Preset connected as TRANSFORM — over-privileged BI connection violates least privilege; use REPORTER user from setup script.
  • Exposure URL rot — dashboard moved in Preset but YAML still points at old link; docs mislead during incidents.
  • depends_on missing hidden dependencies — dashboard uses SQL with joins to undeclared models; lineage under-states impact.
  • on-run-start in parse-only CI — if a job mistakenly runs models against prod with a destructive start hook, damage is project-specific; review hook SQL in code review.
  • Analysis promoted without tests — copying analysis SQL into a model without adding tests ships exploratory logic to production.
  • Hook order with multiple entries — pre-hooks run in list order; later hooks see effects of earlier ones; order matters for truncate-then-load patterns.

Production patterns

Mature teams keep exploratory SQL in analyses/ with a naming convention (investigation_YYYYMMDD_topic.sql) and delete or promote within two sprints. Promotion means a new model under models/mart/, tests, and removal of the analysis to avoid duplicate logic.

Hooks centralise in macros invoked from thin YAML lists; production uses on-run-end to emit structured JSON logs to an observability table rather than per-model INSERTs. Grants in YAML cover dev and CI schemas; production relies on Terraform-managed Snowflake roles plus optional dbt grants only on marts exported to BI.

Pattern: exposures owned by domain

Each dashboard YAML entry lists an owner email matching a Slack channel. Impact analysis from manifest feeds weekly stale-dashboard reviews.

Anti-pattern: hooks as business logic

Complex transformations hidden in post-hooks are invisible in compiled model SQL and break lineage. Keep hooks operational; keep business rules in models.

models:
  airbnb:
    mart:
      +post-hook:
        - "{{ log_mart_build(this) }}"

Cross-adapter notes

Hooks execute arbitrary SQL strings; syntax must match your warehouse. The course audit table uses Snowflake types (STRING, TIMESTAMP). On Postgres you would use TEXT and TIMESTAMPTZ; on BigQuery you might log to a partitioned table in a dedicated dataset instead of {{ target.schema }}.

Grants config keys differ: Snowflake uses role names; BigQuery maps to IAM roles. Exposures and analyses behave identically across adapters because they are parse-time metadata or compile-only SQL.

When to skip hooks entirely

Serverless warehouses, read-only CI roles, and federated projects sometimes cannot run DDL in hooks. Alternatives: Terraform owns grants and audit tables; dbt Cloud job webhooks emit run metadata; observability platforms ingest run_results.json from target/ after each invocation. The course hooks teach the mechanism; production often moves logging out of warehouse INSERTs for cost and separation of concerns.

Interview questions

Answer each one out loud before opening it.

What is a dbt analysis and how is it different from a model?Fundamentals

An analysis is a .sql file under analyses/ (configured by analysis-paths). dbt parses and compiles it with Jinja, resolves ref(), and writes compiled SQL to target/compiled/, but never creates a warehouse relation during dbt run.

A model materialises (table, view, incremental, etc.) and participates in the build schedule. Use analyses for exploratory, version-controlled SQL; promote to a model when the logic needs tests, scheduling, and a stable relation name.

How do you run or inspect an analysis?Fundamentals

Run dbt compile (optionally --select analysis_name). Open the file under target/compiled/<project>/analyses/ and execute that SQL in your warehouse client. List analyses with dbt ls --resource-type analysis.

There is no dbt run --select analysis materialisation step. The analysis node appears in manifest.json for lineage but not in catalog.json unless you manually create a relation from the compiled SQL.

Explain the four hook types and when you would use each.Design

pre-hook and post-hook attach to individual models (or folders via config) and run immediately before or after that model's main statement. Use for model-scoped setup or audit rows tied to a specific relation.

on-run-start and on-run-end are project-level lists that run once at the beginning or end of an invocation. Use for creating shared scratch objects, run-level logging, or notifications after all models finish.

What does the course audit_log pattern demonstrate?Production

on-run-start creates audit_log in {{ target.schema }} if missing. A project-wide +post-hook inserts (model_name, run_timestamp) after each successful model build using {{ this }} for the relation name.

It shows hooks as operational metadata capture without changing model SQL. Production teams often replace raw INSERT hooks with macros writing to an observability schema or streaming logs.

How do grants in dbt_project.yml work on Snowflake?Production

The +grants: config under a project or folder instructs dbt to emit privilege statements when building relations. select: ["transform", "reporter"] grants SELECT to those roles on each created table or view.

Roles must exist beforehand. This keeps BI access (REPORTER) and transform access in git. Adapter support and grant keys differ on BigQuery (IAM) and Postgres (role names).

What is an exposure and why declare one?Fundamentals

An exposure is a YAML-declared downstream consumer (dashboard, app, notebook) with a type, optional url, owner, and depends_on list referencing models or sources via ref() / source().

It does not execute in the warehouse. It adds consumer nodes to the lineage graph for impact analysis and documentation, linking dbt models to the Preset dashboard that reads them.

Your lineage graph shows a dashboard exposure but changing a model did not alert the owner. Why?Gotcha

Exposures are documentation metadata unless integrated with an external tool that monitors manifest changes. dbt docs shows the dependency edge but sends no notifications by itself.

Also verify depends_on lists every model the dashboard actually queries. Undeclared dependencies break the graph silently. Owner email in YAML is for humans reading docs, not automated alerting.

When would you promote an analysis to a model?Design

When the SQL must run on a schedule, be tested in CI, grant SELECT to BI roles automatically, and appear as a stable relation for Preset or other tools. Repeated manual execution of the same compiled analysis is a signal to promote.

Promotion steps: create models/mart/your_model.sql with the analysis logic, add tests in schema.yml, run dbt build, update exposures, delete or archive the analysis file.

How do hooks interact with failed model runs?Troubleshooting

If a model's main statement fails, its post-hook does not run for that model. Pre-hook may have already executed depending on adapter transaction boundaries. Dependent downstream models skip unless force-run.

on-run-end still runs after the invocation completes (with partial success), which is why teams put failure summaries there rather than assuming every post-hook fired.

Compare singular tests, analyses, and ephemeral models.Comparison

Singular tests assert data quality; failure fails dbt test. Analyses explore data; no pass/fail. Ephemeral models are models inlined as CTEs; they run as dependencies but are not queryable relations.

All three can use ref(). Only models (non-ephemeral) and seeds materialise to named tables or views consumers query directly.

How would you connect a BI tool to dbt-built Snowflake tables?Production

Create a least-privilege service user and role (REPORTER in the course), grant SELECT on marts (via dbt +grants and/or Snowflake FUTURE GRANTs), run models to create relations, then configure the BI tool with account, role, warehouse, database, schema from profiles or infra docs.

Declare the dashboard as an exposure with depends_on for lineage. dbt does not push charts to Preset; it only builds tables the tool queries.

What happens if on-run-start and post-hook both touch audit_log?SQL

Start hook ensures the table exists once per invocation. Each successful model post-hook appends a row. Order is guaranteed: start before any model, post after each model. A run building ten models yields up to ten INSERTs plus one CREATE IF NOT EXISTS.

Failed CREATE (permissions) aborts the run early. Failed INSERT (constraint, typo in hook SQL) fails that model's hook step; fix hook SQL or table schema in dev before promoting.

Can an analysis use source() instead of ref()?Fundamentals

Yes. Analyses support the same Jinja functions as models: ref(), source(), var(), and macros. Lineage edges appear for declared sources and refs when you compile or parse.

Prefer ref() for dbt-managed models so the analysis respects environment schema routing. Querying raw sources directly in an analysis bypasses staging cleanses and duplicates the hard-coding problem ref() exists to prevent.

Why does the course grant SELECT to both transform and reporter?Design

TRANSFORM is the build role; it already owns or can access objects it creates. Including it in grants documents intent explicitly and covers edge cases where ownership differs (shared schemas, post-build role switching).

REPORTER is the BI role Preset uses. Without it in grants, each new mart would need manual GRANTs before dashboards work. Listing both in git keeps transform and consume permissions auditable in the same pull request as the model.

Recap

  • Analyses live in analyses/ (configured by analysis-paths); they compile but do not materialise on dbt run.
  • dbt compile writes warehouse-ready SQL to target/compiled/.../analyses/; you execute it manually.
  • full_moon_no_sleep.sql aggregates mart_fullmoon_reviews by full-moon flag and sentiment.
  • pre-hook / post-hook run before and after each model; on-run-start / on-run-end run once per invocation.
  • The course creates audit_log on run start and inserts one row per successful model in a post-hook using {{ this }}.
  • +grants: { select: [...] } applies SELECT privileges when models build; course grants transform and reporter.
  • REPORTER role and PRESET user connect BI with least privilege to AIRBNB.DEV tables.
  • Preset connects to Snowflake using profile credentials; charts query physical marts such as mart_fullmoon_reviews.
  • Exposures in YAML declare dashboards or apps with depends_on refs; they appear in the lineage graph but do not run in dbt.
  • models/dashboards.yml defines executive_dashboard depending on dim_listings_w_hosts and mart_fullmoon_reviews.
  • Complete depends_on lists keep impact analysis accurate; undeclared BI dependencies are invisible to dbt.
  • Promote analyses to models when logic needs tests, scheduling, and stable relations for production BI.
