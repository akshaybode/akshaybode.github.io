What materializations are

A materialization is dbt's answer to one question: after this model's SELECT runs, what object should exist in the warehouse? dbt wraps your SQL in the appropriate DDL — CREATE VIEW, CREATE TABLE AS, an incremental merge, or nothing at all for ephemeral — and manages rebuilds on subsequent runs.

You declare a materialization with the {{ config() }} macro at the top of a model file, or with folder-level defaults in dbt_project.yml. If you set neither, dbt defaults to view.

The four materializations at a glance

MaterializationObject in warehouseRebuilt whenTypical use
viewA view (virtual, no stored rows)Replaced on every dbt run that selects the modelLight transforms queried occasionally; staging layers in dev
tableA physical tableDrop-and-recreate (or truncate-and-insert, adapter-dependent) on every runDimensions, marts, anything dashboards hit repeatedly
ephemeralNothing — logic is inlined as a CTE in downstream modelsRecompiled into parent SQL every runStaging models you never query directly
incrementalA table that grows over timeFirst run builds the full table; later runs append or merge new rows onlyLarge append-only facts like reviews
Warehouse differences. On Snowflake, a table model typically uses CREATE OR REPLACE TABLE … AS SELECT. BigQuery uses CREATE OR REPLACE TABLE as well. Postgres and Redshift behave similarly. The exact DDL is adapter-specific; dbt abstracts it so your model file stays the same. Ephemeral inlining works identically on every adapter because it happens at compile time, before SQL reaches the warehouse.

Four materializations as design choices

view

Defers compute to query time. dbt runs a lightweight CREATE OR REPLACE VIEW. Best when data is small, logic changes often, or few consumers read the model directly.

table

Pays compute at build time and stores rows. Every dbt run rebuilds the whole relation unless you later switch to incremental. Best for dimensions and marts that dashboards hit on every refresh.

ephemeral

No warehouse object. SQL is pasted into parents as a CTE. Best for staging and private intermediate logic that should never appear in a schema browser or BI tool.

incremental

A table that grows. First run is a full load; later runs process a subset you define with is_incremental() and a strategy. Best for large append-mostly facts like reviews, events, or logs.

Materialization is separate from folder naming. A file in models/fct/ is not automatically incremental — it inherits the project default (view) until you set folder or model config. That is why fct_reviews carries an explicit {{ config(materialized='incremental') }} block even though it lives in the fact folder.

View materialization

A view stores no data. dbt runs CREATE OR REPLACE VIEW … AS (your SELECT) and the warehouse executes your logic fresh every time someone queries the view. Build time is cheap; query time is not.

The dim/ folder defaults to table in this project, but dim_listings_cleansed overrides that to view. The instructor's reasoning: listings are small enough that a full rebuild is fast, and a view keeps dev iterations instant while you are still changing the cleansing logic in Section 7.

{{
  config(
    materialized = 'view',
    event_time='created_at'
  )
}}
WITH src_listings AS (
    SELECT * FROM {{ ref('src_listings') }}
)
SELECT
  listing_id,
  listing_name,
  room_type,
  CASE
    WHEN minimum_nights = 0 THEN 1
    ELSE minimum_nights
  END AS minimum_nights,
  host_id,
  REPLACE(
    price_str,
    '$'
  ) :: NUMBER(
    10,
    2
  ) AS price,
  created_at,
  updated_at
FROM
  src_listings

Because src_listings is ephemeral, the compiled SQL for dim_listings_cleansed inlines the staging CTE rather than reading a SRC_LISTINGS relation. You can verify this by opening target/compiled/airbnb/models/dim/dim_listings_cleansed.sql after dbt compile.

When to choose view

  • The model is small or the upstream data is small, so recomputing on read is acceptable.
  • You are iterating on logic in development and want fast dbt run cycles.
  • Few consumers query the model directly; most traffic goes through a downstream table or mart.
  • You want always-fresh results without managing incremental watermarks.

When view is the wrong choice

  • A BI dashboard hits this model on every page load and the underlying join is expensive.
  • The model sits ten layers deep in a chain of views — the warehouse may re-scan sources repeatedly.
  • You need to run tests or snapshots against a stable relation name with predictable row counts at build time.
Views defer cost to query time. Building dim_listings_cleansed as a view costs almost nothing. But every SELECT * FROM dim_listings_cleansed re-executes the full pipeline including inlined ephemeral CTEs. If Tableau refreshes hourly against a view stacked on views, you pay that compute on every refresh.

What the compiled view looks like

After dbt compile --select dim_listings_cleansed, open target/compiled/airbnb/models/dim/dim_listings_cleansed.sql. Because src_listings is ephemeral, the output is one query with nested CTEs — no reference to a SRC_LISTINGS table:

WITH raw_listings AS (
    SELECT * FROM AIRBNB.RAW.RAW_LISTINGS
),
src_listings AS (
    SELECT
        id AS listing_id,
        name AS listing_name,
        …
    FROM raw_listings
)
SELECT
    listing_id,
    listing_name,
    room_type,
    …
FROM src_listings

On BigQuery and Databricks the shape is the same; only the raw source reference changes to your project's source or hard-coded table name until Section 9 introduces source() for src_reviews.

Verifying the object type in Snowflake

After a successful run, confirm the relation is a view, not a table:

SHOW VIEWS LIKE 'DIM_LISTINGS_CLEANSED' IN SCHEMA AIRBNB.DEV;
-- or
SELECT table_type FROM AIRBNB.INFORMATION_SCHEMA.TABLES
WHERE table_schema = 'DEV' AND table_name = 'DIM_LISTINGS_CLEANSED';

Expected result: VIEW. If you see BASE TABLE, the folder default won over your model config or the override was removed from the SQL file.

Certification: know that dbt's default materialization is view, and that a model-level {{ config() }} overrides folder and project defaults. dim_listings_cleansed is the canonical example in this course.

Table materialization

A table materialization persists rows physically. dbt rebuilds the entire table on every run (unless you later switch to incremental). Query time is fast because the work already happened at build time.

Folder defaults in dbt_project.yml

Rather than repeating {{ config(materialized='table') }} in every dimension file, the project sets folder-level defaults. Models under models/dim/ inherit table automatically.

models:
  airbnb:
    +grants:
      select: ["transform", "reporter"]
    +post-hook:
      - "INSERT INTO {{ target.schema }}.audit_log VALUES ('{{ this }}', CURRENT_TIMESTAMP)"
    +materialized: view
    dim:
      +materialized: table
    src:
      +materialized: ephemeral
    fct:
      +tags: ['fact']

The hierarchy here is deliberate. Project default: everything is a view unless you say otherwise. Staging (src/): ephemeral, because nobody should query staging directly. Dimensions (dim/): table, because dimensions are joined constantly and should be fast to read. Facts (fct/): no materialization set at folder level — fct_reviews sets its own config inline.

dim_hosts_cleansed inherits the folder default and builds as a table:

Grants and post-hooks ride along

Folder configs are not limited to materialization. The same models: airbnb: block grants SELECT to the transform and reporter roles and appends an audit row after every model build. These apply to every model unless overridden — another reason to centralise defaults in dbt_project.yml.

Start as view, promote to table. A common team convention is to default new models to view, measure which ones are slow or heavily queried, and promote only those to table or incremental. The course inverts that for dim/ because dimensions are always join targets, but the principle holds for marts and one-off analyses.

Why dim/ defaults to table but one dimension stays a view

The instructor sets dim/ to table because dimensions are join targets: BI tools, wide tables like dim_listings_w_hosts, and fact models all read them repeatedly. Materialising once at build time keeps downstream queries fast.

dim_listings_cleansed is the exception because listings cleansing logic was still evolving in Section 7. A view makes every dbt run cheap while you iterate on the CASE and REPLACE expressions. Once the logic stabilises, many teams would promote it to table — the course keeps it as view to demonstrate overrides.

Table rebuild mechanics on Snowflake

When dbt builds a table model on Snowflake, the adapter typically runs CREATE OR REPLACE TABLE … AS (SELECT …). The entire previous table is replaced atomically. There is no in-place update of rows — a "table" materialization always reprocesses every row in your SELECT on every run.

That is the key motivation for incremental facts: if fct_reviews were a table, each nightly run would scan all of raw_reviews and rewrite every review row even when only a handful of new reviews arrived. On Postgres or Redshift the DDL wording differs slightly, but the full-rebuild semantics are the same.

dbt run --select dim_listings_w_hosts

dbt run --select dim_listings_w_hosts
09:22:01  Running with dbt=1.11.12
09:22:03  1 of 1 START sql table model DEV.dim_listings_w_hosts ............... [RUN]
09:22:06  1 of 1 OK created sql table model DEV.dim_listings_w_hosts .......... [SUCCESS 1 in 2.88s]
09:22:06  Completed successfully

The post-hook from dbt_project.yml fires after the table is created, inserting one row into audit_log with the model name and timestamp. That hook runs regardless of materialization type — views, tables, and incrementals all get an audit entry in this project.

Ephemeral materialization

Ephemeral models never become warehouse objects. dbt inlines their SQL as a WITH clause (a CTE) inside every downstream model that references them via ref(). There is nothing to SELECT FROM in Snowflake, nothing to document as a separate node in the catalog, and nothing to test with a direct ref() in a singular test.

The src/ folder holds staging models — thin renames and casts on raw sources. The instructor materializes them as ephemeral because staging is an implementation detail; analysts should query dimensions and facts, not staging.

WITH raw_listings AS (
    SELECT
        *
    FROM
        AIRBNB.RAW.RAW_LISTINGS
)
SELECT
    id AS listing_id,
    name AS listing_name,
    listing_url,
    room_type,
    minimum_nights,
    host_id,
    price AS price_str,
    created_at,
    updated_at
FROM
    raw_listings
WITH raw_reviews AS (
    SELECT
        *
    FROM
        {{ source('airbnb', 'reviews') }}
)
SELECT
    listing_id,
    DATE AS review_date,
    reviewer_name,
    comments AS review_text,
    sentiment AS review_sentiment
FROM
    raw_reviews

When fct_reviews calls {{ ref('src_reviews') }}, dbt does not generate FROM DEV.SRC_REVIEWS. It pastes the entire src_reviews query as a named CTE in the compiled output.

What dbt generates

Conceptually, the compiled incremental model looks like this (simplified):

WITH raw_reviews AS (
    SELECT * FROM AIRBNB.RAW.RAW_REVIEWS
),
src_reviews AS (
    SELECT
        listing_id,
        DATE AS review_date,
        reviewer_name,
        comments AS review_text,
        sentiment AS review_sentiment
    FROM raw_reviews
)
-- incremental logic wraps the SELECT below
SELECT … FROM src_reviews WHERE review_text IS NOT NULL …

Benefits of ephemeral staging

  • Cleaner warehouse. Your dev schema contains business-ready tables (dim_*, fct_*), not fifteen copies of lightly renamed raw columns.
  • No stale staging tables. A table staging layer can fall behind if someone runs dbt run --select dim_listings_cleansed without rebuilding staging first. Ephemeral staging is always current because it compiles into the parent.
  • Lineage still works. The DAG shows src_reviews → fct_reviews even though no SRC_REVIEWS object exists.

Drawbacks and limits

  • Cannot query directly. SELECT * FROM src_reviews fails — there is no such relation. Debug by compiling and reading the parent, or temporarily switch to view.
  • Cannot singular-test in isolation. A test file that says FROM {{ ref('src_reviews') }} compiles, but you are really testing whichever model inlines it. Errors may point at the downstream file, not staging.
  • Repeated work. If five table models all ref() the same ephemeral model, the warehouse may execute that CTE's logic five times on five separate builds. Usually acceptable for cheap staging; painful for heavy transforms.
  • Compilation size. Deep chains of ephemeral models produce very long compiled SQL. Rarely a problem for staging; can hit query-length limits if abused for complex intermediate layers.
If you previously built src models as views, drop them. Switching a model from view to ephemeral does not remove the old view. Snowflake keeps serving the stale view if something still references it by name. See Dropping stale views.

What happens when you try to query an ephemeral model

Ephemeral models appear in the DAG and in dbt docs, but they have no relation in the warehouse. Running ad-hoc SQL against them fails:

Snowflake · SELECT from ephemeral staging

SELECT * FROM AIRBNB.DEV.SRC_REVIEWS LIMIT 10;
SQL compilation error: Object 'AIRBNB.DEV.SRC_REVIEWS' does not exist or not authorized.

That error is expected after src/ is configured as ephemeral. To inspect staging data, either query the downstream model that inlines it (e.g. fct_reviews), read target/compiled/, or temporarily override one staging file to view for debugging and revert before committing.

When ephemeral hurts: shared heavy transforms

Suppose you refactor a complex 200-line transformation into int_bookings_enriched as ephemeral, and five mart models each ref() it. On a full dbt run, dbt builds five separate compiled queries, each inlining the full 200 lines. The warehouse executes that logic five times.

The fix is to materialise shared heavy logic once as a table or incremental intermediate in an intermediate/ folder, and keep only thin staging as ephemeral. The course keeps staging ephemeral because renaming raw columns is cheap; the pattern breaks if you push business logic into ephemeral layers referenced by many parents.

Incremental models

Incremental materialization is for large, append-heavy tables where rebuilding from scratch every run is too slow or too expensive. The first run creates the table; subsequent runs process only new or changed rows, controlled by your SQL and the {% if is_incremental() %} block.

raw_reviews is the largest table in the Airbnb dataset and grows over time. fct_reviews is the course's incremental fact: it filters null review text, adds a surrogate key, and on incremental runs appends rows with review_date newer than the current maximum.

{{
  config(
    materialized = 'incremental',
    on_schema_change='fail',
    event_time='review_date'
    )
}}

WITH src_reviews AS (
  SELECT * FROM {{ ref('src_reviews') }}
)
SELECT
  {{ dbt_utils.generate_surrogate_key(['listing_id', 'review_date', 'reviewer_name', 'review_text']) }} as review_id,
  *
FROM src_reviews
WHERE review_text is not null
{% if is_incremental() %}
  {% if var("start_date", False) and var("end_date", False) %}
    {{ log('Loading ' ~ this ~ ' incrementally (start_date: ' ~ var("start_date") ~ ', end_date: ' ~ var("end_date") ~ ')', info=True) }}
    AND review_date >= '{{ var("start_date") }}'
    AND review_date < '{{ var("end_date") }}'
  {% else %}
    AND review_date > (select max(review_date) from {{ this }})
    {{ log('Loading ' ~ this ~ ' incrementally (all missing dates)', info=True)}}
  {% endif %}
{% endif %}

The course script shows a simpler version without the surrogate key and variable window — that is the shape to learn first:

{{
  config(
    materialized = 'incremental',
    on_schema_change='fail'
    )
}}
WITH src_reviews AS (
  SELECT * FROM {{ ref('src_reviews') }}
)
SELECT * FROM src_reviews
WHERE review_text is not null

{% if is_incremental() %}
  AND review_date > (select max(review_date) from {{ this }})
{% endif %}

How is_incremental() works

is_incremental() is a dbt macro that returns true when:

  1. The model is configured as incremental.
  2. The target relation already exists in the warehouse.
  3. You are not running with --full-refresh.

On the very first run, the macro returns false, so the watermark filter is skipped and dbt loads all historical reviews. Every run after that adds only rows newer than the current max date.

{{ this }} refers to the relation dbt is building — the existing incremental table on incremental runs. The subquery (SELECT MAX(review_date) FROM {{ this }}) becomes something like (SELECT MAX(review_date) FROM AIRBNB.DEV.FCT_REVIEWS) at compile time.

on_schema_change

The config on_schema_change='fail' tells dbt to stop rather than silently guess if your SELECT produces different columns than the existing table. Alternatives:

ValueBehaviour when columns differ
ignoreContinue; new columns dropped, missing columns filled with null
failRaise an error and stop the run
append_new_columnsAdd new columns to the target table
sync_all_columnsAdd new columns and remove ones no longer in the SELECT

fail is the safe default for production facts. You want to know explicitly when someone adds a column, not discover it weeks later when a dashboard breaks.

Incremental logic is your responsibility. dbt provides the wrapper DDL and is_incremental(); it does not automatically know which rows are new. A missing or wrong watermark silently skips data or duplicates rows depending on your unique keys and strategy.

The {{ this }} macro in incremental models

{{ this }} resolves to the relation dbt is currently building — the schema-qualified name of the incremental table in the active target. In dev that is something like AIRBNB.DEV.FCT_REVIEWS. You use it inside incremental branches to read from the existing table:

  • SELECT MAX(review_date) FROM {{ this }} — watermark for append-only loads
  • DELETE FROM {{ this }} WHERE date = … — custom patterns (advanced; prefer strategy config)
  • {{ log('Loading ' ~ this ~ ' incrementally', info=True) }} — logging which relation is being updated

On first run, the table does not exist yet, so dbt skips the incremental branch entirely. On later runs, the table exists and is_incremental() returns true, so the watermark subquery runs against the populated table.

Late-arriving and backdated rows

The watermark review_date > MAX(review_date) assumes review dates always move forward in time. If a source system backfills a review with an older review_date than the current max, that row never loads on incremental runs.

Fixes depend on the business case:

  • Switch to merge on review_id and widen the filter to include a lookback window (e.g. last 7 days).
  • Use a source ingestion timestamp (_loaded_at) as the watermark instead of business event time.
  • Run a periodic --full-refresh in a controlled window to catch stragglers.

The course dataset is append-only with monotonic dates, so the simple max-date pattern is sufficient for learning. Production pipelines almost always hit late data within the first month.

Variable window for orchestrators (later in the course)

The finished fct_reviews.sql in the repo supports optional start_date and end_date variables so an orchestrator can pass a batch window instead of relying on max-date alone. That pattern appears in Section 18:

dbt run --select fct_reviews --vars '{start_date: "2024-02-15 00:00:00", end_date: "2024-03-15 23:59:59"}'

When both variables are set, the model logs the window and filters review_date into that range. When they are unset, it falls back to the max-date watermark. This is the hand-rolled precursor to incremental_strategy='microbatch' introduced later for mart_fullmoon_reviews.

event_time on incremental models

The repo config includes event_time='review_date'. In dbt 1.10+, this enables dbt run --sample to build a subset of recent rows in dev without scanning full history. It also pairs with microbatch incrementals in later sections. Setting event_time does not change incremental behaviour by itself — your is_incremental() block still controls what loads.

Full refresh

A full refresh rebuilds incremental models from scratch, ignoring existing data and treating the run as if the table did not exist. Use it after logic changes, backfills, or recovering from bad data.

dbt run --full-refresh

dbt run --full-refresh
09:40:01  Running with dbt=1.11.12
09:40:01  Full refresh mode enabled. All incremental models will be rebuilt from scratch.
09:40:05  1 of 12 START sql incremental model DEV.fct_reviews ................. [RUN]
09:40:22  1 of 12 OK created sql incremental model DEV.fct_reviews ........... [SUCCESS 1 in 16.4s]
09:41:08  Completed successfully

You can scope full refresh to one model:

dbt run --select fct_reviews --full-refresh

During full refresh, is_incremental() returns false, so the watermark clause is omitted and every row from src_reviews that passes the WHERE filter is loaded.

Full refresh scoped to one model versus the whole project

CommandWhat rebuildsWhen to use
dbt run --full-refreshEvery incremental model in the projectMajor logic change affecting all facts; rare in prod
dbt run --select fct_reviews --full-refreshOnly fct_reviewsFix one fact after watermark bug or schema change
dbt build --select fct_reviews --full-refreshModel plus its testsRebuild and validate in one command (Section 11)

Non-incremental models (views, tables, ephemeral) ignore --full-refresh — a table model always fully rebuilds anyway. The flag only changes behaviour for models configured as incremental.

What dbt does internally on full refresh

Adapter behaviour varies slightly, but on Snowflake dbt typically drops or truncates the existing incremental table, then runs the model SQL without the incremental filter — equivalent to a first run. Row counts after full refresh should match a fresh SELECT COUNT(*) from the filtered source query.

Compare counts before and after to validate:

SELECT COUNT(*) FROM "AIRBNB"."DEV"."FCT_REVIEWS";
-- expect roughly all non-null review_text rows from raw_reviews

When you need full refresh

  • You changed the incremental filter logic and need to reprocess history.
  • A bug wrote duplicate or corrupt rows and you need a clean slate.
  • You added a column and set on_schema_change='fail' — sometimes a full refresh is the intentional fix after updating the model.
  • You promoted code from dev to prod and want the prod table built consistently.
Full refresh on a large incremental model is the most expensive single command in many projects. fct_reviews is manageable in the course dataset; in production a fact with billions of rows can take hours and scan the entire source table. Guard prod with full_refresh: false in the model config if casual rebuilds must be blocked.

Incremental strategies

The incremental_strategy config tells the adapter how to merge new rows into the existing table. If you omit it, dbt picks a default for your warehouse — on Snowflake that is typically merge when a unique_key is set, otherwise append.

The course mentions strategies as reference material. Official documentation: docs.getdbt.com/docs/build/incremental-strategy.

Merge strategy example

When rows can arrive twice for the same business key (late-arriving updates, reprocessed extracts), append is wrong — you need merge semantics keyed on a unique identifier:

{{
  config(
    materialized='incremental',
    incremental_strategy='merge',
    unique_key='review_id'
  )
}}
WITH src_reviews AS (
  SELECT * FROM {{ ref('src_reviews') }}
)
SELECT * FROM src_reviews
WHERE review_text is not null

{% if is_incremental() %}
  AND review_date > (select max(review_date) from {{ this }})
{% endif %}

The timestamp watermark in fct_reviews (review_date > MAX(review_date)) pairs naturally with append because reviews are insert-only in this dataset. If reviews could be edited in place, you would switch to merge on review_id and widen the incremental filter.

Microbatch arrives in Section 9. dbt 1.9 introduced incremental_strategy='microbatch' with event_time on the model config. The course applies it to mart_fullmoon_reviews. The manual var('start_date') / var('end_date') pattern in the current fct_reviews.sql is the hand-rolled predecessor of that feature.

On Databricks and BigQuery, default strategies and supported options differ slightly from Snowflake. Always check the adapter docs for your warehouse before copying a Snowflake merge config into another platform.

delete+insert and insert_overwrite (reference)

delete+insert removes rows from the target that match a condition, then inserts the staging result. Useful when you reload a sliding window (e.g. last 3 days of mutable data) without rebuilding the entire table. insert_overwrite replaces whole partitions on adapters that support partition-level overwrite (common on BigQuery). Neither appears in the course Airbnb project, but interviewers often ask how they differ from merge.

Dropping stale views after ephemeral

Materialization changes are not always clean. If you first built src_listings, src_hosts, and src_reviews as views — the default before folder config was applied — those views remain in Snowflake after you switch the folder to ephemeral. dbt stops maintaining them, but they still exist and can confuse anyone browsing the schema.

The instructor drops them manually once:

DROP VIEW AIRBNB.DEV.SRC_HOSTS;
DROP VIEW AIRBNB.DEV.SRC_LISTINGS;
DROP VIEW AIRBNB.DEV.SRC_REVIEWS;

This is a one-time cleanup, not part of every run. After dropping, only objects dbt currently materializes appear in DEV.

Why the old views existed

Early in the course, before folder defaults were applied, staging models built as views (the dbt default). The log would have shown START sql view model DEV.src_reviews. After changing dbt_project.yml to set src: +materialized: ephemeral, the next run stopped creating or replacing those views — but Snowflake never drops objects automatically. Anyone browsing the schema still sees SRC_* and may assume they are current.

The same issue appears when changing a model from view to table or renaming a model: the old object persists until dropped. dbt tracks models by name in target/manifest.json; orphaned relations are outside that manifest.

Verify with dbt ls and your warehouse. Run dbt ls --resource-type model to see what dbt knows about, then compare to SHOW VIEWS IN SCHEMA AIRBNB.DEV. Anything in Snowflake but not in dbt's manifest is a candidate for manual drop.

Materialization comparison

Use this table when choosing or reviewing materializations in code review. No row is universally correct — the right choice depends on table size, query patterns, and mutability.

viewLowHigh (recompute every query)NoneYesYesThin transforms, dev iteration, rarely queried layers
tableHigh (full rebuild)LowFull copy of rowsYesYesDimensions, marts, heavily queried models

Everyday analogy — a view is a recipe taped to the fridge: cheap to update, but someone cooks from scratch every dinner. A table is meal prep in the freezer: effort upfront, fast later. Ephemeral is a prep step written inside another recipe, never stored on its own. Incremental is a freezer you only add today's leftovers to, not a full re-cook.

Quick decision checklist

When reviewing a pull request or designing a new model, walk through these questions in order:

  1. Will anyone query this model directly in SQL or BI? If no, consider ephemeral.
  2. Is the dataset large and append-heavy? If yes, consider incremental.
  3. Is the model queried frequently with expensive logic? If yes, prefer table over view.
  4. Is the dataset small and logic still changing? If yes, view is fine for now.
  5. Does the model need a stable relation for tests or snapshots? If yes, not ephemeral.

The Airbnb project applies this checklist: staging is ephemeral (not queried directly), dimensions are mostly tables (joined often), listings cleansing stays a view during early iteration, and reviews are incremental (large and growing).

Config precedence

When the same setting appears in multiple places, dbt resolves it in a fixed order. The most specific config wins. Misunderstanding this order is the main reason a model builds as the wrong materialization.

Order of precedence (highest wins)

  1. Config in the model SQL file — the {{ config(materialized='view') }} block at the top of dim_listings_cleansed.sql beats everything below.
  2. Config on a specific model in dbt_project.yml — e.g. naming one model under models: airbnb: dim: dim_listings_cleansed: +materialized: table (not used in this project, but supported).
  3. Folder-level config in dbt_project.yml — dim: +materialized: table applies to every file in models/dim/ unless overridden by (1) or (2).
  4. Project-level config in dbt_project.yml — models: airbnb: +materialized: view is the default for all models in the project.
  5. dbt defaults — if nothing above sets materialization, dbt uses view.

Where each config lives in the Airbnb project

1. Model SQL file — {{ config(materialized='view') }} in dim_listings_cleansed.sql; materialized='incremental' in fct_reviews.sql
2. Model-specific YAML — not used in this course, but supported: models: airbnb: dim: dim_listings_cleansed: +materialized: table
3. Folder YAML — dim: +materialized: table, src: +materialized: ephemeral in dbt_project.yml
4. Project YAML — models: airbnb: +materialized: view applies to all models without a more specific rule
5. dbt default — view if nothing above is set

The + prefix in dbt_project.yml means "apply this config to all models under this key". Without +, dbt treats the key as a subfolder path. The project name (airbnb) must match the name: field in dbt_project.yml — a common copy-paste error in multi-project repos is nesting config under the wrong project key so folder defaults silently never apply.

Config in profiles.yml does not set materialization

profiles.yml controls connection targets (account, role, warehouse, schema, threads). It never sets materialized. Certification questions sometimes mix the two files: if a model builds as a view when you expected a table, look at dbt_project.yml and the model file, not profiles.yml.

dbt_project.yml vs packages. Materialization defaults belong in your project's dbt_project.yml. Installed packages (e.g. dbt_utils) have their own project configs; your folder defaults do not override models inside packages unless you add a config block for that package name.

Traps that catch people

  • Assuming ephemeral creates a relation — SELECT * FROM src_reviews fails with "object does not exist". Ephemeral models only exist in compiled SQL. Debug via target/compiled/ or temporarily set materialized='view'.
  • Forgetting to drop old views — after switching src/ to ephemeral, orphaned views linger in the schema. Analysts query stale data from the abandoned view while dbt builds correct data through a different path.
  • Incremental without a watermark — if you omit {% if is_incremental() %} logic, every run reprocesses all source rows. With append strategy you duplicate rows; with merge you overwrite expensively.
  • Wrong MAX() column — MAX(review_date) assumes dates always move forward. Backdated source rows never load. Use a source ingestion timestamp or switch to merge on a stable key.
  • Config in the wrong folder key — putting +materialized: table under models: instead of models: airbnb: silently fails to apply in multi-project repos. Match the project name from dbt_project.yml.
  • Expecting folder config to retroactively drop objects — changing dim from view to table leaves the old view until you drop it or rename the model. dbt creates the new object; cleanup is manual.
  • Testing ephemeral models directly — singular tests against ref('src_reviews') compile but test downstream behaviour. Failures may reference the wrong file line.
  • Full refresh in production CI — a pipeline that passes --full-refresh on every merge rebuilds all incrementals nightly. Runtime and cost explode by the second month.
  • on_schema_change='ignore' in prod — new columns silently disappear from the target. Use fail or append_new_columns intentionally, not by accident.
  • Stacking views ten deep — each query scans through every layer. Materialise at least one layer in the middle as a table.
  • Changing materialization without full refresh — switching fct_reviews from table to incremental against an existing table can fail if column types or names differ. Drop the old relation or full-refresh once after the change.
  • Merge without unique_key — on Snowflake, merge strategy requires a stable key. Omitting unique_key falls back to append or errors depending on adapter version.

Production patterns

Mature teams document a materialization decision tree in the project README: staging ephemeral, dimensions table (or view in dev-only schemas), facts incremental when row count or run time crosses a threshold, marts table. Code review checks that any deviation from the tree is justified in the PR description.

Convention that scales

Folder defaults in dbt_project.yml match the decision tree. Overrides in model files require a comment explaining why. CI runs dbt compile on every PR so config merges are validated before merge.

Anti-pattern: everything incremental

Small dimensions do not benefit from incremental complexity. An incremental model needs watermark logic, handles schema changes, and is harder to backfill. A 10,000-row dimension should stay a table.

Interview questions

Answer each one out loud before opening it.

What are the four dbt materializations and what warehouse object does each create?Fundamentals

view creates a view — a stored query, no persisted rows. table creates a physical table rebuilt on each run. ephemeral creates nothing; SQL is inlined as CTEs in downstream models. incremental creates a table that on first run loads all data and on later runs adds or merges only new/changed rows according to your logic and strategy.

When would you choose a view over a table, and when would you reject a view?Comparison

Choose a view when the transform is cheap, the data is small, you want always-fresh results, or you are still iterating in development. Reject a view when many consumers query the model frequently, the underlying logic is expensive, or you have long chains of views that re-scan sources on every query. Views shift cost from build time to query time.

Explain ephemeral materialization and one reason staging is often ephemeral.Modelling

Ephemeral models never become database objects. dbt inlines them as WITH clauses wherever ref() is called. Staging is often ephemeral because it is thin renaming on raw data that nobody should query directly; inlining keeps the warehouse clean and guarantees staging logic is never stale relative to downstream models.

What does is_incremental() return on the first run, on a normal second run, and during --full-refresh?Fundamentals

First run: false, because the target table does not exist yet — dbt performs a full load. Normal subsequent runs: true, so your watermark filter applies and only new rows process. With --full-refresh: false, because dbt drops or truncates and rebuilds, intentionally ignoring incremental logic.

Your incremental model ran successfully but inserted zero rows. How do you debug it?Troubleshooting

Check whether source data actually has rows newer than MAX(watermark_column) in the target table. Inspect the compiled SQL in target/compiled/ to confirm the incremental branch compiled. Verify you did not accidentally pass --full-refresh combined with a filter that excludes everything. Run the source query and watermark subquery manually in a worksheet and compare counts.

What is the difference between append and merge incremental strategies?Comparison

Append inserts new rows only and never updates existing ones — duplicates appear if the same business key arrives twice. Merge requires a unique_key and upserts: matching keys update, new keys insert. Use append for insert-only streams with a reliable watermark; use merge when rows can change or arrive late for the same key.

Describe config precedence for materialized in dbt.Certification

Most specific wins: config block in the model SQL file beats a model-specific entry in dbt_project.yml, which beats folder-level config in dbt_project.yml, which beats project-wide config under models: project_name:, which beats dbt's default of view. dim_listings_cleansed is the course example: folder says table, file says view, view wins.

Why drop SRC_LISTINGS, SRC_HOSTS, and SRC_REVIEWS views after switching src/ to ephemeral?Gotcha

Those views were created when staging was materialized as views. Changing folder config to ephemeral stops dbt from maintaining them, but Snowflake does not auto-drop them. They become orphaned objects that can mislead analysts and even serve stale data if queried directly. Drop once manually and verify the schema matches what dbt now manages.

When is --full-refresh appropriate in production?Production

When incremental logic changed and history must be reprocessed, after data corruption, when promoting a breaking schema change, or during a controlled backfill. It is not appropriate on every scheduled run. Production models often set full_refresh: false to prevent accidental full rebuilds from CI or a mistyped command.

What does on_schema_change='fail' protect you from?Design

It stops the run if your model's SELECT produces a different column set than the existing incremental table. Without it, dbt might ignore new columns or fill missing ones with nulls, and dashboards break silently. fail forces an explicit decision: alter the table, change config to append_new_columns, or full refresh.

Can you run dbt tests directly against an ephemeral model?Testing

Not meaningfully in isolation. Ephemeral models have no warehouse relation, so schema tests that expect a table or view cannot target them the way they target dim_hosts_cleansed. Singular tests that ref() an ephemeral model compile, but they execute against the compiled query context of that ref, which often means you are testing staging logic embedded in a downstream model. Teams test staging indirectly through downstream models or temporarily switch staging to view during development.

Why materialize fct_reviews as incremental instead of table?Cost

raw_reviews is the largest table in the project and grows over time. A table materialization would scan and rewrite every review on each run. Incremental runs process only rows newer than the current watermark (or a passed date window), so runtime and warehouse cost scale with new data, not total history. That is the standard pattern for append-heavy fact tables in production.

What SQL does dbt send to the warehouse for an ephemeral model during dbt run?Fundamentals

None. Ephemeral models are skipped at run time as independent nodes. dbt inlines their SQL into each downstream model that references them and runs the parent's materialization DDL instead. You will never see START sql ephemeral model in the log because there is no ephemeral execution step.

Recap

  • Materialization controls what dbt builds in the warehouse: view, table, ephemeral, or incremental.
  • Default is view if nothing else is configured.
  • Folder defaults in dbt_project.yml: project view, src/ ephemeral, dim/ table.
  • dim_listings_cleansed overrides the dim folder to view with an explicit {{ config() }} block.
  • Ephemeral models inline as CTEs; no relation exists to query directly.
  • After switching staging to ephemeral, drop orphaned SRC_* views manually.
  • fct_reviews is incremental with on_schema_change='fail' and a review_date watermark.
  • is_incremental() is false on first run and during --full-refresh.
  • --full-refresh rebuilds incremental models from scratch.
  • incremental_strategy controls append vs merge vs partition replace; pair merge with unique_key.
  • dim_listings_w_hosts joins listings and hosts as a table in dim/.
  • Config precedence: model file > project YAML (specific) > folder YAML > project default > dbt default.
