The dbt Power User extension

dbt Power User (publisher Innoverio) is a community extension that predates dbt Labs’ official VS Code product. On the course’s poweruser branch it is pre-installed in the devcontainer so every student gets the same IDE experience without hunting the marketplace.

The extension ID is innoverio.vscode-dbt-power-user. The branch’s devcontainer pins it explicitly and sets file associations so YAML and SQL open with Jinja-aware grammars:

{
  "customizations": {
    "vscode": {
      "extensions": [
        "innoverio.vscode-dbt-power-user"
      ],
      "settings": {
        "terminal.integrated.cwd": "${containerWorkspaceFolder}/airbnb",
        "files.associations": {
          "*.yaml": "jinja-yaml",
          "*.yml": "jinja-yaml",
          "*.sql": "jinja-sql",
          "*.md": "jinja-md"
        }
      }
    }
  }
}

Opening the workspace at airbnb/ as the integrated terminal cwd means every dbt command you run from the VS Code terminal already sits in the project root — the same convention Section 6 established for local setup.

Lineage preview

Power User reads your project’s manifest (after dbt parse or dbt run) and renders an interactive lineage graph inside the editor. Click a model in the sidebar or from a ref() call and you see upstream sources and downstream dependents without opening dbt Docs in a browser.

For the Airbnb project, selecting mart_listing_performance on the poweruser branch shows the chain: dim_listings_w_hosts and int_host_performance feeding the mart. That is the same DAG Section 14 documents, but embedded in the editor where you are editing SQL.

Model preview and compiled SQL

From a .sql model file, Power User can compile the active model and show the rendered SQL in a side panel — the same output you would read manually from target/compiled/airbnb/models/... after dbt compile. Use this to verify Jinja resolved correctly before paying for a warehouse run.

The preview uses whichever dbt executable your Python environment provides. If compilation fails, the panel shows the parse error with a line reference back to the source file. That is faster than switching to a terminal for a compile-only loop, though Section 16’s artifact-first debugging still applies when you need the full compiled test SQL.

SQL formatting

Power User includes a formatter tuned for dbt SQL (Jinja blocks plus warehouse dialect). Right-click in a model or use the format command to re-indent CTEs, align keywords, and wrap long lines. It does not replace a team style guide enforced in CI — it keeps local files readable before you commit.

Formatting is opinionated. Teams often combine editor formatting with SQLFluff (covered below) so “format on save” in the IDE and “lint in CI” share the same rules where possible.

Cost estimation

On supported adapters, Power User can estimate the warehouse cost of running the selected model based on metadata and historical run stats where available. Treat this as a directional hint, not an invoice: actual cost depends on warehouse size, clustering, and concurrent load.

Cost estimation is advisory. A model preview or compile is free; a model run bills the warehouse. Use estimation to decide whether to add --sample or run in dev first, especially for full-table materializations from Section 8.

The Fusion engine

Fusion is dbt Labs’ Rust-based execution and compilation engine. It replaces the Python parser/runtime for many workflows while keeping the same project layout: dbt_project.yml, models/, ref(), tests in YAML. Authoring does not change; what changes is how fast compilation happens and how much the tool understands about SQL before touching the warehouse.

What Fusion changes

  • Compile speed — dbt Labs reports up to ~30× faster project parsing and roughly 2× faster full-project compilation versus dbt Core on large projects. Single-file recompile in the IDE can feel instant because Fusion is a native binary, not a Python interpreter loading Jinja for every file.
  • Static analysis — Fusion parses SQL into an AST, resolves columns across ref() dependencies, and can flag invalid identifiers locally. Core often needs a warehouse round-trip or a full compile plus manual inspection to catch the same mistake.
  • SQL comprehension without warehouse round-trips — lineage, type checking, and IDE diagnostics can run on your laptop. The warehouse still executes materializations; Fusion does not eliminate run cost from Section 8 materializations.
  • No Python runtime for the engine itself — the Fusion binary installs separately. Your project may still use Python for dbt-core adapters or Python models from Section 17 until you fully migrate.

Limitations and maturity caveats

Fusion is newer than a decade of dbt Core behaviour. Treat it as evolving software, not a drop-in guarantee for every package and Jinja pattern.

  • Adapter coverage — Snowflake was the first-class beta target; BigQuery, Redshift, Databricks, and others arrived on a rolling basis. Not every adapter feature Core exposes is implemented in Fusion on day one.
  • Stricter validation — patterns Core warned about may become hard errors under Fusion’s parser. Deprecated YAML or macro overrides fail earlier, which is good for greenfield projects and painful for legacy repos until you fix them.
  • Package compatibility — macros that rely on undocumented Core internals (or heavy runtime warehouse queries during parse) may break. The course’s metaplane dbt_expectations and dbt_utils pins should be tested explicitly on Fusion before you switch CI.
  • Jinja compile-time queries — models that call run_query() or introspect information_schema during compilation can be slower on Fusion than Core in edge cases reported on public issue trackers. Parsing speed does not help if compilation must hit the warehouse dozens of times.
  • Core-only features in CI scripts — the course’s test_commands.sh skips inline Jinja comment tests when ENGINE=fusion because Fusion handles inline compile differently. Read adapter release notes before assuming parity.
Check current adapter support before migrating production. dbt Labs publishes Fusion compatibility and GA milestones on their developer blog and docs. Snowflake-first teams benefit earliest; multi-adapter estates should pilot on a branch and run the same dbt build you use in Section 19 Slim CI before cutting over.
Fusion speeds up compile, not warehouse execution. A ten-minute incremental model still runs ten minutes in Snowflake. The win is trying five SQL variants in the IDE without five paid runs — aligned with Section 16’s compile-first debugging loop.

SQLFluff and the dbt templater

SQLFluff is a SQL linter and formatter. With the dbt templater it renders Jinja the same way dbt would, then linting rules apply to the resulting SQL. The poweruser branch adds a minimal project config:

[sqlfluff]
  dialect = snowflake

Why lint dbt SQL separately from dbt test

dbt tests assert data correctness; SQLFluff asserts shape and readability: keyword placement, indent width, trailing commas, ambiguous aliases. A model can pass every unique and not_null test from Section 11 while remaining unreadable or inconsistent with team style.

SQLFluff runs outside the warehouse. It invokes dbt’s compilation context (when configured) so rules see resolved ref() names, not raw Jinja placeholders.

Typical expanded configuration

The course file is intentionally minimal. Production teams usually add templater and rule sections like this:

[sqlfluff]
  dialect = snowflake
  templater = dbt
  exclude_rules = L034

[sqlfluff:templater:dbt]
  project_dir = .
  profiles_dir = ~/.dbt

[sqlfluff:indentation]
  indent_unit = space
  tab_space_size = 2

[sqlfluff:rules:capitalisation.keywords]
  capitalisation_policy = lower

Problems with the legacy pattern:

  • Duplicated cleansing — price parsing diverges from dim_listings_cleansed if either side changes.
  • Source coupling — mart logic depends on raw column names (NAME, string prices) instead of conformed dimensions.
  • No reuse — host aggregates trapped in one file; mart_listing_performance cannot share them without copy-paste.
  • Harder testing — you cannot test host metrics in isolation from staging sources without spinning up raw tables.

After: int_host_performance

The refactored intermediate model reads cleansed dimensions, materializes as a table, and documents metrics in a block comment:

{{
  config(
    materialized = 'table'
  )
}}
WITH dim_hosts AS (
  SELECT host_id, host_name, is_superhost, created_at
  FROM {{ ref('dim_hosts_cleansed') }}
),
dim_listings AS (
  SELECT listing_id, room_type, price, minimum_nights, host_id
  FROM {{ ref('dim_listings_cleansed') }}
),
host_listing_metrics AS (
  SELECT
    h.host_id,
    h.host_name,
    COUNT(DISTINCT dl.listing_id) AS total_listings,
    ROUND(AVG(dl.price), 2) AS avg_listing_price,
    COALESCE(SUM(CASE WHEN dl.room_type = 'Entire home/apt' THEN 1 ELSE 0 END), 0) AS entire_home_count
    -- ... private_room_count, shared_room_count, hotel_room_count ...
  FROM dim_hosts h
  LEFT JOIN dim_listings dl ON h.host_id = dl.host_id
  GROUP BY h.host_id, h.host_name, h.is_superhost, h.created_at
)
SELECT
  h.host_id,
  h.host_name,
  h.total_listings,
  h.avg_listing_price,
  CASE
    WHEN h.total_listings = 0 THEN 'inactive'
    WHEN h.total_listings = 1 THEN 'single_listing'
    WHEN h.total_listings BETWEEN 2 AND 5 THEN 'small_portfolio'
    WHEN h.total_listings BETWEEN 6 AND 15 THEN 'medium_portfolio'
    WHEN h.total_listings >= 16 THEN 'large_portfolio'
  END AS portfolio_size,
  CASE
    WHEN h.is_superhost = 't' THEN 'superhost'
    ELSE 'standard'
  END AS host_status,
  d.dominant_room_type
FROM host_listing_metrics h
LEFT JOIN dominant_room_type_calc d ON h.host_id = d.host_id

Mart after refactor

mart_listing_performance.sql shrinks: listing grain comes from dim_listings_w_hosts; host portfolio context comes from int_host_performance.

WITH listing_base AS (
    SELECT
        listing_id,
        listing_name,
        room_type,
        price,
        minimum_nights,
        host_id,
        host_name,
        host_is_superhost
    FROM {{ ref('dim_listings_w_hosts') }}
),
host_metrics AS (
    SELECT
        host_id,
        total_listings,
        avg_listing_price,
        portfolio_size,
        host_status,
        host_tenure
    FROM {{ ref('int_host_performance') }}
),
final AS (
    SELECT
        l.listing_id,
        l.listing_name,
        l.room_type,
        l.price,
        l.minimum_nights,
        l.host_id,
        l.host_name,
        h.total_listings,
        h.avg_listing_price AS host_portfolio_avg_price,
        h.portfolio_size,
        h.host_status,
        CASE
            WHEN h.total_listings = 1 THEN 'only_listing'
            WHEN l.price >= h.avg_listing_price THEN 'above_portfolio_avg'
            ELSE 'below_portfolio_avg'
        END AS price_position_vs_portfolio,
        CASE
            WHEN l.price < 50 THEN 'budget'
            WHEN l.price >= 50 AND l.price < 150 THEN 'mid_range'
            WHEN l.price >= 150 AND l.price < 300 THEN 'premium'
            ELSE 'luxury'
        END AS price_segment
    FROM listing_base l
    LEFT JOIN host_metrics h ON l.host_id = h.host_id
)
SELECT * FROM final

Legacy folder convention

Keep superseded models in models/legacy/ (or disable them with enabled: false in config) until you verify row-count parity against replacements. Do not delete legacy SQL until tests prove equivalence — stakeholders may compare old dashboard numbers during migration.

Optionally exclude legacy from production selectors:

selectors:
  - name: production_models
    definition:
      union:
        - method: path
          value: models
        - exclude:
            - method: path
              value: models/legacy
Do not ref legacy models from new code. If a new mart still ref()s a legacy file, you inherit all its source coupling. Point refs at dimensions and intermediate models only.

Building models with AI

The final lecture uses an AI assistant inside VS Code (Copilot, Cursor, or similar) to scaffold int_host_performance from a natural-language prompt. The workflow is deliberate: give the model enough context to emit valid dbt, then apply the same review and testing discipline as hand-written SQL.

Prompt Steven uses in the course

From course-resources.md, the instructor pastes:

Create an intermediate model called int_host_performance that calculates host-level performance metrics.

Use the following upstream models:
dim_hosts_cleansed for host data
dim_listings_cleaned for listing data

Calculate these metrics per host:
- total_listings: count of listings
- avg_listing_price: average price across listings
- min_listing_price: minimum price
- max_listing_price: maximum price
- room type distribution (entire_home_count, private_room_count, shared_room_count, hotel_room_count)
- avg_minimum_nights: average minimum night

Add these classifications:
- portfolio_size: based on listing count (inactive = 0, single_listing = 1, small_portfolio = 2-5, medium_portfolio = 6-15, large_portfolio = 16+)
- host_status: 'superhost' if is_superhost = 't', else 'standard'
- host_tenure: based on created_at (new_host <1 year, experienced_host 1-3 years, veteran_host 3+ years)
- dominant_room_type: the room type with most listing

save to models/intermediate/int_host_performance.sql
The prompt typo is intentional teaching. It says dim_listings_cleaned; the real model is dim_listings_cleansed. A good workflow catches that in review when dbt compile fails or when you verify every ref() name against the project.

Prompting patterns that work for dbt

  1. Attach schema context — paste relevant blocks from models/schema.yml or open the upstream model files in the editor context so column names match the project.
  2. Specify grain and path — “one row per host_id” and models/intermediate/int_host_performance.sql prevent the model landing in the wrong folder or at wrong grain.
  3. Require ref(), forbid raw tables — explicitly say “use ref() only, no source()” for transform layers.
  4. Name classifications with enums — listing portfolio buckets as in the prompt reduces vague CASE logic.
  5. Ask for config explicitly — “materialized table” or “view” matches Section 8 decisions.
  6. Iterate in small diffs — generate skeleton CTEs first, then add dominant_room_type logic in a second prompt after the first compile passes.

Honest caveat: AI is not a substitute for tests

Generated SQL can compile and still be wrong: off-by-one tenure boundaries, LEFT JOIN turned into INNER JOIN, or classifications that do not match business definitions. The course expects you to add the same tests and contracts you learned in Section 11 and Section 12.

  • unique and not_null on host_id in int_host_performance
  • Accepted-values tests on portfolio_size, host_status, host_tenure
  • Singular tests on mart_listing_performance like the branch’s test_mart_listing_performance.sql patterns
  • Contract YAML if the mart feeds a governed exposure from Section 15
SELECT *
FROM {{ ref('mart_listing_performance') }}
WHERE (price < 50 AND price_segment != 'budget')
    OR (price >= 50 AND price < 150 AND price_segment != 'mid_range')
    OR (price >= 150 AND price < 300 AND price_segment != 'premium')
    OR (price >= 300 AND price_segment != 'luxury')
Certification angle: the exam tests that you validate models with tests and documentation, not that you used AI. Treat AI output as a first draft from a junior contributor — review, test, document, then merge through the same PR process as Section 19 CI.

Traps that catch people

  • Stale manifest in IDE — lineage shows old graph after renames until dbt parse. You chase ghosts in Power User while CLI works.
  • Two extensions fighting — duplicate formatters and conflicting language servers slow saves or produce contradictory squiggles.
  • Fusion on unsupported adapter — install succeeds but run fails mid-migration. Check adapter matrix before switching CI.
  • SQLFluff without dbt templater — rules flag {{ ref() }} as syntax errors. Set templater = dbt.
  • Legacy folder still in DAG — forgotten ref() to legacy model resurrects duplicate pipelines and doubles warehouse cost.
  • AI typo in ref name — dim_listings_cleaned compiles nowhere. Always grep the project for exact model names.
  • Skipping tests on generated SQL — AI loves plausible CASE boundaries that fail edge rows. Add singular tests for classification logic.
  • Re-parsing prices in intermediate — AI may copy legacy cleansing into new models. Read upstream dims first.
  • Confusing compile speed with pipeline speed — Fusion saves IDE time, not nightly run duration.
  • Committing .sqlfluff that differs from CI — local fix passes, PR fails. Pin sqlfluff version in pyproject or requirements.
  • dim_listings_w_hosts version drift — by course end the join model may use ref('dim_hosts_cleansed', v=2) from Section 19; AI scaffolds against v1 names if schema context is stale.

Production patterns

Mature teams standardize on one IDE extension document in the repo README, pin Fusion or Core explicitly in CI (not both silently), and add a lint job for SQLFluff on changed .sql files. Legacy quarantine uses enabled: false plus a sunset date; selectors exclude legacy/ from production jobs.

AI usage policies require human review, mandatory tests for new models, and no direct merge of uncompiled AI output. Some teams ban AI on macros that touch permissions or PII columns.

Pattern: intermediate extraction

When two marts need the same host aggregates, build int_* once. The course refactor is the template for any legacy monolith.

Anti-pattern: AI + no schema.yml

Generated columns without YAML tests never enter prod CI. Section 11 tests are part of the definition of done.

Interview questions

Answer each one out loud before opening it.

What does the dbt Power User extension give you that the CLI alone does not?Fundamentals

In-editor lineage from the manifest, compiled SQL preview without leaving the file, formatting tuned for dbt SQL, and on some adapters cost estimation before run. The CLI still does the real compile and run; the extension surfaces results faster.

You still need a valid project, profiles, and a parsed manifest for graph features. It does not replace tests or documentation.

How does the official dbt extension differ from Power User?Comparison

Power User is a community extension built around dbt Core. The official extension is from dbt Labs and pairs with the Fusion language server for faster compile and deeper static analysis when Fusion is installed.

Power User emphasizes lineage UI and cost hints; the official extension emphasizes SQL comprehension, column-level lineage, and alignment with dbt Labs’ roadmap. Teams may standardize on one locally while CI stays on Core or Fusion consistently.

What is the Fusion engine and what problem does it solve?Performance

Fusion is a Rust-based dbt engine that reimplements parsing and compilation with native SQL understanding. It speeds project parse and compile dramatically and enables IDE feedback without warehouse round-trips for many error classes.

It does not replace warehouse execution for materializations. Adapter support and package compatibility evolve; treat migration as a pilot, not a flip of a switch.

Why use SQLFluff if dbt already has tests?Design

Tests validate data; SQLFluff validates SQL style and some structural conventions. Consistent formatting makes diffs reviewable and reduces bike-shedding in PRs.

With the dbt templater, SQLFluff renders Jinja before linting, so rules apply to real SQL. It catches different failure modes than unique or not_null.

How would you refactor a legacy dbt model that reads sources directly?Modelling

Identify duplicated logic already in dimensions (price parsing, renaming). Extract shared aggregates to an intermediate model at the correct grain (int_host_performance at host level). Point marts at ref() to dims and intermediate layers only.

Keep legacy files quarantined until row-count and metric parity tests pass. Exclude legacy from production selectors. Delete only after consumers migrate.

What grain should int_host_performance be at and why?Modelling

One row per host_id. Metrics are host-level aggregates (listing counts, portfolio classifications, tenure). Listing-level attributes belong in mart_listing_performance, which joins host metrics to listing grain.

Mixing grains in one model causes fan-out or double-counting when downstream models join incorrectly.

How do you safely use AI to generate a dbt model?Production

Provide schema.yml and upstream model files as context. Specify grain, materialization, target path, and require ref(). Review every name, compile before run, add YAML tests and singular tests for business logic, and merge through normal PR/CI.

AI output is untrusted until tests pass — same standard as junior-authored SQL. Cross-reference Sections 11–12 for contracts on exposed marts.

When would Fusion compile be slower than you expect?Gotcha

When models trigger many compile-time warehouse queries — heavy run_query(), large information_schema introspection, or iterative Jinja that hits the warehouse repeatedly. Fusion’s parse speed does not remove those round-trips.

Profile compile with debug logs; compare Core versus Fusion on the same project before mandating Fusion in CI.

What is the legacy/ folder pattern for?Design

It quarantines superseded SQL during migration. Files remain for comparison and audit but should not be referenced by new models or production selectors.

Pair with enabled: false or selector exclusions once replacements are verified. Document sunset dates so legacy code does not linger for years.

Does Fusion eliminate warehouse cost for dbt development?Cost

No. Fusion reduces local compile and static analysis cost. Any dbt run, dbt build, or test still queries the warehouse and bills compute/storage as before.

The savings come from catching errors before run and iterating in the IDE — fewer failed full-table builds during development.

How does mart_listing_performance use int_host_performance?SQL

Listing attributes come from dim_listings_w_hosts at listing grain. Host portfolio metrics come from int_host_performance joined on host_id. Derived columns like price_position_vs_portfolio compare listing price to the host’s average from the intermediate model.

This avoids recomputing host aggregates inside the mart and matches the DRY principle from Section 1.

What should you check after sqlfluff fix changes a model?Troubleshooting

Run dbt compile to ensure the templater still renders. Re-run affected tests — aggressive formatting can occasionally break Jinja block boundaries if misconfigured.

Diff the file in git; confirm only style changed, not logic. In CI, pin SQLFluff version so fix behaviour is stable.

Why materialize int_host_performance as a table?Performance

Multiple downstream consumers (mart_listing_performance and any future host-facing mart) read the same aggregates. A table avoids recomputing host-level GROUP BY on every mart run.

A view would re-scan dims each time; ephemeral would inline into every child and duplicate work. Table is the course choice for reusable intermediate aggregates at a stable grain.

Recap

  • dbt Power User (innoverio.vscode-dbt-power-user) adds lineage preview, model preview, formatting, and cost hints on top of dbt Core.
  • The official dbt extension (dbtLabsInc.dbt) pairs with Fusion for faster compile and static SQL analysis.
  • Fusion is a Rust engine: faster parse/compile, SQL comprehension without warehouse round-trips for many checks — but run/test still hit the warehouse.
  • Install Fusion in the course via .devcontainer/install-dbt-fusion.sh on the official-extension branch.
  • Check current adapter support before production migration; Fusion is newer and stricter than Core.
  • SQLFluff with dialect = snowflake and templater = dbt enforces SQL style; tests from Sections 11–12 enforce correctness.
  • Legacy models live in models/legacy/ quarantined until refactored; new code uses ref() to dims and intermediate layers.
  • int_host_performance is host grain; mart_listing_performance joins it to listing grain from dim_listings_w_hosts.
  • AI prompts should include schema context, exact ref() names, grain, and path — then compile, test, and review like any other PR.
  • AI-generated SQL still needs YAML tests, singular tests, and contracts — never merge on compile alone.
  • Compare poweruser and official-extension devcontainers side by side to see how extension choice changes the container bootstrap.
