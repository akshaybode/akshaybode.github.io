Why test in dbt

A dbt test is a SELECT that returns rows you do not want to exist. If the query returns zero rows, the test passes. If it returns any rows, dbt marks the test as failed and can block downstream work depending on severity and how you orchestrate the run.

That inversion matters. You are not writing assertions in Python or checking a boolean in application code. You express the violation condition in SQL — “show me listing IDs that appear more than once” — and dbt runs it against the warehouse relation your model materialised. The warehouse does the work; dbt tracks results, names the test, wires it into the DAG, and surfaces failures in the CLI and (optionally) in stored failure tables.

Tests in the analytics engineering workflow

Testing is one of the practices that separates ad-hoc SQL from a maintainable pipeline. When a Fivetran sync duplicates rows, a staging CASE statement maps a new room type to NULL, or an incremental model drops late-arriving reviews, tests turn silent KPI drift into a failed job with a name you can grep. That failure is intentional: it is cheaper than a CFO asking why revenue dropped three weeks after the bug shipped.

dbt tests are not a substitute for:

  • Source freshness (Section 9) — detects stale loads, not bad values inside a fresh load.
  • Unit tests (Section 12) — mock inputs in memory; no warehouse scan required.
  • Database constraints — enforced at insert time by the warehouse; dbt tests run after the fact on schedule.
  • Data observability platforms — anomaly detection on metrics over time; complementary to row-level tests.
Everyday analogy — generic tests are like checking every apple on the conveyor for bruises. Singular tests are the chef tasting one specific dish before it leaves the kitchen. Freshness is asking whether the delivery truck arrived today at all.

When tests run in the DAG

Test nodes depend on the models they reference. dbt will not run not_null_dim_listings_cleansed_listing_id until dim_listings_cleansed exists for the current target. Singular tests that join two models depend on both. In dbt build, dbt interleaves runs and tests; in a plain dbt test, you are responsible for that ordering.

The four built-in generic tests

dbt ships four generic tests that cover the majority of column-level checks analytics engineers need. Each is a Jinja macro that expands into a failing-row query. You reference them by short name under a column’s data_tests: list, or with an arguments: block when parameters are required.

TestWhat it checksTypical columnNeeds arguments?
uniqueNo duplicate valuesPrimary keys, natural keysNo
not_nullNo NULL valuesKeys, required attributesNo
accepted_valuesValue is in an allowed listEnums, flags, status codesYes — values:
relationshipsEvery value exists in a parent column (referential integrity)Foreign keysYes — to:, field:

unique

Assert that a column contains only distinct values. On dim_listings_cleansed.listing_id, this is your primary-key guarantee. Internally dbt groups by the column and returns groups with COUNT(*) > 1.

SELECT
    listing_id
FROM DEV.dim_listings_cleansed
GROUP BY listing_id
HAVING COUNT(*) > 1

If two rows share the same listing_id, the test fails and dbt prints how many failing rows it found (up to the warehouse limit configured for the adapter).

not_null

Returns rows where the column is NULL. Combine with unique on the same column for a minimal primary-key contract before you adopt formal model contracts in Section 12.

SELECT
    listing_id
FROM DEV.dim_listings_cleansed
WHERE listing_id IS NULL

accepted_values

Restrict a column to a finite set. The course uses this on room_type with the four Airbnb room categories. Any unexpected string — a typo in staging, a new category from the API — surfaces as a failing row.

SELECT
    room_type
FROM DEV.dim_listings_cleansed
WHERE room_type NOT IN (
    'Entire home/apt',
    'Private room',
    'Shared room',
    'Hotel room'
)
New categories are data, not test bugs. When Airbnb adds a fifth room type, the test fails correctly. Update the allowed list in YAML (or move to a seed-driven lookup test) after validating the new value with the business.

relationships

Foreign-key style integrity: every non-null value in the child column must appear in the parent column. The course links dim_listings_cleansed.host_id to dim_hosts_cleansed.host_id and later fct_reviews.listing_id to dim_listings_cleansed.listing_id.

The to: argument accepts ref('model_name') or source('source_name', 'table_name'). The parent model must exist in the warehouse when the test runs — another reason to run parents before children, or use dbt test --select +dim_listings_cleansed to include upstream builds if your orchestration bundles them.

SELECT
    child.host_id
FROM DEV.dim_listings_cleansed AS child
LEFT JOIN DEV.dim_hosts_cleansed AS parent
    ON child.host_id = parent.host_id
WHERE child.host_id IS NOT NULL
  AND parent.host_id IS NULL

Generic tests compared at a glance

Column-only vs cross-table

unique, not_null, and accepted_values scan one column on one model. relationships joins two relations and is sensitive to build order and orphaned keys in either direction.

NULL handling

relationships ignores NULL child keys by default (SQL NULL semantics). If NULL foreign keys are invalid, add a separate not_null on the same column.

Warehouse differences. The compiled SQL is standard ANSI-ish SQL; Snowflake, BigQuery, Databricks and Postgres all execute the same pattern. Performance differs: unique on a billion-row column without a supporting statistic can be expensive on any platform. Add warehouse constraints or cluster keys in production; dbt tests do not replace physical indexing.

Combining tests on one column

The course stacks unique and not_null on listing_id. Together they approximate a primary-key constraint without enabling a formal model contract yet. Order in the YAML list does not change execution order — dbt runs tests in dependency order, not declaration order.

On host_id, the course uses not_null then relationships. That pairing is deliberate: every listing must point at a host, and that host must exist in dim_hosts_cleansed. If you only had relationships, NULL host IDs would slip through.

Declaring tests in schema.yml

Generic tests attach to models and columns in YAML. The finished course project centralises most declarations in models/schema.yml alongside descriptions and (later) contracts. dbt discovers them at parse time and registers one test node per declaration.

YAML key rename: tests: → data_tests:. Older projects and course screenshots may show tests: under a column. dbt 1.x expects data_tests: for data quality tests. Generic test parameters (values:, to:, field:) nest under arguments: rather than sitting at the same level as the test name. The course repo on the 1.11 pin already uses the current form.

Old syntax vs current syntax

If you migrate a legacy project or paste from an old blog post, translate both the key and the argument nesting:

Legacy (pre-1.8 style)

columns:
  - name: room_type
    tests:
      - accepted_values:
          values: ['Entire home/apt', ...]

Current (1.11 course)

columns:
  - name: room_type
    data_tests:
      - accepted_values:
          arguments:
            values: ['Entire home/apt', ...]

The same rename applies to sources.yml column tests and to seeds when you attach tests in seed schema YAML. Unit tests use a separate top-level unit_tests: key — not covered until Section 12.

Model-level vs column-level tests

Tests under columns: receive the column name automatically — the macro signature is (model, column_name) for built-ins. Tests under the model itself (not nested under a column) apply to the whole table. The finished repo adds a model-level custom generic test on dim_listings_cleansed:

  - name: dim_listings_cleansed
    data_tests:
      - minimum_row_count:
          arguments:
            min_row_count: 1000
          config:
            severity: error

Model-level declarations still run against the materialised relation for that model. Custom generics are covered in Section 12; the syntax pattern is identical to built-ins.

Singular tests

When a rule does not fit a generic macro — a join across models, a conditional aggregate, a window function — write a singular test: a .sql file in the tests/ directory whose name becomes the test identifier. The file must be a query that returns failing rows only.

dbt compiles Jinja in the file (ref(), source(), macros) and executes the result. Any row returned is a failure. An empty result set is a pass. This is the same pass/fail contract as generic tests, but you own the SQL entirely.

dim_listings_minimum_nights

The staging model coerces minimum_nights = 0 to 1 in dim_listings_cleansed. This singular test verifies that invariant: no row in the cleansed dimension should have minimum_nights < 1.

SELECT
    *
FROM
    {{ ref('dim_listings_cleansed') }}
WHERE minimum_nights < 1
LIMIT 10

The LIMIT 10 caps how many failing rows dbt fetches for the error message and logs. It does not cap how many violations exist — dbt still fails the test if any row matches. Use LIMIT to keep failure output readable on wide tables, not to sample away problems.

Failing-row query pattern

Think in terms of “find the bad rows”:

  • Generic not_null — WHERE column IS NULL
  • Generic unique — GROUP BY … HAVING COUNT(*) > 1
  • Singular business rule — whatever SELECT exposes the violation; often a join or inequality

To debug before adding a test, run the same SELECT in a worksheet against compiled refs. Replace {{ ref('dim_listings_cleansed') }} with your dev schema table name and confirm zero rows.

Worksheet sanity check

SELECT COUNT(*) FROM DEV.dim_listings_cleansed WHERE minimum_nights < 1

Exercise: consistent_created_at

The course exercise asks for a singular test ensuring no review was submitted before its listing existed. Logically: for each review, review_date must be on or after the listing’s created_at. Equivalently, flag rows where the listing was created after the review date.

SELECT * FROM {{ ref('dim_listings_cleansed') }} l
INNER JOIN {{ ref('fct_reviews') }} r
USING (listing_id)
WHERE l.created_at > r.review_date

Notes on this pattern:

  • USING (listing_id) requires the column name on both sides — true for these models.
  • Timestamps vs dates: if types differ, wrap with TO_DATE() or cast consistently so midnight boundaries do not create false failures.
  • An INNER JOIN only checks listings that have reviews. Orphan listings without reviews are out of scope for this rule.

Exercise walkthrough: consistent_created_at

The course exercise (course-resources.md lines 690–702) asks you to enforce a temporal rule across models. Work through it in this order:

  1. State the rule in plain English: a review cannot predate its listing’s creation.
  2. Express the violation: listing created_at is after review_date.
  3. Identify models: dim_listings_cleansed for created_at, fct_reviews for review_date, join on listing_id.
  4. Write the SELECT returning violating rows only — not a boolean, not a count.
  5. Save as tests/consistent_created_at.sql and run dbt test -s consistent_created_at.

If the test fails unexpectedly, inspect sample rows: timezone offsets on created_at vs review_date often explain one or two edge cases in sample data.

Debugging a singular test before commit

Pattern the instructor uses implicitly:

  1. Write the query with literal schema.table names in a worksheet until it returns the rows you expect (zero for a pass).
  2. Replace tables with {{ ref() }} calls.
  3. dbt compile --select consistent_created_at and diff against your worksheet query.
  4. Run dbt test on the singular test alone.
Singular tests can be expensive. A join between two large facts without filters scans both tables every test run. In production, narrow with date windows, incremental watermarks, or move heavy checks to monitored incremental assertions. The course tables are small; the pattern does not scale by default.

Storing test failures

By default, failed tests only appear in the CLI and logs. With store_failures: true, dbt persists failing rows to a table in your warehouse so analysts can inspect, join, and trend them without re-running the test query.

The course enables this globally for all tests in dbt_project.yml:

data_tests:
  +store_failures: true
  +schema: _test_failures

What gets created

On failure, dbt creates (or appends to) a relation named from the test. Convention: schema from +schema, table name derived from the test node name. You will see tables like DEV._TEST_FAILURES.not_null_dim_listings_cleansed_listing_id in Snowflake. Exact naming includes a hash suffix on some adapters to avoid collisions.

  • Columns typically mirror the failing SELECT plus metadata dbt adds (_dbt_source_relation in some versions).
  • Successful tests do not write to these tables.
  • Tables accumulate across runs unless you truncate or drop them — treat them as operational debris with a retention policy.

Per-test overrides

Override globally in YAML on a specific test:

data_tests:
  - relationships:
      arguments:
        to: ref('dim_hosts_cleansed')
        field: host_id
      config:
        store_failures: false

Teams often store failures in dev and CI but disable storage for very wide rows or PII-heavy failures in prod, relying on alerting instead.

Querying stored failures in Snowflake

After a failing run with the course config, list and inspect tables:

SHOW TABLES IN SCHEMA DEV._TEST_FAILURES;

SELECT *
FROM DEV._TEST_FAILURES.not_null_dim_listings_cleansed_listing_id
LIMIT 100;

Failure tables are ordinary relations. Join them back to dimensions on the key column to open Jira tickets with listing IDs, host names, or whatever the failing SELECT projected.

Global config in dbt_project.yml

The complete data_tests: block from the repo sits near the bottom of project config, separate from the models: tree:

models:
  airbnb:
    +materialized: view
    dim:
      +materialized: table
    src:
      +materialized: ephemeral
    fct:
      +tags: ['fact']
data_tests:
  +store_failures: true
  +schema: _test_failures

The leading + merges these settings into every test node unless a test overrides them in its own config: block. This is the same config-merge pattern as +materialized: view under models:.

Elementary and similar tools. The course mentions Elementary Data as a next step: it ingests dbt test results and artifact metadata for dashboards and alerts. store_failures is the native warehouse-native version of “keep the bad rows for me.”
Storage and compute. Every stored failure runs the failing SELECT and an INSERT/CREATE. On large tables with thousands of failing keys, you pay twice. Fix upstream, then drop old failure tables.

Restricting test execution

Full dbt test on a mature project can scan every model and column you have ever declared. Selectors limit scope during development, CI, and incident response — the same --select (or -s) syntax as dbt run, with test-specific graph operators.

Run all tests on a model

Pass the model name to run every generic and singular test that depends on that model (directly or as parent):

This includes column tests declared in YAML and singular tests that ref() the model, because they are part of the model’s test subgraph.

Tags on tests

Assign tags in a test’s config: block to group checks for nightly vs hourly runs:

data_tests:
  - not_null:
      config:
        tags: ['critical', 'nightly']

Singular tests accept a config block at the top of the SQL file via {{ config(tags=['critical']) }}. Section 17 expands selectors with selectors.yml for reusable CI graphs.

Selector syntax at dbt 1.12. Named selectors move to -s selector:name instead of --selector name. The course pin is 1.11; both forms appear in the wild. Check your version in dbt --version.

dbt build vs dbt test

dbt build runs models, seeds, snapshots, and tests in DAG order — tests execute after their dependencies build. Plain dbt test assumes relations already exist. In CI, either run dbt build --select state:modified+ or explicitly dbt run then dbt test on the same selection.

Listing tests with dbt ls

When selectors feel opaque, list before you run:

dbt ls --resource-type test
dbt ls --select dim_listings_cleansed,resource_type:test
dbt ls --select test_type:singular

The output is the exact string to pass to --select. Long generic test names are normal — copy them from dbt ls rather than typing by hand.

Tags inherited from models

Facts in the course carry +tags: ['fact'] under models/airbnb/fct: in dbt_project.yml. Tests do not automatically inherit model tags unless configured; explicitly tag critical tests when you want dbt test -s tag:critical without maintaining parallel selectors. Compiled SQL of a test

Every test is SQL. After compile, the fully expanded query lives under target/compiled/<project>/ mirroring the path of YAML macros or tests/ files. Reading compiled SQL is the fastest way to debug a surprising pass or fail.

Where to look

  • Singular tests — target/compiled/airbnb/tests/dim_listings_minimum_nights.sql
  • Generic tests — under target/compiled/airbnb/models/schema.yml/ with long auto-generated file names per test node
  • Logs — logs/dbt.log contains the exact query on failure at DEBUG level; the instructor prefers compiled files over --debug for readability

Workflow:

  1. dbt compile --select dim_listings_cleansed (or compile a specific test with dbt test --select test_name --no-run where supported, or run test once)
  2. Open the compiled file in your editor
  3. Copy the SQL into a worksheet; run it directly
  4. Compare row counts to what dbt reported

Compiled singular test example

After compile, Jinja resolves to your target schema:

SELECT
    *
FROM
    DEV.dim_listings_cleansed
WHERE minimum_nights < 1
LIMIT 10

Compiled generic test example

A unique test on listing_id compiles to something equivalent to:

SELECT
    listing_id AS unique_field,
    COUNT(*) AS n_records
FROM DEV.dim_listings_cleansed
WHERE listing_id IS NOT NULL
GROUP BY listing_id
HAVING COUNT(*) > 1

How to read the result

Prefer compiled SQL over --debug. Section 16 notes the instructor abandoned live --debug in favour of opening target/compiled/. The file is stable, searchable, and shareable in a PR comment.

Worked example: debugging relationships failure

Suppose relationships_fct_reviews_listing_id__listing_id__ref_dim_listings_cleansed_ fails with FAIL 3:

  1. Open target/compiled/airbnb/models/schema.yml/ and search for relationships and fct_reviews.
  2. Copy the compiled LEFT JOIN query into a Snowflake worksheet.
  3. Run it — you should see three orphan listing_id values.
  4. Trace each ID: missing from dim_listings_cleansed because incremental filter excluded it, or stale fact row after listing delete?
  5. Fix the model or source; dbt run --select fct_reviews dim_listings_cleansed; re-test.

This workflow is faster than reading a stack trace because you see the actual keys that violated the rule.

Reading the status tokens

TokenMeaningExit code impact
PASSZero failing rowsNone
FAIL + numberFailing rows found (error severity)Non-zero exit
WARN + numberFailing rows but severity warnZero by default in many setups; treat as pass in CI at your peril
ERRORTest query could not runNon-zero exit
SKIPDependency failed or selector excludedDepends on configuration

The number after FAIL or WARN is the count of failing rows dbt retrieved (subject to adapter limits). It is not an arbitrary code. Three orphan listing_id values in a relationships test yields FAIL 3.

After a failure

  1. Read the test name — it encodes model, column, and test type for generic tests.
  2. Open compiled SQL in target/compiled/ and run it in a worksheet.
  3. If store_failures is on, query the table in _test_failures.
  4. Fix the model, source data, or test definition; re-run dbt test --select <failed_test>.

Test naming conventions

dbt auto-generates generic test names by concatenating test type, model, column, and argument hash. Examples from this project:

  • unique_dim_listings_cleansed_listing_id
  • not_null_dim_listings_cleansed_host_id
  • accepted_values_dim_listings_cleansed_room_type__Entire_home_apt__Private_room__Shared_room__Hotel_room
  • relationships_dim_listings_cleansed_host_id__host_id__ref_dim_hosts_cleansed_

Singular tests use the file name without extension: dim_listings_minimum_nights, consistent_created_at. Rename the file and dbt renames the test node on the next parse.

Long names are awkward in terminal but self-documenting in logs and Elementary dashboards. Use dbt ls --select test_type:singular when you forget the exact string.

What happens on the first test run

After adding tests to a model that already exists in the warehouse, the first dbt test only executes the new queries — it does not rebuild the model. If you changed model logic and tests together, run dbt build --select dim_listings_cleansed+ so the table reflects the latest SQL before tests scan it. Stale model data with fresh tests is a common source of “test passes but should fail” confusion during development.

On BigQuery and Databricks, failure row counts and store_failures table names follow the same semantics; only the qualified relation syntax (project.dataset.table vs three-part names) differs in compiled output. Always read compiled SQL for your adapter rather than assuming Snowflake quoting.

Traps that catch people

  • Testing before building — running dbt test on a clean clone without dbt run first yields relation-not-found errors, not meaningful failures.
  • Old tests: key — copy-paste from a 2020 blog post silently fails parse or deprecation warnings; use data_tests: and arguments:.
  • LIMIT on singular tests — believing LIMIT 10 means “only fail if more than 10 bad rows”; any match fails the test.
  • relationships without not_null — NULL child keys pass relationships but may still be invalid; add not_null when NULL means missing data.
  • accepted_values stale list — new legitimate enum values fail until YAML updates; communicate with upstream before disabling tests.
  • Testing ephemeral models directly — no relation exists; test downstream materialised models instead.
  • Warn treated as green CI — pipelines exit 0 on WARN while dashboards show wrong data; align severity with SLAs.
  • Duplicate test coverage — same column checked in staging and mart doubles warehouse cost without adding signal.
  • store_failures PII — failure tables contain actual bad rows, which may include names, emails, or prices; restrict schema access.
  • Compiled ref wrong schema — running compiled SQL in a worksheet against PROD while dbt targeted DEV; always check dbt debug target.
  • Join logic inverted — consistent_created_at with < instead of > passes while allowing impossible timelines.
  • Empty table false pass — unique and accepted_values pass on zero rows; pair with row-count or freshness gates for critical marts.
  • Test name too long for shell — generic test node names exceed terminal width; use dbt ls --select and quote the name in PowerShell.

Production patterns

Mature teams tier tests: critical (PK, FK, revenue columns) run on every PR against a slim CI warehouse; monitoring (distribution, regex, custom singular) run nightly; experimental tests start as severity: warn until trusted. Tags encode the tier; selectors in CI reference tags, not hand-maintained model lists.

Failure storage goes to a locked-down schema with seven-day retention. Analysts join failure tables to dimension keys for triage tickets. Some teams export run_results.json from target/ to observability stacks instead of relying on CLI alone.

Pattern: PR slim tests

dbt build --select state:modified+ --exclude tag:nightly after seeding defer to prod artifacts. Catches regressions on changed models without scanning the whole DAG.

Anti-pattern: test everything on raw

Duplicating mart logic tests on raw sources and cleansed layers. Fix once in staging; test the contract at the mart boundary.

data_tests:
  +store_failures: true
  +schema: audit_test_failures
  +severity: warn   # default lenient; override to error on critical columns

# CI: dbt test -s tag:critical,config.severity:error

Interview questions

Answer each one out loud before opening it.

What are the four built-in generic tests in dbt?Fundamentals

unique, not_null, accepted_values, and relationships. They cover primary-key uniqueness, required fields, enum validation, and foreign-key integrity to another model or source.

How does dbt decide whether a test passes or fails?Fundamentals

Every test compiles to a SELECT. Zero rows returned means PASS. Any row returned means FAIL (or WARN if severity is warn). ERROR means the query could not execute — missing relation, syntax error, permission issue.

What is the difference between a generic test and a singular test?Comparison

Generic tests are declared in YAML, backed by reusable macros, and parameterised per column. Singular tests are one-off SQL files in tests/ for business rules that do not fit a macro — joins, complex inequalities, aggregates. Both use the same failing-row semantics.

Why did tests: become data_tests: in schema.yml?Gotcha

dbt split data tests from other test-like resources (unit tests, etc.) and unified config. Older material shows tests:; current projects use data_tests: with parameters under arguments:. Parsing old syntax may warn or fail depending on version.

Explain how a relationships test works internally.SQL

dbt LEFT JOINs the child model to the parent on child.column = parent.field. Rows where the child value is NOT NULL but the parent key IS NULL are returned as failures — orphan foreign keys. NULL child keys are excluded from failure by default.

Your unique test passes but stakeholders report duplicate IDs in the dashboard. What do you check?Troubleshooting

Confirm the dashboard queries the same model and schema the test targets (not a cached extract or different environment). Run the compiled unique test SQL manually. Check whether duplicates exist only in a subset filtered out by the test. Verify the test runs in production CI, not only locally. Look for incremental logic that re-inserted duplicates without merge.

What does store_failures do and when would you disable it?Production

On failure, dbt writes violating rows to a warehouse table (often in a dedicated schema like _test_failures). Disable for PII-heavy failures, extremely wide rows, or high-volume failures that would be expensive to persist. Keep enabled in dev for debugging.

How do you run only the tests related to fct_reviews?Certification

dbt test --select fct_reviews runs tests on that model and tests that reference it. Use +fct_reviews to include upstream dependencies, or fct_reviews+ for downstream. Tag selectors like tag:fact work if tests inherit fact model tags via config.

Why can testing ephemeral staging models be awkward?Modelling

Ephemeral models have no warehouse relation. Generic column tests expect a materialised table or view. You test staging logic indirectly through downstream materialised models, or temporarily switch staging to view during development.

A singular test with LIMIT 10 fails. Does that mean exactly 10 bad rows?Gotcha

No. LIMIT caps rows returned for display and logging. The test fails if any violating row exists. The failure count in CLI may show up to the limit or total depending on adapter. Use a COUNT query in a worksheet for the true total.

Where do you find the SQL dbt actually ran for a failing test?Troubleshooting

target/compiled/<project>/ mirrors test paths or YAML-generated names. logs/dbt.log has the query at debug level. With store_failures, query the failure table. The instructor recommends compiled files over live --debug.

What is the difference between dbt test and dbt build for tests?Comparison

dbt test only runs test nodes and assumes dependencies already exist. dbt build runs seeds, models, snapshots, and tests in DAG order, building prerequisites first. CI often uses build for consistency; local debugging often uses run then test on a subset.

When would you write consistent_created_at as a singular test instead of a relationships test?Design

relationships only checks key existence across tables. Temporal consistency requires comparing two date columns across a join — a custom WHERE clause. That is singular-test territory unless you build a custom generic macro for reuse.

How do WARN severity tests affect CI exit codes?Production

By default many setups exit 0 if only warnings occurred, while ERROR severity failures exit non-zero. Teams explicitly fail CI on warn for critical tests or use config.severity:error selectors. Document the policy; do not assume warn is visible in green pipelines.

Why might a unique test timeout while the table query feels fast?Performance

unique runs a full GROUP BY over the column. A selective dashboard query uses indexes or filters the test does not. On Snowflake, lack of clustering on the tested column hurts; on BigQuery, full column scan billing applies. Mitigate with physical PK constraints, smaller dev samples, or testing only incremental subsets in CI via defer and state.

What is the failing-row query for not_null and how is it different from a singular test?Testing

not_null expands to SELECT * FROM model WHERE column IS NULL. A singular test is the same contract but you write arbitrary SQL. Generic tests are reusable macros; singular tests are one file per rule. Both fail when rows are returned.

Recap

  • A dbt test passes when its SELECT returns zero rows; any row is a failure.
  • Built-in generic tests: unique, not_null, accepted_values, relationships.
  • Declare generics under data_tests: in YAML; parameters nest under arguments: (not the old tests: key).
  • Singular tests live in tests/*.sql and express one-off rules with full SQL.
  • dim_listings_minimum_nights guards the cleansed minimum_nights invariant; LIMIT only caps displayed failures.
  • consistent_created_at joins listings and reviews to catch impossible timelines.
  • store_failures: true in dbt_project.yml persists failing rows to +schema: _test_failures.
  • Restrict runs with dbt test -s model_name, graph operators, tags, and test_type: selectors.
  • Debug from target/compiled/ — compiled SQL is the ground truth for what ran.
  • CLI: PASS / FAIL n / WARN n / ERROR; FAIL with error severity exits non-zero.
  • Run models before tests on fresh environments; use dbt build for ordered run+test.
  • Custom generics, unit tests, contracts and severity depth are in Section 12.
