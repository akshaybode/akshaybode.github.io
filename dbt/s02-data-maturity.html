The Data Maturity Model

This section is pure theory — no commands yet. It explains why the course builds a staging layer before dimensions, and why jumping straight to dashboards or ML models on raw tables fails.

The maturity pyramid

Data maturity is not a checklist of tools. It is a stack of capabilities where each layer only works if the one beneath it is solid. A company that buys a BI licence before it has reliable tables is building on sand; one that trains a churn model on untested aggregates is optimising noise.

The model has four stages, ordered from foundation to summit. They are often drawn as a pyramid because the base is wide — almost every company has some data collection — and the top is narrow. Most organisations never reach stage 4 in a meaningful way, and that is usually the right outcome.

Stage 4 — Machine learning and AI. Predictive models, recommendations, LLM-assisted analytics. Requires clean, labelled, grain-stable features built from stage 3 tables.
Stage 3 — Data analytics. BI dashboards, ad-hoc analysis, agreed metrics, self-serve reporting. Requires modelled tables with documented definitions and tests.
Stage 2 — Data wrangling. Ingestion, landing raw data untouched, storage in a warehouse or lake. Requires sources from stage 1 and a place to put them.
Stage 1 — Data collection. Application databases, event streams, SaaS APIs, files, third-party feeds. The inputs you inherit, rarely under your control.

Dependency between stages

Each stage is a prerequisite for the next, not an optional upgrade. Stage 2 cannot produce trustworthy analytics if stage 1 sources are missing or silently wrong. Stage 3 cannot define revenue once if every team reads a different raw export. Stage 4 cannot learn patterns that do not exist in consistent historical tables.

The central argument of this model: skipping a stage does not skip the work — it hides it. If you deploy Looker on top of spreadsheets and raw API dumps, someone is still doing wrangling and analytics by hand in every dashboard tile. The work moved from a shared pipeline into twelve slightly different SQL snippets nobody maintains.

Everyday analogy — the pyramid is like building a house. You can paint the walls (dashboards) before the plumbing is inspected (tests on core tables), but the first time it rains you discover the roof was never finished (reliable ingestion). dbt is the framing and inspection between foundation and finish — not the foundation itself, and not the furniture.

Stage 1: data collection

Stage 1 is everything that happens before your team touches the data. Application engineers write rows to databases. Product teams emit events. Finance uses SaaS tools. Partners send files. Your job starts with inheriting those shapes, not designing them.

Source types a data team inherits

Application databases

PostgreSQL, MySQL, SQL Server — the system of record for transactions. Normalised schemas, frequent updates, sometimes direct queries you should not run in production.

Event streams

Clickstream, product analytics, IoT. High volume, semi-structured JSON, timestamps that matter more than relational keys.

SaaS APIs

Salesforce, Stripe, Zendesk. Convenient but vendor-controlled schemas, rate limits, and breaking API version changes.

Files and third-party

CSV dumps, SFTP drops, market data, ad networks. Often the messiest: wrong encodings, header rows that move, columns added without notice.

Volume, velocity and variety

The old “three Vs” still describe why stage 1 is hard. Volume determines whether you need a warehouse at all — the Airbnb course uses small CSVs, but production reviews tables are billions of rows. Velocity determines batch versus streaming: nightly loads are stage 2 with Fivetran; sub-minute latency is a different architecture entirely, and dbt is not the answer there. Variety is what forces staging later: the same business concept arrives as a string with a currency symbol in one source and as a numeric column in another.

Why you rarely control the input shape

Data teams almost never own the upstream schema. Product ships a new column when a feature launches. A vendor renames a field in an API response. A legacy system stores price as text because that was expedient in 2014. You cannot rewrite history; you can only land what arrived and document what it meant on the day it landed.

That constraint is the main reason every mature pipeline has a staging layer in stage 2 and 3: one place to rename columns, cast types, and isolate upstream breakage before it reaches a dashboard or a fact table. In the course project, the three raw tables are deliberately imperfect so you practice exactly that.

dbt never appears at stage 1 in a real company. It does not extract from CSVs on a laptop or poll an API. The course pretends the load already happened so you can focus on everything that comes after — which is the job analytics engineers actually own.

Sources versus seeds. In dbt, source() declares tables something else loaded — your stage 1 artefacts. seed is for small reference files the analytics team owns, like the full-moon calendar in Section 9. Do not use a seed to stand in for a production ingestion pipeline.

Stage 2: data wrangling

Stage 2 is ingestion and storage: getting stage 1 data into a system where SQL can run at scale, leaving it as untouched as practical, and keeping enough history to recover when something breaks.

Ingestion tools and patterns

Most teams use a managed loader rather than writing extract code from scratch. Common choices:

  • Fivetran, Airbyte, Stitch — SaaS connectors that sync sources on a schedule, handle API pagination, and write append or upsert loads into your warehouse.
  • Cloud-native pipes — Snowpipe, BigQuery load jobs, Databricks Auto Loader for files landing in object storage.
  • Custom scripts — Python or Spark jobs when no connector exists or when you need business logic at extract time (usually less than people think).

The course skips this layer: the CSVs are already in RAW. In a job interview, still be able to name who owns extract/load versus transform — dbt is firmly on the transform side.

Load first, transform later

For decades the default pattern was ETL: transform in a middle tier, then load clean tables. Cloud warehouses changed the economics. Storage got cheap; compute separated from storage; SQL engines became fast enough to transform in place. ELT won: extract and load raw into the warehouse, then transform with SQL (and dbt) where the data already lives.

Loading raw data untouched has three practical benefits. First, when a transformation bug ships, you can reprocess from the raw layer without re-requesting data from vendors. Second, you preserve fields nobody needed yet — product will ask for a column that existed in the source six months ago. Third, audit and compliance often require proving what arrived, not just what you chose to keep.

Raw is not dirty by accident. Landing raw_reviews exactly as the export arrived is a design choice. The cleansing belongs in src_reviews and downstream models, where it is version controlled and tested — not buried in a one-off load script.

Where stage 2 ends and stage 3 begins

Stage 2 ends at the boundary of structurally faithful copies of sources. Stage 3 begins when you rename, join, aggregate, and encode business rules. That boundary is exactly where dbt's source() and staging models live: dbt reads from raw, but the work it does is stage 3 transformation on top of stage 2 storage.

The modern data stack — loader, warehouse, dbt, BI — is largely a story about making stages 2 and 3 repeatable at scale. Section 4 names the tools and the ELT argument in full; this section only establishes where each stage sits.

Medallion and the raw layer

Many teams label layers bronze (raw), silver (cleaned/conformed), gold (business-ready). The course's RAW schema is bronze; src_* models are the first silver touch; dim_*, fct_*, and mart_* are gold. Naming varies by company, but the idea is constant: do not mix upstream mess with metrics consumers trust.

Stage 3: data analytics

Stage 3 is where data becomes decisions: dashboards, exploratory analysis, KPIs with owners, and definitions that stay stable when the CEO asks the same question twice. This is the stage dbt was built for.

BI, ad-hoc analysis and metrics

Analytics work splits into three overlapping modes. BI and dashboards serve recurring questions — daily active listings, review volume, host growth — to people who will never write SQL. Ad-hoc analysis answers one-off questions with notebooks or worksheets, often faster but rarely governed. Metrics definitions are the contracts between them: what exactly counts as an active listing, whether cancelled bookings subtract from revenue, which timezone defines “today”.

Without a transformation layer, each mode reinvents the definitions. The dashboard builder writes one CASE for price; the analyst exports another; the board deck uses a spreadsheet from finance. Everyone is doing stage 3 work; nobody is doing it in one place.

The different revenue number problem

The classic failure mode: two dashboards, two revenue figures, both “correct” under different assumptions. One sums listing price times nights booked; one uses host payout after fees; one excludes test listings someone forgot to filter. Meetings become theology debates instead of strategy.

The fix is not a better BI tool. It is a single modelled table — say fct_reviews joined to dim_listings_cleansed with price already cast to numeric — documented in YAML, tested for grain and nulls, and referenced by every downstream consumer. When the definition changes, one pull request updates the model and the tests fail if the change breaks an invariant.

Dashboards on raw tables scale badly. Every tile re-implements cleansing logic. When raw_listings.price changes format, twelve dashboards break in twelve different ways. Centralising cleansing in dim_listings_cleansed means one fix propagates everywhere dbt runs.

How the Airbnb project embodies stage 3

By the end of the course, stage 3 artefacts include:

  • Staging — src_listings, src_hosts, src_reviews rename and expose raw columns without business rules.
  • Dimensions — dim_listings_cleansed, dim_hosts_cleansed, dim_listings_w_hosts encode cleansing and conformed grains.
  • Facts — fct_reviews holds review events at the right grain for analysis, incrementally maintained.
  • Marts — mart_fullmoon_reviews answers a specific analytical question with a tested, documented dataset.

Stage 4: machine learning and AI

Stage 4 turns reliable historical tables into predictions: churn scores, recommendations, demand forecasts, and increasingly LLM-powered question answering over governed metrics. It is the narrow top of the pyramid for a reason — most of the work is still stage 3 done well.

Feature engineering on modelled tables

Machine learning models rarely consume raw SaaS exports. They consume features: numeric or categorical columns at a defined grain, aligned in time, with nulls handled consistently. Those features are almost always SQL aggregations over dimensions and facts — average review sentiment per listing per month, host tenure in days, price percentile within neighbourhood.

In the Airbnb project, a stage 4 feature might join fct_reviews to dim_listings_cleansed and compute rolling sentiment averages. If price were still a string in raw, or if fct_reviews double-counted rows, the model would learn artefacts of bad SQL, not patterns in guest behaviour.

Why dimensional tables are the real prerequisite

Data scientists often ask for a “feature store” before anyone has stable dimensions. A feature store caches and serves features for training and inference — useful at scale, irrelevant if the underlying definition of listing changes weekly. Reliable dim_* tables with documented slowly changing dimension policy, plus tested fct_* grains, deliver more value than any serving layer built on top of chaos.

Snapshots in the course (Section 10) exist partly because ML needs point-in-time correctness: a training label must use host attributes as they were on the review date, not today's superhost flag.

Feature stores in one paragraph

A feature store (Feast, Tecton, warehouse-native offerings) registers feature definitions, materialises them on a schedule, and serves the same values in training and production to avoid train-serve skew. It sits above stage 3 tables, not instead of them. Teams without mature dimensions should treat a feature store as a stage 4 aspiration, not a shortcut past stage 3.

Most companies should not be here yet

If dashboards still disagree, if raw loads are manual, if nobody owns data quality on core entities, stage 4 projects produce demos that never reach production. The honest assessment most analytics engineers should make: our organisation is optimising stage 3; ML is a pilot, not the backbone. That is normal and healthy.

AI-assisted analytics is not stage 4 only. Natural-language-to-SQL over a semantic layer is increasingly a stage 3 tool — it still requires governed metrics and column descriptions to answer safely. Section 20 touches AI in the dbt context; the maturity prerequisite remains the same.

Where dbt fits

dbt spans the upper part of stage 2's output and nearly all of stage 3. It transforms data already in the warehouse; it does not collect it, does not schedule itself, and does not replace your BI tool.

Stage 4 — ML / AI. Downstream of dbt marts; dbt may build feature tables but does not train models.
Stage 3 — Analytics. dbt core territory Dimensions, facts, marts, tests, docs, exposures to dashboards.

What dbt does

  • Compile modular SQL with Jinja into warehouse-native statements
  • Build and refresh tables, views, incremental models, snapshots
  • Run tests and stop the DAG when they fail (dbt build)
  • Generate documentation and lineage from the project graph
  • Apply software engineering workflow: packages, macros, environments, CI

What dbt does not do

The course Airbnb pipeline is the canonical picture: something external loaded raw_*; dbt builds everything a analyst or dashboard reads from src_* onward. Keeping that boundary clear prevents the most common organisational mistake — hiring dbt to fix an ingestion problem it cannot see.

Certification framing: exam questions often test this boundary. dbt transforms inside the warehouse; it is not an ETL server, not an orchestrator, and not a visualization layer. When a question lists tools for “loading Salesforce into Snowflake,” dbt is the wrong answer.

Traps that catch people

  • Confusing tool purchase with maturity — signing Snowflake and Looker contracts does not create tested metric definitions. Tools enable stages; people and process climb them.
  • Letting analysts own stage 2 — when loading is manual, vacations become outages. Extract/load needs the same on-call discipline as production apps.
  • Skipping staging because raw “looks fine” — raw_listings.price looks readable until currency symbols break a sum. Staging isolates upstream change to one model.
  • Calling spreadsheets stage 3 — a shared Excel is not a transformation layer. It has no tests, no lineage, and no deploy process.
  • Expecting dbt to backfill ingestion gaps — if raw_reviews stopped loading, dbt runs succeed on stale data. Freshness tests on sources exist precisely for this.
  • Building ML on dashboard SQL — BI tools generate queries; they do not guarantee stable grains. Features must come from named models like fct_reviews.
  • Treating the pyramid as linear forever — mature teams iterate all stages in parallel, but still respect dependencies. You fix ingestion while extending marts; you do not pause all stage 3 work forever.
  • Over-engineering stage 2 for course-scale data — the Airbnb CSVs fit in memory. Production needs partitions and incremental loads; the course deliberately keeps stage 2 simple so stage 3 fits in one repo.
  • Undervaluing documentation as stage 3 — a model without a description in schema.yml is not finished. Consumers cannot trust what they cannot read.
  • Assuming one person spans all four stages equally — startups hire generalists; enterprises split data engineering (1–2) from analytics engineering (3) from ML (4). Know which stage your job emphasizes.

Production patterns

Stage ownership RACI

Platform or data engineering owns stages 1–2 SLAs. Analytics engineering owns stage 3 models and tests. ML platform owns stage 4 serving — but only after signing off on upstream grains. Document this in a one-page data architecture wiki linked from the dbt project README.

Maturity assessment quarterly

Rate each business domain (marketing, finance, product) on the four stages 1–5 scale. Domains stuck at stage 2 do not get ML budget. Domains at stage 3 get dbt investment. The exercise prevents uniform tooling mandates that ignore reality.

The anti-pattern: a single “data platform team” asked to deliver ML, dashboards, ingestion fixes, and governance simultaneously with four engineers. The pyramid explains why that team burns out — it is four jobs with four skill profiles. Splitting ownership by stage, with dbt as the contract between 2 and 3, scales further than hero analysts.

Interview questions

Answer each one out loud before opening it.

What are the four stages of the data maturity model, and why is order important?Fundamentals

Collection (sources you inherit), wrangling (ingestion and raw storage), analytics (modelled metrics and BI), and machine learning (predictive features and models). Order matters because each stage consumes the output of the previous one: you cannot define trusted revenue without loaded raw data and conformed dimensions; you cannot train reliable ML on metrics that disagree across dashboards.

Skipping a stage does not eliminate the work — it pushes it into manual fixes, one-off SQL, and meetings about definitions. The pyramid is a dependency diagram, not a shopping list.

Where does dbt sit relative to extract, load, transform, and BI?Fundamentals

dbt owns transform inside the warehouse after load. Extract and load are handled by connectors, scripts, or cloud ingestion — Fivetran, Airbyte, Snowpipe, and similar. dbt reads from raw or staging relations via source() and ref(), builds modelled tables, runs tests, and publishes docs. BI and ML tools read the outputs; dbt does not render charts or train models.

Scheduling is also external: cron, Airflow, Dagster, or dbt Cloud jobs invoke dbt build; dbt has no built-in scheduler.

Why load raw data unchanged instead of cleaning during extract?Design

ELT separates durability from business logic. Raw landing preserves what actually arrived for audit, replay, and reprocessing when transform code was wrong. It also keeps columns nobody needs yet, which product will eventually ask for.

Cleaning during extract couples ingestion to analytics definitions — every metric change requires re-extracting history. Transforming in the warehouse with versioned SQL lets you fix logic once and rebuild downstream models without touching the loader.

Two dashboards show different revenue. How does the maturity model explain that failure?Troubleshooting

It is a stage 3 failure: analytics without a single governed transformation layer. Each dashboard implemented its own cleansing and business rules on top of stage 2 raw or lightly processed tables, so definitions diverged silently.

The fix is consolidating revenue logic into one tested dbt model at an agreed grain, documenting it, and pointing both dashboards at that model or a semantic layer built on it. Tool upgrades without that step repeat the problem.

When would you tell leadership the company is not ready for machine learning?Design

When stage 3 prerequisites are missing: core entities lack tested dimensions and facts, metrics disagree across teams, ingestion has no monitoring, or nobody can explain grain on the main fact table. ML on that foundation produces demos that fail in production because features inherit the same inconsistencies.

The recommendation is to invest in modelled tables, tests, and ownership first — often faster ROI than a data science hire building features from scratch in notebooks.

What is the difference between stage 2 wrangling and stage 3 analytics in practice?Comparison

Stage 2 is moving bytes faithfully: sync schedules, raw schemas, retention, load monitoring. The data still looks like the source. Stage 3 is encoding business meaning: renamed columns, typed prices, conformed host and listing grains, aggregated facts, documented metrics.

In the Airbnb project, raw_listings is stage 2; dim_listings_cleansed is stage 3. dbt starts at the boundary — src_listings is thin staging, still closer to stage 3 because it is versioned project code, not a loader setting.

How do volume, velocity, and variety affect which maturity investments come first?Fundamentals

High volume forces stage 2 warehouse choice and partition strategy before fancy stage 3 marts. High velocity pushes streaming or micro-batch ingestion — outside dbt's batch sweet spot. High variety forces explicit staging models per source so type mismatches do not propagate.

A small, low-velocity dataset like the course Airbnb files can skip expensive stage 2 tooling but still needs stage 3 patterns because variety (string prices, nullable names) is what breaks naive dashboards.

What role does a feature store play in the maturity model?Comparison

A feature store is a stage 4 serving layer: it registers feature definitions, materialises them on a schedule, and serves consistent values for training and inference to reduce train-serve skew. It assumes stage 3 already provides stable dimensions and facts to compute from.

Without governed upstream models, a feature store merely caches inconsistent SQL faster. Build dim_* and fct_* with tests first; add Feast or Tecton when multiple models reuse the same features at scale.

Why does the course use raw tables loaded outside dbt instead of dbt seeds for everything?Gotcha

Because production raw data is loaded by extract/load tools, not by dbt. Seeds are small reference datasets the analytics team owns — like seed_full_moon_dates.csv — not a stand-in for nightly Fivetran syncs into RAW.

Using source() on raw_listings teaches the correct mental model: dbt transforms data someone else landed. Confusing seeds with ingestion leads teams to run inappropriate full reloads through git.

Explain ELT versus ETL using the four maturity stages.Comparison

ETL transforms before load — stage 2 and early stage 3 work happened in a separate server. ELT loads raw in stage 2, then transforms with warehouse SQL in stage 3. Cloud warehouses made ELT default because compute scaled separately and SQL transformations became cheap enough to run in place.

dbt is the canonical T in ELT. It does not replace stage 2 loaders; it makes stage 3 repeatable, tested, and deployable like software.

Recap

  • Data maturity has four stages: collection, wrangling, analytics, machine learning. Each depends on the stage below.
  • Skipping a stage hides work in manual SQL and metric debates; it does not remove the work.
  • Stage 1 sources — app DBs, events, SaaS, files — arrive in shapes you rarely control; the Airbnb raw_* tables are deliberately imperfect.
  • Stage 2 lands raw data in the warehouse (ELT); loaders like Fivetran and Airbyte live here, not dbt.
  • Stage 3 is trusted analytics: modelled tables, tests, docs, single definitions for KPIs like revenue.
  • Stage 4 needs reliable dimensions and facts; most companies should invest in stage 3 before scaling ML.
  • dbt spans the top of stage 2 (sources, snapshots) and most of stage 3 (models, tests, marts).
  • dbt does not extract, load, orchestrate, serve BI, or train models.
  • The course DAG — raw_* → src_* → dim_* / fct_* → mart_* — is a stage 3 pipeline on stage 2 storage.
  • When dashboards disagree, the fix is a shared transformation layer, not a new BI licence.
  • Section 4 continues the ELT and modern data stack story from stage 2 onward.
