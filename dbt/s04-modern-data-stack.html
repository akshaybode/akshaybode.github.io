ETL: extract, transform, load

For twenty years, the default data pipeline pattern was extract from sources, transform on a separate server, then load the finished tables into a warehouse. That order was not an accident — it was the rational response to expensive storage, expensive compute and rigid warehouse engines that could not do much beyond serving pre-built tables.

The classic ETL pattern

In the classic pattern, data leaves the source system and passes through a transformation engine before it ever reaches the warehouse. The engine might be Informatica, Talend, Microsoft SSIS, a hand-rolled Python script on a cron job, or a stored-procedure chain inside an on-prem database. Regardless of tool, the shape is the same: read from A, reshape in the middle, write to B.

The warehouse received curated, denormalised tables. Raw source rows rarely landed intact. If a column was messy, the ETL job cleaned it before load. If two sources needed joining, the join happened in the middle tier. The warehouse was treated as an expensive filing cabinet for finished goods, not a workshop.

Why transformation happened before loading

Three constraints drove that design, and they reinforced each other.

Storage was expensive. Keeping every raw row forever in a warehouse billed per gigabyte per month. Teams loaded only what they had already shaped into something useful, which meant throwing away or never copying messy fields, duplicate keys and columns nobody had named yet.

Compute was expensive and fixed. The transformation engine often ran on a dedicated ETL server or a batch cluster whose size you provisioned months ahead. You paid for that capacity whether the nightly job took twenty minutes or four hours. It made sense to do heavy work there and ship small, finished tables to the warehouse.

Warehouses were rigid. Traditional MPP databases and early cloud warehouses could scan and aggregate, but they were awkward places to express complex business logic, had poor tooling for version control, and charged you to store data you might never query. Transformation outside the warehouse kept the bill down and kept analysts away from production schemas they could accidentally break.

Everyday analogy — ETL is a commercial kitchen that receives raw ingredients, cooks everything off-site, and delivers plated meals to a restaurant that only has a warming drawer. The restaurant never sees the flour, the bones or the failed batch of sauce.

The tooling generation: Informatica, Talend, SSIS, Python

Enterprise ETL tools dominated large companies for a decade. Informatica and Talend offered visual DAG editors where transformations were boxes and wires. SSIS shipped with SQL Server and filled the same niche in Microsoft shops. They handled connectivity to dozens of source systems, scheduling, error handling and operational monitoring — things a warehouse alone did not provide.

Smaller teams often skipped the licence fees and wrote Python or Scala jobs: pull from an API, pandas-transform, bulk-insert into Postgres or Redshift. The pattern was identical; only the tooling differed. In every case the transformation logic lived outside the warehouse, in a runtime the analytics team did not always control.

Real failure modes of ETL

ETL worked until organisations needed to move faster than a central pipeline team could schedule changes. The failure modes are structural, not accidental.

  • Transformation logic locked in a GUI — a business rule lives as a box on a canvas in Informatica. You cannot diff it in git, you cannot review it in a pull request, and when the author leaves, the job becomes archaeology.
  • No version control — even when SQL snippets exist, they are exported XML or checked into a tool-specific format nobody reads outside the ETL server. Rolling back a bad deploy means restoring a backup of the job repository, not reverting a commit.
  • No tests — ETL tools have row-count checks at best. Nobody asserts that status is one of five values, that grain is one row per order, or that revenue matches finance's definition. Bad data reaches dashboards and the first signal is an angry Slack message.
  • Re-processing means re-extracting — if you fix a transformation bug, you often re-pull from the source because the warehouse never kept the raw rows. That re-extract may be slow, may hit API rate limits, and may be impossible if the source no longer has historical data.
  • One team owns the pipeline — analysts who understand the business cannot safely change the transform layer. Every new metric queues behind a data-engineering backlog. Definitions diverge in spreadsheet pivots while everyone waits for the same ETL job to be edited.
ETL is not wrong for every workload. Streaming ingestion, heavy ML feature engineering outside SQL, and compliance pipelines that must strip PII before data enters a shared store still look like ETL or ETL-adjacent patterns. The shift to ELT is about analytics on a cloud warehouse, not a universal law.

ELT: extract, load, transform

ELT reverses the middle steps: extract from sources, load raw data into the warehouse cheaply, then transform with SQL inside the warehouse itself. The pattern only became dominant once storage separated from compute, warehouses scaled elastically, and SQL engines got fast enough to be the transformation runtime.

What cheap storage and elastic compute changed

Cloud warehouses decoupled storage from compute. On Snowflake, BigQuery, Databricks and Redshift, you pay for storage at object-store rates and spin compute up or down independently. Keeping a full copy of raw data is affordable. Running a heavy transformation for an hour and then suspending the warehouse is affordable. Re-running yesterday's logic against five years of history without re-touching the source is affordable.

That economics change the design. There is no longer a strong reason to discard messy columns at the door. Land everything, keep it append-only or slowly mutable in a RAW schema, and let downstream models decide what to expose. When a bug is found in a cleansing rule, you fix the SQL and re-run — the inputs are still there.

Raw data lands untouched and is kept

In ELT, the loader's job is fidelity, not business logic. Fivetran copies raw_listings with the price still a string containing $ because that is what the source had. dbt's src_listings and dim_listings_cleansed models — built in Section 7 — are where cleansing happens. If marketing later decides they need the original string for an audit, it still exists in AIRBNB.RAW.

Retention policy becomes a governance question rather than a pipeline constraint. Time Travel on Snowflake, partition expiry on BigQuery, and lifecycle rules on object storage give you cheap history without re-extracting from SaaS APIs that only expose the last ninety days.

Transformation becomes SQL inside the warehouse

The warehouse is now the compute engine. Joins, aggregations, window functions and case expressions run where the data already lives. No bulk export to a Spark cluster, no CSV round trip, no second copy in flight. On Snowflake the course uses, dbt sends SQL over a connection; Snowflake's warehouse does the work and bills you for credits consumed.

That shift is why dbt exists. dbt does not replace the warehouse engine — it organises the SQL that the engine runs. A folder of .sql files becomes a dependency-ordered pipeline with tests and documentation, which is what the ETL GUI never provided but git-native analytics teams needed.

Re-processing is a re-run, not a re-extract

Fix a bug in dim_listings_cleansed, run dbt run --select dim_listings_cleansed+, and every downstream model rebuilds from the raw tables already in Snowflake. You do not call the Airbnb CSV again. You do not re-run Fivetran unless the source schema changed.

That property is the operational payoff of ELT. Incidents shorten from "wait for a full re-extract this weekend" to "merge the fix and run the DAG". Incremental models and snapshots (Sections 8 and 10) refine the cost of those re-runs, but the raw layer is always the reset button.

Transformation logic as reviewable code

When transformation is SQL in git, anyone who reads SQL can review a pull request. Analysts with strong SQL can contribute models. Data engineers focus on ingestion and platform. Tests live next to the models they protect. Documentation generates from the same YAML that defines tests. The transformation layer inherits software-engineering practice instead of resisting it.

The T in ELT is where analytics engineering lives. Extraction and loading remain specialised — connectors, credentials, rate limits, schema drift detection. Transformation is where business definitions live, and that is the layer dbt was built to own.

The layers of the modern data stack

"Modern data stack" is a label for a particular arrangement: SaaS and cloud-native tools snapped together around a central warehouse, with dbt at the transformation layer. The label is imperfect, but the layer model is a useful map for where each tool in this course sits.

Cross-cutting: cataloguing & governance — Alation, Atlan, Collibra, Snowflake Horizon, Unity Catalog. Business glossary, PII tagging, access policies, column lineage across tools.
Cross-cutting: observability & data quality — Monte Carlo, Soda, Elementary, dbt tests. Freshness alerts, anomaly detection, incident workflows when pipelines break silently.
Cross-cutting: reverse ETL — Census, Hightouch, RudderStack. Sync modeled warehouse tables back into SaaS tools (Salesforce, Braze, ad platforms).
Serving / BI — Preset (Superset), Looker, Tableau, Power BI, Hex, Mode. Dashboards, self-serve exploration, embedded analytics. The course uses Preset against Snowflake.
Orchestration — Dagster, Airflow, Prefect, dbt Cloud jobs. Schedules dependencies, passes variables, retries failures, coordinates dbt with non-dbt steps. The course uses Dagster (Section 18).
Transformation — dbt Core or dbt Cloud. SQL models, tests, documentation, snapshots, lineage. Owns the T only.
Storage / compute (warehouse) — Snowflake, BigQuery, Databricks, Redshift, Postgres. Stores data and executes SQL. The course uses Snowflake database AIRBNB.
Ingestion / loading — Fivetran, Airbyte, Stitch, Meltano, Snowpipe, custom scripts. Extracts from sources and loads into the warehouse raw layer. The course loads CSVs via Snowflake COPY INTO instead of a SaaS loader.
Data sources — Application databases, SaaS APIs, event streams, files, spreadsheets. The course's sources are three CSV datasets representing listings, hosts and reviews.

Data sources

Everything upstream of your warehouse: production Postgres, Salesforce, Stripe webhooks, Kafka topics, S3 buckets, Google Sheets someone refuses to retire. Sources define freshness expectations, schema volatility and compliance boundaries. The Airbnb course simplifies this to static CSV files on S3 loaded once into AIRBNB.RAW, but the layer is the same — without source data in the warehouse, dbt has nothing to transform.

Ingestion and loading

Loaders move data from sources into warehouse tables with minimal transformation. Managed EL tools (Fivetran, Airbyte, Stitch, Meltano) handle connectors, incremental sync, primary-key detection and schema drift alerts. Custom paths use Snowpipe, Kafka connectors, or Python. Responsibility: reliable delivery, credential management, and landing a faithful copy in a raw schema. Not business logic, not aggregations, not naming conventions for metrics.

The course skips a SaaS loader and uses Snowflake SQL:

                     listing_url string,

Storage and compute

The warehouse is the system of record and the SQL execution engine. Snowflake separates storage (micro-partitions in cloud object storage) from compute (virtual warehouses sized in credits). BigQuery bills on-demand by bytes scanned. Databricks unifies lake storage (Delta/Iceberg) with Spark and SQL warehouses. This layer persists raw and transformed tables, enforces roles and grants, and runs every dbt model. Section 3 compares warehouse, lake and lakehouse shapes; this course commits to Snowflake.

Transformation

dbt sits here exclusively. It compiles project SQL, builds tables and views in dependency order, runs tests, generates docs and tracks lineage. It does not schedule itself, does not extract, and does not serve charts. In the Airbnb project, transformation turns RAW.RAW_LISTINGS into staging models, dimensions like dim_listings_cleansed, facts like fct_reviews, and marts like mart_fullmoon_reviews.

Orchestration

Something must invoke dbt on a cadence and handle failures. Options include cron, Apache Airflow, Prefect, Dagster, Azure Data Factory, and dbt Cloud's job scheduler. Orchestrators pass variables (date windows for incremental runs), run non-dbt steps (exports, ML training), and surface SLAs. The course scaffolds a Dagster project with dagster-dbt and runs dagster dev locally (Section 18).

Serving and BI

BI tools query the tables dbt builds. Preset is a hosted Apache Superset offering; the course creates a Snowflake PRESET user with the REPORTER role and builds an executive dashboard exposed in dbt as an exposure (Section 15). Looker, Tableau and Power BI play the same layer in other companies. Responsibility: visualisation, exploration, and sometimes a semantic layer — though metric definitions ideally originate in dbt, not in twelve conflicting workbook calculated fields.

Cataloguing and governance

As stack surface area grows, teams add catalogues (Alation, Atlan, Collibra) and warehouse-native governance (Snowflake Horizon, Unity Catalog). These tools index tables across systems, document owners, classify sensitive columns, and enforce access. dbt's generated docs and manifest.json feed many of them, but they also track assets dbt never touches — raw landing tables, BI dashboards, ML features.

Observability and data quality

Beyond dbt tests, platforms like Monte Carlo, Soda and Elementary monitor freshness, volume anomalies and schema changes in production. dbt tests catch bad values; observability tools catch "the pipeline ran but the row count dropped 40%". The course uses dbt built-in tests plus dbt_expectations (Section 16); larger teams add a dedicated observability layer.

Reverse ETL

Reverse ETL tools (Census, Hightouch) sync curated warehouse segments back into operational systems — pushing a "high LTV customer" list into Salesforce or an ad audience into Meta. They read the same marts BI tools read, but write outward. Not part of the course project, but commonly drawn as an arrow leaving the serving layer back to SaaS apps.

Where dbt sits, precisely

dbt owns the T and only the T. It is the transformation layer in an ELT stack: the place where raw warehouse tables become tested, documented datasets with agreed business meaning. Everything else is a different product with a different job.

What dbt adds on top of raw SQL

You could run the same transforms as naked SQL scripts in Snowflake worksheets. dbt adds the engineering wrapper that makes that approach survivable at team scale.

  • Dependency resolution from ref() — models declare parents; dbt builds the DAG and runs in order. See Section 7 for the first models that use it.
  • Environments — the same project compiles to DEV or PROD schemas via profiles.yml targets without editing model SQL.
  • Materialisation strategies — view, table, incremental, ephemeral, snapshots; each model picks how it persists. Covered in Section 8.
  • Tests — schema tests, singular tests, unit tests, contracts. A failing test can block downstream builds when you use dbt build.
  • Documentation and lineage — descriptions in YAML become a static docs site with a graph of dependencies.
  • Version control — transformations live in git, reviewed like application code.
  • Reusable macros — Jinja macros deduplicate patterns across models (Section 13).
Certification: expect a question that lists five things dbt does and asks you to pick the one it does not — scheduling, extracting, and serving dashboards are the usual wrong answers.

Sources versus refs

Models built by dbt reference each other with ref(). Tables loaded by something else — Fivetran, a script, Snowflake COPY — are declared in sources.yml and referenced with source(). That distinction marks the boundary between the L layer and the T layer. The staging model src_listings reads source('airbnb', 'listings') (configured to point at RAW.RAW_LISTINGS); everything downstream reads ref().

WITH raw_listings AS (
    SELECT *
    FROM AIRBNB.RAW.RAW_LISTINGS
)
SELECT
    id AS listing_id,
    name AS listing_name,
    ...
FROM raw_listings

By Section 9 the hard-coded name becomes a proper source() call with freshness tests — the pattern is the same.

Tools around dbt in the wider ecosystem

The course stack is intentionally small. In production you often add Fivetran or Airbyte at the load layer, Elementary or Monte Carlo for observability, and Census for reverse ETL. dbt integrates with all of them by convention: loaders land raw tables dbt sources point at; observability tools read manifest.json and warehouse metadata; reverse ETL reads marts dbt builds. dbt Labs also sells dbt Cloud, which collapses orchestration, CI and development into one product — the course uses Core plus Dagster instead so you see each layer separately.

Criticisms and where the stack is heading

The modern data stack solved real problems — slow ETL queues, opaque transformations, warehouse bills for unused rigid capacity — but it introduced its own costs and abstractions. A working analytics engineer should know the counterarguments without dismissing either side.

Tool sprawl and cost. A minimal stack is already loader + warehouse + dbt + orchestrator + BI + git + CI. Each line item has a subscription or a cloud meter. Fivetran bills on monthly active rows; Snowflake bills on storage and warehouse uptime; Preset and dbt Cloud bill per seat; GitHub Actions bills on minutes. Teams discover they spend more on integration and overlap than they saved leaving Informatica. FinOps for data — tagging workloads, right-sizing warehouses, incremental models instead of nightly full refreshes — becomes a discipline of its own.

"Modern data stack" as marketing. The phrase was popularised by vendors whose business model depends on you buying six SaaS products instead of one. Critics note that best-of-breed composability favors well-funded US tech companies with dedicated data platform teams. Smaller orgs sometimes get further with Postgres, Metabase and a single strong analyst than with a fully snapped-together MDS. The pattern is a default, not a moral upgrade.

Consolidation and the semantic layer. The pendulum is swinging back toward integrated platforms: Snowflake buying Streamlit, Databricks pushing Unity Catalog and AI/BI, dbt Cloud adding scheduling and the Semantic Layer. The Semantic Layer (formerly dbt Metrics) aims to centralise metric definitions so Looker, Preset and Excel do not each redefine "revenue". Data contracts push schema guarantees upstream so loaders cannot silently break dbt models. Open table formats (Iceberg, Delta) blur warehouse/lake boundaries from Section 3. AI-assisted SQL and transformation copilots sit on top but still need the same layer boundaries — someone must own definitions, tests and lineage.

None of this makes ELT wrong. It means the stack is evolving toward fewer hand-wired pipes and stronger contracts at layer boundaries. dbt's bet remains that transformation should be code in the warehouse; the open question is how much orchestration, metrics and cataloguing fold into the same tool versus stay separate.

Traps that catch people

  • Calling the whole stack "dbt" — stakeholders say "dbt is down" when Fivetran failed or Snowflake suspended the warehouse. Clarify layer boundaries in incident comms.
  • Assuming raw is always present — teams migrate from ETL and never backfill raw history. ELT's re-run advantage only works if someone actually loaded the raw tables.
  • Transforming in the loader — Fivetran and Airbyte support column hashing and basic casts. Business logic there is invisible to dbt lineage and duplicates in models later.
  • No orchestration layer — cron runs dbt run without dbt test or freshness checks. Dashboards update with untested data; use dbt build from Dagster instead.
  • Hard-coded schemas in models — bypasses environment separation. Same failure mode as ETL: dev code touches prod relations.
  • BI semantic layer overrides dbt — Preset metrics contradict mart_fullmoon_reviews because an analyst added a calculated field. Pick one source of truth for definitions.
  • Treating views as free at every layer — a stack of views from raw to mart means one dashboard query scans everything. Materialise the mart.
  • Ignoring loader schema drift — a new nullable column is fine; a type change or rename breaks compiled SQL until sources.yml and staging models update.
  • Reverse ETL before mart quality — syncing immature data into Salesforce amplifies errors into operational tools.

Production patterns

Mature teams document their stack as a diagram with named owners per layer. Ingestion is owned by data platform; dbt project by analytics engineering; BI by analytics or product; orchestration often shared. Contracts at the raw-to-staging boundary — column names, types, freshness SLAs — prevent the loader from becoming a shadow transform layer.

Anti-pattern: "ELT without the L" — analysts write dbt models against production application databases via federated queries. You skip reliable loading, overload operational OLTP systems, and lose raw history. The fix is always a dedicated load into the warehouse first, even if it is a nightly export rather than Fivetran.

Interview questions

Answer each one out loud before opening it.

Explain ETL and name two structural reasons it dominated before cloud warehouses.Fundamentals

ETL extracts data from sources, transforms it on a separate engine, then loads finished tables into a warehouse. Transformation happened outside the warehouse because storage and compute were both expensive and fixed-size, and because legacy warehouses were poor places to express and version complex business logic.

Teams minimised warehouse storage by loading only curated tables, and they sized ETL servers separately from the database. That made sense when adding a raw column cost real money and when the warehouse could not elastically scale compute for ad hoc SQL transforms.

What changed that made ELT practical at scale?Comparison

Cloud warehouses separated storage from compute and priced storage near object-store rates. Compute became elastic — spin up a warehouse for an hour, run SQL transforms, suspend it. Loaders (Fivetran, Airbyte, native pipes) made landing raw data cheap and reliable.

Once raw data was affordable to keep, reprocessing became a SQL re-run instead of a re-extract, and transformation could move into the warehouse where dbt manages it as version-controlled code with tests.

Where does dbt sit in the modern data stack, and what are three things it explicitly does not do?Fundamentals

dbt owns the transformation layer: it compiles and runs SQL models inside the warehouse, with tests, docs and lineage. It does not extract data from source systems, does not load raw tables (except small seeds), does not schedule itself, does not store data outside the warehouse, and does not render dashboards.

Extraction and loading belong to connectors and scripts; scheduling belongs to Dagster, Airflow or dbt Cloud; serving belongs to BI tools like Preset or Looker. dbt generates SQL — the warehouse executes it.

Compare ETL and ELT on reprocessing after a transformation bug is found.Comparison

In ETL, raw data often never reached the warehouse, so fixing logic frequently requires re-extracting from sources — slow, rate-limited and sometimes impossible if history was truncated. In ELT, raw tables remain in the warehouse; you fix the dbt model and re-run the DAG, and downstream models rebuild from retained history.

ELT turns reprocessing into a warehouse compute problem you control. ETL turns it into a cross-system replay problem involving the source application.

Name the major layers of the modern data stack in order from source to dashboard.Fundamentals

Sources → ingestion/loading → warehouse storage/compute → transformation (dbt) → orchestration → BI/serving, with cross-cutting cataloguing/governance, observability/data quality, and often reverse ETL back to operational tools.

Interviewers accept different wording, but the critical separations are load vs transform vs serve, and the fact that orchestration wraps the transform step rather than replacing it.

Why is transformation logic in a GUI ETL tool harder to maintain than dbt models in git?Design

GUI jobs are difficult to diff, review in pull requests, and bisect when a metric changes. Logic is stored in proprietary formats tied to the ETL server, not in plain SQL your team already knows. Testing is weaker — row counts instead of grain and uniqueness assertions.

dbt puts transformations in text files with version control, CI, and tests colocated with models. That is the organisational shift ELT enables: analytics engineers can own the T layer without waiting for a central ETL team queue.

Your CFO asks why the data stack costs more after moving to ELT. What do you say?Cost

ELT shifts spend from fixed ETL infrastructure to variable meters: raw storage, warehouse compute for dbt runs, loader MAR pricing, BI seats, and orchestration hosting. Initial costs often rise because teams keep all raw data, run more frequent transforms, and add tools that were previously bundled in one ETL licence.

The answer is not to revert to ETL but to optimise each layer: incremental models, Slim CI, scoped tests, warehouse auto-suspend, and selective sync from loaders. Cost visibility is better because each layer bills separately — which is both the problem and the lever.

What is reverse ETL and how does it relate to dbt?Fundamentals

Reverse ETL syncs data from the warehouse back into operational systems — CRM, marketing automation, support tools. Tools like Census and Hightouch read curated tables (often dbt marts) and push segments outward.

dbt does not perform reverse ETL. It builds the marts reverse ETL reads. Quality and tests on those marts matter more because errors propagate into systems customers and sales teams touch directly.

When would you still choose ETL or an ETL-style pattern over ELT?Design

When data must be redacted or filtered before entering a shared environment (PII, HIPAA), when transforms are not expressible in SQL (heavy ML feature engineering in Python), when streaming latency requirements are sub-minute, or when the destination is not a SQL warehouse at all.

Many real pipelines are hybrid: ELT for analytics in Snowflake, ETL-style streaming for operational events, and batch exports for legal archives. The label matters less than matching pattern to constraints.

The dashboard shows yesterday's revenue but dbt Cloud job succeeded. Walk through how you debug across stack layers.Troubleshooting

Start by confirming which relation the dashboard queries — wrong schema or a cached dataset in Preset is common. Check orchestration logs: did the job run dbt build on the full mart or a slim selection that skipped the revenue model? Verify the mart's max(date) in Snowflake against source freshness.

If dbt truly built current data, the break is in the serve layer (BI cache, wrong connection) or in a semantic layer calculated field overriding the mart. If the mart is stale, trace upstream incremental watermarks and loader sync times. Stack debugging moves down from BI to transform to load, never assuming one green checkmark covers all layers.

Recap

  • ETL transforms before load, driven by expensive storage, fixed compute and rigid warehouses. Logic often lived in GUI tools without version control or tests.
  • ELT loads raw data first, transforms with SQL inside the warehouse. Reprocessing is a re-run; raw history stays available.
  • The modern data stack layers: sources → load → warehouse → transform (dbt) → orchestration → BI, plus governance, observability and reverse ETL.
  • dbt owns the T only. It does not extract, load, schedule, store data outside the warehouse, or serve dashboards.
  • On top of raw SQL, dbt adds ref(), environments, materialisations, tests, docs, lineage, git workflow and macros.
  • Raw loaded tables use source(); dbt-built tables use ref() — that line is the L/T boundary.
  • This course: Snowflake + manual COPY load + dbt Core 1.11 + uv + Dagster + Preset + GitHub Actions CI.
  • Real ETL failure modes: opaque GUI logic, re-extract to fix bugs, single pipeline team bottleneck.
  • Real ELT failure modes: tool sprawl, warehouse and MAR costs, untested views, metric definitions split across BI and dbt.
  • The stack is consolidating toward semantic layers, data contracts, Iceberg/Delta convergence and integrated platforms — without undoing ELT's core idea.
  • Production should use dbt build (tests gate downstream), orchestrated by Dagster or equivalent, with exposures linking marts to Preset dashboards.
