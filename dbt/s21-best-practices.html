Recommended project structure

dbt Labs’ canonical layout separates models into layers: staging (light transforms on raw sources), intermediate (reusable logic that is not yet a mart), and marts (dimensions, facts, and department-specific datasets). The Airbnb course project follows this pattern almost exactly — with src_ where many teams use stg_, and an intermediate/ folder that appears on the power-user branch.

The three-layer model

Each layer has one job. Staging reads from sources and renames columns. Intermediate joins and aggregates when the logic is shared by multiple downstream models. Marts answer business questions at a defined grain. When you open a pull request, the folder path tells the reviewer what kind of change they are looking at before they read a line of SQL.

src_ versus stg_. dbt Labs’ public guide uses stg_ and a staging/ folder. The course uses src_ and models/src/. Both are valid; what matters is consistency within a project. When you join a team, adopt their prefix rather than renaming everything to match a blog post.

One folder per source system in staging

When a company loads data from Salesforce, Stripe, and an internal Postgres app, staging typically gets three subfolders: models/staging/salesforce/, models/staging/stripe/, models/staging/postgres_app/. The Airbnb project is small enough that all three raw tables share one source (airbnb in sources.yml) and one staging folder (models/src/). The principle is the same: a reader should know which upstream system a staging model touches from its path alone.

Staging models in the course read exactly one source table each:

WITH raw_listings AS (
        SELECT * FROM {{ source('airbnb', 'listings') }}
)
SELECT 
   id AS listing_id,
   listing_url,
   name AS listing_name,
   room_type,
   minimum_nights,
   host_id,
   price AS price_str,
   created_at,
   updated_at
FROM raw_listings

Downstream dimensions own cleansing and type coercion. dim_listings_cleansed casts price strings to numbers and normalises minimum nights — work that belongs out of staging so every consumer gets the same rules.

Folder-level config in dbt_project.yml

Structure is not only directories. The project file encodes defaults so individual models stay short:

models:
  airbnb:
    +materialized: view
    dim:
      +materialized: table
    src:
      +materialized: ephemeral
    fct:
      +tags: ['fact']
data_tests:
  +store_failures: true
  +schema: _test_failures

dim_listings_cleansed overrides the dim-folder default back to view in its own config block — a pattern you will see when a model’s access pattern differs from siblings in the same folder. See Section 8 for when to override folder defaults.

Everyday analogy — staging, intermediate, and marts are like prep, cooking, and plating in a restaurant kitchen. Prep washes and chops; cooking combines ingredients; plating is what the customer sees. You do not serve raw carrots because someone skipped prep.

Naming conventions

Prefixes tell you the layer; suffixes tell you the grain or variant. The Airbnb project uses src_, dim_, fct_, and mart_ consistently. Column names follow snake_case with semantic suffixes for keys and booleans.

Model prefixes

Singular versus plural table names

dbt Labs recommends plural model names for entities that represent collections: customers, orders, order_items. The course project uses a mix — dim_listings_cleansed (plural entity), fct_reviews (plural), mart_fullmoon_reviews (plural). What matters is picking one rule and applying it in code review.

Column naming patterns

Consistent column names let analysts join across marts without a data dictionary open on a second monitor. The Airbnb models demonstrate the usual patterns:

  • Primary and foreign keys — listing_id, host_id, review_id (surrogate key generated in fct_reviews via dbt_utils.generate_surrogate_key).
  • Booleans — prefix with is_ or has_: is_superhost in dimensions, is_full_moon in mart_fullmoon_reviews, host_is_superhost when disambiguating joined columns in dim_listings_w_hosts.
  • Timestamps — created_at, updated_at, review_date for event time; align with event_time config on incremental models.
  • Raw versus cleansed — keep the raw string as price_str in staging; expose the typed column as price only after cleansing in the dimension.
{{
  config(
    materialized = 'incremental',
    on_schema_change='fail',
    event_time='review_date'
    )
}}

WITH src_reviews AS (
  SELECT * FROM {{ ref('src_reviews') }}
)
SELECT 
  {{ dbt_utils.generate_surrogate_key(['listing_id', 'review_date', 'reviewer_name', 'review_text']) }} as review_id,
  *
FROM src_reviews
WHERE review_text is not null
{% if is_incremental() %}
  {% if var("start_date", False) and var("end_date", False) %}
    {{ log('Loading ' ~ this ~ ' incrementally (start_date: ' ~ var("start_date") ~ ', end_date: ' ~ var("end_date") ~ ')', info=True) }}
    AND review_date >= '{{ var("start_date") }}'
    AND review_date < '{{ var("end_date") }}'
  {% else %}
    AND review_date > (select max(review_date) from {{ this }})
    {{ log('Loading ' ~ this ~ ' incrementally (all missing dates)', info=True)}}
  {% endif %}
{% endif %}
Rename at the earliest stable layer. If id becomes listing_id, do it in staging so every downstream model uses the same name. Renaming again in a mart confuses lineage and breaks tests that reference column names.

Files outside models/

Naming extends beyond SQL models:

  • Sources — source name airbnb, table names listings, hosts, reviews (logical names); identifiers point at raw_listings etc.
  • Seeds — descriptive CSV names: seed_full_moon_dates.csv.
  • Snapshots — raw_listings_snapshot.yml mirrors the source table name.
  • Singular tests — named after the rule: dim_listings_minimum_nights.sql, consistent_created_at.sql.
  • Macros — verb or behaviour: generate_schema_name, select_positive_values.

Source naming in sources.yml

Logical source and table names should read naturally in source() calls. The identifier maps to the physical warehouse table when names differ:

sources:
  - name: airbnb
    schema: raw
    tables:
      - name: listings
        identifier: raw_listings
      - name: hosts
        identifier: raw_hosts
      - name: reviews
        identifier: raw_reviews
        config:
          loaded_at_field: date
          freshness:
            warn_after: {count: 1, period: hour}

In SQL, the call is {{ source('airbnb', 'listings') }} — not source('raw', 'raw_listings'). Decoupling logical names from physical names lets you rename warehouse tables without rewriting every staging model, as long as you update the identifier once.

Disambiguating joined column names

When two entities share column semantics, prefix with the entity name in join models. dim_listings_w_hosts exposes host_is_superhost instead of a bare is_superhost that could refer to either side of the join:

WITH
l AS (
    SELECT * FROM {{ ref('dim_listings_cleansed') }}
),
h AS (
    SELECT * FROM {{ ref('dim_hosts_cleansed', v=2) }}
)
SELECT 
    l.listing_id,
    l.listing_name,
    l.room_type,
    l.minimum_nights,
    l.price,
    l.host_id,
    h.host_name,
    h.is_superhost AS host_is_superhost,
    l.created_at,
    GREATEST(l.updated_at, h.updated_at) AS updated_at
FROM l
LEFT JOIN h ON (h.host_id = l.host_id)

The dbt style guide

dbt Labs publishes a SQL style guide; most teams adopt a subset and enforce it in pull request review (often with SQLFluff, as on the power-user branch). The goals are readability, predictable structure, and diffs that show logic changes rather than formatting noise.

SQL formatting rules

KeywordsUppercase SELECT, FROM, WHEREMixed case Select From where

Trailing commasLeading commas in column lists (team preference) or trailing on prior lineInconsistent comma placement across files

CTE naming: import, logical, final

The community convention divides CTEs into three groups:

  1. Import CTEs — one per upstream relation, usually named after the model: src_listings AS (SELECT * FROM {{ ref('src_listings') }}).
  2. Logical CTEs — business steps with descriptive names: host_listing_metrics, dominant_room_type_calc.
  3. Final — either a CTE named final or a terminal SELECT with no further CTEs after it.

The power-user model int_host_performance.sql is the course’s best example of logical CTEs with a documented grain comment:

{{
  config(
    materialized = 'table'
  )
}}
WITH dim_hosts AS (
  SELECT
    host_id,
    host_name,
    is_superhost,
    created_at
  FROM {{ ref('dim_hosts_cleansed') }}
),

dim_listings AS (
  SELECT
    listing_id,
    room_type,
    price,
    minimum_nights,
    host_id
  FROM {{ ref('dim_listings_cleansed') }}
),

host_listing_metrics AS (
  SELECT
    h.host_id,
    h.host_name,
    h.is_superhost,
    h.created_at,
    COUNT(DISTINCT dl.listing_id) AS total_listings,
    ROUND(AVG(dl.price), 2) AS avg_listing_price
    /* … additional aggregates … */
  FROM dim_hosts h
  LEFT JOIN dim_listings dl ON h.host_id = dl.host_id
  GROUP BY h.host_id, h.host_name, h.is_superhost, h.created_at
),

dominant_room_type_calc AS (
  SELECT
    host_id,
    CASE
      WHEN entire_home_count >= private_room_count THEN 'Entire home/apt'
      /* … */
    END AS dominant_room_type
  FROM host_listing_metrics
)

SELECT
  h.host_id,
  h.host_name,
  h.total_listings,
  h.avg_listing_price,
  d.dominant_room_type
FROM host_listing_metrics h
LEFT JOIN dominant_room_type_calc d ON h.host_id = d.host_id
Short aliases in small models are acceptable. dim_listings_w_hosts uses l and h for brevity in a two-table join. That is fine at this size. In a ten-CTE model, prefer full names so reviewers can trace columns without scrolling.

One model, one grain

Every model should answer: “What does one row represent?” If you cannot state it in one sentence, split the model.

ModelGrain (one row per…)
src_listingslisting in the raw source
dim_listings_cleansedlisting (cleansed attributes)
dim_listings_w_hostslisting with host attributes joined
fct_reviewsreview event (surrogate review_id)
int_host_performancehost (aggregated listing metrics)
mart_fullmoon_reviewsreview enriched with full-moon flag

Mixing grains — for example listing-level and host-level columns in the same table without a clear primary grain — causes double-counting in BI tools. Aggregations in Looker, Tableau, or Metabase assume uniform grain unless the semantic layer says otherwise.

Jinja and config placement

Put {{ config(...) }} at the top of the file. Keep business logic in SQL; use Jinja for environment-dependent behaviour (incremental filters, variables), not for logic that belongs in a macro. The course’s incremental pattern in fct_reviews is the upper bound of acceptable inline Jinja for many teams — beyond that, extract a macro.

Staging versus cleansing: where each transform belongs

The style guide is also about responsibility boundaries. Compare staging and dimension for hosts:

WITH raw_hosts AS (
    SELECT * FROM {{ source('airbnb', 'hosts') }}
)
SELECT
    id AS host_id,
    name AS host_name,
    is_superhost,
    created_at,
    updated_at
FROM raw_hosts
{{
  config(
    materialized = 'table' 
    )
}} 
WITH src_hosts AS (
    SELECT * FROM {{ ref('src_hosts') }}
)
SELECT
    host_id,
    NVL(host_name, 'Anonymous') AS host_name,
    is_superhost,
    created_at,
    updated_at
FROM src_hosts

If NVL(host_name, 'Anonymous') lived in staging, every downstream model would inherit the default whether it wanted it or not. Keeping staging pure makes intermediate models flexible — some marts might need raw nulls for a data-quality report.

SQLFluff and automated formatting

The power-user branch adds .sqlfluff configuration so formatting is checked automatically rather than debated in every PR comment thread. SQLFluff does not replace human review for grain and logic, but it eliminates diff noise from comma placement and keyword casing. Teams typically run it in pre-commit hooks alongside dbt parse.

BigQuery and Databricks formatting. SQLFluff dialect must match your warehouse. Snowflake-specific casts like :: NUMBER in dim_listings_cleansed fail lint under a BigQuery dialect — another reason to keep warehouse-specific casts in the dimension layer where they are explicit, not scattered through staging.

Reviewers read the compiled SQL in target/compiled/ when Jinja obscures the final query. They confirm relationship tests point at the model version consumers use — the course deliberately uses ref('dim_hosts_cleansed', v=2) after introducing model versions.

  - name: dim_listings_cleansed
    description: Cleansed table which contains Airbnb listings.
    data_tests:
      - minimum_row_count:
          arguments:
            min_row_count: 1000
    columns:
      - name: listing_id
        data_tests:
          - unique
          - not_null
      - name: host_id
        data_tests:
          - not_null
          - relationships:
              arguments:
                to: ref('dim_hosts_cleansed')
                field: host_id
Approving without running tests. SQL that compiles can still fail uniqueness checks or relationship tests. CI must run dbt build or at least dbt test on the modified subgraph. A green compile alone is not sufficient.

Questions reviewers ask out loud

  • What grain is this model? Did we document it?
  • If this column disappears, who breaks — check exposures in dashboards.yml.
  • Is this logic duplicated elsewhere? Should it be a macro or intermediate model?
  • Will full refresh on this incremental model be acceptable in production?
  • Does on_schema_change match how we handle additive columns?

PR description template for analytics

Good analytics PRs state intent in prose because SQL diffs rarely explain why. A minimal template teams reuse:

  • Context — ticket link, stakeholder request, or metric definition change.
  • Grain — one sentence on what a row represents.
  • Backfill — whether production needs --full-refresh or a one-time script.
  • Validation — row counts, key metrics compared to legacy, screenshots from dev schema.
  • Downstream — exposures, dashboards, reverse-ETL jobs affected.

Introducing dbt to a company with none

Teams fail dbt adoption when they treat it as a big-bang migration. The pattern that works: prove value on one vertical slice, then expand layer by layer with tests and docs from day one.

Migration order that works

  1. Pick one business question end to end. Example: “How many reviews per listing last month?” Map raw tables, one staging model per source, one mart that answers the question.
  2. Get staging running first. Mirror the course: sources.yml + ephemeral src_ models. Analysts can validate row counts against legacy SQL.
  3. Add tests early, not late. not_null and unique on primary keys from the first merged PR. Tests are how you earn trust with stakeholders who saw pipelines break silently before.
  4. Introduce dimensions and facts. Move cleansing out of staging into dim_ models; add fct_ for events. Match materializations to access patterns (see Section 8).
  5. Wire CI when the second contributor appears. Slim CI on pull requests; full nightly build. Section 19 patterns apply even before production deployment.
  6. Migrate legacy SQL incrementally. Park old scripts in legacy/ (as on the power-user branch) until each is replaced by a tested model, then delete.
  7. Add orchestration last. Cron or Dagster/Airflow once models stabilise — Section 18. Orchestrating chaos just runs broken jobs on a schedule.

Adoption timeline: avoid boiling the ocean

Week 1–2 · one source · staging + sources.yml · row-count parity checks
Week 3–4 · first dim/fct · primary key tests · docs generation
Month 2 · first mart · BI cutover for one dashboard
Month 3+ · CI · incremental models · retire legacy scripts

Organisational prerequisites

You need

  • Raw data already in the warehouse (EL done)
  • Git repository and branch protection
  • Dev schemas or targets per analyst
  • One person accountable for merge quality

You do not need on day one

  • dbt Cloud (Core + CI works)
  • Every dashboard migrated
  • Perfect folder structure
  • Custom macros and packages

The course itself follows this arc: Section 6 setup, Section 7 first models, Section 9 sources, Section 11 tests, Section 19 production. Section 21 is the explicit map of what you were doing implicitly.

Socialise lineage early. Generate docs (Section 14) after the first three models. Stakeholders who see a DAG understand why staging must exist before marts — and why the migration takes weeks, not days.

Parallel run with legacy SQL

During migration, run dbt models and legacy scripts side by side. Compare row counts and key metrics daily. The course’s singular test consistent_created_at.sql is the kind of cross-model rule you write when proving parity. Decommission legacy only when tests pass consistently for a full business cycle (often a month for finance metrics).

Stakeholder communication during adoption

Engineers feel progress when models compile; executives feel progress when a dashboard they trust still matches yesterday. Bridge the gap with visible artifacts:

  • Weekly parity report — row counts for three key tables: legacy SQL versus dbt marts.
  • Published lineage — share the docs site URL after Section 14 setup so analysts see where metrics originate.
  • Named owners — one DRI per mart folder in CODEOWNERS; questions route to a person, not a channel.
  • Explicit cutover dates — “Finance dashboard switches to mart_fullmoon_reviews on 1 September” prevents two definitions running indefinitely.

Anti-patterns and fixes

Most failed dbt projects are not tooling failures. They are convention failures: one giant model, logic trapped in the BI layer, no tests, ad hoc scripts beside the project, hardcoded database names. The table below maps common mistakes to fixes grounded in what the Airbnb project does instead.

Most expensive anti-pattern: a full-table incremental fact run with --full-refresh in production because nobody documented the incremental predicate. One mistaken flag rebuilds months of reviews and burns warehouse credits. Lock full refresh behind manual approval.

When ad hoc analyses are fine

Not every query belongs in the DAG. The analyses/ folder holds SQL that compiles with ref() but never materialises — perfect for one-off investigations. The rule: if leadership will ask for the same number next quarter, promote it to a mart with tests.

Mart configuration patterns from the course

mart_fullmoon_reviews demonstrates several best practices in one file: it reads from a fact not raw sources, uses microbatch incremental for time-bounded rebuilds, and overrides schema to isolate marts from dev dimensions:

{{ config(
  materialized = 'incremental',
  incremental_strategy='microbatch',
  event_time='review_date',
  begin='2009-06-20',
  batch_size='year',
  full_refresh=false,
  tags = ['fact'],
  schema='mart'
) }}

WITH fct_reviews AS (
    SELECT * FROM {{ ref('fct_reviews') }}
),
full_moon_dates AS (
    SELECT * FROM {{ ref('seed_full_moon_dates') }}
)
SELECT
  r.*,
  CASE
    WHEN fm.full_moon_date IS NULL THEN 'not full moon'
    ELSE 'full moon'
  END AS is_full_moon
FROM fct_reviews r
LEFT JOIN full_moon_dates fm
  ON (TO_DATE(r.review_date) = DATEADD(DAY, 1, fm.full_moon_date))

A reviewer seeing this file should immediately note: grain unchanged from fct_reviews (one row per review), enrichment only adds is_full_moon, and the join to a seed is appropriate because calendar data is small and version-controlled.

Tags and selectors for convention enforcement

The project tags facts with fact in dbt_project.yml and defines selectors in selectors.yml for common run patterns. Tags let CI run dbt build --select tag:fact after fact-layer changes without rebuilding every dimension. See Section 17 for selector syntax on dbt 1.11 versus 1.12.

Traps that catch people

  • Renaming models without aliases — changing dim_listings_cleansed to dim_listings creates a new node; downstream ref() calls break unless you use alias config during transition.
  • Folder defaults ignored — a model in models/dim/ becomes a table even if you forgot to add config, because dbt_project.yml sets dim: +materialized: table. Surprises teams expecting view defaults.
  • Ephemeral staging in BI — analysts cannot SELECT from src_listings directly. Point them at dimensions or temporarily materialise staging as views for debugging.
  • Intermediate layer skipped too long — copying the same join into three marts means three places to fix bugs. Extract int_ when the second mart needs the same logic.
  • Plural/singular drift — host versus hosts across models breaks auto-generated relationship tests and confuses semantic layers.
  • Hardcoded schema= in model config — bypasses generate_schema_name and breaks multi-env deployments from Section 19.
  • Tests on ephemeral models — dbt cannot query ephemeral relations directly; test downstream tables that materialise the logic.
  • Legacy folder never deleted — legacy/ models still parse and may run if someone executes dbt run without selection. Exclude via tags or remove when migration completes.
  • Over-nesting folders — models/marts/marketing/finance/... deeper than three levels makes dbt ls output hard to scan. Prefer flat layer folders with long descriptive names.
  • Confusing analyses with models — analyses do not run in production DAGs; promoting to a mart requires tests and materialization choice.

Production patterns

Large organisations often split one warehouse into multiple dbt projects: a staging project per source system and a marts project that reads staging via cross-project ref (dbt Mesh) or published views. The Airbnb repo is a single project because it is a teaching artifact; do not assume one repo scales to fifty sources without boundaries.

Enforce conventions with automation: SQLFluff in pre-commit (power-user branch), required CODEOWNERS on models/mart/, and CI gates that fail when select * appears in changed files. The human-readable style guide becomes worthless if nothing checks it.

Pattern: staging as views on BigQuery

BigQuery nested views perform well for moderate depth. Teams materialise staging as views instead of ephemeral so analysts can inspect intermediate layers in the console.

Anti-pattern: mart reads raw directly

mart_* selecting from source() skips tests on staging and dims. Any raw schema change breaks the mart with no intermediate failure signal.

    {%- else -%}

Interview questions

Answer each one out loud before opening it.

Why does dbt Labs recommend a staging layer between raw sources and marts?Design

Staging isolates the rest of the project from raw schema quirks: renamed columns, type casts deferred to later layers, and one-to-one mapping with source tables. When Fivetran adds a column or renames a field, you fix one staging model instead of every downstream mart.

In the Airbnb project, src_listings reads source('airbnb', 'listings') and exposes listing_id and price_str. Dimensions never touch RAW.RAW_LISTINGS directly after sources are declared.

What is the difference between an intermediate model and a dimension?Modelling

An intermediate model (int_) holds reusable logic that is not yet meant for BI consumption — often joins and aggregates at a grain that multiple marts need. A dimension (dim_) describes a business entity at a stable grain and is intended for analysis.

int_host_performance aggregates listings per host for internal metrics; dim_hosts_cleansed describes host attributes one row per host without portfolio aggregates unless that is the defined entity.

When would you use ephemeral staging versus staging as views?Comparison

Ephemeral staging (the course default) inlines into downstream queries — no extra object, no extra storage, but not queryable on its own. Staging as views creates inspectable objects analysts can browse, at the cost of an extra view layer in every query plan.

Choose ephemeral on Snowflake when staging is simple and only dbt models consume it. Choose views on BigQuery or when debugging staging frequently. Postgres projects sometimes hit query-length limits with deep ephemeral chains.

What does "one model one grain" mean in practice?Fundamentals

Every model's output rows must represent the same unit — one listing, one review, one host-day, etc. If a model mixes listing-level and host-level facts without a bridge, BI tools double-count when aggregating.

fct_reviews is one row per review (via surrogate review_id). dim_listings_w_hosts is one row per listing with host attributes joined — not one row per host.

What should you look for when reviewing a dbt pull request?Production

Check tests on new keys and relationships, docs on models and columns, naming aligned with layer prefixes, ref()/source() instead of hardcoded schemas, appropriate materialization, and incremental logic that cannot silently drop rows. Confirm CI ran against the modified subgraph.

Also scan for exposures and downstream dashboards affected by column renames — the course uses model versions for breaking host column changes instead of silent edits.

How would you introduce dbt to a team that only runs ad hoc SQL today?Design

Start with one end-to-end pipeline: sources.yml, staging models, one mart answering a real business question. Add primary-key tests on the first merge. Run legacy SQL in parallel until counts match, then expand layer by layer. Do not migrate every dashboard before proving one slice.

Introduce git, dev schemas, and CI when a second contributor appears — matching the course arc from Section 6 through Section 19.

Why is SELECT * discouraged in production dbt models?Gotcha

SELECT * passes through new upstream columns automatically. That sounds convenient but breaks explicit contracts, hides grain changes, and can introduce duplicate column names after joins. Schema drift surfaces in production instead of at compile time.

Explicit column lists make diffs readable in review and enable enforced contracts — as on dim_hosts_cleansed v2 in the course.

What is wrong with putting business logic in the BI tool instead of dbt?Modelling

The same metric gets defined differently in each dashboard; there is no version control, test, or lineage for BI-calculated fields. When the definition changes, someone must find every workbook manually.

Centralising logic in marts — price parsing in dim_listings_cleansed, full-moon flag in mart_fullmoon_reviews — gives one tested definition analysts consume uniformly.

How do import CTEs differ from logical CTEs in the dbt style guide?SQL

Import CTEs pull from {{ ref() }} or {{ source() }} — typically one CTE per upstream relation, often named after that relation. Logical CTEs encode business steps: aggregations, CASE logic, fan-out joins with descriptive names like host_listing_metrics.

The final SELECT should read as a thin composition of logical CTEs so reviewers grasp the pipeline top to bottom without parsing nested subqueries.

When should you add an int_ layer instead of joining directly in a mart?Performance

Add intermediate when two or more marts need the same non-trivial join or aggregation, when the logic is complex enough to warrant its own tests, or when build time improves by persisting an expensive step once.

The power-user branch introduces int_host_performance before mart_listing_performance — the pattern you would follow when host metrics feed multiple downstream datasets.

Recap

  • Structure models in layers: staging (src_ or stg_) → optional intermediate (int_) → dimensions/facts (dim_/fct_) → marts (mart_).
  • The Airbnb project uses models/src/, dim/, fct/, mart/ with folder-level materialization defaults in dbt_project.yml.
  • Staging: one model per source table; rename columns; no cross-source joins.
  • Prefixes encode layer; column names use _id for keys and is_/has_ for booleans.
  • SQL style: import CTEs → logical CTEs → final SELECT; avoid SELECT * in production models.
  • Every model declares one grain — state it in docs or comments.
  • PR review checks tests, docs, naming, ref()/source(), materialization, and incremental safety.
  • Adopt dbt incrementally: one vertical slice, tests early, legacy parallel run, CI when team grows.
  • Anti-patterns: god models, BI-layer logic, no tests, ad hoc scripts, hardcoded schemas, daily full refreshes without cause.
  • Power-user branch adds intermediate/ and mart_listing_performance — the scaling pattern for shared logic.
  • analyses/ is for exploration; recurring metrics belong in tested marts.
  • Enforce conventions with SQLFluff, CODEOWNERS, and slim CI — structure only works if review catches drift.
