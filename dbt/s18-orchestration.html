Why dbt needs an external scheduler

dbt is a build tool, not a workflow engine. When you run dbt build, dbt executes the selected subgraph once and exits. Nothing in dbt Core wakes up at midnight, checks whether Fivetran finished loading, retries a failed test, or sends a Slack alert when a mart is stale.

Section 1 already stated this plainly: dbt does not schedule itself. You need cron, an orchestrator, or dbt Cloud's job scheduler. That gap is not a missing feature — it is a deliberate boundary. dbt owns transformation logic inside the warehouse; everything around it (ingestion timing, retries, alerting, cross-system dependencies) belongs to a scheduler that understands your whole pipeline, not just SQL models.

What cron alone cannot do

A naive setup is 0 6 * * * dbt build in crontab. That works until it does not:

  • No upstream awareness. If the raw load finishes at 06:45, cron still fires at 06:00 and builds against yesterday's data — or half-loaded tables.
  • No dependency graph across systems. dbt knows ref() order inside the project, but cron does not know that Snowpipe must finish before dbt run starts.
  • Blunt retries. A single model failure re-runs the entire dbt build unless you wrap it in shell logic. Orchestrators retry at task granularity.
  • No partition backfill UI. Reprocessing one bad day of incremental data requires passing --vars or partition keys — awkward from cron, natural from Dagster or Airflow.
  • Observability gap. Cron emails stderr. Orchestrators store run history, task logs, SLA metrics, and lineage across dbt and non-dbt steps.

Where scheduling fits in the modern data stack

Section 4 placed orchestration alongside ingestion and transformation. By Section 18 you have the full Airbnb DAG — sources, staging, dimensions, facts, marts, snapshots, tests, and exposures. None of it runs on a clock until you add a scheduler. In a typical stack the sequence is:

  1. Fivetran or Airbyte loads raw tables on its own schedule (or near-real-time).
  2. A sensor or time-based trigger waits until the load marks complete (or a fixed offset, e.g. 30 minutes after midnight).
  3. dbt runs build or a tagged subset — staging and dimensions first, then facts, then marts and tests.
  4. Downstream consumers (Looker, Metabase, reverse ETL) read refreshed marts.

dbt sits at step 3 only. Steps 1, 2, and 4 are orchestrator or SaaS responsibilities. That separation is why analytics engineers learn both dbt and a scheduler — the job is not "write SQL" alone, it is "keep the SQL running reliably after the data lands."

Cron without selection is the hidden bill. A nightly dbt build on a growing project re-runs every test and rebuilds every incremental model's default path. Before adding orchestration, fix selection — Section 17 tags and selectors pay off immediately when the scheduler starts firing unattended.

BashOperator versus native dbt integrations

The Airflow branch starts with the simplest pattern: one BashOperator that runs dbt build in the airbnb/ folder. That is one Airflow task for the entire dbt project. It works, but you lose per-model retries, granular SLA tracking, and visual lineage at the model level.

Dagster's @dbt_assets and Airflow's Astronomer Cosmos generate one orchestration node per dbt model (or configurable groupings). The setup cost is higher, but production teams almost always migrate to this because a failed test on dim_listings_cleansed should not require re-running every mart.

When BashOperator is enough

Small projects, proof-of-concept, or "we already have Airflow and need dbt running tonight." One task, one log stream, same venv as the CLI.

When to invest in asset mapping

More than ~15 models, incremental partitions, separate retry policies per layer, or stakeholders who need model-level run history in the orchestrator UI.

Same venv pattern as the course. Both Dagster and Airflow in this repo share the root pyproject.toml virtualenv with dbt. The orchestrator shells out to the same dbt binary your terminal uses — no duplicate installs, no container path translation for local dev.

Other tools the course links

course-resources.md also lists Prefect, Azure Data Factory, and the official dbt deployment integrations page. Prefect fits teams who want Python-native flows with less operational weight than Airflow — you decorate a Python function that calls dbt run and Prefect handles retries and scheduling. Azure Data Factory can invoke dbt via Azure-hosted compute or wrapper activities, common in Microsoft-centric enterprises already on ADF for ingestion. Neither is wired in the course repo; Dagster and Airflow are the hands-on paths because they represent the two most common self-hosted patterns in analytics engineering job postings.

The dbt_dagster_project walkthrough

Four Python modules wire dbt into Dagster: constants.py locates the project, assets.py declares dbt-backed assets (including a partitioned asset for fct_reviews), schedules.py defines the daily cron job, and definitions.py bundles everything for dagster dev.

constants.py — project path and manifest

This module resolves the dbt project directory relative to the Dagster package and configures DbtCliResource:

import os
from pathlib import Path

from dagster_dbt import DbtCliResource

dbt_project_dir = (
    Path(__file__)
    .joinpath("..", "..", "..", "dbtlearn")
    .resolve()
)
dbt = DbtCliResource(project_dir=os.fspath(dbt_project_dir))

if os.getenv("DAGSTER_DBT_PARSE_PROJECT_ON_LOAD"):
    dbt_manifest_path = (
        dbt.cli(
            ["--quiet", "parse"],
            target_path=Path("target"),
        )
        .wait()
        .target_path.joinpath("manifest.json")
    )
else:
    dbt_manifest_path = dbt_project_dir.joinpath("target", "manifest.json")

The relative path walks up three directories from constants.py to the repo root, then into dbtlearn/. For the Airbnb project, replace "dbtlearn" with "airbnb". DbtCliResource is the Dagster resource that invokes the dbt CLI with the correct working directory.

assets.py — two asset groups

The course splits dbt models into two @dbt_assets definitions: one for the bulk of the project, and one partitioned asset group exclusively for fct_reviews.

import json
from typing import Any, Mapping

from dagster import (AssetExecutionContext, DailyPartitionsDefinition,
                     OpExecutionContext)
from dagster_dbt import (DagsterDbtTranslator, DbtCliResource, dbt_assets,
                         default_metadata_from_dbt_resource_props)

from .constants import dbt_manifest_path


@dbt_assets(manifest=dbt_manifest_path, exclude="fct_reviews")
def dbtlearn_dbt_assets(context: AssetExecutionContext, dbt: DbtCliResource):
    yield from dbt.cli(["build"], context=context).stream()


daily_partitions = DailyPartitionsDefinition(start_date="2022-01-24")


class CustomDagsterDbtTranslator(DagsterDbtTranslator):
    def get_metadata(self, dbt_resource_props: Mapping[str, Any]) -> Mapping[str, Any]:
        metadata = {"partition_expr": "date"}
        default_metadata = default_metadata_from_dbt_resource_props(dbt_resource_props)
        return {**default_metadata, **metadata}


@dbt_assets(manifest=dbt_manifest_path,
            select="fct_reviews",
            partitions_def=daily_partitions,
            dagster_dbt_translator=CustomDagsterDbtTranslator())
def dbtlearn_partitioned_dbt_assets(context: AssetExecutionContext, dbt: DbtCliResource):
    (
        first_partition,
        last_partition,
    ) = context.asset_partitions_time_window_for_output(
        list(context.selected_output_names)[0]
    )
    dbt_vars = {"start_date": str(first_partition), "end_date": str(last_partition)}
    dbt_args = ["build", "--vars", json.dumps(dbt_vars)]
    dbt_cli_task = dbt.cli(dbt_args, context=context, raise_on_error=False)

    yield from dbt_cli_task.stream()

Key design choices in this file:

  • exclude="fct_reviews" on the main asset group prevents double-building the partitioned model.
  • select="fct_reviews" on the second group scopes Dagster partitions to that one incremental model.
  • DailyPartitionsDefinition(start_date="2022-01-24") aligns with review data in the Airbnb dataset.
  • CustomDagsterDbtTranslator adds partition_expr: date metadata so Dagster knows how to map partitions to warehouse rows.
  • asset_partitions_time_window_for_output converts the selected partition into start_date and end_date strings passed to dbt via --vars.
  • raise_on_error=False on the partitioned run lets Dagster capture partial stream output — useful during development; tighten for production.

schedules.py — daily materialisation

The course starts with the schedule commented out; the instructor asks you to uncomment it. The committed file already has the schedule active:

from dagster_dbt import build_schedule_from_dbt_selection

from .assets import dbtlearn_dbt_assets

schedules = [
    build_schedule_from_dbt_selection(

build_schedule_from_dbt_selection is a Dagster-dbt helper that creates a schedule tied to dbt selection syntax. cron_schedule="0 0 * * *" fires at midnight UTC daily. Note this schedule targets dbtlearn_dbt_assets only — the partitioned fct_reviews group is materialised separately (by partition backfill or a second schedule you would add in production).

Advanced Dagster features in the course README

The dbt_dagster_project/README.md summarises what this code location implements:

  • Daily partitioned assets — fct_reviews with partitions from 2022-01-24.
  • Custom DagsterDbtTranslator — adds partition metadata to dbt resources for Dagster's partition picker.
  • Partition-aware dbt execution — passes start_date and end_date as dbt vars.
  • Daily schedule — midnight cron on the non-partitioned asset group via build_schedule_from_dbt_selection.

Streaming CLI output with yield from

Both asset functions use yield from dbt.cli(...).stream() rather than blocking .wait(). That streams dbt events into Dagster's event log in real time — you see model START/OK lines as they happen in the Dagster run timeline, similar to watching terminal output. For long nightly builds, streaming is the difference between a frozen UI and a progress view you can monitor.

Two resources, one path

constants.py instantiates a module-level dbt = DbtCliResource(...) used for manifest parsing, while definitions.py registers a separate DbtCliResource in the resources dict injected into asset functions. Both must point at the same project_dir. If you refactor paths, update both — a mismatch causes manifest load from one directory and execution from another.

Partitioned incremental runs

Orchestrators shine when incremental models accept time-window parameters. The course updates fct_reviews to filter on start_date and end_date vars when an orchestrator passes them, falling back to max-timestamp logic when vars are absent.

The updated fct_reviews model

This is the committed model in the Airbnb project — it matches what the instructor types in the orchestration lecture:

{{
  config(
    materialized = 'incremental',
    on_schema_change='fail',
    event_time='review_date'
    )
}}

WITH src_reviews AS (
  SELECT * FROM {{ ref('src_reviews') }}
)
SELECT
  {{ dbt_utils.generate_surrogate_key(['listing_id', 'review_date', 'reviewer_name', 'review_text']) }} as review_id,
  *
FROM src_reviews
WHERE review_text is not null
{% if is_incremental() %}
  {% if var("start_date", False) and var("end_date", False) %}
    {{ log('Loading ' ~ this ~ ' incrementally (start_date: ' ~ var("start_date") ~ ', end_date: ' ~ var("end_date") ~ ')', info=True) }}
    AND review_date >= '{{ var("start_date") }}'
    AND review_date < '{{ var("end_date") }}'
  {% else %}
    AND review_date > (select max(review_date) from {{ this }})
    {{ log('Loading ' ~ this ~ ' incrementally (all missing dates)', info=True)}}
  {% endif %}
{% endif %}

The branching logic matters for two run modes:

  • Manual / cron without vars: the else branch appends every row newer than the current max review_date — standard incremental behaviour from Section 8.
  • Orchestrator with vars: Dagster's partition handler passes start_date and end_date, so each daily partition processes exactly one day's reviews. The log(..., info=True) calls print which branch ran — visible in Dagster task logs.

Connection to microbatch and event_time

The model config includes event_time='review_date'. That column enables dbt's --sample flag (Section 16) and the microbatch incremental strategy covered in Section 19. Microbatch is dbt-native partitioning: the engine splits the run into batches by time column. Dagster partitions solve a similar problem from the orchestrator side by passing vars.

ApproachWho owns the partition logicWhen to use
var("start_date") / var("end_date")You write the Jinja; orchestrator passes varsCourse pattern; works on any dbt version; full control over filter SQL
Microbatch incremental (incremental_strategy='microbatch')dbt engine batches by event_timedbt 1.9+; needs threads: 4 in profiles; see Section 19
Max timestamp fallbackModel SQL onlySimple nightly cron with no orchestrator vars
Half-open interval. The filter uses review_date >= start_date AND review_date < end_date. Dagster's partition window end is exclusive. If you see duplicate or missing days at partition boundaries, check whether your orchestrator's end timestamp is inclusive when you expected exclusive.
Backfill without vars re-processes everything new. Running dbt run --select fct_reviews without vars uses max-date logic, not a historical window. To reprocess February 2024, you must pass explicit dates or use Dagster's partition backfill UI.

Why on_schema_change='fail' here

The model sets on_schema_change='fail' so an unexpected column add from the source stops the run instead of silently altering the incremental table. In orchestrated pipelines that is preferable: the scheduler alerts, you review the source change, and you deploy a deliberate model update. sync_all_columns is convenient in dev but dangerous in unattended nightly jobs.

Mapping partition metadata to the warehouse

CustomDagsterDbtTranslator adds partition_expr: date to asset metadata. Dagster uses this to align partition keys with the column that filters rows — here, review_date cast or truncated to date. If your warehouse column is timestamp with timezone, ensure partition boundaries use the same timezone as the source data or you will see off-by-one-day gaps at midnight boundaries.

Incremental strategy reference

The course links to the dbt docs on incremental strategies. The Airbnb fct_reviews model uses default merge/append behaviour for Snowflake with a custom Jinja filter rather than a named strategy. When you adopt microbatch in Section 19, the orchestrator can simplify to plain dbt build --select fct_reviews while dbt batches internally — but you still need the external scheduler to trigger the run.

Airflow integration

The airflow branch adds a minimal Airflow setup: one DAG, one BashOperator, running dbt build against airbnb/. Cosmos — one task per model — is documented as the next step but not implemented in the branch.

Why the course uses the devcontainer for Airflow

Apache Airflow has no native Windows support. The course recommends the Linux-based devcontainer/Codespace (same environment as Section 6) rather than WSL2 or native Windows installs. Airflow and dbt share the root pyproject.toml venv managed by uv, so BashOperator shells out to the same dbt binary with no extra Snowflake provider configuration — connection details live in airbnb/profiles.yml.

The dbt_pipeline.py DAG

This file exists only on the airflow branch:

from datetime import datetime
from airflow import DAG
from pathlib import Path
from airflow.providers.standard.operators.bash import BashOperator

REPO_ROOT = Path(__file__).resolve().parents[2]
AIRBNB_DIR = REPO_ROOT / "airbnb"

with DAG(
    dag_id="dbt_build_bash_operator",
    schedule=None,
    start_date=datetime(2024, 1, 1),
    catchup=False,
) as dag:
    dbt_build = BashOperator(
        task_id="dbt_build",
        bash_command=f'cd "{AIRBNB_DIR}" && dbt build',
    )

Design notes:

  • REPO_ROOT resolves two levels up from airflow/dags/ to the bootcamp repo root — portable regardless of where Airflow is installed.
  • schedule=None means the DAG is manually triggered from the UI — a safe default while learning.
  • BashOperator in Airflow 3 imports from airflow.providers.standard.operators.bash (the old airflow.operators.bash path still works but emits a deprecation warning).
  • One task runs the entire project. Failed test on any model fails the single task.

Traps that catch people

  • dbtlearn/ vs airbnb/ — committed constants.py points at dbtlearn/. Dagster fails with manifest not found until you fix the path. Always verify after scaffold.
  • Stale manifest — new models added in dbt but Dagster asset graph unchanged until dbt parse refreshes target/manifest.json.
  • Double-building fct_reviews — if you remove exclude="fct_reviews" from the main asset group, both asset definitions run the same model.
  • Partition boundary duplicates — inclusive end dates in vars when Dagster already provides exclusive window ends insert duplicate rows into incremental tables without proper unique keys.
  • Vars JSON in shell — nested quotes break in BashOperator. Dagster's json.dumps(dbt_vars) avoids this; manual cron strings often do not.
  • Airflow on native Windows — unsupported. Use devcontainer or WSL2 with a separate Linux venv — Windows uv venv does not carry over.
  • Port 8080 conflict — Docker Desktop binds 8080; Airflow API server fails silently without AIRFLOW__API__PORT=8081 and matching execution API URL.
  • schedule=None forever — the course DAG is manual trigger only. Production needs a cron or dataset schedule.
  • Missing threads for microbatch — if you migrate fct_reviews to microbatch in Section 19, threads: 4 in profiles is required or runs hang.
  • Orchestrator retry + incremental — retrying a partially successful partition without idempotent keys can duplicate rows. Surrogate key on fct_reviews helps only if merge strategy deduplicates.
  • Wrong target in scheduled job — Dagster and Airflow inherit shell env. If DBT_PROFILES_DIR or target is unset, nightly jobs may write to dev schema. Pin target in orchestrator env or use explicit --target prod.
  • Cosmos manifest drift — same as Dagster: Airflow DAG generation reads dbt manifest; stale manifest means new models never become tasks until CI regenerates it.

Production patterns

Mature teams treat the orchestrator as the system of record for when and with what parameters dbt runs, while dbt remains the system of record for what SQL executes. A common pattern: upstream sensor (Fivetran sync complete or Snowpipe load) triggers a Dagster job that runs dbt build --select state:modified+ in CI and a broader nightly job with tag:nightly tests. Partitioned facts get their own job with backfill policies — seven-day rolling catch-up, never unbounded full refresh.

Pattern: sensor-driven dbt

Do not cron dbt at 06:00 because the load "usually" finishes by then. Trigger on the load's success event or Airflow dataset outlet. dbt runs once, completely.

Anti-pattern: orchestrator logic in SQL

Encoding business calendars, holiday skips, or "run only on Tuesdays" inside Jinja makes models untestable from the CLI. Keep schedule policy in the orchestrator; keep SQL focused on data transforms.

Certification: dbt requires an external scheduler (cron, orchestrator, or dbt Cloud). Orchestrators run dbt build/dbt run with optional --select and --vars. Incremental models can filter on vars for partition-based processing.

Observability: where logs land

dbt still writes to airbnb/logs/dbt.log when invoked from Dagster or Airflow — the orchestrator captures stdout/stderr separately in its task run UI. For partition debugging, the log(..., info=True) lines in fct_reviews appear in both places. Production teams often ship orchestrator logs to Datadog or CloudWatch and treat dbt.log as secondary unless debugging compile issues.

Idempotency and partition replays

Re-materialising the same Dagster partition re-runs the incremental filter for that date window. Without a unique key and merge strategy, duplicates accumulate. The course model generates review_id via dbt_utils.generate_surrogate_key but uses default incremental append — replaying a partition may insert duplicate business rows if the surrogate inputs repeat. Production teams add unique_key='review_id' or switch to merge incremental before enabling partition backfills in prod.

Interview questions

Answer each one out loud before opening it.

Why does dbt need an external orchestrator?Fundamentals

dbt is a build tool that compiles and executes SQL against your warehouse once per invocation. It has no built-in scheduler, retry engine, cross-system dependency tracking, or alerting. When you run dbt build, it completes the selected subgraph and exits.

Production pipelines need to trigger dbt after loads finish, retry failed models without rebuilding everything, pass partition parameters to incremental models, and record run history. Cron can fire dbt on a timer but cannot express "run after Fivetran sync succeeds" or backfill one partition. Orchestrators (Dagster, Airflow, Prefect) or dbt Cloud's job scheduler fill that gap.

Compare running dbt under Dagster versus a simple Airflow BashOperator.Comparison

BashOperator runs one shell command — typically cd airbnb && dbt build — as a single Airflow task. Setup is minimal and works in the same Python venv as dbt. The downside is no per-model retries, no model-level lineage in Airflow, and one failed test fails the entire task.

Dagster's @dbt_assets reads manifest.json and maps each dbt model to a software-defined asset. You get partition support (daily backfills on fct_reviews), granular materialisation in the UI, and native integration with build_schedule_from_dbt_selection. Setup cost is higher: manifest management, Python code location, and understanding partition vars.

How does Dagster pass partition dates to an incremental dbt model?Design

Dagster defines DailyPartitionsDefinition on the partitioned asset group. When a partition is materialised, asset_partitions_time_window_for_output returns first_partition and last_partition timestamps. The asset function builds dbt_vars = {"start_date": ..., "end_date": ...} and invokes dbt.cli(["build", "--vars", json.dumps(dbt_vars)]).

In the dbt model, Jinja checks var("start_date") and var("end_date") inside is_incremental() and filters review_date to that half-open window. Without vars, the model falls back to max-timestamp incremental logic.

What is manifest.json and why does Dagster require it?Fundamentals

manifest.json is dbt's compiled project graph — every model, test, source, and their dependencies. Dagster-dbt reads it to generate asset definitions without re-implementing dbt's parser. The path is configured in constants.py, defaulting to <dbt_project>/target/manifest.json.

You generate it with dbt parse or dbt compile. If the manifest is stale, Dagster's asset graph does not reflect new models. Setting DAGSTER_DBT_PARSE_PROJECT_ON_LOAD triggers parse at startup at the cost of slower loads.

When would you choose dbt Cloud scheduling over self-hosted Airflow?Comparison

Choose dbt Cloud when your team already pays for it and wants scheduling, Slim CI, environment management, and documentation in one product with minimal ops overhead. Job configuration is UI-driven; no metadata database or scheduler process to maintain.

Choose self-hosted orchestration when you need dbt integrated into a broader platform (existing Airflow or Dagster estate), custom partition logic, or cost control at the expense of setup. The course demonstrates Dagster and Airflow for teams on dbt Core.

Your incremental model works from the CLI but inserts zero rows from Dagster partitions. How do you debug?Troubleshooting

First, read Dagster task stdout for the log(..., info=True) line — it shows whether the vars branch or max-date branch executed. If max-date ran, vars did not arrive: inspect the --vars JSON in the CLI invocation inside Dagster logs.

If vars are correct but rows are zero, query source data for that date window — the partition may legitimately be empty. Check timezone alignment on review_date versus partition timestamps. Finally, confirm constants.py points at the correct dbt project folder.

Why does the course exclude fct_reviews from the main Dagster asset group?Design

fct_reviews needs partition-aware execution with start_date and end_date vars. The main @dbt_assets group runs a plain dbt build without vars. Including fct_reviews in both groups would either double-build it or run it without partition filters.

exclude="fct_reviews" on the bulk group and select="fct_reviews" on the partitioned group cleanly separates concerns. Production might add a dedicated partition schedule for the second group.

What are the risks of using BashOperator for dbt in production?Production

One task equals one failure domain: any test failure fails the entire build, and retries re-run the whole project. There is no model-level SLA tracking, no selective retry, and no visual DAG at the dbt model granularity in Airflow.

Shell quoting for --vars and --select is fragile in bash_command strings. Logs are one stream — harder to pinpoint which model failed without parsing dbt output. Teams typically migrate to Astronomer Cosmos or Dagster assets once the project exceeds a handful of models.

Explain the dbtlearn/ versus airbnb/ path issue in the course Dagster project.Gotcha

The instructor scaffolds with --dbt-project-dir=airbnb, but the committed constants.py resolves the path to dbtlearn/ — a folder name from an earlier course iteration. Dagster loads dbtlearn/target/manifest.json, which does not exist in your clone.

Fix line 8 in constants.py to "airbnb" (or symlink/rename). This is the most common setup failure in Section 18. Always verify dbt_project_dir matches your actual folder before running dagster dev.

How do orchestrator partitions differ from dbt microbatch incremental?Comparison

Orchestrator partitions (Dagster daily partitions + --vars) push time-window logic from outside dbt. You write explicit Jinja filters on var("start_date"). dbt microbatch (incremental_strategy='microbatch' with event_time) lets the dbt engine batch internally — no vars required, but needs threads: 4 and dbt 1.9+.

Both solve backfill and daily processing. Orchestrator-side partitions give cross-system coordination (wait for load, then materialise partition). Microbatch keeps partition logic inside dbt, simpler when the orchestrator only runs dbt build without custom vars.

How would you add a nightly test-only job without rebuilding all models?Production

dbt commands accept the same selection syntax everywhere — CLI, Dagster schedule, Airflow BashOperator. A test-only nightly job runs dbt test --select fqn:* or a tag subset like tag:nightly without dbt run. In Dagster, create a second schedule with dbt_select scoped to tests or use a separate @dbt_assets group that invokes dbt test instead of dbt build.

In Airflow, add a second BashOperator task or DAG with dbt test --select tag:critical. The key is not rebuilding models that did not change — tests still scan warehouse tables, so tag expensive tests separately from fast PR checks as covered in Section 19.
