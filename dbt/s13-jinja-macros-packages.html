Jinja basics

Every dbt model file is a Jinja template. dbt reads the file, evaluates the Jinja, and sends the resulting SQL string to your warehouse. You already used Jinja in earlier sections — {{ ref('src_listings') }} and {% if is_incremental() %} are Jinja — without necessarily naming it.

The three delimiter types

SyntaxNamePurposeExample
{{ ... }}ExpressionPrint a value into the compiled SQL{{ ref('dim_hosts_cleansed') }}
{% ... %}StatementControl flow, set variables, define macros{% if target.name == 'prod' %}
{# ... #}CommentNotes for developers; stripped at compile time{# dev-only filter #}

Whitespace control matters in production macros. A minus sign immediately inside the delimiter trims whitespace on that side: {%- for col in cols -%} prevents blank lines in compiled SQL. The course solution for no_empty_strings uses {%- and -%} for that reason.

Try Jinja without a model file

The fastest way to learn what dbt will compile is dbt compile --inline. Pass a quoted string of Jinja; dbt renders it and prints the result. No model file required.

dbt compile --inline

dbt compile --inline "{# This is a comment #}{% set my_name = 'Zoltan' %}{{ my_name }}"
15:04:12  Running with dbt=1.11.12
15:04:13  Compiled inline node is:
Zoltan

The comment disappears entirely. The {% set %} statement assigns a variable in Jinja scope; the {{ my_name }} expression prints it. Nothing hits the warehouse until you add SQL and run dbt show or dbt run.

Variables with set

Jinja variables are not warehouse columns. They exist only while dbt compiles the file. Use them to build repeated fragments, hold lists of column names, or branch on environment.

{% set schema_prefix = target.name ~ '_analytics' %}
SELECT * FROM {{ schema_prefix }}.dim_listings_cleansed

The tilde operator ~ concatenates strings in Jinja. target is a global dbt object: target.name is your active profile target (dev, prod, etc.). On BigQuery the same pattern works; on Postgres/Databricks the schema naming convention may differ but the Jinja mechanics are identical.

if and for

Conditional blocks let one model file serve dev and prod. Loops generate repetitive SQL — column lists, union branches, pivot columns — from a list you define once.

{% if is_incremental() %}
  AND review_date > (SELECT MAX(review_date) FROM {{ this }})
{% endif %}
{% set numeric_cols = ['price', 'minimum_nights'] %}
SELECT
  listing_id,
{% for col in numeric_cols %}
  COALESCE({{ col }}, 0) AS {{ col }}{% if not loop.last %},{% endif %}
{% endfor %}
FROM {{ ref('src_listings') }}

Read compiled SQL when Jinja confuses you. After dbt compile, open target/compiled/<project>/models/.... Every {{ ref() }} is replaced with a fully qualified relation name; every {% if %} branch that did not apply is gone. That file is what the warehouse actually receives.

Parse phase versus execute phase

dbt runs Jinja in two contexts. During parsing, it builds the DAG: ref() resolves dependencies, configs merge, but execute is false and warehouse queries in macros should not run. During execution, execute is true, models compile fully and run against the warehouse. Macros that call run_query or adapter.get_columns_in_relation behave differently between dbt parse and dbt run — always guard expensive work with {% if execute %}.

Commandexecute flagTypical use
dbt parsefalseValidate project structure; CI manifest-only jobs
dbt compiletrue when connectedInspect compiled SQL in target/compiled
dbt compile --inline "..."true when connectedTest one Jinja expression or macro
dbt runtrueBuild models; macros expand per model
dbt lsfalseList nodes without compiling SQL bodies fully
Compile is the macro debugger. When a model fails with a Jinja error, the stack trace points at a macro file line. Reproduce the macro call with --inline, then read target/compiled for the full expansion. Faster than adding log() statements and re-running the whole DAG.

Jinja filters and string operations

Filters pipe a value through a function: {{ column_name | lower }}. Common filters in dbt macros include upper, replace, trim, default, and as_text. The course's fct_reviews uses the concatenation operator ~ inside log() to build a readable message string at compile time.

Operator / filterExampleResult in compiled SQL or log
~ concatenate{% set msg = 'dev' ~ '_suffix' %}Jinja string dev_suffix
| lower{{ 'Room Type' | lower }}room type in output
| replace{{ 'a b' | replace(' ', '_') }}a_b
| default{{ var('x') | default('none') }}Falls back when var unset
loop.indexInside {% for %}1-based iteration counter
loop.last{% if not loop.last %},{% endif %}Comma between items, not after last

env_var versus var

Project variables (var()) belong in dbt_project.yml under vars: or passed on the CLI with --vars '{"start_date": "2024-01-01"}'. Environment variables (env_var()) read from the shell — typical for secrets in profiles.yml like password: "{{ env_var('SNOWFLAKE_PASSWORD') }}". Do not put secrets in var(); they can appear in compiled artifacts and logs.

vars:
  start_date: '2020-01-01'
  end_date: '2024-12-31'

The finished fct_reviews.sql checks var("start_date", False) to choose between a bounded incremental window and the default max-date strategy from Section 8. Passing vars on the CLI lets orchestration backfill a date range without editing SQL:

Incremental run with vars

dbt run --select fct_reviews --vars '{"start_date": "2024-06-01", "end_date": "2024-07-01"}'
16:02:11  Loading DEV.fct_reviews incrementally (start_date: 2024-06-01, end_date: 2024-07-01)
16:02:14  1 of 1 OK created sql incremental model DEV.fct_reviews .......... [SUCCESS 892 in 2.1s]
Certification: distinguish ref() (dbt relations), source() (declared raw tables), var() (project variables), and env_var() (OS environment). Only ref and source participate in lineage.

Writing macros

A macro is a Jinja function you define once in the macros/ folder and call from any model, test, snapshot or hook. dbt loads every .sql file under macro-paths (default macros/) at parse time.

  • airbnb/
    • macros/ ← new in this section
      • select_positive_values.sql
      • no_empty_strings.sql
    • models/
    • packages.yml ← added later in section

Writing macros: {% macro %}...{% endmacro %}

Macro files contain no bare SQL outside a macro definition unless you are using older undocumented patterns — every .sql file in macros/ should wrap logic in {% macro name(args) %}...{% endmacro %}. dbt parses all macros into a global namespace; file name does not constrain macro name, but matching them (select_positive_values.sql defines select_positive_values) keeps the project navigable.

Define a macro with macro/endmacro

The course's first macro filters rows where a numeric column is positive. It takes two arguments: the relation to query and the column name.

{% macro select_positive_values(model, column_name) %}
    SELECT *
    FROM {{ model }}
    WHERE {{ column_name }} > 0
{% endmacro %}

Arguments are positional by default. Call the macro with {{ select_positive_values(...) }} inside an expression delimiter. The macro body can contain any mix of SQL and Jinja; dbt inlines the returned string at the call site.

Calling macros from the CLI

Before wiring a macro into a model, prove it compiles and returns sensible rows with --inline:

dbt show --inline "{{ select_positive_values('dim_listings_cleansed', 'price') }}"

dbt show executes the compiled SQL and prints a sample (default five rows). Use it to validate macro output before embedding it in a production model. On warehouses without a native preview API, dbt wraps the query in a limit.

Macro arguments and defaults

Macros accept positional and keyword arguments like Python functions. Define defaults in the macro signature for optional behaviour:

{% macro select_above_threshold(model, column_name, threshold=0) %}
    SELECT *
    FROM {{ model }}
    WHERE {{ column_name }} > {{ threshold }}
{% endmacro %}

Call with one or two overrides: {{ select_above_threshold(ref('dim_listings_cleansed'), 'price') }} uses 0; {{ select_above_threshold(ref('dim_listings_cleansed'), 'price', 100) }} filters above 100.

Advanced macros

Once you can pass arguments, macros become code generators: loops emit SQL fragments, the adapter object introspects the warehouse, and run_query executes SQL at compile time when you need metadata back in Jinja.

Loops that generate SQL

The no_empty_strings macro builds a WHERE clause predicate for every string column in a relation. It loops over columns returned by the adapter instead of hard-coding column names.

{# Here is my solution after removing most of the white spaces #}

{% macro no_empty_strings(model) %}
    {%- for col in adapter.get_columns_in_relation(model) -%}
        {%- if col.is_string() %}
            {{ col.name }} IS NOT NULL AND {{ col.name }} <> '' AND
        {%- endif %}
    {%- endfor %}
    TRUE
{% endmacro %}

Calling it inside a model wraps the table in a dynamic string-column guard:

SELECT * FROM {{ ref('dim_listings_cleansed') }}
WHERE {{ no_empty_strings(ref('dim_listings_cleansed')) }}

Compile no_empty_strings inline

dbt compile --inline "SELECT * FROM {{ ref('dim_listings_cleansed') }} WHERE {{ no_empty_strings(ref('dim_listings_cleansed')) }}"
15:22:41  Running with dbt=1.11.12
15:22:42  Compiled inline node is:
SELECT * FROM ...
WHERE LISTING_NAME IS NOT NULL AND LISTING_NAME <> '' AND
ROOM_TYPE IS NOT NULL AND ROOM_TYPE <> '' AND
...
TRUE

The trailing TRUE absorbs the final AND from the loop so you never write invalid SQL like ... AND with nothing after it. This pattern — loop plus sentinel value — appears often in macro-generated filters.

The adapter object

adapter is dbt's handle to the connected warehouse. Macros use it for capabilities that differ by database: listing columns, checking relation existence, quoting identifiers, dispatching dialect-specific implementations.

adapter methodTypical use
get_columns_in_relation(relation)Dynamic column lists (audit macros, schema drift checks)
get_relation(database, schema, identifier)Check if a table exists before conditional logic
dispatch(macro_name, macro_namespace)Call a warehouse-specific implementation of a macro
quote(column_name)Apply correct quoting for the active adapter
Adapter behaviour is warehouse-specific. col.is_string() works on Snowflake, BigQuery, Postgres and Databricks through dbt's type abstraction, but edge cases exist (VARIANT columns on Snowflake, STRUCT on BigQuery). Always compile against your target when a macro introspects the catalog.

run_query and statement blocks

Most Jinja runs at compile time without touching the warehouse. When you need query results during compilation — for example reading the max partition date from a table to build a dynamic predicate — use run_query() inside a {% set %} block:

{% macro get_max_review_date() %}
  {% set sql = "select max(review_date) as max_dt from " ~ ref('fct_reviews') %}
  {% set results = run_query(sql) %}
  {% if execute %}
    {% set max_dt = results.columns[0].values()[0] %}
    {{ return(max_dt) }}
  {% endif %}
{% endmacro %}

The execute flag is false during the parsing phase; wrap warehouse calls so dbt can build the DAG without connecting twice. Package macros like dbt_utils.get_column_values use this pattern internally.

Generating pivot-style SQL with loops

Another common advanced pattern is turning a list of values into a wide query:

{% macro pivot_room_types(room_types) %}
  {% for rt in room_types %}
    SUM(CASE WHEN room_type = '{{ rt }}' THEN 1 ELSE 0 END) AS {{ rt | replace(' ', '_') | lower }}_cnt{% if not loop.last %},{% endif %}
  {% endfor %}
{% endmacro %}

The | replace and | lower filters are Jinja filters applied to strings. Package macros such as dbt_utils.pivot generalise this for production use.

statement blocks for readable multi-line SQL

When a macro embeds a large SQL string, block forms keep indentation readable. The checker on this site requires balanced tags — in your project files, {% set query %} ... {% endset %} captures multi-line SQL for run_query:

{% set query %}
  select count(*) as cnt from {{ ref('fct_reviews') }}
{% endset %}
{% set results = run_query(query) %}

Logging from macros

{{ log(message, info=True) }} writes to logs/dbt.log always; with info=True it also prints to the console during dbt run. The course fct_reviews logs which incremental branch executed — invaluable when debugging backfills in CI logs. Section 16 adds a dedicated logging macro exercise.

Adapter docs are the reference for introspection. The course links to adapter functions in the dbt docs. Methods differ slightly by warehouse; always verify against your adapter when using get_columns_in_relation or custom materializations.

Custom generic tests

Generic tests are macros defined with {% test name(...) %} instead of {% macro %}. dbt registers them as test nodes you attach in YAML. You built two in the previous section; this section names the mechanism without repeating the full walkthrough.

The positive_values test fails when any row has a non-positive value in the named column. The entire implementation is a macro body that returns rows matching the failure condition — dbt fails the test when the query returns any rows.

{% test positive_values(model, column_name) %}
SELECT * FROM {{ model }} WHERE {{ column_name }} <= 0
{% endtest %}
Full coverage lives in Section 12. For the complete generic test lifecycle — writing positive_values and minimum_row_count, attaching them in schema.yml, contract tests, constraints, and unit tests — see Advanced Testing. The key insight for this section: {% test %} is syntactic sugar over {% macro %} with a naming convention dbt's test runner understands.

The test query pattern — return rows that violate the rule — is identical to singular tests, but reusable across models.

Setting test parameters via macro arguments

Generic test macros accept the same argument pattern as regular macros. YAML passes values under arguments:; dbt maps them to macro parameters. Optional parameters get defaults inside the macro definition.

The minimum_row_count test warns or errors when a model has fewer rows than expected. It demonstrates a numeric macro argument and default severity inside the test body:

{% test minimum_row_count(model, min_row_count) %}
{{ config(severity = 'warn') }}

SELECT
    COUNT(*) as cnt
FROM
    {{ model }}
HAVING
    COUNT(*) < {{ min_row_count }}
{% endtest %}

Attach it in schema.yml with the parameter value and an optional severity override:

  - name: dim_listings_cleansed
    description: Cleansed table which contains Airbnb listings.
    data_tests:
      - minimum_row_count:
          arguments:
            min_row_count: 1000
          severity: error

Severity semantics (warn vs error, exit codes, CI behaviour) are covered in depth in Section 12. For this section, remember that macro arguments and test YAML arguments are the same pipe: name the parameter in the {% test %} signature, pass it under arguments: in YAML.

arguments.column_name: pricecolumn_nameStandard for column-scoped tests
severity: errorNot a macro argTest node config; overrides {{ config(severity=...) }} in macro
where: "country = 'US'"Often where in package testsScoped subset of rows to test

positive_values in YAML (Section 12)

Column-scoped generic tests attach under columns:. The test name matches the macro name; arguments map to macro parameters:

columns:
  - name: price
    data_tests:
      - positive_values:
          arguments:
            column_name: price

In many cases dbt infers column_name from context when the test is nested under a column block — behaviour depends on dbt version and test definition. Explicit arguments: avoids ambiguity and matches the 1.11 YAML style used throughout this course.

Combining macro defaults and YAML overrides

The minimum_row_count test sets {{ config(severity = 'warn') }} inside the macro body as a default. YAML on dim_listings_cleansed overrides to severity: error because node config wins over inline macro config for that test invocation. This layering lets you ship warn-by-default tests that become errors on critical models without forking the macro.

Severity is owned by Section 12. For warn versus error exit codes, CI implications, and dbt build behaviour when warnings fail the job, read Advanced Testing. This section only connects severity to macro-defined defaults and YAML overrides.

Packages

Packages are dbt projects you depend on. They install into dbt_packages/, bringing macros, models, tests and seeds you can call from your project. The hub at hub.getdbt.com lists maintained packages; you can also install from a Git URL.

packages.yml and dbt deps

Create packages.yml at the project root (alongside dbt_project.yml). List each dependency with a version pin, then run dbt deps to download and lock them.

packages:
  - package: dbt-labs/dbt_utils
    version: 1.3.3
  - package: metaplane/dbt_expectations
    version: 0.10.10 # Check https://github.com/metaplane/dbt-expectations/releases for the latest release

Hub syntax versus Git URL

The course uses the hub shorthand package: org/name. For forks or unreleased commits, install directly from Git:

packages:
  - git: "https://github.com/metaplane/dbt-expectations.git"
    revision: 0.10.10
  - package: dbt-labs/dbt_utils
    version: 1.3.3
Use the metaplane fork, not calogica. The original calogica/dbt_expectations package is unmaintained. The course and repo pin metaplane/dbt_expectations at 0.10.10. Older tutorials referencing calogica will fail on modern dbt versions.

package-lock.yml and reproducibility

Modern dbt writes package-lock.yml when you run dbt deps, recording the exact resolved versions and commit SHAs. Commit this file so every developer and CI runner installs identical package code. When a hub package publishes a patch you did not intend, the lockfile prevents silent drift until you deliberately run dbt deps --upgrade.

Local packages and monorepos

Besides hub and Git remotes, dbt supports local path dependencies for monorepos or vendored code:

packages:
  - local: ../shared_macros
  - package: dbt-labs/dbt_utils
    version: 1.3.3

Local packages symlink or copy into dbt_packages/ on deps. Teams use this when multiple dbt projects share a macro library without publishing to the hub. The trade-off is path fragility in CI — ensure checkout layout matches the relative path.

Upgrading packages safely

  1. Read the package changelog on GitHub for breaking macro renames.
  2. Bump the version in packages.yml (or run dbt deps --upgrade with a lockfile).
  3. Run dbt deps locally and grep your project for deprecated macro names.
  4. Run dbt compile or dbt build --select state:modified+ in CI before merging.
The course script shows dbt_utils 1.3.0; the repo pins 1.3.3. Always follow the committed packages.yml in the Airbnb repo, not an older lecture screenshot. Patch releases fix adapter compatibility without changing macro names.

Using dbt_utils macros

After dbt deps, package macros are namespaced by package name. dbt_utils is the most widely used package: surrogate keys, date spines, pivot helpers, safe casts, and dozens of generic tests.

generate_surrogate_key in fct_reviews

The course updates fct_reviews to hash natural key columns into a single review_id. Why surrogate keys matter for dimensional modelling is in Section 5; here is the implementation the project actually runs:

{{
  config(
    materialized = 'incremental',
    on_schema_change='fail',
    event_time='review_date'
    )
}}

WITH src_reviews AS (
  SELECT * FROM {{ ref('src_reviews') }}
)
SELECT 
  {{ dbt_utils.generate_surrogate_key(['listing_id', 'review_date', 'reviewer_name', 'review_text']) }} as review_id,
  *
FROM src_reviews
WHERE review_text is not null
{% if is_incremental() %}
  {% if var("start_date", False) and var("end_date", False) %}
    {{ log('Loading ' ~ this ~ ' incrementally (start_date: ' ~ var("start_date") ~ ', end_date: ' ~ var("end_date") ~ ')', info=True) }}
    AND review_date >= '{{ var("start_date") }}'
    AND review_date < '{{ var("end_date") }}'
  {% else %}
    AND review_date > (select max(review_date) from {{ this }})
    {{ log('Loading ' ~ this ~ ' incrementally (all missing dates)', info=True)}}
  {% endif %}
{% endif %}

On Snowflake the macro typically compiles to MD5(COALESCE(CAST(listing_id AS VARCHAR), '') || '-' || ...). On BigQuery expect TO_HEX(MD5(...)). The point is stable cross-platform hashing without maintaining dialect-specific SQL yourself.

How generate_surrogate_key fits the grain

One row in fct_reviews represents one guest review. The natural key is the combination of listing, date, reviewer and review text — four columns that are awkward foreign keys. Hashing them into review_id gives downstream marts and dashboards a single join column. If any component of the natural key changes (for example a typo fix in review_text), the hash changes and the row gets a new surrogate — treat that as a new fact row or accept Type 1 correction depending on business rules. Dimensional theory is in Section 5: Grain, surrogate keys and conformed dimensions.

Incremental logic and Jinja together

The finished fct_reviews.sql combines three Jinja techniques from this section: a package macro in the SELECT list, nested {% if is_incremental() %} with a secondary branch on var(), and log() calls that explain which branch ran. The surrogate key applies to every inserted row; incremental filters only control which source rows are considered on a given run.

{% if is_incremental() %}
  {% if var("start_date", False) and var("end_date", False) %}
    AND review_date >= '{{ var("start_date") }}'
    AND review_date < '{{ var("end_date") }}'
  {% else %}
    AND review_date > (select max(review_date) from {{ this }})
  {% endif %}
{% endif %}

Microbatch and event_time='review_date' extend this pattern in later production sections. The Jinja structure stays the same: outer incremental guard, inner business rule branch.

surrogate_key naming history

Older projects and blog posts reference dbt_utils.surrogate_key. dbt_utils 1.x renamed it to generate_surrogate_key for clarity. Searching the repo for surrogate_key should return only documentation cross-references — the live macro name in fct_reviews is generate_surrogate_key. The macro accepts a list of column names; order matters for hash stability but not for uniqueness as long as the set is consistent.

date_spine in practice

Sparse fact tables leave gaps on calendar charts. date_spine generates one row per day (or hour, week, month) between bounds, which you left-join to facts so dashboards show zeroes instead of disconnected lines. The start and end arguments are SQL snippets, not Jinja strings — pass warehouse-cast dates as shown below.

On BigQuery use cast('2020-01-01' as date); on Snowflake the same cast works. Databricks may prefer DATE'2020-01-01' in the argument strings. dbt_utils handles the dialect-specific date arithmetic inside dispatched macros.

Traps that catch people

  • Missing dbt deps in CI — parse fails with "Could not find macro dbt_utils.generate_surrogate_key". Fresh clones never include dbt_packages/. Run dbt deps before dbt parse, dbt run, or dbt build.
  • Wrong expectations package — copying calogica/dbt_expectations from an old blog post installs unmaintained code that breaks on dbt 1.11. Pin metaplane/dbt_expectations at 0.10.10.
  • Macro name collision — defining generate_surrogate_key in your project overrides the package macro depending on dispatch order. Prefix project macros (airbnb_generate_surrogate_key) or use namespaces deliberately.
  • Unbalanced Jinja in macros — a missing {% endif %} fails at compile time with a line number in the macro file, not the calling model. Test macros with --inline before embedding.
  • Quoting macro arguments — passing 'dim_listings_cleansed' as a string to select_positive_values produces invalid SQL (FROM dim_listings_cleansed without schema). Pass ref('dim_listings_cleansed') instead.
  • Adapter introspection in parsing phase — calling run_query without {% if execute %} can error during dbt compile on a cold DAG. Guard warehouse calls.
  • Whitespace explosions — forgetting {%- -%} in loop macros adds dozens of blank lines to compiled SQL, making debugging harder and occasionally breaking parsers. Copy the trim pattern from no_empty_strings.
  • Surrogate key column order — changing the column list in generate_surrogate_key reassigns every review_id, breaking downstream joins and historical snapshots. Treat key definitions as contract changes.
  • Package version drift — developer A pins dbt_utils 1.3.3, developer B runs deps without pulling and stays on 1.2.x. Commit package-lock.yml and enforce deps in CI.
  • Git URL without revision — installing a package from main branch breaks reproducibility the next time someone runs deps. Always pin revision to a tag or SHA.
  • Macro SQL injection style bugs — interpolating {{ column_name }} without validation lets YAML typos produce invalid SQL or, in worst cases, unsafe dynamic SQL. Validate allowed identifiers in macros that accept names.
  • Assuming macros are DAG nodes — they expand inline and do not appear separately in lineage. Documentation and ownership stay with the calling model.

Production patterns

Mature teams treat macros/ like a standard library: small, well-named functions with docstrings in comments, each tested via dbt compile --inline or a dedicated unit test model. Project-specific business logic stays in models; macros hold repeated SQL mechanics (surrogate keys, standardised incremental filters, audit column bundles). Package pins live in packages.yml with Renovate or Dependabot PRs; CI runs dbt deps then a slim dbt build to catch breaking macro signature changes.

Adapter dispatch lets you ship one macro name with Snowflake, BigQuery and Postgres implementations — dbt picks the right one at compile time. dbt_utils uses this internally; large organisations mirror the pattern for warehouse-specific optimisations without forking entire models.

Pattern: macro library folder

macros/utils/ for generic SQL helpers, macros/audit/ for logging and metadata, macros/schema/ for generate_schema_name overrides. One macro per file, named after the macro function.

Anti-pattern: mega-macro

A 400-line macro that builds an entire mart. Impossible to test, debug or reuse. Split into composable macros or move orchestration into models with CTEs.

Interview questions

Answer each one out loud before opening it.

What is Jinja's role inside dbt?Fundamentals

Jinja is the templating layer dbt uses to generate warehouse SQL from model files. Expressions like {{ ref('model') }} inject relation names; statements like {% if is_incremental() %} control which SQL branches compile; comments like {# note #} are stripped before execution.

dbt never sends Jinja to the warehouse — it compiles templates locally (or in Cloud's compile step) into pure SQL, then executes that. Macros are Jinja functions that return SQL fragments or full queries.

What is the difference between {{ }} and {% %} in Jinja?Jinja

{{ ... }} is an expression delimiter: it evaluates Jinja and prints the result into the compiled output. Use it wherever a value belongs in SQL — column lists, relation names, macro return values.

{% ... %} is a statement delimiter: it runs logic without necessarily printing anything — if, for, set, macro, test. Statements control structure; expressions produce text in the final SQL.

How do you define and call a dbt macro?Jinja

Define it in a .sql file under macros/ with {% macro name(arg1, arg2) %} ... {% endmacro %}. dbt loads all macro files at parse time.

Call it from any model, test, or hook with {{ name(value1, value2) }} inside expression delimiters. The macro body can contain SQL and nested Jinja; the compiled result replaces the call site. Test macros quickly with dbt compile --inline "{{ name(...) }}".

When would you use a macro instead of a CTE?Design

Use a CTE when the logic is specific to one model and readable inline. Use a macro when the same pattern repeats across many files, needs parameters, or must be shared with tests and hooks.

Examples macro-worthy in production: standard audit columns, surrogate key generation, dynamic pivot column lists, incremental date-window predicates, and generic test SQL. A one-off three-step transform stays a CTE.

What does the adapter object provide in Jinja macros?Fundamentals

adapter is dbt's connection to the active warehouse adapter. It exposes methods for metadata (get_columns_in_relation), relation lookup (get_relation), identifier quoting, and dispatching dialect-specific macro implementations.

The course's no_empty_strings macro uses adapter.get_columns_in_relation(model) to loop string columns dynamically. Without adapter introspection you would hard-code column names and break when schemas change.

How are generic tests related to macros?Testing

Generic tests are macros defined with {% test test_name(model, ...) %} instead of {% macro %}. dbt registers them as reusable tests attachable in YAML. The test body returns rows that represent failures; zero rows means pass.

Custom tests like positive_values and minimum_row_count from Section 12 follow this pattern. Package tests from dbt_expectations are the same mechanism with richer parameter sets.

How do you install and pin dbt packages?Production

Declare dependencies in packages.yml at the project root. Hub packages use package: org/name and version:. Git forks use git: URL and revision: tag or SHA. Run dbt deps to download into dbt_packages/.

Pin exact versions — the course uses dbt-labs/dbt_utils at 1.3.3 and metaplane/dbt_expectations at 0.10.10. Commit packages.yml and the generated package-lock.yml; gitignore dbt_packages/.

What does dbt_utils.generate_surrogate_key do and why use it?Modelling

It hashes a list of column values into a single surrogate key column, handling nulls consistently and using warehouse-appropriate MD5/SHA logic via adapter dispatch. In fct_reviews it produces review_id from listing, date, reviewer and text.

Surrogate keys simplify joins, stabilise facts when natural keys are composite, and decouple the warehouse from source identifiers. Changing the column list changes every key — treat it as a breaking contract. Theory is in Section 5.

What is the difference between var(), env_var() and ref()?Comparison

ref('model') resolves to a relation dbt builds — models, seeds, snapshots — and establishes DAG dependencies. var('name', default) reads dbt project variables from dbt_project.yml or CLI --vars. env_var('NAME') reads operating-system environment variables, common for secrets in profiles.yml.

Mixing them up causes subtle bugs: ref() in a macro argument expects a relation object; a string table name skips schema resolution. var('start_date') in fct_reviews drives optional incremental windows without editing SQL.

Your CI job fails with "macro not found" for dbt_utils. What happened?Troubleshooting

The CI runner parsed or compiled the project without installing packages. dbt_packages/ is not committed to git, so a fresh clone has no package macros until dbt deps runs.

Fix: add dbt deps as the first CI step after checkout, before dbt parse, dbt build, or dbt test. Verify packages.yml is present and version pins resolve. Cache the deps folder in Docker layers to speed pipelines.

When does run_query execute and what are the risks?Performance

run_query() executes SQL against the warehouse during the execution phase of compilation (when execute is true). Macros use it to fetch metadata — distinct column values, max dates — back into Jinja for dynamic SQL generation.

Risks: extra warehouse cost on every run, failures when the warehouse is unreachable at compile time, and non-deterministic compiles if source data changes between runs. Guard with {% if execute %} and prefer static vars or metadata models when possible.

Why pin dbt_expectations to the metaplane fork?Gotcha

The original calogica/dbt_expectations package lagged behind dbt Core releases. Metaplane maintains a fork compatible with modern dbt (0.10.10 in this course). Installing the wrong package name yields missing tests or compile errors on current dbt.

Install via hub package: metaplane/dbt_expectations or Git URL https://github.com/metaplane/dbt-expectations.git with revision: 0.10.10. Check releases on GitHub before upgrading.

Explain how dbt compile --inline helps you develop macros.Jinja

dbt compile --inline renders an arbitrary Jinja/SQL string using your project's macro context — package macros, project macros, ref(), and vars — without creating a throwaway model file. You see the exact SQL dbt would produce, printed to stdout or written for inspection.

Pair it with dbt show --inline to execute a preview when the macro returns a SELECT. This shortens the feedback loop for macros like select_positive_values and no_empty_strings before embedding them in production models where errors are harder to isolate.

Recap

  • Jinja has three delimiters: {{ }} expressions, {% %} statements, {# #} comments.
  • Macros live in macros/*.sql, defined with {% macro %}...{% endmacro %}, called with {{ macro_name(args) }}.

  • Advanced macros loop with {% for %}, introspect via adapter, and optionally call run_query at compile time.
  • Generic tests are {% test %} macros; full walkthrough is in Section 12.
  • Test parameters pass through YAML arguments:; severity is test config, not a macro arg.
  • Packages declare in packages.yml; install with dbt deps into dbt_packages/.
