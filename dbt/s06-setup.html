Snowflake environment setup

dbt needs a warehouse that already holds your raw data and a service account with permission to create objects in a development schema. The course uses Snowflake with an AIRBNB database, a RAW schema for untouched source tables, and a DEV schema where dbt builds models.

Finding your Snowflake account URL

The account identifier in profiles.yml is not the full URL you paste into a browser. Take the string from your Snowflake registration email that appears before .snowflakecomputing.com. In the instructor's example that is frgcsyo-ie17820. Some accounts include a cloud region suffix such as frgcsyo-ie17820.aws — copy exactly what Snowflake shows you, because a missing .aws segment is one of the most common reasons dbt debug fails with a connection error.

dbt Labs documents the same confusion in their Snowflake connection guide. On BigQuery you would use a project ID and dataset; on Databricks a host and HTTP path; on Postgres a hostname and database name. The pattern is the same: the adapter needs the identifier your platform expects, not a URL you guessed.

Write your account identifier down before you touch profiles.yml. You will need it twice — once when configuring Snowflake and again when pasting into the profile. Students who skip this step often paste the full browser URL and spend twenty minutes debugging a connection that was never going to work.

What automated setup creates step by step

The Streamlit app at dbtsetup.nordquant.com walks you through RSA key upload and account connection, then runs the same SQL the manual scripts contain. Understanding the output helps when something is missing later.

  1. Warehouse — creates or reuses COMPUTE_WH and grants OPERATE to the transformation role.
  2. Database and schemas — creates AIRBNB with RAW (sources) and DEV (dbt build target during learning).
  3. Raw tables — defines raw_listings, raw_reviews, raw_hosts and loads CSV data from the public S3 bucket.
  4. TRANSFORM role and dbt user — service account with RSA key auth, ALL privileges on the database for modeling work.
  5. REPORTER role and PRESET user — read-only access to DEV for the Preset dashboard lesson in Section 15.
  6. profiles.yml download — a pre-filled profile you drop into the airbnb folder after dbt init.

If the primary URL fails, the backup at udemy-dbt-setup.streamlit.app runs the same application. Both require a Snowflake trial or paid account with ACCOUNTADMIN access for the initial grant scripts.

Roles, users, warehouse and schemas

Manual setup creates two roles with different privilege levels. TRANSFORM is what dbt runs as: full control over the AIRBNB database so it can create and replace models. REPORTER is read-only on the DEV schema, used later by Preset for dashboards.

The dbt user is a service account (TYPE=SERVICE) authenticated with an RSA key pair, not a password. Snowflake key-pair auth is documented on the Snowflake site; on Windows, PuTTYgen is a common way to generate the pair. Paste the public key content into the SQL below where indicated.

-- Use an admin role
USE ROLE ACCOUNTADMIN;

-- Create the `transform` role
DROP ROLE IF EXISTS TRANSFORM;
CREATE ROLE TRANSFORM;
GRANT ROLE TRANSFORM TO ROLE ACCOUNTADMIN;

-- Create the default warehouse if necessary
GRANT OPERATE ON WAREHOUSE COMPUTE_WH TO ROLE TRANSFORM;

-- Create the `dbt` user and assign to role
DROP USER IF EXISTS dbt;
CREATE USER IF NOT EXISTS dbt
  LOGIN_NAME='dbt'
  TYPE=SERVICE
  RSA_PUBLIC_KEY="<<Add Your Public Key File's content here>>"
  DEFAULT_ROLE=TRANSFORM
  DEFAULT_WAREHOUSE='COMPUTE_WH'
  DEFAULT_NAMESPACE='AIRBNB.RAW'
  COMMENT='DBT user used for data transformation';

GRANT ROLE TRANSFORM to USER dbt;

-- Set up permissions to role `transform`
GRANT ALL ON WAREHOUSE COMPUTE_WH TO ROLE TRANSFORM;
GRANT ALL ON DATABASE AIRBNB to ROLE TRANSFORM;
GRANT ALL ON ALL SCHEMAS IN DATABASE AIRBNB to ROLE TRANSFORM;
GRANT ALL ON FUTURE SCHEMAS IN DATABASE AIRBNB to ROLE TRANSFORM;
GRANT ALL ON ALL TABLES IN SCHEMA AIRBNB.RAW to ROLE TRANSFORM;
GRANT ALL ON FUTURE TABLES IN SCHEMA AIRBNB.RAW to ROLE TRANSFORM;

-- Create the user and permissions for Preset.io
USE ROLE ACCOUNTADMIN;

DROP ROLE IF EXISTS REPORTER;
CREATE ROLE REPORTER;

DROP USER IF EXISTS PRESET;
CREATE USER PRESET
  LOGIN_NAME='preset'
  TYPE=SERVICE
  RSA_PUBLIC_KEY="<<Add Your Public Key File's content here>>"
  DEFAULT_WAREHOUSE='COMPUTE_WH'
  DEFAULT_ROLE=REPORTER
  DEFAULT_NAMESPACE='AIRBNB.DEV'
 COMMENT='Preset user for creating reports';

GRANT ROLE REPORTER TO USER PRESET;
GRANT ROLE REPORTER TO ROLE ACCOUNTADMIN;
GRANT ALL ON WAREHOUSE COMPUTE_WH TO ROLE REPORTER;
GRANT USAGE ON DATABASE AIRBNB TO ROLE REPORTER;
GRANT USAGE ON ALL SCHEMAS IN DATABASE AIRBNB to ROLE REPORTER;
GRANT USAGE ON FUTURE SCHEMAS IN DATABASE AIRBNB to ROLE REPORTER;
GRANT SELECT ON ALL TABLES IN SCHEMA AIRBNB.DEV to ROLE REPORTER;
GRANT SELECT ON FUTURE TABLES IN SCHEMA AIRBNB.DEV to ROLE REPORTER;

Notice the separation: dbt writes into schemas it controls; Preset reads from DEV only. That is the pattern a real team uses — transformation and consumption get different roles so a misconfigured dashboard cannot drop a table.

On Postgres or BigQuery the role model differs. Postgres uses database users and GRANT on schemas directly. BigQuery uses IAM roles on datasets. The course uses Snowflake roles because they map cleanly to dbt's role: profile field, but the principle — a write role for dbt and a read role for BI — is universal.

Generating RSA key pairs for Snowflake

Snowflake key-pair authentication requires a 2048-bit RSA key pair. The public key is registered on the Snowflake user; the private key goes into profiles.yml. On Windows the course points students to PuTTYgen; on Mac and Linux, OpenSSL is standard.

openssl genrsa 2048 | openssl pkcs8 -topk8 -v2 des3 -inform PEM -out rsa_key.p8
openssl rsa -in rsa_key.p8 -pubout -out rsa_key.pub

Snowflake expects the public key as a single line without header/footer lines. Copy the base64 content between the BEGIN and END markers. The private key in profiles.yml must include the full PEM block with newlines written as \n inside the YAML string, exactly as the EXAMPLE-profiles file demonstrates.

ObjectWhere it livesWho uses it
Public keySnowflake user definition (RSA_PUBLIC_KEY)Snowflake validates JWT signatures against it
Private keyprofiles.yml (never git)dbt signs JWT tokens on each connection
Passphraseprivate_key_passphrase in profileDecrypts the private key if encrypted
Everyday analogy — the RSA key pair works like a mailbox: the public key is the slot anyone can drop mail into (Snowflake holds it), and the private key is the key only you hold to retrieve mail (dbt presents it to prove identity). There is no password to forget, but losing the private key means generating a new pair and updating both sides.

WAREHOUSE, DATABASE and schema layout

Manual import creates COMPUTE_WH if it does not exist, drops and recreates the AIRBNB database, and creates two schemas:

  • RAW — landing zone for CSV data loaded from S3. dbt reads from here via source() but never writes here.
  • DEV — where dbt builds models during development. The example profile sets schema: DEV; in production the course later switches to per-developer schemas like DBT_YOURNAME.

Snowflake object hierarchy for the Airbnb project

COMPUTE_WH — virtual warehouse; all dbt queries run here and bill here
AIRBNB database

DEV schema — models dbt creates: views, tables, snapshots, test failures

COMPUTE_WH sizing and auto-suspend

The manual import script creates COMPUTE_WH if it does not already exist. For learning, the default X-Small size is sufficient — the Airbnb dataset is small and dbt debug runs a single lightweight query. What matters more than size during setup is auto-suspend: set the warehouse to suspend after 60 seconds of idle time so a forgotten session does not burn trial credits overnight.

In the Snowflake UI: Admin → Warehouses → COMPUTE_WH → set Auto Suspend to 60 and Auto Resume to On. Every dbt command that touches the warehouse may incur a minimum billing window when the warehouse resumes from suspended state. That is normal and is why dbt debug can appear to "hang" for a few seconds before returning OK.

Python environment with uv

dbt Core is a Python package. The course uses uv to create a virtual environment and install pinned dependencies from pyproject.toml, rather than managing pip and requirements.txt by hand.

Why uv instead of pip

uv reads pyproject.toml, resolves dependencies, creates a venv/ folder, and installs everything in one command. That matters because dbt's adapter must match the Core version exactly — a mismatched dbt-snowflake is a common source of cryptic import errors.

Supported Python versions for dbt Core are listed on the dbt docs compatibility page. The course repo requires Python >=3.10,<3.14.

Installing uv and syncing the environment

Install uv following the Astral getting-started guide, clone the student repo (nordquant/dbt-student-repo) or the full bootcamp repo, and run sync from the repo root where pyproject.toml lives:

uv sync
# Activate virtualenv on Windows (PowerShell):
venv\Scripts\activate
# Activate virtualenv on Mac:
source venv/bin/activate
PowerShell execution policy errors on Windows. If activation fails with a permission error, run Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass in the same session, then activate again. This affects some corporate laptops; it does not change your permanent policy.

Verifying the environment

After activation your prompt should show (venv). Confirm Python and dbt are reachable:

Installing dbt Core and dbt-snowflake

You do not pip-install dbt manually in this course. uv sync reads the pinned versions in pyproject.toml and installs the matching Core and adapter together.

Installing on other warehouses

The pattern is identical: install dbt-core plus one adapter package (dbt-bigquery, dbt-redshift, dbt-postgres, dbt-databricks). Only the adapter and the type: field in profiles.yml change. The project SQL in this course is Snowflake-specific in places (double-colon casts, COPY INTO), but the dbt concepts transfer directly.

Never commit profiles.yml to a public repository. It contains private keys. The course puts it in the project folder for learning convenience; a real team stores credentials in environment variables or a secrets manager and adds profiles.yml to .gitignore.

Profile name must match the project

The top-level key in profiles.yml (airbnb:) must match the profile: field in dbt_project.yml. A mismatch produces Profile 'airbnb' not found even when every credential is correct.

Where profiles.yml can live

dbt init and project anatomy

dbt init scaffolds a project directory with the folder structure dbt expects. The course skips the interactive profile setup because you already have profiles.yml.

Creating the airbnb project

Run from the repository root (where pyproject.toml lives), not from inside an existing project:

dbt init --skip-profile-setup airbnb

Then copy your profiles.yml into the new airbnb folder. From this point forward, every dbt command runs from inside airbnb:

cd airbnb

cd airbnb first, always. The course script states explicitly: once profiles.yml is in place, execute every dbt ... command from the airbnb folder. Running from the repo root gives Could not run dbt: fatal: Not a dbt project.

dbt_project.yml anatomy

The course replaces the scaffold default with a project file that sets materialization defaults, folder-level configs, hooks and test settings. Read it top to bottom before writing your first model.

# Name your project! Project names should contain only lowercase characters
# and underscores. A good package name should reflect your organization's
# name or the intended use of these models
name: 'airbnb'
version: '1.0.0'

# This setting configures which "profile" dbt uses for this project.
profile: 'airbnb'

# These configurations specify where dbt should look for different types of files.
# The `model-paths` config, for example, states that models in this project can be
# found in the "models/" directory. You probably won't need to change these!
model-paths: ["models"]
analysis-paths: ["analyses"]
test-paths: ["tests"]
seed-paths: ["seeds"]
macro-paths: ["macros"]
snapshot-paths: ["snapshots"]
asset-paths: ["assets"]

clean-targets:         # directories to be removed by `dbt clean`
  - "target"
  - "dbt_packages"

# Configuring models
# Full documentation: https://docs.getdbt.com/docs/configuring-models

# In this example config, we tell dbt to build all models in the example/ directory
# as tables. These settings can be overridden in the individual model files
# using the `{{ config(...) }}` macro.
on-run-start:
  - "CREATE TABLE IF NOT EXISTS {{ target.schema }}.audit_log ( model_name STRING, run_timestamp TIMESTAMP )"

models:
  airbnb:
    +grants:
      select: ["transform", "reporter"]
    +post-hook:
      - "INSERT INTO {{ target.schema }}.audit_log VALUES ('{{ this }}', CURRENT_TIMESTAMP)"
    +materialized: view
    dim:
      +materialized: table
    src:
      +materialized: ephemeral
    fct:
      +tags: ['fact']
data_tests:
  +store_failures: true
  +schema: _test_failures

What each block means at setup time:

  • name and profile — project identifier and link to profiles.yml.
  • Path lists — where dbt looks for models, tests, seeds, macros, snapshots and analyses. Changing a folder name without updating these breaks discovery.
  • on-run-start — SQL executed before any model runs; here it creates an audit log table.
  • models: airbnb: — folder-level defaults: views by default, tables in dim/, ephemeral in src/, facts tagged.
  • data_tests: — failed test rows are stored in _test_failures schema for inspection.
Older tutorials use tests: instead of data_tests:. dbt 1.8 renamed the key; both parse in 1.11, but new projects should use data_tests:. See the version table in the deeper section below.

on-run-start hook and Jinja in project config

The on-run-start block in the course dbt_project.yml runs before any model builds. It creates an audit log table in the active target schema:

CREATE TABLE IF NOT EXISTS {{ target.schema }}.audit_log (
  model_name STRING,
  run_timestamp TIMESTAMP
)

At parse time dbt renders {{ target.schema }} from the active profile target. That is why debug must pass before your first run: the hook touches the warehouse immediately. If TRANSFORM lacks CREATE TABLE on the target schema, the run fails before any model SQL executes.

The matching +post-hook on every model inserts a row into that audit table after each model completes. You will revisit hooks in Section 15; at setup time the important point is that project YAML can contain Jinja, not only model files.

Traps that catch people

  • Full URL as account identifier — pasting https://xy12345.snowflakecomputing.com into account: fails JWT authentication. Use only the account prefix Snowflake documents, sometimes with a region suffix.
  • Public and private key mismatch — regenerating keys on your laptop but not updating the CREATE USER statement leaves the JWT invalid. The error mentions JWT, not "wrong key", which sends people to network debugging first.
  • Newlines in private_key — YAML requires escaped \n for multiline keys. A PEM pasted with literal line breaks often parses incorrectly. Follow the EXAMPLE-profiles format exactly.
  • Running dbt outside airbnb — the project root contains dbt_project.yml. Commands from the repo root fail with "Not a dbt project" even when profiles.yml is correct in a subdirectory.
  • Profile name mismatch — profile: 'airbnb' in the project file must match the top-level key in profiles.yml. Renaming one without the other fails before connection is tested.
  • Forgetting to activate venv — a system Python without dbt installed gives "dbt is not recognized". Always activate after uv sync.
  • Shared DEV schema collisions — building into DEV means two students overwrite each other's models. Per-developer schemas (Section 19) exist to fix this.
  • Committing profiles.yml — convenience of keeping it in the project folder leads to pushing private keys to GitHub. Use env vars or gitignore before any remote push.
  • Skipping raw data verification — proceeding to models when COPY INTO loaded zero rows produces empty staging models that "work" but teach nothing. Always count rows first.
  • Adapter/Core version skew — upgrading dbt-core without dbt-snowflake causes import errors. Pin both in pyproject.toml and use uv.
  • Wrong Snowflake role default — the dbt user defaults to TRANSFORM, but if your personal login runs setup scripts and forgets to USE ROLE TRANSFORM when testing, you see objects created under ACCOUNTADMIN that the dbt user cannot see. Always verify with SHOW GRANTS TO USER dbt.
  • COPY INTO silently loading zero rows — wrong S3 stage permissions or a typo in the file format leaves an empty table. Row count queries after import are mandatory, not optional.

Production patterns

Teams treat setup as two separable problems: warehouse infrastructure (roles, schemas, raw data ingestion) and developer tooling (Python env, dbt project, CI). The course combines them for learning; production splits them cleanly. A platform team owns Snowflake roles and the raw layer; analytics engineers clone the dbt repo and never run CREATE USER themselves.

Credentials never live in the repo. The pattern from _prod_profiles/profiles.yml — {{ env_var('PRIVATE_KEY') }} and separate targets for dev, staging and prod — is the minimum for any shared git remote. CI systems inject secrets at runtime; developers export them locally or use a secrets manager wrapper.

Convention worth adopting early

One schema per developer in dev (DBT_FIRSTNAME), a shared STAGING for pre-prod, and PROD for consumption. Same project code, different target, no manual editing.

Anti-pattern: shared dev schema forever

Everyone building into DEV works until two people run dbt run concurrently and overwrite each other's tables. The failure is silent until someone's model disappears.

Certification pointers

The exam assumes you can set up a dbt project from scratch: where profiles.yml lives relative to dbt_project.yml, what the profile and target keys do, and which files define project structure versus connection details. Expect distinction questions between project-level config (dbt_project.yml) and connection config (profiles.yml).

  • Section 7 — first models assume debug passed; connection and schema defaults determine where models land.
  • Section 19 — multi-target profiles, env vars and CI are the production evolution of what you set up here.
  • Section 16 — when debug passes but runs fail, logs and compiled SQL become the next tool.
Certification: know which config file owns which settings. Materialization defaults and model paths are in dbt_project.yml; account, role, warehouse and schema target are in profiles.yml. Mixing them up is a common exam distractor.

Interview questions

Answer each one out loud before opening it.

What is the difference between dbt_project.yml and profiles.yml?Fundamentals

dbt_project.yml is project configuration checked into git: model paths, default materializations, hooks, tests and project name. It describes how the project behaves and is identical for every developer.

profiles.yml is connection configuration: warehouse credentials, target database, schema, role and threads. It describes where and as whom the project runs, differs per developer and environment, and should not be committed with secrets. The profile: key in the project file links the two by name.

Why does the course use a TRANSFORM role and a separate REPORTER role?Design

Least privilege. dbt needs write access to create and replace models; BI tools need read access only. Granting SELECT on the mart schema to REPORTER while TRANSFORM holds DDL rights means a compromised dashboard credential cannot drop a fact table.

The pattern scales: ingestion roles write to RAW, transformation roles write to modeled schemas, consumption roles read from marts. The exam occasionally tests whether you understand that dbt runs with elevated privileges compared to end users.

Walk me through what dbt debug actually tests.Troubleshooting

Three layers. First, it locates and parses profiles.yml, validating the adapter type and required fields for that adapter. Second, it locates and parses dbt_project.yml, confirming the profile name referenced in the project exists. Third, it opens a real connection to the warehouse and runs a lightweight query to verify credentials, role, warehouse and network access.

A failure at layer one or two is a local config problem. A failure at layer three is credentials, grants or network. The command is deliberately run before any models exist because connection problems should be solved before you write SQL.

Why use RSA key-pair authentication instead of a password for the dbt user?Production

Service accounts should not use passwords that expire, appear in logs or get shared in chat. RSA keys are designed for machine-to-machine auth: the private key lives in a secret store or env var, the public key is registered once on the Snowflake user, and rotation means updating both sides deliberately.

Snowflake encourages TYPE=SERVICE users for automation. Password auth still works but is discouraged for anything running in CI or on a schedule.

What does threads control in profiles.yml and what happens if you set it too high?Performance

threads is the maximum number of models dbt builds in parallel during one invocation. Independent models at the same DAG depth can run concurrently up to that limit.

Too high for your warehouse size causes query queuing, memory pressure or credit spikes. Too low serialises everything and makes even small projects feel slow. The course starts at 1 for safety during learning; production uses 4. The right value depends on warehouse size and model count — watch the warehouse query history and adjust.

Explain the RAW versus DEV schema split.Modelling

RAW is the landing zone: data arrives from ingestion unchanged and dbt reads it via source() but never writes there. DEV is where dbt creates models during development. Separating them makes lineage clear, lets you drop and rebuild the modeled layer without touching source data, and mirrors the medallion pattern (bronze/silver/gold) at a small scale.

In production the names change (PROD, per-developer schemas) but the principle holds: sources and transformations live in different namespaces with different retention and access policies.

Your colleague's dbt debug fails with "JWT token is invalid". How do you help?Troubleshooting

Work through the key pair systematically. Confirm the public key registered on the Snowflake user matches the private key in profiles.yml — regenerating keys on the laptop without updating Snowflake is the most common cause. Check the private key formatting: PEM content with newlines escaped as \n in YAML, including the BEGIN and END lines.

If the key is encrypted, verify private_key_passphrase matches. As a last resort, generate a fresh pair, update both Snowflake and profiles.yml, and debug again. Do not assume a network problem until the key pair is verified.

Why does the course pin dbt-core~=1.11.0 instead of installing latest?Gotcha

Reproducibility. A tutorial written for 1.11 may use syntax that changed in 1.12 (selector flags, YAML keys, default behaviours). Pinning the minor version ensures every student and the CI pipeline run the same compiler, adapter and deprecation warnings.

The tilde allows patch releases (bug fixes) without jumping to a new minor. Teams upgrade deliberately after reading release notes, not because pip decided to.

What is uv and why use it over pip for dbt?Fundamentals

uv is a Python package manager from Astral (the Ruff team). It resolves dependencies from pyproject.toml, creates a virtualenv, and installs locked versions quickly. For dbt, the critical benefit is installing Core and the adapter together at compatible versions.

pip works too, but students frequently end up with a mismatched adapter or a system Python that conflicts with dbt's supported range. uv's lockfile and single uv sync command remove that class of error.

When would you choose the devcontainer over a local virtualenv?Comparison

When the local machine cannot reliably run Python 3.10–3.13 with dbt's dependencies — corporate policy blocking installs, inconsistent system Python, or repeated "works on my machine" issues across the team. The devcontainer provides a known-good image with uv and dbt pre-configured.

It does not help with Snowflake credentials or data setup; those are still your problem. Local venv is faster to iterate when your machine is already configured.

What happens if you run dbt commands from the repository root instead of airbnb?Gotcha

dbt looks for dbt_project.yml in the current working directory and its parents. The repo root contains pyproject.toml but not a dbt project file, so the CLI exits with Could not run dbt: fatal: Not a dbt project. This happens even when airbnb/profiles.yml exists and is correct.

The fix is always cd airbnb first. Some teams open only the airbnb subfolder in their IDE to make the default terminal path correct. CI pipelines use working-directory: airbnb for the same reason.

How does the course load raw Airbnb data without dbt?Fundamentals

dbt does not load CSVs from S3. Snowflake's COPY INTO runs inside the warehouse during manual or automated setup, landing files into AIRBNB.RAW. dbt enters the picture later when models reference those tables via source() in Section 9, or hard-coded schema names in Section 7 staging models before sources are declared.

That separation reinforces the ELT pattern: load first with warehouse-native or ingestion tooling; transform second with dbt. Seeds are the one exception — dbt can load small CSVs from the project — but the three main Airbnb tables are too large and arrive through Snowflake, not the repo.
