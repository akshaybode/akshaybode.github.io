Snapshots sit beside models, seeds, and tests in the dbt project. They read from declared sources (or models) and write Type 2 history tables you reference with ref('scd_raw_listings'). Theory on SCD types, validity joins, and when to choose snapshot over incremental is in Section 5; this section is the hands-on mechanics.

The dbt snapshot command and snapshots/ folder

A snapshot is a dbt node that watches a mutable relation, detects row-level changes, and appends history rows with validity timestamps. You run it with dbt snapshot, not dbt run.

What problem snapshots solve

Your ELT loader lands raw_listings and raw_hosts in Snowflake. Rows get updated in place: a host renames, a listing changes minimum_nights, a price string changes. Staging models and Type 1 dimensions (dim_listings_cleansed, dim_hosts_cleansed) show only the current value after each rebuild. If you need to know what the listing looked like when a review was written, you need Type 2 history — and that is what snapshots produce.

dbt does not infer changes from transaction logs or CDC streams. On each snapshot run it compares the current source query result to what it stored last time, using either a timestamp column or an explicit column list. When a row changed, it closes the old snapshot row and inserts a new one. See Section 5 for the full SCD type taxonomy and point-in-time join pattern.

Running dbt snapshot

The command builds or refreshes every snapshot in the project (or a selection). It is separate from dbt run and dbt build — though dbt build can include snapshots when they are in the selected subgraph.

First snapshot run

dbt snapshot --select scd_raw_listings
11:04:12  Running with dbt=1.11.12
11:04:14  1 of 1 START snapshot DEV.scd_raw_listings ........................ [RUN]
11:04:18  1 of 1 OK snapshotted DEV.scd_raw_listings .................... [SUCCESS 3847 in 3.91s]
11:04:18  Completed successfully

On the first run, dbt creates the snapshot table and inserts every row from the source, setting dbt_valid_from to the snapshot run time and leaving dbt_valid_to null for all rows (all are current). On subsequent runs, only changed, new, and (depending on config) deleted rows trigger writes.

CommandWhat it runsWhen to use
dbt snapshotAll snapshotsNightly job after raw loads complete
dbt snapshot --select scd_raw_listingsOne snapshot by nameAfter you change one YAML file or one source table
dbt snapshot --select scd_raw_*Name patternBoth Airbnb snapshots in one command
dbt build --select scd_raw_listings+Snapshot then downstream modelsWhen a mart reads from the snapshot
Order matters in pipelines. Run snapshots after the loader finishes updating raw tables and before models that ref() the snapshot. If dbt run builds a mart from scd_raw_hosts before dbt snapshot runs, the mart sees yesterday's history.

dbt build including snapshots

dbt build runs models, tests, seeds, and snapshots in dependency order when selected. Example that snapshots listings then builds downstream dependents:

dbt build --select scd_raw_listings+

The + suffix includes all downstream nodes that ref('scd_raw_listings'). If nothing downstream exists yet in the course project, the command behaves like dbt snapshot --select scd_raw_listings plus any configured snapshot tests.

Columns dbt adds to every snapshot table

Regardless of strategy, dbt appends metadata columns to the snapshot output. Downstream models and point-in-time joins rely on these names:

ColumnRole
dbt_scd_idSurrogate key for this version of the row (UUID on most adapters)
dbt_valid_fromWhen this version became valid (timestamp of the snapshot run that inserted it, or derived from updated_at on some configs)
dbt_valid_toWhen this version was superseded; NULL means current
dbt_updated_atWhen dbt last processed this row in the snapshot logic

All source columns are copied through. The snapshot table name in the warehouse follows the name: field in YAML — here scd_raw_listings and scd_raw_hosts — uppercased by Snowflake to SCD_RAW_LISTINGS in schema DEV (your target schema).

Snapshots versus models in the DAG

Snapshots are first-class nodes alongside models and seeds. They appear in dbt ls --resource-type snapshot, in lineage documentation, and in selectors. They do not inherit the models: materialization defaults from dbt_project.yml — snapshot behaviour is entirely config-driven in the YAML file.

Downstream models depend on snapshots through ref('scd_raw_listings') the same way they depend on dims and facts. dbt will not automatically run snapshots before models unless you use dbt build with a selection that includes both, or your orchestrator runs dbt snapshot explicitly before dbt run.

Everyday analogy — a snapshot is a photo album that keeps every version of your passport photo when you renew, while a Type 1 dimension is the single ID card in your wallet that gets replaced. The album takes more shelf space but answers “what did you look like in 2019?”

Adapter notes (Snowflake, BigQuery, Postgres)

The course runs on Snowflake. Snapshot semantics are consistent across dbt adapters, but merge implementation differs:

  • Snowflake — merge into the snapshot table in your target schema. Identifiers uppercased unless quoted.
  • BigQuery — merge into a native table; consider partitioning large history tables by dbt_valid_from manually for query pruning.
  • Postgres / Redshift — same YAML config; watch lock duration on wide tables during merge.
  • Databricks — Delta merge under the hood; ensure updated_at time zones match the cluster default.

Timestamp strategy versus check strategy

The Airbnb raw tables include a trustworthy updated_at column maintained by the sample dataset, so the course uses strategy: timestamp. dbt selects rows from the source where updated_at is newer than the last time that unique_key was snapshotted, then merges changes into the history table.

When the source lacks reliable change metadata, use strategy: check with check_cols — either all or an explicit list of columns that matter for history. dbt compares hashed values of those columns; any difference triggers a new Type 2 row. The comparison table and trade-offs are documented in Section 5; the practical difference for you is config only:

snapshots:
  - name: scd_legacy_hosts
    relation: source('airbnb', 'hosts')
    config:
      unique_key: id
      strategy: check
      check_cols: ['name', 'is_superhost']
      hard_deletes: invalidate
Timestamp strategy trusts the source. If application code forgets to bump updated_at on edit, dbt will not see the change. Check strategy is safer when timestamps are unreliable but costs a wider column comparison each run.

relation: source versus ref

The course snapshots sources declared in Section 9:

relation: source('airbnb', 'listings')

You can also snapshot a dbt model:

relation: ref('dim_hosts_cleansed')

Snapshotting raw sources keeps history aligned with what the loader landed. Snapshotting a cleansed model records history after your business rules — useful when raw columns are noisy but transformations are stable.

YAML snapshots replaced {% snapshot %} SQL blocks in dbt 1.9. Older projects may still have snapshots/my_snapshot.sql wrapping a SELECT in {% snapshot %}...{% endsnapshot %}. The course repo uses YAML only. Migration is mechanical: move unique_key, strategy, and the query target into relation: plus config:.

Legacy SQL snapshot form (history only)

If you maintain an older project, you may encounter this shape. Do not create new snapshots this way in dbt 1.11:

{% snapshot scd_raw_listings %}

{{
    config(
      target_schema='dev',
      unique_key='id',
      strategy='timestamp',
      updated_at='updated_at',
      invalidate_hard_deletes=True,
    )
}}

select * from {{ source('airbnb', 'listings') }}

{% endsnapshot %}

Note the legacy boolean invalidate_hard_deletes=True in the old block — the YAML equivalent is hard_deletes: invalidate.

check_cols in detail

When you cannot trust updated_at, list the columns whose change should open a new history row:

config:
  unique_key: id
  strategy: check
  check_cols: ['minimum_nights', 'price', 'room_type']
  hard_deletes: invalidate

check_cols: all compares every column except metadata — convenient in tutorials, expensive in production on wide raw tables. Omit columns that drift cosmetically (ETL load timestamps unrelated to business change) to reduce noise and cost.

Walkthrough: raw_listings_snapshot.yml

The listings snapshot is the instructor's first demonstration. The file is short because dbt handles the merge SQL; your job is correct config against a declared source.

Create snapshots/raw_listings_snapshot.yml with the exact contents from the course repo:

The course resources misspell this filename. course-resources.md calls the file raw_listins_snapshot.yml, dropping the g; the repo itself has raw_listings_snapshot.yml. snapshots:
  - name: scd_raw_listings

Line-by-line

  • name: scd_raw_listings — The dbt node name. Referenced as ref('scd_raw_listings') in models. Snowflake creates DEV.SCD_RAW_LISTINGS (database and schema from your target).
  • relation: source('airbnb', 'listings') — Reads models/sources.yml, resolves logical listings with identifier: raw_listings to AIRBNB.RAW.RAW_LISTINGS.
  • unique_key: id — Listing primary key from the raw table. One active history chain per id.
  • strategy: timestamp with updated_at: updated_at — A row is considered changed when its source updated_at exceeds the snapshot's last recorded value for that id.
  • hard_deletes: invalidate — If listing 3176 is deleted from raw_listings, dbt sets dbt_valid_to on the current snapshot row instead of leaving it open forever.

First run behaviour

Updating the source and reading validity columns

The instructor demonstrates Type 2 behaviour by mutating a raw row, re-running the snapshot, and querying history for listing 3176.

Step 1: change the raw table

Run an UPDATE against the raw listings table. The course script sets minimum_nights to 30 and bumps updated_at so timestamp strategy detects the change:

UPDATE AIRBNB.RAW.RAW_LISTINGS
SET
    minimum_nights = 30,
    updated_at = CURRENT_TIMESTAMP()
WHERE id = 3176;
Never UPDATE raw in production pipelines. This exercise simulates what your loader does when source applications edit rows. In real projects the ELT tool performs the update; you only run dbt snapshot afterward.

Step 2: re-run the snapshot

dbt snapshot --select scd_raw_listings

Second snapshot run after UPDATE

dbt snapshot --select scd_raw_listings

11:18:04  1 of 1 START snapshot DEV.scd_raw_listings ........................ [RUN]

The SUCCESS 1 count reflects changed rows processed, not total table size. Most listings were unchanged; only id 3176 (and any others with newer updated_at) merged.

Step 3: query dbt_valid_from and dbt_valid_to

The instructor selects all snapshot rows for the listing:

SELECT *
FROM AIRBNB.DEV.SCD_RAW_LISTINGS
WHERE id = 3176
ORDER BY dbt_valid_from;

You should see two rows for id = 3176:

minimum_nightsdbt_valid_fromdbt_valid_toMeaning
Previous valueFirst snapshot run timeSecond snapshot run timeHistorical version — closed
30Second snapshot run timeNULLCurrent version

dbt_valid_from and dbt_valid_to define the validity window for point-in-time joins. A fact row joins to the snapshot version where fact_date >= dbt_valid_from and fact_date < dbt_valid_to OR dbt_valid_to IS NULL. The full join pattern is in Section 5; the critical rule is never join on unique_key alone without the validity predicate, or facts duplicate across history rows.

Current-row filter for dashboards

When you only need today's truth, filter to open rows:

SELECT *
FROM {{ ref('scd_raw_listings') }}
WHERE dbt_valid_to IS NULL

For most Airbnb marts the course still uses dim_listings_cleansed (Type 1). Reach for the snapshot when the question explicitly needs history or audit trail.

Third run: no change

If you run dbt snapshot --select scd_raw_listings again without touching raw data, dbt finds no rows with updated_at newer than the last merge. The terminal reports SUCCESS 0 — success with zero changes. That is expected and cheap on timestamp strategy.

Building a mart from snapshot history

When a mart must answer historical questions, join facts to the snapshot with the validity predicate from Section 5 rather than to dim_listings_cleansed:

SELECT
    r.review_id,
    r.review_date,
    s.minimum_nights,
    s.room_type
FROM {{ ref('fct_reviews') }} r
JOIN {{ ref('scd_raw_listings') }} s
  ON r.listing_id = s.id
 AND r.review_date >= s.dbt_valid_from
 AND (r.review_date < s.dbt_valid_to OR s.dbt_valid_to IS NULL)

This pattern is not in the course repo but is the natural next step after completing both snapshots.

Hard deletes: invalidate, new_record, and ignore

When a row disappears from the source query result, dbt must decide whether the entity still exists. hard_deletes controls that behaviour.

The three options

hard_deletes valueWhen source row is goneSnapshot effect
invalidateRow deleted from source tableSet dbt_valid_to on the current row; entity no longer current
new_recordRow deleted from source tableInsert a new row marked deleted (adapter-specific nulling pattern)
ignoreRow deleted from source tableLeave the snapshot row open with dbt_valid_to NULL — pretends entity still exists

The course uses hard_deletes: invalidate on both listings and hosts. If a listing is removed from Airbnb and your loader deletes the raw row, the snapshot closes that listing's history instead of reporting it as active inventory.

Config rename in dbt 1.9. Older docs and videos use invalidate_hard_deletes: true inside snapshot config. That boolean mapped to today's hard_deletes: invalidate. hard_deletes: new_record and hard_deletes: ignore replace the old false/absent behaviour with explicit semantics. Projects pinned below 1.9 may still use the legacy key.

Why ignore is dangerous

With hard_deletes: ignore, deleted listings remain current in scd_raw_listings. Active listing counts inflate; joins to facts still attach to ghost listings. Use ignore only when source deletes are unreliable false positives (bad loader behaviour) and you accept stale entities.

Testing hard deletes locally

To see invalidation in dev:

DELETE FROM AIRBNB.RAW.RAW_LISTINGS WHERE id = 9999;

-- then
-- dbt snapshot --select scd_raw_listings

SELECT id, dbt_valid_from, dbt_valid_to
FROM AIRBNB.DEV.SCD_RAW_LISTINGS
WHERE id = 9999;

Pick an id that exists in your sample data. Undo by reloading raw data or re-inserting the row from backup before continuing other exercises.

new_record mode

hard_deletes: new_record inserts an additional row when the source key vanishes, marking the deletion in a way that preserves audit trail for compliance teams who want an explicit “deleted” event row. It is less common than invalidate in analytics marts. Choose based on whether downstream consumers expect a row to exist for every deletion event versus simply excluding deleted entities from current-state filters.

Snapshotting a view versus a table, and target_schema conventions

The course snapshots physical raw tables. Real projects sometimes point snapshots at views or models; schema placement follows the same rules as models with a few snapshot-specific defaults.

Table sources (what the course uses)

raw_listings and raw_hosts are base tables in AIRBNB.RAW. The loader inserts and updates rows; timestamp strategy reads updated_at directly. This is the recommended pattern: snapshot as close to the mutable truth as possible.

View sources

dbt can snapshot a view if the adapter supports reading it like a table. Practical constraints:

  • Mutability must appear in the view result. A view over a Type 1 join does not create history the snapshot has not seen before — it reflects current underlying tables only.
  • Performance. Each snapshot run executes SELECT * FROM your_view. Complex views with many joins multiply warehouse cost versus snapshotting a narrow raw table.
  • Timestamp columns. Views must expose an updated_at (or use check strategy) that actually changes when business attributes change.

Prefer relation: source(...) on the landing table, then build cleansed models with ref('scd_raw_listings') filtered to dbt_valid_to IS NULL or joined with validity predicates.

target_schema conventions

By default snapshots land in the same schema as models for your target — DEV in development, a custom prod schema after you adopt generate_schema_name in Section 19.

Override per snapshot:

snapshots:
  - name: scd_raw_listings
    relation: source('airbnb', 'listings')
    config:
      unique_key: id
      strategy: timestamp
      updated_at: updated_at
      hard_deletes: invalidate
      target_schema: snapshots

Teams often use one of these conventions:

ConventionProsCons
Same schema as models (DEV)Simple; works with default profileHistory tables mixed with dims and facts

Project-wide defaults go in dbt_project.yml under a snapshots: key (parallel to models:):

  airbnb:

The course leaves defaults: snapshots live in DEV beside dim_listings_cleansed and fct_reviews.

Snapshots in CI and defer

Production Slim CI in Section 19 often runs modified models with --defer against a prod manifest. Snapshots are stateful: they compare against the existing snapshot table in the target environment. Deferring snapshot runs to prod while testing models in CI can desynchronise history unless the snapshot table itself is prod-backed or CI runs snapshots against a clone with copied history.

Practical pattern: run snapshots in the same environment that owns the mutable source (typically prod or a staging schema fed by the same loader), not in ephemeral PR schemas, unless you seed the snapshot table first.

Snapshotting a model instead of raw

Some teams snapshot ref('src_listings') or a cleansed intermediate model when raw columns are unusable but the staging output is stable. Trade-offs:

  • History reflects cleansed values (prices already cast, names trimmed) — good for analyst-facing audit.
  • Changes to staging SQL rewrite history semantics on the next snapshot unless you version the model carefully.
  • Ephemeral staging cannot be snapshotted; materialise as view or table first.

The course snapshots raw because the loader owns mutability and staging is ephemeral. That is the pattern to copy unless you have a documented reason to snapshot downstream.

Traps that catch people

  • Joining without validity predicate — joining facts to scd_raw_hosts on host_id alone duplicates rows across every history version. Always constrain dbt_valid_from / dbt_valid_to or filter to dbt_valid_to IS NULL for current state.
  • Forgetting to bump updated_at — timestamp strategy misses in-place edits if the loader does not update the timestamp column. Symptoms: snapshot run succeeds with zero changes while raw data clearly changed.
  • Running snapshot before loader — snapshot captures stale source state; the next loader run changes raw without a matching snapshot until the next schedule. Order orchestration: load, snapshot, transform.
  • Using dbt run instead of dbt snapshot — models rebuild; snapshots do not. New YAML files sit idle until someone runs the snapshot command.
  • unique_key not actually unique — duplicate keys in the source create undefined merge behaviour and overlapping validity windows. Add a source test before snapshotting.
  • hard_deletes: ignore on prod — deleted entities stay active forever in reporting. Default to invalidate unless you document why ignores are safe.
  • Snapshotting ephemeral models — ephemeral models have no warehouse relation to read. Point relation: at a table, view, or materialised model.
  • Full refresh surprise — dropping the snapshot table loses history unless you have backup. Treat snapshot tables as production-critical state.
  • Confusing snapshot with incremental — incremental facts append events; snapshots version mutable entities. Using incremental on a slowly changing dimension loses history (see Section 8).
  • CI defer without prod snapshot — PR builds that defer to prod for refs but run snapshots locally create divergent history. Align snapshot execution with the environment that owns sources.

Production patterns

Schedule after load

Orchestrator DAG: Fivetran sync completes → dbt source freshness → dbt snapshot on raw entities → dbt run on marts. Snapshots belong in the same job as transforms, not a forgotten manual step.

Separate history schema

Set +target_schema: audit for all snapshots in prod. Grant analysts read on dims; restrict history tables to compliance roles. Keeps ref('scd_raw_listings') explicit about crossing schema boundaries.

Anti-pattern: snapshotting wide raw tables with check_cols: all on hourly schedules. At scale the hash comparison dominates warehouse spend. Fix: timestamp strategy with reliable CDC, or snapshot a narrow staging model that selects only columns needed for history.

Interview questions

Answer each one out loud before opening it.

When would you reach for a snapshot instead of an incremental model?Comparison

Use a snapshot when the source row mutates in place and you need Type 2 history of attribute changes — host renames, price changes, status flips. dbt closes the old version and opens a new one with validity timestamps.

Use an incremental model when the grain is append-only events — new reviews, new orders — and each row is immutable once loaded. Incrementals add new rows; they do not version changes to existing entities.

If you only need current state, a Type 1 dimension rebuilt with dbt run is simpler and cheaper than maintaining snapshot history.

What command runs snapshots and how is it different from dbt run?Fundamentals

dbt snapshot executes snapshot nodes defined in snapshots/. It performs merge logic that compares the source to existing history and updates dbt_valid_from / dbt_valid_to.

dbt run materialises models only. Snapshot YAML files are invisible to dbt run. In orchestration, schedule both commands or use dbt build with a selection that includes snapshot nodes.

Explain timestamp strategy versus check strategy.Design

Timestamp strategy requires a reliable updated_at (configured via the updated_at key). dbt considers a row changed when that column is newer than the last snapshotted version for the same unique_key.

Check strategy compares configured columns — check_cols — between source and snapshot. Any difference creates a new Type 2 row. Use it when timestamps are missing or untrustworthy; pay the cost of broader comparisons each run.

What do dbt_valid_from and dbt_valid_to mean?Modelling

They bound the period during which a snapshot row version was true. dbt_valid_from is when the version opened; dbt_valid_to is when it was superseded or invalidated. NULL in dbt_valid_to means the current version.

Point-in-time joins filter facts so the event timestamp falls inside this window. Current-state reporting filters dbt_valid_to IS NULL.

What happens when a row is deleted from the source and hard_deletes is invalidate?Fundamentals

On the next snapshot run, dbt detects the unique_key missing from the source query. With hard_deletes: invalidate, it sets dbt_valid_to on the open row, closing the entity's history without inserting a new current row.

Reporting that filters to open rows excludes the deleted entity. With ignore, the entity would incorrectly remain current.

Your snapshot run reports SUCCESS 0 every time but raw data changes. Why?Troubleshooting

Most common cause with timestamp strategy: the source row's updated_at did not change when attributes changed. dbt sees no newer timestamp and skips the row.

Verify with a direct SELECT updated_at, ... FROM raw_table WHERE id = .... Fix the loader, manually bump timestamps in dev, or switch to check strategy on the columns that matter.

Can you snapshot a dbt ephemeral model?Gotcha

No. Ephemeral models are inlined as CTEs and never become warehouse relations. Snapshots need a queryable table or view as relation:.

Snapshot the raw source or a materialised staging model instead. Course staging models under src/ are ephemeral — snapshots point at source('airbnb', ...), not ref('src_listings').

Why should unique_key be tested before snapshotting?Testing

Snapshot merge logic assumes one history chain per unique_key. Duplicate keys in the source produce overlapping validity ranges and duplicate current rows — silent corruption in downstream marts.

Add unique and not_null tests on the source key column in sources.yml before enabling snapshots in prod.

How do snapshots interact with Slim CI and defer in production?Production

Snapshots are stateful: they read and write the same history table each run. CI environments that defer model refs to prod but run snapshots locally without a copy of prod history produce inconsistent results.

Common pattern: run snapshots only in prod (or staging with prod-equivalent raw feeds), while PR CI defers to prod for snapshot ref() outputs. See Section 19 for defer and state selection details.

What changed between invalidate_hard_deletes and hard_deletes?Certification

Older snapshot config used boolean invalidate_hard_deletes: true to close rows when source keys disappeared. dbt 1.9+ replaced it with explicit hard_deletes: invalidate | new_record | ignore.

true maps to invalidate. false maps closer to ignore, though teams should choose explicitly rather than rely on defaults.

How would you get current listings from a snapshot table in a mart?SQL

Filter to open rows: WHERE dbt_valid_to IS NULL on ref('scd_raw_listings'). Alternatively build a thin view model wrapping that filter so mart SQL stays clean.

For historical analysis, keep all versions and apply the validity join on fact timestamps instead of filtering to current.

Snapshot versus source freshness: which detects stale data?Comparison

Source freshness (dbt source freshness) checks whether the latest load timestamp exceeds warn/error thresholds — operational staleness of the whole table.

Snapshots record row-level attribute history after data arrives. A fresh table can still be snapshotted; a stale table fails freshness before snapshots run. Use both: freshness gates the pipeline; snapshots preserve change history.

What is stored in dbt_scd_id and do you use it in joins?Modelling

dbt_scd_id is a surrogate key dbt generates for each version row in the snapshot table. It uniquely identifies one historical version independent of the business unique_key.

Downstream joins typically still use the business key plus validity dates, not dbt_scd_id. The surrogate is useful for debugging, deduplication tests, and incremental exports that need a stable row identifier for each version.

How do you rebuild snapshot history from scratch?Troubleshooting

Drop the snapshot table in the warehouse (DROP TABLE DEV.SCD_RAW_LISTINGS), then run dbt snapshot --select scd_raw_listings. dbt treats it as a first run and loads all current source rows as open history.

There is no --full-refresh for snapshots comparable to models. Document drop-and-rebuild procedures carefully in prod — you lose prior history unless you backed up the table.

Recap

  • Snapshots implement Type 2 SCD over mutable sources; theory and join patterns live in Section 5.
  • Run them with dbt snapshot, not dbt run. Definitions live in snapshots/*.yml via snapshot-paths.
  • YAML snapshots use name, relation:, and config: with unique_key, strategy, and strategy-specific keys.
  • Course snapshots: scd_raw_listings and scd_raw_hosts on source('airbnb', ...) with strategy: timestamp and updated_at: updated_at.
  • dbt adds dbt_scd_id, dbt_valid_from, dbt_valid_to, and dbt_updated_at to every snapshot table.
  • After a source UPDATE with bumped updated_at, re-snapshot closes the old row and opens a new current row.
  • hard_deletes: invalidate closes history when a unique_key disappears; replaced legacy invalidate_hard_deletes: true in dbt 1.9.
  • Other hard delete modes: new_record and ignore (avoid ignore in prod unless deletes are untrustworthy).
  • Check strategy uses check_cols when timestamps are unreliable.
  • Snapshot physical raw tables; view sources work but often cost more and hide mutability.
  • Default target_schema is your profile target schema; override per snapshot or in dbt_project.yml.
  • In CI, treat snapshots as stateful — align with Section 19 defer patterns.
  • Reference snapshots in models with ref('scd_raw_listings'); filter dbt_valid_to IS NULL for current state.
