Node selection syntax

Every dbt command that touches project nodes accepts --select (short form -s). The string you pass is not a SQL fragment — it is a graph query over the manifest. dbt resolves matching nodes, expands parent dependencies where the syntax requires it, and runs only that subgraph.

Why selection matters

In development you rarely want a full project rebuild. In CI you want the smallest subgraph that proves the pull request is safe. In production incident response you want one mart and its upstream chain. Selection is how dbt stays fast and cheap at scale. The instructor demonstrates this after weeks of adding models: a blind dbt run rebuilds staging, dimensions, facts, marts, and every Python experiment whether you touched them or not.

The selection string is evaluated at parse time against the manifest graph. dbt does not re-read your SQL to guess dependencies — it uses the compiled DAG from ref(), source(), and test attachments. That is why renaming a model breaks selection by old name immediately on dbt parse, and why dbt ls is the safe preview step before any warehouse work.

Development habit

End every model edit with dbt build -s +my_model+ — upstream parents, the model, downstream children, and attached tests — instead of a full project run.

CI habit

Never run bare dbt build on a pull request. Combine state:modified+ with tag filters or a named selector from selectors.yml.

Selection by model name

The simplest form is a node name. When you run dbt run --select dim_listings_cleansed, dbt builds that model and every upstream parent it depends on (parent inclusion is default). It does not build unrelated branches of the DAG.

Ephemeral models like src_listings compile inline and may not appear as separate warehouse objects, but dbt still parses and executes them as part of the selected subgraph. Use dbt ls --select dim_listings_cleansed to preview the exact node list before spending warehouse credits.

Graph operators

Graph operators control how far dbt walks the DAG from your anchor node. They work on models, tests, seeds, snapshots and sources depending on the command.

SyntaxMeaningExampleTypical use
model_nameNode plus upstream parents (default inclusion)dbt run -s fct_reviewsRebuild one fact and its staging chain
+modelAll upstream ancestors (parents, grandparents, …)dbt run -s +dim_listings_w_hostsBuild everything needed before a mart
model+Node and all downstream childrendbt run -s dim_listings_cleansed+Refresh a dimension and every mart that reads it
+model+Full upstream and downstream neighbourhooddbt test -s +fct_reviews+Integration test around one hub model
@modelParents and children (local subgraph)dbt run -s @mart_fullmoon_reviewsImpact radius around one node
N+modelLimit upstream depth to N hopsdbt ls -s 1+dim_listings_cleansedDirect parents only
model+NLimit downstream depth to N hopsdbt ls -s dim_hosts_cleansed+1Immediate children only

The prefix + on the left walks upstream; the suffix + on the right walks downstream. You can combine depth limits with either direction. The at-sign form is easy to confuse with email syntax but means “everything one step away in both directions” — useful when you changed a shared dimension and want to see the blast radius without rebuilding the entire project.

List before you run. dbt ls --select +dim_listings_w_hosts prints node names without touching the warehouse. Copy the output into a ticket or CI log to prove your selector matches what you intended.

Combining and excluding

Commas form a union — nodes matching any clause are included. Use --exclude to subtract nodes from an otherwise matching set. You can pass multiple space-separated selection arguments; dbt treats them as intersections in some versions, but the pattern that survives code review is comma unions plus explicit excludes.

PatternMeaningExample
Comma unionMatch A OR Bdbt run -s tag:fact,path:models/dim
--excludeSubtract from matched setdbt run -s path:models/dim --exclude dim_fullmoon
Space intersectionMatch A AND Bdbt run -s tag:fact --select path:models/fct
Graph + excludeDownstream minus one nodedbt run -s dim_listings_cleansed+ --exclude dim_review_sentiment
 
dbt run --select tag:fact --exclude mart_fullmoon_reviews
dbt test --select tag:fact,source:airbnb.listings
dbt build --select path:models/dim --exclude dim_fullmoon

Parent inclusion still applies per selected node. If you exclude an upstream model but select its child, dbt may still build the parent because the child cannot compile without it — unless you also use defer (covered in Section 19).

state:modified and CI

State-aware selectors compare the current project graph to a saved artifact (usually manifest.json from the last production deploy). The selector state:modified matches nodes whose SQL, config or dependencies changed. Related selectors include state:new (nodes that exist only in the current project) and body-only variants like state:modified.body when you want to ignore config-only diffs. Append + to include downstream dependents: state:modified+.

dbt ls --state target-prod --select state:modified
dbt ls --state target-prod --select state:modified+

The course pin is dbt 1.11. State comparison requires you to pass --state path/to/artifacts pointing at a directory containing a prior manifest.json. Without that directory, state:modified matches nothing useful. On BigQuery and Databricks the mechanics are identical; only artifact storage and CI wiring differ.

Certification: know the difference between +model (upstream), model+ (downstream), and @model (both directions). Expect a question on tag: and source: prefixes and on what parent inclusion means when you name a single child model.

Previewing with dbt ls

dbt ls uses the same selection grammar as dbt run, dbt test, and dbt build. Add flags to inspect metadata:

dbt ls --select tag:fact --output name
dbt ls --select +dim_listings_cleansed --resource-type model
dbt ls --select state:modified+ --state target-prod --output json

The --output json form is what Slim CI scripts parse to post a comment on a pull request listing every model that will rebuild. The human-readable default is enough for local debugging.

Selection on other commands

The same grammar applies uniformly. dbt seed --select seed_full_moon_dates reloads one CSV. dbt snapshot --select raw_listings_snapshot runs one snapshot YAML definition. dbt compile --select dim_listings_cleansed renders Jinja without executing DDL. dbt test --select dim_listings_w_hosts runs tests scoped to that model subgraph. Consistency is deliberate: learn one language, use it everywhere.

result: and test selection

When debugging a failed test, select by result status to rerun only what broke. dbt test --select result:fail reruns tests that failed in the previous invocation. Pair with dbt retry after fixing the underlying data or test logic. You can also select by resource type alone: dbt test -s resource_type:test runs every test without rebuilding models first.

Select failing tests only

dbt test --select dim_listings_w_hosts

dbt test --select result:fail

16:04:46  1 of 1 PASS unique_dim_listings_w_hosts_listing_id ............... [PASS in 0.41s]

Intersection with spaces

Passing multiple selection strings as separate arguments creates an intersection (AND). The model must match every clause:

dbt ls --select path:models/dim config.materialized:table
dbt run --select tag:fact --select path:models/fct

This is easy to confuse with comma unions inside a single -s string. Rule of thumb: commas inside one quoted argument are OR; repeated --select flags are AND.

Everyday analogy — comma in one -s string is “models tagged fact or under path dim”. Two --select flags are “models that are tagged fact and under path fct”. Mixing the two without reading the docs produces empty selections that waste a CI minute before you notice.

Tags

Tags are string labels attached to dbt nodes. They exist so you can select groups without maintaining brittle lists of model names. A nightly job runs dbt test -s tag:critical; a fact rebuild runs dbt run -s tag:fact; CI runs only what changed via state selectors layered on tags.

Folder-level tags in dbt_project.yml

The course tags every model under models/fct/ at the project config level. The + prefix merges the tag into each child model's config:

models:
  airbnb:
    +grants:
      select: ["transform", "reporter"]
    +post-hook:
      - "INSERT INTO {{ target.schema }}.audit_log VALUES ('{{ this }}', CURRENT_TIMESTAMP)"
    +materialized: view
    dim:
      +materialized: table
    src:
      +materialized: ephemeral
    fct:
      +tags: ['fact']

After this change, fct_reviews carries fact automatically. Verify with:

dbt ls --select tag:fact

Model-level tags override and extend

Individual models can set tags in a {{ config() }} block. The course adds fact to mart_fullmoon_reviews even though it lives under models/mart/, outside the fct/ folder default. Without this inline tag, dbt run -s tag:fact would build fct_reviews but skip the full-moon mart — a common surprise when folder conventions and business taxonomy diverge.

{{ config(
  materialized = 'incremental',
  incremental_strategy='microbatch',
  event_time='review_date',
  begin='2009-06-20',
  batch_size='year',
  full_refresh=false,
  tags = ['fact'],
  schema='mart'
) }}

Config precedence follows the usual dbt order: model file config beats folder config in dbt_project.yml, which beats project-wide defaults. Tags from multiple levels merge unless explicitly replaced.

Tags on tests

Tests do not inherit model tags automatically. Tag critical tests explicitly in YAML or in a singular test's config block so CI can run dbt test -s tag:critical without scanning the whole project. See Section 11 for examples.

WhereHowSelector
dbt_project.yml folder block+tags: ['fact']dbt run -s tag:fact
Model config()tags = ['fact', 'nightly']dbt run -s tag:nightly
YAML column testconfig: tags: ['critical']dbt test -s tag:critical
Singular test SQL file{{ config(tags=['critical']) }}dbt test -s tag:critical
Convention over lists. Real teams define a small tag vocabulary in the README: critical, nightly, fact, dim, pii. Selectors in CI reference tags; nobody maintains a 40-model comma list in GitHub Actions YAML.

Verifying tags in the manifest

After adding tags, confirm they landed on the nodes you expect before wiring CI. The fastest check is dbt ls; the authoritative source is target/manifest.json after dbt parse or any run:

dbt parse
dbt ls --select tag:fact --output json

Each node entry includes a tags array under config. If mart_fullmoon_reviews is missing the fact tag, the inline config(tags=[...]) block was not saved or a parse error prevented compilation. Tags on folder defaults apply at parse time — no warehouse round trip required.

Named selectors in selectors.yml

Long --select strings are hard to review in CI YAML and easy to typo. selectors.yml at the project root stores named, reusable selection definitions. dbt evaluates them the same way as inline selectors, but the name becomes documentation and a stable contract for orchestrators.

The course selector

The Airbnb project defines one selector that builds every dimension except dim_listings_w_hosts:

selectors:
  - name: dim_except_listings_w_hosts
    description: Selects all dim models, excluding dim_listings_w_hosts.
    definition:
      union:
        - method: path
          value: models/dim
        - exclude:
            - method: fqn
              value: dim_listings_w_hosts

The union key means "include everything matching any clause below". The exclude block removes nodes even if the path clause would have included them. Equivalent inline CLI (without the YAML file) would be roughly path:models/dim --exclude dim_listings_w_hosts, but the YAML form is version-controlled and self-documenting.

Executing named selectors

Selector CLI syntax changed at dbt 1.12. Before 1.12, pass the selector name with a dedicated flag: dbt run --selector dim_except_listings_w_hosts. From 1.12 onwards, named selectors use the same -s flag with a selector: prefix: dbt run -s selector:dim_except_listings_w_hosts. The course repo pins dbt 1.11 — use --selector locally unless you upgrade. Check dbt --version before copying CI snippets from blog posts.
# Before dbt v1.12:
dbt run --selector dim_except_listings_w_hosts

# Starting from dbt v1.12:
dbt run -s selector:dim_except_listings_w_hosts

Named selectors work with any command that accepts --select: dbt build, dbt test, dbt compile, and dbt ls. Combine with state flags in CI: dbt build --selector nightly_models --state path/to/prod/manifest (pre-1.12) or dbt build -s selector:nightly_models --state ... (1.12+).

Why exclude dim_listings_w_hosts

The course selector builds every dimension except dim_listings_w_hosts because that model joins hosts and listings and depends on versioned refs — useful for demos where you want dim tables without the join mart. The pattern generalises: exclude slow, experimental or permission-sensitive models from nightly rebuilds while keeping the rest of a folder on schedule.

run versus build

dbt run executes models only. Tests do not run; a broken primary key can propagate silently into marts. dbt build interleaves tests according to the DAG — if fct_reviews fails a unique test, downstream models that depend on it skip. Production pipelines prefer build; interactive development often alternates run and test for speed.

Supporting commands in practice

dbt parse is cheap relative to a full run — it validates YAML, resolves refs, and writes artifacts without warehouse DDL. CI pipelines often run dbt parse --warn-error on every pull request. dbt clean followed by dbt deps is the fix when package macros look stale.

dbt retry re-executes only failed nodes from the immediately previous invocation, preserving selection and vars. Useful when a warehouse blip caused one model in a long run to fail.

dbt docs generate queries the warehouse information schema to enrich column types in documentation. On large projects it can take minutes; schedule it rather than running on every commit. dbt debug should be the first command on a new laptop — it validates profiles.yml, tests the adapter connection, and confirms the project parses.

Postgres and Redshift note. Every command above works on all adapters, but Python models and some materializations are adapter-specific. A command that succeeds on Snowflake may fail on Postgres if the selection includes an unsupported node type.

dbt parse — validate without running

dbt parse reads every project file, resolves ref() and source() dependencies, validates YAML, and writes target/manifest.json plus target/partial_parse.msgpack. It never opens a warehouse connection for model execution. CI pipelines use it as a fast lint step; Slim CI uploads the manifest as the comparison artifact for state:modified.

dbt parse

dbt parse --warn-error
16:12:01  Running with dbt=1.11.12
16:12:03  Performance info: target/manifest.json
16:12:03  Completed successfully

--warn-error promotes deprecation warnings to hard failures — useful on pull requests so team members fix renames before they become breaking changes in the next minor version.

dbt deps — install packages

dbt deps reads packages.yml, downloads pinned package versions into dbt_packages/, and installs any package dependencies recursively. Run it after clone, after changing a package version pin, or when macros from dbt_utils or dbt_expectations are missing. It does not require a warehouse connection.

dbt clean          # optional — removes stale dbt_packages/
dbt deps           # install packages.yml pins
dbt parse          # confirm package macros resolve

dbt clean — reset local artifacts

dbt clean deletes directories listed under clean-targets in dbt_project.yml — by default target/ and dbt_packages/. Use it when compiled SQL looks stale after a macro change, when partial parse causes confusing errors, or before a demo where you want a cold start. It does not touch models in the warehouse.

dbt docs generate and dbt docs serve

Documentation is a two-step process. dbt docs generate compiles the project, queries the warehouse information schema for column types and row counts, and writes target/catalog.json alongside the manifest. dbt docs serve starts a local web server (default port 8080) that renders lineage, column descriptions, and test results.

dbt debug — connection and config check

dbt debug validates that profiles.yml exists, the named profile and target resolve, the adapter can connect to the warehouse, and the project directory parses. Run it first on a new machine or after rotating credentials. It is the fastest way to distinguish “dbt misconfigured” from “SQL wrong”.

dbt retry — resume after partial failure

When a long dbt build fails on model 17 of 40, fix the root cause and run dbt retry instead of rebuilding models 1–16. Retry reads the run results artifact from the immediately previous invocation and re-executes only failed nodes, preserving selection and --vars. It does not help with logic bugs you have not fixed yet — those will fail again.

When retry helps

Transient warehouse timeouts, network blips, warehouse auto-suspend resume delays, and rate-limited API errors during metadata queries.

When retry does not help

Compilation errors, test assertion failures, and permission errors. Fix the model or YAML first, then run or retry explicitly.

Project variables

Variables let you parameterise a project without editing SQL between runs. Orchestrators pass dates, environment names or feature flags through --vars; Jinja reads them with var(). Defaults live in dbt_project.yml so local runs work without extra flags.

Defaults in dbt_project.yml

The course adds a top-level vars: block (sibling to models:):

vars:
  user_name: default_user_name_for_this_project

Reading variables in Jinja

var('name') raises an error if the variable is undefined and no default is provided. var('name', default) returns the default when missing. This differs from {% set %}, which is compile-time Jinja scope only — not overridable from the CLI.

The course macro learn_variables demonstrates both patterns:

{% macro learn_variables() %}

    {% set your_name_jinja = "Zoltan" %}
    {{ log("Hello " ~ your_name_jinja, info=True) }}

    {{ log("Hello dbt user " ~ var("user_name", "NO USERNAME IS SET!!") ~ "!", info=True) }}

    {% if var("in_test", False) %}
       {{ log("In test", info=True) }}
    {% else %}
       {{ log("NOT in test", info=True) }}
    {% endif %}

{% endmacro %}

Run it with defaults, then override from the shell:

dbt run-operation learn_variables

dbt run-operation learn_variables --vars "{user_name: zoltanctoth}"
16:15:01  Running with dbt=1.11.12
16:15:02  Hello Zoltan
16:15:02  Hello dbt user zoltanctoth!
16:15:02  NOT in test

Variables in model SQL

Vars are not limited to macros. Any model can read a var for a filter threshold or a logical run date. Section 19 passes start_date and end_date to incremental models from Airflow or Dagster:

{% set start = var('start_date', '2000-01-01') %}

FROM {{ ref('fct_reviews') }}

Python models

A Python model is a .py file in models/ with a model(dbt, session) function instead of a SQL SELECT. dbt uploads your code to the warehouse Python runtime, passes upstream relations as DataFrames, and materialises the returned DataFrame like any other model. Use Python when you need a library SQL cannot call — NLP, holidays, scipy — not when SQL would be clearer.

dim_long_term_listings.py — Snowpark DataFrame API

The simplest course model filters listings with at least 30 minimum nights using Snowpark column syntax — no Pandas conversion. This is the idiomatic pattern on Snowflake: lazy evaluation stays in the warehouse until dbt materialises the result as a table.

Every Python model must expose a top-level function named model accepting (dbt, session). The dbt object provides ref(), source(), and config() — the same concepts as Jinja macros, but in Python. The session object is the warehouse-specific runtime (Snowpark Session on Snowflake).

def model(dbt, session):
    listings = dbt.ref("dim_listings_cleansed")

    return (listings.filter(listings["MINIMUM_NIGHTS"] >= 30)
                   .select("LISTING_ID", "LISTING_NAME", "PRICE"))

Column names are uppercase because Snowflake returns unquoted identifiers folded to upper case. The model inherits table materialisation from the dim/ folder default in dbt_project.yml. You could override inside the function with dbt.config(materialized="view") if you wanted a non-persisted result — same keys as SQL {{ config() }}.

dim_fullmoon.py — Pandas and third-party packages

This model reads a seed, converts to Pandas, and applies the holidays library. dbt.config() sets materialisation and declares pip packages the warehouse should install:

import holidays

def is_holiday(date_col):
    german_holidays = holidays.Germany()
    is_holiday = (date_col in german_holidays)
    return is_holiday

def model(dbt, session):
    dbt.config(
        materialized = "table",
        packages = ["holidays"],
        enabled=False # We add this line in the Model Lifecycle / Disabling Models section
    )

    orders_df = dbt.ref("seed_full_moon_dates")

    df = orders_df.to_pandas()

    df["IS_HOLIDAY"] = df["FULL_MOON_DATE"].apply(is_holiday)

    # return final dataset (Pandas DataFrame)
    return df

to_pandas() pulls data into the driver — fine for a small seed, expensive for a fact table. Prefer native Snowpark operations on large inputs.

dim_review_sentiment.py — TextBlob sentiment

Sentiment scoring on review text demonstrates a heavier library and a fact-table input:

from textblob import TextBlob

def get_sentiment(text):
    return TextBlob(text).sentiment.polarity

def model(dbt, session):
    dbt.config(
        materialized = "table",
        enabled= False, # We are disabling this Model later in the Model Lifecycle section
        packages = ["textblob"]
    )

    reviews_df = dbt.ref("fct_reviews")

    df = reviews_df.to_pandas()

    df["SENTIMENT_SCORE"] = df["REVIEW_TEXT"].apply(get_sentiment)

    return df
Python on full facts is expensive. Converting fct_reviews to Pandas and running TextBlob row-by-row moves compute out of Snowflake's set-based engine into a single Python worker. For production NLP, teams often batch score in a dedicated service and land results as a source table dbt reads with SQL.

config in Python models

SQL models use {{ config(materialized='table') }} at the top of the file. Python models call dbt.config(materialized="table", tags=[...], packages=[...]) inside model(). The same keys apply: schema, tags, enabled, incremental settings where the adapter supports them.

Enabling disabled Python models

To run dim_fullmoon or dim_review_sentiment, set enabled=True in dbt.config() or override at runtime. Ensure upstream seeds and facts exist first:

dbt seed --select seed_full_moon_dates
dbt run --select dim_listings_cleansed dim_fullmoon

First run on Snowflake may take longer while pip installs declared packages into the Snowpark environment. Subsequent runs reuse cached packages.

Adapter differences beyond Snowflake

BigQuery Python models use the BigQuery DataFrames API; the session object differs from Snowpark but dbt.ref() and dbt.config() work the same way. Databricks models return Spark or Pandas DataFrames depending on configuration. None of these adapters accept arbitrary pip packages without explicit packages=[...] declaration — undeclared imports fail at runtime with ModuleNotFoundError, not at parse time.

Postgres developers. Python models parse in a polyglot repo but fail at run time on unsupported adapters. Tag them python and exclude with --exclude tag:python in local Postgres CI, or set enabled: false until you have a Snowflake target.

Traps that catch people

  • Wrong selector flag after upgrade — CI still calls --selector nightly on dbt 1.12+, which fails or is ignored depending on parser version. Pin dbt in CI and update flags when upgrading.
  • Assuming tests inherit model tags — dbt test -s tag:fact selects fact models' tests only if those tests are tagged or attached to tagged models per dbt's rules. Tag tests explicitly for tiered CI.
  • Exclude without understanding parent inclusion — excluding src_listings while selecting dim_listings_cleansed still builds the parent because the child requires it.
  • state:modified without --state — the selector matches nothing or behaves unexpectedly. You need a prior manifest directory.
  • Comma typo in --vars — invalid YAML/JSON silently fails parse or drops keys. Test with dbt compile --vars '...' first.
  • Secrets in --vars — values log to logs/dbt.log and appear in orchestrator UIs. Use env_var() for credentials.
  • Python model on Postgres — parse succeeds in a polyglot repo but run fails with adapter error. Gate Python models behind tags and warehouse checks.
  • enabled=False surprise — dim_fullmoon and dim_review_sentiment ship disabled in the repo; dbt run -s path:models/dim skips them without error.
  • Uppercase column names in Snowpark — Python models must reference MINIMUM_NIGHTS not minimum_nights unless quoted in SQL source.
  • Package install on every run — missing packages in config causes runtime pip installs. Declare all third-party deps in dbt.config(packages=[...]).
  • dbt run vs build in CI — run-only pipelines ship broken data when tests fail after merge. Prefer build for deployment-bound jobs.
  • Over-broad @ selector — @hub_model on a widely referenced dimension rebuilds half the project. Use depth limits or state selectors instead.

Production patterns

Mature teams check three selectors into git: ci_modified (state plus downstream), nightly_full (tagged heavy tests), and deploy_production (full build minus disabled experimental models). GitHub Actions calls dbt ls -s selector:ci_modified --state prod_artifacts in a dry-run step before spending warehouse credits. Tags encode tier; selectors encode graph logic; orchestrators pass vars for logical dates.

Python models belong at the edge of the DAG — small inputs, library transforms SQL cannot express, outputs consumed as ordinary tables downstream. Anti-pattern: a 200-line Python mart that replaces SQL because the author prefers Pandas. It forfeits warehouse parallelism, obscures lineage debugging, and breaks on adapters that lack Python support.

Local development mirrors the same discipline. After editing dim_listings_cleansed, run dbt build -s +dim_listings_cleansed+ instead of rebuilding facts and unrelated marts. When experimenting with Python, select the single .py file: dbt run -s dim_long_term_listings. The instructor's point in this section is that dbt's power scales with project size only if you learn selection early — before the DAG has forty nodes and a full run takes twenty minutes.

Pattern: selector review in CI

Anti-pattern: mega --select string

Interview questions

Answer each one out loud before opening it.

What is the difference between dbt run and dbt build?Fundamentals

dbt run executes selected models only — materialising tables and views. Tests are separate unless you invoke dbt test.

dbt build runs models, seeds, snapshots and tests in DAG order. Failed tests block downstream nodes. CI and production deploys prefer build because it enforces quality gates in one invocation.

Explain the graph operators +model, model+, and @model.Fundamentals

+model selects the model and all upstream ancestors. model+ selects the model and all downstream descendants. @model selects parents and children — the local neighbourhood around one node.

Depth limits like 2+model cap how far upstream you walk. Use dbt ls to verify the subgraph before running against the warehouse.

How do tags help in CI pipelines?Production

Tags group nodes by tier or domain: critical, nightly, fact, pii. CI runs dbt test -s tag:critical on every pull request and reserves heavy tag:nightly tests for scheduled jobs.

Tags decouple pipeline YAML from model lists. Adding a model to a tier means setting a tag in config, not editing GitHub Actions.

What is selectors.yml and when would you use it?Design

selectors.yml stores named, reusable selection definitions composed from methods like path, tag, fqn, state, union, and exclude.

Use it when the same complex selection appears in CI, Airflow, and local docs. Named selectors are self-documenting and survive dbt version changes better than 200-character CLI strings.

How did named selector CLI syntax change in dbt 1.12?Gotcha

Before 1.12: dbt run --selector my_selector. From 1.12: dbt run -s selector:my_selector.

The YAML definition file is unchanged; only the invocation flag changed. Projects on 1.11 (like the course pin) still use --selector.

What is state:modified and what does it require?Production

state:modified selects nodes whose body, config or dependencies differ from a comparison manifest — typically the last production deploy.

You must pass --state path/to/artifacts containing a prior manifest.json. Append + for downstream: state:modified+. Slim CI in Section 19 builds on this pattern.

How do project variables differ from Jinja set variables?Jinja

{% set x = 1 %} is compile-time scope inside one file or macro — not overridable from the CLI.

var('x') reads from dbt_project.yml defaults and --vars at invocation time. Use vars for dates, thresholds and environment-specific business parameters orchestrators inject per run.

Which warehouses support dbt Python models?Comparison

Snowflake (Snowpark), BigQuery, and Databricks support Python models. Postgres and Redshift do not.

Python models define a model(dbt, session) function, return a DataFrame, and configure materialisation via dbt.config(). Keep them on supported adapters or set enabled: false.

When would you choose a Python model over SQL?Design

When you need a Python library SQL cannot access — NLP, statistical packages, complex iterative logic — and the input size fits the warehouse Python runtime.

Prefer SQL for set-based transforms. Python on large facts via to_pandas() is slow and expensive. Many teams score in a separate service and land results as sources instead.

What does dbt ls do and why run it before dbt run?Troubleshooting

dbt ls lists project nodes matching the same --select grammar as run/test/build, without executing warehouse queries.

It previews CI blast radius, confirms tag and selector YAML works, and gives exact test node names to copy. Cheap insurance before an expensive dbt build.

What does dbt parse produce and why does CI care?Production

dbt parse validates the project and writes target/manifest.json describing every node, its dependencies, config and tags. No warehouse DDL runs.

Slim CI uploads that manifest (or a production copy) so state:modified can diff pull requests against main. --warn-error turns deprecations into failures on lint jobs.

How do you combine union and exclude in selectors.yml?Design

Put clauses under union: for OR logic. Nest exclude: as a sibling entry with its own method list to subtract nodes from the union result.

The course example unions path: models/dim then excludes fqn: dim_listings_w_hosts. Equivalent inline CLI: path:models/dim --exclude dim_listings_w_hosts.

Recap

  • --select / -s filters the DAG; graph operators +, suffix +, and @ control upstream/downstream scope.
  • Resource prefixes include tag:, path:, source:, fqn:, and state:modified (requires --state).
  • Tags in dbt_project.yml use +tags; model files override with config(tags=[...]).
  • selectors.yml stores named selections; pre-1.12 uses --selector name, 1.12+ uses -s selector:name.
  • dbt build runs tests in DAG order; dbt run does not.
  • dbt ls previews selection; dbt parse writes manifest; dbt retry reruns failures only.
  • Vars default in dbt_project.yml; override with --vars; read with var('name', default).
  • Python models implement model(dbt, session); configure via dbt.config(materialized=..., packages=[...]).
  • Python models run on Snowflake, BigQuery, and Databricks — not Postgres or Redshift.
  • dim_long_term_listings uses Snowpark; dim_fullmoon and dim_review_sentiment use Pandas plus pip packages.
  • Never put secrets in --vars; use env_var() for credentials.
  • dbt docs generate builds catalog JSON; dbt clean removes target/ and dbt_packages/.
  • dbt run-operation invokes macros; combine with --vars to demo learn_variables.
  • Comma in one -s string is union (OR); repeated --select flags are intersection (AND).
  • result:fail reruns only tests that failed in the previous invocation.
