[COF-CO3] Dynamic Table

A dynamic table (DT) is defined by a SELECT query. Snowflake automatically refreshes it to stay within a target lag. Queries against a DT use your session warehouse; refreshes use the DT's assigned warehouse.

Exam note: Dynamic tables have storage + compute cost. TARGET_LAG controls freshness. DTs can depend on other DTs (multi-hop pipelines). For Snowpipe/stream/task CDC patterns see Section 8.

CREATE OR REPLACE TABLE sales_raw (
  id INT, amount FLOAT, region STRING, sale_date DATE
);

INSERT INTO sales_raw VALUES
  (1, 100, 'APAC', '2025-09-01'),
  (2, 200, 'US',   '2025-09-02'),
  (3, 150, 'APAC', '2025-09-03');

CREATE OR REPLACE DYNAMIC TABLE sales_sum
  TARGET_LAG = '1 minute'
  WAREHOUSE = COMPUTE_WH
AS
  SELECT region, SUM(amount) AS total_sales, COUNT(*) AS num_orders
  FROM sales_raw
  GROUP BY region;

SELECT * FROM sales_sum;

INSERT INTO sales_raw VALUES (4, 300, 'US', '2025-09-04');

ALTER DYNAMIC TABLE sales_sum SET TARGET_LAG = '1 hour';
ALTER DYNAMIC TABLE sales_sum SUSPEND;
ALTER DYNAMIC TABLE sales_sum RESUME;

CREATE OR REPLACE DYNAMIC TABLE region_share
  TARGET_LAG = '1 minute'
  WAREHOUSE = COMPUTE_WH
AS
  SELECT region, total_sales,
         total_sales / SUM(total_sales) OVER () AS pct_of_total
  FROM sales_sum;

SELECT * FROM region_share;

Cleanup

DROP DYNAMIC TABLE IF EXISTS region_share;

[COF-CO3] Iceberg Table Concept

Apache Iceberg stores data and metadata in cloud storage. Snowflake-managed Iceberg uses an external volume and CATALOG = 'SNOWFLAKE'. Benefits: ACID compliance, single copy in the lake, interoperability with other engines.

External table

File-level metadata; read-only; raw file queries.

Iceberg table

Table-format ACID; read/write; better governance on large lakes.

[COF-CO3] Event Table Concept

Event tables capture LOG, TRACE, and METRIC records from stored procedures, UDFs, and Snowpark handlers.

  • System default: SNOWFLAKE.TELEMETRY.EVENTS / EVENTS_VIEW.
  • Account parameters: LOG_LEVEL, TRACE_LEVEL, METRIC_LEVEL.
  • Custom event table: CREATE EVENT TABLE + ALTER DATABASE SET EVENT_TABLE = ....
  • Cost: EVENT_USAGE_HISTORY tracks CREDITS_USED and BYTES_INGESTED.

CREATE OR REPLACE TABLE demo_data AS
SELECT UNIFORM(1, 1000, RANDOM())::FLOAT AS feature_1,
       UNIFORM(1, 1000, RANDOM())::FLOAT AS feature_2,
       UNIFORM(1, 1000, RANDOM())::FLOAT AS feature_3,
       UNIFORM(1, 1000, RANDOM())::FLOAT AS feature_4,
       MOD(SEQ4(), 3) AS label
FROM TABLE(GENERATOR(ROWCOUNT => 500000));

CREATE OR REPLACE PROCEDURE train_and_benchmark()
RETURNS TABLE (warehouse STRING, duration_sec FLOAT, status STRING)
LANGUAGE PYTHON RUNTIME_VERSION = '3.10'
PACKAGES = ('snowflake-snowpark-python', 'scikit-learn', 'pandas')
HANDLER = 'run'
AS $$
import time
from sklearn.ensemble import RandomForestClassifier
def run(session):
    df = session.table("demo_data").to_pandas()
    X = df[['FEATURE_1','FEATURE_2','FEATURE_3','FEATURE_4']].values
    y = df['LABEL'].values
    start = time.time()
    model = RandomForestClassifier(n_estimators=20, max_depth=5, n_jobs=-1)
    model.fit(X, y)
    duration = time.time() - start
    wh = session.get_current_warehouse()
    return session.create_dataframe([[wh, duration, "SUCCESS"]],
           schema=["WAREHOUSE", "DURATION_SEC", "STATUS"])
$$;

USE WAREHOUSE standard_wh;
CALL train_and_benchmark();

USE WAREHOUSE snowpark_wh;
CALL train_and_benchmark();

Cleanup

[COF-CO3] Demo : Warehouse Credit Consumption

Course file: [COF-CO3] Exclusive lecture for new test/WH Credit Consumption.txt

SELECT 'WAREHOUSE' AS credit_type, warehouse_name AS resource_name,
       DATE_TRUNC('day', start_time) AS usage_date,
       SUM(credits_used) AS total_credits,
       SUM(credits_used_compute) AS compute_credits,
       SUM(credits_used_cloud_services) AS cloud_services_credits
FROM snowflake.account_usage.warehouse_metering_history
WHERE start_time >= DATEADD('day', -30, CURRENT_TIMESTAMP())
GROUP BY warehouse_name, DATE_TRUNC('day', start_time)
ORDER BY usage_date DESC, total_credits DESC;

SELECT 'SERVERLESS_TASK' AS credit_type,
       database_name || '.' || schema_name || '.' || task_name AS resource_name,
       DATE_TRUNC('day', start_time) AS usage_date,
       SUM(credits_used) AS total_credits
FROM snowflake.account_usage.serverless_task_history
WHERE start_time >= DATEADD('day', -30, CURRENT_TIMESTAMP())
GROUP BY database_name, schema_name, task_name, DATE_TRUNC('day', start_time)
ORDER BY usage_date DESC, total_credits DESC;

SELECT service_type,
       SUM(credits_billed) AS actual_billed_credits,
       SUM(credits_used) AS total_credits,
       ROUND(SUM(credits_billed) * 100.0 / SUM(SUM(credits_billed)) OVER(), 2) AS pct_of_total_bill
FROM snowflake.account_usage.metering_daily_history
WHERE usage_date >= DATEADD('day', -30, CURRENT_TIMESTAMP())
GROUP BY service_type
ORDER BY actual_billed_credits DESC;

[COF-CO3] Trust Centre Concept

Trust Center in Snowsight scans your account for security hygiene and compliance gaps — a governance dashboard, not a billing tool.

  • Recommendations: enforce MFA, limit ACCOUNTADMIN count, find stale users (90+ days inactive).
  • Detect over-privileged roles and objects owned by PUBLIC.
  • Complements manual SHOW GRANTS audits and Access History reviews.

[COF-CO3] Demo : Trust Centre

Open Admin → Trust Center in Snowsight. Review each recommendation category:

  1. Authentication — MFA enrollment gaps on privileged users.
  2. Authorization — excessive admin grants, unused roles.
  3. Network — missing network policies on service accounts.
  4. Data protection — unmasked sensitive columns, missing tags.

Remediate in order of severity; re-scan after changes to confirm score improvement.

[COF-CO3] Privacy

Snowflake privacy features help publish aggregate insights without exposing individual rows — increasingly tested on COF-C03 governance questions.

  • Differential privacy policies — add calibrated noise to query results so individuals cannot be re-identified from aggregates.
  • Aggregation policies — enforce minimum group sizes (k-anonymity style) before returning SUM/COUNT/AVG on sensitive columns.
  • Projection policies — block or mask specific columns unless the query meets privacy predicates.
  • Privacy domains — group related tables/columns under a shared privacy policy scope for consistent enforcement.
Exam distinction: Masking policies hide values per role at query time. Privacy policies protect against statistical disclosure in aggregates — complementary, not interchangeable. Row access policies filter rows; privacy policies govern what can be computed across rows.

Interview questions

Try to answer each one before opening it.

What does a dynamic table give you that a task plus a stream does not?Comparison

A dynamic table is a declarative pipeline — you define a SELECT, set TARGET_LAG, and Snowflake manages refresh scheduling and incremental maintenance. Stream-plus-task CDC requires you to author the MERGE logic, wire SYSTEM$STREAM_HAS_DATA, and operate task graphs yourself. Dynamic tables also chain natively (multi-hop: sales_sum → region_share in the course demo). Trade-off: DTs bill storage plus refresh compute and are less flexible for complex branching logic than hand-written task SQL.

How do TARGET_LAG, incremental refresh, and full refresh interact on a dynamic table?Fundamentals

TARGET_LAG is the maximum staleness Snowflake targets — the course starts at '1 minute' then alters to '1 hour'. Snowflake attempts incremental refreshes when source changes allow; it falls back to full refresh when the definition or upstream changes require it. Queries against the DT use your session warehouse; refreshes use the DT's assigned warehouse. Use ALTER DYNAMIC TABLE … SUSPEND/RESUME to pause refresh spend. Compare to materialized views (automatic maintenance, different feature set) and to streams/tasks (imperative MERGE).

What makes external tables read-only, and how do you map file columns?Fundamentals

External tables point at files in cloud storage via an external stage — Snowflake stores partition and file metadata, not a full copy of the data. They are read-only: no INSERT/UPDATE/DELETE. Column definitions use VALUE:cN expressions to cast positional CSV/JSON fields (e.g. VALUE:c1::INT). Use metadata$filename and related metadata columns for file-level filtering. Refresh the file list with ALTER EXTERNAL TABLE … REFRESH; set AUTO_REFRESH when event notifications are configured. DML belongs in native or Iceberg tables, not external tables.

Why do Iceberg tables matter commercially compared with plain external tables?Comparison

External tables treat files as opaque blobs with file-level metadata. Iceberg adds table-format ACID, snapshot isolation, and schema evolution while keeping a single copy in the lake. Snowflake-managed Iceberg uses an EXTERNAL VOLUME and CATALOG = 'SNOWFLAKE' — the course inserts from tpch_sf1.customer into customer_iceberg. That interoperability lets Spark, Trino, and Snowflake share one governed table without duplicating storage. Commercially it reduces egress and sync cost versus copying lake data into native tables.

What telemetry levels do event tables capture, and how do system vs custom tables differ?Fundamentals

Event tables ingest LOG, TRACE, and METRIC records from stored procedures, UDFs, and Snowpark handlers. Account parameters LOG_LEVEL, TRACE_LEVEL, and METRIC_LEVEL control verbosity — the course demo sets TRACE_LEVEL = 'ON_EVENT' (production-safe) versus 'ALWAYS' (expensive). The system default lives in SNOWFLAKE.TELEMETRY.EVENTS / EVENTS_VIEW. A custom table uses CREATE EVENT TABLE plus ALTER DATABASE SET EVENT_TABLE = …. Monitor ingestion cost in EVENT_USAGE_HISTORY.

Standard Gen2 supports which warehouse sizes, and when must you stay on Gen1?Gotcha

Standard Gen2 warehouses support sizes XS through 4XL when created with GENERATION = '2'. 5XL and 6XL require Gen1 — you cannot simply "move everything to Gen2" on the largest tiers. Gen2 and Snowpark-optimized are orthogonal choices: Gen2 is hardware generation; Snowpark-optimized trades higher credits for more memory per node. Exam trap: a scenario asking for a 5XL Gen2 warehouse has no valid answer — pick Gen1 at that size or scale out with multi-cluster instead.

How do you read warehouse credit consumption from account usage views?Fundamentals

WAREHOUSE_METERING_HISTORY gives per-warehouse, time-range credits — credits_used, credits_used_compute, and credits_used_cloud_services — ideal for daily rollups by warehouse name. METERING_DAILY_HISTORY aggregates by service_type (warehouse, storage, serverless, AI_SERVICES, etc.) for account-wide percentage-of-bill analysis. The course also queries SERVERLESS_TASK_HISTORY for task spend. Join warehouse metering to tags for chargeback; use daily history to spot Cortex or storage spikes resource monitors miss.

Which parameters can only be set at account level?Gotcha

Not every parameter exists at every scope. MIN_DATA_RETENTION_TIME_IN_DAYS is account-only — attempting ALTER SESSION SET min_data_retention_time_in_days errors. TIMEZONE can be set at account, user, and session (session wins). DATA_RETENTION_TIME_IN_DAYS and EVENT_TABLE belong at database/schema level. MAX_CONCURRENCY_LEVEL is warehouse-scoped. Always check SHOW PARAMETERS at the intended level before exam scenario questions about where a knob can be turned.

How do alerts and SYSTEM$SEND_EMAIL work with notification integrations?Fundamentals

An alert runs on a SCHEDULE and executes its THEN clause when the IF condition is true — the course checks warehouse credits in the last hour exceeding a threshold. Alerts start suspended; use ALTER ALERT … RESUME and EXECUTE ALERT to test. A NOTIFICATION INTEGRATION of TYPE = EMAIL enables SYSTEM$SEND_EMAIL(integration, recipient, subject, body). Grant EXECUTE ALERT on the account to the owning role. Suspend alerts before dropping them in cleanup.

What does Trust Center scan for?Fundamentals

Trust Center in Snowsight (Admin → Trust Center) is a governance dashboard that scans account security hygiene — not billing. It surfaces recommendations such as enforcing MFA on privileged users, limiting ACCOUNTADMIN count, finding stale users (90+ days inactive), detecting over-privileged roles, and spotting objects granted to PUBLIC. Categories include authentication, authorisation, network policies, and data protection (unmasked sensitive columns, missing tags). Re-scan after remediation to confirm score improvement; complement with SHOW GRANTS and Access History.

How does Git integration execute SQL from a repository?Fundamentals

Create an API INTEGRATION with API_PROVIDER = git_https_api, allowed URL prefixes, and an ALLOWED_AUTHENTICATION_SECRETS list. Store a GitHub PAT in a SECRET object — never leave PASSWORD = '' as in the raw course file. Create a GIT REPOSITORY pointing at your remote, list files with LS @repo/branches/main, then run EXECUTE IMMEDIATE FROM @git_integration_demo/branches/main/sample_new. Repository names in the path must match the created object. Drop secrets and integrations after labs.

How do Snowflake privacy policies differ from masking policies?Comparison

Masking policies hide or hash column values per role at query time. Privacy policies protect against statistical disclosure in aggregates — differential privacy adds calibrated noise, aggregation policies enforce minimum group sizes (k-anonymity style), and projection policies block sensitive columns unless predicates pass. Privacy domains group related tables under consistent policy scope. Row access policies filter which rows a role sees; privacy policies govern what can be computed across rows. They are complementary on COF-C03 governance questions.

How do dynamic tables compare to materialized views for exam scenarios?Comparison

Both store precomputed results, but dynamic tables are first-class declarative pipelines with explicit TARGET_LAG, warehouse assignment, multi-hop chaining, and suspend/resume controls — the COF-C03 focus. Materialized views auto-maintain on base-table changes within edition/feature limits and suit single-query acceleration. Dynamic tables fit SLA-driven transformations (minutes-level freshness); MVs fit transparent read optimisation. Neither replaces streams/tasks when you need complex conditional MERGE logic or external orchestration triggers.

What happens if you DROP TABLE a dynamic table instead of DROP DYNAMIC TABLE?Gotcha

Dynamic tables are a distinct object type — the course cleanup explicitly uses DROP DYNAMIC TABLE IF EXISTS sales_sum. Using plain DROP TABLE on a dynamic table fails or targets the wrong object type depending on context. The same applies to operational commands: ALTER DYNAMIC TABLE for lag, suspend, and resume. Exam scenarios about pipeline teardown expect you to know DT-specific DDL. After drop, downstream DTs that depend on the object break until you recreate or repoint the chain.

Hands-on practice

Run these in a trial account on an X-Small warehouse with AUTO_SUSPEND = 60. Clean up when you finish.

  1. Build the dynamic-table chain from the course demo: sales_raw → sales_sum (regional totals) → region_share (percentage of total). Insert a fourth row and query both dynamic tables.

    sales_sum shows three regions after refresh; region_share includes pct_of_total summing to 1.0 across regions.

    Show solutionSQL

    Cost note: Use TARGET_LAG = '1 hour' in trial accounts if you are not actively testing freshness — minute-level lag triggers more refreshes.

    USE ROLE ACCOUNTADMIN;
USE WAREHOUSE COMPUTE_WH;

CREATE OR REPLACE TABLE sales_raw (
  id INT, amount FLOAT, region STRING, sale_date DATE
);

INSERT INTO sales_raw VALUES
  (1, 100, 'APAC', '2025-09-01'),
  (2, 200, 'US',   '2025-09-02'),
  (3, 150, 'APAC', '2025-09-03');

CREATE OR REPLACE DYNAMIC TABLE sales_sum
  TARGET_LAG = '1 hour'
  WAREHOUSE = COMPUTE_WH
AS
  SELECT region, SUM(amount) AS total_sales, COUNT(*) AS num_orders
  FROM sales_raw
  GROUP BY region;

CREATE OR REPLACE DYNAMIC TABLE region_share
  TARGET_LAG = '1 hour'
  WAREHOUSE = COMPUTE_WH
AS
  SELECT region, total_sales,
         total_sales / SUM(total_sales) OVER () AS pct_of_total
  FROM sales_sum;

INSERT INTO sales_raw VALUES (4, 300, 'US', '2025-09-04');

SELECT * FROM sales_sum;
SELECT * FROM region_share;

    After CALL demo_event_proc(), recent rows show LOG entries including "Demo event proc started".

    Show solutionSQL

  4. Create the high-credit alert that inserts into alert_log when hourly warehouse credits exceed 10. Resume, execute once, then suspend the alert.

    Alert object exists in resumed then suspended state; manual EXECUTE ALERT may insert a row if the condition is true (or completes without error if false).

    Show solutionSQL 
    USE ROLE ACCOUNTADMIN;

CREATE DATABASE IF NOT EXISTS alert_demo_db;
CREATE SCHEMA IF NOT EXISTS alert_demo_db.ops;
USE SCHEMA alert_demo_db.ops;

GRANT EXECUTE ALERT ON ACCOUNT TO ROLE ACCOUNTADMIN;

CREATE OR REPLACE TABLE alert_log (
    alert_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP(),
    alert_name VARCHAR,
    message VARCHAR
);

CREATE OR REPLACE ALERT high_credit_alert
  SCHEDULE = '10 MINUTE'
  IF (EXISTS (
    SELECT 1
    FROM snowflake.account_usage.warehouse_metering_history
    WHERE start_time >= DATEADD('hour', -1, CURRENT_TIMESTAMP())
    HAVING SUM(credits_used) > 10
  ))
  THEN
    INSERT INTO alert_log VALUES (
      CURRENT_TIMESTAMP(),
      'high_credit_alert',
      'Warehouse credits exceeded 10 in the last hour'
    );

ALTER ALERT high_credit_alert RESUME;
EXECUTE ALERT high_credit_alert;
ALTER ALERT high_credit_alert SUSPEND;

Recap

  • Dynamic tables: declarative pipelines with TARGET_LAG; use DROP DYNAMIC TABLE.
  • External tables read lake files; Iceberg adds ACID via external volumes (s07 for stages).
  • Event tables centralise LOG/TRACE/METRIC telemetry — mind ingestion cost.
  • Gen2: XS–4XL; 5XL/6XL = Gen1. Snowpark-optimized = more memory per node.
  • Parameters: account-only vs session-overridable; alerts start suspended.
  • Trust Center scans security posture; Git + VS Code for dev workflows.
  • Privacy policies: differential privacy, aggregation/projection policies, privacy domains.
