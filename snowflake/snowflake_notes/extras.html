Snowpipe Streaming

The course teaches Snowpipe, which is file-driven: something writes a file to a stage, a notification fires, Snowflake loads the file. Snowpipe Streaming removes the file entirely — a client writes rows into a channel through an SDK, and Snowflake commits them into the table.

Everyday analogy — post versus phone call: Snowpipe is posting a letter: you fill an envelope (a file), drop it in the box (the stage), and the postal service collects it on its own schedule. Snowpipe Streaming is phoning the office directly — each sentence lands as you speak it, with no envelope in between.
Bulk COPY INTOSnowpipeSnowpipe Streaming
Unit of workFiles you chooseFiles, event-drivenRows, via channels
ComputeYour virtual warehouseServerlessServerless
Typical latencyWhenever you run itAround a minuteSeconds
Stage requiredYesYesNo
InterfaceSQLSQL pipe + notificationsJava/Scala SDK, or the Kafka connector in streaming mode
OrderingNo guarantee across filesNo guarantee across filesOrdered within a channel, via offset tokens
Default ON_ERRORABORT_STATEMENTSKIP_FILENot applicable — errors surface per row to the client

A channel is a named, logical connection from one client to one table. Each channel keeps an offset token so a restarted client can ask Snowflake what it last committed and resume without duplicating rows — this is how exactly-once delivery is achieved.

-- Snowpipe Streaming is driven from client code, not SQL. From SQL you
-- mainly observe it:

SHOW CHANNELS IN TABLE my_db.my_schema.events;

SELECT *
FROM SNOWFLAKE.ACCOUNT_USAGE.SNOWPIPE_STREAMING_FILE_MIGRATION_HISTORY
ORDER BY start_time DESC
LIMIT 50;

-- Streaming credits appear as their own service type
SELECT service_type, SUM(credits_used) AS credits
FROM SNOWFLAKE.ACCOUNT_USAGE.METERING_DAILY_HISTORY
WHERE usage_date >= DATEADD('day', -30, CURRENT_DATE())
GROUP BY service_type
ORDER BY credits DESC;
COF-C03 exam tip: If a question says "sub-minute latency", "row by row", or "no files", the answer is Snowpipe Streaming. If it says "files arrive in a bucket", it is Snowpipe. If it says "load this month's export once", it is COPY INTO. Snowpipe Streaming bills for the time a client is actively writing plus a per-client charge — it is not free when idle in the way a suspended warehouse is.

Hybrid Tables (Unistore)

Every table type the course covers is columnar and optimised for scanning lots of rows. A hybrid table is the opposite: a row-store table designed for single-row lookups and high-concurrency small writes — the transactional half of Snowflake's Unistore workload.

Standard tableHybrid table
StorageColumnar micro-partitionsRow store, with a columnar copy maintained for analytics
Best atScans and aggregations over many rowsPoint lookups and single-row updates
Primary keyInformational onlyRequired and enforced
Unique / foreign keysInformational onlyEnforced
Secondary indexesNot availableSupported
LockingTable-level for DMLRow-level
Time TravelUp to 90 days (Enterprise+)Limited — check current documentation for your region
 
CREATE OR REPLACE HYBRID TABLE order_status (
  order_id     NUMBER       PRIMARY KEY,
  customer_id  NUMBER       NOT NULL,
  status       VARCHAR(20)  NOT NULL,
  updated_at   TIMESTAMP_NTZ DEFAULT CURRENT_TIMESTAMP(),
  INDEX idx_customer (customer_id)
);

-- Enforced uniqueness: the second statement fails
INSERT INTO order_status (order_id, customer_id, status) VALUES (1, 100, 'NEW');
INSERT INTO order_status (order_id, customer_id, status) VALUES (1, 101, 'NEW');
-- Duplicate key value violates unique constraint

-- Indexed point lookup — the pattern hybrid tables exist for
SELECT status FROM order_status WHERE order_id = 1;
Availability. Hybrid tables are not enabled in every region or edition, and they are billed differently from standard tables. Confirm availability before planning a lab around them.
COF-C03 exam tip: The single most testable fact is that hybrid tables are the only Snowflake table type that enforces PRIMARY KEY and UNIQUE constraints, and the only one supporting secondary indexes. Everywhere else, NOT NULL is the only enforced constraint.

Native Apps and Snowpark Container Services

Section 12 covers sharing data. The Native App Framework extends the same distribution machinery to sharing logic: a provider packages stored procedures, UDFs, Streamlit UIs and even container images, publishes them as a listing, and a consumer installs the application into their own account. The provider's code runs on the consumer's data without either party moving the data.

Application package

The provider-side container holding versions, patches and the setup script that creates objects on install.

Setup script

Runs in the consumer account at install time. Creates the application role, views over shared content and any procedures.

Container Services

Runs long-lived container images on Snowflake-managed compute pools, so an app can ship a full service rather than only SQL.

COF-C03 exam tip: Distinguish the three collaboration outputs. A share gives live read access to objects. A listing is the packaging and discovery layer (private listing, or public on the Marketplace) around a share or an app. A Native App ships executable logic that the consumer installs and runs on their own compute.

Data Metric Functions and Data Quality

The course covers governance policies but not data quality monitoring. A data metric function (DMF) is a function that measures something about a table — a null count, a duplicate count, a freshness lag — and that Snowflake evaluates on a schedule you attach to the table. Results land in a system view you can alert on.

Snowflake ships system DMFs in the SNOWFLAKE.CORE schema:

System DMFMeasures
NULL_COUNT / NULL_PERCENTMissing values in a column
DUPLICATE_COUNTRows sharing the same value in a column
UNIQUE_COUNTDistinct values in a column
BLANK_COUNT / BLANK_PERCENTEmpty strings, as distinct from NULLs
ROW_COUNTRows in the table
FRESHNESSSeconds since the newest timestamp in a column
 
USE ROLE ACCOUNTADMIN;

-- 1. Decide how often metrics are evaluated for this table
ALTER TABLE customers SET DATA_METRIC_SCHEDULE = '60 MINUTE';
-- or: DATA_METRIC_SCHEDULE = 'USING CRON 0 8 * * * UTC'
-- or: DATA_METRIC_SCHEDULE = 'TRIGGER_ON_CHANGES'

-- 2. Attach system metrics to specific columns
ALTER TABLE customers
  ADD DATA METRIC FUNCTION SNOWFLAKE.CORE.NULL_COUNT ON (email);

ALTER TABLE customers
  ADD DATA METRIC FUNCTION SNOWFLAKE.CORE.DUPLICATE_COUNT ON (customer_id);

-- 3. A custom DMF for a business rule
CREATE OR REPLACE DATA METRIC FUNCTION negative_amounts(t TABLE(amount NUMBER))
RETURNS NUMBER
AS
$$
  SELECT COUNT(*) FROM t WHERE amount < 0
$$;

ALTER TABLE orders
  ADD DATA METRIC FUNCTION negative_amounts ON (amount);

-- 4. Read the results
SELECT measurement_time, metric_name, table_name, value
FROM SNOWFLAKE.LOCAL.DATA_QUALITY_MONITORING_RESULTS
ORDER BY measurement_time DESC
LIMIT 50;

-- 5. What is attached where
SELECT * FROM TABLE(INFORMATION_SCHEMA.DATA_METRIC_FUNCTION_REFERENCES(
  REF_ENTITY_NAME   => 'customers',
  REF_ENTITY_DOMAIN => 'TABLE'
));

-- Cleanup
ALTER TABLE customers DROP DATA METRIC FUNCTION SNOWFLAKE.CORE.NULL_COUNT ON (email);
ALTER TABLE customers UNSET DATA_METRIC_SCHEDULE;
Cost. DMF evaluation is serverless and billed per run. A TRIGGER_ON_CHANGES schedule on a busy table can evaluate far more often than an hourly cron. Resource monitors will not cap this — see Budgets.

Aggregation, Projection and Tag-Based Policies

Section 10 teaches masking policies and row access policies. Snowflake Horizon adds two more policy types the course never mentions, plus a way to attach any of them through tags instead of one object at a time.

Aggregation policy — no single-row answers

Forces queries against a table to return grouped results with at least N rows behind each group. Useful when you want a partner to analyse a population without identifying individuals.

CREATE OR REPLACE AGGREGATION POLICY min_group_of_five
  AS () RETURNS AGGREGATION_CONSTRAINT ->
    AGGREGATION_CONSTRAINT(MIN_GROUP_SIZE => 5);

ALTER TABLE patients SET AGGREGATION POLICY min_group_of_five;

SELECT * FROM patients;                       -- blocked: not an aggregate
SELECT city, COUNT(*) FROM patients GROUP BY city;
-- groups with fewer than 5 rows are combined into a remainder group

ALTER TABLE patients UNSET AGGREGATION POLICY;

Projection policy — a column you may filter on but never see

CREATE OR REPLACE PROJECTION POLICY no_projection
  AS () RETURNS PROJECTION_CONSTRAINT ->
    PROJECTION_CONSTRAINT(ALLOW => false);

ALTER TABLE customers MODIFY COLUMN email
  SET PROJECTION POLICY no_projection;

SELECT email FROM customers;                    -- blocked
SELECT COUNT(*) FROM customers WHERE email LIKE '%@example.com';  -- allowed

Tag-based masking — attach once, apply everywhere

Instead of applying a masking policy to every column individually, attach it to a tag. Any column that carries the tag inherits the policy, including columns created later.

CREATE OR REPLACE TAG pii_tag;

CREATE OR REPLACE MASKING POLICY mask_email AS (val STRING)
  RETURNS STRING ->
    CASE WHEN CURRENT_ROLE() IN ('ACCOUNTADMIN') THEN val ELSE '***MASKED***' END;

-- Bind policy to tag, then tag columns
ALTER TAG pii_tag SET MASKING POLICY mask_email;
ALTER TABLE customers MODIFY COLUMN email SET TAG pii_tag = 'high';

-- Any newly tagged column is masked automatically
ALTER TABLE leads MODIFY COLUMN work_email SET TAG pii_tag = 'high';
COF-C03 exam tip: Learn the shapes. Masking policy changes a value in a column. Row access policy removes rows. Projection policy stops a column being selected while still allowing it in a predicate. Aggregation policy stops row-level output entirely. A masking policy and a projection policy can sit on the same column; a column can only have one masking policy at a time.

Automatic Data Classification

Classification scans column data, infers what kind of information it holds, and can tag it for you — the input that makes tag-based masking practical at scale.

-- Classify a schema and write the resulting tags automatically
CREATE OR REPLACE SNOWFLAKE.DATA_PRIVACY.CLASSIFICATION_PROFILE
  my_profile(
    {
      'minimum_object_age_for_classification_days': 0,
      'maximum_classification_validity_days': 30,
      'auto_tag': true
    }
  );

ALTER SCHEMA sales_db.public
  SET CLASSIFICATION_PROFILE = 'my_profile';

-- Or classify on demand
CALL SYSTEM$CLASSIFY('sales_db.public.customers', {'auto_tag': true});

-- Review what was found
SELECT * FROM TABLE(
  INFORMATION_SCHEMA.TAG_REFERENCES_ALL_COLUMNS('customers', 'table')
);

Snowflake reports two things per column: a semantic category (what the data means — EMAIL, NAME, PHONE_NUMBER) and a privacy category (how sensitive it is — IDENTIFIER, QUASI_IDENTIFIER, SENSITIVE).

Organizations, ORGADMIN and Organization Usage

The course works inside one account. In reality an organization sits above accounts and is how enterprises separate production from development, meet data-residency rules, and roll usage up for billing.

Organization
ORGADMIN · one contract, many accounts
Account
One cloud, one region, one edition
Database → Schema → Object
Everything the rest of these notes covers
USE ROLE ORGADMIN;

SHOW ORGANIZATION ACCOUNTS;

CREATE ACCOUNT dev_account
  ADMIN_NAME     = 'dev_admin'
  ADMIN_PASSWORD = '<strong_password>'
  EMAIL          = 'your-team@example.com'
  EDITION        = ENTERPRISE
  REGION         = 'aws_us_east_1';

-- Usage across every account in the organization
SELECT account_name, usage_date, SUM(credits_used) AS credits
FROM SNOWFLAKE.ORGANIZATION_USAGE.METERING_DAILY_HISTORY
WHERE usage_date >= DATEADD('day', -30, CURRENT_DATE())
GROUP BY account_name, usage_date
ORDER BY usage_date DESC;

SELECT * FROM SNOWFLAKE.ORGANIZATION_USAGE.CONTRACT_ITEMS;
COF-C03 exam tip: ORGADMIN is not in the normal role hierarchy under ACCOUNTADMIN. It is granted separately, it exists to manage accounts and read ORGANIZATION_USAGE, and it cannot see the data inside those accounts. Remember the three usage schemas: INFORMATION_SCHEMA (current database, live, short retention), SNOWFLAKE.ACCOUNT_USAGE (whole account, up to 365 days, latency of minutes to hours), SNOWFLAKE.ORGANIZATION_USAGE (all accounts).

Budgets versus Resource Monitors

Section 9 covers resource monitors. Their well-known limitation is that they only see credits from the user-managed warehouses assigned to them. Everything serverless — Snowpipe, tasks, materialized view maintenance, search optimization, Cortex, DMFs — is invisible to them. Budgets close that gap.

Resource monitorBudget
CoversAssigned user-managed warehouses, plus their cloud-services usageWarehouses, serverless features, storage and AI services
Can suspend computeYes — SUSPEND and SUSPEND_IMMEDIATENo — notification only
GranularityAccount, or a set of warehousesAccount budget, plus custom budgets over any set of objects
PeriodDaily, weekly, monthly, yearly, or never resetMonthly spending limit
 
USE ROLE ACCOUNTADMIN;

-- Account-level budget
CALL SNOWFLAKE.LOCAL.ACCOUNT_ROOT_BUDGET!SET_SPENDING_LIMIT(1000);
CALL SNOWFLAKE.LOCAL.ACCOUNT_ROOT_BUDGET!SET_EMAIL_NOTIFICATIONS(
  'my_email_integration', ARRAY_CONSTRUCT('your-team@example.com')
);

-- Custom budget over a chosen set of objects
CREATE OR REPLACE SNOWFLAKE.CORE.BUDGET analytics_budget();
CALL analytics_budget!SET_SPENDING_LIMIT(250);
CALL analytics_budget!ADD_RESOURCE(SYSTEM$REFERENCE('WAREHOUSE', 'ANALYTICS_WH'));
CALL analytics_budget!ADD_RESOURCE(SYSTEM$REFERENCE('DATABASE', 'ANALYTICS_DB'));

SELECT analytics_budget!GET_SPENDING_LIMIT();
CALL analytics_budget!GET_SERVICE_TYPE_SPENDING_HISTORY();
COF-C03 exam tip: "Stop the spend" is a resource monitor. "Tell me about the spend, including serverless" is a budget. A question that mentions capping Snowpipe or Cortex costs with a resource monitor is describing something that does not work.

Replication, Failover Groups and Client Redirect

Section 12 introduces replication. This is the business-continuity depth behind it.

CapabilityWhat it doesMinimum edition
Database replicationRead-only secondary copy of one database in another account or regionStandard
Replication groupReplicates a set of databases and account objects together, consistentlyBusiness Critical
Failover groupA replication group that can be promoted to primaryBusiness Critical
Client redirectA connection URL that can be pointed at a different account without changing client configBusiness Critical
 
-- On the primary account
CREATE FAILOVER GROUP prod_fg
  OBJECT_TYPES  = DATABASES, ROLES, USERS, WAREHOUSES, INTEGRATIONS
  ALLOWED_DATABASES = sales_db, finance_db
  ALLOWED_ACCOUNTS  = myorg.dr_account
  REPLICATION_SCHEDULE = '10 MINUTE';

-- On the secondary account
CREATE FAILOVER GROUP prod_fg
  AS REPLICA OF myorg.prod_account.prod_fg;

ALTER FAILOVER GROUP prod_fg REFRESH;

-- Failover: promote the secondary
ALTER FAILOVER GROUP prod_fg PRIMARY;

-- Client redirect
CREATE CONNECTION prod_conn;
CREATE CONNECTION prod_conn AS REPLICA OF myorg.prod_account.prod_conn;
ALTER CONNECTION prod_conn PRIMARY;   -- run on the account taking over

SELECT * FROM SNOWFLAKE.ACCOUNT_USAGE.REPLICATION_GROUP_REFRESH_HISTORY
ORDER BY start_time DESC;
Two things that catch people out. You cannot replicate into an account of a lower edition than the primary. And replication transfers data across regions, which is billed as egress on top of the storage the secondary consumes — a frequent REPLICATION_SCHEDULE on a large database is expensive.

Constraints, Enforcement and Join Elimination

The course creates tables with PRIMARY KEY and NOT NULL without dwelling on which of them Snowflake actually enforces. The answer is a reliable exam question.

ConstraintStandard tablesHybrid tablesWhy declare it anyway
NOT NULLEnforcedEnforcedGenuine data protection
PRIMARY KEYNot enforcedEnforcedDocuments intent; the optimizer can use it
UNIQUENot enforcedEnforcedDocuments intent
FOREIGN KEYNot enforcedEnforcedEnables join elimination; tools read it for ER diagrams
 
CREATE OR REPLACE TABLE dim_customer (
  customer_id NUMBER PRIMARY KEY,          -- informational
  name        VARCHAR NOT NULL             -- enforced
);

-- Both rows insert: the primary key is not enforced
INSERT INTO dim_customer VALUES (1, 'Ann'), (1, 'Bob');

-- This fails: NOT NULL is enforced
INSERT INTO dim_customer VALUES (2, NULL);

-- Declaring RELY lets the optimizer trust the constraint and
-- eliminate joins that select no columns from the dimension
ALTER TABLE dim_customer
  ALTER CONSTRAINT PRIMARY KEY (customer_id) RELY;

SHOW PRIMARY KEYS IN TABLE dim_customer;
COF-C03 exam tip: "Which constraint does Snowflake enforce on a standard table?" — only NOT NULL. Declaring the others is still worthwhile, because with RELY the optimizer may skip a join entirely.

Full Data-Type Reference

The course meets data types as it needs them. Here they are in one place, including the geospatial types it never uses.

NumericNUMBER(p,s), DECIMAL, INT, FLOAT, DOUBLEAll the integer aliases are NUMBER(38,0). FLOAT is approximate — never use it for money.
StringVARCHAR(n), CHAR, STRING, TEXTMaximum 16 MB. Declaring a length costs nothing extra in storage; Snowflake only stores what is there.

  TO_GEOGRAPHY('POINT(-122.35 37.55)')                AS from_wkt,
  ST_DISTANCE(
    TO_GEOGRAPHY('POINT(-122.35 37.55)'),
    TO_GEOGRAPHY('POINT(0.13 51.51)')
  )                                                    AS metres_apart,
  [1.0, 2.0, 3.0]::VECTOR(FLOAT, 3)                    AS embedding;

External Functions

Section 13 names external functions without demonstrating them. They let a SQL query call code running outside Snowflake — a Lambda, an Azure Function, any HTTPS endpoint behind a cloud API gateway.

USE ROLE ACCOUNTADMIN;

CREATE OR REPLACE API INTEGRATION my_api_int
  API_PROVIDER         = aws_api_gateway
  API_AWS_ROLE_ARN     = 'arn:aws:iam::<aws_account_id>:role/snowflake_api_role'
  API_ALLOWED_PREFIXES = ('https://<api_id>.execute-api.<region>.amazonaws.com/prod/')
  ENABLED              = TRUE;

CREATE OR REPLACE EXTERNAL FUNCTION sentiment_score(text VARCHAR)
  RETURNS VARIANT
  API_INTEGRATION = my_api_int
  AS 'https://<api_id>.execute-api.<region>.amazonaws.com/prod/sentiment';

SELECT review_id, sentiment_score(review_text) FROM reviews LIMIT 10;
COF-C03 exam tip: Know the four ways to run non-SQL logic and where each executes. UDF and stored procedure: inside Snowflake. Snowpark: inside Snowflake, on a warehouse. External function: outside Snowflake, reached through an API integration, and therefore subject to network latency and the remote service's availability. External functions cannot be shared and are not available in all deployments.

Query Hash and Recurring-Query Analysis

Section 9 tunes one query at a time using Query Profile. Query hashes let you find which queries are worth tuning, by grouping executions that share the same shape.

-- QUERY_HASH: identical text. QUERY_PARAMETERIZED_HASH: same shape,
-- different literals — the one you usually want.
SELECT
  query_parameterized_hash,
  ANY_VALUE(query_text)                       AS example_query,
  COUNT(*)                                    AS executions,
  ROUND(SUM(total_elapsed_time) / 1000 / 60, 1) AS total_minutes,
  ROUND(AVG(total_elapsed_time) / 1000, 1)      AS avg_seconds,
  SUM(bytes_spilled_to_local_storage)           AS local_spill
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY
WHERE start_time >= DATEADD('day', -7, CURRENT_TIMESTAMP())
  AND execution_status = 'SUCCESS'
GROUP BY query_parameterized_hash
ORDER BY total_minutes DESC
LIMIT 20;

Sorting by total time rather than average time is the point: a two-second query run 400,000 times costs far more than a ten-minute report run once a week.

Build it in seven phases

Prerequisites: trial account, an S3 bucket you control Role: ACCOUNTADMIN for setup, custom roles thereafter Warehouse: X-Small with AUTO_SUSPEND = 60 Cost: low if you complete the cleanup Time: 2–3 hours
  1. Foundation — database, schemas (raw, curated, marts), a warehouse with auto-suspend, and a resource monitor. Covered in Section 2 and Section 9.
  2. Ingest — storage integration, external stage, file format, then a pipe with AUTO_INGEST = TRUE. Section 7 and Section 5.
  3. Transform — a stream on the raw table feeding a task that MERGEs into curated, and a dynamic table for the aggregate mart. Section 5 and Section 15.
  4. Govern — custom roles for loader, transformer and analyst; a masking policy on customer email; a row access policy on region. Section 10.
  5. Optimise — run the mart query, read the Query Profile, decide honestly whether clustering or the search optimization service is justified. Section 9.
  6. Collaborate — a secure view over the mart, shared to a reader account. Section 12.
  7. Operate — an alert on credit usage, cost attribution by tag, and a Git-backed deployment script. Section 14 and Section 15.

Verification checklist

  • Dropping a file in the bucket lands rows in raw within about a minute.
  • SYSTEM$STREAM_HAS_DATA returns TRUE before the task runs and FALSE after.
  • The analyst role sees masked emails and only its own region's rows.
  • The reader account can query the secure view and nothing else.
  • The alert fires when you lower its threshold below current usage.

Recap

  • Snowpipe Streaming loads rows through channels with offset tokens — no files, no stage, seconds of latency.
  • Hybrid tables are the only table type that enforces PRIMARY KEY and UNIQUE and supports secondary indexes.
  • Data metric functions plus a DATA_METRIC_SCHEDULE give you scheduled data-quality monitoring.
  • Masking changes a value, row access removes rows, projection blocks selection, aggregation blocks row-level output.
  • Resource monitors can suspend warehouses but ignore serverless; budgets see everything but only notify.
  • Failover groups and client redirect require Business Critical; plain database replication does not.
  • On standard tables only NOT NULL is enforced — the rest are informational, though RELY helps the optimizer.
  • Group QUERY_PARAMETERIZED_HASH by total elapsed time to find what is actually worth tuning.
