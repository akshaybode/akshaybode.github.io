How to answer a scenario question

Scenario questions are not really about the answer. The interviewer already knows how to fix a spilling query; what they want to see is whether you diagnose before you act, whether you know where the evidence lives, and whether you think about cost and blast radius rather than reaching for a bigger warehouse.

Almost every operational scenario in a Snowflake interview can be answered with the same four-beat structure. Use it out loud and you will sound like someone who has been on call.

  1. Contain. Say what you would do in the first two minutes to stop the bleeding — cancel the query, suspend the warehouse, revoke the grant, pause the task. State it explicitly even when it is obvious, because a lot of candidates skip straight to root cause and never mention the customer waiting.
  2. Diagnose with evidence. Name the view or screen you would open. QUERY_HISTORY, the Query Profile, WAREHOUSE_LOAD_HISTORY, COPY_HISTORY, ACCESS_HISTORY. Naming the source is what separates experience from theory.
  3. Fix, cheapest first. Offer the smallest change that solves the problem, then the next one up. Rewriting a predicate is free; a clustering key is a permanent credit line. Interviewers notice which one you reach for.
  4. Prevent. Finish with the guardrail — a resource monitor, a statement timeout, a test, an alert. This is the beat most candidates forget and the one that reads as seniority.
Say the trade-off out loud. There is rarely one right answer to these questions, and the interviewer usually knows it. "I would size up first because we are five minutes from a board meeting, then fix the predicate properly tomorrow" is a much stronger answer than either option on its own.
Know where the numbers come from. SNOWFLAKE.ACCOUNT_USAGE is retained for about a year but lags by roughly 45 minutes to 3 hours depending on the view, so it is useless during a live incident. For anything happening right now, use the INFORMATION_SCHEMA table functions or the Query History page in Snowsight, which are current but only reach back 7 days (14 for some views). Mixing these two up mid-answer is a common tell.

Round 1 — Slow and long-running queries

The most-asked scenario family in every Snowflake interview. Try to answer before opening.

A query that normally finishes in two minutes has been running for 45 minutes. Walk me through what you do.Flagship

I work through it in the same order every time: is it running or waiting, is it doing more work than usual, and is the work being done badly.

First, find it and decide whether to kill it. Snowsight's Query History, filtered to running queries, or the table function if I am in a worksheet:

SELECT query_id, user_name, warehouse_name, execution_status,
       total_elapsed_time/1000       AS elapsed_secs,
       queued_overload_time/1000     AS queued_secs,
       bytes_spilled_to_local_storage,
       bytes_spilled_to_remote_storage
FROM   TABLE(information_schema.query_history_by_warehouse(
               warehouse_name => 'REPORTING_WH',
               result_limit   => 100))
WHERE  execution_status = 'RUNNING'
ORDER  BY elapsed_secs DESC;

If it is blocking a business deadline and I can rerun it later, I cancel it with SYSTEM$CANCEL_QUERY('<query_id>') rather than let it burn credits while I investigate. Cancelling is safe: Snowflake rolls back the statement.

Second, separate queuing from execution. If queued_overload_time is most of the elapsed time, the query is not slow — the warehouse is saturated. Sizing up will not help; adding clusters or moving the workload to its own warehouse will. Check WAREHOUSE_LOAD_HISTORY to confirm.

Third, open the Query Profile. I look for four things in this order:

  • Partitions scanned versus partitions total. If it is scanning everything, pruning has failed — usually a function wrapped around the filter column, a leading-wildcard LIKE, an implicit cast, or a genuinely unclustered table.
  • Spilling. Bytes spilled to local storage means the warehouse ran out of memory; spilling to remote storage is far worse and usually the single biggest cause of a 20x slowdown. That is the one case where sizing up is the correct fix, because a larger warehouse has proportionally more memory.
  • An exploding join. A join node emitting far more rows than it consumed means a duplicate key or a missing join condition. This is a data problem, not a warehouse problem.
  • The most expensive node's percentage. If one node is 90% of the time, that is where the whole conversation goes.

Fourth, ask what changed. A query that was fine last week and is terrible today has usually had its input volume grow, lost its result-cache hit because someone added CURRENT_TIMESTAMP(), been pointed at a bigger warehouse's workload, or had a clustering key silently stop matching the new query pattern. I compare today's profile with a historical run of the same query_hash.

Finally, prevent. Set STATEMENT_TIMEOUT_IN_SECONDS on the warehouse or role so a runaway query dies on its own next time, and if this is a shared warehouse, give the offending workload its own so it cannot starve everyone else.

How do you tell the difference between a query that is queued and a query that is slow, and why does it matter?Diagnosis

In QUERY_HISTORY, total_elapsed_time is the wall clock the user experienced, and it decomposes into queueing components (queued_provisioning_time, queued_repair_time, queued_overload_time) plus execution_time. If queued_overload_time dominates, the warehouse had no free slots.

It matters because the two problems have opposite fixes. Slow execution is fixed by a bigger warehouse or better SQL; queuing is fixed by more warehouses or more clusters, and sizing up can even make queuing worse by encouraging more concurrent work onto the same warehouse. A candidate who says "I would size it up" to every performance question fails on exactly this distinction.

The same dashboard query is fast for you and slow for a business user. What is going on?Gotcha

Almost always the result cache. My run hit it and theirs did not. The result cache only serves a query when the SQL text matches exactly, the underlying data has not changed, the query contains no non-deterministic functions, and the role has the necessary privileges on all referenced objects — so a different role can legitimately miss a cache another role hits.

The other common causes are a different warehouse (theirs is X-Small, mine is Large), a warm warehouse cache for me and a cold resume for them, or a row access policy that makes their version of the query scan differently. I would compare the two query_ids side by side in Query History rather than guess.

A table is 4 TB and every query on it does a full scan. What do you do, in what order?Cost

Cheapest first, always. I start by reading the actual predicates: if the filters are wrapped in functions (WHERE TO_DATE(event_ts) = ...) or cast implicitly, pruning is disabled and rewriting the SQL fixes it for free.

If the predicates are clean and still scanning everything, I look at how the data arrived. Data loaded in natural order is usually well clustered on the load timestamp already, so filtering on a different column is the real issue. Then I choose between three paid options based on the access pattern:

  • Clustering key when queries filter on a low-to-medium cardinality column with range predicates. Ongoing reclustering credits, so it needs to earn its keep.
  • Search optimization service when queries are highly selective point lookups on high-cardinality columns. Storage and maintenance cost, but no reclustering churn.
  • Materialized view when one expensive aggregate is queried repeatedly over a stable subset.

I would validate with SYSTEM$CLUSTERING_INFORMATION before and after rather than assuming, and I would not cluster a table this size without checking that the reclustering cost is smaller than the scan cost it saves.

Query Profile shows 40 GB spilled to remote storage. What does that mean and how do you fix it?Diagnosis

The operation needed more memory than the warehouse had. Snowflake first spills to local SSD, and when that fills too, it spills to remote object storage, which is orders of magnitude slower. Remote spilling is the clearest signal in the whole profile that the warehouse is undersized for the work.

Two fixes. Size up — doubling the warehouse doubles memory as well as threads, and a query that spills often gets cheaper on a larger warehouse because it finishes more than twice as fast for twice the per-second rate. Or reduce the memory footprint: filter earlier, drop the columns you do not need, avoid an unnecessary ORDER BY on a huge intermediate, or fix a join that is exploding row counts. For genuinely memory-hungry Snowpark or ML work, a Snowpark-optimized warehouse gives more memory per node than the equivalent standard size.

Your team wants to add a clustering key to every large table. How do you respond?Judgement

I would push back and ask for evidence per table. Clustering is not free: automatic reclustering consumes serverless credits continuously, and on a table with heavy DML it can cost more than the queries it accelerates. It only pays off when the table is large, the queries consistently filter or join on the key, and the current clustering depth is genuinely bad.

My rule of thumb is to measure first with SYSTEM$CLUSTERING_INFORMATION, only consider tables in the multi-terabyte range, cluster on at most three or four columns ordered from lowest to highest cardinality, and never cluster a table that is rewritten in full on every load — in that case the load order is the clustering key.

Overnight batch used to finish at 6am and now finishes at 9am. Nothing in the code changed. Where do you look?Scenario

I would build a time series rather than look at one run. Pull the last 30 days from ACCOUNT_USAGE.QUERY_HISTORY grouped by query_hash, and plot elapsed time, bytes scanned and partitions scanned per night. That immediately tells me whether every step degraded slightly (data growth) or one step fell off a cliff (a plan change, a new join key skew, a clustering key that stopped matching).

Then I check contention: did another workload start using the same warehouse? WAREHOUSE_LOAD_HISTORY and WAREHOUSE_EVENTS_HISTORY show queuing and cluster behaviour over the window. Finally I check whether a table it reads is now a view over something much larger, or whether someone changed AUTO_SUSPEND so every step pays a cold-cache penalty.

Users complain the BI tool is slow at 9am every day but fine by 10. What is your fix?Scenario

That shape is concurrency, not query complexity — everyone opens their dashboard at the start of the day. The fix is a multi-cluster warehouse in auto-scale mode with MIN_CLUSTER_COUNT = 1 and a max of two or three, so extra clusters spin up for the morning peak and shut down afterwards. I would use the STANDARD scaling policy so it adds clusters eagerly rather than making users wait.

Supporting moves: give BI its own warehouse so ETL cannot starve it, keep AUTO_SUSPEND generous enough (a few minutes) that the warehouse cache survives between dashboard refreshes, and check whether the dashboards can hit the result cache — identical queries from many users are exactly what it is for. If the same heavy aggregate is behind every tile, a materialized view or a small pre-aggregated table pays for itself quickly.

Would you ever solve a performance problem by making the warehouse smaller?Gotcha

Yes, for cost-performance rather than raw latency. Snowflake bills per second by size, so a query that does not parallelise — a single-threaded UDF, a tiny lookup, a load of one small file — costs four times as much on a Large as on a Small and finishes at the same time. Downsizing those workloads is free money.

It is also the right answer when an oversized warehouse is encouraging people to run everything on it. Splitting one Large into two Smalls by workload can reduce both cost and queuing, because each workload gets its own cache and cannot block the other.

How would you find the ten most expensive queries in the account this month, and what would you do with the list?SQL

Credits are not on QUERY_HISTORY directly, so I approximate by execution time weighted by warehouse size, or use the QUERY_ATTRIBUTION_HISTORY view where available. A workable first pass:

SELECT query_hash,
       ANY_VALUE(query_text)              AS sample_sql,
       COUNT(*)                            AS runs,
       SUM(total_elapsed_time)/1000/60     AS total_minutes,
       AVG(partitions_scanned)             AS avg_parts_scanned,
       SUM(bytes_spilled_to_remote_storage) AS remote_spill
FROM   snowflake.account_usage.query_history
WHERE  start_time >= DATE_TRUNC('month', CURRENT_DATE())
  AND  warehouse_size IS NOT NULL
GROUP  BY query_hash
ORDER  BY total_minutes DESC
LIMIT  10;

Grouping by query_hash rather than query_id is the important part: the biggest cost is usually a cheap query run 40,000 times, not one monster. Then I triage the list into "fix the SQL", "cache or materialise it", and "does this need to run at all", in that order.

Round 2 — Cost, credits and the bill

Cost questions are where interviewers separate engineers from administrators. Know what is and is not chargeable.

Finance says the Snowflake bill tripled last month. You have one day to explain it. What do you do?Flagship

I would answer the question in three layers, because the bill has three components and they behave completely differently.

Split the total first. Compute, storage and data transfer, from ACCOUNT_USAGE.METERING_DAILY_HISTORY. That single query usually ends the investigation, because a tripled bill is nearly always compute and the service type column tells you which kind.

SELECT usage_date, service_type, SUM(credits_used) AS credits
FROM   snowflake.account_usage.metering_daily_history
WHERE  usage_date >= DATEADD(day, -60, CURRENT_DATE())
GROUP  BY 1, 2
ORDER  BY 1, 3 DESC;

Attribute the compute. WAREHOUSE_METERING_HISTORY gives credits per warehouse per hour, which localises it to a team if warehouses are named by team. Serverless features bill separately — Snowpipe, tasks, automatic clustering, materialized view maintenance, search optimization, replication and Cortex each have their own *_HISTORY view, and they are the usual culprits behind a mysterious increase because nobody is watching them.

Explain the delta, not the total. Compare the same query for the previous month and report the difference by warehouse and service type. Typical findings: someone set AUTO_SUSPEND to zero or removed it, a multi-cluster warehouse had MIN_CLUSTER_COUNT raised above one so it never scales to nothing, a clustering key was added to a high-churn table, a task started failing and retrying, a dev warehouse was resized to X-Large and left there, or a new Cortex or Document AI workload went live.

Then the guardrails: resource monitors with notify-and-suspend thresholds per warehouse, budgets for account-level spend, tags on warehouses and databases so attribution is automatic next time, and a weekly alert on credit growth. I would also be honest that resource monitors do not cap serverless, storage or Cortex spend — budgets and alerts are what cover those.

What does Snowflake actually charge for?Fundamentals

Three things. Compute — virtual warehouse credits billed per second with a 60-second minimum each time a warehouse resumes, plus serverless compute for Snowpipe, tasks, reclustering, materialized view maintenance, search optimization, replication and Cortex. Storage — a flat rate per terabyte per month on compressed data, covering active bytes plus Time Travel plus Fail-safe plus stage files. Data transfer — egress when data leaves the region or cloud.

The nuance interviewers listen for: cloud services compute is only charged when it exceeds 10% of the daily warehouse credits, which is why metadata-only queries such as SELECT COUNT(*) or a DESCRIBE are usually free, and why result-cache hits cost nothing.

A resource monitor is set to suspend at 100% but the account still overspent. How?Gotcha

Resource monitors only govern virtual warehouse credits. They do not cover serverless compute (Snowpipe, tasks, automatic clustering, materialized views, search optimization, replication), storage, data transfer, or Cortex usage. If the overspend came from a runaway Snowpipe or a clustering key on a churning table, the monitor never saw it.

The other two explanations are that the monitor was created but never assigned to any warehouse, or that the action was NOTIFY rather than SUSPEND. Also worth saying: SUSPEND lets running queries finish, only SUSPEND_IMMEDIATE kills them, and monitors are evaluated on an interval so a very fast burn can overshoot. For the categories monitors miss, budgets and alerts are the right tool.

Storage costs are climbing but nobody is loading new data. Explain it.Scenario

Storage is active bytes plus Time Travel plus Fail-safe plus staged files, so several things can grow with no new data arriving. The usual causes are a table with a long DATA_RETENTION_TIME_IN_DAYS being fully rewritten every night, which keeps a complete historical copy per day; internal stages full of files nobody removed after loading; dropped tables still sitting in Time Travel and then Fail-safe for seven more days; and clones whose parents have since been rewritten, so the shared micro-partitions are no longer shared.

I would query TABLE_STORAGE_METRICS and compare active_bytes, time_travel_bytes, failsafe_bytes and retained_for_clone_bytes per table. The fixes follow directly: switch churn-heavy staging tables to transient (no Fail-safe, one day of Time Travel maximum), shorten retention where it is not needed, use PURGE = TRUE or REMOVE on stages, and use TRUNCATE or INSERT OVERWRITE rather than drop-and-recreate.

How would you cut 30% off a Snowflake bill without breaking anything?Cost

I would go after idle and waste before touching workloads. In rough order of effort-to-saving: set AUTO_SUSPEND to 60 seconds on everything except BI warehouses that benefit from a warm cache; find warehouses that are oversized for what they run and drop a size; consolidate the long tail of near-idle warehouses; convert staging and scratch tables to transient and cut Time Travel on them to zero or one day; delete abandoned clones and stage files; and turn off clustering, search optimization or materialized views that are no longer earning their maintenance cost.

Only then do I look at the top-10 queries by total runtime and rewrite the worst offenders. Throughout, I would tag warehouses and databases by team so the saving is attributable, and I would put a budget in place so the gain does not quietly erode.

A dev left an X-Large warehouse running over a long weekend. Whose fault is it and what changes?Judgement

It is a systems failure, not a person failure, and saying that is part of the answer. Any warehouse that a human can create should have AUTO_SUSPEND set by policy — Snowflake will happily let you create one with auto-suspend disabled, and that is the actual bug.

Concretely: set AUTO_SUSPEND and STATEMENT_TIMEOUT_IN_SECONDS defaults, attach a resource monitor to the dev warehouse with a monthly quota and a suspend action, restrict CREATE WAREHOUSE to a small set of roles, and cap the size developers can create by provisioning warehouses centrally rather than granting the privilege. Then an alert on any warehouse running more than N hours continuously.

Why might a query that scans one row still cost a meaningful amount?Gotcha

Because you pay for warehouse time, not rows. If the warehouse was suspended, resuming it triggers the 60-second minimum billing, so a one-row lookup on an X-Large costs a full minute of X-Large credits. Run a hundred of those a day on an oversized warehouse and it adds up.

The fix is to route small lookups to a small warehouse, or to a serverless path where possible, and to keep a modest warehouse warm rather than resuming a large one repeatedly.

Your manager asks for per-team cost attribution. How do you deliver it?Scenario

Object tags plus ACCOUNT_USAGE. I would define a cost_center tag and apply it to warehouses, databases and roles, then join TAG_REFERENCES to WAREHOUSE_METERING_HISTORY to allocate compute, and to TABLE_STORAGE_METRICS for storage.

The honest caveat, which is the part interviewers want: tagging is not retrospective, so this only works from the day the tags go on. If teams share warehouses, warehouse-level attribution is a guess — the cleaner design is one warehouse per team per workload type, named consistently, which makes attribution a naming convention rather than a project. Where available, QUERY_ATTRIBUTION_HISTORY gives per-query credit attribution and can split a shared warehouse by user or role.

Is it cheaper to run a query on an X-Small for 60 minutes or a Large for 8 minutes?Cost

Do the arithmetic out loud: X-Small is 1 credit per hour, so 60 minutes is 1 credit. Large is 8 credits per hour, so 8 minutes is about 1.07 credits. Near enough identical — which is the whole point of Snowflake's pricing model. If a workload parallelises perfectly, size is cost-neutral and you should pick the larger warehouse for the better user experience.

The interesting part is where it breaks. If the work does not parallelise, the Large finishes in 40 minutes rather than 8 and costs five times as much. If the query is spilling to remote storage, the Large may finish in under 8 minutes and cost less. So the real answer is: measure it on both, and remember the 60-second minimum makes very short queries disproportionately expensive on big warehouses.

Round 3 — Loading failures

Everything here has a specific view behind it. Name the view.

The nightly load reported success but the table has no new rows. What happened?Flagship

Almost certainly load metadata. COPY INTO records every file it has already ingested into a table and skips it on subsequent runs, and that metadata is kept for 64 days. If the upstream system rewrote the same filenames with new content, or the job re-staged yesterday's files, Snowflake considers them loaded and returns a successful COPY with zero rows.

I would confirm rather than assume, using COPY_HISTORY:

SELECT file_name, status, row_count, row_parsed,
       first_error_message, last_load_time
FROM   TABLE(information_schema.copy_history(
               table_name  => 'SALES.PUBLIC.ORDERS',
               start_time  => DATEADD(hour, -24, CURRENT_TIMESTAMP())));

A status of LOAD_SKIPPED confirms it. The tactical fix is FORCE = TRUE, but that risks duplicates, so the real fix is to make filenames unique per batch (a timestamp or run id in the path) and to load from a dated prefix rather than a flat folder. The other candidates worth mentioning: the COPY pointed at an empty prefix because a date variable resolved wrongly, or a pattern regex that matched nothing.

A COPY INTO fails on row 4,000,000 of a 5-million-row file. What are the options?Scenario

The behaviour depends on ON_ERROR, which defaults to ABORT_STATEMENT for bulk loads — so the whole statement rolls back and nothing lands. The options are CONTINUE (load the good rows, skip the bad), SKIP_FILE (abandon that file, keep the others), SKIP_FILE_<n> or SKIP_FILE_<n>% (tolerate a threshold), and ABORT_STATEMENT.

Which one I choose depends on the data contract. For financial data I keep ABORT_STATEMENT and fix the source, because a partial load is worse than no load. For clickstream I use CONTINUE and route rejects somewhere visible. Either way I would first run VALIDATION_MODE = RETURN_ERRORS to see all the bad rows without loading anything, and I would say that a 5-million-row single file is itself the problem — splitting into 100–250 MB compressed files parallelises the load and limits the blast radius of one bad file.

Snowpipe silently stopped loading files three days ago. How do you debug it?Diagnosis

Start with the pipe itself: SELECT SYSTEM$PIPE_STATUS('my_pipe') returns the execution state, pending file count and, crucially, lastReceivedMessageTimestamp and lastForwardedMessageTimestamp. If messages stopped arriving, the problem is the cloud notification, not Snowflake — an expired SQS subscription, a changed bucket event configuration, or IAM permissions revoked on the storage integration.

If messages are arriving but nothing loads, the pipe may be paused (someone ran ALTER PIPE ... SET PIPE_EXECUTION_PAUSED = TRUE, or ownership transferred, which pauses it), or every file is erroring. Snowpipe defaults to ON_ERROR = SKIP_FILE, so bad files disappear quietly — that is exactly how a pipe "silently" stops delivering data. COPY_HISTORY and VALIDATE_PIPE_LOAD show those failures. For recovery I would use ALTER PIPE ... REFRESH to pick up files staged while it was broken, remembering it only looks back seven days.

Duplicate rows appeared in a target table after a load retry. How do you prevent recurrence?Scenario

First establish which retry did it — COPY_HISTORY plus the metadata columns will usually show the same filename loaded twice, meaning someone used FORCE = TRUE or the file was re-staged under a new name. Then dedupe with a window function into a new table and swap.

Prevention is a design change, not a setting. I would load into a staging table and MERGE into the target on a natural or hash key so retries are idempotent, keep filenames unique and immutable, and add a post-load count reconciliation between source and target that fails the pipeline loudly. If the source genuinely has no key, a hash of the row plus the file name works.

A CSV loads fine into a VARCHAR staging table but fails going into the typed table. How do you find the offending rows?SQL

That is the classic reason for a two-step load, and the answer is to test each cast with the TRY_ family, which returns NULL instead of raising:

SELECT *
FROM   stg_orders
WHERE  TRY_TO_NUMBER(amount)      IS NULL AND amount      IS NOT NULL
   OR  TRY_TO_DATE(order_date, 'YYYY-MM-DD') IS NULL AND order_date IS NOT NULL;

Typical culprits are thousands separators, currency symbols, European decimal commas, empty strings that should be NULL (fix with EMPTY_FIELD_AS_NULL and NULL_IF), and dates in a different format from the file format's DATE_FORMAT. If I were loading directly, VALIDATION_MODE = RETURN_ALL_ERRORS gives the same information without a staging table.

You need to load 10 TB from S3 as fast as possible. How do you approach it?Scenario

File layout matters more than warehouse size. I want many roughly equal files of 100–250 MB compressed, because each thread takes one file and one huge file cannot be parallelised. Then I size the warehouse to the file count — each node handles eight files concurrently, so throwing a 4X-Large at 20 files wastes most of it.

Beyond that: use a storage integration rather than inline credentials, keep the warehouse in the same region as the bucket to avoid egress and latency, load into a transient staging table to avoid Fail-safe on data you are about to transform, and consider several parallel COPY statements against different prefixes on separate warehouses. I would validate on a 1% sample first with VALIDATION_MODE rather than discover a format problem 9 TB in.

The business wants data available within seconds of it being produced. What do you propose?Design

First I would challenge the requirement, politely — "seconds" often means "not tomorrow", and micro-batching every minute is dramatically simpler and cheaper than true streaming. If it genuinely needs seconds, Snowpipe is not the answer either: it is file-driven and typically lands data in around a minute.

The right tool is Snowpipe Streaming, where a client writes rows into a channel through the SDK or the Kafka connector in streaming mode, with no files and no stage. It gives second-level latency and ordered delivery within a channel via offset tokens. I would pair it with dynamic tables for downstream transformation so the whole chain has a declared freshness target rather than a hand-built task DAG.

An external table's queries return stale data. Why?Gotcha

External tables read metadata about the files in the stage, and that metadata has to be refreshed. If AUTO_REFRESH is off, or the notification integration behind it has broken, new files in the bucket are invisible until someone runs ALTER EXTERNAL TABLE ... REFRESH.

The other possibility is partition pruning on a partitioned external table: if the partition expression is derived from metadata$filename and the upstream system changed its path convention, new files fall outside every partition and are effectively ignored.

Round 4 — Pipelines and orchestration

Streams, tasks, dynamic tables and the failure modes nobody documents.

A stream that has fed a task reliably for months is suddenly empty, and the task is not firing. What is wrong?Flagship

Two different failures look identical from the outside, so I would check both.

The stream may be stale. A stream's offset must stay inside the source table's Time Travel retention window. If the table has one day of retention and nothing consumed the stream for a day and a half, the offset falls off the end and the stream becomes permanently stale — SELECT SYSTEM$STREAM_GET_TABLE_TIMESTAMP and the STALE and STALE_AFTER columns in SHOW STREAMS confirm it. Recovery is to recreate the stream and backfill the gap manually, which is why this is a genuine incident and not a quick fix.

Or the task is suspended. Tasks auto-suspend after a configured number of consecutive failures, and a task whose owner role lost a privilege will fail every run. TASK_HISTORY shows the state and the error. Also remember that a resumed child task does nothing unless the root is resumed, and a task gated on SYSTEM$STREAM_HAS_DATA reports success while skipping — so "the task ran fine" and "nothing happened" are compatible.

Prevention: set the source table's retention longer than the maximum tolerable consumer outage, monitor stream staleness proactively rather than discovering it, and alert on task failures instead of relying on someone noticing missing rows.

How do you make a Snowflake pipeline idempotent?Design

Every step has to be safe to run twice. In practice: land raw files with unique immutable names and rely on load metadata rather than FORCE; transform into staging tables that are fully rebuilt each run with INSERT OVERWRITE or CREATE OR REPLACE; apply changes to the target with MERGE on a stable key rather than INSERT; and make deletes soft where possible.

The subtle part is streams: reading a stream inside a transaction advances its offset when the transaction commits, so if the downstream write fails after the read, you lose the changes. Consuming the stream and writing the target in the same transaction is what makes the pattern exactly-once.

When would you choose a dynamic table over a stream plus a task?Comparison

Dynamic tables when I can express the result as a query and I care about freshness rather than execution order. I declare a TARGET_LAG and Snowflake works out the refresh schedule, the incremental logic and the dependency graph between chained dynamic tables. Far less code and far fewer failure modes.

Streams plus tasks when I need imperative control — calling a stored procedure, doing something non-deterministic, hitting an external function, branching, or applying a complex merge that cannot be written as a single declarative query. I would also stay with tasks where a construct in my query forces a dynamic table into full refresh, which quietly turns a cheap incremental pipeline into an expensive rebuild.

A task DAG has one slow branch holding everything up. How do you restructure it?Scenario

First measure with TASK_HISTORY to find where the time actually goes, because the perceived bottleneck is often a child waiting on a parent that finished long ago. Then the structural options: split independent branches so they no longer share a root, give the slow branch its own warehouse so it stops competing, or convert it to a serverless task and let Snowflake size it.

If the slow step is genuinely slow SQL, that becomes a performance problem and I would profile it. If it is slow because it processes everything each run, converting it to a stream-driven incremental step or a dynamic table is the real fix. I would also check the schedule is not overlapping itself — a task that takes longer than its interval skips runs, which looks like a stall.

How do you get alerted when a pipeline breaks, without a third-party tool?Ops

Snowflake alerts plus a notification integration. An alert runs a condition query on a schedule and fires an action when it returns rows, and SYSTEM$SEND_EMAIL delivers to verified addresses. So I write a condition over TASK_HISTORY for failures in the last hour, or over COPY_HISTORY for load errors, or a freshness check that the target table's max timestamp is within tolerance.

I would add that freshness and row-count checks catch more real incidents than error alerts do, because the worst pipeline failures succeed technically and deliver nothing. Data metric functions give a declarative way to attach those checks to the table itself.

Two tasks write to the same table and you are seeing lost updates. What is happening?Gotcha

Snowflake gives you ACID transactions, but concurrent MERGE or UPDATE statements against overlapping rows serialise at the partition level and the later writer can overwrite the earlier one's view of the data — a classic read-modify-write race, not a Snowflake bug.

The fixes are to serialise the writers (chain them in one DAG rather than scheduling both), to partition the work so each writer owns a disjoint key range, or to make the merge condition idempotent and include a version or timestamp so an older update cannot overwrite a newer one.

How would you implement slowly changing dimension type 2 in Snowflake?Design

A stream on the source table to capture changes, then a MERGE that closes the current row and inserts a new one. The merge sets valid_to and is_current = FALSE on the matched open row, and a second insert writes the new version with valid_from = CURRENT_TIMESTAMP() and is_current = TRUE. Because MERGE cannot both update and insert the same target row in one pass, the standard trick is to union the source with itself so the change appears twice, once for the close and once for the insert.

I would compare row hashes rather than column-by-column so that no-op updates do not create versions, and drive the whole thing from a task gated on SYSTEM$STREAM_HAS_DATA. Worth saying that Time Travel is not a substitute for SCD2 — it is an operational safety net with a short window, not a modelling technique.

Round 5 — Recovery and disaster

The "someone dropped the production table" family. Stay calm and know the retention windows.

Someone ran an UPDATE without a WHERE clause on a production table 20 minutes ago. What do you do?Flagship

Contain first. Stop anything else writing to the table and find the offending statement's query_id in Query History. That id is what makes the recovery exact rather than approximate.

Verify before restoring. Time Travel lets me read the table as it was immediately before that statement, so I check the data is what I expect before I overwrite anything:

SELECT COUNT(*) FROM orders BEFORE (STATEMENT => '01b2c3d4-...');

Restore. The safest route is to clone the pre-damage state to a new table, reconcile it, then swap:

CREATE TABLE orders_restored CLONE orders BEFORE (STATEMENT => '01b2c3d4-...');
-- reconcile, then:
ALTER TABLE orders        SWAP WITH orders_restored;

Cloning is zero-copy so this costs almost nothing and, unlike an in-place overwrite, it leaves the damaged version available if the reconciliation surfaces a surprise. If writes continued after the bad update, I cannot simply revert — I have to merge the good post-incident changes back in, which is why containment comes first.

Prevent. Revoke direct DML on production tables from humans, require changes through reviewed code, and consider a transaction-scoped workflow where destructive statements run inside an explicit BEGIN with a verification query before COMMIT.

A table was dropped nine days ago and Time Travel is one day. Can you get it back?Gotcha

Not by myself. Once Time Travel expires, a permanent table's data enters Fail-safe for seven days, and Fail-safe is not user-accessible — only Snowflake Support can attempt recovery, on a best-effort basis measured in hours or days. At nine days, even Fail-safe has passed for a table with one day of retention (1 + 7 = 8), so the honest answer is that the data is gone and the conversation moves to what backup should have existed.

The follow-up worth volunteering: transient and temporary tables have no Fail-safe at all, so for them the Time Travel window is the entire safety net. And if the table were still inside its window, UNDROP TABLE would restore it — unless someone had created a new table with the same name, in which case you must rename the new one first because UNDROP restores to the original name.

How would you design backup and recovery for a Snowflake warehouse holding regulated data?Design

I would layer it. Time Travel set deliberately per table — up to 90 days on Enterprise for the tables that matter, one day for staging — and MIN_DATA_RETENTION_TIME_IN_DAYS at account level so nobody can lower it below policy. Fail-safe underneath that for permanent tables, understood as Snowflake's safety net rather than my backup.

On top: periodic zero-copy clones as named restore points (cheap, instant, and they only cost storage as the parent diverges), and database replication to a secondary region with failover groups for regional outage. For true archival I would unload to cloud storage in an open format on a retention schedule, because that is the only copy that survives losing the Snowflake account itself.

Then the part people forget: rehearse the restore. A recovery plan nobody has executed is a hypothesis.

Your primary region has an outage. Walk me through failover.Scenario

This only works if it was set up in advance. With Business Critical, I would have replication and failover groups configured to a secondary account in another region, replicating databases plus account objects such as users, roles, warehouses and integrations — replicating data alone leaves you with a database nobody can log into.

Failover itself is ALTER FAILOVER GROUP ... PRIMARY in the secondary account, which promotes it. The operational reality is what I would emphasise: client connection strings have to point at the new account URL, which is why client redirect with a connection object matters; and the recovery point is bounded by the replication schedule, so anything written since the last refresh is lost. Afterwards, failing back is a deliberate exercise, not automatic.

A developer cloned production to test last month and storage has quietly grown. Explain the mechanism.Cost

A clone is zero-copy at creation: it references the same micro-partitions and adds no storage. Cost appears as the two diverge. Every change to either the clone or the original writes new micro-partitions, and the old ones must be retained as long as some object still references them.

So a clone of a table that is fully rewritten nightly holds onto a complete extra copy within days. TABLE_STORAGE_METRICS exposes this as retained_for_clone_bytes. The fix is lifecycle policy: name clones with an owner and a date, and drop them on a schedule.

How do you recover a single row deleted three hours ago from a 2 TB table without disturbing anything else?SQL

Read the past and insert just that row back — no restore required:

INSERT INTO orders
SELECT *
FROM   orders BEFORE (OFFSET => -60*60*3)
WHERE  order_id = 987654
  AND  order_id NOT IN (SELECT order_id FROM orders);

Time Travel queries read historical micro-partitions, so this is cheap and touches nothing else. I would run the SELECT alone first to confirm the row is the one I want, and use BEFORE (STATEMENT => ...) instead of a time offset if I can find the delete in Query History, since that is exact rather than approximate.

What is the difference between UNDROP, Time Travel and Fail-safe, in one answer?Fundamentals

They are three points on the same timeline. Time Travel is the user-accessible window — 0 to 90 days depending on edition and table type — during which you can query, clone or restore historical data yourself. UNDROP is one operation within that window, specifically for objects that were dropped rather than modified. Fail-safe is the seven days after Time Travel expires, available only for permanent objects, recoverable only by Snowflake Support, and not something you can plan around.

The examinable details: Standard edition caps Time Travel at one day, transient and temporary tables have a maximum of one day and no Fail-safe, and you pay storage for all three.

Round 6 — Security, access and governance

Answer these as though the auditor is in the room, because sometimes they are.

An analyst can see a table they should not. How do you investigate and remediate?Flagship

Establish the path first. Privileges in Snowflake are inherited up the role hierarchy, so the grant is rarely on the role they used. I would work out every role they can activate and every privilege each inherits:

SHOW GRANTS TO USER "analyst_name";
SHOW GRANTS TO ROLE analyst_role;
SELECT * FROM snowflake.account_usage.grants_to_roles
WHERE  granted_on = 'TABLE' AND name = 'SALARIES' AND deleted_on IS NULL;

The usual causes are a role granted to a role granted to PUBLIC, a future grant on the schema that quietly covered new tables, ownership left with a role that everyone inherits, or secondary roles letting them combine privileges from a role they did not explicitly assume.

Then establish impact. ACCESS_HISTORY tells me whether they actually read it and which columns, which is the question compliance will ask. QUERY_HISTORY gives the statements.

Remediate and prevent. Revoke the specific grant, not the role, unless the role itself is wrong. Then fix the structural cause: never grant on PUBLIC, use functional roles built from access roles so grants are auditable, review future grants when creating schemas, and put a masking policy on the sensitive columns so that even an over-broad grant does not expose values.

Design an access model for a company with three teams and a regulated data domain.Design

I would use the access-role and functional-role pattern. For each schema, create access roles carrying a single level of privilege — SALES_RAW_R, SALES_RAW_RW — and grant object privileges only to those. Then create functional roles that match job titles — ANALYST_SALES, ENGINEER_PLATFORM — and build them by granting the access roles they need. Users only ever get functional roles.

That separation means adding a new dataset is one grant to an access role, and onboarding a person is one grant to a functional role. Object ownership sits with SYSADMIN or a role beneath it so nothing is orphaned; USERADMIN manages users and roles; SECURITYADMIN manages grants; ACCOUNTADMIN is used by two named people with MFA and nothing else.

For the regulated domain I would add masking policies on the sensitive columns keyed off CURRENT_ROLE(), row access policies driven by a mapping table for territory or entity restrictions, tags to mark the columns as PII so they can be discovered and reported, and ACCESS_HISTORY-based reporting for the auditor.

You are locked out after applying a network policy. What now?Gotcha

Snowflake blocks you from activating a network policy that excludes your own current IP, which prevents the most obvious version of this. But you can still lock out everyone else — for example by allow-listing only the office range when half the company is remote, or by having your own IP change afterwards.

If it happens, another ACCOUNTADMIN connecting from a permitted address can alter or unset the policy. If nobody can get in, it is a Snowflake Support ticket. Prevention is the real answer: apply new policies to a single test user first, keep a break-glass ACCOUNTADMIN whose access path is separate, and stage the rollout rather than applying at account level in one go.

An auditor asks who accessed customer PII in the last six months. What do you give them?Governance

SNOWFLAKE.ACCOUNT_USAGE.ACCESS_HISTORY, which records the base objects and columns each query touched, including indirect access through views. That last point is what makes it the right view rather than QUERY_HISTORY: a query against a view that exposes a PII column shows up as access to the underlying column.

I would join it to tag references so the report is "who read anything tagged PII" rather than a hand-maintained list of columns, and note the constraints honestly: ACCESS_HISTORY requires Enterprise edition, retains a year, and lags by up to about three hours. If the account is younger than the audit window or the feature was enabled late, I say so rather than producing a report that looks complete and is not.

How do you give a contractor access to production data for two weeks?Scenario

The design goal is that access expires whether or not anyone remembers. I would create a dedicated functional role scoped to exactly the objects needed, ideally over secure views rather than base tables, apply masking policies so PII is redacted for that role regardless of what they query, and give them their own user with key-pair or SSO authentication and MFA rather than a shared account.

Snowflake does not expire grants natively, so I would implement the expiry: a scheduled task that revokes the role and disables the user on the end date, plus a resource monitor on their dedicated warehouse so the engagement has a cost ceiling. I would also record the justification, because the auditor will ask why the grant existed rather than whether it was removed.

Marketing wants to analyse customer emails but must not see the addresses. How?Governance

A masking policy on the column, applied conditionally by role:

CREATE MASKING POLICY email_mask AS (val STRING) RETURNS STRING ->
  CASE WHEN CURRENT_ROLE() IN ('PII_READER') THEN val
       ELSE SHA2(val)
  END;

Hashing rather than blanking is deliberate: marketing can still join, group and count distinct customers without ever seeing an address. If they need the domain for segmentation, mask to '***@' || SPLIT_PART(val,'@',2) instead. Policies are attached to the column, so they apply to every view and every query path, which is what makes this stronger than building a "safe" view and hoping nobody queries the base table.

Why should service accounts not use passwords, and what do you use instead?Security

Passwords for service accounts end up in configuration files, cannot take MFA, are rarely rotated, and are shared between people. Key-pair authentication replaces them: the private key lives in the client's secret store, Snowflake holds only the public key, and RSA_PUBLIC_KEY_2 allows rotation with no downtime — set the new key as the second key, roll clients over, then promote it.

I would pair that with a network policy restricting the service user to known egress addresses, a role scoped to precisely what the job needs, and an authentication policy that forbids password login for that user. OAuth is the alternative where the client supports it.

How would you detect that someone is exfiltrating data?Security

The signals are all in ACCOUNT_USAGE. Large or unusual COPY INTO <location> unloads, especially to an external stage created recently; GET activity against internal stages; queries returning very large result sets to a client; a user's rows_produced jumping far above their baseline; logins from new IP ranges or countries in LOGIN_HISTORY; and new shares or listings appearing.

I would build baseline-versus-today alerts rather than fixed thresholds, and pair detection with prevention: restrict who can create external stages and integrations, use STORAGE_ALLOWED_LOCATIONS so unloads can only go to approved buckets, enforce network policies, and switch on the Trust Center scanners for account-level misconfiguration.

Round 7 — Sharing and collaboration

Data sharing questions are really questions about who pays and what leaks.

A partner needs daily access to a slice of your data. They are not on Snowflake. What do you propose?Flagship

My first choice is still secure data sharing, via a reader account. I create the share over a secure view that exposes only the agreed rows and columns, provision a reader account for them, and they query it in Snowsight with no infrastructure of their own. No files, no scheduled extract, no stale copy, and revocation is immediate.

The trade-off I would raise unprompted is cost: I own the reader account, so I pay for their compute, and I need a resource monitor on it before I hand over the URL. If their volume is unpredictable or they want the data inside their own systems, the alternative is a scheduled unload to a cloud bucket they own, which is cheaper for me but reintroduces copies, latency and the question of how I revoke access to data already delivered.

If they are willing to get their own Snowflake account, that is strictly better than either — a direct share costs me nothing but the storage I already pay for.

Who pays for what in a data share?Cost

The provider pays for storage, because there is only one copy of the data and it belongs to them. The consumer pays for the compute they use to query it, using their own warehouses. Nothing is copied, which is why a share is instant regardless of data volume and why the consumer sees provider updates immediately.

The exception is a reader account: it belongs to the provider, so the provider pays the consumer's compute too. That is the detail interviewers probe, and it is the reason reader accounts need a resource monitor from day one.

You shared a view and the consumer gets an error. Why?Gotcha

Standard views cannot be shared — only secure views, secure materialized views and secure UDFs. Beyond the permission model, the reason is information leakage: a standard view's definition is visible and the query optimiser can push predicates down in ways that let a consumer infer rows they cannot see. CREATE SECURE VIEW hides the definition and disables those optimisations.

The other common cause is that the share grants access to the view but not USAGE on the database and schema containing it, or the view references an object in a database that is not part of the share — a share cannot cross database boundaries.

The consumer is in a different cloud region. Does sharing still work?Scenario

Not directly. Secure data sharing is metadata pointing at storage, so both accounts must be in the same region on the same cloud provider. To share across regions or clouds you replicate the database to an account in the consumer's region and share from there.

That changes the economics materially, which is the point of the question: replication means a real second copy, so you pay storage twice plus replication compute plus egress, and the consumer sees data as fresh as your last refresh rather than live. For a Marketplace listing, cross-region reach is handled by publishing to auto-fulfilment regions, which does the same replication under the covers.

Two companies want to match customer overlap without either seeing the other's list. What do you suggest?Design

A data clean room. Both parties share data into an environment where only approved, pre-agreed queries can run, and only aggregate results above a minimum threshold are returned — so each side learns the size of the overlap without either seeing the other's rows.

Under the hood it is built from the primitives already covered: secure sharing so no data moves, secure views and row access policies to constrain what can be selected, and stored procedures or approved query templates so the consumer cannot write arbitrary SQL. Snowflake packages this so you do not have to hand-roll it, but knowing what it is made of is what the question is testing.

Round 8 — Architecture and design decisions

Open-ended by nature. State your assumptions, then commit to a recommendation.

Design the warehouse topology for a company with ETL, BI and data science workloads.Flagship

Separate warehouses per workload, because they have genuinely different shapes and the whole point of Snowflake's architecture is that separating them costs nothing extra.

  • ETL — a single-cluster warehouse sized to the batch, AUTO_SUSPEND at 60 seconds because there is no interactive user to keep the cache warm for. Size is driven by whether the loads spill, not by data volume.
  • BI — a multi-cluster auto-scale warehouse with min 1 and max 3, standard scaling policy, and a longer AUTO_SUSPEND (5–10 minutes) so the warehouse cache survives between dashboard interactions. Concurrency is the constraint here, not size.
  • Data science — its own warehouse so exploratory queries cannot starve the dashboards, likely Snowpark-optimized if there is real ML work, with a resource monitor because ad-hoc usage is the least predictable.
  • Ad-hoc / admin — a small warehouse for everyone else, so no one has a reason to borrow another team's.

Then the governance layer: consistent naming that encodes team and workload so cost attribution is free, resource monitors on every warehouse, statement timeouts set at the warehouse level, and a rule that new warehouses are provisioned centrally rather than created ad hoc.

How would you structure databases and schemas for a medallion architecture?Design

I would put the layers in separate databases rather than separate schemas — RAW, CURATED, ANALYTICS — because database is the boundary for cloning, replication, sharing and most grants, and you want those operations to be layer-aligned. Inside each, schemas by source system in raw and by business domain in the upper layers.

Table types follow the layer: raw landing tables transient with short Time Travel (the files still exist, so Fail-safe is paying twice for the same insurance), curated and analytics permanent with meaningful retention. Access follows too: engineers write to raw and curated, analysts read analytics only, and nobody queries raw directly in production.

I would also make dev and prod separate databases in the same account with identical schema names, so promoting code is a database swap rather than a rewrite, and use zero-copy clones to create dev environments from prod on demand.

Should you model in star schema, or load everything wide and denormalised?Judgement

Snowflake handles joins well, so the old "denormalise because joins are expensive" argument is much weaker than it was on older platforms — and micro-partition pruning works better on narrower tables. I would default to a star schema for the analytics layer because it is comprehensible, maintainable and what BI tools expect.

Where I would denormalise is at the serving edge: a wide, pre-joined table behind a heavily used dashboard, maintained as a dynamic table so it stays fresh without hand-written pipeline code. That gives the performance of denormalisation without giving up the modelled layer underneath it. The trade-off I would name is that every denormalised copy is another thing that can drift.

When would you use a transient table, and what is the risk?Cost

Whenever the data can be regenerated from something else: raw landing tables where the source files still exist, intermediate transformation steps, and anything rebuilt on every run. Transient tables have no Fail-safe and a Time Travel maximum of one day, which cuts storage cost substantially on high-churn tables.

The risk is exactly that missing safety net. If someone truncates a transient table and the upstream files have been purged, there is no Fail-safe and no Support ticket that recovers it. So the rule is: transient only where the regeneration path is real and tested, not where it is theoretical.

How do you manage dev, test and production environments in Snowflake?Design

Two defensible patterns, and I would pick based on the regulatory position. Separate accounts per environment give the hardest isolation, independent resource monitors and no chance of a dev query touching prod, at the cost of needing replication or shares to move data between them. Separate databases in one account are simpler and let you clone prod to dev instantly, but isolation is only as strong as your RBAC.

Either way: everything defined as code in Git, deployed through a pipeline rather than by hand, with Snowflake's Git integration and EXECUTE IMMEDIATE FROM if I want the repository visible from inside Snowflake. Zero-copy clones give each developer a realistic dataset in seconds, and masking policies mean cloned production data in dev is not a data-protection incident.

Snowflake or a lakehouse on open table formats? Argue both sides.Judgement

The honest answer is that the distinction has narrowed. Snowflake's case is operational simplicity — no clusters to tune, strong governance, mature RBAC, sharing and Time Travel — and total cost of ownership that includes the engineers you do not need to hire. The lakehouse case is open storage you control, no vendor lock-in on the data itself, and freedom to point any engine at the same files.

What makes this a good answer in 2026 is Iceberg tables, which let you have both: the data sits in your own object storage in an open format, while Snowflake provides the query engine and governance. I would frame the decision around who else needs to read the data, how much platform engineering capacity the organisation actually has, and whether the workload is predictable enough for reserved capacity to matter.

The business wants sub-second lookups on a Snowflake table for an application. Is that the right tool?Gotcha

Usually no, and saying so is the right answer. Snowflake is an analytical engine: micro-partitions, columnar storage and no traditional indexes mean single-row lookups carry overhead that an OLTP database does not have, and a suspended warehouse adds resume latency on top.

If it must be Snowflake, the tools are the search optimization service for selective point lookups, a warehouse kept warm, and the result cache for repeated identical queries. Hybrid tables (Unistore) are the purpose-built answer, giving row storage with primary keys and enforced constraints for operational access patterns alongside analytical tables. But if the requirement is thousands of single-row reads per second, a transactional database in front of Snowflake is the honest recommendation.

How would you decide between a materialized view, a dynamic table and a scheduled table rebuild?Comparison

I would decide on query complexity and freshness. A materialized view is the narrowest: single table, no joins, limited aggregations, maintained automatically and transparently substituted into queries by the optimiser. Use it when one expensive aggregate over one big table is hit constantly.

A dynamic table handles joins and multi-step chains, refreshes to a declared TARGET_LAG, and manages its own dependency graph. That is my default for derived datasets. A scheduled rebuild — a task running CREATE OR REPLACE or INSERT OVERWRITE — is what I fall back to when the logic is imperative, non-deterministic, or when a full refresh is genuinely cheaper than incremental maintenance on a table that turns over completely anyway.

Round 9 — Migration and modernisation

Common for consultancy and platform roles. They want a plan, not a tool list.

You are migrating an on-premises warehouse to Snowflake. How do you plan it?Flagship

I would sequence it so that value arrives before the migration finishes, because a big-bang cutover that slips is how these programmes die.

  1. Inventory and rank. Catalogue tables, jobs, reports and consumers, and rank by business value against migration difficulty. A surprising proportion of legacy objects have no consumers at all — finding those early is the cheapest win available.
  2. Land the data first. Bulk export to cloud storage, then COPY INTO raw tables. Keep types simple on landing and cast in a curated layer, so a type mismatch does not fail the extract.
  3. Convert the logic. Stored procedures become Snowflake Scripting or Snowpark; proprietary SQL dialect gets translated; anything relying on indexes, hints or explicit distribution keys gets deleted rather than translated, because those concepts do not exist here.
  4. Run in parallel and reconcile. Both systems produce the same reports for a period, with automated row-count and checksum comparison. This is the phase everyone under-budgets and the one that actually earns trust.
  5. Cut over by consumer, then decommission. Move reports in waves, and only switch off the legacy system when nothing has queried it for an agreed period.

Throughout: build the cost guardrails on day one, not at the end. Migrated workloads that ran on fixed on-premises hardware have no habit of caring about credits.

What legacy patterns do you have to unlearn when moving to Snowflake?Judgement

Indexes, statistics management, vacuum and analyse jobs, manual distribution and sort keys, and capacity planning for peak concurrency — none of them exist. Teams that carry those habits over end up building clustering keys everywhere as an index substitute and paying for it.

The bigger mental shift is that compute is elastic and disposable. On-premises you shape workloads to fit one fixed cluster; here you give each workload its own warehouse and size it independently. And you stop avoiding SELECT on large tables out of fear, but start caring about which columns you touch, because storage is columnar.

How do you validate that a migrated table matches the source?SQL

Three levels, cheapest first. Row counts per partition or load date; aggregate checksums per column (sums for numerics, COUNT(DISTINCT) and a hash aggregate for strings); and then a full row-level hash comparison for the tables that matter, using HASH_AGG or MD5 over a canonical concatenation of the columns.

The traps worth naming: floating-point sums differ across engines, so compare rounded; NULL handling and empty-string semantics differ, especially coming from Oracle; character set and trailing-whitespace differences produce hash mismatches on data that is logically identical; and time zones will bite you unless both sides are normalised to UTC first.

Stakeholders expect Snowflake to be cheaper than the system it replaced. It is not. What do you do?Scenario

I would separate three things before defending or conceding anything: has usage genuinely grown (people run more queries when queries are fast), is the workload badly configured, and was the original comparison sound (a fixed on-premises cost that ignored hardware refresh, licensing and staff is not a fair baseline).

Then I bring evidence — credits by warehouse and by team, the top workloads by cost, and the specific waste I can remove. In my experience the recoverable waste is idle warehouses, oversized warehouses, unnecessary Fail-safe on staging data, and a handful of queries running far more often than anyone realises. I would commit to a specific reduction target with a date rather than argue about the baseline.

How do you handle a source system that has no reliable change tracking?Design

If there is a trustworthy modified timestamp, incremental extraction on that with a safety overlap and an idempotent MERGE. If there is not, the options are full extracts compared against the previous snapshot using row hashes to derive the changes, or log-based change data capture from the source database's transaction log via a connector.

I would be explicit about the cost of each: full snapshots are simple and robust but expensive and slow as the table grows; hash comparison shifts the cost into Snowflake, which is usually the cheaper place for it; log-based CDC is the correct long-term answer but needs cooperation from whoever owns the source. Whichever I pick, deletes are the part that gets missed — a source that never tells you about deletions needs a periodic full reconciliation regardless.

Round 10 — Ways of working

Behavioural questions with a Snowflake angle. Answer with a real example if you have one.

Tell me about a time you broke production.Behavioural

Answer it straight, with a real incident, and spend most of the time on the response rather than the mistake. Structure: what you did, how it was detected, what you did in the first ten minutes, how it was resolved, and what changed permanently as a result.

What the interviewer is grading is whether you detected it yourself or a user did, whether you escalated early, and whether the fix was systemic. "I now always double-check" is a weak ending; "we added a pre-merge check that would have caught it, and a freshness alert that would have caught it in five minutes rather than four hours" is the ending they want. Never blame a colleague, and never claim you have not broken anything.

A stakeholder insists on a design you think is wrong. How do you handle it?Behavioural

Find out what they actually need before arguing about the design — very often the request is a solution they have already chosen for a problem they have not explained. Once the underlying requirement is on the table, quantify the trade-off in terms they care about: cost per month, hours of engineering, risk of the thing they are worried about.

If they still disagree and it is reversible, I would build their version, instrument it and let the data settle it. If it is irreversible or a compliance risk, I escalate — explicitly and in writing, without drama. Interviewers are checking that you can disagree without either capitulating or becoming an obstacle.

How do you document a data platform so people actually use the docs?Behavioural

Put the documentation where the work happens rather than in a separate wiki that rots. Column and table comments in Snowflake itself, visible in Snowsight and queryable from INFORMATION_SCHEMA; tags for classification; a data dictionary generated from metadata rather than maintained by hand.

Then a short, human-written layer for the things metadata cannot express: why the model looks like this, what the known caveats are, and who to ask. I would keep that in the same repository as the code so it is reviewed alongside changes, and I would treat "someone asked a question in Slack" as a documentation bug.

You inherit an undocumented Snowflake account. What are your first steps?Scenario

I would spend the first week reading metadata rather than changing anything. Where the money goes (WAREHOUSE_METERING_HISTORY, METERING_DAILY_HISTORY), what actually gets queried (QUERY_HISTORY grouped by table and by user, which usually reveals that a minority of objects carry all the traffic), who has access to what (GRANTS_TO_ROLES, and specifically anything granted to PUBLIC or with ACCOUNTADMIN attached), and what is scheduled (tasks, pipes, streams and their failure rates).

The immediate safe wins are usually auto-suspend settings, resource monitors where there are none, and dropping objects nothing has touched in a year — after checking, not before. Anything structural waits until I understand why it is the way it is.

How do you keep up with Snowflake's release pace?Career

Weekly and behavioural change release notes are the primary source, because behaviour change bundles are the ones that can break you and they have opt-in windows. Beyond that: the Snowflake community and blog for context, and a personal trial account to actually run new features rather than read about them.

The practical habit worth mentioning is testing behaviour change bundles in a non-production account during the opt-in period, so you find out about a breaking change on your schedule rather than Snowflake's.

What would you do in your first 90 days on our data platform team?Career

Days 1–30: learn and ship something small. Understand the domain and the account as above, fix a visible irritant so people see output early, and map who depends on what.

Days 31–60: address the biggest measurable problem, which in most accounts is either cost or a fragile pipeline, and put monitoring around it so the improvement is provable. Days 61–90: propose the structural change I have earned the right to propose — a governance model, an environment strategy, a migration off something fragile — with evidence gathered in the first two months.

The framing matters more than the specifics: learn, then a quick win, then a measured improvement, then a structural proposal. Candidates who arrive planning to rewrite everything in week two are the ones interviewers worry about.

Round 11 — Rapid fire

Short answers, asked fast, usually as a screen. If you cannot answer these in one breath, revise the section they came from.

What are the three layers of Snowflake's architecture?Rapid

Centralised storage, multi-cluster compute (virtual warehouses), and cloud services — the brain that handles authentication, metadata, optimisation, transactions and the result cache.

What is a micro-partition?Rapid

An immutable, columnar storage unit of 50–500 MB uncompressed, created automatically. Snowflake stores min/max and other metadata per partition, which is what enables pruning.

Scale up versus scale out?Rapid

Up is a bigger warehouse for one heavy query. Out is more clusters for many concurrent queries. Complexity versus concurrency.

Name the three caches.Rapid

Result cache (24 hours, cloud services, free), metadata cache (statistics, enables instant COUNT(*)), and warehouse local disk cache (lost on suspend).

What invalidates the result cache?Rapid

Changed underlying data, different SQL text (even whitespace), non-deterministic functions, and insufficient privileges on the referenced objects.

Permanent, transient or temporary — how do they differ?Rapid

Permanent: up to 90 days Time Travel plus Fail-safe. Transient: max 1 day, no Fail-safe. Temporary: max 1 day, no Fail-safe, and dies with the session.

What is zero-copy cloning?Rapid

A metadata-only copy that shares micro-partitions with its source. Instant, free at creation, and storage accrues only as the two diverge.

Snowpipe versus COPY INTO?Rapid

Snowpipe is event-driven, serverless, roughly one-minute latency, defaults to ON_ERROR = SKIP_FILE. COPY is batch, uses your warehouse, defaults to ABORT_STATEMENT.

What does a stream store?Rapid

An offset and change metadata, not the data itself. Standard, append-only and insert-only are the three types.

Ideal file size for loading?Rapid

Roughly 100–250 MB compressed, many files rather than one, so the load parallelises across threads.

What is the maximum size of a VARIANT value?Rapid

16 MB compressed per value.

Which role manages users, and which manages grants?Rapid

USERADMIN creates users and roles; SECURITYADMIN manages grants globally and inherits USERADMIN.

What privilege do people always forget to grant?Rapid

USAGE on the database and the schema. Without it, a table grant is invisible.

INFORMATION_SCHEMA versus ACCOUNT_USAGE?Rapid

INFORMATION_SCHEMA: real time, per database, 7–14 days, no dropped objects. ACCOUNT_USAGE: account-wide, about a year, includes dropped objects, lags 45 minutes to 3 hours.

Which edition do you need for materialized views?Rapid

Enterprise or higher. Same for multi-cluster warehouses, extended Time Travel beyond one day, search optimization and column-level security.

What does Tri-Secret Secure add?Rapid

A customer-managed key combined with Snowflake's key to form the account master key. Business Critical and above.

Can you share a standard view?Rapid

No. Secure views, secure materialized views and secure UDFs only.

What does a resource monitor not cover?Rapid

Serverless compute, storage, data transfer and Cortex. Warehouse credits only.

How is the exam scored?Rapid

100 questions in 115 minutes, scaled score out of 1000, 750 to pass.

Which warehouse sizes require Gen1?Rapid

5X-Large and 6X-Large. Standard Gen2 covers X-Small through 4X-Large.

Recap

  • Answer every scenario in four beats: contain, diagnose with named evidence, fix cheapest-first, then prevent.
  • Use INFORMATION_SCHEMA table functions for live incidents and ACCOUNT_USAGE for trends — never the other way round.
  • Queuing and slow execution look identical to a user and have opposite fixes.
  • Resource monitors cover warehouse credits only; budgets, tags and alerts cover the rest.
  • Say the trade-off out loud. The interviewer is buying your judgement, not your recall.
